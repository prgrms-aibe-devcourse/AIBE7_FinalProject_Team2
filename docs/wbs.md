### 2-3. 위험 요소와 대응

| # | 위험 | 영향 | 대응 |
| --- | --- | --- | --- |
| R1 | **대표 판례가 아직 없다.** 조건(자백 · 단일 죄명 · 확정판결 · 양형기준 근거)을 만족하는 판례를 찾지 못한 상태(요구사항 FR-1-9) | 데이터 → 시드 → AI 판결 → 통합 테스트 전체가 막힌다 (**가장 긴 경로**) | D1 ~ D2에 확보 경로를 정한다(유료 열람 또는 조건 완화). 그 전에는 문서 예시 사건을 임시 시드로 쓰고, D5에 실제 사건으로 바꾼다. D2까지 못 정하면 팀 회의로 조건 완화를 결정한다 |
| R2 | 프론트엔드가 API 완성을 기다린다 | 화면 작업이 D4 이후로 몰린다 | API 명세 v0.3의 응답 예시로 **목(mock) 데이터를 만들어 D1부터 화면을 먼저 만든다.** D5에 실제 API로 바꾼다 |
| R3 | 스키마가 늦어지면 모든 백엔드 작업이 막힌다 | 백엔드 전체 지연 | 1.1 스키마를 **D1에 끝내는 최우선 작업**으로 둔다. D2에 스키마 · API 계약을 동결한다 |
| R4 | 팀원 모두 백엔드 담당이라 프론트 숙련도 편차가 있다 | S-04 · S-06 같은 복잡한 화면 지연 | 공통 컴포넌트(진행 표시 · 경고 박스 · 판단 요소 목록)를 3.1에서 먼저 만든다. 화면별 주 담당 외에 보조 담당을 둔다 |
| R5 | AI 판결 오프라인 생성 · 검수에서 목록 밖 요소나 범위 밖 형량이 나온다 | 재생성 반복 | 판단 요소 목록 안에서만 고르도록 지시하는 프롬프트 · 검증 스크립트를 D1 ~ D2에 먼저 만든다 |

### 2-4. 범위 조정안 (위에서부터 줄인다)

| 순위 | 조정 | 줄이는 양 | 영향 |
| --- | --- | --- | --- |
| 1 | 배포(EC2 · Nginx)를 MVP 일정에서 뺀다 (로컬 · 시연 환경만) | 이미 반영 | 확장 단계 첫 작업으로 한다 |
| 2 | 통합 테스트 자동화는 핵심 3개만 한다: 상태 전이, 선고 가능 범위 검증, 비교 분류 (기술 스택 7장) | 0.5 | 나머지 API는 수동 시나리오로 확인 |
| 3 | 반응형은 모바일에서 깨지지 않는 수준만 (390px 전용 레이아웃은 확장, REQ-004와 같음) | 0.5 | 3.8 축소 |
| 4 | S-09 규칙 문장(`ruleSentences`)과 내 판결 요약을 **분류 태그별 1개 틀**로 고정 (API 명세 6장 #4 · #7 제안안 그대로) | 0.5 | 문장 다양성이 줄어든다 |
| 5 | S-01 랜딩을 히어로 + 특징 카드 3개만으로 단순화 | 0.5 | 이미지 영역은 기본 이미지 |
| 6 | S-06에서 사건 기록을 보러 갔다 올 때 입력값을 복원하는 기능(v1.5 결정)을 뺀다 | 0.5 | 돌아오면 빈 폼. 확장에서 다시 넣는다 |
| 7 | 권고 범위 막대를 숫자 표시로 대체 (S-04c · S-05 · S-06) | 0.5 | 시각화는 확장 |

- **1 ~ 4순위를 적용하면 약 1.5인일**, **1 ~ 7순위를 모두 적용하면 약 3인일**이 줄어 추정 작업량이 약 22.5인일이 된다. 실제 용량(약 22.4)과 거의 같으므로, 모자라는 부분은 D7 버퍼로 흡수한다.
- **줄이면 안 되는 것**: 서버의 상태 강제 · 수정 불가 · 선고 가능 범위 검증, 사전 판단은 S-09에서 처음 공개, 실제 판결은 S-08 전 비노출. 서비스의 핵심 규칙이다.

- **API 계약 변경**은 API 명세서(`api-specification.md`)를 먼저 고치고, 해당 화면 담당에게 알린다. D2 이후 변경은 팀 합의가 필요하다.

- **D2 · D4 종료 점검**에서 일정표 대비 늦으면 2-4의 범위 조정안을 순서대로 적용한다.
