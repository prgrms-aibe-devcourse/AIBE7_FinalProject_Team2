## A. 프로젝트 전체 Why–What–How 요약

**Why (문제의식)** — 뉴스·커뮤니티에서 판결을 접할 때 드는 직관("형량이 가볍다", "내가 판사라면")에서 출발했다. 실제 판결은 다양한 양형 요소가 함께 작용해 정해지는데, 사용자는 그 과정을 보지 못한다. 서비스명 자체가 질문이다: "남의 판결을 평가할 때와 내가 직접 판결할 때 같은 기준을 적용하고 있을까?" [`final-planning.md:25,47-57,77`]

차별화 지점은 명확히 문서화돼 있다 — 기존 "국민 양형체험"(대법원 양형위)이 "판사는 이렇게 판단한다"는 정답 확인형이라면, 이 서비스는 "같은 사건 앞에서 나는 어떤 기준으로 판단하는 사람인가"를 비추는 데 초점을 둔다. **"나 vs 법원(정답)"이 아니라 "나 vs 여러 관점"**, **"체험 전후 통계"가 아니라 "개인의 판단 이유가 어떻게 바뀌었는지"**다. [`final-planning.md:59-77`]

**What (MVP 범위, 합의됨)** — 로그인 없이 대표 사건 1건으로 사전 판단 → 단계별 사건 확인 → 직접 판결 → AI 판결 → 실제 판결 → 세 판결 비교까지 **끝까지 동작**하는 체험. REQ 48개, 화면 S-01~S-09·S-14, API 14개. [`mvp-definition.md:33,93-204`]

명시적 제외: 경합범 사건, 무죄 선택지(MVP), "만약에" 조건 변경 시뮬레이션, 판결 전 실제 형량 공개 후 평가하는 방식(앵커링 우려로 검토 후 제외). AI 판결 실시간 파이프라인(RAG/Agent), AI 비교 분석 실시간 생성은 확장 단계로 분리. [`mvp-definition.md:234-258`, `final-planning.md:243-248`]

**How (실행·검증)** — 사용자·AI·재판부 판단을 `judgment` 테이블 하나에 `subject_type`+`timing`으로 통합하고, 판단 요소 평가도 `judgment_factor` 한 테이블로 통일해 비교 매트릭스를 조회 한 번으로 구성한다(DR-1, DR-2). [`erd.md` 22-23줄] 실제 사건 콘텐츠(판결문·형량·판단요소)는 공개 저장소에 올리지 않고 비공개 저장소로 분리하며, 공개 저장소의 설계 문서에는 가상 예시 사건만 쓴다(COMMON-11 결정). AI 판결은 MVP에서 오프라인 생성 → `validate_output.py` 자동 검증 → 사전 학습 오염 점검(`check_contamination.py`) → 사람 검수 → SQL 적재 파이프라인을 거친다. [`tools/ai-judgment/README.md:25-125`] 일정은 7영업일 WBS로 관리하며 "조건부 가능" 판정 하에 범위 조정안을 순위별로 준비해 둔다. [`wbs.md` 2장]

## C. STAR — 실제 기획 경험 (BE-14, 2026-10-02 ~ 10-06 수행)

- **Situation**: WBS 4.3(BE-14)은 대표 사건 실제 판결문에서 판단 요소별 방향·근거 문장(evidence)·발췌(excerpt)·쉬운 설명(plainExplanation)을 사람이 직접 만드는 작업이었다. 선행 작업(BE-17) 담당자가 "결과물을 공개 저장소에 올리면 안 된다"는 제약과 함께 일정·형식·판단요소 번호 확인을 Jira 댓글로 요청해 둔 상태였다. [BE-14 설명, BE-14 댓글 id 10033]
- **Task**: 비공개 저장소 구조를 확인하고, 1심·항소심 판결문 원문을 직접 읽어 ERD(`judgment`/`judgment_factor`) 스키마에 맞는 JSON 산출물을 만들고, Jira 질문에 답한 뒤 비공개 저장소에 브랜치·커밋·PR을 올리는 것.
- **Action**: 비공개 저장소 소스 PDF 2건(1심 2020고합856, 항소심 2021노266)을 직접 읽어 "양형의 이유" 원문에서 요소별 근거 문장을 추출하고, 팀 비식별화 기준(나이 일반화 등)을 적용해 JSON을 작성했다. Jira에 형식(JSON)·일정·display_order 확인 댓글을 남기고, `feature/BE-14-court-judgment` 브랜치 생성 → 커밋 → PR(#6) 생성, Jira를 "진행 중 → 검토 중"으로 전환했다.
- **Result**: 리뷰에서 진료과 비식별화 누락(🟠, 블로커급)과 사소한 지적 3건을 받아 전부 수정 반영했고, 2026-10-06 PR이 머지된 것을 확인한 뒤 Jira를 "완료"로 전환했다. [PR #6]

## D. 네 준비 영역별 주요 결정 예상 답변

### 1. 제품 기획 — "정답 확인"이 아니라 "판단 이유 변화"를 보여주는 비교 구조

**60초 설명**: 세 판결 비교를 사용자·AI·재판부 중 "누가 맞았나"로 설계하지 않고, 사전 판단("구경꾼의 나")에서 최종 판결("판사의 나")까지 **판단 이유가 어떻게 바뀌었는지**를 먼저 보여준 뒤 세 시각을 비교하도록 설계했습니다. 경쟁 서비스가 이미 정답 확인형 체험을 제공하고 있어서, 저희는 서비스 목적 자체인 "내 판단 기준을 돌아보게 하는 것"에 맞춰 차별화했습니다. 이 구조는 요구사항 FR-6-6과 ERD의 judgment/judgment_factor 통합 스키마로 구현 중이며, 화면(S-09)은 현재 코드 리뷰 단계입니다.

**근거**: `final-planning.md:59-77`(차별화), `requirements-specification.md` FR-6-6, `erd.md` DR-1/DR-2.

**확정 (2026-10-06 회의)**: `mvp-definition.md:333`의 "내 판결" 한 줄 요약 틀은 **판단 요소 태그화** 방식으로 확정했다. 각 판단 요소를 짧은 태그로 변환한 뒤 "{태그} 을(를) 무겁게/가볍게 본 판단" 틀에 넣는다. 예: 판단 요소 "다투던 중 집에 있던 흉기를 집어 들었다" → 태그 "흉기 사용" → 요약 "흉기 사용 을(를) 무겁게 본 판단".

### 2. 데이터·콘텐츠 — 실제 판결문 비식별화와 공개/비공개 저장소 분리

**60초 설명**: 실제 사건 원문·형량·판단 요소는 비공개 저장소에서만 관리하고, 공개 저장소의 설계 문서에는 가상 예시 사건만 둡니다. 저장소가 공개라 실제 개인정보·사건 특정 정보가 노출되면 안 되기 때문입니다. COMMON-11에서 예시 사건을 가상 사건으로 교체했고, BE-17에서 비공개 저장소를 서브모듈로 연결하는 방식을 확정했습니다. 실제로 BE-14를 진행하면서 코드 리뷰에서 "진료과" 같은 비식별화 누락을 지적받아 바로 수정한 사례가 있어서, 이 원칙이 실제로 작동하는 걸 확인했습니다.

**근거**: COMMON-11 결정, BE-17 댓글(id 10014), `cases/README.md`, PR#6 리뷰.

**확정 (2026-10-06 회의)**: 비공개 저장소 CI 도입은 **보류**하기로 했다. 실제 사건 데이터는 자동 검사만으로 비식별화 품질을 보장하기 어렵고 사람의 직접 검수가 반드시 필요하다고 판단했기 때문이다. E-2 항목은 "보완 필요"가 아니라 "보류 결정"으로 정리한다.

### 3. 범위·일정 관리 — "조건부 가능" 판정과 사전 범위 조정안

**60초 설명**: 7영업일 동안 추정 작업량(25.5인일)이 실제 가용 용량(약 22.4인일)보다 많다고 판단해서 "조건부 가능"으로 결론 냈고, 미리 순위를 매긴 범위 조정안(배포 제외, 통합 테스트 축소 등)을 준비해 뒀습니다. 4명 전원이 백엔드 중심이라 프론트엔드·데이터 작업을 사용자 흐름 순서로 4등분했습니다. 현재 Jira 기준 전체 53개 이슈 중 39개(74%)가 완료, 5개가 검토 중, 5개가 할 일로 남아 있습니다.

**근거**: `wbs.md` 2장(가능성 점검), Jira 전체 현황(BE 25/FE 14/COMMON 14, 완료 39).

**미확정**: 세 판결 비교 API(BE-11)가 아직 "할 일" 상태라, WBS D4 마일스톤(M2: 백엔드 API 1~14 완료)이 실제로 끝났는지는 재확인이 필요합니다.

### 4. 기술 설계 — AI 판결의 오프라인 생성·검증 파이프라인

**60초 설명**: MVP에서는 서비스 안에서 LLM을 실시간으로 호출하지 않고, 오프라인에서 AI 판결을 생성한 뒤 자동 검증 스크립트와 사전 학습 오염 점검을 거쳐, 사람이 검수하고 나서 DB에 적재합니다. 2주라는 기간에 실시간 RAG까지 넣으면 범위가 과다하고, AI가 사건을 미리 알고 있으면 검증 자체가 무의미해지기 때문입니다. 실제로 여러 모델을 반복 점검해서 모두 "CLEAN"(오염 없음) 판정을 확인했습니다.

**근거**: `mvp-definition.md`(AI 판결 MVP 정의), `tools/ai-judgment/README.md`, `long-marriage-conflict-v4.md` 8장(자가 리뷰).

**확정 (2026-10-06 회의)**: 최종 생성 모델은 **Gemini 3.7 Flash `run1`(사고 수준 medium)**으로 확정했다. 유사 판례(`references.similarCases`)는 MVP 범위에 넣지 않고, MVP 이후 RAG·VectorStore 구현 단계에서 처리하기로 했다.

### 2. 비공개 저장소 CI 부재 — **보류 확정 (2026-10-06 회의)**
