## 1. 서비스 개요

**서비스명**: 내Law남불

**한 줄 소개**: 사용자가 직접 판결을 내려보고 AI·실제 판결과 비교하면서, 판결이 왜 그렇게 내려졌는지를 스스로 생각해보게 하는 체험형 서비스.

**포지셔닝 (v5 신규)**: 국민 양형체험이 "판사는 이렇게 판단한다"를 알려 준다면, 내Law남불은 **"같은 사건 앞에서 나는 어떤 기준으로 판단하는 사람인가"**를 비춰 준다.

| 축 | 국민 양형체험 | 내Law남불 |
| --- | --- | --- |
| 핵심 질문 | 당신이 판사라면 몇 년을 선고하겠습니까? | 다 알고 나서도 같은 판단일까? |
| 출발점 | 사건 (절차 체험) | 판결을 볼 때 드는 내 반응 |
| 주인공 | 양형 절차와 양형기준 | 사용자의 판단 기준 |
| 비교 구도 | 나 vs 법원 (정답 확인) | 나 vs 여러 관점 (AI, 재판부, 이후 배심원·참여자) |
| 남는 것 | 판사는 이렇게 판단하는구나 | 나는 이런 걸 무겁게 보는구나 |
| 변화의 해석 | 체험 전·후 형량 분포 통계 | 개인의 판단 이유가 어떻게 바뀌었는지 |

**기획 배경**: 뉴스나 커뮤니티에서 판결을 접할 때 드는 직관("형량이 너무 가벼운 것 아닌가?", "나라면 어떤 판결을 내렸을까?", "판사를 AI로 바꾸면 다르지 않을까?")에서 출발한다. 실제 판결은 법정형 하나만으로 정해지지 않고 사실관계·피해 정도·피고인 상황·양측 주장·법정형·양형기준·양형 요소가 함께 고려된다. 내Law남불은 이 직관에서 한 단계 더 나아가, 사용자가 직접 사건을 검토하고 판결을 내리고 그 판결이 왜 그렇게 내려졌는지 생각해보는 경험을 제공한다.

**서비스 목적**: 사용자가 판사의 입장에서 실제 사건을 검토하고 판결을 내린 뒤, 자신의 판결을 AI 판결·실제 판결과 비교하도록 한다. 특정 판결의 정답을 제시하는 것이 아니라, 나는 어떤 요소를 중요하게 생각했는지·AI는 어떤 근거로 판단했는지·실제 재판부는 어떤 요소를 고려했는지·같은 사건에서 왜 다른 결과가 나왔는지를 사용자가 직접 확인하고 생각해보게 하는 것이 목표다.

**프로젝트 방향 요약**: 내Law남불은 AI에게 판결의 정답을 묻는 서비스가 아니다. 사용자가 실제 사건을 직접 살펴보고 자신의 판단을 내린 뒤, AI와 실제 재판부가 같은 사건을 어떻게 바라봤는지 비교하는 서비스다. 최종 목표는 "누가 맞는가"를 결정하는 것이 아니라 "같은 사건을 보고도 왜 서로 다른 판단이 나왔는가"를 사용자가 직접 확인하고 생각해볼 수 있도록 하는 것이다. 이 주제의식이 화면 전반(카피, 정보 구성, 결과 화면 톤)에서 분명히 드러나도록 하는 것을 UI/UX(11장)에서도 함께 챙긴다.

## 2. 핵심 사용자 경험 및 전체 흐름 (v5.2 갱신)

1. **랜딩/홈 (S-01)** — 서비스 목적·핵심 경험 소개. "당신이 판사라면 어떤 판결을 내리겠습니까?" 메시지 중심. 사용자는 사건 체험을 시작하거나 사건 목록으로 이동한다.
2. **사건 선택 (S-02)** — 사건 목록에서 판결해보고 싶은 사건 선택. 그리드 카드형으로 확정.
3. **사건 개요 확인 (S-03)** — 죄명, 범죄 유형, 사건에 대한 간략한 설명을 뉴스 기사 수준으로 먼저 확인.
4. **사전 판단 — 구경꾼의 나 (S-03)** — 개요만 본 상태에서 형량 구간을 선택한다(FR-2-8). 개요와 사전 판단은 상세 사실관계 이전의 **별도 화면**이며, **제출 후에는 수정할 수 없다**(FR-2-10).
5. **사건 정보 확인 (S-04)** — 상세 사실관계, 양측 주장, 법률·양형기준을 아코디언 누적 공개 방식으로 단계적으로 확인. 사전 판단 결과는 이 화면에 표시하지 않는다.
6. **최종 정리 (S-05)** — 지금까지 확인한 사건 정보를 한 화면에서 다시 검토.
7. **사용자 판결 — 판사의 나 (S-06)** — 형벌·형량을 입력하고, 판단 요소 목록에서 중요하게 고려한 요소와 방향을 선택. **확정 후에는 수정할 수 없다**(FR-3-9).
8. **AI 판결 확인 (S-07)** — 사전에 생성된 AI의 판결과 주요 판단 근거를 확인.
9. **실제 판결 확인 (S-08)** — 실제 법원의 판결 결과와 주요 판단 근거를 확인.
10. **세 판결 비교 및 판단 차이 분석 (S-09)** — 사용자·AI·실제 판결의 형량과 판단 요소를 비교하고, 사전 판단에서 최종 판결까지 **판단 이유가 어떻게 바뀌었는지**도 함께 확인한다(FR-6-6). 사전 판단은 이 화면에서 처음 다시 보여 준다.

> 이전 버전 문서에서는 "세 판결 비교"와 "판단 차이 분석"을 8·9단계로 분리했으나, 기획서 v2의 전체 사용자 흐름에서는 하나의 단계(10단계)로 통합되어 있다. 화면 설계 시 두 내용을 한 화면(또는 같은 화면의 하위 섹션)으로 묶는 것을 기준으로 한다.
>

> **(v5 결정)** 실제 판결은 9단계 전까지 어떤 형태로도 노출하지 않는다. 처음에 실제 형량을 보여 주고 평가하게 하는 방식, 실제 판결 공개 후 재판부 판결을 평가하게 하는 방식은 검토 후 제외했다(앵커링으로 독립 판단이 무너지거나, 새로운 정보를 만들지 못함).
>

> **(v5.2)** 화면 목록, 이동 규칙, 진입 조건, 체험 진행 상태는 정보 구조도(`information-architecture.md`)를 기준으로 한다.

## 3. MVP 목표

초기 약 2주 동안, 사용자가 하나의 실제 사건을 선택해 검토하고 직접 판결을 내려 AI·실제 판결과 비교하기까지의 전체 체험 흐름을 완성하는 것을 우선 목표로 한다. 기능 개발 초기에는 대표 판례 1건으로 전체 흐름을 검증하고, 이후 MVP 단계에서 최소한의 사건 콘텐츠를 추가한 뒤 점진적으로 확대한다.

> **(회의 결정, 기획서 v2)** 2주 동안의 구현 범위는 현재 기획대로 유지하되, 팀이 학습하며 구현하는 과정에서 진행 상황에 따라 기능을 유동적으로 덜어내거나 더해가는 방식으로 운영한다. 회의에서는 "2주 내에 Must Have 13개 항목 + 에이전트 4개 + RAG 저장소 3종 + 권고 형량 계산 로직 + 실시간 AI 비교 분석"이 범위상 과다할 수 있다는 우려가 제기되었고, 이에 따라 Agent 1 제외(7장) 등으로 실질 범위를 일부 축소했다. "세 판결 비교" 단계에서 AI가 생성하는 공통점·차이점 분석(FR-6-3, 확장)은 **체험별로 실시간 생성**하기로 확정했다(v5.3, FR-6-3 참고).
>

**MVP를 통해 검증하고 싶은 것 (회의 논의)**: 이번 MVP의 핵심은 완성된 RAG 시스템 자체가 아니라, "사용자가 판결을 내리고 AI·실제 판결과 비교하며 판단 차이를 스스로 확인한다"는 핵심 경험이 실제로 유의미하게 동작하는지 검증하는 데 있다. 이에 따라 MVP의 AI 판결은 오프라인에서 생성 · 검수한 결과를 적재하고, 서비스 안의 AI 판결 파이프라인(확장 단계)은 **RAG(Vector Store 검색)를 기본으로** 구현하되, 판례 수가 적거나 검색 품질이 부족해 **RAG를 적용할 수 없으면** 사건 관련 자료(유사 판례 후보, 양형기준 조문 등)를 프롬프트에 직접 넣는 퓨샷 방식으로 대체한다(v5.5, 7장 참고). 서비스 주제 자체에 무게가 실려 있는 만큼, 기능 구현 못지않게 "같은 사건을 보고도 왜 판단이 달라지는가"라는 주제의식이 화면과 문구에 잘 드러나도록 하는 것이 중요하다.

> **(v5 추가) 범위 축소 기준**: 기능 명세의 우선순위를 줄일 때는 "사용자가 자신의 판단 기준을 비춰 보는 데 필요한가"를 기준으로 삼는다.
>

## 4. 사건 제공

### 기능 목적

사용자가 판결 체험을 진행할 실제 사건을 선택할 수 있도록 한다.

### 사용자 흐름

사건 목록 확인 → 사건 선택 → 사건 체험 시작

### 요구사항

- **FR-1-1 (원본 유지)** 실제 판결문이 존재하는 판례만 사용한다. 인명·지명 등 사건을 특정할 수 있는 정보는 비식별화하되, 범행 내용·피해 정도·주요 쟁점·전과·반성 관련 사실·합의 및 피해 회복 여부·범행 횟수·피해 금액·범행 기간 등 양형에 영향을 미치는 핵심 사실관계는 원 사건과 동일하게 유지한다. 필요할 경우 정보 항목을 변경 가능/변경 금지로 구분하는 가공 기준을 별도로 정의해 태깅한다.
- **FR-1-2 (범죄 유형)** 최종적으로 **살인·사기·상해** 3개 유형을 포함하도록 콘텐츠를 확장하는 것을 목표로 한다. 유형별 최소 10건 확보를 목표로 하며, 일반적 사례·상대적으로 높은/낮은 형량 사례·주요 양형 요소가 크게 작용한 사례·사회적·법적 쟁점이 있는 사례 등 다양하게 구성한다. (와이어프레임 v2에서 상해 기준으로 교체 완료)
- **FR-1-3 (사건 선정 원칙, 기획서 v2로 확정)** 대표 판례 1건을 먼저 선정해 서비스 흐름에 필요한 정보를 추출하고 데이터 구조 초안을 작성한 뒤, 동일 유형의 추가 판례를 적용해 공통 요소와 사건별 선택 요소를 구분, 범죄 유형별 최종 데이터 구조를 확정한다. 이때 다음 조건을 만족하는 사건만 사용한다.
  - **확정된 판결**이 있는 사건만 사용한다(기준 판결의 정의는 FR-5-4 참고).
  - **단일 범행 사건만** 사용한다. 여러 죄명이 결합된 사건뿐 아니라 같은 죄를 여러 번 저지른 **동종 경합범**(예: 피해자 여러 명 반복 사기)도 서비스 대상에서 제외한다(v5.5, REQ-081). 경합범 가중이 선고 가능 범위를 바꾸기 때문이다.
  - 초기 MVP에서는 **현행 양형기준이 적용되는 사건**을 우선 선정한다. 과거 양형기준이 적용된 사건은 이후 확장 단계에서 다룬다(FR-3-5-1, FR-4-3 참고).
  - 개발 단계는 대표 판례 1건 → 초기 MVP 최소 콘텐츠 → 핵심 기능 안정화 이후 확대 순으로 진행한다. **초기 MVP 최소 콘텐츠를 "하나의 범죄 유형에 N개 사건"으로 구성할지, "N개 유형에 각 1개 사건"으로 구성할지는 아직 결정되지 않았다.**
- **FR-1-4 (목록 화면 필수 정보, 원본 유지)** 사건 제목, 범죄 유형, 짧은 사건 소개를 필수로 제공한다.
- **FR-1-5 (목록 화면 선택 정보)** 사건 키워드, 난이도, 예상 소요시간, 그리고 사건 선택을 돕는 기타 정보(참여자 수, 좋아요, 댓글 수, 별점 등)를 제공한다. **사건 키워드는 사실 정보 나열보다 사건의 "느낌" 위주로 표현한다**(기획서 v2 반영). 사용자의 판단에 영향을 주지 않도록 중립적인 표현은 유지한다. (와이어프레임 v2에서 중립 키워드로 교체 완료)
  - **(v5.5) 카드 이미지 · 범죄 분류명**: 사건 카드 이미지는 사건별 이미지 경로(ERD `legal_case.thumbnail_url`, 없으면 범죄 유형별 기본 이미지)로, 죄명 옆 범죄 분류명(예: "사기 / 재산범죄")은 범죄 유형별 코드 상수로 제공한다(API `crimeCategoryLabel`).
- **FR-1-6 (진행 상태 배지 — 범위 주의, 12장 참고)** 사용자별 체험 상태(미체험/진행 중/완료)를 목록 카드에 배지로 표시하고, 진행 중인 사건은 "이어서 하기", 완료된 사건은 "결과 다시 보기"로 분기한다. 배지 표시는 확장 단계(REQ-010)이며, 와이어프레임 v2 S-02에는 배지가 없다. 단, **분기 자체는 MVP**다(v5.3): 배지가 없어도 `체험 시작`을 누르면 진행 중인 사건은 현재 단계로, 완료한 사건은 S-09로 이동한다(REQ-011, 012, 16장 DR-6).

  > **(v5.2)** 배지가 없는 MVP에서도, 이미 체험을 시작한 사건의 `체험 시작`을 누르면 새 체험을 만들지 않고 현재 진행 단계의 화면으로 이동한다. 완료한 사건이면 S-09로 이동한다(IA 6장, ERD 7장).
>
- **FR-1-7 (필터·정렬, 원본 유지)** 범죄 유형, 난이도, 소요 시간, 내 체험 상태 기준 필터와 정렬(최신순/난이도순 등)을 제공한다. S-02는 범죄 유형 칩만 MVP이고, 나머지 필터·정렬은 이후 단계(REQ-008, 009).
- **FR-1-8 (UI 시안 — v5.1 확정)** 사건 목록은 **그리드 카드형(S-02, v1: 1b)으로 확정**한다.
- **FR-1-9 (데이터 출처)** 실제 판례 데이터는 공공데이터포털, 국가법령정보 공동활용 API(law.go.kr), 기타 합법적으로 이용 가능한 공개 판례 데이터를 확보 경로로 검토한다.

  > ⚠️ **실제 조사 결과 반영**: 대표 판례 후보 조사 결과(노션 보관)에 따르면 law.go.kr(국가법령정보 공동활용 API)에 공개된 하급심 형사판결 중, 상해·사기 유형에서 필수 조건(자백·단일 죄명·확정판결·양형기준 적용 근거 명시 등)을 모두 만족하는 사건을 아직 찾지 못했다. 공개된 하급심 판결은 선별 게재되어 법리 다툼(무죄 주장, 파기) 사건 비중이 높고, "양형기준의 적용" 항목이 기재된 사건 자체가 드물다. 다음 두 가지 대응 방향이 제안되어 있다: ① 사법정보공개포털 판결서 인터넷열람(유료, 로그인 필요)에서 형사 단독 사건을 직접 검색, ② 판결문에 권고형 범위 기재가 없어도 우리가 양형기준으로 직접 계산하는 방식으로 조건 완화. 최종 채택 경로 확정이 필요하다.
>

### 보류 사항

- 초기 MVP 최소 콘텐츠 구성 방식: 단일 유형 N개 사건 vs. N개 유형 1개씩.
- 판례 데이터 확보 경로 최종 확정(공공데이터포털/law.go.kr로 조건을 만족하는 사건을 찾지 못한 상태 — 유료 열람 서비스 활용 또는 조건 완화 검토).
- 진행 상태 배지 기능을 확장 단계에서 넣을 때 S-02 카드 내 배지 위치.
- 과거 양형기준 적용 사건 확장 시, 양형위원회 공개 과거 양형기준 확보 방법(FR-4-3 참고).

## 5. 사건 정보 확인

### 기능 목적

사용자가 직접 판결을 내릴 수 있도록 필요한 사건 정보를 제공한다. 또한 상세 정보와 법적 기준을 확인하기 전에, 뉴스로 사건을 접한 사람처럼 개요만 보고 먼저 판단하게 하여(사전 판단, "구경꾼의 나"), 이후 모든 정보를 확인하고 내린 최종 판결("판사의 나")과 **판단 이유가 어떻게 달라졌는지** 확인할 수 있도록 한다.

### 사용자 흐름

사건 개요 확인 → 사전 판단(형량 구간, 확장: 작용 요소) → 세부 사실관계 확인 → 양측 주장 확인 → 법률·양형기준 확인 → 판결 전 최종 정리

### 요구사항

- **FR-2-1 (필수 제공 정보, 원본 유지)** 죄명 및 범죄 유형, 사건 개요, 주요 사실관계, 피해 결과, 양형 판단에 필요한 사실(피고인 관련 주요 사실, 합의·피해 회복), 검사 측 주장, 피고인·변호인 측 주장, 적용 법률, 법정형, 양형기준, 법률 및 양형기준 상세 설명을 제공한다(MVP는 권고 범위 산출 근거와 사건별 주요 용어 설명을 S-04 ④에 표시, REQ-024 · 035). (선택 제공: 관련 판례 — 추후 AI Q&A 챗봇 방식 추가 제공을 검토한다.)
- **FR-2-2 (정보 구조 — 병합 규칙 추가, 기획서 v2 반영)** 1) 사건 개요 2) 사건 상세 정보 3) 양측 주장 4) 법률 및 양형 기준 5) 관련 판례(선택)의 5개 그룹으로 구분한다. **1심과 항소심의 형량이 다른 사건은, 항소심에서 새로 드러난 사정(합의 성립, 피해 회복 등)까지 포함해 1심·항소심 두 판결문을 합친 내용으로 사건 정보를 구성한다.** (기준 판결 정의는 FR-5-4 참고.)
- **FR-2-3 (피해 결과 표시 스펙)** 피해자 수, 피해 금액 합계, 범행 기간, 회복 금액을 숫자 요약 카드 4칸으로 제공한다(S-04a).
- **FR-2-4 (단계적 제공, 원본 유지)** 사건 개요 → 사전 판단 → 사건 상세 정보 → 양측 주장 → 법률 및 양형기준 → 판결 전 최종 정리 순으로 제공한다. 현재 단계를 확인하지 않으면 다음 단계 정보를 확인할 수 없도록 하며, 이 순서는 서버가 강제한다(잠긴 섹션 본문은 응답하지 않음, REQ-019 · 16장 DR-6).
- **FR-2-5 (판결 전 최종 정리 화면)** 사건 개요, 핵심 사실 요약, 양측 주장(2단 카드), 적용 법률·법정형·선고할 수 있는 범위, 양형기준 권고 범위(시각화 막대 + 산출 근거)를 한 화면에서 재검토할 수 있도록 제공하고, "전체 기록 다시 보기"와 "판결 내리러 가기"로 분기한다(S-05).
- **FR-2-6 (내 메모)** 정보 확인 단계에서 사용자가 자유롭게 메모를 작성할 수 있는 입력창을 제공한다. 기능 명세서 기준으로 이후 단계(REQ-027)이며, 와이어프레임 v2의 MVP 화면에는 넣지 않는다.
- **FR-2-7 (화면 구성 — v5.2 확정)**
  - **사건 개요 + 사전 판단은 상세 사실관계 이전의 별도 화면(S-03)으로 둔다.**
  - 사건 정보 확인(S-04)은 **아코디언 누적 공개형**으로, 섹션은 ① 사건 개요(다시 보기용, 접힘) ② 상세 사실관계 ③ 양측 주장 ④ 법률·양형기준이다.
  - 이전 섹션은 접힌 상태로 남아 언제든 다시 펼쳐 볼 수 있다. 확인하지 않은 다음 섹션은 "잠김 · 이전 단계 확인 후 열립니다"로 표시하고, "읽었습니다 · 다음 단계 열기" 버튼으로 연다.
  - **S-04에는 사전 판단 결과를 표시하지 않는다.** 사이드바 진행 상황에 "사건 개요 · 사전 판단" 완료 표시만 둔다. 상세 정보를 보는 동안 자신의 사전 판단을 계속 보면 최종 판결이 영향을 받을 수 있기 때문이다.
  - 진행 표시는 6단계: 1 사건 개요 · 사전 판단(S-03) / 2 상세 사실관계 / 3 양측 주장 / 4 법률·양형기준(S-04) / 5 판결 전 최종 정리(S-05) / 6 판결(S-06). 상단 "N / 6"은 S-03 ~ S-05에, 진행 사이드바는 S-03 · S-04에 둔다. **S-06에는 진행 표시가 없다**(사이드바는 참고 정보, FR-3-6).
- **FR-2-8 (사전 판단 — "구경꾼의 나", v5 재정의)** 사건 개요를 확인한 직후, 사용자가 뉴스로 이 사건을 접했을 때처럼 현재까지 제공된 정보만으로 먼저 판단하도록 한다(S-03).
  - **안내 문구 (필수)**: 판단 전에 정보가 일부라는 사실을 알린다. 예: "지금은 뉴스에서 볼 수 있는 정도의 정보만 있어요. 기사로 이 사건을 접했다고 생각하고 판단해 보세요."
  - **형량 구간 선택 (필수)**: 여러 형량 범위 선택지 중 하나를 고르는 객관식. MVP 선택지(7개): 벌금형 / 징역형 집행유예 / 실형 3년 미만 / 실형 3년 이상~5년 미만 / 실형 5년 이상~10년 미만 / 실형 10년 이상~20년 미만 / 실형 20년 이상. 범죄 유형별 세부 조정은 추후 정의한다(ERD `sentence_range_option`).
  - **작용 요소 선택 (확장 단계)**: "지금 가장 크게 작용한 것"을 1~2개 고른다. 선택지는 사건별 판단 요소 목록(FR-3-4) 중 **공개 단계가 개요(`OVERVIEW`)인 요소만**, 2~3개로 제한한다. 방향(↑/↓)은 받지 않는다.
  - 사전 판단은 최종 판결(6장)과 별도의 기록(같은 판단 테이블, 시점 `PRE`)으로 저장한다. 작용 요소는 판단 요소 기록에 시점 `PRE`로 저장한다(16장).
  - 사전 판단은 세 판결(사용자·AI·실제) 중 하나로 취급하지 않는다. **S-09 비교 화면 최상단에서 처음 다시 보여 준다**(FR-6-6). S-04 ~ S-08에는 표시하지 않는다.
  - **(v5 결정) 실제 판결은 노출하지 않는다.** 실제 형량을 먼저 보여 주고 "가볍다/적절하다/무겁다"로 평가하게 하는 방식은 앵커링 때문에 제외했다.
- **FR-2-9 (사건 개요 작성 원칙, v5 신규)** 사전 판단의 근거가 되는 사건 개요는 실제 기사 수준의 정보를 **중립적인 표현**으로 작성한다. 분노나 동정을 유발하는 사실만 골라 보여 주지 않는다. 판단 요소 목록의 중립 표현 원칙(FR-3-4)을 개요 작성에도 동일하게 적용한다. 목적은 사용자가 나중에 "몰랐구나"를 느끼게 하는 것이지 "속았다"를 느끼게 하는 것이 아니다.
- **FR-2-10 (사전 판단 수정 불가, v5.2 신규)** 사전 판단은 **제출 후 어떤 경로로도 수정할 수 없다.**
  - 제출 버튼 앞에 "제출하면 이 판단은 바꿀 수 없어요."를 표시한다.
  - 제출 후 뒤로 가기, 새로고침, URL 직접 입력으로 S-03에 들어오면 현재 상태의 화면(IA 9장 "보낼 화면")으로 이동한다.
  - 이 규칙은 화면이 아니라 서버에서 강제한다(16장 DR-6).
- **FR-2-11 (진행 상태 유지, v5.2 신규)** S-04에서 확인한 섹션은 서버에 기록해, 새로고침·재접속 후에도 확인한 섹션과 다음에 확인할 섹션(`lastReviewedStep + 1`)까지 펼쳐진 상태로 복원한다(16장 DR-6, API 6 `openStep`).

## 6. 사용자 판결

### 기능 목적

사용자가 직접 판사의 입장에서 사건의 형벌과 형량을 결정할 수 있도록 한다.

### 사용자 흐름

사건 검토 → 판결 선택/입력 → 판결 확정

### 요구사항

- **FR-3-1 (형벌 입력, 원본 유지)** 해당 사건에서 가능한 형벌(예: 징역 년·개월, 벌금 금액, 필요 시 집행유예 여부·기간)만 선택 가능하도록 노출한다. 사건별로 필요하지 않은 판결 선택지는 노출하지 않는다. **무죄는 MVP 선택지에서 제외한다**(v5.5). 도입 여부와 입력 처리 규칙은 추후 검토한다(15장).
- **FR-3-2 (권고 범위 제공 여부, 회의 결론으로 확정)** 0 ~ 선고 가능 상한 구간의 막대(라벨: "0" ~ "**선고할 수 있는 상한** N년", v5.5 확정. 와이어프레임 v2.1의 "법정형 상한 10년" 라벨은 고칠 예정)에 양형기준 권고 범위를 음영으로, 사용자가 입력한 형량을 마커로 표시하고 "권고 범위는 정답이 아니라 참고 기준"이라는 안내를 상시 노출한다. 권고 형량 범위는 **판단을 한정하는 기준이 아니라 가이드라인으로서 필요**하다고 판단해, 현재와 같이 **판결 전에 제공**하는 것으로 확정한다. 추후 난이도를 높이는 모드에서 권고 범위를 비공개하는 방향은 Could Have로 검토한다(12장).

  > **(v5 재검토 제기)** 판결 전에 권고 범위를 보여 주면 사용자·AI·실제 판결이 모두 권고 범위로 모여 비교할 차이가 줄어들 수 있다는 의견이 있다. 대안: 판결 전에는 법정형만 제공하고 권고 범위·산출 근거는 공개 단계에서 기준선으로 제공 / 권고 범위를 "참고 보기" 뒤에 두고 열람 여부를 기록. 화면 순서 문제라 데이터 구조에는 영향이 없다(15장).
>
- **FR-3-3 (범위 이탈 처리 — v5.2 확정)** 입력한 형량이 어느 범위에 있는지에 따라 다르게 처리한다.


    | 구분 | 조건 | 처리 | 화면 | 단계 |
    | --- | --- | --- | --- | --- |
    | 범위 안 | 권고 범위 안 | 참고 박스 "입력한 형량은 권고 범위 안에 있습니다." | S-06a | MVP |
    | ① 권고 범위 이탈 | 선고 가능 범위 안, 권고 범위 밖 | 경고 박스 "권고 형량 범위를 벗어났습니다." — **확정은 가능** | S-06b | 확장 |
    | ② 선고 가능 범위 이탈 | 선고 가능 범위 밖 | 경고 박스 "선고할 수 있는 범위를 벗어났습니다." — **확정 불가** (확정 버튼 비활성 + 서버에서 저장 거절) | S-06c | MVP |
    - **선고 가능 범위**: 판사는 법이 정한 범위(처단형) 밖에서 선고할 수 없으므로, 사용자도 그 범위 밖으로는 판결을 확정할 수 없다. 기준은 법정형이 아니라 **선고할 수 있는 가장 넓은 범위**로 한다.
        - 하한: 법정형 하한에 사실관계로 인정되는 법률상 감경(자수 · 심신미약 등)과 작량감경(재판상 감경, 형법 제53조)을 모두 적용한 값
        - 상한: 법정형 상한. 누범처럼 사실관계로 정해지는 가중이 있으면 반영한 값
        - 재판부가 실제로 감경했는지와 관계없이 가장 넓은 범위를 쓴다. 판결 전에 재판부의 감경 여부가 드러나지 않게 하고, 나중에 가중·감경 로직을 붙이기 쉽게 하기 위해서다.
        - MVP는 팀이 판결문·법조문·양형기준을 확인해 계산한 값을 사건마다 입력한다(ERD `penalty_rule`). 자동 계산은 확장 단계.
    - **화면 안내**: 법정형과 선고 가능 범위가 다르면 둘을 함께 표시한다. 예: "법정형: 10년 이하 징역 또는 2천만 원 이하 벌금 / 선고할 수 있는 범위: 징역 1개월 ~ 10년" (와이어프레임 v2.1 예시 사건). 법정형 하한이 있는 경우의 예: "법정형: 1년 이상 10년 이하 징역 / 선고할 수 있는 범위: 6개월 ~ 10년" (법률상 감경 사유 없이 작량감경만 적용)
    - **경고 UI**: S-06(v1: 1g) 화면 안, 형량 입력 영역 바로 아래에 1h의 경고 박스(레드 테두리 + 연한 레드 배경, "!" 아이콘, 제목 + 본문)를 배치한다. ①의 본문은 "판단 요소나 추가 판단 이유에 그렇게 판단한 이유를 남겨 주세요."로 한다. 사유 입력 강제 여부는 미정(15장).
- **FR-3-4 (판단 요소 — 공통 분류 체계 확정, v5 보강)** 사용자는 판결을 내릴 때 자신이 중요하게 고려한 판단 요소를 **사건별 판단 요소 목록**에서 선택한다.
  - 판단 요소 목록은 사건별 주요 사실관계를 기반으로 팀이 미리 만들고, 중립적인 표현으로 제공한다.
  - **사용자·AI·실제 판결은 모두 같은 판단 요소 목록을 사용한다.** 이를 통해 세 판결의 판단 요소를 같은 기준으로 비교한다(7·8·9장과 데이터 구조를 공유).
  - 복수 선택이 가능하며, 각 요소가 형량을 높이는/낮추는 방향인지 표시한다.
  - 목록에 없는 판결 이유는 자유 의견으로 **별도** 입력할 수 있다(공통 목록에는 포함되지 않으며 비교 대상에서도 제외, 확장 단계).
  - **(v5 신규) 공개 단계**: 각 판단 요소에 사용자가 그 사실을 처음 알게 되는 단계(`OVERVIEW` / `DETAIL` / `ARGUMENT` / `LAW`)를 사건 등록 시 팀이 표시한다. 사전 판단의 선택지 필터링(FR-2-8)과 판단 이유 변화 유형 구분(FR-6-6)에 사용한다.
  - **기록 형식**: 판단 요소 기록은 모든 주체가 같은 형식을 따른다 — 주체(`USER` / `AI` / `COURT`), 시점(`PRE` / `FINAL`), 요소, 방향(↑/↓). 시점 `PRE`는 사용자에게만 있고 방향이 없다. **고려하지 않은 요소는 기록하지 않는다**(기록이 없으면 "—"로 표시, ERD 결정 #1).
- **FR-3-5 (양형 기준 활용)** 법정형은 법적으로 가능한 처벌 범위 확인용, 양형기준은 구체적 형량 판단의 참고 기준으로 제공한다. 권고 형량 범위는 공식 양형기준에 따라 계산한 참고 범위로 산출 근거를 함께 설명한다. 사용자가 선택한 판단 요소는 권고 범위 계산에는 사용하지 않는다.
  - **FR-3-5-1 (양형기준 버전 관리, 기획서 v2 신규)** 양형기준과 권고 형량 범위는 **사건이 발생한 시점의 양형기준**을 적용한다. MVP에서는 현행 양형기준이 적용되는 사건을 사용하고, 이후 과거 사건을 추가할 때는 양형위원회에서 공개하는 과거 양형기준을 확보해 적용한다. 판례마다 적용 양형기준의 버전(시행일)을 데이터 필드로 관리해야 한다.
- **FR-3-6 (참고 정보 상시 노출)** 판결 입력 화면 사이드바에 법정형(선고 가능 범위 포함), 권고 범위, 산출 근거, 사건 기록 바로가기를 상시 노출한다(S-06).
- **FR-3-7 (임시 저장 — 이후 단계)** 판결 확정 전 입력 내용을 임시 저장할 수 있어야 한다. 기능 명세서 기준 이후 단계(REQ-039)이며, MVP에서는 판결 입력 중 새로고침하면 입력값이 유지되지 않는다(진행 단계는 유지).
  - **(v5.4)** S-06에서 사건 기록을 보러 S-04로 갔다 돌아오면, 화면이 입력값을 브라우저 메모리에 기억했다가 복원한다. 서버에는 저장하지 않는다.
- **FR-3-8 (UI 시안 — 회의 결정)** 형벌·형량·판단 요소를 한 화면에서 입력하는 통합형(S-06, v1: 1g)을 채택한다. 3스텝 분할형(v1: 1h)은 채택하지 않되 경고 박스 UI만 차용한다(FR-3-3).
- **FR-3-9 (판결 확정 및 수정 불가, v5.2 신규)**
  - `판결 확정하기`를 누르면 화면 안 확인 박스(모달 아님)를 보여 준다: "확정하면 판결을 바꿀 수 없고, AI 판결과 실제 판결이 차례로 공개돼요." / `다시 검토하기` · `확정하기` (S-06d)

## 7. AI 판결

### 기능 목적

사용자와 동일한 사건을 바탕으로 AI가 독립적으로 판결을 내리고, 이후 사용자 및 실제 판결과 비교할 수 있도록 한다.

### 요구사항

- **FR-4-1 (AI 제공/제외 정보 — 기획서 v2로 항목 추가)** AI에는 사용자가 판결 과정에서 확인한 것과 동일한 수준의 정보(죄명·범죄유형, 사건 개요, 주요 사실관계, 피해 결과, 피고인 관련 사실, 합의·피해 회복 정보, 검사 측 주장, 피고인·변호인 측 주장)를 제공한다.
  - **추가 제공 정보(신규)**: 적용 죄명·법조문·법정형·선고 가능 범위(사건 등록 시 고정한 입력값, 아래 FR-4-3 Agent 1 제외 참고), **사건별 판단 요소 목록**(FR-3-4와 동일한 공통 목록).
  - **제외 정보**: 실제 판결 결과, 실제 형량, 실제 재판부의 최종 판단 근거, 사용자가 내린 판결, 사용자가 선택한 판단 요소.
  - 이를 통해 사용자와 AI가 서로의 판단이나 실제 판결에 영향받지 않고 동일 사건을 독립적으로 판단하도록 한다.
- **FR-4-2 (활용 자료 — RAG 대상 축소, 기획서 v2 반영)** AI 판결에는 관련 법률, 법정형, 양형기준, 유사 판례를 활용한다. **다만 관련 법률과 법정형은 RAG로 검색하지 않고, 사건 등록 단계에서 확정한 입력값을 그대로 사용한다.** 양형기준은 RAG로 검색하되 **사건 발생 시점의 버전만** 검색되도록 한다(FR-3-5-1). 유사 판례 검색 시 대상 사건 자신은 검색 결과에서 제외해 실제 판결 결과가 AI에게 노출되지 않도록 한다.
  - **MVP 구현 방식**: MVP는 오프라인에서 생성 · 검수한 AI 판결을 DB에 적재한다(REQ-046). 서비스 안의 생성 파이프라인(REQ-040 ~ 045)은 확장 단계이며, Agent 2·3의 검색은 **정식 RAG(pgvector 임베딩 검색)를 기본으로** 구현한다. 판례 수가 적거나 검색 품질이 부족해 **RAG를 적용할 수 없으면**, 관련 자료(유사 판례 후보, 양형기준 조문 등)를 프롬프트에 직접 넣는 퓨샷 방식으로 대체한다(v5.5, 3장 참고).
- **FR-4-3 (에이전틱 구조 — Agent 1 제외, 기획서 v2 핵심 결정)** 법률 판단·유사 판례 분석·양형기준 분석은 원래 역할을 분리한 4개 에이전트로 기획했으나, **Agent 1(법률 분석)은 두지 않는다.** 죄명·적용 법조문·법정형은 실제 판결문에서 이미 확정되어 있고 사용자에게도 그대로 제공되므로, AI가 이를 다시 추론하면 죄명 오적용 위험만 생긴다. 대신 이 값들을 **사건 등록 시 입력값으로 고정**해 Agent 2·3·4에 공통으로 전달한다.
  - Agent 2(유사 판례 분석): 판례 Vector Store(RAG를 적용할 수 없으면 퓨샷 프롬프트) → 유사 판례, 해당 판례 형량, 중요 고려 요소, 현재 사건과의 공통점·차이점.
  - Agent 3(양형기준 분석): 양형기준 RAG(사건 발생 시점 버전, RAG를 적용할 수 없으면 퓨샷 프롬프트) → 적용 양형기준, 범죄 유형, 특별·일반 양형인자 후보, 각 요소의 근거 사실.
  - Agent 4(최종 AI 판결 생성): 입력값(죄명·법조문·법정형)과 Agent 2·3의 분석 결과를 종합해 형벌, 형량, 주요 판단 요소, 형량을 높이는/낮추는 요소, 판결 이유를 생성한다. **판단 요소는 반드시 사건별 판단 요소 목록 안에서만 선택하고, 각 요소의 방향(높임/낮춤)을 표시하도록 지시한다**(FR-3-4와 동일한 공통 목록 사용). AI 판결도 선고 가능 범위(FR-3-3) 안에 있어야 한다.
- **FR-4-4 (결과 화면 스펙)** 형벌·형량, 집행유예 정보, "내 판결과의 차이" 비교 문구, 참고 자료 태그, 주요 판단 근거 서술, 가중·감경 요소 목록을 포함한다. "AI가 참고한 유사 판례와 양형인자 판단 과정 자세히 보기" 펼치기 영역은 확장 단계(S-07).
- **FR-4-5 (공개 순서)** 사용자 판결 확정 후 AI 판결(2/3 공개) → 실제 판결(3/3 공개) 순서로 순차 공개한다(S-07, S-08). 서버는 진행 상태에 맞는 결과만 응답한다(16장 DR-6).
- **FR-4-6 (신뢰성 확보, 원본 유지)** AI 판결은 사용자 요청마다 실시간 생성하지 않는다. 사건 등록 단계에서 미리 생성 후 내용·근거를 검토해 저장하고, 검토가 완료된 결과만 서비스에 등록해 모든 사용자에게 동일한 결과를 제공한다. AI 모델·프롬프트·참고 데이터가 변경되어도 기존 판결을 자동으로 덮어쓰지 않고 필요 시 재생성 후 다시 검토한다.
  - **예외 (v5.3)**: 세 판결 비교 분석(FR-6-3, 확장)은 사용자 판결에 따라 달라지므로 사전 검수 없이 체험별로 실시간 생성한다. 대신 FR-6-3의 안전장치로 신뢰성을 보완한다.

### 보류 사항

- "내 판결과의 차이" 자동 비교 문구 생성 로직 및 9장 비교 로직과의 공유 여부.
- Agent 간 입출력 데이터 구조, AI 판결 결과 검증 기준의 상세 설계.
- 과거 양형기준 확보 방법과 버전 관리 방식(범위 확장 시).

### 결정 상태

🟢 확정 (Agent 구조(1 제외)·제공/제외 정보·공개 순서·신뢰성 정책·MVP 구현 방식(오프라인 생성 · 검수 결과 적재, 파이프라인은 확장 단계에서 RAG 우선 · 불가 시 퓨샷, v5.5)·고정 입력값 데이터 구조(ERD) 확정) / 비교 문구 로직·Agent 입출력 설계는 🟡 추가 논의 필요 (비교 분석 생성 시점은 v5.3에서 실시간 생성으로 확정, FR-6-3)

## 8. 실제 판결 공개

### 기능 목적

사용자가 자신의 판결과 AI 판결 이후 실제 법원의 판결 결과와 판단 근거를 확인할 수 있도록 한다.

### 요구사항

- **FR-5-1 (제공 정보)** 실제 선고된 형벌 및 형량, 재판부가 중요하게 고려한 판단 요소, 각 요소가 형량에 유리/불리하게 작용한 방향, 해당 판단의 근거가 되는 판결문 내용, 판결문 내용을 사용자가 이해하기 쉽게 정리한 설명을 중심으로 제공한다. 판결문 발췌(인용 박스)와 "쉽게 말하면" 설명을 함께 제공한다(S-08).
  - **판단 요소 공통 분류 체계**: 실제 판결의 판단 요소는 AI처럼 자동 추출하지 않는다. **팀이 판결문을 직접 읽고, 사건별 판단 요소 목록에 방향·판결문 근거(어느 문장에서 그렇게 판단했는지)를 수기로 표시**한다(FR-3-4의 공통 목록 사용).
- **FR-5-2 (화면 스펙)** 강조 배너(형량 + 집행유예 + 부가 처분 요약, 내 판결·AI 판결 형량 재노출), 재판부의 판단 근거 요약 문단, 판결문 발췌, 가중·감경 요소 목록으로 구성한다. "이 사건에 대하여" 안내 문단, 비식별화 정보 항목 태그, 출처 기관 안내는 확장 단계(S-08).
- **FR-5-3 (원문 출처 비공개, 원본 유지)** 사건번호 및 원문 링크는 사용자에게 직접 제공하지 않는다. 실제 공개 판례를 기반으로 재구성한 사건임을 명시하고 출처 기관을 안내한다(안내 영역은 확장 단계, FR-5-2). 원본 판결문·사건번호는 내부적으로 보관해 재구성 사건과의 일치 여부를 검증할 수 있도록 관리하며, 비식별화 및 재구성 원칙을 사용자에게 안내한다. **사용자에게 제공하는 판결문 발췌 내용에도 동일한 비식별화 원칙을 적용한다.**
- **FR-5-4 (기준 판결 — 기획서 v2 핵심 결정)** 서비스에서 비교 대상으로 삼는 "실제 판결"은 **최종 확정 판결**을 기준으로 한다.
  - 1심 형량이 그대로 확정된 사건은 1심 판결과 확정 판결이 같으므로, 1심 판결 또는 확정 판결 중 하나만 가져온다.
  - 1심과 항소심의 형량이 다른 사건은 1심 판결문과 항소심 판결문을 합쳐 제공한다(FR-2-2 병합 규칙 참고).
  - 판결 확정 여부를 확인하는 구체적인 방법(대법원 상고 여부 확인 등)은 아직 결정되지 않았다.

### 보류 사항

- 판결문 원문 인용과 비식별화 원칙을 양립시키는 구체적 규칙(치환 범위, 검수 절차).
- 판결 확정 여부 확인 방법.
- 1심·항소심 판결문 병합의 세부 기준(어디까지를 "새로 드러난 사정"으로 포함할지).

## 9. 세 판결 비교 및 판단 근거 분석

### 기능 목적

사용자 판결, AI 판결, 실제 판결의 결과와 판단 근거를 비교하여 각각의 판결이 어떻게, 왜 달라졌는지 사용자가 이해할 수 있도록 한다. 또한 사전 판단("구경꾼의 나")에서 최종 판결("판사의 나")까지 사용자 자신의 판단 이유가 어떻게 바뀌었는지 보여 준다.

### 요구사항

- **FR-6-1 (비교 항목)** 형벌 종류 및 형량, 각 판결에서 중요하게 고려한 판단 요소, 각 판단 요소의 방향(↑/↓), 주요 판결 이유를 비교하며 형량 차이뿐 아니라 그 차이가 발생한 판단 근거까지 함께 비교한다. **세 판결의 판단 요소는 같은 판단 요소 목록(FR-3-4)을 기준으로 비교한다.**
- **FR-6-2 (판단 포인트 분석, 예시 — 확장 단계, REQ-062)** 사용자·AI·실제 판결 각각에서 중점적으로 고려한 요소를 분석해 제공한다. 예시: 사용자 판결은 범행의 계획성을 중요하게 고려하고 피해 정도를 형량↑ 요소로 판단; AI 판결은 양형기준·피해 회복 여부를 중요하게 고려하고 초범 여부를 형량↓ 요소로 판단; 실제 판결은 범행 결과와 범행 후 행동을 중요하게 고려하고 자수를 유리한 사정으로 판단하는 식이다.
- **FR-6-3 (AI 비교 분석)** 세 판결에 기록된 판단 근거를 바탕으로 공통적으로 중요하게 고려한 요소, 특정 판결에서만 고려한 요소, 같은 요소를 다르게 평가한 부분, 각 판결이 상대적으로 중점을 둔 관점을 분석한다. AI는 새로운 사실이나 근거를 임의로 생성하지 않으며, 어떤 판결이 옳은지 결정하지 않고 "어디에서 판단이 달라졌는가"를 설명하는 역할에 집중한다. MVP에서는 매트릭스 기반 규칙 문장으로 공통점·차이점을 보여 주고, AI 분석은 확장 단계로 한다.
  - **생성 시점 (v5.3 확정)**: 체험별 **실시간 생성**. 실제 판결 공개 시(S-08 진입, `AI_REVEALED`) 비동기로 생성을 시작하고, S-09는 규칙 문장을 먼저 보여 준 뒤 분석이 준비되면 공통점·차이점 영역만 교체한다. 체험당 한 번만 생성해 저장하고, 다시 열면 저장된 분석을 보여 준다(`sequence-diagram.md` 8장).
  - **안전장치**: ① 입력은 구조화된 기록만 — 세 판결의 형벌·형량·판단 요소 기록(요소 ID·문구·방향), 사전 판단 구간, 요소의 공개 단계. 사건 원문·판결문 전문은 넣지 않고, (확장) 사용자의 자유 의견은 넣지 않거나 지시문으로 해석되지 않도록 분리한다(`sequence-diagram.md` 8장 안전장치 #1) ② 항목마다 근거 요소 ID를 붙인 JSON 출력, 목록 밖 요소면 실패 ③ "정답·옳다/틀렸다·이중 잣대"·점수 표현이 있으면 실패 ④ 실패·오류·시간 초과 시 규칙 문장 유지 ⑤ 체험당 1회 생성 ⑥ 입력·출력·프롬프트 버전 기록 후 팀이 주기적으로 샘플 점검.
- **FR-6-4 (화면 구성)** 3열 카드 헤더 + 판단 요소 비교 매트릭스(S-09, v1: 1k)를 기본 화면으로 한다. 매트릭스 각 행에 요소 분류 태그("셋 모두 같게 본 요소" / "판단이 엇갈린 요소" / "나만 고려하지 않은 요소", v1: 1l에서 차용)를 붙인다. 형량 눈금 비교 막대는 확장 단계.
  - **(v5.5) 판결 카드 한 줄 요약 (REQ-109)**: 3열 카드마다 그 판결이 무엇을 무겁게 봤는지 한 줄로 요약해 보여 준다.
    - AI · 실제 판결: 판결을 등록할 때 팀이 작성한다(ERD `judgment.summary`).
    - 내 판결 (MVP, REQ-109): 판단 요소마다 팀이 붙인 **요약 태그**(예: 피해 규모, 범행 방식, 피해 회복, 반성, 전력)를 사용자가 고른 요소에서 방향별로 모아 규칙 문장으로 만든다. 예: "피해 규모 · 범행 방식을 무겁게 보고 반성을 감안한 판단". AI를 부르지 않는다(DR-10).
    - 내 판결 (확장, REQ-062): AI가 사용자가 입력한 형벌 · 형량 · 판단 요소 · 방향으로 **실시간 요약**을 만들어 규칙 문장을 바꾼다. AI 비교 분석(FR-6-3)과 같은 호출 · 같은 안전장치를 쓰고, 실패하거나 생성 중이면 규칙 문장을 그대로 둔다.
- **FR-6-5 (매트릭스 시각화 강화)** 판단 요소 비교 매트릭스는 표 형태 텍스트(↑/↓/―)뿐 아니라 차트·그래픽 형태로 시각화해 직관성을 높이는 방향을 검토한다(이후 단계).
- **FR-6-6 (사전 판단 → 최종 판결의 변화, v5 재정의)** 비교 화면 최상단에 사용자·AI·실제 판결 비교와 별개로 **"처음 판단 → 직접 판결"**을 제공한다. 사전 판단을 다시 보여 주는 첫 화면이다. 사전 판단은 세 판결의 네 번째 축으로 취급하지 않는다.
  - **형량 변화 (MVP)**: "뉴스로 봤을 때 / 사전 판단 형량 구간" → "모두 보고 판결했을 때 / 최종 판결 형량" + 한 줄 요약(예: "사건을 모두 확인한 뒤, 처음 생각보다 가벼운 판결을 내렸어요.").
  - **판단 이유 변화 (확장 단계, 작용 요소 선택 전제)**: 판단 요소의 공개 단계(FR-3-4)와 시점(`PRE`/`FINAL`) 기록을 조합해 **변화 2유형(새로 알게 된 요소로 바뀜 / 이미 알던 요소의 무게가 바뀜) + 변화 없음 1유형(처음부터 알던 요소를 그대로 반영), 총 3가지**로 구분하고, 유형별로 문구를 다르게 쓴다.


        | 유형 | 판별 기준 | 예시 문구 | 다루는 방식 |
        | --- | --- | --- | --- |
        | 새로 알게 된 요소로 바뀜 | 공개 단계가 `OVERVIEW` 이후인 요소가 최종 판결에서 고려됨 | "새 정보를 반영해 판단을 바꾼 건 자연스러운 일이에요. 처음 판단에는 돈을 받은 방식과 반성 여부가 빠져 있었어요." | 정당한 변화로 인정 |
        | 처음부터 알던 요소를 그대로 반영 | 공개 단계가 `OVERVIEW`인 요소가 `PRE`와 `FINAL` 모두에서 선택됨 | "피해 금액이 크다는 점은 처음부터 알고 있었어요. 판결할 때도 형량을 높이는 요소로 봤어요." | 변화 없음으로 서술 (와이어프레임 S-09 "처음부터 알던 요소" 카드) |
        | 이미 알던 요소의 무게가 바뀜 | 공개 단계가 `OVERVIEW`인 요소가 `PRE`에서는 선택됐지만 `FINAL`에서 고려되지 않았거나, 그 반대 | "지인 관계를 이용했다는 점은 처음부터 알고 있었는데, 판결할 때는 고려하지 않았어요." | 성찰할 거리 제시 |
    - 판단을 바꾼 것을 점수처럼 다루지 않는다. "틀렸다", "바뀌었다" 대신 무엇이 판단에 들어오고 빠졌는지를 서술한다.
- **FR-6-7 (화면 세부)** 형벌·형량과 주요 판단 요소는 세 판결을 한눈에 비교할 수 있도록 한 화면에 제공한다. 공통점·차이점 핵심 내용도 같은 화면에서 확인 가능하게 하고, 세부 판결 이유·근거는 "판결 이유 전문 펼치기"로 추가 확인한다(확장 단계).
- **FR-6-8 (체험 후 안내, 확장 단계)** 비교 화면 하단에 체험을 서비스 밖으로 이어 주는 안내를 둔다. 예: "다음에 뉴스에서 판결을 보면, 아직 모르는 정보가 무엇일지 한 번 떠올려 보세요."

### 보류 사항

## 11. UI/UX 공통 원칙

내Law남불은 일반 서비스보다 사용자에게 제공해야 하는 사건·법률 정보의 양이 많다. 따라서 정보를 많이 보여주는 것보다 사용자가 부담 없이 순서대로 이해하도록 만드는 것을 우선한다.

- 복잡한 정보는 단계적으로 제공한다.
- 한 화면에 지나치게 많은 정보를 배치하지 않는다.
- 어려운 법률 용어에는 간단한 설명을 함께 제공한다.
- 필요한 경우 클릭·펼쳐보기 등을 통해 상세 설명을 제공한다.
- 판결 전에는 실제 판결 결과가 노출되지 않도록 구성한다.
- 결과 화면에서는 세 판결을 직관적으로 비교할 수 있도록 구성한다.
- 데스크톱(1180px)과 모바일(390px) 핵심 흐름을 함께 고려한다. 모바일 화면은 S-02 · S-03 · S-04a · S-06a · S-09 (와이어프레임 v2.1 p.16).
- 서비스의 주제의식("같은 사건을 보고도 왜 서로 다른 판단이 나왔는가")이 카피와 화면 구성 전반에서 드러나도록 한다(3장 MVP 검증 목표 참고).
- **톤**: "당신은 이중 잣대다"처럼 단정하지 않고 "다 알고 나서도 같은 판단일까?"처럼 질문하는 톤을 쓴다. 사전 판단과 최종 판결의 차이는 대부분 정보 차이에서 오므로, 내로남불을 단정하면 과장처럼 보인다.
- **"속았다"가 아니라 "몰랐구나"**: 정보가 일부라는 사실을 미리 알리고(FR-2-8), 개요를 중립적으로 쓰며(FR-2-9), 결과에서 판단 변화를 정당하게 인정한다(FR-6-6).
- **되돌릴 수 없는 행동은 미리 알린다 (v5.2)**: 사전 판단 제출과 판결 확정 전에 "바꿀 수 없다"는 사실을 화면에 표시한다(FR-2-10, FR-3-9).
- **채택 화면 기준**: 와이어프레임 v2.1 PDF(`wireframe.pdf`). 점선 + "확장" 태그 요소는 추후 확장 요소로, MVP 구현에서는 제외한다.

## 12. 기능 우선순위 (MoSCoW)

> **(v5.5) MoSCoW와 구현 단계의 관계**: MoSCoW는 기능의 **가치 우선순위**이고, 기능 명세서의 구현 단계(MVP / 확장 / 이후 / 데이터)는 **일정**이다. 그래서 Should Have 항목이라도 일정상 "이후" 단계일 수 있다(예: 회원가입/로그인 REQ-066 ~ 070, AI Q&A REQ-028, 판단 요소 단위 참여자 통계 REQ-100). 실제 구현 여부 · 시점은 기능 명세서의 구현 단계를 따른다.
>

### Must Have (핵심 판결 체험, 반드시 구현)

실제 판례 기반 사건 제공 · 사건 개요 기반 사전 판단(형량 구간) · 단계별 사건 정보 확인 · 판결 전 최종 정보 정리 · 사용자 직접 판결 · 사용자 판단 요소 입력 · 사건별 판단 요소 목록(공개 단계 포함) · 법정형 및 양형기준 제공 · 권고 형량 범위 제공 · **선고 가능 범위 검증** · AI 판결 생성 및 제공(MVP는 오프라인 생성 · 검수 결과 적재) · 실제 판결 공개 · 사용자·AI·실제 판결 비교 · 사전 판단과 최종 사용자 판결의 변화 확인 · 세 판결의 판단 근거 및 차이 분석(MVP는 판단 요소 매트릭스 · 분류 태그 · 규칙 문장, AI 비교 분석은 확장) · **체험 진행 상태 서버 저장 · 제출/확정 후 수정 불가**

### Should Have (완성도 향상, 상황에 따라 추가)

회원가입/로그인 · 회원 계정 기준 판결 기록 저장 · 이전 판결 기록 목록 조회 · 사용자 선택 및 판결 과정 기록 · 사건 콘텐츠 확대 · 판결 비교 결과에 대한 추가 설명 · 선택 정보를 확인할 수 있는 AI Q&A · 사전 판단의 작용 요소 선택과 판단 이유 변화 유형 표시 · 판단 요소 단위 참여자 통계

> **4·6장과의 정합성**: 로그인·판결 기록 저장이 Should Have이므로, 초기 MVP에는 로그인 없이도 핵심 체험이 끝까지 동작해야 한다. 진행 상태는 익명 ID 기준으로 서버에 저장하므로 "이어서 하기"는 같은 브라우저 안에서 자동으로 동작한다. 임시 저장(입력 중 값 보존)은 이후 단계.
>

### Could Have (핵심 서비스 안정화 이후 확장 검토)

실제 판결과 AI 판결 맞히기 퀴즈 · 다른 사용자의 평균 형량 및 판결 통계 · 내 판결이 전체 사용자 중 어느 범주에 있는지 확인 · 판결 결과 SNS 공유 · AI를 활용한 가상 사건 생성 · 해외 법률 및 판결 비교 · 게임형/시나리오형 판결 콘텐츠 · 사용자 판결 데이터를 활용한 통계 및 분석 · 난이도 상향 모드: 권고 형량 범위 비공개 · 국민참여재판 배심원 의견을 추가 관점으로 제공 · **같은 사건 재체험 (REQ-110)** · **선고 가능 범위 · 권고 범위 자동 계산 (REQ-111)**

## 13. 서비스 운영 및 검증 방향

실제 판례와 AI를 함께 사용하는 서비스이므로 기능 구현뿐 아니라 운영 과정의 검증도 관리한다.

**판례 검증**: 원 판결문과 가공된 사건 정보 비교, 핵심 사실관계 누락 여부 확인, 비식별화 과정에서 판결 의미가 변하지 않았는지 확인. 사건 개요가 중립적으로 작성됐는지, 판단 요소의 공개 단계가 실제 화면 노출 순서와 일치하는지 확인. **(v5.2)** 선고 가능 범위(하한·상한)가 법조문·판결문 기준으로 맞게 계산됐는지 확인.

**AI 판결 검증**: 사건 등록 전 AI 판결 내용 검토, 참고 법률·양형기준·판례와 결과의 일치 여부 확인, AI가 존재하지 않는 근거나 사실을 생성하지 않았는지 확인.

**서비스 운영**: 운영 중 발생한 AI 오류·데이터 문제 기록, 문제 원인과 수정 과정 문서화, 모델·프롬프트·RAG 데이터 변경 시 결과 변화 확인, 운영 중 발견한 개선 사항의 지속적 반영.

## 16. 데이터 구조 요구사항 (ERD·API 반영용)

기획 방향이 일부 바뀌어도 데이터 구조가 흔들리지 않도록 다음 구조를 ERD·API 설계에 반영한다. 구체적인 테이블 설계는 `erd.md`(v1.3)를 따른다.

- **DR-1 (판결 주체 통합)** 판결과 판단 요소 기록은 주체 구분값 `subject_type`(`USER` / `AI` / `COURT`) 하나로 관리한다. 이후 배심원(`JURY`)이나 참여자 평균 등 다른 관점을 스키마 변경 없이 추가할 수 있어야 한다.
- **DR-2 (판단 요소 기록 형식)** 판단 요소 기록은 주체·시점·요소·방향(`direction`: ↑/↓)을 모든 주체가 같은 형식으로 저장한다(FR-3-4). **고려 여부는 기록의 존재 여부로 표현한다**(기록이 없으면 "고려하지 않음", ERD 결정 #1).
- **DR-3 (기록 시점)** 판단 요소 기록에 시점 `PRE`(사전 판단) / `FINAL`(최종 판결)을 둔다. 사전 판단은 최종 판결과 같은 판단 테이블에 `timing = PRE`로 저장한다(ERD 결정 #2).
- **DR-4 (공개 단계)** 판단 요소 마스터에 공개 단계(`OVERVIEW` / `DETAIL` / `ARGUMENT` / `LAW`)를 둔다. 사전 판단 선택지 필터링과 판단 이유 변화 유형 구분에 사용한다(FR-2-8, FR-6-6).
- **DR-5 (익명 ID)** 로그인 없이 체험이 끝까지 동작하도록 익명 ID로 체험 기록을 저장한다. 이후 판단 요소 단위 참여자 통계의 기반이 된다.
- **DR-6 (체험 진행 상태, v5.2 신규)** 체험 진행을 익명 ID × 사건 단위의 상태(`STARTED` → `PRE_JUDGED` → `REVIEWING` → `REVIEWED` → `VERDICT_CONFIRMED` → `AI_REVEALED` → `COMPLETED`)로 서버에 저장한다(IA 9장).
  - 상태는 앞으로만 이동하고, 이전 상태로 되돌리는 기능은 두지 않는다.
  - 사전 판단과 최종 판결은 체험당 한 번만 저장된다(FR-2-10, FR-3-9).
  - 결과는 상태에 맞는 것만 응답한다: AI 판결은 판결 확정 후, 실제 판결은 AI 판결 확인 후, 비교 결과(사전 판단 포함)는 실제 판결 확인 후.
  - S-04에서 확인한 마지막 섹션을 함께 저장해 새로고침 시 복원한다(FR-2-11).
- **DR-7 (재체험 · 회원 연결 대비, v5.2 신규)** MVP는 같은 브라우저 기준 사건당 1회 체험이지만, 나중에 스키마를 바꾸지 않고 재체험과 회원 연결을 열 수 있도록 다음을 미리 둔다.
  - 체험 회차(`attempt_no`, MVP에서는 항상 1). 통계에는 1회차만 사용한다.
  - 체험 시작 시점의 로그인 여부(체험의 `member_id`)와, 익명 ID와 회원의 연결(익명 ID의 `member_id`, 회원 1명에 익명 ID 여러 개).
- **DR-8 (선고 가능 범위, v5.2 신규)** 사건별 · 형벌별로 법정형 범위와 **선고 가능 범위**(FR-3-3)를 따로 저장하고, 선고 가능 범위의 산출 근거를 함께 둔다. 사용자 판결 저장 시 선고 가능 범위 밖이면 거절한다.
- **DR-9 (비교 분석 저장, v5.3 신규, 확장)** AI 비교 분석은 체험당 1개로 저장하고 생성 상태(`PENDING` / `DONE` / `FAILED`), 입력·원본 출력, 모델·프롬프트 버전을 함께 남긴다(ERD `comparison_analysis`). 검증을 통과한 결과만 화면에 보여 준다.
- **DR-10 (판결 요약, v5.5 신규)** 판단 요소 마스터에 요약 태그(`summary_tag`)를 두고, 판결에는 한 줄 요약(`summary`, AI · COURT)을 둔다. 사용자 판결의 요약은 저장하지 않고 조회 시 요약 태그로 규칙 문장을 만든다. 확장 단계의 AI 요약은 비교 분석 저장(DR-9)에 함께 남긴다.
- **제외**: 재판부 판결 평가 컬럼(`court_verdict_rating`), 사전 판단 유형 구분 컬럼(`PREDICTION` / `EVALUATION`)은 관련 기능을 제외했으므로 두지 않는다.

**API 반영 포인트**

- 체험 시작: 익명 ID 발급(없을 때) + 기존 체험이 있으면 그 체험의 진행 상태를 돌려준다.
- 판단 요소 조회: 공개 단계 필터를 지원한다(사전 판단 단계에서는 `OVERVIEW` 요소만 반환).
- 사전 판단 제출: 형량 구간을 받는다. (확장, REQ-093) 작용 요소 0 ~ 2개를 함께 받을 수 있다. 이미 제출했으면 거절한다.
- 사건 정보 섹션 확인: 확인한 섹션 번호를 기록한다.
- 판결 제출: 선고 가능 범위를 검증하고, 이미 확정했으면 거절한다.
- 판결 조회: 사용자·AI·실제 판결을 `subject_type` 기준의 같은 응답 형식으로 반환하되, 진행 상태에 맞는 것만 반환한다.
- 비교 결과 조회: 요소별로 주체별 기록과 분류 태그를 반환한다. (확장, REQ-096) 사전 판단 작용 요소가 있으면 변화 유형(새로 알게 됨 / 처음부터 알던 요소 / 무게 변화)을 함께 반환한다.
- (확장) 비교 분석 조회: 생성 중 / 완료 / 실패 상태를 돌려주고, 완료일 때만 분석 내용을 반환한다. 비교 결과 조회와 분리해 S-09가 AI를 기다리지 않게 한다.
