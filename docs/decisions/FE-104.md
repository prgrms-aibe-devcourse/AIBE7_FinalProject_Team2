# FE-104 의사결정 기록

## 문제 / 배경
- 로그인 · 로그인 콜백 · 약관/개인정보 · 404 화면 critique(28/40)에서 P1 2건 · P2 4건 · P3 9건이 나왔다.
- 404는 흰 판에 문구 두 줄뿐이라 앱의 책상 은유와 동떨어져 있었고, `<main>`이 없었고, 없는 사건과 잘못된 주소를 같은 문구로 보였다.
- 로그인은 실제 모드에서 관리자 전용 아이디 · 비밀번호 폼이 카카오 로그인과 같은 무게로 보여, 일반 사용자가 무엇을 넣어야 하는지 알 수 없었다. 오류 문구도 원인과 상관없이 "잠시 뒤 다시 시도"였다.
- 개발용 넘어가기 버튼 줄은 목 모드인지로만 막고 있었는데, `VITE_API_MODE` 없이 배포 빌드를 만들면 목 모드가 되어 그대로 노출될 수 있었다.

## 검토한 대안
- 404 모양
  - A. 기존 흰 패널을 다듬기(테두리 제거 · 여백): 작지만 서비스 개성은 그대로 없다.
  - B. 로그인 책상(`loginDesk`)을 그대로 빌려 펠트 패드에 문구: 손이 적지만 404가 로그인 화면처럼 보인다.
  - C. 같은 책상 위에 펠트 대신 "찾지 못한 서류" 한 장(종이 · 크라프트 띠) + 내로 · 남불 미안한 얼굴: 집무실 물건 은유(서류)를 지키고 새 이미지가 필요 없다.
- 로그인 폼 위계
  - A. 실제 모드에서 폼을 없애고 `/admin/login`으로 분리: 위계는 가장 깔끔하지만 새 경로 · 관리자 흐름(FE-53) 변경이 필요하다.
  - B. "관리자 로그인" 접이식(`details`) 안에 접기: 같은 화면 · 같은 로직을 유지하면서 일반 사용자에게는 카카오 하나만 보인다.
- 개발용 버튼 노출
  - A. `API_MODE` 기본값을 배포 빌드에서 real로 바꾸기: 앱 전체 동작이 바뀌고, 목 데모 배포가 필요한 경우를 막는다.
  - B. 넘어가기 버튼 줄만 `import.meta.env.DEV`로 한 번 더 막기: 영향이 그 도구에 한정된다.
- 약관 모바일 목차: 2열로 줄이기 / 접이식. 2열은 조항 제목이 길어 줄바꿈이 많아 접이식을 택했다.

## 선택한 방법과 이유
- 404는 C. 문구는 주소로 나눈다(`/cases/…` · `/me/cases/…`는 "사건 기록을 찾지 못했어요"). 찾은 주소를 크라프트 꼬리표로 보여 무엇을 못 찾았는지 알 수 있게 했다. 화면이 통째로 바뀌는 것이라 `role=alert`는 뺐다.
- 로그인은 처음에 B로 했다가, 리뷰 중 사용자 결정으로 되돌렸다(아래 "회원가입 추가"). 패드 안에 "로그인 없이 사건 보러 가기" 출구를 두었다.
- 오류 문구는 `NETWORK_ERROR` · 틀린 입력(`VALIDATION_ERROR`) · 그 밖으로 나눴다. 문구는 누른 버튼 가까이로 옮긴다.
- 개발용 버튼 줄은 B. 목업 로그인 안내 문구는 목 모드 빌드에서는 사실이라 그대로 둔다.
- 콜백은 카드 전체 대신 안내 한 줄에 `role=status` · `alert`를 두고, 탭 제목을 "로그인하는 중" · "로그인 실패"로 바꾼다.
- 약관 탭의 현재 문서는 `disabled`를 빼고 `aria-current`만 두어 키보드로 닿게 했다(눌러도 그대로).
- 개인정보처리방침의 DB 이전 날짜는 운영 DB 일정이 정해지지 않아 "옮길 예정 · 정해지면 알림"으로 바꿨다.

## 고려한 제약 사항
- 헤더 로그인 버튼의 누르는 범위(44px)와 본문 건너뛰기는 FE-99(PR #287)가 이미 다루어 이 이슈에서 건드리지 않았다. 헤더 포커스 링(3px)만 바꿔 같은 파일 인접 줄에서 충돌이 날 수 있다.
- 모바일 헤더 메뉴 잘림 · 헤더 Tab 순서는 FE-103에서 다룬다.
- 새 캐릭터 이미지는 만들지 않는다(이미지 생성은 별도 담당). 기존 `cheek/idle-sorry`를 썼다.

## 추후 재검토가 필요하면
- 데스크톱 로그인 패드의 좌우 공백(1080px 패드 · 400px 단)은 메인 책상과 닮게 한 의도라 그대로 두었다.
- 문의처("정해지면 알려 드려요")는 운영 연락처가 정해지면 `legalPage.js`에서 채운다.
- 관리자 로그인을 `/admin/login`으로 분리할지는 관리자 화면 critique 때 다시 본다.
- 회원가입 API(BE)가 생기면: `realApi.js`에 `signup`을 붙이고 입력 규칙(`signupRule.js`)을 서버와 맞춘다. 그때 이용약관 "회원가입과 계정" · 개인정보처리방침의 수집 항목(지금은 "카카오 회원번호만")에 아이디 · 닉네임을 더해야 한다.

## 회원가입 추가 (같은 PR)

### 문제 / 배경
- 일반 회원가입(아이디 · 비밀번호)을 추가할 예정이라, 아이디 · 비밀번호 폼을 "관리자 로그인"으로 접어 두면 곧 다시 바꿔야 한다. 회원가입 화면도 미리 만들어 둔다.
- 서버에는 회원가입 API가 아직 없다.

### 검토한 대안
- 실제 모드 가입하기: A. 버튼을 숨기고 카카오만 / B. 폼은 그대로 두고 입력 검사 뒤 "준비 중" 안내. B는 API가 붙을 때 화면을 다시 손대지 않아도 된다.
- 약관 링크: 같은 탭 이동은 입력값이 사라져 새 탭으로 연다.
- 칸 오류: 한 줄 오류(로그인처럼) / 칸마다 오류. 칸이 다섯이라 칸마다 둔다.

### 선택한 방법과 이유
- 로그인 폼은 모드와 상관없이 펼치고, 아래에 "처음이신가요? 회원가입" 링크. 실제 모드 틀린 입력 문구에서 "관리자"를 뺐다.
- 회원가입은 B. 목 모드는 목업 가입으로 화면 흐름(가입 → 로그인 상태 → 보던 화면)을 끝까지 확인할 수 있다.
- 로그인 ↔ 회원가입은 replace로 오가 가입 뒤 뒤로 가기가 로그인 화면에 걸리지 않는다.
- 입력 규칙은 `signupRule.js`로 떼어 테스트한다. 수치(4~20자 · 8자 · 2~12자)는 임시이며 서버 API와 함께 확정한다.
- 이용약관 · 개인정보처리방침 문구는 실제 가입이 열리기 전이라 바꾸지 않았다(지금 실제로 받는 정보는 그대로라서).
