## 검토한 대안

### 호버 규칙을 어떤 기준으로 정리할까

- **대안 A: "밝아짐"을 기준으로 통일**: 모든 호버를 "한 단계 밝게"로 맞춘다. 단점: 흰 카드 위 보조 버튼, 목록 줄처럼 밝게 만들 수 없는 면이 많고, 주 버튼은 지금 오히려 어두워진다. 기준 자체가 맞지 않는다.
- **대안 B: 요소 종류별 패턴으로 정리**: 버튼 · 면 단위 항목 · 선택지 · 글자 링크 · 헤더 메뉴처럼 요소 종류마다 호버 방식을 하나씩 정한다. 선택.

### 글자 링크의 밑줄 방식

- 대안 A: 평소에도 밑줄 + 호버에서 변화. 링크라는 단서가 확실하다.
- 대안 B: **평소 밑줄 없음 + 호버에서 밑줄**. 선택. 평소 화면이 깔끔하고, 이미 6개 요소가 이 방식이다.
- 비용: 지금 평소 밑줄이 있는 6개(`login-link` · `footer-link` · `admin-link` · `cm-text-button` · `stage-skip` · `result-turn-button`)는 링크 단서가 줄어든다. 팀 결정으로 "일단 전부 B로 하고 하나씩 보며 추후 수정"하기로 했다 → **임시 확정**.

### 면 단위 항목의 호버 틴트

- 후보: `surface`(중립) · `accent-tint` · `kraft 14%` · `kraft 16%` · `kraft 28%` · 글자색 8%. 코드에 4~5종이 흩어져 있다.
- 흰 카드 위와 신문지 위 두 배경에서 같은 목록으로 비교했고(비교 HTML P2), **`kraft 16%` 하나**로 정했다. 두 배경 모두에서 읽히고 책상 · 종이 세계관과 맞는다.

### 선택지의 테두리 색과 틴트

- 테두리 후보 `navy`(`#1c2b4f`) · `heading`(`#101d39`) · `accent`(`#1f3563`)는 모두 어두운 네이비라 눈으로는 구분되지 않는다. 실제로 갈리는 것은 틴트다.
- 결정: **테두리 `heading` + 틴트 `kraft 16%`**(P2와 같은 틴트). 시스템에 틴트가 하나만 남는다.

### 공통 규칙

- 호버는 `@media (hover: hover) and (pointer: fine)` 안에서만 쓴다. 터치 화면에서 호버가 눌린 채 남는 것을 막는다.
- 예외 연출은 `prefers-reduced-motion`일 때 끈다. 비활성이면 반응이 없다.
- 호버 전환은 `.12s ~ .2s`, `ease-out`을 기본으로 하고 예외 연출만 `cubic-bezier(.2, .8, .2, 1)`을 쓴다.

### 그 밖의 결정

- **마이페이지 스코프 테마**: `myPage.css`가 역할 토큰을 덮어쓰는 것은 의도된 설계로 보고, "스코프 테마는 `palette`를 직접 써도 된다"를 규칙으로 공식화한다. `myPage.css`는 고치지 않는다.
- **DESIGN.md 범위**: 프론트 전체. 화면 계열(책상 · 신문 지면 · 판결 체험 무대 · 성향 테스트 종이 · 마이페이지 · 커뮤니티 · 관리자 · 로그인)을 동등하게 다룬다.
- **작업 분리**: DESIGN.md와 "명백히 틀린 토큰" 몇 개를 먼저 하고, 여러 화면 CSS를 건드리는 일괄 정리와 호버 CSS 수정은 그 뒤(기능 작업이 끝난 마감 직전)에 한다.

```bash

```

점검 수치는 `frontend/src`의 CSS를 주석을 뺀 뒤 정규식으로 센 값이다. 다시 확인하려면 아래를 쓴다.

```bash
# 토큰 개수 / 화면 CSS에 직접 쓴 색값

grep -rnE "#[0-9a-fA-F]{3,8}\b|rgba?\(" frontend/src/pages frontend/src/utils --include="*.css"
# 호버 규칙과 가드(@media hover: hover) 확인
grep -rn ":hover" frontend/src --include="*.css" | wc -l
grep -rn "hover: hover" frontend/src --include="*.css" | wc -l
```
