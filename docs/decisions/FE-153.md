# FE-153 의사결정 기록

## 문제 / 배경
- 의견 보내기 창(`feedbackDialog.js`)은 창 크기가 바뀌면(`resize`) 닫혔다. 책상에서 날아온 펜이 열릴 때 계산한 자리(px)에 있어 크기가 바뀌면 어긋나기 때문이다.
- 모바일(≤ 720px)은 메뉴 카드로 창을 열어 펜이 날아오지 않는데도 같은 규칙으로 닫혔다. 모바일 · 태블릿 브라우저는 주소창이 접히고 펴질 때도 `resize`를 보내므로 창이 저절로 닫힐 수 있었다.

## 검토한 대안
- 대안 A: 높이만 바뀐 `resize`는 무시하고 폭이 바뀔 때만 닫는다(PR #403 리뷰 제안). 주소창(높이 변화)은 막지만, 펜의 세로 자리도 창 세로 가운데(`toY`)를 열 때 한 번 계산한 값이라 높이만 바뀌어도 창은 움직이고 펜은 제자리에 남는다. 폭이 바뀌면 창이 닫힌다.
- 대안 B: 닫지 않고 `resize`마다 펜 자리를 다시 놓는다. 펜의 도착 자리 계산을 함수(`penEnd`)로 빼면 열 때와 같은 식을 쓴다. 날아가는 중에 크기가 바뀌면 끝난 뒤에 놓는다.
- 대안 C: 날아온 펜이 있을 때만 `resize`에 닫는다(1차 수정). 모바일 메뉴 카드 경로는 해결하지만 721px 이상 터치 기기(태블릿)의 주소창 `resize`에는 여전히 닫힌다.

## 선택한 방법과 이유
- 대안 B. 닫는 이유가 "펜이 어긋난다" 하나뿐이었으므로 펜을 다시 놓으면 닫을 이유가 사라진다. 모바일 · 태블릿 주소창, 폭 변화, 높이 변화를 한 가지 방식으로 모두 처리한다. 처음 기록(대안 B를 "코드가 커진다"며 제외)은 과대평가였고 실제로는 열 줄 안팎이었다. 1000 × 800 창에서 높이(800 → 700)와 폭(1000 → 900)을 바꿔 보니 창은 열려 있고 펜 중심이 창 세로 중심과 일치했다.

## 고려한 제약 사항
- **데스크톱 동작이 바뀐다(의도):** 창 크기를 바꿔도 창이 닫히지 않고 펜이 따라온다. FE-151의 "데스크톱 모양은 그대로" 원칙에서 보이는 모양이 아니라 동작이 바뀌는 유일한 곳이다. 사용자에게 나쁜 변화는 아니지만 PR에 밝힌다.
- 모바일 메뉴 카드 경로(펜 없음)는 `resize`에 아무 일도 하지 않는다.

## 추후 재검토가 필요하면 (선택)
- 실기기(아이패드 사파리)에서 주소창 변화 중 펜이 한 박자 늦게 따라오는 것이 거슬리면 `resize` 대신 `visualViewport`의 변화를 보거나 `requestAnimationFrame`으로 묶는다.
