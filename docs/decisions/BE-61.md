# BE-61 의사결정 기록

> 확장 단계(WBS 7.1.4) · PR #123 · 담당 정민석

## 새로 도입한 기술 (선택)

### Redis AOF(Append Only File, `everysec`)
- 무엇인가: Redis의 영속화(persistence) 방식 중 하나로, 받은 쓰기 명령을 로그 파일에 순서대로 append해 재시작 후에도 데이터를 복구할 수 있게 한다. `everysec`은 그 로그를 1초마다 디스크에 fsync하는 동기화 정책이다.
- 동작 원리: 1) 클라이언트가 쓰기 명령을 보낸다 → 2) Redis가 메모리에 반영하고 AOF 로그에도 기록한다 → 3) 1초마다 디스크에 실제로 쓴다(fsync) → 4) 재시작 시 AOF 로그를 재생해 데이터를 복구한다. `everysec`은 매 명령마다 디스크에 쓰는 것(always)보다 빠르고, 아예 안 쓰는 것(no)보다 안전한 절충값이다.
- 우리 프로젝트에서: `backend/docker-compose.yml`(로컬)·`deploy/docker-compose.prod.yml`(운영)의 Redis 서비스 설정. 토큰(DB 1)이 재시작으로 사라지면 사용자가 강제 로그아웃되므로 영속화가 필요했다.
- 주의할 점: `everysec`은 "최대 1초치 쓰기 유실 가능"을 받아들인다는 뜻이다. 캐시(DB 0)는 유실돼도 다시 채워지지만, 토큰(DB 1)은 유실되면 해당 세션이 끊긴다는 걸 감안해야 한다.
- 참고: [Redis Persistence 공식 문서](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)

### Redis `maxmemory-policy noeviction`
- 무엇인가: Redis가 설정된 최대 메모리(`maxmemory`)에 도달했을 때 어떤 키를 지울지 정하는 정책. `noeviction`은 "아무 키도 자동으로 지우지 않고, 대신 쓰기 명령을 에러로 거부"하는 정책이다.
- 동작 원리: 메모리 사용량이 `maxmemory`(200mb)에 도달하면, `noeviction`에서는 읽기는 계속 되지만 새 쓰기(SET 등)는 OOM 에러로 실패한다. LRU 등으로 기존 키를 지워서 공간을 만드는 다른 정책과 다르다.
- 우리 프로젝트에서: `backend/src/main/java/com/team2/project/common/redis/RedisConfig.java`와 compose의 Redis 설정. 토큰이 임의로 지워지면 안 되므로(강제 로그아웃 방지), 캐시처럼 "지워져도 되는" 데이터에 쓰는 LRU 계열 정책 대신 `noeviction`을 택했다.
- 주의할 점: `noeviction`은 메모리가 꽉 차면 쓰기 자체가 실패하므로, 모든 키에 TTL을 강제해 메모리가 무한정 쌓이지 않게 하는 운영 규칙과 반드시 같이 가야 한다(PR 본문의 "모든 키 TTL 필수").
- 참고: [Redis `maxmemory-policy` 공식 문서](https://redis.io/docs/latest/develop/reference/eviction/)

## 문제 / 배경
- 캐시와 토큰(세션)을 같은 Redis 인스턴스/DB에 두면, 캐시 운영(삭제·만료 정책)과 토큰 보호 요구사항(절대 유실·삭제되면 안 됨)이 충돌한다.
- 운영 환경에서 Redis가 재시작되거나 장애가 나는 상황에서 토큰이 사라지는 것과, 백엔드 전체가 장애로 처리되는 것(health check)을 구분해야 했다.

## 검토한 대안
- **캐시와 토큰을 같은 DB에 둘지, 분리할지**: 같은 DB에 두면 캐시 삭제·만료 정책이 토큰에도 영향을 줄 위험이 있다. DB 0(캐시)·DB 1(토큰)로 커넥션 팩토리·템플릿을 분리하기로 했다. (PR 확인 사항에 "후속 검토: 캐시/토큰 Redis 자체를 분리(R11)"로 더 나아간 분리안도 남겨 두었다.)
- **자동 생성 RedisTemplate vs 전용 템플릿**: Spring Boot가 자동 생성하는 `RedisTemplate<Object,Object>`는 JDK 직렬화를 쓴다. 토큰처럼 다른 언어/도구에서도 읽을 수 있어야 하거나 직렬화 형식을 명시적으로 통제해야 하는 데이터에는 적합하지 않다고 판단해, `@Qualifier(RedisConfig.TOKEN)` 전용 템플릿을 쓰기로 했다.
- **백엔드 health check 기준**: Redis 장애 시 `/actuator/health`(전체 상태)는 DOWN(503)이 되지만, API 자체는 Redis 없이도 정상 동작한다는 걸 실측으로 확인했다. CD(BE-60)의 배포 판단에 전체 health를 쓰면 Redis 장애만으로 정상 배포가 "실패"로 오판될 수 있어, `/actuator/health/liveness`를 쓰기로 했다.

## 선택한 방법과 이유
- 캐시(DB 0)·토큰(DB 1)을 분리하고, 설정(`AppRedisProperties`)에서 두 DB 번호가 같으면 기동을 거부하게 했다 — 설정 실수로 섞이는 사고를 기동 시점에 막는다.
- 커맨드 타임아웃을 2초로 뒀다 — Redis 응답 지연이 API 응답 지연으로 무한정 이어지지 않게 한다.
- 영속화는 AOF `everysec` + `maxmemory 200mb` + `noeviction`을 택했다 — 토큰이 재시작으로 사라지지 않게 하면서도, 메모리가 꽉 찼을 때 캐시용 LRU 삭제가 토큰까지 건드리는 걸 막는다. 대신 모든 키에 TTL을 강제해 메모리가 끝없이 쌓이는 것을 막는다.
- 토큰 전용 템플릿(`@Qualifier(RedisConfig.TOKEN)`)을 쓰고, Redis 장애는 토큰 오류 코드로 바꾸지 않고 500으로 응답하게 했다 — "토큰이 유효하지 않다"와 "Redis가 죽었다"를 구분해 클라이언트가 잘못된 재로그인을 유도하지 않게 한다.
- 백엔드 health check는 `/actuator/health`가 아니라 `/actuator/health/liveness`를 쓰기로 팀에 공유했다 — Redis 장애가 전체 서비스 장애로 오판되지 않게 한다(BE-60의 CD 배포 판단이 이 값을 그대로 따른다).
- 운영 Redis는 비밀번호(`requirepass`)를 필수로 하고 외부 포트를 열지 않는다 — 토큰 저장소를 네트워크 바깥에서 직접 접근할 수 없게 한다.

## 고려한 제약 사항
- 모든 Redis 키에 TTL이 필수다 — `noeviction` 정책상 TTL 없는 키가 쌓이면 메모리가 꽉 찼을 때 쓰기 자체가 멎는다.
- 머지 후 서버 반영 전에 EC2 `deploy/.env`에 `REDIS_PASSWORD`를 추가해야 한다(없으면 운영 compose가 기동을 거부한다).
- 팀원은 머지 후 로컬에서 `docker compose up -d`를 한 번 더 실행해야 Redis가 뜬다(기존에 떠 있던 compose에는 자동 반영되지 않음).
- Redis ACL로 위험 명령을 차단하는 것, TTL을 코드 레벨에서 강제하는 래퍼, 캐시/토큰 Redis 인스턴스 자체 분리(R11)는 이번 범위 밖으로 남겼다.

## 추후 재검토가 필요하면
- Redis ACL 도입, TTL 강제 래퍼, 캐시·토큰 Redis 완전 분리(R11)를 후속으로 검토한다.
