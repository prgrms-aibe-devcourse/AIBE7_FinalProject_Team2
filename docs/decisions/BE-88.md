# BE-88 의사결정 기록

> 관련: [BE-88](https://aibe7-team2-final.atlassian.net/browse/BE-88), 강사 피드백에 따른 관리자 API 인증·인가 응답 검증.
> 응답 기준은 [API 명세 8-1](../api-specification.md#8-1-공통), 프론트 정책은 [FE-16](FE-16.md)을 함께 참조한다.

## 문제 / 배경

- 강사 피드백은 익명 사용자에게 쿠키·세션이 있으면 401/403 중 무엇이 맞는지, 일반 사용자 토큰이 관리자 요청에서도 인증되는지, 응답 코드 선택의 설계 근거가 있는지 확인하자는 것이었다.
- 기존 구현은 관리자 세션과 사용자 Bearer 인증을 다른 필터 체인으로 분리한다. 쿠키·세션이 존재한다는 사실과 관리자 체인이 유효한 인증을 복원했다는 사실을 구분해야 했다.
- 기존 테스트는 미인증 GET 401, 회원 토큰의 관리자 접근 401, 로그인 성공, CSRF 실패 403, 비활성·삭제 계정의 인증 폐기를 검증했다. 빈 세션·익명 쿠키, 인증된 비관리자의 403, 실제 컨테이너의 유휴 세션 만료와 익명/만료 POST의 CSRF 조합은 보완이 필요했다.

## 검토한 대안

- **관리자 요청 거절을 모두 403으로 통일**: 인증이 필요한 경우와 인증 후 권한이 부족한 경우를 구분하지 못하고, 기존 프론트의 401 로그인 이동 정책과 충돌한다.
- **관리자 체인도 사용자 JWT를 검증해 일반 회원을 403으로 거절**: 인증 영역을 합치는 변경이다. 관리자 세션·계정 상태 검사와 사용자 토큰을 연결하는 별도 설계가 필요하며, 특정 상태 코드를 만들기 위해 적용할 변경이 아니다.
- **CSRF 검사보다 인증 부재 검사를 먼저 수행**: 익명 POST도 항상 401로 맞출 수 있지만 필터 처리 순서와 기존 거절 동작을 바꾸게 된다. 이번 목적은 기존 정책 검증이므로 선택하지 않았다.
- **현행 정책을 유지하고 실제 요청 조합을 검증 (선택)**: 인증 수단의 경계와 먼저 거절하는 필터를 명시해, 운영 코드를 바꾸지 않고 응답의 근거를 설명할 수 있다.

## 선택한 방법과 이유

### 1. 관리자 세션과 사용자 JWT 인증 영역 유지

- `/api/v1/admin/**`는 먼저 매칭되는 관리자 체인만 거친다. 로그인·CSRF 발급을 제외한 경로는 관리자 세션의 인증과 `ROLE_ADMIN`을 요구한다.
- 관리자 로그인은 `AdminPrincipal`을 서버 세션에 저장하고, 요청마다 관리자 계정의 활성 여부를 다시 확인한다. 사용자 Bearer 검증은 이 체인에서 실행하지 않아 일반 사용자 토큰이 관리자 인증으로 승격되지 않는다.
- 사용자 체인은 무상태이며 관리자 세션을 인증에 사용하지 않는다. 반대 방향도 분리해 두므로 회원 토큰만 보낸 관리자 GET은 권한 부족 403이 아니라 관리자 인증 부재 401이다.
- `NLNB_AID`는 익명 체험 식별자이며 관리자 로그인 인증이 아니다. 빈 세션이나 오래된 세션 쿠키도 그 자체로 인증을 보장하지 않는다.

### 2. 401/403은 인증 상태와 거절 지점으로 구분

- 관리자 체인에 유효한 인증이 없으면 401 `UNAUTHORIZED`, 인증된 주체가 `ROLE_ADMIN`을 갖지 않으면 403 `FORBIDDEN`이다. `AnonymousAuthenticationToken`의 존재를 실제 로그인 성공으로 해석하지 않는다.
- CSRF 누락·불일치는 `CsrfFilter`가 인가 검사 전에 거절해 403을 반환한다. 따라서 익명 또는 만료된 세션의 POST도 CSRF가 잘못되면 403이고, 정상 CSRF를 보내면 뒤의 인증·인가 검사에서 401이다.
- 계정 상태 필터는 CSRF보다 먼저 동작한다. 복원된 관리자 계정이 비활성·삭제되었다면 세션과 인증을 폐기하고 보호 경로는 바로 401로 끝낸다. 이미 만료되어 인증을 복원하지 못한 세션과는 처리 경로가 다르다.
- 로그인·CSRF 발급 경로는 관리자 인증 없이 사용할 수 있다. 계정 상태 필터도 해당 공개 경로에서는 오래된 인증을 폐기한 뒤 계속 진행한다. 로그인 POST의 CSRF 및 자격 증명 검사는 그대로 유지한다.
- HTTP 상태의 의미는 [RFC 9110의 401](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.5.2)·[403](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.5.4), 익명 요청 및 CSRF 거절 경로는 Spring Security의 [익명 인증](https://docs.spring.io/spring-security/reference/servlet/authentication/anonymous.html)·[CSRF](https://docs.spring.io/spring-security/reference/servlet/exploits/csrf.html) 설명을 참고했다. 상태 코드 의미와 `WWW-Authenticate` 헤더 요건은 별개이며, 이번에는 헤더 정책을 변경하지 않았다.

### 3. 프론트 오류 처리와 기존 응답 계약 유지

- [FE-16](FE-16.md) 및 [관리자 클라이언트](../../frontend/src/pages/admin/adminClient.js)는 로그인 실패(`INVALID_CREDENTIALS`)를 제외한 401을 로그인 화면 복귀에 사용한다.
- 상태 변경 요청의 403은 CSRF 재발급 후 한 번만 재시도한다. 이 처리만으로 권한 부족과 CSRF 실패를 완전히 구분하지는 못하며, 권한 부족이면 재시도도 거절된다. 현재 프론트는 수정하지 않았다.
- API 명세 8-1에 현행 우선순위와 공개 경로 예외를 추가하되 기존 오류 코드·응답 형식·운영 코드는 유지한다. 기존의 포괄적인 “로그인하지 않으면 401”·“없는 관리자 경로도 401” 및 A-3 문장은 CSRF 실패 POST의 우선순위가 빠져 있으므로 정합성 확인 사항으로 명시했다. 기존 계약 문구를 임의로 교체하지 않았다.

## 고려한 제약 사항

- BE-87의 [테스트 전용 환경](../../backend/TESTING.md)과 `TestEnvironmentGuard`를 그대로 사용한다. 개발 DB·비공개 시드에는 접근하지 않고 Docker 볼륨을 삭제·초기화하지 않는다.
- 기존 테스트와 겹치는 로그인 성공·미인증 GET·회원 Bearer·CSRF 회전·계정 삭제·비활성 계정의 CSRF 누락 거절은 재사용한다. 이번 신규 검증은 빠진 조합에 집중한다.
- 인증·인가 상태를 분리하려고 테스트 세션에 `ROLE_USER` SecurityContext를 인위적으로 저장한다. 이는 세션 저장소를 통한 인증 복원 이후의 인가 분기 검증이며, 실제 회원 로그인이나 JWT가 관리자 세션을 발급한다는 뜻이 아니다.
- 실제 세션 만료는 테스트 전용 `HttpSessionListener`로 정상 HTTP 로그인에서 생성된 세션을 관찰하고 유휴 시간을 1초로 줄여 확인한다. 인증 객체를 직접 주입하거나 세션을 수동 무효화해서 만료를 흉내 내지 않는다. 리스너는 `@TestConfiguration`으로 등록해 다른 테스트나 운영 구성에 스캔되지 않도록 했다.
- HTTP 테스트는 로컬 임의 포트를 사용하고 Secure 쿠키를 직접 요청 헤더에 넣는다. 실제 브라우저의 HTTPS·Secure·SameSite 처리를 검증했다고 설명하지 않는다. 테스트가 만든 세션·계정·감사 로그만 정리한다.

## 검증 범위와 결과

- [AdminAuthApiTest](../../backend/src/test/java/com/team2/project/admin/AdminAuthApiTest.java): 기존 15건에 빈 세션·UUID 형식 익명 쿠키, 인위적 인증 주체의 `ROLE_USER` 403, 익명 POST의 CSRF 3조합, 비활성 계정 POST의 정상/불일치 CSRF, 비활성 세션의 공개 CSRF 발급 예외를 더해 23건을 검증한다. 비활성 계정의 CSRF 누락 사례는 기존 테스트를 재사용한다.
- [AdminAuthSessionHttpTest](../../backend/src/test/java/com/team2/project/admin/AdminAuthSessionHttpTest.java): 알 수 없는 세션 쿠키와 정상 HTTP 로그인 후 실제 유휴 만료된 세션을 각각 검증한다. 두 경우 모두 GET 401 및 POST의 정상 CSRF 401·누락/불일치 403을 확인한다.
- [UserSecurityChainTest](../../backend/src/test/java/com/team2/project/common/security/UserSecurityChainTest.java): 기존 12건을 재사용해 회원 Bearer의 관리자 GET 401과 관리자 세션·사용자 인증 영역 분리를 확인한다. 토큰 검증기는 가짜 구현으로, 실제 JWT 서명 검증 전체를 수행하는 테스트는 아니다.
- 관련 3개 클래스 **37건 통과**(실패·오류·건너뜀 0건). 그 후 `cleanTest test --no-daemon`으로 전체 **58개 클래스·597건 통과**(기존 587건 + BE-88 신규 10건, 실패·오류·건너뜀 0건)를 확인했다. 테스트 전용 PostgreSQL·Redis를 사용했고 보호 장치는 우회하지 않았다. 이번 실행에서 실패한 테스트는 없었다.

## 남은 한계와 후속 검토

- 기본 세션 유휴 시간 30분을 실제로 기다리는 검증, 브라우저 쿠키 정책, 재시작·다중 인스턴스 세션 공유, 실제 회원 JWT 서명/발급 연동은 이번 검증 범위가 아니다.
- 기존 API 계약의 포괄적인 401 문구와 현행 CSRF 우선 응답의 표현 정합성은 팀 확인 후 정리한다. 우선순위를 바꾸려면 별도 계약 변경과 프론트 영향 검토가 필요하다.
- 401 응답의 `WWW-Authenticate` 헤더, 관리자 IP 허용 목록·VPN·내부 네트워크 제한은 별도 후속 과제다. 현재 지원하지 않는 인증 스킴을 헤더에 광고하거나 네트워크 정책을 임의로 추가하지 않는다.
- GitHub Actions 및 운영 환경 결과는 로컬 테스트 통과와 별도로 확인해야 한다.
