# BE-63 의사결정 기록

> 확장 단계(WBS 7.4.6) · 1차 PR #148 · 2차 PR #236 · 담당 정민석

## 1차 (PR #148)

### 새로 도입한 기술 (선택)

#### Nginx `limit_req` (Rate limiting)
- 무엇인가: Nginx가 IP(또는 다른 키) 단위로 요청 속도를 제한하는 모듈. 정해진 평균 속도(rate)를 넘는 요청은 대기시키거나 거부할 수 있다.
- 동작 원리: 1) `limit_req_zone`으로 어떤 키(여기서는 클라이언트 IP, `$binary_remote_addr`) 기준으로 얼마나 빠른 평균 속도(rate)까지 허용할지 http 블록에 정의한다 → 2) `location`에서 `limit_req zone=... burst=...`로 순간 허용치(burst)를 함께 지정한다 → 3) 평균 속도를 넘되 burst 안이면 큐에서 기다리거나(`nodelay` 없으면 지연), `nodelay`면 기다리지 않고 바로 처리하거나 거부한다 → 4) burst까지 넘으면 429(Too Many Requests)를 반환한다.
- 우리 프로젝트에서: `frontend/nginx/default.conf`(이후 BE-75에서 `frontend/nginx/snippets/app.conf`로 공용 분리). `/api`(슬래시 없는 `/api` 포함)에만 적용하고 화면·정적 파일에는 적용하지 않는다. 기본 429(HTML) 응답은 `error_page 429`로 가로채 API 명세 1-4 형식의 JSON으로 바꾼다.
- 주의할 점: 기준 IP가 실제 사용자 IP가 아니라 프록시/로드밸런서 IP로 뭉뚱그려지면(예: 172.x 사설 대역) 모든 사용자가 한 IP로 묶여 제한이 엉뚱하게 걸린다 — 반드시 운영 환경에서 Nginx 접속 기록의 IP가 실제 공인 IP인지 확인해야 한다.
- 참고: [Nginx `ngx_http_limit_req_module` 공식 문서](https://nginx.org/en/docs/http/ngx_http_limit_req_module.html)

### 문제 / 배경
- `/api`에 요청량 제한이 없어, 과도한 요청(의도적이든 아니든)이 백엔드에 그대로 전달될 수 있었다.
- Nginx 기본 429 응답은 HTML이라, 프론트의 `api/client.js`가 이를 "서버 오류"(`INTERNAL_ERROR`)로 잘못 해석해 보여주는 문제가 있었다.

### 검토한 대안
- **제한값(속도) 산출 근거**: 화면은 동시 호출·폴링이 없어 혼자 쓰면 초당 1~3번 정도의 요청만 발생한다. 다만 발표장처럼 여러 명이 같은 공인 IP(와이파이)를 공유하는 상황도 고려해, 개인 사용 패턴보다 넉넉한 평균 초당 20·순간(burst) 40까지 허용하기로 했다.
- **429 응답 형식**: Nginx 기본 HTML 429를 그대로 둘지, API 명세 형식(JSON)으로 바꿀지 검토했다. 그대로 두면 프론트 에러 처리가 모든 429를 "서버 오류"로 오인하므로, JSON `TOO_MANY_REQUESTS`(API 명세 1-4 형식, `Retry-After: 1`·`Cache-Control: no-store`·`X-Content-Type-Options: nosniff`)로 바꿨다.
- **1차/2차 범위 분리**: `/api` 전체 제한(1차)과 로그인·토큰 재발급 엔드포인트 제한(2차)을 한 번에 할지, 나눌지 검토했다. 2차는 7.4.2(카카오 로그인) 이후에나 대상 엔드포인트가 확정되므로, 1차(`/api` 공통 제한)만 먼저 반영하고 2차는 이어서 진행하기로 했다.

### 선택한 방법과 이유
- `/api`(슬래시 없는 `/api` 포함)에 IP별 평균 초당 20·순간 40까지 허용하고, 화면·정적 파일은 제한하지 않는다 — API 호출만 보호 대상으로 좁혔다.
- 429 응답을 API 명세 1-4 형식의 JSON으로 바꿨다 — 프론트가 `TOO_MANY_REQUESTS`로 정확히 인식하게 하기 위해서다(실제로 `api/client.js`에 429 응답을 넣어 확인).
- **1차만 반영하고 완료 처리하지 않는다**: 로그인·재발급 제한(2차)은 7.4.2 이후 대상 엔드포인트가 정해져야 구현할 수 있어, PR #148은 머지해도 Jira 이슈를 완료로 바꾸지 않기로 했다.
- 백엔드 감사 로그 IP(`forward-headers-strategy=native`)는 Nginx가 실제 사용자 IP를 올바르게 보는지 EC2에서 먼저 확인한 뒤에 켜기로 했다 — 먼저 켜면 위조된 `X-Forwarded-For` 값이 감사 로그에 그대로 기록될 위험이 있다.

### 고려한 제약 사항
- EC2 반영 후 Nginx 접속 기록의 IP가 실제 공인 IP인지 반드시 확인해야 한다(172.x 등 사설 대역이면 전체 사용자가 한 IP로 묶인다).
- 429는 백엔드 지표·Loki에 잡히지 않는다(로그 수집 도구가 백엔드 로그만 수집). 웹(Nginx) 로그 수집이 필요하면 후속 검토 대상이다.
- HTTPS(BE-75)로 443 server 블록이 추가될 때, 같은 `limit_req` 규칙을 443에도 반드시 적용해야 한다(놓치면 https 요청은 제한이 걸리지 않는다). 실제로 BE-75에서 두 server가 공용 snippet을 include하는 구조로 이를 구조적으로 보장했다(`docs/decisions/BE-75.md`).
- API 명세 이력 번호가 BE-74(v0.29)와 충돌해 BE-63을 v0.30으로 조정했다(BE-74 문서는 변경하지 않음).

## 2차 (PR #236)

### 문제 / 배경
- 7.4.2(BE-62 카카오 로그인 · BE-94 JWT)로 대상 엔드포인트가 정해졌다: M-1 토큰 재발급 · M-2 로그아웃 · A-2 관리자 로그인. 지금은 모두 `/api` 공통 제한(IP별 초당 20 · 순간 40)만 받는다.
- 카카오 로그인 시작(M-3)은 요청마다 Redis에 state를 쓰는 문제로 BE-62(PR #229 리뷰)에서 먼저 전용 제한(`oauth_per_ip` · `oauth_all`)을 넣었다.
- 관리자 로그인에는 백엔드 실패 횟수 잠금이 없어, 비밀번호 대입을 막는 것이 사실상 초당 20번 제한뿐이었다.
- 1차의 남은 항목 중 "429가 Loki · Grafana에 안 잡힌다"가 그대로였다(1차 "고려한 제약 사항").

### 검토한 대안
- **어디서 막을까 — Nginx vs 백엔드 필터(Bucket4j 등)**: 백엔드 필터는 계정 단위 잠금까지 할 수 있지만 B 소유 영역(`SecurityConfig` · 관리자 로그인)을 고쳐야 하고, Redis에 카운터를 새로 둬야 한다. 7-2-1에서 "Nginx `limit_req` · 로그인 엔드포인트 제한"이 D 소유이고, 1차와 같은 구조(zone + location + JSON 429)를 그대로 쓸 수 있어 Nginx로 했다. 계정 단위 잠금은 필요해지면 별도 이슈다.
- **재발급에 전체 합계 zone을 둘까**: 카카오 시작은 요청마다 state를 새로 써서 IP를 바꿔 가며 Redis를 채울 수 있었다. 재발급은 `RefreshTokenStore.consume`(`getAndDelete`) 후 새 토큰 하나를 쓰므로 키 수가 늘지 않고, 모르는 토큰은 401로 끝나 아무것도 쓰지 않는다 → IP별만 둔다.
- **전용 zone 키 — IP vs POST일 때만 IP**: IP 그대로면 같은 경로의 GET도 전용 한도를 써서, 같은 IP(같은 와이파이)의 누군가가 GET을 반복하면 정상 POST가 막힌다(PR #236 CodeRabbit 리뷰) → POST가 아니면 빈 키(Nginx가 세지 않음). GET도 `/api` 공통 제한은 받는다.
- **429 로그 수집 방법**:
  - Alloy에 Docker socket을 붙여 컨테이너 stdout 읽기 → Docker 제어 권한(사실상 root)을 주게 돼 제외
  - `/var/lib/docker/containers` 읽기 전용 마운트 → 다른 컨테이너의 로그와 `config.v2.json`(환경변수 = DB 비밀번호 · JWT 키 등)까지 읽게 돼 제외
  - Nginx syslog → Alloy → syslog 서버 호스트 이름을 Nginx 시작 때 찾으므로, 에이전트 없는 서버(CI · 로컬)에서 웹이 뜨지 않게 돼 제외
  - **429만 별도 파일 + 볼륨 공유** → 선택. 웹은 에이전트 유무와 상관없이 뜨고, Alloy는 파일 하나만 본다

### 선택한 방법과 이유
- 전용 zone 두 개를 `/api` 공통 제한에 **더해** 건다(`default.conf` · `snippets/app.conf`, 카카오 시작과 같은 방식).
  - `auth_token_per_ip`: 재발급 · 로그아웃이 나눠 씀. IP별 분당 30 · 순간 30 — 정상 화면은 액세스 토큰 만료(15분) · 새로고침 때만 재발급하고 동시 재발급은 프론트가 하나로 묶는다. 같은 와이파이에서 여러 명이 동시에 새로고침해도 막히지 않게 카카오 시작과 같은 값
  - `admin_login_per_ip`: IP별 분당 5 · 순간 5 — 처음 5번 뒤 12초에 1번(시간당 약 300번). 요청마다 Argon2id 검증(BE-90) CPU도 아낀다
- `Retry-After`를 경로별로 바꿨다(공통 1 · 재발급 · 로그아웃 · 카카오 시작 2 · 관리자 로그인 12초) — 1차의 `1` 고정은 전용 제한에서 실제보다 짧게 안내했다.
- 재발급 429는 로그아웃이 아니다: 프론트(`api/client.js`)는 재발급이 401일 때만 로그인 표시를 지운다. 관리자 로그인 화면은 429를 "잠시 뒤 다시 시도"로 보여 준다. 그래서 프론트 변경 없이 넣을 수 있었다.
- 429 로그: Nginx가 429만 JSON 한 줄씩 `/var/log/nginx-ratelimit/rate-limited.log`에 남기고(`if=$rate_limited`), 모니터링 에이전트 오버레이가 이 폴더를 `web-ratelimit-logs` 볼륨으로 Alloy와 나눈다. 라벨은 `job="web"` · `route`(값 4개)뿐, `ip` · `path`는 본문 필드(BE-71 카디널리티 규칙). Grafana 서비스 대시보드에 "Rate limit 429 (제한별)" 패널.
- 로그 크기 상한: `41-trim-rate-limit-log.sh`가 1분마다 10MB(`RATE_LIMIT_LOG_MAX_BYTES`)를 넘으면 비운다 — 공격 중에도 디스크를 채우지 않게. 비워도 Nginx는 같은 파일에 이어 쓰고 Alloy는 처음부터 다시 읽는다(로컬에서 확인).
- 7.2.3 로그 수집은 C 영역이지만, 원인(Rate limit)이 D 작업이고 C 일정이 가장 빠듯해 D가 함께 처리하고 C 리뷰를 받는다.

### 고려한 제약 사항
- `route`는 **경로 기준**이라 zone과 1:1이 아니다 — 재발급 경로의 429가 전용 · 공통 어느 쪽에서 났는지는 웹 오류 로그의 `by zone "..."`으로 본다(Nginx가 막은 zone을 변수로 주지 않음).
- 로그를 비우기 직전 1분 안에 Alloy가 아직 못 읽은 줄은 빠질 수 있다. 공격처럼 상한에 닿을 때만 생기고, 그때는 개수보다 "많이 막혔다"는 사실이 중요하다고 봤다.
- **Alloy가 멈춘 사이 파일이 비워지면 그 구간 줄은 빠진다**(PR #236 리뷰 질문으로 로컬 확인). Alloy는 재시작할 때 기억한 위치부터 읽는다 — 새 내용이 그 위치보다 짧으면 전부, 길면 앞부분이 빠지고 앞이 잘린 조각 한 줄이 생긴다. 조각은 Alloy `stage.drop`(`{`로 시작하지 않는 줄)으로 버리고, 패널은 `route` 라벨이 있는 줄만 센다. 이름을 바꿔 돌리는 방식(`.1`)은 다시 읽기로 **중복**이 생겨 낫지 않다고 봤다. 상한에 닿을 만큼 막히는 중에 Alloy까지 멈춘 경우에만 생긴다.
- Loki 엔트리 시각은 줄의 `time`을 쓴다(`stage.timestamp`, PR #236 리뷰). 없으면 Alloy가 읽은 시각이 돼, Alloy가 멈췄던 구간의 429가 복구 시각 한 점에 몰린다. 기존 백엔드 로그(`loki.process "backend"`)도 같은 상태지만 BE-71 영역이라 별도 이슈로 둔다.
- 429 로그에 사용자 IP가 남는다(막힌 쪽을 찾기 위해). 백엔드 마스킹(토큰 · 이메일) 대상은 아니며, 보존 기간은 지금 운영 Loki(모니터링 전용 EC2 자체 호스팅)의 `monitoring/loki-config.yml` `retention_period: 15d`를 따르고, 7.3.3에서 Grafana Cloud로 옮기면 그쪽 보존 기간을 따른다(PR #236 리뷰).
- Docker 자체의 컨테이너 로그(stdout) 회전 설정은 아직 없다 — 이 PR 범위 밖(별도 확인).
- zone의 `rate`를 바꾸면 `$rate_limit_retry_after`도 같이 바꿔야 한다(주석으로 남김).

## 추후 재검토가 필요하면
- **계정 단위 로그인 잠금**: IP를 바꿔 가며 관리자 비밀번호를 대입하면 IP별 제한만으로는 늦출 뿐이다. 관리자 계정이 늘거나 외부 노출이 커지면 백엔드에 실패 횟수 잠금(B 영역)을 검토한다.
- **Docker 로그 회전**: 웹 · 백엔드 stdout이 쌓이는 양을 보고 `daemon.json` 또는 Compose `logging`에 `max-size`를 둔다.
- **백엔드 로그 시각**: `loki.process "backend"`에도 `stage.timestamp`(logback JSON의 시각 필드)를 넣을지 BE-71 후속으로 본다.
- **429 경보**: 7.3.1 경보 규칙(C)에 `sum(count_over_time({job="web"}[5m]))` 기준을 넣을지 실제 빈도를 본 뒤 정한다.
