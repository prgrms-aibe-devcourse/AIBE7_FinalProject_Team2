# BE-63 의사결정 기록

> 확장 단계(WBS 7.4.6) · PR #148 · 담당 정민석

## 1차 (PR #148)

### 새로 도입한 기술 (선택)

#### Nginx `limit_req` (Rate limiting)
- 무엇인가: Nginx가 IP(또는 다른 키) 단위로 요청 속도를 제한하는 모듈. 정해진 평균 속도(rate)를 넘는 요청은 대기시키거나 거부할 수 있다.
- 동작 원리: 1) `limit_req_zone`으로 어떤 키(여기서는 클라이언트 IP, `$binary_remote_addr`) 기준으로 얼마나 빠른 평균 속도(rate)까지 허용할지 http 블록에 정의한다 → 2) `location`에서 `limit_req zone=... burst=...`로 순간 허용치(burst)를 함께 지정한다 → 3) 평균 속도를 넘되 burst 안이면 큐에서 기다리거나(`nodelay` 없으면 지연), `nodelay`면 기다리지 않고 바로 처리하거나 거부한다 → 4) burst까지 넘으면 429(Too Many Requests)를 반환한다.
- 우리 프로젝트에서: `frontend/nginx/default.conf`(이후 BE-75에서 `frontend/nginx/snippets/app.conf`로 공용 분리). `/api`(슬래시 없는 `/api` 포함)에만 적용하고 화면·정적 파일에는 적용하지 않는다. 기본 429(HTML) 응답은 `error_page 429`로 가로채 API 명세 1-4 형식의 JSON으로 바꾼다.
- 주의할 점: 기준 IP가 실제 사용자 IP가 아니라 프록시/로드밸런서 IP로 뭉뚱그려지면(예: 172.x 사설 대역) 모든 사용자가 한 IP로 묶여 제한이 엉뚱하게 걸린다 — 반드시 운영 환경에서 Nginx 접속 기록의 IP가 실제 공인 IP인지 확인해야 한다.
- 참고: [Nginx `ngx_http_limit_req_module` 공식 문서](https://nginx.org/en/docs/http/ngx_http_limit_req_module.html)

### 문제 / 배경
- `/api`에 요청량 제한이 없어, 과도한 요청(의도적이든 아니든)이 백엔드에 그대로 전달될 수 있었다.
- Nginx 기본 429 응답은 HTML이라, 프론트의 `api/client.js`가 이를 "서버 오류"(`INTERNAL_ERROR`)로 잘못 해석해 보여주는 문제가 있었다.

### 검토한 대안
- **제한값(속도) 산출 근거**: 화면은 동시 호출·폴링이 없어 혼자 쓰면 초당 1~3번 정도의 요청만 발생한다. 다만 발표장처럼 여러 명이 같은 공인 IP(와이파이)를 공유하는 상황도 고려해, 개인 사용 패턴보다 넉넉한 평균 초당 20·순간(burst) 40까지 허용하기로 했다.
- **429 응답 형식**: Nginx 기본 HTML 429를 그대로 둘지, API 명세 형식(JSON)으로 바꿀지 검토했다. 그대로 두면 프론트 에러 처리가 모든 429를 "서버 오류"로 오인하므로, JSON `TOO_MANY_REQUESTS`(API 명세 1-4 형식, `Retry-After: 1`·`Cache-Control: no-store`·`X-Content-Type-Options: nosniff`)로 바꿨다.
- **1차/2차 범위 분리**: `/api` 전체 제한(1차)과 로그인·토큰 재발급 엔드포인트 제한(2차)을 한 번에 할지, 나눌지 검토했다. 2차는 7.4.2(카카오 로그인) 이후에나 대상 엔드포인트가 확정되므로, 1차(`/api` 공통 제한)만 먼저 반영하고 2차는 이어서 진행하기로 했다.

### 선택한 방법과 이유
- `/api`(슬래시 없는 `/api` 포함)에 IP별 평균 초당 20·순간 40까지 허용하고, 화면·정적 파일은 제한하지 않는다 — API 호출만 보호 대상으로 좁혔다.
- 429 응답을 API 명세 1-4 형식의 JSON으로 바꿨다 — 프론트가 `TOO_MANY_REQUESTS`로 정확히 인식하게 하기 위해서다(실제로 `api/client.js`에 429 응답을 넣어 확인).
- **1차만 반영하고 완료 처리하지 않는다**: 로그인·재발급 제한(2차)은 7.4.2 이후 대상 엔드포인트가 정해져야 구현할 수 있어, PR #148은 머지해도 Jira 이슈를 완료로 바꾸지 않기로 했다.
- 백엔드 감사 로그 IP(`forward-headers-strategy=native`)는 Nginx가 실제 사용자 IP를 올바르게 보는지 EC2에서 먼저 확인한 뒤에 켜기로 했다 — 먼저 켜면 위조된 `X-Forwarded-For` 값이 감사 로그에 그대로 기록될 위험이 있다.

### 고려한 제약 사항
- EC2 반영 후 Nginx 접속 기록의 IP가 실제 공인 IP인지 반드시 확인해야 한다(172.x 등 사설 대역이면 전체 사용자가 한 IP로 묶인다).
- 429는 백엔드 지표·Loki에 잡히지 않는다(로그 수집 도구가 백엔드 로그만 수집). 웹(Nginx) 로그 수집이 필요하면 후속 검토 대상이다.
- HTTPS(BE-75)로 443 server 블록이 추가될 때, 같은 `limit_req` 규칙을 443에도 반드시 적용해야 한다(놓치면 https 요청은 제한이 걸리지 않는다). 실제로 BE-75에서 두 server가 공용 snippet을 include하는 구조로 이를 구조적으로 보장했다(`docs/decisions/BE-75.md`).
- API 명세 이력 번호가 BE-74(v0.29)와 충돌해 BE-63을 v0.30으로 조정했다(BE-74 문서는 변경하지 않음).
