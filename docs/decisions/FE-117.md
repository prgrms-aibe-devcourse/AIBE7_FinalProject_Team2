# FE-117 의사결정 기록

## 문제 / 배경
- BE-113에서 아이디 회원가입(M-5) · 로그인(M-6) API가 생겼다. 화면은 가입 폼 · 로그인 폼이 이미 있었지만(FE-104) 실제 모드에서는 "준비 중"이었다.
- 로그인 화면은 아이디 · 비밀번호를 **모두 관리자 로그인(A-1 · A-2)에 먼저** 보냈다(FE-53). 회원 로그인이 생긴 뒤에도 그대로 두면
  ① 회원 비밀번호가 관리자 API로 가고 ② 관리자 감사 로그에 로그인 실패가 쌓이고 ③ 관리자 로그인 요청 제한(IP별 분당 5번)을 회원이 써서
  같은 와이파이의 관리자 · 회원이 429를 받고 ④ 요청마다 Argon2 비교를 두 번 한다.
- 아이디 회원이 생기면서 이용약관 · 개인정보처리방침의 "카카오 회원번호만 저장"이 사실과 달라진다.

## 검토한 대안
- 관리자 · 회원 구분: (A) 지금처럼 관리자 먼저, 실패하면 회원 / (B) 아이디에 `@`가 있으면 관리자, 없으면 회원 / (C) 관리자 로그인 화면을 따로(`/admin/login`)
- 로그인 뒤 액세스 토큰: (A) 로그인 응답 본문에서 받기 / (B) 카카오 콜백처럼 바로 M-1 재발급 호출
- 목 모드 관리자 구분: (A) 예전처럼 `admin` 접두어 / (B) 실제 모드와 같이 `@`

## 선택한 방법과 이유
- 구분 (B): 회원 아이디는 영문 · 숫자 · 밑줄만 받아(BE-113 결정 2) `@`가 있을 수 없고, 관리자는 이메일로 로그인한다. **계정 기준으로는** 겹치지 않아 한쪽 API만 부른다(`adminLoginRule.js loginTarget`).
  **입력 기준으로는** 회원이 실수로 자기 이메일을 넣으면 그 비밀번호가 관리자 로그인으로 간다(같은 서버 안이고, 관리자 실패와 같은 안내가 나온다). 이 경우는 `/admin/login` 분리(C)로만 완전히 없어진다.
  (A)는 위 문제 ①~④가 그대로고, (C)는 관리자 화면 · 라우터 · 메뉴를 새로 만들어야 해 이번 일정(M3 10/30)에 맞지 않는다.
- 토큰 (B): 서버가 리프레시 쿠키만 주고 본문에 토큰을 싣지 않는다(BE-113 결정 3). 카카오와 같은 흐름이라 `client.js`의 토큰 보관 방식을 바꾸지 않는다.
- 재발급 실패(`api/authFlow.js completeLogin`): 가입 · 로그인은 됐는데 재발급이 실패하면(연결 오류 · 429 · 5xx) 서버가 이미 심은 리프레시 쿠키가 남는다.
  화면은 실패로 보여 주므로 **로그아웃(M-2)으로 쿠키를 지워** 상태를 맞추고(공용 PC에서 로그인이 몰래 살아 있지 않게) `TOKEN_NOT_ISSUED`로 알린다.
  가입 화면은 "가입하지 못했어요" 대신 **"가입은 됐어요. 로그인해 주세요"** 로 안내한다 — 다시 누르면 409(이미 쓰는 아이디)를 보게 되기 때문이다 (PR 리뷰 반영).
- 화면 이탈: 가입 · 로그인을 기다리는 사이 다른 화면으로 가도 로그인 표시(`saveUser`)는 남기고 이동만 하지 않는다. 건너뛰면 서버는 로그인됐는데 헤더만 로그아웃으로 보인다 (PR 리뷰 반영).
- 목 모드 (B): 목과 실제가 다른 규칙이면 목 모드에서 확인한 분기가 실제와 달라진다. 목 가입의 `admin` 접두어 = 중복 아이디 안내는 화면 확인용이라 그대로 둔다.
- 실패 안내: 서버가 아이디 없음 · 비밀번호 틀림을 나누지 않으므로 화면도 "아이디 또는 비밀번호가 맞지 않아요" 한 문구로 알린다. 관리자 쪽 실패도 같은 문구다.
  가입의 중복 아이디(409)는 아이디가 있는지 드러나지만 가입 화면에서는 피할 수 없어 **의도적으로 허용**한다(Nginx 가입 요청 제한으로 대량 조회를 늦춘다, BE-113 결정 6).

## 고려한 제약 사항
- 가입 규칙은 서버와 같아야 한다: 비밀번호 최대 64자(서버 Argon2 비용 상한)를 화면 검사에 더했다. 닉네임은 FE-114에서 정리한 `utils/nickname.js`를 그대로 쓴다.
- 처리방침: 마이페이지에서 바꾸는 닉네임은 여전히 브라우저에만 저장된다(서버 닉네임 변경 API 없음). 서버에 저장되는 것은 **가입할 때 적은 닉네임**뿐이라 그렇게 나눠 적었다.
- 비밀번호 찾기는 없다(BE-113 범위 밖). 이름 · 이메일을 받지 않아 본인 확인 수단이 없으므로 약관에 "문의처로 알려 주세요"로 안내한다.

## 추후 재검토가 필요하면
- **닉네임이 두 곳에 있음**: 아이디 회원의 서버 닉네임(가입 때 값)과 브라우저 닉네임(마이페이지에서 바꾼 값)이 다를 수 있다. 다른 기기에서 로그인하면 서버 값(가입 때 이름)으로 돌아간다. 닉네임 변경 API가 생기면 마이페이지 저장을 서버로 옮긴다.
- **관리자 로그인 화면 분리(`/admin/login`)**: 관리자 화면을 따로 만들면 로그인 화면의 `@` 분기를 없앤다.
- **비밀번호 찾기 · 변경 · 탈퇴**: 서버 기능이 생기면 화면을 붙이고 약관 · 처리방침을 함께 고친다.
- **관리자 계정 이메일 형식**: `@` 분기는 관리자 계정 이메일에 `@`가 있다는 전제다. DB · 첫 계정 생성(`AdminBootstrap`)은 이를 강제하지 않는다 → 운영 계정은 확인했고(PR 확인 사항), 서버에서 `@`가 없는 부트스트랩 이메일을 거절하는 검사는 BE 후속으로 둔다.
- **이메일을 넣은 회원 안내**: 로그인 아이디 칸에 "회원 아이디에는 @가 없어요" 같은 안내를 둘지 화면 담당과 정한다.
- **만 14세 미만 가입**: 아이디 가입에 연령 확인이 없다. 약관 · 처리방침에 정책이 필요한지 법무 검토 때 함께 본다.
- **429 안내**: 서버가 주는 `Retry-After`(초)를 화면에 "N초 뒤 다시"로 보여 줄 수 있다. 지금은 공통 문구다.
