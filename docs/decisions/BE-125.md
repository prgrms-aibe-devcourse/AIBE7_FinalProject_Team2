# BE-125 의사결정 기록

`legal_case`에 배역(`cast_roles`) · 민감 플래그(`sensitive_flags`) 컬럼 추가, 적재 시 배정 · 기록, 공개 API 16 필드, 관리자 수정(A-11).

## 문제 / 배경

- 사건마다 내로 · 남불이 판사 · 검사(묶음 A)와 변호인 · 피고인 역(묶음 B)을 번갈아 맡기로 했다(COMMON-65, `character-profile-worldview.md` 5-2). 기준은 **범죄 유형별 균형이 연속 금지보다 우선**이고, 단일 출처는 `legal_case`다.
- 사건 분류(BE-123)가 켠 민감 플래그를 사건에 고정 저장하고, 사용자 안내(FE-129)와 대본 가드가 같은 값을 쓰게 해야 한다.
- 대본에는 캐릭터 이름이 들어가므로 배역은 **대본보다 먼저** 정해져야 한다. 처음 인수인계서는 2단계 등록(분류까지 → 적재하며 배정 → 그 배역으로 대본)을 **추천**했다(해송님이 택한 것이 아니다). 이 이슈는 어느 방식으로 가도 쓸 수 있게 "적재하며 배정"과 저장 · 공개 · 수정을 맡았다. 등록 방식은 10/29에 해송님이 **1회 방식**(처음 1회는 개입 없이 적재까지 자동, 관리자는 후검수)으로 정했다. 등록 요청의 범죄 유형으로 대본 전에 배정하는 연결과 `toPipelineRequest` 수정은 BE-129가 맡는다.

## 검토한 대안

### 1. 배역 저장 모양

- 대안 A: 칸 둘(`prosecutor_character` · `defense_character`) + DB CHECK. 검사가 DB에서 되지만, 공동 피고인 배역(COMMON-65 2차)이 생기면 칸과 마이그레이션이 늘어난다.
- 대안 B(채택): jsonb 한 칸 `{"prosecutor": "naero", "defense": "nambul"}`. `case_script.cast_roles`(V32) · 파이프라인 `stages.script.cast`와 같은 모양이라 옮길 때 변환이 없고, 키를 더하면 확장된다. 검사는 코드(`CastRoles.parse`: 키 둘, 내로 · 남불 하나씩)가 한다.

### 2. 민감 플래그 값 검사

- 대안 A: DB CHECK로 12종을 고정. 플래그 목록을 정하는 쪽은 파이프라인이라 값이 늘 때마다 CHECK를 다시 만들어야 한다. 감사 로그 CHECK에서 앞 마이그레이션의 값을 빠뜨리는 위험을 이미 겪었다(V32 · V34 머리말).
- 대안 B(채택): `keywords`처럼 열린 jsonb 배열로 두고, 코드 상수(`SensitiveFlag` enum)가 검사한다. 적재에서 모르는 값도 **이름 그대로 저장**하고 로그만 남기며(적재를 막지 않음), 공개 API는 아는 안내 대상만 내보낸다. 관리자 수정(A-11)에서는 모르는 값을 거절한다. 처음에는 모르는 값을 버렸는데, 파이프라인에 플래그가 늘고 enum이 못 따라가면 대본은 그 가드로 만들어졌는데 사건에는 기록이 없어 안내가 조용히 빠진다는 리뷰(PR #338)로 바꿨다. 두 목록이 같은지는 `SensitiveFlagContractTest`가 `script_assembler.py`를 읽어 비교한다.

### 3. 배정 규칙

- 대안 A: 같은 범죄 유형에서 마지막 배정의 반대. 단순하지만, 초기값이 쏠렸거나(살인 5 : 4) 관리자가 배역을 고친 유형에서는 쏠림이 그대로 이어진다.
- 대안 B(채택): 같은 유형에서 피고인 역을 **덜 맡은** 캐릭터가 맡고, 같으면 마지막 배정의 반대, 그 유형의 첫 사건이면 기본값(`defense = nambul`, 서비스 설정 기본값과 같다). 수가 같을 때는 A와 결과가 같고, 쏠렸을 때만 균형 쪽으로 간다. "균형이 연속 금지보다 우선"을 그대로 옮긴 규칙이다. 인수인계 때 정한 "마지막의 반대"를 이 규칙으로 보완했다.

### 4. 동시 적재

- 대안 A: 마지막 배정 사건 행을 `FOR UPDATE`로 잠근다. 두 적재가 같은 기존 행을 기다렸다 읽을 뿐이고, 막아야 할 것은 아직 없는 **새 행**이라 같은 배정이 나온다.
- 대안 B: SERIALIZABLE 격리. 직렬화 실패가 나면 적재 전체를 다시 시도해야 하는데, 적재는 일곱 표에 쓰는 긴 트랜잭션이라 재시도 경로를 새로 만들어야 한다.
- 대안 C(채택): 범죄 유형별 트랜잭션 권고 잠금(`pg_advisory_xact_lock(hashtext('legal_case_cast:' || crime_type))`). 같은 유형의 두 번째 적재는 첫 적재가 커밋될 때까지 기다리고, 그 뒤의 조회는 새 행까지 본다(READ COMMITTED). 다른 유형끼리는 서로 막지 않는다. 테스트로 잠금을 빼면 두 사건이 같은 배정을 받는 것을 확인했다(3회 중 3회).

### 5. 대본이 함께 온 적재의 배역

- 대안 A: 대본과 상관없이 규칙으로 배정. 대본은 이미 다른 배역으로 대사가 쓰여 있어 화면과 대사가 어긋난다.
- 대안 B(채택): 대본에 유효한 배역이 있으면 그 배역을 사건 배역으로 쓰고(규칙 배정과 같은 범죄 유형별 잠금을 잡는다), 대본이 없으면 규칙으로 배정한다. **대본에 배역이 있는데 읽을 수 없으면 규칙으로 덮지 않고 배정하지 않는다**(`cast_roles = null`, 생성 기록 `castWarning`에 남김). 대사에 대본의 배역 이름이 이미 들어 있어 규칙으로 정하면 화면과 대사가 어긋나기 때문이다(PR #338 리뷰). 파이프라인이 `prosecutor` · `defense` 밖의 키를 허용하게 되면 `CastRoles.parse`를 함께 넓힌다. 지금처럼 전역 설정 배역으로 대본까지 한 번에 돌리는 등록도 사건 · 대본 배역이 일치한다.

### 6. 공개 API 16에 내보내는 값

- 대안 A: 플래그 전체. 가드 전용 플래그 중 `CAPITAL_PENALTY`(법정형이 사형 · 무기)는 판결 전에 형량을 짐작하게 해 FR-2-8(판결 전 앵커링 방지)과 맞지 않는다.
- 대안 B(채택): 사용자 안내 대상 6종만. 관리자 상세(A-6)는 전체를 보인다.
- 값이 없을 때: `[]` · `null`로 내보내는 안과 필드를 빼는 안 중, 인수인계 결정대로 **필드를 뺐다**(배정 전 · 안내할 플래그 없음 → 화면 기본 동작). 같은 파일의 다른 필드(`myStatus`)는 `null`로 내보내므로 필드 단위로 `@JsonInclude(NON_NULL)`을 붙였다.

### 7. 관리자 수정 경로

- 대안 A: 새 API(`PUT /admin/cases/{id}/cast` 등). 경로 · 권한 · 감사 로그를 새로 만든다.
- 대안 B(채택): A-11(사건 내용 수정)에 두 필드를 더한다. 공개 사건 수정 금지 · DRAFT → REVIEW · 행 잠금 · 감사 로그(`CASE_UPDATE`)를 그대로 쓴다. 감사 로그에는 원래 필드 이름만 남기지만, 이 두 필드는 짧고 자동 결과를 사람이 뒤집은 기록이라 바꾼 값까지 남긴다.
- `castRoles: null`과 `sensitiveFlags: null`은 거절한다. 배정을 지우면 균형 계산에서 빠지고, 플래그 `null`은 "분류 전"이라 되돌릴 이유가 없다(모두 끌 때는 `[]`).

### 8. 이미 적재된 사건의 초기값

- 대안 A: 공개 마이그레이션에 UPDATE를 넣는다. 사건 식별 정보가 공개 저장소에 들어간다.
- 대안 B(채택): 공개 마이그레이션(V37)에는 컬럼만, 값은 비공개 시드 저장소의 1회 실행 수정 SQL(`loads/fixes/`)로 넣는다. 배역은 사건별 재연 컷 이미지를 뽑은 배정과 같게 했다(사진 속 배역과 대본 배역을 맞추기 위해, 해송님 확인). 1심 사건번호로 사건을 찾고, 두 칸이 비어 있는 사건만 고치며, 한 건이라도 1행이 아니면 전체를 되돌린다.

## 선택한 방법과 이유

- 위 각 항목의 채택안. 공통 기준은 **기존 관례와의 일관성**(jsonb 열린 목록 · A-11 · 감사 로그 · 1회 실행 수정 SQL)과 **대본과 사건 배역의 일치**다.
- 적재는 `result.classify.classification.sensitiveFlags`만 읽는다. 분류를 돌리지 않은 등록은 `null`(분류 전)로 남겨 "분류했고 켜진 것 없음(`[]`)"과 구분한다.

## 고려한 제약 사항

- 파이프라인은 DB를 모르고, 사건(`legal_case`)은 적재 때 생긴다. 그래서 배정 시점은 적재다.
- 관리자 A-11은 공개 사건을 고칠 수 없다(API 명세 8-3 #1). 공개 뒤 플래그 · 배역을 고치려면 공개 취소(A-13-14) → 수정 → 다시 공개다. 사진 교체(BE-103)와 같은 절차다.
- `docs/decisions/`는 공개 저장소다. 사건별 배정표 · 분류 결과는 이 문서에 적지 않았다(비공개 시드 저장소 수정 SQL과 Jira BE-125 댓글에 있다).

## 추후 재검토가 필요하면

- **중간 상태**: BE-125만 머지되면 배역이 저장되지만, 서비스 등록은 여전히 `toPipelineRequest`의 전역 설정 배역으로 대본을 만들고 `classify`를 켜지 않는다. 그래서 새 등록의 민감 플래그는 BE-129 전까지 `null`이고, 대본이 함께 오는 등록은 대본 배역(전역 값)이 사건 배역이 된다. BE-129를 바로 이어서 한다.
- **범죄 유형은 등록 요청에 이미 있다**: 사건 등록 요청(A-14)에 관리자가 고르는 `crimeType`이 있다(`case_import.crime_type`). 인수인계 문서의 "범죄 유형은 extract가 정하므로 대본 전에 배정할 수 없다"는 전제와 다르다.
  - 1회 방식과 2단계 방식을 가르는 실제 기준은 **관리자가 분류 결과(민감 플래그 · 분위기)를 확인하는 자리를 지킬지**다. 1회 방식은 분류가 틀려도 그 플래그와 가드로 대본(약 3만 토큰)이 바로 만들어진다. 2단계는 처음에 배역 때문에 추천했고 확인 자리는 곁들인 이점이었다. 필수 요건으로 정해진 적은 없고, 10/29에 해송님이 확인 자리를 필수로 두지 않는 **1회 방식**으로 정했다(검수에서 분류를 고치면 대본만 다시 만든다).
  - 1회로 가려면 먼저 요청의 범죄 유형과 추출 결과(`case.json`)의 범죄 유형이 같아야 한다. 지금은 어디서도 잡지 않아 양형기준(요청값)과 사건 유형(추출 값)이 달라질 수 있다. 이 점검은 **BE-138**로 분리했다.
  - **`needsReview` 게이트의 대체(10/30 해송님, PR #346 리뷰)**: BE-123은 "`needsReview`가 있으면 관리자 확인 전에는 대본을 만들거나 공개하지 않는다"고 적었지만, 1회 방식은 멈추지 않고 적재까지 간다. 그래서 **생성 게이트는 대체**한다 — 대본은 끝까지 만들고 `needsReview`는 검수 화면에 표시한다(BE-129). **공개 게이트는 그대로** 관리자 승인이 지킨다(최초 통승인 · 거절 뒤 블록 승인, BE-126). 이유: 안내 대상 플래그가 잘못 켜지면 안내문이 잘못 뜨고 놓치면 안내가 빠지는데, 둘 다 공개 전에 사람이 보면 막을 수 있어서다. **한계**: 모델이 일관되게 틀리거나 놓친 항목(분위기 오분류, 레드플래그 누락)은 표가 갈리지 않아 `needsReview`가 뜨지 않는다. 이는 사람이 [대본 최종 검수 체크리스트](../script-final-review-checklist.md)로 잡는다.
  - 실패 · 취소된 등록이 배정 수에 섞이는 문제는 1회 방식에서도 남는다. BE-129에서 다시 비교한다.
- 배역을 A-11로 바꿔도 이미 만든 대본(`case_script`)은 그대로라 API 16의 `cast`와 API 18의 `cast`가 달라질 수 있다. 대본 재생성 경로는 BE-129에서 정한다.
- 분위기 · 쟁점 등 나머지 분류 값은 저장하지 않았다. 2차 작업(대본)에 관리자가 확인한 분류를 넘기려면(인수인계 "설계 문제 2", 정신건강 사건의 냉혹 톤) 저장 위치가 필요하다 — BE-129에서 정한다.
- `needsReview`(표가 갈린 플래그)도 저장하지 않았다. 관리자 화면에서 "확인 필요" 표시가 필요해지면 함께 저장한다.
