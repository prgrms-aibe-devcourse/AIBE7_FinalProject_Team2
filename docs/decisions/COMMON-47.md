# COMMON-47 의사결정 기록

> 근거: Jira COMMON-47(운영 S3 반영 세팅 적용), [`deploy/README.md`](../../deploy/README.md) "파일 저장소 S3". 파일 API 구현은 별도 담당자가 진행한다.

## 문제 / 배경
- 파일 업로드 기능을 위해 운영 환경에 S3 저장소가 필요하다. 버킷 · IAM 설정은 AWS 콘솔에서 끝났고, 이번 작업은 애플리케이션 · 배포 설정을 그에 맞추는 일이다.
- 지금 요청 경로는 업로드를 받을 수 없다. Nginx `client_max_body_size`가 1m(JSON 요청만 있어 의도적으로 둔 값)이고, Spring multipart도 기본값(파일 1MB)이다.
- 공개 저장소이므로 키 · 계정 ID · 실제 버킷 이름 · IAM 역할 이름을 저장소에 두지 않아야 한다.

## 검토한 대안
- **인증 방식**
  - 대안 A — 접근 키를 서버 `.env`에 두고 Compose로 넘김: 설정은 단순하지만 장기 비밀값이 서버 파일에 남고, 교체 · 유출 대응을 사람이 해야 한다.
  - 대안 B — EC2 인스턴스에 IAM 역할을 연결하고 SDK 기본 자격증명 체인으로 받음: 비밀값이 저장소 · 서버 파일 어디에도 없고 자격증명은 자동으로 갱신된다. 대신 컨테이너가 인스턴스 메타데이터(IMDSv2)에 닿아야 한다.
- **업로드 용량을 어디에서 올릴지**
  - 대안 A — 업로드 API 경로에만 큰 상한을 두고 나머지 `/api`는 1m 유지: 노출 범위가 가장 좁지만, 업로드 API 경로가 아직 정해지지 않았다(API는 별도 담당자가 구현).
  - 대안 B — `app.conf`의 공통 상한을 20m로 올림: 경로가 정해지지 않아도 바로 쓸 수 있고, 80 · 443 server가 같은 snippet을 include하므로 두 곳이 어긋나지 않는다(BE-75 구조).
- **버킷 이름 기본값**: `application.yml`에 운영 버킷 이름을 기본값으로 둘지, 비워 둘지.

## 선택한 방법과 이유
- **인증은 대안 B(EC2 IAM 역할 + `DefaultCredentialsProvider`)**. 역할 정책은 이 버킷의 객체 읽기 · 쓰기 · 삭제 · 목록만 허용한다(최소 권한). `AWS_ACCESS_KEY_ID` · `AWS_SECRET_ACCESS_KEY`는 `.env` · Compose · 코드에 넣지 않는다 — 넣으면 SDK가 역할보다 그 키를 먼저 쓰기 때문에, 남아 있으면 역할 설정이 무력해진다.
- **IMDSv2 응답 홉 제한을 2로 둠**: 기본값 1이면 Docker 브리지 네트워크를 한 번 더 거치는 컨테이너 안에서는 토큰 응답을 받지 못한다. host 네트워크로 바꾸는 대신 홉 제한만 늘려 기존 Compose 네트워크 구성을 유지했다.
- **용량은 대안 B(공통 20m)**, Spring은 파일 10MB · 요청 20MB. Nginx 상한과 Spring `max-request-size`를 같은 값으로 맞춰, 어느 한쪽만 작아서 생기는 원인 찾기 어려운 실패(413 또는 백엔드 오류)를 막는다. 두 파일 주석에 "함께 고친다"를 남겼다.
- **버킷 기본값은 비워 둠(`${S3_BUCKET_NAME:}`)**: 환경변수를 빠뜨린 로컬 실행이 운영 버킷에 쓰지 않도록 안전한 쪽에 둔다. 로컬은 `S3_DIR_PREFIX=local`로 경로를 나눌 수 있게 `dir-prefix` 키를 두었다.
- **설정 키 이름(`cloud.aws.region` · `cloud.aws.s3.bucket` · `cloud.aws.s3.dir-prefix`)을 이번 PR에서 먼저 정함**: API 담당자가 같은 키를 읽도록 Jira 이슈에 전달 사항으로 남겼다.

## 고려한 제약 사항
- 공개 저장소: 실제 버킷 · 역할 · 정책 이름은 서버 `.env`와 AWS 콘솔에만 둔다. 문서에는 `<운영 버킷 이름>` 같은 자리표시자만 쓴다.
- 환경변수는 컨테이너를 새로 만들어야 반영된다. 서버에서 backend를 다시 만들 때 지금 쓰는 Compose 덧붙임 파일(`-f`) 조합을 빼면 그 설정이 사라지므로 README에 경고를 남겼다.
- 버킷이 비어 있으면 S3를 쓰는 기능만 동작하지 않고, 서버 기동 · 기존 기능에는 영향이 없다.

## 추후 재검토가 필요하면
- 업로드 API 경로가 정해지면, `/api` 공통 상한을 다시 1m로 낮추고 업로드 경로에만 20m를 두는 방식(용량 대안 A)을 검토한다.
- 파일 API 보안(로그인 필수, 소유자 검증, 파일 형식 화이트리스트)은 API 구현 PR에서 확인한다.
