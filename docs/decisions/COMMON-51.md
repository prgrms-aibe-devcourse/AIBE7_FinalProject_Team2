# COMMON-51 의사결정 기록

> COMMON-50(PR #219) 리뷰에서 나온 후속 항목. 파이프라인 서비스가 **오래된 작업을 스스로 지우게** 한다.

## 문제 / 배경
- 작업 폴더에는 **판결문 원문**이 들어 있다(`raw/`, `cases/job-<id>.source_internal.json`). 지금은 관리자가 검수를 마친 뒤 백엔드가 `DELETE /jobs/{id}`를 부르는 것에 전적으로 기대고 있다.
- 그 호출이 빠지는 경우가 있다: 백엔드가 삭제 직전에 재시작 · 교체되거나, 검수가 미완으로 남거나, 호출이 실패하고 재시도되지 않는 경우. 그러면 원문이 볼륨에 무기한 남는다 — 요구사항 FR-5-3("원본 판결문 정보는 내부 전용")의 마지막 안전장치가 없는 셈이다.

## 검토한 대안

### 1. 보관 기간(N)을 어떻게 정할까
- 대안 A — 운영에서 파이프라인을 돌려 실제 검수 소요 시간을 본 뒤 숫자를 정하고 그때 구현한다. 이슈가 처음 권한 방식이고, 근거 있는 숫자가 나온다. 다만 **그때까지 안전장치가 없다** — 안 지워지는 문제는 지금도 일어날 수 있다.
- 대안 B(선택) — **보수적인 기본값(7일) + 환경변수(`PIPELINE_JOB_RETENTION_DAYS`)**. 지금 안전장치를 켜 두고, 운영 관찰 뒤에는 값만 바꾼다(코드 · 배포 변경 없음). `0` 이하를 "정리 끔"으로 둬서, 문제가 생기면 값 하나로 멈출 수도 있다.
- 7일로 정한 이유: 검수가 하루 이틀에 끝난다면 넉넉하고, 반대로 너무 길어 원문이 오래 남지도 않는다. 애매하면 **지우지 않는 쪽**으로 기울인 값이다 — 잘못 지우면 되돌릴 수 없고, 다시 돌리려면 원문을 다시 올려야 한다.

### 2. 나이를 무엇으로 잴까
- 대안 A — `finishedAt`만 본다. 깔끔하지만 **끝을 기록하지 못한 작업**(시작 실패, 프로세스가 죽어 `_settle`이 돌지 못한 경우)은 영영 남는다. 그런 작업도 원문을 품고 있다.
- 대안 B(선택) — `finishedAt` → `createdAt` → **작업 폴더 수정 시각** 순으로 본다. 마지막 단계가 중요하다: `job.json`이 없거나 깨진 폴더도 `raw/`에 원문이 있을 수 있는데, 읽을 값이 없다고 건너뛰면 **정리에서 영영 빠지는 폴더**가 생긴다. 안전장치가 가장 필요한 경우가 바로 메타가 망가진 경우다.

### 3. 지우는 범위를 따로 만들까
- 기존 `JobStore.delete`를 **그대로 쓴다**. 이 함수는 네 군데(작업 폴더 · `out/pipeline` · `cases` · `out/runs`)를 지우는데, 그 범위는 PR #219 리뷰에서 "작업 폴더만 지우면 원문이 남는다"를 발견하고 정한 것이다. 정리용 삭제를 따로 만들면 **같은 실수를 한 번 더 할 자리**가 생긴다.
- 덤으로 `delete`는 도는 작업이면 `JobConflict`를 던진다 — 정리가 "살아 있나" 확인한 뒤 실제로 지우기까지 사이에 작업이 시작돼도 안전하다.

### 4. 어떻게 주기 실행할까
- 대안 A — APScheduler · Celery 같은 스케줄러. 작업 하나를 지우는 데 파일 삭제 몇 번이 드는 일에 의존성과 운영 거리를 늘릴 이유가 없다(파이프라인 도구는 표준 라이브러리만 쓴다는 원칙도 있다).
- 대안 B(선택) — **데몬 스레드 하나 + `threading.Event`**, FastAPI `lifespan`에 붙인다. 워커가 1개라(`--workers 1`) 스레드도 하나뿐이고, 내려갈 때 `Event`로 즉시 깨워 정리한다. 6시간 간격 — 보관 기간이 날 단위라 더 자주 돌아도 지워지는 시점이 의미 있게 빨라지지 않는다.
- 루프는 `jobs.py`에 두고 스레드만 `app.py`에서 띄운다. `jobs.py`는 FastAPI에 기대지 않는다는 기존 구조를 지키고, 덕분에 **루프 자체를 FastAPI 없이 테스트**할 수 있다(가짜 `Event`로 즉시 멈춘다).

## 선택한 방법과 이유
- `JobStore.cleanup(retention_days=None, now=None)` — 끝난 작업 중 마지막 기록이 보관 기간보다 오래된 것을 `delete`로 지우고, 지운 ID 목록을 돌려준다. 인자 둘은 테스트에서 시간을 직접 주기 위한 것이다(기다리지 않는다).
- `run_cleanup_loop(store, stop, interval)` — 뜨자마자 한 번, 그 뒤 간격마다. **한 번 실패해도 끝내지 않는다**: 정리가 조용히 멈추면 원문이 남는 것을 아무도 모르게 된다. 한 작업 삭제가 실패해도 나머지는 계속 지우고 다음 주기에 다시 시도한다.
- 로그에는 **작업 ID와 마지막 기록 시각만** 남긴다. 원문 · 내용은 남기지 않는다(FR-5-3, 기존 로그 정책과 같다).
- **루트 로거를 `app.py`에서 설정한다.** 처음에는 `logger.info`만 넣었는데, 실제 uvicorn으로 띄워 보니 지우는 동작은 되는데 **로그가 한 줄도 찍히지 않았다** — uvicorn은 자기 로거(`uvicorn*`)만 설정하고 루트에는 핸들러를 두지 않아 INFO가 그대로 버려진다. "지운 작업은 추적 가능해야 한다"가 이 이슈의 완료 조건이라, 그대로 뒀으면 **조용히 조건을 못 지키는** 상태였다. uvicorn이 로깅을 먼저 설정한 뒤 app 모듈을 불러오므로 진입점에서 `basicConfig`를 부르면 서로 덮어쓰지 않는다(실제로 띄워 확인).

## 고려한 제약 사항
- "도는 작업은 건드리지 않는다"가 이슈의 명시 조건이다. 며칠째 도는 작업도 마찬가지로 두고, 끝난 뒤 다음 주기에 지워진다. 멈춘 것처럼 보이는 작업을 정리가 알아서 죽이지는 않는다 — 그건 `POST /jobs/{id}/cancel`이 할 일이고, 사람이 판단한다.
- 운영 볼륨은 컨테이너를 다시 만들어도 남는다(`pipeline-out` · `pipeline-cases`). 그래서 서비스를 다시 띄우는 것만으로는 아무것도 지워지지 않고, 이 정리가 없으면 정말로 무기한 쌓인다.
- 테스트는 네트워크 · 실제 대기 없이 돈다(이슈 완료 조건). 시간은 `now=` 인자로, 주기는 가짜 `Event`로 대신한다.

## 추후 재검토가 필요하면
- **보관 기간 7일**은 운영 관찰 전의 값이다. 파이프라인을 운영에서 돌려 본 뒤(7.1.2 RDS 전환 이후) 실제 검수 소요 시간을 보고 `PIPELINE_JOB_RETENTION_DAYS`로 조정한다. 코드를 고칠 일은 아니다.
- 지금은 **지운 사실이 서비스 로그에만** 남는다. 나중에 "그 작업 어디 갔나"를 자주 묻게 되면 지운 기록을 따로 남기는 방법(가벼운 JSON 한 줄 등)을 보되, 원문 · 사건 내용은 넣지 않는다.
- 삭제 호출이 빠지는 **근본 원인**(백엔드가 검수 뒤 `DELETE`를 확실히 부르게 하기)은 이 이슈 범위 밖이다. 이 정리는 그 경로가 실패했을 때의 그물이지 대체재가 아니다.
