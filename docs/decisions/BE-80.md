# BE-80 의사결정 기록

> 근거: [#153 리뷰](https://github.com/prgrms-aibe-devcourse/AIBE7_FinalProject_Team2/pull/153) 후속 결정, [`ai-judgment-pipeline.md`](../ai-judgment-pipeline.md) 3장 ①, ERD v1.24.

## 문제 / 배경
- BE-53에서 요약어 후보를 계산해 파이프라인 보고서(`report.json`)에만 남겼다. 관리자가 후검수 화면에서 근거로 보려면 DB에 저장하고 A-6으로 내려 줘야 한다.

## 검토한 대안
- **저장 위치**
  - 대안 A: 별도 테이블(`factor_summary_tag_candidate`, 후보 한 줄씩). 질의는 자유롭지만 테이블 · 엔티티 · 리포지토리가 늘고, 후보로 검색할 일이 없다.
  - 대안 B: `factor`에 jsonb 칸 하나. 가치관 축 투표 기록(`value_axis_votes`, V10 · BE-48)과 같은 방식이다.
- **이미 적재된 사건**
  - 대안 C: 가치관 축처럼 다시 적재할 때 후보도 맞춘다.
  - 대안 D: 새 사건을 넣을 때만 넣고, 이미 적재된 사건은 건드리지 않는다.

## 선택한 방법과 이유
- **B + D.**
- B: 후보는 요소 하나에 딸린 읽기 전용 기록이라 jsonb 하나로 충분하고, 기존 패턴과 같아 적재 SQL · 엔티티 · A-6 변경이 각각 한두 줄이다.
- D: 후보는 extract 때 정해진다. 이미 적재된 사건을 다시 맞추는 경로(`--from axis`)는 축만 다시 투표하는 경우라 후보가 바뀌지 않는다. 다시 extract하면 요소 자체가 달라질 수 있어 번호 · 라벨로 맞추는 것도 믿기 어렵다.
- 마이그레이션은 **추가만**(nullable 칸) 한다. 자동 배포가 이전 앱으로 되돌려도 뜬다(#161 리뷰에서 제안한 규칙).

## 고려한 제약 사항
- 요약어 자체를 바꾸는 API는 없다. 이 이슈는 제안을 보여 주는 데까지다.
- 형식 검사는 적재 SQL을 만들 때 한다(`check_summary_tag_candidates`). 형식이 틀리면 적재 SQL을 만들지 않는다.

## 추후 재검토가 필요하면
- 관리자 화면(S-19) 표시는 A 후속. 관리자가 제안을 받아들이는 기능(요약어 수정)이 필요해지면 A-11에 요약어 필드를 더하는 쪽으로 검토한다.
