# FE-137 의사결정 기록

> 근거: BE-115(커뮤니티 API, API 명세 12장) · BE-139(닉네임 설정 M-7 · 내 회원 정보 M-8) · FE-47 · FE-116(화면 목 계약)

## 문제 / 배경
- 커뮤니티 화면은 목 모드(`communityMockApi.js`)로만 동작했고 실제 모드는 "준비 중"이었다. 닉네임은 내 정보 수정이 이 브라우저의 로그인 표시값(session)에만 저장했다.
- 서버가 커뮤니티 API와 닉네임 · 회원 정보 API를 갖게 되어 화면을 잇는다.

## 검토한 대안
- 오류 코드: A 목의 임시 코드 `LOGIN_REQUIRED`를 서버 응답에서 바꿔 준다 / B 서버 코드 `UNAUTHORIZED`로 화면 · 목을 맞춘다(선택)
- 사진 올리기: A 사진 칸을 두고 서버 400을 보여 준다 / B 실제 모드에서는 칸을 숨긴다(선택) / C 사진을 조용히 버린다
- 카카오 회원(닉네임 없음)의 표시 이름: A 화면의 "카카오 회원" 고정 문구 / B 서버 표시 이름(`displayName`, 없으면 `방청객 {회원 ID}`)을 쓴다(선택, 사용자 결정으로 회원 정보 API를 함께 만들었다)
- 닉네임 칸의 초기값: 자동 이름을 채운다 / 비운다(선택)

## 선택한 방법과 이유
- **`UNAUTHORIZED`로 통일**: 목의 코드는 "API 설계 때 BE와 확정한다"는 임시 이름이었다. 서버가 401 `UNAUTHORIZED`로 정했으므로 목 · 화면 · 목 테스트를 맞춘다. `client.js`가 401을 한 번 재발급한 뒤 다시 보내고, 그래도 401이면 이 코드가 화면까지 온다.
- **사진 칸은 실제 모드에서 숨긴다**: 서버가 `images`가 있으면 400이라, 올려 놓고 거절당하는 것보다 처음부터 보이지 않는 편이 낫다. 목 모드는 그대로 사진을 쓴다(`PHOTO_UPLOAD = API_MODE === 'mock'`). 사진이 서버에 생기면 이 한 줄을 지운다.
- **표시 이름은 서버 값**: 카카오 콜백이 재발급 뒤 `getMe()`로 `displayName`을 받아 로그인 표시를 남긴다(못 받으면 예전 임시 문구 `카카오 회원`). 닉네임 칸은 **정하지 않은 회원이면 비워 두고** 안내 문구만 둔다 — 표시 이름 `방청객 {회원 ID}`는 공백이 있어 닉네임 형식이 아니라, 채워 넣으면 저장할 수 없다(`isUnnamed`). 바뀌지 않은 칸은 다시 저장하지 않는다.
- **저장 순서**: 닉네임(서버 M-7)과 한 줄 소개(P-8)를 따로 저장하고, 한쪽이 실패해도 다른 쪽은 저장한다. 닉네임 중복(409) · 형식(400)은 닉네임 칸 아래에 고칠 방법으로, 그 밖의 실패는 저장 결과 줄에 알린다. 성공했을 때만 session을 바꾼다(예전에는 서버 없이 먼저 바꿨다).
- **목에도 `putNickname`을 둔다**: 목 모드에서도 같은 경로(`api.putNickname`)를 타게 해 화면 코드에 분기를 두지 않았다. `중복`으로 시작하는 닉네임은 중복으로 보아 오류 화면을 확인할 수 있다(admin 아이디와 같은 방식). `getMe`는 목에 두지 않는다 — 목 모드 계정 정보는 예전 안내 그대로다.

## 고려한 제약 사항
- 닉네임 · 회원 정보 연동은 BE-139(PR #343)가 병합되어야 실서버에서 동작한다. 그 전에는 실제 모드에서 `putNickname`이 404를 받아 "저장하지 못했어요"가 나온다.
- 실제 서버 · 실제 브라우저로 끝까지 확인하지는 못했다(node 테스트 · 빌드까지). 사파리 확인은 사용자가 한다.
- 닉네임 변경이 커뮤니티의 이전 글 · 댓글 이름에도 반영된다(서버가 회원에서 읽는다, BE-115 · BE-139 결정).

## 추후 재검토가 필요하면
- 사진 올리기가 서버에 생기면 사진 칸을 다시 연다.
- 탈퇴 · 비밀번호 변경 API가 생기면 내 정보 수정의 준비 중 문구를 바꾼다.
