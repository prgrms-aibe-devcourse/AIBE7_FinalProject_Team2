# BE-112 의사결정 기록

범죄 유형 강도(ROBBERY) · 절도(THEFT) 추가 — 스키마 · enum 담당(D). PR #297.

## 문제 / 배경

- 확정 사건 21건 중 기존 세 유형(살인 · 사기 · 상해)에 들어가지 않는 사건이 있어, 범죄 유형을 넓혀야 했다(범죄 유형 추가 B안).
- 범죄 유형 값은 DB CHECK 4곳(`sentence_range_option` · `legal_case` · `rag_precedent` · `case_import`)과 `CrimeType` enum에 같은 문자열로 들어 있고, 사전 판단 형량 구간(S-03)은 유형별 고정 데이터다.
- 화면(A, FE-111) · 파이프라인 · RAG(B)가 이 enum 값을 받아 동시에 진행하므로 값 이름과 구간을 먼저 확정해야 했다.

## 검토한 대안

### 1. 어떤 유형을 새로 만들 것인가

- 대안 A — 강도 · 절도를 기존 유형에 흡수(예: 강도상해 → `INJURY`, 절도 → `FRAUD`와 같은 재산범죄): 마이그레이션이 필요 없지만, 사전 판단 구간이 법정형과 맞지 않는다(강도는 법정형에 벌금이 없는데 사기 구간에는 벌금형이 있다). 목록 필터 · 통계에서 죄명과 유형이 어긋난다.
- 대안 B — 강도 · 절도를 새 유형으로 만들고, 상해치사 · 폭행치사는 기존 `INJURY`에 흡수 (**선택**): 법정형 구조가 다른 죄만 유형을 나누고, 결과가 사망이어도 행위가 상해 · 폭행인 죄는 상해와 같은 구간 · 분류로 충분하다.
- 대안 C — 위험운전치사상까지 새 유형으로 추가: 확정 사건이 없어 구간 · 분류를 검증할 데이터가 없다. 사건이 생기면 같은 방식으로 추가한다.

### 2. 강도의 사전 판단 구간

- 공통 7개 그대로 / 살인처럼 벌금형을 빼고 무기징역 · 사형을 더한 8개 / 벌금형을 빼고 무기징역만 더한 7개 (**선택**).
- 강도(강도치상 · 강도상해 포함)는 법정형에 벌금이 없고, 강도상해 · 강도치상은 무기 또는 7년 이상이다. 사형이 법정형에 있는 강도살인은 이번 범위가 아니라 사형 구간을 두지 않는다.

### 3. 절도의 사전 판단 구간 — 상한 쪽도 자를 것인가

- 대안 A — 법정형 상한에 맞춰 "실형 10년 이상 ~ 20년 미만" · "실형 20년 이상"을 뺀다: 실제로 선고될 수 있는 구간만 남는다.
- 대안 B — 공통 7개를 그대로 쓴다 (**선택**).
- 구간을 자르는 기준을 **"법정형에 없는 형벌 종류(벌금 · 무기 · 사형)는 빼거나 더한다"** 로 정했다. 기간 구간은 형벌 종류가 아니라 길이의 눈금이라 유형마다 다르게 자르지 않는다. 이유는 다음과 같다.
  - 사전 판단은 "처음 생각"을 받는 단계라, 실제 선고 범위보다 무겁게 고르는 것도 의미 있는 응답이다. S-08이 "처음 생각보다 가벼운 판결"을 보여 주는 근거가 된다.
  - 사기도 공통 7개를 쓰고 있어(단순 사기 법정형은 10년 이하) 기존 관례와 같다. 특가법 절도는 가중 처벌로 상한이 높아질 수 있어 유형 단위로 상한을 자르기도 어렵다.
  - 유형마다 구간 개수 · 이름이 달라지면 화면(S-03) · 비교(S-08) 문구가 유형별로 갈라진다.

### 4. CHECK 4곳을 바꾸는 방식

- 대안 A — `DROP CONSTRAINT` → `ADD CONSTRAINT ... CHECK` (**선택**)
- 대안 B — `ADD CONSTRAINT ... NOT VALID` → 후속 마이그레이션에서 `VALIDATE CONSTRAINT` (CodeRabbit · 리뷰 제안): 큰 테이블에서 기존 행 검증 중 잠금 시간을 줄인다.
- 대안 C — 허용 값을 참조 테이블(`crime_type` 마스터) + FK 또는 PostgreSQL enum type으로 옮겨 4곳 중복을 없앤다.
- A를 택했다. 대상 테이블이 모두 작아(형량 구간 22행 · 사건 수십 건 · 등록 건수 · MVP 판례 규모) 기존 행 검증은 밀리초 단위다. B는 `DROP` · `ADD` 자체의 `ACCESS EXCLUSIVE` 잠금은 그대로이고, 검증용 마이그레이션이 하나 더 생겨 열린 PR들과 Flyway 번호가 겹칠 위험만 커진다. C는 구조 변경이 커서 이번 범위를 넘는다. 4곳 중복은 `DbConstraintTest`가 enum과 허용 값 집합이 같은지 검사해 막는다.
- `DROP CONSTRAINT`에 `IF EXISTS`를 두지 않았다. 이름이 다른 환경에서 건너뛰면 옛 CHECK(3개 값)가 남은 채 마이그레이션이 성공하고, 강도 · 절도 저장이 나중에 실패한다. 적용 시점에 바로 실패하는 쪽이 원인을 찾기 쉽다.

## 선택한 방법과 이유

- 새 유형 `ROBBERY` · `THEFT`, 화면 분류명은 둘 다 "재산범죄". enum은 맨 뒤에 추가했다(`@Enumerated(STRING)`이라 기존 행 영향 없음).
- 형량 구간: 강도 7개(벌금형 제외 + 무기징역, ID 23 ~ 29), 절도 7개(공통, ID 30 ~ 36). ID는 V1과 같이 `INSERT ... SELECT ... ORDER BY`의 삽입 순서에 의존한다.
- 양형기준 버전 자동 연결은 살인만 데이터가 있어 바꾸지 않았다(`CaseImportLoader` 변경 없음). 강도 · 절도는 양형기준 없이 만들어진다.
- API 명세(v0.55)의 값 목록도 이 PR에서 함께 고쳤다. 구현이 바뀌는 시점에 명세가 뒤처지지 않게 하려는 것이다(PR #297 리뷰).

## 고려한 제약 사항

- **Flyway out-of-order가 꺼져 있다(기본값).** V30(BE-106 #294)보다 V31이 먼저 적용된 DB는 나중에 V30을 받지 못해 검증에 실패한다. 그래서 #294를 먼저 머지했다.
- 공용 개발 DB(Supabase, COMMON-59)는 담당자가 develop 기준으로만 마이그레이션을 적용한다. 적용 전에 CHECK 4개 이름이 실제로 있는지 확인한다.

  ```sql
  -- 4행이 나와야 한다
  SELECT conname FROM pg_constraint
  WHERE conname IN ('chk_sentence_range_option_crime_type', 'chk_legal_case_crime_type',
                    'chk_rag_precedent_crime_type', 'chk_case_import_crime_type');
  ```

- 백엔드에서 범죄 유형으로 분기하는 코드는 없다(결과 · 비교 로직은 구간 종류 `kind`로만 판단). 사건 목록 `summary.byCrimeType`은 `CrimeType.values()`로 만들어 새 키가 자동으로 생긴다.

## 추후 재검토가 필요하면

- **범죄 유형 허용 값 4곳 중복**: 유형을 추가할 때마다 CHECK 4곳을 고쳐야 한다. 유형이 더 늘어나면 참조 테이블(`crime_type` 마스터) + FK 또는 PostgreSQL enum type으로 옮기는 안을 검토한다. 그 전까지는 `DbConstraintTest`가 enum과 4곳의 허용 값이 정확히 같은지 확인한다.
- **CHECK 교체 시 잠금**: `rag_precedent`가 수십만 행 규모로 커지면 `ADD CONSTRAINT ... NOT VALID` → 후속 마이그레이션 `VALIDATE CONSTRAINT` 2단계로 바꾼다.
- **위험운전치사상 · 강도살인**: 확정 사건이 생기면 같은 방식으로 추가한다. 강도살인은 강도 구간에 사형을 더할지, 별도 유형으로 둘지 그때 정한다.
- **절도 상한 구간**: 사용자 응답이 "실형 20년 이상"에 거의 없고 화면에서 혼란을 준다는 피드백이 있으면, 유형별 상한 자르기를 다시 검토한다.
- **RAG 판례**: 강도 · 절도 판례가 아직 없어 유사 판례 검색이 빈 결과를 돌려준다(예외 없이 진행). 판례 적재는 B 담당이다.
