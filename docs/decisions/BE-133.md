# BE-133 의사결정 기록

회원가입 약관 동의 서버 검증 및 동의 기록 저장 (BE-113 후속). 담당 D(정민석).

## 문제 / 배경

- 가입 화면(FE-117)은 약관 동의 체크를 강제하지만 서버(M-5, BE-113)는 동의 여부를 받지도 검증하지도 않았다.
  - 2026-10-29 운영 점검: `agree: false`로 보내도 형식 검사를 통과해 중복 아이디 검사(409)까지 진행됐다. 화면을 거치지 않고 API를 직접 부르면 동의 없이 가입할 수 있다.
- 동의 시각 · 동의한 약관 버전이 어디에도 남지 않았다.
- 화면의 실제 요청도 동의 값을 싣지 않았다: `signupPage.js`는 `agreed`를 읽어 화면에서만 검사하고, `realApi.signup`이 `{ id, password, nickname }`만 보냈다. 서버 검증만 먼저 배포하면 정상 가입이 모두 400이 된다.

## 검토한 대안

### 1. 요청 칸 이름

- `agree`(Jira 초안) / `agreed` (**선택**): 화면이 이미 `agreed`라는 이름으로 값을 읽고 검사한다(`signupRule.validateSignup`, `fields.agreed`). 서버 `details[].field`가 같은 이름이면 화면의 칸 안내(`SERVER_FIELD_MESSAGE`)에 그대로 이어진다.

### 2. 검증 방식

- `boolean agreed` + `@AssertTrue`: Jackson 3(Spring Boot 4)은 primitive에 null · 빠진 칸이 오면 역직렬화 실패(`FAIL_ON_NULL_FOR_PRIMITIVES` 기본 켜짐)라 400이 나도 `details`에 칸 이름이 없다.
- `Boolean agreed` + `@NotNull @AssertTrue` (**선택**): 빠짐 · null은 `NotNull`, `false`는 `AssertTrue`로 늘 `field: agreed`가 실린다. 형식 검사라 409(중복 아이디 · 닉네임)보다 먼저 거절한다 — 운영 점검의 재현 요청도 이제 400이다.
- 서비스(`LocalAccountService.signup`)도 `agreed`를 받아 한 번 더 확인한다. 다른 호출 경로가 생겨도 동의 없이 동의 기록이 남지 않게 한다.

### 3. 저장 위치 · 약관 버전

- 별도 동의 이력 테이블(약관이 바뀔 때마다 다시 동의받은 기록을 쌓는다) / `member`에 두 칸 (**선택**): 지금은 다시 동의받는 흐름이 없고 가입 때 한 번만 묻는다. 칸 두 개(`terms_agreed_at` · `terms_version`)와 CHECK(함께 있거나 함께 없다)면 충분하다. 재동의가 생기면 그때 이력 테이블로 옮긴다.
- 동의 시각은 가입 트랜잭션의 `now`(`last_login_at`과 같은 값)로 남긴다. 화면 시각은 믿지 않는다.
- 약관 버전은 코드 상수 `TermsVersion.CURRENT`. 화면의 동의 한 줄이 이용약관과 개인정보처리방침을 함께 묻으므로 한 버전으로 묶는다. 지금 문서는 법무 검토 전 초안이고 시행일이 없어 `2026-10-draft`로 둔다. 시행일이 정해지거나 문서를 바꾸면 `legalPage.js`와 함께 올린다.

### 4. 기존 회원

- 가입일로 채운다 / NULL로 둔다 (**선택**): 그동안 화면이 동의를 강제했지만 서버가 확인한 적이 없고 어떤 문구에 동의했는지도 남지 않았다. 추정값을 동의 기록처럼 남기지 않는다. NULL은 "동의 기록이 없다"는 뜻이다.

### 5. 카카오로 처음 가입하는 경로

- **이번 범위 밖으로 둔다.** 카카오 회원은 첫 로그인 때 `member` 행이 생기는데(M-4), 그 전에 동의를 묻는 화면이 없다. 가입 화면 맨 위 "카카오로 시작하기"도 동의 줄보다 먼저 있어 체크 없이 누를 수 있다.
- 이 경로를 막으려면 화면 · 서버를 함께 바꿔야 한다(로그인 화면과 가입 화면이 같은 카카오 버튼을 쓰고, 이미 가입한 회원과 처음 온 회원을 콜백 뒤에야 구분할 수 있다). 후속 이슈로 둔다. 방향 후보:
  - A: 카카오 버튼 아래에 "시작하면 약관에 동의한 것으로 봐요" 안내 + 첫 로그인 때 동의 기록(가볍지만 명시 동의가 아니다)
  - B: 카카오 첫 로그인 뒤 동의 화면을 한 번 거쳐야 회원 기능을 쓰게 한다(명시 동의, 화면 · API 추가)
- 그 전까지 카카오 회원의 두 칸은 NULL이다.

## 선택한 방법과 이유

- 서버: M-5 요청에 `agreed`(필수, `true`만). 가입하면 `member.terms_agreed_at`(가입 시각) · `terms_version`(`TermsVersion.CURRENT`)을 남긴다. V40은 NULL 허용 칸 두 개와 CHECK만 추가한다(BE-60 "추가만").
- 화면: `realApi.signup`이 `agreed`를 보낸다(`true`가 아니면 `false` — 서버가 400으로 알려 준다). 목(`authMockApi.signup`)도 서버처럼 `agreed`가 `true`가 아니면 `details agreed`로 거절한다. 서버가 `agreed`로 거절하면 동의 줄에 안내를 붙인다.
- 서버 · 화면을 한 PR로 묶었다. 화면만 먼저 나가면 서버가 모르는 칸이라 무시하고, 서버만 먼저 나가면 가입이 모두 400이 되기 때문이다.
- API 명세 M-5 v0.73, ERD v1.50(`member` 표).

## 고려한 제약 사항

- **배포 순서**: main 머지 때 백엔드 · 웹 이미지가 함께 나간다. 배포 직후 예전 화면을 열어 둔 브라우저는 `agreed`를 보내지 않아 가입이 400이 되고 "가입하지 못했어요"가 나온다(예전 화면은 `agreed` 칸 안내를 모른다). 새로고침하면 새 화면이 받는다. 가입은 드물고 한 번 새로고침으로 풀려 따로 이행 기간을 두지 않았다.
- **마이그레이션**: 칸 추가 · CHECK뿐이라 기존 행(모두 NULL)과 충돌하지 않는다. 한 ALTER로 묶어 `member` 잠금 · CHECK 검사를 한 번만 한다. 배포 중 구버전 코드가 회원을 만들어도 두 칸이 함께 NULL이라 CHECK를 통과한다. 자동 롤백이 없으므로 develop(스테이징)에서 V40 적용을 먼저 확인한다.
- 개인정보처리방침의 수집 항목은 바꾸지 않았다. 동의 시각 · 약관 버전은 서비스가 만든 기록이지 이용자에게서 받은 정보가 아니다.

## 확인

## 추후 재검토가 필요하면

- **카카오 첫 가입의 약관 동의**: 위 5번. 후속 이슈로 화면(FE) · 서버(BE)를 함께 정한다.
- **약관 개정 · 재동의**: 문서를 바꿔 다시 동의받아야 하면 `member` 두 칸 대신 동의 이력 테이블로 옮기고, 로그인 때 버전이 다르면 동의를 다시 묻는다.
- **약관 버전 값**: 시행일이 정해지면 `TermsVersion.CURRENT`를 시행일 기준 값으로 바꾸고 `legalPage.js`의 시행일 표시와 맞춘다.
