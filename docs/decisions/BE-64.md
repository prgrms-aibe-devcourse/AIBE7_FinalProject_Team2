# BE-64 의사결정 기록

> 확장 단계(WBS 7.6.7) · 담당 정민석

## 문제 / 배경
- 판결 체험이 끝나면(API 13 비교 공개, `AI_REVEALED` → `COMPLETED`) 그 체험의 판결 성향 기여(축별 감경 · 가중 개수)를 `experience_personality`에 저장해야 한다. 저장해야 마이페이지(P-5)의 종합 성향 · 성향 변화 흐름이 채워진다(PR #128 본문).
- 무엇을 어떻게 세는지는 [`personality-scoring.md`](../personality-scoring.md) 3장(3-1 쓰는 기록 · 3-2 방향 → 글자 · 3-4 저장 시점)과 6장(`axis_counts` 형식)에 이미 정해져 있다. 이 이슈는 그 계산을 상태 전이에 **언제 · 어떻게 끼울지**를 정한 것이다.
- 저장 테이블 · 엔티티(`ExperiencePersonality.of`)는 BE-69, 조회(`findFirstAttemptsByAnonymousUser`)는 BE-72에서 이미 만들어져 있었다.

## 새로 도입한 기술 (선택)

### 트랜잭션 전파 `Propagation.MANDATORY`
- **무엇인가**: Spring `@Transactional`의 전파 방식 중 하나로, "이미 진행 중인 트랜잭션 안에서만 실행한다"는 뜻이다. 진행 중인 트랜잭션이 없으면 새로 만들지 않고 `IllegalTransactionStateException`을 던진다.
- **동작 원리**: 기본값 `REQUIRED`는 트랜잭션이 없으면 새로 시작하고 있으면 참여한다. `MANDATORY`는 참여만 하고 시작은 하지 않는다. 그래서 "반드시 다른 작업과 한 묶음이어야 하는 작업"을 실수로 따로 부르는 것을 실행 시점에 막는다.
- **우리 프로젝트에서**: `personality/service/ExperiencePersonalityRecorder.recordOnCompleted`에 붙였다. 이 메서드는 `RevealService.revealComparison`(`@Transactional`)의 트랜잭션 안에서만 불려야 COMPLETED 전이와 함께 커밋 · 롤백된다.
- **주의할 점**: 이 메서드를 Mockito로 스텁(`doThrow().when(spy).recordOnCompleted(...)`)하면 스텁을 설정하는 호출 자체가 트랜잭션 프록시를 거쳐 트랜잭션 밖에서 실행되므로 실패한다. 롤백 테스트는 그래서 기록기가 마지막에 부르는 저장소를 스파이로 실패시켰다(`ExperiencePersonalityRecordRollbackTest`).
- **참고**: Spring Framework 문서 "Transaction Propagation" https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/tx-propagation.html

## 검토한 대안
- **저장을 어디에 끼울지**
  - 대안 A: `Experience.revealComparison()`(엔티티) 안에서 저장 — 엔티티가 리포지토리를 알아야 하고, 상태 규칙만 두는 엔티티의 역할(ExperienceTransitionService 주석 "규칙은 엔티티 한 곳에만")이 흐려진다. 탈락.
  - 대안 B: `ExperienceTransitionService.applyIdempotent`에 "함께 저장할 작업"을 넘기는 방식(`apply(experience, relatedWrites, change)`처럼) — 이 서비스의 `relatedWrites`는 **전이 전에** 실행된다. 성향은 "이번 요청이 실제로 COMPLETED로 바꿨는지"를 안 뒤에 저장해야 해서 맞지 않는다. 탈락.
  - 대안 C: 이벤트(`@TransactionalEventListener`)로 분리 — 기본 단계(AFTER_COMMIT)는 커밋 뒤라 같은 트랜잭션이 아니고(3-4 위반), BEFORE_COMMIT으로 쓰면 결국 같은 일을 간접적으로 하는 것이라 흐름만 찾기 어려워진다. 탈락.
  - **선택: `RevealService.revealComparison`에서 `TransitionResult.changed()`가 참일 때만 기록기 호출.**
- **패키지 의존 방향** (리뷰 관점 점검)
  - 이번 변경으로 `judgment`(RevealService) → `personality`(기록기) → `judgment`(JudgmentFactorRepository) 방향이 생겨 두 패키지가 서로를 안다. 스프링 빈 순환은 아니다(기록기는 RevealService를 모른다).
  - 대안: `experience` 패키지에 "체험 완료 시 할 일" 인터페이스를 두고 `personality`가 구현하게 하면 `judgment` → `personality` 의존이 사라진다. 다만 구현체가 하나뿐인 지금은 간접 호출만 늘고, 흐름을 찾기 어려워지는 비용이 더 크다.
  - **선택: 직접 호출 유지.** 완료 시 할 일이 둘 이상 생기면(예: 리뷰 작성 조건 FE-55, 통계 갱신) 그때 인터페이스로 뺀다.
- **같은 트랜잭션으로 묶을지 (PR #109 확인 요청 3-4)**
  - 묶지 않으면 성향 계산이 실패해도 체험은 완료되지만, 그 체험은 다시 공개해도 `changed = false`라 **저장할 기회가 다시 오지 않는다.** P-5 `experienceCount`(성향 기여가 저장된 체험 수)와 완료 체험 수가 영구히 어긋난다(PR #128 리뷰).
  - 묶으면 계산 실패가 완료를 막지만, 계산은 DB 집계 한 번 · 저장 한 번이라 실패할 일이 드물고, 실패하면 사용자가 다시 눌러 재시도할 수 있다.
  - **선택: 묶는다** (3-4 그대로). 기록기를 `MANDATORY`로 둬 묶음이 깨지지 않게 했다.
- **첫 회차만 저장할지, 모든 회차를 저장하고 조회에서 거를지**
  - 조회 쿼리가 이미 `attempt_no = 1`만 읽으므로 모두 저장해도 결과는 같다.
  - PR #109 본문의 결정이 "저장: `attempt_no = 1`만"이고, 쓰지 않을 행을 쌓을 이유가 없다.
  - **선택: 첫 회차만 저장**, 조회 필터는 그대로 두어 이중으로 막는다. MVP는 회차가 항상 1이라 지금은 차이가 없다.

## 선택한 방법과 이유
- `JudgmentFactorRepository.countFinalFactorsByAxis`: 판단 요소 행을 전부 불러와 자바에서 세지 않고, DB에서 한 번에 집계해 인터페이스 프로젝션(`AxisDirectionCount`, 기존 `CaseParticipantCount`와 같은 방식)으로 받는다. USER · FINAL 판단에서 `value_axis`가 있는 요소를 축 · 방향별로 센다. `timing` · `subject_type` 조건은 서비스 코드가 아니라 리포지토리 메서드에만 둔다(ERD 7장, `JudgmentRepository`와 같은 규칙). `value_axis_status`는 따지지 않는다(3-1).
- `ExperiencePersonalityRecorder.recordOnCompleted`: 첫 회차가 아니면 바로 끝낸다. 센 결과를 `ExperiencePersonality.of()`로 저장한다 — `of()`가 빠진 축을 `{down: 0, up: 0}`으로 채워, 축 값이 `null`이면 걸리는 V15 CHECK를 피한다(PR #124 리뷰). 판단 요소가 0개여도 행은 남는다(3-4).
- 전이 뒤 체험 엔티티는 영속성 컨텍스트에서 분리돼 있어(ExperienceTransitionService), 저장할 때는 `getReferenceById`로 참조를 다시 얻는다.
- 동시 요청: 조건부 UPDATE라 한 요청만 `changed = true`가 되고, `experience_id` 유니크가 한 번 더 막는다.

## 고려한 제약 사항
- 이미 COMPLETED인 기존 체험(이 기능 배포 전에 완료)은 보정하지 않는다. 그런 체험은 마이페이지 종합 · 흐름에 들어가지 않을 뿐 체험 기록은 그대로이고, 이 차이는 PR #128에서 P-5 `experienceCount`("성향 기여가 저장된 첫 회차 체험 수") 정의로 이미 받아들였다. 운영에 사건이 올라가 있어(10/20 확인) 배포 전 완료 체험이 있을 수 있으므로, 보정이 필요해지면 같은 집계 쿼리로 한 번 채우는 스크립트를 따로 만든다(고정 저장 원칙상 그 시점의 `value_axis`로 센다는 점을 기록에 남긴다). 로컬 · 개발 DB는 다시 체험하면 된다.
- `ApiIntegrationTest`의 정리 순서에 `experience_personality` 삭제를 추가했다. API 13을 부르는 기존 테스트(`JudgmentResultApiTest` 등)도 이제 성향 기여를 만들기 때문에, 체험을 먼저 지우면 FK에 걸린다.

## 추후 재검토가 필요하면
- 감경 → 관대 일괄 규칙(3-2 한계)이 요소의 뜻과 어긋나는 사례가 많이 쌓이면, `factor` 옆 요소별 글자 · 가중치 보조 테이블을 추가하고 `countFinalFactorsByAxis`가 그것을 읽게 바꾼다(성향 산식 8장 #7).
- 재체험(`attempt_no > 1`)이 실제로 생기면, 두 번째 체험을 성향 흐름에서 어떻게 보여 줄지(완전히 뺄지 · 따로 표시할지) 화면 쪽과 다시 정한다.
