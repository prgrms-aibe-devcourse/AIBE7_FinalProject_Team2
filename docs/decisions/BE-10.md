# BE-10 의사결정 기록

> MVP 단계(WBS 2.5) · PR #54 · 담당 백승호

## 문제 / 배경
- AI 판결 조회(API 10), 실제 판결 공개(API 11), 실제 판결 조회(API 12), 비교 공개(API 13) 4개 엔드포인트를 구현해야 했다.
- 공개 요청(API 11·13)은 여러 번 호출돼도 상태가 되돌아가지 않아야 했고(멱등), 사건번호·법원명 같은 비식별 대상 정보가 응답에 노출되면 안 됐다(FR-5-3).

## 검토한 대안
- **신규 Repository/마이그레이션을 추가할지, 기존 자산을 재사용할지**: `Experience.revealCourt`/`revealComparison`, `ExperienceTransitionService.applyIdempotent`, `JudgmentRepository`의 목적별 조회, `CaseSourceRepository.findFinalByCaseId`가 이미 있었다. 새로 만드는 대신 이 자산들을 그대로 조합하는 방법을 검토했다.
- **공개 사건에 검수된 판결이 없는 경우의 처리**: 400대 거절 응답으로 막을지, 500 + 로그로 남길지 검토했다.

## 선택한 방법과 이유
- 기존 자산을 그대로 재사용했다. 새 Repository 메서드나 마이그레이션이 필요 없을 만큼 기존 설계가 이번 요구사항을 충분히 커버했고, 범위를 최소화해 리뷰·테스트 부담을 줄일 수 있었다.
- 공개 사건에 검수된 판결이 없는 경우는 사용자가 고칠 수 없는 데이터 문제(운영 측의 사전 검수 누락)이므로 요청 거절 조건으로 다루지 않고 500 + 로그로 처리했다. API 명세에도 이 처리를 명시했다.
- 판결 응답 공통 형식(`JudgmentView`)과 내 판결 한 줄 요약 규칙 문장(`UserSummarySentence`)을 이 이슈에서 만들어, 같은 응답 구조가 필요한 BE-11(API 14)에서 그대로 재사용하도록 했다.

## 고려한 제약 사항
- FR-5-3: 사건번호·법원명은 어떤 응답에도 나오면 안 된다 — 전용 테스트로 응답 본문 전체를 검사해 보장했다.
- 주체별로 내려가면 안 되는 필드가 있다(`excerpt`·`plainExplanation`·`factors[].evidence`는 `COURT`만, `reasoning`은 `USER` 제외).
- `AI`/`COURT` 판결은 `is_published = true`인 행만 조회 대상이다.
