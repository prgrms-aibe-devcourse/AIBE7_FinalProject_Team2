# BE-136 의사결정 기록

컬렉션 수집 항목 서버 화이트리스트 검증 — 레벨 비교 기능 노출 전 (BE-83 후속). 담당 D(정민석).

## 문제 / 배경

- BE-83(PR #335)의 수집 기록(P-9)은 서버가 항목 목록을 몰라 가짜 `itemId`를 상한까지 받았다(일러스트 사건당 5 · 의상 사용자당 12). 항목당 10 XP가 붙어 레벨이 오른다.
- BE-83 결정 2는 "다른 사용자와 레벨 · `collected`를 비교하는 기능이 서버 값을 쓰기 전에 화이트리스트로 바꾼다"였다. 커뮤니티 메인(C-6, BE-115)의 레벨 랭킹이 서버 레벨을 쓰게 되어 그 조건에 걸렸다.
- BE-83 때는 "대본이 서버에 없어 사건별 목록을 만들 수 없다"고 봤다. 지금도 수집 판정에 쓰는 화면 대본(`content/case-1/script.json`)은 서버에 없다. 대신 두 가지가 생겼다.
  - 사건 사진 이름 규칙(BE-141): `/images/cases/case-{id}-{reenact|origin|conclusion}.webp`. FE-132의 일러스트 id(`case-1-origin`)와 같은 이름이고, "사건당 일러스트 3장"이 콘텐츠 규칙이다.
  - 일러스트 목록 파일(BE-142, `illustration-images.txt`): 역할 의상 그림 `characters/roles/{who}_{role}.webp`가 들어 있다. 화면이 만난 모습(`castOf`)을 그릴 때 쓰는 그림이다.

## 검토한 대안

### 1. 일러스트 목록

- 대안 A — 일러스트 목록 파일(BE-142)의 `cases/` 그림 이름: 관리자가 DB(S3)에만 올린 사진은 파일에 없어(BE-143) 정상 항목이 거절될 수 있다.
- 대안 B — 요청한 사건의 규칙 이름만(`case-{caseId}-{slot}`): 가장 엄격하다. 그러나 같은 그림을 여러 사건이 다시 쓰는 **그림별 key**(BE-83 결정 3, 김해송 정리)를 막는다. 사건 사진을 배경 · 시간대 · 일러스트로 쪼개 합성하는 계획과 어긋난다.
- 대안 C — **공개 중인 사건의 규칙 이름이면 받는다(선택)**: `case-{n}-{origin|conclusion|reenact}`에서 사건 n이 공개 중이어야 한다. 요청한 사건과 달라도 된다. 파일이 아닌 이름 규칙이라 S3에만 있는 사진도 받는다. 남는 여유(다른 사건 그림을 먼저 얻는 것)는 사건당 상한 5가 묶는다.
  - 그래서 완료한 사건 하나로 모을 수 있는 일러스트는 최대 5장이고, 모두 실제로 있는 공개 사건의 그림이다. 가짜 id로 늘릴 수 없다.

### 2. 의상 목록

- 대안 A — 화면 `castOf`의 인물 × 역할 표(내로 · 남불 × A씨 역 · 검사 · 변호인 · 판사, 8가지)를 서버에 옮겨 적는다: 화면 표와 서버 표를 함께 고쳐야 한다.
- 대안 B — **일러스트 목록의 역할 의상 그림(선택)**: `characters/roles/{who}_{role}.webp` → `{who}:{role}`. 그림이 있어야 화면이 만난 모습을 그릴 수 있으므로 같은 기준이다. 그림을 더하면 목록(`update-manifest.sh`)과 함께 자동으로 늘고, 이미지 폴더와 어긋나면 `IllustrationCatalogTest`가 실패한다. 지금 10가지(8가지 + 사건 1 전용 의상 `naero:case-1` · `nambul:case-1`).

### 3. 상한

- 일러스트 사건당 5는 **남긴다** — 다른 사건의 그림도 받으므로 한 사건에서 모을 수 있는 수를 묶는 값이다.
- 의상 사용자당 12는 **지운다** — 목록이 곧 전체(10가지)라 더 막을 것이 없고, 역할 그림이 12가지를 넘으면 정상 사용자가 막히게 된다.

### 4. 거절 응답

- 409(상한)와 같은 코드 / **400 `VALIDATION_ERROR`(선택)**: 목록에 없는 id는 입력 오류다. `details`에 `items[i].itemId` · `NOT_COLLECTIBLE`(요청 순서)를 담아 형식 오류(`items[i].itemId` · `Pattern`)와 같은 모양으로 둔다. 새 에러 코드를 만들지 않는다.
- 쿠키 · 체험 확인보다 먼저 거절한다(입력 검사). 하나라도 걸리면 아무것도 저장하지 않는다(BE-83과 같다).

### 5. 이미 쌓인 목록 밖 항목

- 화면이 아직 P-9를 부르지 않는다(FE-132 진행 전). V35는 `achievement_unlock`만 백필했고 `collection_item`은 채우지 않았다. 그래서 운영 · 스테이징의 `collection_item`은 비어 있거나 직접 API를 부른 행뿐이다.
- 마이그레이션으로 지우지 않는다(BE-60 "main으로 가는 마이그레이션은 추가만"). PR에서 운영 행 수를 확인하고, 목록 밖 행이 있으면 그때 정리 방법(관리자 SQL)을 정한다.

## 선택한 방법과 이유

- `CollectibleCatalog`(수집 패키지): 일러스트는 규칙 이름 + 사건 공개 여부(가리키는 사건들을 한 번에 조회), 의상은 일러스트 목록의 역할 의상 그림.
- `CollectionService.record`가 맨 처음 목록 검사를 한다. 통과한 뒤 기존 순서(쿠키 → 체험 완료 → 사건당 상한)를 그대로 탄다.
- API 명세 v0.75(P-9 · 1-5). v0.74는 BE-133 PR(#349)이 쓴다.

## 고려한 제약 사항

- **대본이 서버에 없어 "그 사건에서 실제로 본 그림인가"는 보지 않는다.** 완료한 사건 하나로 다른 공개 사건의 그림을 (사건당 5장 안에서) 먼저 얻을 수 있다. 실제로 있는 그림이고 총량이 묶여 랭킹을 크게 흔들지 못한다. 대본이 서버로 오면(BE-143 · FE-132 이후) 사건별 목록으로 좁힌다.
- **FE-132(김해송)와의 계약**: 일러스트 id는 `case-{사건 id}-{origin|conclusion|reenact}`, 의상은 역할 의상 그림의 `{who}:{role}`. 공용 배경 · 시간대처럼 사건 이름이 아닌 그림을 일러스트로 모으려면 이 목록부터 넓혀야 한다(그 전에는 400).
- 의상 목록은 서버가 시작할 때 일러스트 목록 파일에서 한 번 읽는다. 그림을 더하면 배포해야 늘어난다(일러스트 총 개수 API BE-142와 같다).
- 공개를 취소한 사건(BE-118)의 그림은 다시 공개될 때까지 새로 모을 수 없다. 이미 모은 항목은 그대로 둔다.

## 확인

- `CollectionApiTest`
  - 목록 밖 항목(없는 칸 이름 · 사건 규칙이 아닌 이름 · 공개 전 사건 · 없는 사건 · 그림 없는 역할 · 모르는 인물)은 400 `items[i].itemId` · `NOT_COLLECTIBLE`, 섞인 정상 항목도 저장하지 않음, 쿠키가 없어도 400
  - 다른 공개 사건의 그림은 받고 처음 얻은 사건 · 시각을 유지(그림별 key)
  - 사건당 상한 5 — 이 사건 3장 + 다른 사건 3장이면 409, 5장까지는 저장
  - 기존 시나리오(저장 · 멱등 · 해금 · 봤음 · 백필)를 목록에 있는 id로 다시 확인
- `CollectibleCatalogTest`: 역할 의상 그림 이름 → 의상 id(밑줄 없는 이름 · 하위 폴더 · 다른 폴더는 제외), 지금 목록이 화면 `castOf`의 8가지를 모두 담고 id 형식을 통과

## 추후 재검토가 필요하면

- **대본이 서버로 오면**: "그 사건의 일러스트 · 의상"으로 좁힌다(사건별 목록). BE-143(컬렉션 사진을 DB 기준으로)과 함께 본다.
- **공용 배경 · 시간대(새 `kind`) 또는 사건 이름이 아닌 일러스트**를 모으게 되면 목록 규칙을 넓힌다.
- **BE-140(마이페이지 · 수집을 회원 기준으로)**: 목록 검사는 저장 주체와 무관하게 그대로 쓴다.
