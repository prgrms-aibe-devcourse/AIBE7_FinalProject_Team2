# BE-94 의사결정 기록

## 문제 / 배경
WBS 7.4.3(BE-57 · docs/tech-stack.md 3장 "사용자 인증 기반"에서 계약만 정의된 `TokenIssuer` · `AccessTokenVerifier`)를
실제로 구현해야 했다. 범위는 액세스 토큰 발급 · 검증, 리프레시 토큰 발급 · Redis 저장 · 재발급(로테이션) · 로그아웃(폐기)이며,
재발급 · 폐기 · CSRF 대책은 계약에 없어 이번에 새로 설계했다. 카카오 로그인(BE-62, 7.4.2)이 아직 구현되지 않은 상태에서
먼저 작업했다.

## 검토한 대안

### 1. 리프레시 토큰을 화면(브라우저)에 어떻게 넘길까
- **대안 A: 액세스 · 리프레시 토큰을 모두 JSON 응답에 담는다** — 일반 로그인이면 되지만, 카카오 로그인은 OAuth 리다이렉트로
  끝나 서버가 JSON 응답을 줄 시점이 없다(브라우저가 리다이렉트를 따라가는 중). 채택 불가.
- **대안 B: 토큰을 리다이렉트 URL 쿼리 파라미터에 싣는다** — 주소창 · 방문 기록 · Referer로 유출될 수 있어 제외.
- **대안 C(채택): 리프레시 토큰만 HttpOnly 쿠키로 내려주고 화면으로 리다이렉트, 화면은 재발급 API를 한 번 불러 액세스
  토큰을 받는다.** 액세스 토큰은 쿠키에 담지 않고 화면 메모리에만 둔다.

### 2. 리프레시 토큰 값의 형식
- **대안 A: 리프레시 토큰도 JWT로 만든다** — 자체 검증 가능하지만, 탈취 시 즉시 무효화하려면 결국 블랙리스트(Redis)가
  필요해 자체 검증의 이점이 줄어들고 토큰 크기만 커진다.
- **대안 B(채택): SecureRandom 32바이트를 Base64Url로 인코딩한 불투명한 값**. Redis(토큰 DB)에 회원 ID · 권한을 매핑해
  저장하고, 저장소에 없으면 바로 무효로 본다. 폐기 · 로테이션이 Redis 키 삭제 하나로 끝난다.

### 3. 재발급 시 리프레시 토큰 재사용 여부
- **대안 A: 재발급 때 리프레시 토큰을 그대로 둔다** — 구현은 단순하지만, 탈취된 리프레시 토큰이 계속 유효해 피해 기간이
  길어진다.
- **대안 B(채택): 재발급마다 리프레시 토큰을 로테이션한다**(기존 키 삭제 + 새 키 발급). 탈취된 토큰이 먼저 재발급을
  써버리면 원래 주인의 다음 재발급이 실패해 이상 징후를 알아챌 수 있다.
- **재사용 탐지(두 번째 사용을 적극적으로 로그 · 전체 세션 무효화하는 것)는 범위 밖으로 미뤘다** — 아래 "추후 재검토" 참고.

### 4. 재발급 · 로그아웃의 CSRF 대책
- **대안 A: 관리자 체인처럼 CSRF 토큰 발급 · 검증 왕복을 추가한다**(`CookieCsrfTokenRepository` 방식) — 일관성은 있지만,
  재발급 전에 CSRF 토큰을 받는 API를 하나 더 두거나 리프레시 쿠키와 별개로 토큰을 관리해야 해 왕복이 늘어난다.
- **대안 B(채택): Origin(없으면 Referer) 검증**. 재발급 · 로그아웃은 항상 우리 화면이 같은 출처에서 호출하므로
  (docs/tech-stack.md "CORS는 설정하지 않는다"), 요청의 Origin이 서버 자신과 같은지만 확인하면 충분하다. 포트는 비교하지
  않는다(Nginx가 TLS를 끝내고 내부 포트로 넘긴다). `OriginVerificationFilter`로 구현, 두 경로에만 적용했다.
  보호 경로 판정은 `getRequestURI()` 원시 문자열 비교가 아니라 Spring Security `RequestMatcher`
  (`PathPatternRequestMatcher` + `OrRequestMatcher`)로 한다 — 원시 비교는 context path를 포함하고
  디코딩되지 않아, percent-encoding된 경로(`/token/%72eissue`)가 검증을 건너뛸 수 있었다(PR #218 리뷰).

### 5. 리프레시 토큰 쿠키 속성
- **SameSite**: 관리자 세션 쿠키 · 익명 ID 쿠키는 Lax를 쓰지만(OAuth 리다이렉트 직후에도 세션 쿠키가 필요해서), 재발급 ·
  로그아웃은 항상 우리 화면이 능동적으로 부르는 요청이라 Strict로 더 좁혔다(Origin 검증과 이중 방어).
- **Path**: `/`가 아니라 `/api/v1/auth`로 좁혀, 이 쿠키가 다른 API 요청에는 실리지 않게 했다.

## 선택한 방법과 이유
- `common.security.token.jwt` 패키지에 `JwtTokenIssuer`(`TokenIssuer` 구현) · `JwtAccessTokenVerifier`
  (`AccessTokenVerifier` 구현) · `RefreshTokenStore`(Redis 저장) · `TokenRefreshService`(재발급 로테이션 · 로그아웃)를 둔다.
  둘 다 `@Component`로 등록해, 이미 BE-57이 만들어 둔 `ObjectProvider<AccessTokenVerifier>` 주입 지점에 코드 수정 없이
  연결된다.
- 액세스 토큰은 HS256 JWT(`jjwt` 라이브러리), subject=회원 ID, `roles` claim, 발급자(iss) 검증까지 한다. 서명 키는
  `jwt.secret`(Base64, 환경변수 `JWT_SECRET`)로 외부 주입하고, 32바이트 미만이면 기동 시 막는다(`JwtProperties`).
- 리프레시 토큰은 Redis 토큰 DB(RedisConfig.TOKEN)에 `refresh:{token}` 키로 저장, 값은 JSON(`{memberId, roles}`),
  TTL은 `jwt.refresh-token-ttl`과 동일하게 맞춘다(RedisConfig 규칙 — 모든 키에 TTL).
- 쿠키 헬퍼 `RefreshTokenCookies`(common.web)를 두어 성공 처리 쪽(카카오 로그인, BE-62)이 같은 규칙으로 쿠키를
  심게 했다 — 쿠키 규칙이 두 곳으로 갈라지지 않도록.
- `AuthController`(`/api/v1/auth/token/reissue`, `/api/v1/auth/logout`)는 `Authorization` 헤더를 보지 않고 리프레시
  쿠키로만 인증한다(docs/tech-stack.md "재발급 요청"). 둘 다 멱등하게 만들었다(없는 토큰으로 로그아웃해도 204).

## 고려한 제약 사항
- 카카오 로그인(BE-62)이 아직 없어 `TokenIssuer.issue(MemberPrincipal)` 호출 쪽을 실제로 왕복 검증하지 못했다.
  `MemberPrincipal.user(long)`로 만든 가짜 회원으로 단위 · 통합 테스트를 했다.
- 테스트는 실제 Redis 토큰 DB(로컬 docker-compose, 포트 56379)에 붙는 통합 테스트로 작성했다(`RedisConfigTest`와
  같은 방식). CI에도 같은 서비스 컨테이너가 떠 있어야 통과한다.
- `jwt.secret`은 기본값을 두지 않는다(`${JWT_SECRET:}`) — 처음에는 로컬 개발 전용 값을 `application.yml`에
  하드코딩했으나, PR #218 코드 리뷰에서 "환경변수 하나가 빠져도 그 값으로 조용히 기동해 누구나 토큰을 위조할 수
  있다"는 지적을 받아 제거했다. 값이 없으면 `JwtProperties`가 기동을 막는다. 로컬 · 테스트는 각자 환경
  (`application-test.yml`, README.md `JWT_SECRET` 안내)에서 넘긴다.

## 추후 재검토가 필요하면
- 재사용 탐지(같은 리프레시 토큰이 로테이션 후 다시 쓰이면 그 회원의 모든 세션을 무효화하는 것)는 지금은 "두 번째
  사용이 실패"하는 정도만 보장한다(동시 요청에서도 `RefreshTokenStore.consume()`이 Redis GETDEL로 원자적으로
  처리해 정확히 하나만 성공한다 — PR #218 리뷰로 `find` + `delete` 두 단계였던 것을 바꿨다). 피해가 커지면
  재사용 탐지 시 전체 세션 무효화를 추가로 설계한다.
- Origin 검증은 Nginx가 `X-Forwarded-Host` 등을 올바르게 넘긴다는 전제(`server.forward-headers-strategy: native`,
  BE-62에서 추가 예정)에 기댄다. 그 설정이 빠지면 운영에서 Origin 비교가 실제 배포 호스트와 어긋날 수 있다.
- 액세스 토큰은 블랙리스트를 두지 않아, 로그아웃해도 이미 나간 액세스 토큰은 자연 만료(기본 15분)까지 유효하다.
  더 짧은 무효화가 필요해지면 액세스 토큰에도 jti 기반 블랙리스트를 추가로 검토한다.
