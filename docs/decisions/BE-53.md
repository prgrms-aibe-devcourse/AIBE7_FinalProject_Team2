# BE-53 의사결정 기록

> 확장 단계(WBS 7.5.4) · PR #153 · 담당 정민석

## 새로 도입한 기술 (선택)

### 임베딩 cosine 유사도 매칭 (SEMANTIC_SIMILARITY)
- 무엇인가: 텍스트를 숫자 벡터(임베딩)로 바꾼 뒤, 두 벡터의 코사인 유사도(cosine similarity)로 "의미가 얼마나 비슷한가"를 점수화하는 방법. 문자열이 달라도 뜻이 같으면("흉기 사용" / "흉기를 씀") 높은 점수가 나온다.
- 동작 원리:
  1. 비교할 텍스트(공개 기준 목록 17개 + 추출된 요약어)를 한 번에 임베딩 API로 보내 벡터를 받는다.
  2. 요약어 벡터와 기준 목록 벡터 각각의 코사인 유사도를 계산해 점수를 매긴다.
  3. 점수 높은 순으로 상위 K개를 후보로 추리고, 1·2위 점수 차가 작으면 "애매함"으로 표시해 제안하지 않는다.
  4. 최고 점수가 기준(minScore) 이상이고 이미 목록에 있는 말이 아니면 "제안(suggested)"으로 남긴다.
- 우리 프로젝트에서: `tools/ai-judgment/summary_tags.py`의 `find_candidates()`가 핵심 로직이다. `cosine()` 함수가 유사도를 직접 계산하고, `annotate_report()`가 `pipeline.py`의 extract 단계 결과(`factorExtras[]`)에 `summaryTagCandidates`를 덧붙인다. 기준 목록은 `tools/ai-judgment/summary_tags.json`(공개 값 17개, 실제 사건 요약어는 포함하지 않음).
- 주의할 점:
  - 요약어를 자동으로 바꾸지 않는다 — 결과는 어디까지나 "제안"이고 최종 판단은 관리자 후검수다.
  - 임베딩에는 요약어만 보내고 판단 요소 문장·판결문 원문은 보내지 않는다(개인정보·사건 정보 노출 방지).
  - minScore·AMBIGUOUS_MARGIN은 공개 샘플 17개로 실측한 값이라, 실제 사건 요약어가 쌓이면 다시 조정해야 한다(아래 "검토한 대안" 참고).
  - 임베딩 API 키가 없거나 호출이 실패하면 `SKIPPED` 상태로 추출 자체는 계속 진행한다(이 단계가 전체 파이프라인을 막지 않는다).
- 참고: [Gemini 임베딩(Task type) 문서](https://ai.google.dev/gemini-api/docs/embeddings), 운영 설정은 `tools/ai-judgment/README.md` · `docs/ai-judgment-pipeline.md` 8-1 참고.

## 문제 / 배경
- 사건마다 LLM이 뽑는 요약어 표현이 제각각이라("흉기 사용" / "흉기를 씀") 같은 뜻인데도 다른 문자열로 쌓이는 문제가 있었다.
- WBS 6.4.2에는 "선행 BE-51(요약어 목록)"이라고 적혀 있었지만, 실제로는 BE-51(PR #97)·문서·DB·비공개 시드 어디에도 공통 목록이 없었다(사실 정정, WBS v1.24).
- 요약어·사전 판단 선택지(preLabel)가 개인정보·실제 형량 노출 검사에서 빠져 있던 빈틈과, court 인용에 마스킹 표시([주소] 등)가 남아도 통과하던 빈틈도 같이 막아야 했다.

## 검토한 대안
- **minScore 기준값**: 0.85는 무관한 쌍(계획적 범행 → 범행 동기 0.894, 심신미약 주장 → 우발적 범행 주장 0.900)과 구분이 안 됐다. 샘플 17개 실측 결과 0.90에서는 같은 뜻 9/10·오제안 1, 0.91에서는 8/10·오제안 0이었다.
- **기준 목록의 겹치는 쌍 처리**(피해 회복 ↔ 피해 회복 공탁 0.928, 반성 ↔ 범행 인정·반성 0.949): 하나로 합칠지, 둘 다 둘지 검토했다. 실제로 서로 다른 요소로 쓰이는 말이라 합치지 않기로 했다.
- **비공개 시드의 실제 사건 요약어를 비교 대상에 포함할지**: 지금 포함하면 공개 저장소에 두지 않는 원칙(BE-17)과 충돌할 여지가 있어, 관리자 후검수 연결 이후로 미뤘다.
- **1·2순위 점수 차가 작을 때의 처리**: 부정어 구분이 약해(초범 → 전과 없음 0.877 / 동종 전과 0.871) 반대 뜻이 같이 올라오는 경우가 있어, 이를 그대로 제안할지 "애매함"으로 걸러낼지 검토했다.

## 선택한 방법과 이유
- (리뷰 반영) minScore를 0.90으로 올렸다. 실제 사건 요약어가 쌓이면 다시 정할 잠정값이다.
- (리뷰 반영) 겹치는 기준 쌍은 둘 다 목록에 남겨 두고, 흔들림은 "애매함(ambiguous)" 표시로 드러내는 쪽을 택했다 — 목록을 줄이는 대신 판단을 관리자에게 넘긴다.
- (리뷰 반영) 1·2순위 점수 차가 `AMBIGUOUS_MARGIN`(0.01) 미만이면 `ambiguous: true` + `suggested: null`로 표시해 자동 제안을 하지 않는다.
- 비공개 시드 비교는 지금 하지 않는다 — 실제 사건 적재가 쌓이고 관리자 후검수 화면이 연결된 뒤에 다시 정하기로 했다.
- 요약어·preLabel 개인정보·형량 검사, court 인용 마스킹 토큰(MASK_TOKENS) 잔존 검사를 함께 보강했다 — 기존 검사에 있던 빈틈이라 요약어 후보 기능과 별개로 같이 막아야 했다.

## 고려한 제약 사항
- 임베딩은 한 번만 호출한다(목록 + 요약어, 같은 글자는 중복 호출하지 않음) — 비용·지연 관리.
- 요약어 후보 DB 적재·관리자 화면 표시(S-19)는 이 이슈 범위 밖이며 후속 이슈로 넘겼다.
- CI 워크플로에는 `tools/ai-judgment`의 파이썬 테스트가 없어, 이 PR의 GitHub Actions 체크는 이번 변경을 검증하지 않는다(로컬에서만 442개 테스트 통과 확인).

## 추후 재검토가 필요하면
- 실제 사건 요약어가 쌓이면 minScore·AMBIGUOUS_MARGIN을 다시 실측해 조정한다.
- 요약어 후보 DB 적재(factor jsonb)·관리자 화면 표시(S-19)를 후속 이슈로 진행한다.
- `tools/ai-judgment` 파이썬 테스트를 CI에 추가하는 것을 별도 이슈로 검토한다.
