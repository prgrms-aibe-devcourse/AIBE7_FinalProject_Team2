# FE-152 의사결정 기록

Epic FE-151(전 페이지 모바일 390px 대응)의 공통 기반. 화면 묶음별 작업(FE-153 ~ 159)이 따르는 기준을 여기서 정했다.

## 문제 / 배경
- 모바일 전환 분기점이 600 · 680 · 720 · 760 · 768 다섯 가지로 섞여 있었다(DESIGN.md "현재 코드와 차이" 10번). 같은 폭에서 화면마다 모바일/데스크톱 모양이 갈렸다.
- 터치 공통 규칙(탭 번쩍임 · touch-action)은 이미 있었지만, iOS 입력창 확대 · 가로 모드 글자 키움 · 노치 여백 · 화면별 상태 바 색은 없었다.

## 검토한 대안
- 분기점
  - A. 720 / 721 하나로 통일: 이미 가장 많이 쓰였고(720 20곳 + 721 8곳), 공통 헤더 두 줄 전환도 720이다. 681 ~ 720 구간을 쓰던 무대(680)는 이 구간 모양이 바뀐다.
  - B. 680으로 통일: 무대 · 판결 체험(19곳)은 그대로지만 헤더(720)와 어긋나 681 ~ 720에서 "헤더는 모바일, 본문은 데스크톱"이 생긴다.
  - C. 여러 단(480 · 720 · 1024) 체계: 정교하지만 지금 화면 수에 비해 확인 비용이 크다.
- 입력창 16px
  - A. `pointer: coarse`에서만, 낮은 우선순위(`input:not(...)`)로 올림
  - B. 모든 기기에 `!important`로 강제: 확실하지만 지면 축소 연출 안 입력창(데스크톱 포함)의 모양을 깬다
- 상태 바 색
  - A. 화면 테마 표(routes.js)에 색을 적는다: 색이 CSS와 두 곳에 생긴다
  - B. 라우터가 그린 헤더의 실제 바탕색을 읽는다(`getComputedStyle`): CSS가 단일 출처

## 선택한 방법과 이유
- 분기점 A(720 / 721). 헤더와 본문이 같은 폭에서 함께 바뀌는 것이 가장 중요했다. 무대의 681 ~ 720 구간은 FE-155에서 그 폭을 찍어 확인한다. 작은 폰(≤ 380), 태블릿(≤ 1100), 헤더 압축(721 ~ 1000)은 뜻이 달라 그대로 둔다.
- 입력창 A. 데스크톱 모양을 바꾸지 않고, 클래스로 더 작게 정한 화면은 각 묶음에서 고친다.
- 상태 바 색 B. 마이페이지 커피 헤더처럼 테마가 늘어도 따로 고칠 곳이 없다. 헤더를 직접 그리는 관리자는 index.html 처음 값으로 돌린다.
- `overscroll-behavior: none`을 html에 두지 않았다. 문서형 사이트라 당겨서 새로고침이 자연스럽고, 오버스크롤 색 맞추기는 사파리 한계로 이미 포기한 항목이다.

## 고려한 제약 사항
- 화면 묶음 7개를 병렬 브랜치로 고치므로 공통 파일(`style.css` · `index.html` · `app/*` · `siteLayout.js`)은 이 이슈만 고친다.
- 헤드리스 크롬 에뮬레이션으로는 탭 지연 · 노치 · 키보드 · 입력 확대를 재현할 수 없다. 실기기(사파리) 확인은 FE-36과 함께 한다.

## 추후 재검토가 필요하면
- 묶음 작업이 끝난 뒤 남은 600 · 680 · 760 · 768이 있으면 이유를 DESIGN.md에 적거나 정리한다.
- 다크 모드가 생기면 `theme-color`를 색 체계별로 나눈다.
