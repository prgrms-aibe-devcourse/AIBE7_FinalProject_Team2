# BE-89 의사결정 기록

## 문제 / 배경

COMMON-41에서 사건 사진(사건 대표사진 · 사건 발단 사진)을 Cloudflare AI(Workers AI)로 직접 생성하기로 결정했다(`docs/decisions/COMMON-41.md`). BE-89는 이 결정을 메인 백엔드(Spring Boot)에 실제로 연동하는 작업이다. 참고용으로 미리 만들어 둔 예제 프로젝트(`/Users/baegseungho/IdeaProjects/imagegen`, Spring Boot + Spring AI)가 있어 이 구조를 가져왔다.

## 검토한 대안

### 1. Cloudflare Workers AI 호출 방식

- **대안 A — Spring AI의 `ImageModel`/`ChatModel`을 쓴다.** 메인 프로젝트가 Spring AI를 이미 도입했다면 일관성이 있겠지만, **Spring AI는 Cloudflare Workers AI를 공식 지원하지 않는다**(참고 프로젝트도 Cloudflare 이미지 호출은 Spring AI가 아니라 커스텀 `RestClient`로 직접 구현했다). 메인 프로젝트에도 Spring AI 의존성이 없다.
- **대안 B(선택) — 메인 프로젝트가 이미 쓰고 있는 RAG 임베딩 클라이언트 패턴(`rag/config/RagConfig.java` · `RagProperties.java` · `GeminiQueryEmbeddingClient.java`)을 그대로 따라 `RestClient` 빈 + `@ConfigurationProperties` record + 인터페이스/구현체 분리로 만든다.** 새 의존성(Spring AI) 추가 없이 기존 컨벤션 그대로 확장할 수 있다.

### 2. 재시도 정책

- RAG 임베딩 클라이언트는 429 · 5xx를 지수 백오프로 재시도한다. 이미지 생성은 **재시도하지 않기로 했다** — 실패 원인이 같아도(한도 초과 등) 이미지 생성 1회 비용이 텍스트 임베딩보다 커서, 자동 재시도가 호출 비용을 조용히 배로 늘릴 위험이 더 크다고 판단했다. 실패하면 호출한 쪽(서비스 레이어, 후속 이슈)이 사람 판단을 거쳐 다시 시도하게 한다.

### 3. 생성된 이미지의 저장 · DB 기록 범위

- 메인 프로젝트에는 아직 **S3/MinIO 같은 파일 스토리지 연동이 없고**, `LegalCase` 엔티티에도 "사건 대표사진 · 발단사진"을 위한 전용 컬럼/테이블이 없다(`thumbnailUrl` 단일 문자열 필드만 존재). 참고 프로젝트(`imagegen`)는 `S3Template` + JPA 엔티티로 저장까지 구현하지만, 이를 그대로 가져오려면 ① 스토리지 선택(S3/MinIO/다른 방식, 비용 · 운영 부담 검토) ② 사건 사진 데이터 구조 설계(대표사진 1장 vs 발단사진 여러 장, `LegalCase`에 컬럼 추가 vs 별도 테이블)가 먼저 필요하다.
- **대안 A — 이번 이슈에서 저장 · DB 기록까지 전부 구현한다.** 스토리지 · 스키마를 임시로 정해서 밀어붙이면 "Cloudflare 연동"과 "사건 사진 저장 구조 설계"라는 서로 다른 두 결정이 한 PR에 섞여, 나중에 스토리지를 바꾸거나 스키마를 다시 설계할 때 되돌리기 어렵다.
- **대안 B(선택) — 이번 이슈는 Cloudflare Workers AI 호출(설정 · 클라이언트 · 프롬프트 빌더)까지만 구현하고, 생성된 이미지 바이트를 반환하는 데서 끝낸다.** 저장 · DB 기록 · 컨트롤러는 스토리지 · 스키마 결정이 끝난 뒤 후속 이슈에서 진행한다.

## 선택한 방법과 이유

- Cloudflare Workers AI는 `com.team2.project.imagegen` 패키지에 RAG 클라이언트와 같은 패턴(`ImageGenConfig` · `ImageGenProperties` · `CaseImageGenClient`/`CloudflareCaseImageGenClient`)으로 구현했다. 계정 ID · API 토큰이 없으면 `enabled() == false`로 꺼지고 서버는 정상 기동한다(RAG와 동일한 원칙).
- 이미지 생성 실패는 재시도 없이 바로 `ImageGenException`으로 알린다.
- 사건 사진 프롬프트는 `CaseImagePromptBuilder`로 분리했다. 등장인물은 얼굴 없는 회색 엑스트라, 내로 · 남불은 미등장이라는 COMMON-41 결정을 문구로 강제한다.
- **저장(업로드) · DB 기록 · 컨트롤러는 이번 이슈 범위에서 뺐다.** 스토리지 선택과 사진 데이터 구조 설계는 팀 논의가 필요한 별도 결정이라, 섣불리 정하지 않고 후속 이슈로 넘긴다.

## 고려한 제약 사항

- `CloudflareCaseImageGenClient.generateImage()`는 이미지 바이트(byte[])만 돌려준다. 호출하는 쪽(향후 서비스 레이어)이 스토리지 업로드 · DB 기록 · URL 생성을 책임져야 한다.
- 모델명(`@cf/black-forest-labs/flux-1-schnell`)에 `/`가 들어 있어, `RestClient`의 경로 변수(`{model}`)로 넘기면 한 세그먼트로 보고 `%2F`로 인코딩해 버린다. 문자열을 직접 이어붙이는 방식(`"/run/" + model`)으로 우회했다 — 모델명이 신뢰 가능한 설정값이라 인코딩 생략에 따른 위험은 없다.
- `CaseImagePromptBuilder`의 스타일 문구(그림체 세부 묘사)는 실제 생성 테스트 없이 작성한 초안이다. 실제 호출 결과를 보고 다듬어야 한다(`docs/decisions/COMMON-41.md`의 "추후 재검토" 항목과 동일).

## 추후 재검토가 필요하면

- 생성된 이미지를 어디에 저장할지(S3 호환 스토리지 신규 도입 여부, 비용), 사건 사진을 어떤 테이블/컬럼 구조로 저장할지(대표사진 1장 · 발단사진 여러 장을 `LegalCase`에 붙일지 별도 테이블로 뺄지)는 별도 이슈에서 정해야 한다.
- 실제 호출 테스트(비용 발생)로 응답 시간 · 실패율 · 프롬프트 품질을 확인하고 `CaseImagePromptBuilder`의 문구를 다듬어야 한다.
- 관리자 화면(사건 등록)에서 이 기능을 어떻게 트리거할지(버튼 · API 경로 등)는 컨트롤러를 만들 후속 이슈에서 설계한다.
