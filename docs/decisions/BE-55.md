# BE-55 의사결정 기록

## 문제 / 배경

AI 판결 생성(generate)은 같은 사건을 3회 돌린다(모델 호출마다 답이 조금씩 달라지므로). `select` 단계가
그중 실제로 적재할 1건을 고른다. 기본 전략 `consensus`는 **판단 요소(요소 13개 안팎)의 방향("유리" ·
"불리" · "선택 안 함")이 다수 의견과 가장 많이 일치하는 회차**를 고른다(`pipeline.py`의 `direction_table`
· `_majority`).

방향은 3값짜리 라벨이라 **3회 전부 같은 방향을 고르는 경우가 흔하다** — 실제로 BE-76(RAG 끔·켬 비교
시험)에서 "요소 방향은 13/13 그대로인데 형량은 회차마다 낮은 쪽으로 움직였다"는 결과가 나왔다
([RAG 인수인계 5-7](../rag-handover.md)). 구조 점수가 동점이면 지금 코드는 "경고 적은 · 앞선 회차"로
떨어지는데, 경고 수도 보통 같아서 **사실상 1번 회차를 그대로 쓰는 셈**이 된다. 판결 이유(`reasoning`)
본문이 다른 회차들과 얼마나 수렴했는지(= 대표성)는 이 과정에서 전혀 반영되지 않는다. (주의: 이건
"설득력 · 구체성"과는 다른 성질이다 — 여러 회차가 수렴했다고 해서 그 reasoning이 더 설득력 있다는
보장은 없다. 아래 "선택한 방법과 이유"의 medoid 설명 참고.)

BE-55는 이 구멍을 메우려고, 판결 이유 본문이 다른 회차와 얼마나 수렴하는지(의미 유사도, 임베딩)를
선택 기준에 더하는 작업이다.

## 검토한 대안

### 1. 기존 `consensus`에 어떻게 반영할까

- **대안 A: 새 전략으로 분리** (`stages.select.strategy`에 `semantic-consensus` 같은 값 추가) — 기존
  `consensus` 코드를 안 건드려 안전하지만, "둘 중 뭘 기본으로 할지"를 또 한 번 정해야 하고, 설정이 늘어난다.
- **대안 B: 동점일 때만 tie-breaker로** — 구조 점수가 완전히 같을 때만 임베딩으로 가른다. 변경은 작지만,
  "구조 점수가 2/3 vs 3/3처럼 근소하게 갈리는데 판결 이유는 3/3 쪽이 훨씬 부실한" 경우를 못 잡는다.
- **대안 C: 가중 합산** — `최종점수 = 구조점수 × (1 - w) + 유사도점수 × w`. 동점 상황뿐 아니라 근소한
  차이도 함께 반영된다. 가중치 `w`로 영향력을 조절할 수 있어 샘플 비교로 값을 좁혀 갈 수 있다.

**선택: 대안 C.** Jira 이슈 설명에 "점수 반영 방식 설계(가중치 예시 0.3, 샘플 검증으로 확정)"로 이미
방향이 적혀 있었고, 완료 조건("기존 select 모드 유지")도 맞춰야 해서, **기존 `consensus` 전략 안에
`semanticWeight`라는 설정 하나를 추가**하는 형태로 구현했다(새 전략을 만들지 않음). `first-valid` ·
`fewest-warnings` · `manual`은 전혀 건드리지 않는다.

### 2. 가중치 기본값

- **대안 A: 이슈 설명의 예시값 0.3을 기본값으로** — 바로 효과가 생긴다.
- **대안 B: 기본값 0(끔)** — 설정으로 켜야 영향이 생긴다.

**선택: 대안 B.** 0.3은 "샘플 검증으로 확정"하라고 명시된 예시값이지, 확정값이 아니다. 지금 가진 사건
수가 적어(BE-76 비교 시험도 1건으로 했다) 실제 사건으로 비교해 보지 않은 값을 기본으로 올리면, 서비스에
들어가는 판결이 검증 안 된 기준으로 바뀐다. **기본 0이면 이 변경 자체가 완전히 안전하다** — 기존
`consensus` 결과와 100% 같다(완료 조건 "기존 select 모드 유지, 회귀 없음 확인"을 그대로 만족한다).
가중치를 실제로 정하려면 `db_case_input.py` → `--until select`로 여러 사건 · 여러 회차에 0.3 안팎의 값을
돌려 보고 비교하는 절차가 필요한데(BE-76과 같은 방법), 이는 **실제 사건이 더 쌓인 뒤의 후속 작업**으로
남긴다.

### 3. 무엇을 임베딩할까

- **대안 A: `reasoning`(판결 이유 전체 본문)**
- **대안 B: `factors[].reason`(요소별 이유)까지 합쳐서**

**선택: 대안 A.** `reasoning`이 판결의 핵심 서술이고, 이미 검증(`validate_output.py`)에서 "이유에
까닭이 있는지"를 보는 필드이기도 하다. 요소별 이유까지 합치면 텍스트가 길어져 임베딩 차이가 희석되고,
형량 숫자가 섞여 들어갈 위험(이슈 설명에는 없지만 BE-53 요약어 임베딩에서 "판결문 원문은 안 보낸다"는
원칙과 같은 결의 우려)도 있다. 필요하면 후속으로 넓힐 수 있다.

### 4. 유사도 계산 방법 (어떤 회차를 고를까)

- **대안 A: 가장 비슷한 두 회차끼리만 비교해서, 그 쌍 중 하나를 고른다**
- **대안 B: "다른 후보 전원과의 평균 코사인 유사도"(medoid 점수)**

**선택: 대안 B.** 3회만 도는 상황에서 "가장 가까운 쌍"은 결국 3개 중 2개를 고르는 것과 비슷하지만, 평균
유사도는 "혼자 튀는 회차"를 자연스럽게 낮은 점수로 만든다(통계의 medoid와 같은 생각). 후보가 늘어나도
(향후 `runs`를 키울 경우) 같은 방식으로 확장된다.

### 5. 임베딩 호출이 실패하면

- **대안 A: 사건 등록 전체를 실패시킨다**
- **대안 B: RAG(`rag_context.py`) · 요약어 후보(BE-53, `summary_tags.py`)와 같은 정책 — 조용히 건너뛰고
  기존 방식으로 진행한다**

**선택: 대안 B.** 이미 파이프라인에 있는 두 선례와 같은 정책을 따른다. select는 반드시 회차 하나를
골라야 하는 필수 단계라, 임베딩(부가 기능)이 실패했다고 사건 등록 전체를 막을 이유가 없다.

## 선택한 방법과 이유

1. `tools/ai-judgment/select_semantic.py` 신설 — `reasoning_similarity_scores()`(medoid 평균 코사인
   유사도), `option_errors()`, `default_embed()`(모델 `gemini-embedding-001` · task type
   `SEMANTIC_SIMILARITY` 고정, BE-53 `summary_tags.py`와 같은 패턴).
2. `pipeline.py`의 `select_run()`에 `semantic_weight`(기본 0) · `embed_fn` · `log` 매개변수 추가.
   `consensus` 전략에서 `semantic_weight > 0`이고 임베딩이 성공하면
   `blended = structural/max_structural × (1 - w) + semantic × w`로 고르고, 실패하거나 0이면 기존 구조
   점수만으로 고른다(기존 동작과 동일).
3. `stages.select.semanticWeight` 설정 추가(기본 0, 범위 0 ~ 1), `validate_config`에 검사 추가.
4. 테스트: `tests/test_select_semantic.py`(모듈 단위) · `test_pipeline.py`의 통합 테스트(동점 깨짐 확인,
   임베딩 실패 시 fallback 확인) — 전부 가짜 임베딩 함수로 네트워크 호출 없이 돈다.

## 고려한 제약 사항

- 완료 조건 "기존 select 모드(`first-valid` · `fewest-warnings` · `manual`) 유지"를 지켜야 해서, 이
  전략들은 `semantic_weight` 매개변수 자체를 보지 않는다.
- 임베딩 비용: 사건 1건당 3회 생성 → 텍스트 3개 → 배치 호출 1번. RAG 판례 검색(수십 건)보다 훨씬 적다.
- 가중치 0.3이 실제로 적절한지는 검증되지 않았다(아래 "추후 재검토" 참고).

## 추후 재검토가 필요하면

- 실제 사건이 더 쌓이면 `db_case_input.py` → `pipeline.py run --until select`로 `semanticWeight`를
  0.1 ~ 0.5 사이 몇 값으로 돌려 비교하고(BE-76과 같은 방법), 기본값을 0이 아닌 값으로 올릴지 정한다.
  결과는 [RAG 인수인계](../rag-handover.md) 5-6에 추가한다.
- `runs`(생성 회차 수)를 3보다 늘리면 medoid 평균 계산 비용이 커진다(현재 O(n²) 코사인 비교) — 지금
  규모(3회)에서는 무시할 수준이라 최적화하지 않았다. 위 대안 4(medoid)의 "회차 수 3"도 이 가정 위에서
  고른 것이다 — `runs`가 커지면 다시 봐야 한다.
- **대안 C가 "근소한 차이"도 뒤집는다는 근거는 아직 실측하지 않았다.** 구조 점수 1칸 차이는
  `(1 - w) / len(consensus)`인데(요소 13개 · w=0.3이면 약 0.054), `reasoning_similarity_scores`가
  돌려주는 유사도는 같은 사건의 회차끼리라 좁은 범위에 몰릴 수 있다(실측 필요). 후보 간 평균 코사인
  차이가 이 값보다 작으면 사실상 "동점 깰 때만 반영"(대안 B와 같은 동작)이 된다. 실제 사건으로 유사도
  분포를 재 보고, 필요하면 후보 간 min-max 정규화를 검토한다.
- **후보 풀이 여러 모델을 가로지르면 medoid가 "모델 문체"에 가까워질 수 있다.** `reasoning_similarity_scores`는
  `select_run`에 넘어온 후보 전체(모든 모델 × 회차)로 medoid를 구한다. 지금은 `generate.models`가
  사실상 모델 1개(BE-54 COMMON-40 결정)라 괜찮지만, 모델이 2개 이상으로 늘면 문체가 비슷한 모델 쪽
  회차가 유리해질 수 있다. 또 검증 통과 후보가 2개로 줄면 두 점수가 항상 같아 가중치가 효과가 없다.
  모델이 늘어나는 시점에 모델별로 따로 medoid를 구하는 방식을 다시 검토한다.
- **`stages.select.score`가 `semanticWeight > 0`일 때는 혼합 점수(0~1 float), 아닐 때는 구조 일치
  개수(int)로 의미가 달라진다.** 지금은 보고서에만 쓰여 문제가 없지만, BE-76류 회차 비교 시험에서 이
  필드를 가중치 다른 실행 간에 직접 비교하면 안 된다. 비교가 필요해지면 `semanticScore` 같은 별도
  필드로 분리한다.
