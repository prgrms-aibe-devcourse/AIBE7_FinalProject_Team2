# FE-47 의사결정 기록

> 담당 김해송 · 범위 확정 2026-10-20 (Jira FE-47 설명)

## 문제 / 배경
- 메인 책상의 노트북(커뮤니티)과 헤더의 "커뮤니티" 메뉴가 "준비 중"이었다. S-18은 IA에 "로그인 · 운영 정책이 정해진 뒤 설계"로만 남아 있었다.
- 범위: 게시글 목록 · 상세 · 작성, 댓글, 좋아요, 판결 결과 공유, 이미지 첨부. 커뮤니티 API는 아직 명세에 없어 목데이터로 만든다.

## 검토한 대안
- 판결 결과 공유
  - 대안 A: 세 판결(내 판결 · AI · 실제)을 모두 공유. 비교 화면을 그대로 옮길 수 있지만, 그 사건을 아직 안 한 사람에게 실제 판결이 먼저 보인다(앵커링 방지 원칙과 충돌).
  - 대안 B: 체험을 마친 사람에게만 결과를 펼침(가림 처리). 원칙은 지키지만 글마다 열람 조건을 따져야 해 화면 · API가 복잡해진다.
  - 대안 C: 내 판결만 공유(형량 · 무겁게 / 가볍게 본 요소 수). 
- 게시판 단위: 사건별 게시판 vs 전체 피드 + 사건 태그
- 권한: 익명도 쓰기 가능 vs 읽기는 누구나 · 쓰기 · 댓글 · 좋아요는 로그인
- 화면 구성(impeccable 구성 세 안): 타임라인 + 고정 글쓰기 / 고밀도 게시판 표 / 사건 탭 + 카드 격자

## 선택한 방법과 이유
- 판결 공유는 **대안 C(내 판결만)**. 사용자 결정. AI · 실제 판결은 글에 담지 않고, 판결 값은 화면이 보내지 않고 서버(목)가 내 확정 판결에서 붙인다(`shareVerdict: true`). 판결을 확정하기 전(S-06 제출 전)에는 붙일 수 없다.
- **전체 피드 + 사건 태그**. 지금 체험할 수 있는 사건이 사실상 1건이라 사건별 게시판은 한 방만 찬다. 말머리(판결 공유 · 질문 · 자유)와 사건으로 거른다.
- **읽기는 누구나, 쓰기는 로그인**. 기존 목업 로그인(FE-52)을 쓴다. 로그아웃 상태에서 좋아요 · 댓글을 누르면 그 자리에 로그인 안내를 띄운다.
- 화면은 **타임라인 + 고정 글쓰기**(사용자 선택). 메인 책상 노트북의 연장이라 화면 전체를 노트북 베젤 테두리 안에 두고, 노트북을 누르면 화면이 위아래에서 눈을 감듯 어두워졌다가 눈을 뜨듯 열리며 커뮤니티가 나온다 — 컴퓨터 부팅 표현(`utils/laptopBoot.js`). 확대 연출은 노트북 그림이 흐려지고 기울기 때문에 어색해 버렸다. 좁은 화면(1023px 이하)에서는 한 열이 되고 글쓰기는 화면을 덮는 창이 된다.
- 상세는 주소를 가진 화면(`/community/posts/:postId`). 라우터에 `:postId` 자리표시자를 추가했다(`:caseId` · `:shareId`와 같은 방식). 링크는 진짜 `<a>`라 새 탭 열기가 된다.
- 첨부 사진은 긴 변 1280px JPEG로 줄여 보낸다(최대 3장). 목은 브라우저 저장소에 둔다.

## 고려한 제약 사항
- 서버 명세 없음 → 함수 이름 · 응답 모양은 화면이 필요한 최소로 가정했다(`mocks/communityMockApi.js`, 테스트 `communityMockApi.test.js`). 오류 코드 `LOGIN_REQUIRED` · `POST_NOT_FOUND`는 임시 이름이다.
- 실제 사용자 글 · 통계가 없다 → 목 글은 판결 방향을 정답처럼 말하지 않게 썼고, 제목 · 많이 본 글에 "목데이터"를 붙였다.
- 거르기 값은 주소가 아니라 기록 항목(`history.state`)에 둔다. 라우터가 쿼리 문자열을 다루지 않아서다. 상세에서 뒤로 오면 같은 목록이 보인다.

## 추후 재검토가 필요하면
- 글 · 댓글 수정 · 삭제, 신고 · 숨김(관리자 FE-45 게시글 · 신고 메뉴와 연결), 레벨 프로필(REQ-130)은 운영 정책과 API 설계 때 정한다.
- 내 판결이 공개 글에 실리면, 사건을 아직 안 한 사람이 다른 사람의 형량을 먼저 보게 된다. 실제 판결보다 영향은 작지만 운영 뒤 반응을 보고 B(가림)를 다시 검토한다.
- 거르기 값을 주소(쿼리)로 옮길지, 쓰던 글이 있을 때 화면을 떠나면 경고할지.
