# BE-160 의사결정 기록

## 문제 / 배경
- 운영 사건 등록(A-14)에서 사전 학습 점검(contamination 단계, BE-37)을 켜야 한다.
- 파이프라인 서비스는 이 단계를 기본으로 끈다(`tools/ai-judgment/service/jobs.py` `DISABLED_STAGES`). 호출 수가 많아서다(생성 모델마다 기본 10회).
- 서비스는 요청의 `stages.contamination`으로 다시 켤 수 있게 이미 열어 두었다. 그래서 파이프라인 쪽은 바꿀 것이 없고, 백엔드가 켜 달라고 보내기만 하면 된다.

## 검토한 대안
- 대안 A: 백엔드가 항상 켜서 보낸다
  - 장점: 설정이 하나 줄어든다.
  - 단점: 설정을 건드린 적 없는 서버(로컬 · 다른 개발 서버)에서도 등록마다 모델 호출이 10회씩 늘어난다. 끄려면 코드를 바꿔야 한다.
- 대안 B: 환경변수 스위치 `PIPELINE_CONTAMINATION_ENABLED`(기본 꺼짐)
  - 장점: 대본(`PIPELINE_SCRIPT_MODEL`, BE-129)과 같은 방식이다. 운영에서 켜고 끄는 데 재배포 없이 `.env`만 바꾸면 된다.
  - 단점: 운영 `.env`에 값을 넣는 작업이 하나 더 생긴다.
- 판정 동작(`onContaminated` · `onSuspect` · `onInsufficient`)까지 백엔드 설정으로 열지도 검토했다.
  - 기본값(오염 → 중단, 의심 → 계속, 응답 부족 → 중단)을 그대로 쓰기로 했고, 지금 바꿀 필요가 없다. 설정을 늘리면 파이프라인 기본값과 어긋날 곳만 생긴다.

## 선택한 방법과 이유
- 대안 B를 택했다. 스위치를 켜면 `stages.contamination`에 `{"enabled": true}`만 보낸다.
  - 판정 동작은 보내지 않는다. 그래야 파이프라인 `DEFAULT_CONFIG`의 기본값이 쓰이고, 기본값을 바꿀 때 한 곳만 고치면 된다.
- 값은 `Boolean`으로 받고, null은 꺼짐으로 본다.
  - Compose는 `.env`에 없는 값을 빈 문자열로 넘긴다(`${PIPELINE_CONTAMINATION_ENABLED:-}`). 빈 문자열은 바인딩 결과가 null이 되므로, 원시형 `boolean`이면 바인딩이 실패할 수 있다.
  - 모델 값들을 빈 문자열에서 "설정 안 함"으로 되돌리는 것과 같은 이유다(`PipelineProperties` 생성자).

## 고려한 제약 사항
- 점검은 generate 앞 단계라 `until`(기본 axis)을 바꾸지 않는다.
- 비식별화한 사건 개요가 생성 모델 공급자로 나간다. 생성(generate)과 같은 모델 · 같은 공급자라 새로 나가는 정보는 없다.
- 등록 시간이 늘고 서버 메모리 여유가 크지 않다(t3.small). 켠 뒤 첫 등록 때 `free -m` · `docker stats`를 기록하기로 했다(운영 메모는 Jira BE-160).

## 추후 재검토가 필요하면 (선택)
- 운영에서 의심(SUSPECT) 판정이 잦으면 `onSuspect`를 백엔드 설정으로 열지 다시 본다.
- 점검 호출 수(`runs` 10)가 비용 · 시간에 부담이면 줄일지 다시 본다.
