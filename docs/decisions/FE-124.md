# FE-124 의사결정 기록

> 프론트 화면 다듬기 모음. 이 이슈로 처음 만든 내 정보 수정(서명 미리보기 · 카드 아래 버튼) · 성향카드 캐릭터 선택 · 메인 신문 모서리 · 러그 밑 서류철 조정은 FE-119 브랜치 커밋(`a4c86b2`)에 함께 들어가 PR #314로 이미 `develop`에 머지됐다. 이 문서는 FE-124 브랜치에 남은 세 가지를 다룬다.

## 1. 메인에서 신문 · 서류철을 누르면 메인이 위로 튀던 현상

### 문제 / 배경
- 신문 · 서류철을 누르면 다음 화면이 아래에서 올라오는 동안 메인을 뒤에 남겨 흐리게 걷는다(`.paper-ghost` · `.personality-ghost`). 이 층이 화면 맨 위(`inset: 0`)부터 그려져 메인이 공통 헤더 높이(약 53px)만큼 위로 튀었다.
- 스크롤을 내린 채 누르면 라우터가 이동 직전에 스크롤을 맨 위로 올려, 서류철은 새 화면이 그려지기 전 약 0.4초 동안 메인이 위로 올라가 있다가 다시 내려왔다(신문은 들어 올리는 연출 380ms가 가려 덜 보였다).
- 맨 아래 신문 끝자락 경로(`from: 'tail'`)는 이미 실제 위치를 재서 맞추는 보정이 있었다.

### 검토한 대안
- 남기는 층만 헤더 아래부터 두기: 헤더 높이 튐은 사라지지만 스크롤이 있을 때의 튐은 남는다.
- 끝자락 경로처럼 화면마다 위치를 재서 `translate`로 보정: 신문 · 서류철마다 같은 코드를 또 두게 된다.
- 누른 순간의 스크롤 값을 넘기고, 라우터는 그 경우 미리 올리지 않기: 새 화면이 자리를 바꾸는 순간에 직접 올리고 뒤 책상은 그 값만큼 내린 자리에 둔다.

### 선택한 방법과 이유
- 세 번째 안. 남기는 층은 `inset: var(--site-header-h) 0 0`, 책상에서 누를 때 `deskY`를 넘기고, 라우터는 `deskY`가 있으면 이동 직전에 스크롤을 올리지 않는다(그린 뒤 한 번 더 올려 빠지는 경우를 막는다). 새 화면은 DOM을 바꾸는 순간 맨 위로 올리고 뒤 층의 `scrollTop`을 `deskY`로 둔다.
- 측정(헤드리스 크롬, 물건 윗변의 화면 위치): 신문 스크롤 0 · 300px, 서류철 0 · 80px 모두 이동 전후가 같다. 끝자락 경로도 보정이 실제 위치를 재는 방식이라 그대로 맞는다.

## 2. 커뮤니티 3열 → 2열, 글쓰기를 별도 페이지로

### 문제 / 배경
- 넓은 화면은 왼쪽 거르기 · 가운데 글 · 오른쪽 늘 열린 글쓰기 칸의 3열이었다. 오른쪽 칸 아래의 "많이 본 글"은 사용자도 있는 줄 몰랐다.

### 검토한 대안
- 많이 본 글: 왼쪽 열 아래 · 글 목록 위 가로 줄 · 빼기.
- 글쓰기: 큰 화면만 별도 페이지(좁은 화면은 지금의 덮는 창 유지) · 모든 폭을 한 페이지로 통일.

### 선택한 방법과 이유
- 많이 본 글은 왼쪽 열 아래(사용자 결정). 좁은 화면(1023px 이하)에서는 위 칸이 거르기만 남도록 숨긴다.
- 글쓰기는 모든 폭에서 `/community/write` 한 페이지(사용자 결정). 덮는 창의 열기 · 닫기 · 포커스 가두기 · 폭 변경 처리 코드가 통째로 빠졌다.
- 글쓰기 폭은 고정하지 않고 가운데 열을 그대로 쓴다(처음 720px 고정은 넓은 화면 오른쪽이 비어 사용자가 반응형을 요구).
- 글쓰기 버튼은 왼쪽 열 맨 아래(거르기 · 많이 본 글이 나중에 붙어도 `order`로 맨 아래), 좁은 화면은 그 열 오른쪽 위(사용자 결정). 글쓰기 페이지 자신에는 두지 않는다.
- 커뮤니티 메인의 "모든 글 보기"는 말머리 "전체"와 역할이 겹쳐 지웠고, 메인은 목록과 다른 화면이라 거르기에 눌림 표시를 두지 않는다.

### 고려한 제약 사항
- 좁은 화면에서 왼쪽 열을 `relative`로 바꾸자 넓은 화면용 `sticky`의 `top` 값이 남아 칸이 66px 밀렸다. `top: auto`로 푼다.

## 3. 오버스크롤(고무줄 스크롤) 색 — 포기

### 문제 / 배경
- 쪽 끝에서 더 당기면 드러나는 자리가 헤더 · 푸터와 다른 색으로 보였다. 처음 요구는 "위로 당기면 헤더 색, 아래로 당기면 쪽 맨 아래 색이 무조건 이어지게"였다.

### 검토한 대안 (모두 사파리에서 사용자가 확인)
- 헤더(`sticky`)에 붙인 위쪽 띠(`#route-header::before`, 메인이 쓰던 방식): 위가 베이지로 보였다.
- `html` 배경을 상시 덮기(위쪽 한 화면만 헤더 색 그림 + 나머지 쪽 맨 아래 색): 한쪽만 되고, 평소 바탕까지 바뀌어 성향 테스트 · 사건 목록 · 마이페이지 색이 달라졌다.
- 쪽 위 바깥(`top: -100vh`) 덮개 판 + 당기는 동안(`scrollY < 0`, `> max`)에만 html 배경색 바꾸기: 위 · 아래 대부분 안 됐고, 성향 테스트 · 신문 지면은 당길 때마다 깜박였으며 아래는 바닥 무늬 대신 단색이었다.
- 고무줄 스크롤 끄기(`html { overscroll-behavior-y: none }`): 드러나는 자리는 없어지지만 조작감이 어색하다는 피드백.
- 쪽 전체를 창 스크롤이 아닌 안쪽 스크롤 칸으로 옮기기: 칸 자신의 배경이 드러나므로 위 · 아래를 다른 색 · 무늬로 이을 수 있는 유일한 방법이지만, 창 스크롤을 쓰는 곳이 14개 파일 32곳이라 시도하지 않았다.

### 선택한 방법과 이유
- 포기하고 감수한다(사용자 결정). 사파리는 드러난 자리를 페이지가 아니라 브라우저가 html 배경색 하나로 칠해서 페이지 코드로 위 · 아래를 따로 맞출 수 없다. 끄는 안은 조작감 손실이 더 컸다.
- 시도한 코드는 모두 되돌렸다. DESIGN.md "오버스크롤 색은 맞추지 않는다"에 하지 말 것을 남겼다.

### 고려한 제약 사항
- 헤드리스 크롬은 고무줄 스크롤을 그리지 못해 매번 사용자의 사파리 확인에 기대야 했다. 스크롤 값을 가짜로 바꿔 로직만 확인한 것을 "된다"로 믿은 것이 반복 실패의 원인이었다.

### 추후 재검토가 필요하면
- 위 · 아래 색을 꼭 맞춰야 하면 안쪽 스크롤 칸 구조로의 전환을 별도 이슈로 다룬다(창 스크롤 · `scrollTo` · `scroll` 이벤트 · sticky 헤더 · 스크롤 잠금 · 스크롤 복원 전부 영향).
