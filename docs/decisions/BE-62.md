# BE-62 의사결정 기록

## 문제 / 배경
- 카카오 로그인(REQ-066 · 067, WBS 7.4.2)으로 회원을 만들고, 비로그인 때 한 체험(익명 ID 쿠키 `NLNB_AID`)을 회원 기록으로 잇는다.
- 토큰 발급 · 재발급 · 로그아웃은 C가 BE-94(#218)로 만들었다. D는 카카오 로그인 성공 후 `TokenIssuer`를 호출한다(#106 담당 경계).
- #106에서 **D 결정**으로 남긴 것: 카카오 로그인 왕복의 `state` 저장 · 콜백 경로 · 성공 · 실패 후 정리.
- 관리자 OAuth(BE-40)는 제외했다(관리자 = 이메일 · 비밀번호, 일반 사용자 = 카카오. WBS v1.42). 카카오 로그인은 관리자 권한을 주지 않는다.

## 결정
### 1. 보안 체인 — OAuth 전용 체인 (B 김현중 제안 · 합의)
- 관리자 `@Order(1)` → **OAuth `@Order(2)`**(`securityMatcher("/api/v1/auth/oauth2/**")`, `oauth2Login`만) → 사용자 `@Order(3)`
- 브라우저 이동 경로라 실패를 JSON 401이 아니라 리다이렉트로 처리해야 해서, 사용자 체인의 `JsonSecurityErrorHandler` · permitAll · Bearer 401 규칙과 분리했다. BE-63 2차(로그인 경로 요청 제한) 대상도 분명해진다.
- `KAKAO_CLIENT_ID`가 없으면 체인째 만들지 않는다(로컬 · 테스트 · CI는 그대로 뜬다). ID가 있는데 SECRET이 없으면 기동 실패(설정 실수를 바로 알린다).

### 2. 경로 — `/api` 아래
- 시작 `GET /api/v1/auth/oauth2/authorization/kakao`, 콜백 `GET /api/v1/auth/oauth2/callback/kakao`
- Spring 기본 경로(`/oauth2/...`, `/login/oauth2/code/...`)는 `/api` 밖이라 운영 Nginx에서 SPA로 빠진다.
- 카카오 콘솔 Redirect URI: `https://<도메인>/api/v1/auth/oauth2/callback/kakao`(로컬은 `http://localhost:<포트>/...`)

### 3. `state` 저장 — Redis + state 쿠키, 세션 없음
- 인가 요청 내용은 Redis 토큰 DB에 JSON(TTL 5분), 브라우저에는 state 값만 `NLNB_OAUTH_STATE` 쿠키(`HttpOnly` · `Secure` · `SameSite=Lax` · `Path=/api/v1/auth/oauth2` · 5분)
- 콜백의 `state` 파라미터와 쿠키가 같을 때만 GETDEL로 한 번 꺼낸다 → 로그인 CSRF · 콜백 재사용 방지
- 쿠키는 **Lax**여야 한다: 카카오에서 돌아오는 콜백은 다른 사이트발 최상위 이동이라 Strict면 쿠키가 실리지 않는다.

### 4. 성공 · 실패 후 정리
- 성공: 회원 찾기 · 만들기 → 익명 기록 연결 → `TokenIssuer.issue` → **리프레시 토큰만** `RefreshTokenCookies`(BE-94)로 심고 `/auth/callback`으로 302. 토큰은 URL에 싣지 않는다 → 화면이 재발급 API(M-1)로 액세스 토큰을 받는다(BE-94 합의).
- 실패 · 취소: `/auth/callback?error=login_failed`로 302. 로그에는 오류 코드만(인가 코드 · 토큰 · 개인정보 없음).
- 기본 성공 처리(`SavedRequestAware...`)는 세션을 쓰므로 직접 만든 핸들러로 바꿨다. 카카오 액세스 토큰은 보관하지 않는다(로그인 확인 뒤 카카오 API를 다시 부르지 않음, 메모리 저장소에 쌓이는 것도 막음).
- 화면 경로는 환경변수로 바꿀 수 있지만 우리 사이트 안의 경로(`/...`)만 허용한다(열린 리다이렉트 방지).

### 5. 회원 테이블 — 개인정보 없이 (V25)
- `member(provider, provider_user_id)`만. 카카오 동의항목(닉네임 · 이메일 · 프로필)을 요청하지 않는다.
- `INSERT ... ON CONFLICT DO NOTHING` 후 조회 → 같은 계정의 첫 로그인이 동시에 와도 한 행
- `anonymous_user.member_id`에 FK · 부분 인덱스 추가(V3에서는 member 테이블이 없어 FK를 두지 않았다)

### 6. 익명 기록 연결 규칙
| 상황 | 처리 |
| --- | --- |
| 익명 ID가 아직 연결 안 됨 | 이 회원에 연결 |
| 이미 같은 회원에 연결됨 | 그대로 |
| **다른 회원에 연결됨 (공용 PC 등)** | 덮어쓰지 않음 + **이 회원에 연결된 새 익명 ID 발급** |
| 같은 회원이 다른 브라우저에서 로그인 | 그 브라우저 익명 ID도 연결 (회원 1 : 익명 N) |
| 익명 쿠키 없음 · DB에 없는 값 | 이 회원에 연결된 새 익명 ID 발급 |

- 연결은 `member_id IS NULL`일 때만 바꾸는 조건부 UPDATE라 동시에 와도 꼬이지 않는다.
- 기존 체험(`experience.member_id`)은 일괄로 채우지 않는다(`anonymous_user`를 거쳐 찾는다).

### 7. 프록시 헤더 — `server.forward-headers-strategy: native` (#118 권장)
- Nginx(TLS 종료) 뒤에서 `{baseUrl}`이 https 도메인이 되고, Origin 검증(BE-94) · 요청 제한 · 감사 로그 IP가 실제 값을 본다.
- 백엔드가 이 헤더들을 믿으므로 **Nginx가 `Proto` · `Host` · `Port`는 자기가 본 값으로 덮어쓴다**. `X-Forwarded-Host`를 비워 두면 클라이언트가 보낸 값이 그대로 넘어가 `{baseUrl}` · Origin 검증이 조작된 Host를 볼 수 있다(PR #229 리뷰).
- **`X-Forwarded-For`는 덮어쓰지 않고 기존 값 뒤에 Nginx가 본 접속 IP를 덧붙인다**(`$proxy_add_x_forwarded_for`). 백엔드 RemoteIpValve는 `internal-proxies` 밖의 가장 오른쪽 IP를 클라이언트 IP로 쓰므로, 클라이언트가 앞쪽에 넣은 위조 값은 쓰이지 않는다(PR #229 리뷰).

### 8. 카카오 로그인 경로 요청 제한 — Nginx 전용 zone (PR #229 리뷰)
- 시작 요청마다 Redis에 state를 5분 보관하므로, `/api` 공통 제한(IP별)만으로는 여러 IP로 나눠 Redis(200MB, `noeviction`)를 채울 수 있다.
- 로그인 시작(`/api/v1/auth/oauth2/authorization/`)에 **IP별(분당 30 · 순간 30)** + **전체 합계(초당 10 · 순간 50)** 제한을 더 건다. 전체 합계가 있어서 대기 중 state는 많아야 약 3,000개(약 3MB)다.
- 콜백에는 전용 제한을 두지 않고 `/api` 공통 제한(IP별 초당 20 · 순간 40)만 받는다. 콜백은 Redis에 새로 쓰지 않고(state는 GETDEL로 꺼내기만 함), 쿠키와 state가 맞지 않으면 카카오를 부르기 전에 끝난다. 시작과 같은 zone에 묶으면 동시 로그인 때 시작이 용량을 써서 콜백이 429가 된다(PR #229 리뷰).
- 백엔드에 개수 상한을 따로 두지 않았다: 백엔드 포트는 밖으로 열려 있지 않아(Compose 내부망) 모든 요청이 Nginx를 지나고, 앱에서 세려면 Redis 카운터를 하나 더 써야 한다. Nginx 한 곳에서 막는 편이 단순하다.
- 운영 이미지와 같은 `nginx:1.28-alpine`으로 확인: 40번 동시 요청 중 31번 통과 · 9번 429, 다른 `/api`는 영향 없음.

## 검토한 대안
- 체인: (A) 사용자 체인에 `oauth2Login` 추가 / (B) OAuth 전용 체인
- `state` 저장: (A) 세션(로그인 경로만 허용) / (B) 인가 요청 전체를 쿠키에 직렬화 / (C) Redis + state 쿠키
- 공용 PC의 남의 익명 기록: (A) 연결만 건너뜀 / (B) 덮어씀 / (C) 건너뛰고 새 익명 ID 발급

## 선택한 방법과 이유
- 체인 (B): 실패 처리 · 오류 형식이 사용자 API와 달라 섞으면 사용자 체인 규칙이 흔들린다. B 제안대로 관리자 체인은 그대로다.
- `state` (C): (A)는 사용자 쪽 무상태 원칙이 깨지고, (B)는 사용자가 고칠 수 있는 쿠키 값을 서버가 역직렬화하게 된다. Redis는 이미 토큰 DB가 있어 추가 인프라가 없다.
- 익명 기록 (C): (A)는 쿠키가 앞 사람 것으로 남아 **이후 체험이 앞 사람 계정으로 쌓이고**, (B)는 남의 기록을 가져간다.

## 고려한 제약 사항
- Spring Boot 4.1 · Spring Security 7.1 (`spring-boot-starter-security-oauth2-client`)
- 리프레시 토큰 쿠키는 BE-94 규칙(`SameSite=Strict` · `Path=/api/v1/auth`)을 그대로 쓴다. 카카오 콜백 응답에서 심는 것은 최상위 이동 응답이라 저장되고, 화면이 같은 사이트에서 부르는 재발급 요청에는 실린다 → **실제 브라우저에서 한 번 확인한다**(아래)

## 추후 재검토가 필요하면
- **로그아웃 시 익명 ID 새로 발급**: 로그아웃 뒤에도 익명 쿠키가 회원에 연결된 채 남아, 공용 PC에서 다음 사람의 체험이 회원 계정으로 쌓일 수 있다. 로그아웃 API(BE-94, C)에서 새 익명 ID를 발급하도록 C와 맞춘다(후속).
- **화면 `/auth/callback`**: 프론트에 이 경로(도착 → 재발급 API → 원래 화면)가 필요하다(FE 후속 이슈).
- **재발급 · 로그아웃 요청 제한**: 카카오 로그인 경로는 이번에 막았다(결정 8). 재발급 · 로그아웃은 BE-63 2차에서 정한다.
- **실제 브라우저 확인**: 운영 도메인에서 카카오 로그인 → `/auth/callback` 도착 → 재발급 200(`NLNB_RT` 쿠키가 실리는지)까지 M2(10/23) 전에 확인한다.
- 표시 이름 등 개인정보가 필요해지면 카카오 동의항목 · 칼럼 · 개인정보 처리 안내를 함께 추가한다.
- **화면 표시 닉네임**: 서버는 닉네임을 두지 않고, 화면은 로그인 성공 시 고정 문구(`카카오 회원`)를 표시 이름으로 쓴다(FE 후속, PR #229 리뷰 · 김해송 확인). 헤더 · 마이페이지는 이것으로 충분하지만, 커뮤니티 글 · 댓글과 사건 리뷰는 서버 응답의 `author.nickname`을 작성자로 보여 주므로 모두 같은 이름이 된다. 커뮤니티 API에서 내려줄 작성자 이름(예: ID에서 만든 `익명 1234`)은 별도 이슈로 정한다.
- **다시 로그인할 때 예전 리프레시 토큰**: 같은 브라우저에서 다시 로그인하면 쿠키는 새 토큰으로 바뀌지만, 예전 토큰은 Redis에 TTL(14일)까지 남는다. 콜백은 카카오에서 오는 다른 사이트발 이동이라 `SameSite=Strict`인 `NLNB_RT`가 실리지 않아 로그인 시점에 지울 수 없다. 쿠키가 없어 쓸 수 없는 값이라 위험은 낮다. 회원별 토큰 목록이 생기면(C) 함께 정리한다.
- **로그인을 동시에 두 번 시작하면**(탭 두 개 등) 나중 것이 state 쿠키를 덮어써 앞의 시도는 `authorization_request_not_found`로 실패한다(로컬 확인 때 관찰). 다시 누르면 되므로 그대로 둔다.
- **전체 합계 제한(`oauth_all`)으로 로그인 시작이 막힐 수 있음**: 고정 키라 한 곳에서 시작 요청을 몰아 보내면 정상 사용자의 로그인 시작도 429가 된다(콜백은 `/api` 공통 제한만, PR #229 리뷰). Nginx를 여러 대로 늘리거나 다른 진입점(로드 밸런서 등)이 생기면 합계 제한이 인스턴스별로 걸리고 결정 8의 전제(단일 진입점)가 깨지므로, 그때 앱 쪽 state 개수 상한을 함께 재검토한다.
- **시작 단계 Redis 장애 시 오류 JSON**: 성공 처리 오류는 실패 화면으로 보내지만, 시작 단계에서 state 저장이 실패하면 오류 JSON(500)이 그대로 보인다(PR #229 리뷰). 같은 실패 화면으로 보내는 것은 후속으로 둔다.
- **OAuth 보안 체인 중복**: STATELESS · CSRF · 헤더 · 기본 로그인 비활성화 설정이 사용자 체인과 겹친다. 실패 처리(리다이렉트 vs JSON 401)가 달라 체인은 유지하고, 공통 설정을 헬퍼로 묶는 정리는 후속으로 둔다(PR #229 리뷰).
- **프록시 헤더 신뢰 범위**: `server.tomcat.remoteip.internal-proxies`를 Docker 기본 대역(172.16/12)과 루프백으로 명시했다. 같은 Compose 망의 다른 컨테이너도 이 범위라 `X-Forwarded-*`를 보낼 수 있지만, 영향은 그 컨테이너 자신의 요청(IP · Host 판단)에 한정된다. Nginx 앞에 로드 밸런서를 두거나 외부에서 백엔드로 들어오는 경로가 생기면 Nginx IP 고정 + 그 IP만 신뢰로 좁힌다(PR #229 리뷰).
- **회원 탈퇴**: `anonymous_user.member_id` FK에 `ON DELETE` 동작을 두지 않았다. 탈퇴 기능을 만들 때 익명 기록을 끊을지(SET NULL) 함께 정한다.
