# BE-116 의사결정 기록

> 근거: BE-108(대본 적재 · 검수, `docs/decisions/BE-108.md`) · BE-109(API 18 공개 서빙, `docs/decisions/BE-109.md`) · FE-118 · FE-119(사건 목록 정렬 · 포스트잇 · 도장)

## 문제 / 배경

- 프론트는 "체험 가능 / 준비 중"을 프론트에 든 로컬 대본(`scriptFor`)으로 판정한다. 서버 대본으로 넘어가면 판정 기준이 서버가 된다.
- API 18(`GET /cases/{caseId}/script`)은 대본이 없으면 `SCRIPT_NOT_FOUND`(404)로만 알려 준다. 사건 목록(S-02)이 체험 가능한 사건을 알려면 사건마다 API 18을 불러야 해서 요청이 N번 든다.
- 목록은 API 1 한 번으로 알아야 하는 값이 있다: 머리기사 · 추천 정렬(체험 가능한 사건이 먼저), 남불 포스트잇의 "지금 체험할 수 있는 기사는 N건", S-20의 "준비 중" 도장.

## 검토한 대안

### 1. 준비 여부를 어떻게 알릴까
- A. 프론트가 사건마다 API 18을 호출: 서버 변경은 없지만 사건 수만큼 요청이 든다. 404를 정상 분기로 쓰게 되고, 사건이 늘면 목록이 느려진다.
- B. 별도 API(`GET /cases/script-ready` 등)로 ID 목록: 요청이 2번이고, 사건 카드와 값이 따로 놀아 정렬 · 포스트잇에서 매번 합쳐야 한다.
- C(선택). **API 1 · API 16 응답에 `scriptReady`(boolean)를 더한다.** 한 번 요청으로 카드와 같이 오고, 필드 추가만이라 기존 클라이언트와 호환된다.

### 2. 필드 모양
- A. `scriptStatus`(`NONE` · `PENDING` · `APPROVED` · `REJECTED`): 더 많이 알려 주지만, 검수 상태는 공개 API에 노출할 이유가 없다(BE-109가 검수용 값을 뺀 것과 같은 원칙). 화면이 쓰는 건 "체험 가능한가" 둘뿐이다.
- B(선택). **`scriptReady`(boolean).** 이름은 "대본이 있다"가 아니라 "체험할 준비가 됐다"를 뜻하게 `Ready`로 했다. 비공개 · 검수 중 · 반려 · 대본 없음은 모두 `false`다.

### 3. 목록에서 값을 구하는 방법
- A. 사건마다 `findByLegalCaseId`: 사건 수만큼 쿼리(N+1).
- B(선택). **승인된 대본의 사건 ID 집합을 한 번 조회**(`CaseScriptRepository.findApprovedCaseIds`)해 메모리에서 대조한다. 목록이 이미 공개 사건을 한 번에 읽고 `participantCount` · `myStatus`도 같은 방식으로 한 번에 모으는 구조와 맞다.
- 상세(API 16)는 사건 하나라 `findByLegalCaseId(...).filter(CaseScript::isPublic)`를 그대로 쓴다 — API 18이 쓰는 코드와 같다.

## 선택한 방법과 이유

- **`scriptReady` = 사건이 `PUBLISHED`이고 대본 `reviewStatus`가 `APPROVED`.** API 18이 200을 주는 조건과 같다. 목록 · 상세는 이미 `PUBLISHED`만 보이므로 대본 조건만 더하면 된다.
- **같은 기준이 두 곳(JPQL · `CaseScript.isPublic()`)에 있다.** 목록 쿼리는 `reviewStatus = APPROVED`를 직접 쓰고, 상세 · API 18은 `isPublic()`을 쓴다. 한쪽만 고치면 어긋나므로 레포지토리 메서드 주석에 짝을 적었고, `CaseListApiTest` · `CaseDetailApiTest`가 승인 · 검수 대기 · 반려 · 없음 네 경우를 만들어 `scriptReady`와 API 18의 응답(200 / 404)이 같은지 함께 본다.
- 사용자와 무관한 값이라 `myStatus`와 달리 캐시 규칙에 영향을 주지 않는다.

## 고려한 제약 사항

- 사건 하나에 대본 한 건(`findByLegalCaseId`가 `Optional`)이라는 BE-108 구조를 전제로 한다. 사건당 여러 대본이 생기면 "승인된 것이 하나라도 있는가"로 바꿔야 한다(집합 조회는 그대로 맞고, 상세만 손봄).
- 프론트 소비(정렬 · 포스트잇 · 도장)는 이 이슈 범위 밖이다(FE-33 · FE-119 후속).

## 추후 재검토가 필요하면

- 사건이 수백 건을 넘어 목록 페이징 · 검색이 들어오면(별도 후속 이슈) 집합 조회를 페이지 단위 `IN` 조회로 바꾼다.
- 대사를 직접 수정(A-13-13)하면 검수 상태가 대기로 돌아가 `scriptReady`가 `true → false`가 되고 API 18도 404가 된다. 이미 체험 중인 사용자의 증거조사 화면이 어떻게 보일지는 FE-125에서 함께 확인한다.
- 서버는 `scriptReady`로 체험 시작(API 2)을 막지 않는다(화면 정책). 서버에서도 막아야 하면 별도 이슈로 다룬다.
- `findApprovedCaseIds()`는 비공개 사건의 승인된 대본 ID도 읽는다(결과에는 영향 없음). 사건이 많아지면 공개 사건 ID로 범위를 줄인다.
