# FE-61 의사결정 기록

## 문제 / 배경
- 화면 대부분이 갖춰진 뒤 용어를 훑어보니 같은 대상을 여러 이름으로 부르고 있었다. (사건 개요 · 사전 판단 · 첫인상 / 사건 정보 확인 · 재판 · 사건 기록 / 성향검사 · 성향 테스트 / 독자 엽서 · 독자 의견 엽서 · 리뷰하기 / 내 데이터베이스 · 만난 모습 등)
- `user-flow.md` · `information-architecture.md`는 8막을 기준으로 쓰여 있었지만 실제 코드의 막 칩은 6막(FE-48)이라 문서와 화면이 어긋나 있었다.

## 검토한 대안
- 형량 용어(법정형 · 선고할 수 있는 범위 · 권고 범위)
  - 대안 A: 하나로 합쳐 짧게 부른다. 단순하지만 법적으로 다른 개념이 섞여 오해를 만든다.
  - 대안 B: 합치지 않고 처음 나오는 곳에 한 줄 풀이를 붙인다.
- 1막 엽서와 8막(6막 칩 기준) 엽서
  - 대안 A: 둘 다 "독자 엽서"로 둔다. 하나는 첫인상 입력, 하나는 체험 뒤 리뷰라 같은 이름이면 헷갈린다.
  - 대안 B: 이름을 가른다.
- 문서의 용어(사전 판단 등)
  - 대안 A: 문서와 API 용어까지 화면 용어로 전부 바꾼다.
  - 대안 B: 문서 · API · 데이터 용어는 두고, 화면 문구만 바꾸고 둘의 대응표를 문서에 남긴다.

## 선택한 방법과 이유
- 형량 용어는 **합치지 않고 풀이를 추가**했다. 법적 의미가 달라서다.
- 엽서는 **1막 = 첫인상 엽서, 6막 = 독자 엽서(버튼 `엽서 쓰기`)** 로 갈랐다.
- 화면 표기는 막 칩 이름을 기준으로 맞췄다. (첫인상 · 재판 · 내 판결 · AI 판결 · 실제 판결 · 세 판결 비교)
- 문서는 **대안 B**. `PRE_JUDGED`, API 4 · 5 등 서버 · 데이터 이름이 사전 판단에 묶여 있어 바꾸면 영향 범위가 크다. 대신 `user-flow.md` 3-3-1과 `information-architecture.md` 12장에 화면 표기 ↔ 문서 표기 대응표를 두었다.
- `체험`은 서비스 전체에서 쓰이는 핵심 단어라 그대로 유지했다.

## 고려한 제약 사항
- 서버 진행 상태 · 주소 · 대본의 막 번호(1 ~ 8)는 건드리지 않았다. (주소 · 막 번호 정리는 BE-82)
- 신문 지면 안의 장식 문구(`오늘의 사건 N건` 등)는 신문 느낌을 살리려고 남겼다. 메뉴 · 버튼 이름만 맞췄다.

## 추후 재검토가 필요하면
- BE-82에서 주소 · 막 번호를 정리하면 문서의 `S-05`, 대본의 막 번호 설명을 다시 맞춘다.
- `체험` 대신 `판결해 보기` 같은 더 구체적인 말을 쓸지는 사용자 반응을 본 뒤 다시 정한다.
