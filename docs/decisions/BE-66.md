# BE-66 의사결정 기록

> 확장 단계(WBS 7.2.1) · PR #110, #122 · 담당 백승호

## 문제 / 배경
- Actuator · Micrometer로 체험 시작 · 판결 확정 · AI 호출 성공률 같은 커스텀 비즈니스 메트릭을 노출해야 했다.
- Actuator 엔드포인트를 외부에 노출하지 않으면서, Prometheus(BE-70)가 스크레이프할 수 있어야 했다.

## 검토한 대안
- **Actuator 포트 분리 여부**: 애플리케이션 포트(8080)에 `/actuator`를 그대로 열지, 관리 전용 포트로 분리할지 검토했다 (#106 리뷰에서 먼저 합의).
- **메트릭 태그에 사건 ID·체험 ID를 포함할지**: 태그로 넣으면 Grafana에서 사건별로 바로 필터링할 수 있지만, 고유값이라 시계열이 무한히 늘어나는 카디널리티 문제가 있었다.
- **판결 확정 메트릭을 언제 집계할지**: 서비스 메서드 호출 시점에 바로 셀지, 트랜잭션이 실제로 커밋된 뒤에 셀지 검토했다 (#110 리뷰).

## 선택한 방법과 이유
- `management.server.port`로 Actuator를 애플리케이션 포트와 분리하고 `health`·`prometheus`만 노출했다. 모니터링 전용 접근을 애플리케이션 트래픽과 완전히 분리해, Nginx가 8081을 외부로 열지 않기만 하면 안전하기 때문이다.
- 사건 ID·체험 ID 등 고카디널리티 값은 메트릭 태그로 쓰지 않았다. 이후 BE-71(로그 traceId)에서도 같은 이유로 traceId를 Loki 라벨에 쓰지 않는 동일한 원칙을 적용했다.
- 판결 확정 메트릭은 `afterCommit`에서만 집계하도록 바꿨다 (#110 리뷰). 집계를 서비스 호출 시점에 하면 트랜잭션이 롤백돼도 메트릭은 이미 올라간 상태가 되어 실제 저장된 판결 수와 어긋난다.

## 고려한 제약 사항
- 임베딩 재시도 대기(`sleeper.sleep`) 중 인터럽트로 발생하는 `EmbeddingException`이 성공·실패 어디에도 집계되지 않는 경로가 있었다 (#122에서 발견). 기존 재시도 로직(지수 백오프·Retry-After)은 그대로 두고, 이 엣지 케이스만 보강해 성공률 분모에서 누락되지 않게 했다.
- 인터럽트 상태 플래그는 삼키지 않고 호출자에게 그대로 전달해야 했다(스레드 인터럽트 처리 관례).
