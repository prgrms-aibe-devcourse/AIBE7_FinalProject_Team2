# COMMON-40 의사결정 기록

## 문제 / 배경

2026-10-16 자동화 파이프라인 구성 계획 회의에서 AI 호출 한도를 줄이기 위해, 오프라인 AI 판결 파이프라인 ④ generate 단계를 "여러 모델 × 다회차 생성" 방식에서 **검증된 모델 하나로 고정**하기로 했다. 고정 근거는 직접 테스트로 확인하기로 했다(담당 C 백승호, `docs/wbs.md` v1.27).

선행 작업으로 Groq · NVIDIA NIM 공급자를 추가(BE-84)하고 `.env` 파일로 API 키를 관리할 수 있게(BE-86) 한 뒤, `compare.py`에 여러 사건을 모델별로 합산하는 집계 기능(BE-85)을 추가해 이 테스트를 준비했다.

## 검토한 대안

### 1. 테스트에 쓸 사건을 어떻게 구할 것인가

- **대안 A — 법제처(국가법령정보센터) Open API로 실제 판례를 찾아 쓴다.** 살인·사기·상해 각 유형으로 하급심 판례를 넓게 검색해(최대 60건) "최종 확정·단일 범행·자백·양형기준 명시" 조건으로 걸러봤으나, 조건을 전부 만족하는 사건을 찾지 못했다. 항소심까지 간 사건은 대부분 유죄를 다투기 때문에 항소한 것이라 "자백 사건"이 거의 없었고, 단순 상해·사기는 법원이 판결문에 "양형기준에 따른 권고형의 범위" 같은 정형화된 문구를 아예 안 쓰는 경우가 많았다(살인 1건은 조건을 만족하는 판례를 찾았다 — 아래 "찾은 성과").
- **대안 B — LBox Open 데이터셋에서 사건을 가져온다.** LBox는 CC BY-NC(-ND) 라이선스로 **상업적 이용 자체가 금지**돼 있어(`docs/rag-precedent-sources.md`), "어떤 모델을 상용 서비스에 쓸지 고르는 테스트"에 쓰는 것도 상업적 이용에 해당할 수 있다고 판단해 제외했다(RAG 판례 저장소에서도 같은 이유로 전부 삭제한 전례가 있다, BE-54).
- **대안 C(선택) — 완전히 지어낸 가상 사건을 만들어 쓴다.** `examples/case_input.json`(기존 가상 살인 사건)과 같은 방식으로, COMMON-40 테스트 전용 가상 사건을 2건(살인·상해) 새로 작성했다.

### 2. 가상 사건을 무료 등급 API로 보내도 되는가

- 무료 등급(Free tier) API는 약관상 제출된 입력을 "제품 개선(학습)에 쓰고, 사람이 검토할 수 있다"고 되어 있어, **실제 서비스에 쓸 사건**을 무료 등급으로 보내면 그 내용이 나중에 모델 학습에 섞여 들어가 "AI가 사건·형량을 미리 알지 못해야 한다"(REQ-102)는 전제가 깨질 위험이 있다.
- 대안 C로 만든 사건은 **완전히 지어낸 내용이고 실제 서비스에도 넣지 않을 것**이므로, 이 오염 문제 자체가 발생하지 않는다. 그래서 테스트는 안전하게 무료 등급으로 진행했다.

### 3. 비교 기준을 무엇으로 할 것인가

- **대안 A — 모델 자신의 회차 간 표준편차 · IQR만 본다.** 같은 모델이 매번 비슷한 형량을 내는지는 보여주지만, "다른 모델들과 비교했을 때 유별나게 가볍거나 무거운 판단을 하는가"는 보여주지 못한다.
- **대안 B(선택) — "교차 모델 중앙값"(여러 모델의 중앙값들 중 중앙값)과의 거리를 함께 본다.** 한 모델만 너무 가볍거나 무겁게 판단하면(이상치) 그 모델은 다수 모델의 판단과 동떨어진 것이므로 거른다. 토큰 사용량 · 검증 통과율 · 판단 요소 일관성(`factorConsistency`) · 전체 합의도(`consensusAgreement`)를 함께 본다(BE-85로 추가한 징역 표준편차 · IQR · 사건 간 집계 기능을 그대로 썼다).

## 선택한 방법과 이유

### 1. 가상 사건 2건으로 테스트 (대안 C)

- `tools/ai-judgment/cases/common40-murder-test.json`(층간소음 갈등 끝에 이웃을 살해한 사건, 기존 예시와 다른 시나리오로 다양성 확보), `tools/ai-judgment/cases/common40-injury-test.json`(주점 시비 끝에 상해를 입힌 사건)을 새로 작성했다. 둘 다 단일 혐의·자백·양형기준 명시 조건을 깨끗하게 만족하도록 설계했다(법제처 검색에서 못 찾은 조건을 가상 사건으로는 그대로 구현할 수 있다). 두 파일 모두 `cases/`(git 제외)에 두고, 저장소에는 올리지 않는다.
- `build_prompt.py`로 실제 프롬프트 생성까지 검증했다(사건 입력 형식 오류 없음).

### 2. 후보 모델 16개 × 2사건 × 4회차로 테스트 (대안 B)

`free_models.json`에 있던 무료 등급 모델 26개 중, 사전 확인에서 이미 죽은 것으로 드러난 10개를 빼고 16개로 테스트했다.

- **Gemini 2.5-pro · 2.5-flash · 2.5-flash-lite**: 공급자가 "신규 사용자에게 더 이상 제공 안 함"(404)으로 이미 내린 모델. `free_models.json` 목록이 오래돼 있었다(별도 정리 필요, 아래 "추후 재검토").
- **Groq llama-3.3-70b-versatile · llama-3.1-8b-instant · minimaxai/minimax-m2.7 · meta-models/muse-spark-open**: Groq의 실제 `/v1/models` 목록에 없는(404) 모델. 마찬가지로 `free_models.json`이 오래돼 있었다.
- **NIM nemotron-nano-3-30b-a3b · moonshotai/kimi-k2.6 · mistralai/mistral-large-2-instruct**: NIM 호출이 "Function ... Not found for account"(404)로 거절됨. 계정에서 해당 모델에 대한 접근이 없거나 공급자가 내린 것으로 보인다.

**테스트 중 발견한 버그 (BE-84 후속)**: Groq 호출이 전부 403 Forbidden으로 막혀 처음엔 API 키 문제로 의심했으나, 원인은 **Cloudflare가 `urllib` 기본 User-Agent(`Python-urllib/3.x`)를 자동화 봇으로 차단**하는 것이었다(응답 본문이 `error code: 1010`, Groq가 아니라 Cloudflare의 차단 코드). `llm.py`의 `_request_json`에 `User-Agent` 헤더를 추가해 해결했다(기존 테스트 393개 전부 통과 확인). 코드 변경이라 BE-84에 귀속되는 수정으로 보고 별도 PR(#185, `fix/BE-84-groq-user-agent`)로 먼저 머지했다.

### 3. 최종 선정: `gemini:gemini-3.7-flash`

16개 중 호출 실패율이 높은 모델(`nim:z-ai/glm-5.3` 8/8 실패, `nim:deepseek-ai/deepseek-v4.1-flash` 8/8 실패, `nim:google/gemma-4-31b-it` 7/8 실패, `nim:nvidia/nemotron-3.5-lightning-30b-a3b` 3/8 실패)과 검증 실패가 섞인 모델(`groq:qwen/qwen3.8-27b` 2/8 검증 실패)을 먼저 제외했다. 남은 모델 중 아래를 종합했다.

| 모델 | 살인 중앙값(교차모델 중앙값 156개월과 비교) | 상해 중앙값(교차모델 중앙값 5.5개월과 비교) | 평균 출력 토큰 | 판단 요소 일관성·합의도 | 형벌 종류 선택 |
| --- | --- | --- | --- | --- | --- |
| **gemini:gemini-3.7-flash** | **156 (정확히 일치)** | 6 (근접) | 469 | **1.0 / 1.0 (완벽, 양쪽 사건 모두)** | 매번 징역 (흔들림 없음) |
| gemini:gemini-3.8-flash | 156 (정확히 일치) | 6 (근접) | 462 | 1.0 / 1.0 | 매번 징역, 다만 경고 평균 0.5건(상해) |
| gemini:gemini-3.5-flash-lite | 144 (12개월 낮음) | 6 (근접) | **398 (가장 적음)** | 0.925 ~ 1.0 | **상해에서 벌금·징역이 절반씩 갈림 (불일치)** |
| gemini:gemini-3.1-flash-lite | 156 (정확히 일치) | 산출 안 됨(전부 벌금 선택) | 448 | 1.0 / 0.8 ~ 1.0 | 상해에서 벌금 위주, 일부 파싱 실패 |
| groq:openai/gpt-oss-120b | 156 (정확히 일치) | 4 (1.5개월 차이) | 1269 | 0.95 / 0.85 (살인), 0.875 / 0.875 (상해) | 매번 징역, 경고 평균 1.9건 |

- `gemini:gemini-3.7-flash`가 **두 사건 모두 교차 모델 중앙값에 가장 가깝고**(살인은 정확히 일치), **판단 요소 일관성 · 전체 합의도가 두 사건 모두 완벽(1.0)** 하며, **형벌 종류(징역/벌금) 선택이 한 번도 흔들리지 않았다.**
- `gemini-3.5-flash-lite`는 토큰을 가장 적게 쓰지만, 상해 사건에서 벌금과 징역을 절반씩 선택하는 **진짜 불일치**가 있었다(단순히 형량 폭이 아니라 형벌 종류 자체가 흔들림). "일관적인 결과"라는 기준에서 이 흔들림이 토큰 절약보다 더 중요하다고 판단했다.
- `gemini-3.8-flash`는 `3.7-flash`와 거의 동률이지만, 상해 사건에서 평균 0.5건의 검증 경고가 있어(`3.7-flash`는 0건) 근소하게 밀렸다.
- 응답 속도(약 40 ~ 65초)는 Gemini 3.x 계열 중 가장 느린 편이지만, **이 파이프라인은 오프라인 배치 작업**(`pipeline.py`가 판결문 → 생성 → 선택 → 적재를 사람 대기 없이 이어서 실행)이라 실시간 응답 속도는 모델 선정 기준에서 제외했다.

## 테스트 방법 요약 (재현용)

```bash
# tools/ai-judgment/.env에 GEMINI_API_KEY · GROQ_API_KEY · NVIDIA_API_KEY 설정 후
python3 generate.py run cases/common40-murder-test.json --model <모델1> --model <모델2> ... --runs 4 --delay 2
python3 generate.py run cases/common40-injury-test.json --model <모델1> --model <모델2> ... --runs 4 --delay 2
python3 compare.py out/runs/common40-murder-test out/runs/common40-injury-test --out out/runs/common40-aggregate.md
```

테스트 사건 파일(`cases/common40-*.json`)과 결과 폴더(`out/runs/`)는 git에 올리지 않는다(둘 다 `.gitignore` 대상). 재현하려면 이 문서의 사건 설계(위 "1. 가상 사건 2건으로 테스트")를 참고해 다시 만든다.

## 고려한 제약 사항

- **실제 판례를 못 구해 가상 사건으로 대체했다.** 가상 사건은 작성자가 의도한 대로 "조건이 깨끗한" 사건이라, 실제 판결문의 복잡함(여러 쟁점이 얽힌 사실관계, 애매한 자백 여부 등)을 반영하지 못한다. 모델이 정돈된 입력에서는 잘하다가 실제 입력에서 흔들릴 가능성은 이번 테스트로 배제되지 않는다.
- **회차 수가 적다(4회).** 더 많은 회차로 돌리면 지금 안 보인 불안정성이 드러날 수 있다.
- **사건 2개뿐이다.** 살인·상해 각 1건씩이라 죄명 안에서의 다양성(가벼운 사건 ↔ 무거운 사건)은 보지 못했다. 사기 유형은 테스트하지 못했다(법제처에서 조건에 맞는 사기 사건을 아예 못 찾았고, 가상 사건도 이번에는 만들지 않았다).
- **`free_models.json` 목록이 오래돼 있었다.** 이번 테스트로 Gemini 2.5 계열 3개 · Groq 모델 4개가 이미 내려갔다는 것을 확인했지만, 이 파일 자체를 고치는 것은 이번 이슈 범위 밖이다(목록 갱신은 `list_models.py`로 사람이 확인하고 고치는 절차, BE-84 결정).

## 추후 재검토가 필요하면

- **아직 실제 설정에는 반영하지 않았다.** `pipeline.py`의 `stages.generate.models`는 사건별 설정 파일에 적는 값이라, 기존에 이미 만들어 둔 설정 파일들을 전부 고칠지, 새로 만드는 사건부터만 적용할지는 팀이 정해야 한다(현재는 새 사건부터 적용하는 쪽으로 `docs/ai-judgment-pipeline.md`에 적어 뒀다).
- **사기 유형 테스트가 빠져 있다.** 사기 가상 사건을 만들어 같은 방식으로 추가 검증하는 것을 권장한다.
- **③ 사전 학습 점검 대상 모델, ⑤ select의 다수결 전제(모델이 하나면 "여러 모델 합의"라는 지금 로직의 전제가 깨진다), 무료 등급 대체 체인(BE-45) 유지 여부**는 이 이슈에서 다루지 않았다. 모델을 하나로 고정하는 작업을 실제로 적용할 때 함께 정해야 한다.
- `free_models.json`의 Gemini 2.5 계열(3개) · Groq 죽은 모델(4개) · NIM 접근 불가 모델(3개)은 `list_models.py`로 다시 확인해 정리하는 후속 작업이 필요하다.
