# FE-63 의사결정 기록

## 문제 / 배경
- 사건 이미지는 대표 1장 + 기사 지면 작은 사진 2장(`extraPhotos`) + 증거조사 사진 2장(`evidencePhotos`)이 섞여 있었고, 사건 1 대본은 사진 3장이 어긋나게 쓰였다(`sub`만 겹침).
- 사진이 없거나 로딩에 실패할 때의 처리가 자리마다 달랐다. 대표 사진만 공용 컷으로 대체했고, 기사 지면 작은 사진은 깨진 이미지가 보일 수 있었다.
- 백엔드 BE-78 · BE-91이 사건별 이미지 매칭 정책을 정하는 중이라, 프론트 방향을 먼저 맞출 필요가 있었다.

## 검토한 대안
- 대안 A: 필드를 그대로 두고 대본에서 같은 사진을 두 곳에 적는다. 구조 변경은 없지만, 발단 · 결론 사진이 두 필드에 중복되어 서버 연동 때 어긋나기 쉽다.
- 대안 B: 필드 이름을 `origin` · `conclusion`으로 바꿔 새 구조로 옮긴다. 이름은 명확하지만 서버 계약이 정해지기 전에 바꾸면 FE-64에서 다시 바뀔 수 있다.
- 대안 C(선택): 필드는 그대로 두고, 사진 자리(발단 · 결론)에 같은 사진을 쓰도록 대본만 정리한다. 대체 컷 로직은 화면 한 곳(`useCommonPhotoOnError`)에 모은다.

## 선택한 방법과 이유
- 사진 3장을 대표 · 발단 · 결론으로 부르고, 증거조사 변호인 측 = 발단, 검사 측 = 결론으로 한다. 기사 지면 작은 사진 2장과 같은 그림을 공유한다.
- 사건 1은 기존 `sub`를 발단(`case-1-origin.webp`), `detail`을 결론(`case-1-conclusion.webp`)으로 이름을 바꿔 쓴다. 대표사진 `case-1-reenact.webp`는 백엔드 시드(BE-78)가 참조하므로 이름을 그대로 둔다(새 이미지는 파일만 교체하면 된다).
- 로딩 실패나 누락 시 공용 컷으로 바꾸고, 공용 컷도 실패하면 사진을 뺀다. 자리마다 seed를 달리해 한 화면에 같은 컷이 겹치지 않게 했다.
- 이유: API 계약이 정해지기 전이라 필드 이름은 건드리지 않는 것이 FE-64의 재작업을 줄인다.

## 고려한 제약 사항
- 서버 연동(API 계약, `paperFromCase`)은 FE-64에서 다룬다.
- 공용 컷 3장뿐이라 서로 다른 자리의 대체 컷이 겹칠 수 있다. 분류와 추가 생성은 FE-65에서 다룬다.

## 리뷰 반영 (YOLO-NIM)
- `extraPhotos`가 없는 사건은 처음에 작은 사진 자리를 그리지 않았으나, 지면 구성이 사건마다 달라지는 것보다 같은 모양을 유지하는 편이 낫다고 보아 발단 · 결론 공용 컷으로 채운다. (`extraPhotosOf`)
- 공용 컷에 발단용 · 결론용을 둔다(`commonStagePhotos`). 전용 이미지가 나오기 전까지는 임시로 `common-2` · `common-3`을 가리키며, 이미지가 오면 경로만 바꾼다.
- 사건 목록 · 메인 화면 사진에도 로딩 실패 fallback(`useCommonPhotoOnError`)을 적용했다.

## 추후 재검토가 필요하면
- 서버가 발단 · 결론 사진을 내려 주기 시작하면 필드 이름을 `origin` · `conclusion`으로 바꿀지 FE-64에서 다시 정한다.
