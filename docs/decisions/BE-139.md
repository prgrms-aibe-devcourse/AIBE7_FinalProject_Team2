# BE-139 의사결정 기록

> 근거: BE-113(아이디 회원, 닉네임 형식) · BE-115(커뮤니티 글쓴이 이름 `방청객 {회원 ID}`) · FE-114(닉네임 형식 화면 규칙). 계약은 API 명세 M-7(v0.69), 인덱스는 ERD 3장 member(v1.49 · V39)

## 문제 / 배경
- 닉네임은 아이디 회원가입 때만 저장되고 수정 API가 없었다. 카카오 회원은 닉네임이 NULL이라 커뮤니티에 `방청객 {회원 ID}`로 보인다(BE-115).
- BE-113은 닉네임 중복을 허용했다("표시 이름"이라). 커뮤니티가 생기면서 닉네임이 글 · 댓글 · 랭킹에서 사람을 구분하는 이름이 되어 중복을 막기로 했다.

## 검토한 대안
- 중복: A 허용(기존) / B 대소문자 구분 없이 금지(선택) / C 대소문자는 구분해 금지
- 기존 중복 데이터: A 마이그레이션이 비운다(선택) / B 유니크 인덱스를 만들지 않고 서비스에서만 검사 / C 겹치는 닉네임에 숫자를 붙인다
- 변경 횟수 제한: 있음 / 없음(선택, 사용자 결정) — 필요하면 후속

## 선택한 방법과 이유
- **대소문자 구분 없이 금지**(B): 아이디(`naero`와 `Naero`는 같다)와 같은 규칙이고, `Judge`와 `judge`를 서로 다른 사람으로 흉내 내는 것을 막는다. DB 유니크 인덱스 `uq_member_nickname ON member (lower(nickname)) WHERE nickname IS NOT NULL` — 서비스 검사만 두면 동시 요청 두 개가 둘 다 통과한다. 닉네임이 없는(NULL) 카카오 회원은 겹쳐도 된다.
- **서비스 검사 + 유니크 위반 변환**: 먼저 `existsByNicknameIgnoreCase…`로 거절하고(비싼 비밀번호 해시 전에 끝낸다), 동시 요청은 유니크 위반(SQLSTATE 23505)을 `DUPLICATE_NICKNAME`으로 바꾼다. 가입은 회원 행의 다른 유니크(공급자 + 새 UUID)가 겹칠 수 없어 저장 시 유니크 위반은 닉네임뿐이다.
- **내 닉네임의 대소문자 변경은 허용**: 중복 검사에서 나를 뺀다(`…AndIdNot`).
- **형식은 한 곳**(`Nickname.validate`): 가입(BE-113)과 수정이 같은 규칙을 쓴다. 공백이 없는 형식이라 자동 이름 `방청객 {회원 ID}`(공백 포함)와 겹칠 수 없다 — 테스트로 고정했다.
- **기존 중복은 마이그레이션이 비운다**: 겹치는 닉네임은 먼저 가입한 회원(작은 id)만 남기고 나머지는 NULL로 만든 뒤 인덱스를 만든다. 아이디 회원가입(BE-113)이 10/27에 들어가 데이터가 적고, 닉네임은 표시용이라 비워도 로그인에 영향이 없으며, 비운 회원은 이 API로 다시 정하면 된다(그 전까지 커뮤니티에는 자동 이름). 숫자를 붙이는 방식은 12자 제한에 걸린다.
- **엔드포인트**: `PUT /api/v1/members/me/nickname`. 경로를 `members/me/**`로 열어 두어 이후 내 회원 정보 API가 같은 로그인 규칙(`authenticated()`)을 받게 했다. 로그인 쿠키가 아니라 Bearer 토큰으로 인증하므로 가입 · 로그인과 달리 Origin 검증이 필요 없다.

- **내 회원 정보 API**(M-8, `GET /api/v1/members/me`)를 같은 이슈에서 함께 만들었다(FE-137 연동 요청): 화면이 카카오 회원에게 "카카오 회원"이라고 쓰던 표시 이름을 서버 값(`displayName` = 닉네임 또는 `방청객 {회원 ID}`)으로 맞추고, 내 정보 수정의 계정 관리(로그인 방식 · 아이디 · 가입일 · 최근 로그인)를 서버 값으로 채우기 위해서다. 자동 이름 규칙은 `Nickname.displayName`으로 모아 커뮤니티와 같은 값을 쓴다. 개인정보는 저장하지 않아(BE-62) 닉네임 · 로그인 방식 · 아이디 · 시각만 준다.

## 고려한 제약 사항
- 가입 응답에 새 에러 `DUPLICATE_NICKNAME`(409)이 생겨 화면(FE-117 가입 폼)이 처리해야 한다 — 가입 화면 연동은 FE 작업이다.
- 운영 DB(RDS 이전 뒤)에 마이그레이션이 적용될 때 겹치는 닉네임이 비워질 수 있다. 배포 전 `SELECT lower(nickname), count(*) FROM member GROUP BY 1 HAVING count(*) > 1`로 건수를 확인할 수 있다.
- 다른 브랜치가 같은 번호를 먼저 쓰면 다시 매긴다(Flyway는 순서가 어긋난 번호를 받지 않는다). 이 브랜치는 BE-115(V38 커뮤니티) 뒤에 병합되는 것을 전제로 V39를 썼다.

## 추후 재검토가 필요하면
- 금칙어 검사(금칙어 기능 A-39 ~ A-41), 변경 횟수 · 간격 제한(닉네임을 자주 바꿔 사람을 헷갈리게 하는 경우), 탈퇴한 회원의 닉네임 회수(탈퇴 기능이 생길 때).
- 닉네임을 바꾸면 과거 글 · 댓글의 이름도 바뀐다(글에 이름을 복사해 두지 않고 회원에서 읽는다, BE-115). 의도한 동작이다.
