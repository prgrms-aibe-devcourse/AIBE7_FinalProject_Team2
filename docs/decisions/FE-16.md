# FE-16 의사결정 기록

> 소급 작성(COMMON-39). 근거: PR #117 본문.

## 문제 / 배경
- 관리자 검수 화면(S-19)을 만들면서 사용자 화면과 어디까지 코드를 나눌지, 세션 · CSRF를 어떻게 다룰지 정해야 했다.

## 선택한 방법과 이유
- 관리자 API 클라이언트(`adminClient.js`)를 공용 `client.js`와 **분리**했다(BE-67 합의). 관리자 에러가 사용자 화면의 에러 이동(`errorRedirect`)을 타면 사용자 화면이 열리는 문제를 피하기 위해서다.
- 요청마다 쿠키 `XSRF-TOKEN`을 읽어 `X-XSRF-TOKEN` 헤더에 담고 값을 변수에 저장하지 않는다. 상태를 바꾸는 요청이 403이면 A-1을 다시 불러 한 번만 재시도한다.
- 로그인 실패(`INVALID_CREDENTIALS`)를 뺀 **모든 401은 "로그아웃됨"**으로 통일해 로그인 폼으로 보낸다.
- 관리자 코드 · CSS는 `/admin`으로 들어올 때만 동적 import로 불러와 별도 청크로 둔다.
- 원문 · 생성 정보는 브라우저 저장소에 넣지 않고(`cache: 'no-store'`, 값은 `textContent`), 목은 로그인 여부만 `sessionStorage`에 둔다.
- 범위는 검수 + 사건 내용 수정이고 **사건 등록은 뺐다**(계약에 등록 API가 없고 등록은 파이프라인 · SQL 경로).
- 공개 전 체크리스트 3개는 화면 장치일 뿐이고 서버 조건은 A-13 `publishReadiness`가 판단한다.

## 고려한 제약 사항
- API는 `api-specification.md` 8장 A-1 ~ A-13 계약만 썼고 백엔드 · 명세는 고치지 않았다. 계약에 없는 필드(`raw_output` 등)는 받지 않는다.
- 실제 백엔드 연동은 BE-41 ~ BE-43 구현 뒤 확인하기로 남겼다.
