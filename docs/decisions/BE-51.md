# BE-51 의사결정 기록

> 소급 작성(COMMON-39). 근거: PR #97 본문, `docs/ai-judgment-pipeline.md` 8-1, ERD 3-4장.

## 문제 / 배경
- AI 판결이 비슷한 판례를 참고하는 RAG 저장소가 필요했다. 단, 판결하려는 사건의 실제 판결이 AI에게 노출되면 안 된다.

## 선택한 방법과 이유
- 적재는 오프라인 Python, 검색어 임베딩 · 검색은 백엔드 Java로 나눴다(관리자 연동 · Java 전환은 BE-56).
- 테이블 `rag_precedent`에는 판결문 원문 · 사건번호 · 법원명을 넣지 않는다. 사건번호는 SHA-256 해시(`text[]`, 병합 사건은 번호마다)로만 둔다.
- 검색 함수는 판결하려는 사건의 해시가 있는 **사건 그룹 전체**(다른 심급 · 사본)를 제외해 실제 판결 노출을 막는다. 사건 그룹당 1건, 사용 보류 판례 제외, 코사인 유사도 + 점수 하한.
- 임베딩은 사실관계 요약**만** 보낸다(양형 이유 · 원문 제외). 요약 유사도 0.95 이상은 같은 사건으로 묶는다(판례 분포로 정함).
- 수백 건 규모라 인덱스 없이 전체 비교한다(수만 건이면 halfvec + HNSW).
- 사용 보류: LBox(라이선스 확인 전), 살인 관련 공소사실 무죄 판례(사실관계가 비슷해 유사도로 걸러지지 않음). 보류 목록은 비공개 저장소에서 읽는다.
- 서비스 쪽 RAG는 `GEMINI_API_KEY`가 없거나 저장소가 비면 꺼지고, 호출하는 쪽은 퓨샷으로 대체한다.

## 고려한 제약 사항
- 운영 DB에 pgvector 확장이 있어야 V11이 통과한다(앱 계정에 권한이 없으면 배포 전에 관리자가 먼저 생성).
- 점수 하한 0.6은 현재 점수 분포(0.7 ~ 0.85)에서 거르는 효과가 없다. 판례가 늘면 다시 정한다.
- R__40은 비공개 저장소에 있어 머지 순서(이 PR → 비공개 PR)를 지켜야 한다.

## 추후 재검토가 필요하면
- 점수 하한 · `top_k`, 판례 수가 늘 때의 인덱스.
