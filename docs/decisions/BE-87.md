# BE-87 의사결정 기록

> 관련: [BE-87](https://aibe7-team2-final.atlassian.net/browse/BE-87), WBS 7.0.3 통합 회귀 테스트.
> 실행·정리 절차와 설정값은 [테스트 환경 안내](../../backend/TESTING.md)를 기준으로 한다.

## 문제 / 배경

- 기존 테스트는 별도 프로필 없이 개발용 PostgreSQL·Redis 기본 접속 설정을 사용할 수 있었다. 테스트에는 데이터 삽입·수정·삭제와 독립 트랜잭션을 사용하는 동시성 검증이 있어, 개발 데이터와 같은 저장소에 연결하면 데이터 손실이나 테스트 간 간섭이 발생할 위험이 있었다.
- 트랜잭션 롤백만으로는 모든 테스트의 영향을 격리할 수 없다. 별도 트랜잭션에서 커밋된 데이터와 Redis 변경은 테스트 메서드의 DB 롤백으로 되돌아가지 않는다.
- 통합 회귀 테스트를 반복 실행하려면 개발·운영 데이터와 분리된 환경뿐 아니라, 잘못된 접속 설정을 테스트 시작 전에 거절하는 장치가 필요했다.

## 검토한 대안

- **개발 PostgreSQL 안에서 테스트 DB만 분리**: 준비는 간단하지만 PostgreSQL 인스턴스와 Redis를 공유하며, 잘못된 주소 설정이나 인스턴스 정리 작업의 영향을 함께 받는다.
- **테스트 프로필과 환경변수만 분리**: 설정 파일은 줄어들지만 `SPRING_DATASOURCE_URL`·`SPRING_APPLICATION_JSON` 등 우선순위가 높은 외부 설정이 접속 대상을 바꿀 수 있다. 프로필만으로는 오접속을 막기 어렵다.
- **Testcontainers로 테스트마다 서비스 생성**: 수명주기를 테스트와 묶을 수 있지만 새로운 의존성과 기존 테스트 실행 구조 변경이 필요하다.
- **전용 Compose + 테스트 프로필 + Gradle 접속 검증 (선택)**: 기존 테스트와 CI 서비스 컨테이너 구조를 유지하면서 로컬 서비스·데이터 저장소를 분리하고 접속 대상을 제한할 수 있다.

## 선택한 방법과 이유

### 1. PostgreSQL·Redis를 별도 컨테이너로 분리

- 독립된 Compose 파일과 프로젝트 `lawnambul-test`를 사용한다. 개발용 Compose와 합치지 않고 별도의 포트·볼륨·네트워크를 사용해 데이터와 정리 범위를 분리한다.
- PostgreSQL은 기존 마이그레이션의 `vector` 확장을 지원하는 PostgreSQL 17 + pgvector 이미지를, Redis는 기존과 같은 7.4 이미지를 사용한다. H2로 대체하지 않아 PostgreSQL 전용 제약·JSONB·벡터 기능을 실제 DB에서 검증한다.
- 로컬 호스트 포트는 PostgreSQL 55432, Redis 56379이며 localhost에만 바인딩한다. healthcheck로 서비스 준비 상태를 확인한다.
- Redis 논리 DB 번호는 기존 캐시 0·토큰 1을 유지한다. 번호를 바꾸는 대신 서버 자체를 분리해 기존 테스트의 전제를 유지한다.

### 2. Spring 설정과 Gradle 실행 경계를 함께 분리

- 테스트 리소스에 `application-test.yml`을 두고 Gradle의 모든 `Test` 작업에서 `test` 프로필을 자동 활성화한다. 테스트마다 프로필 어노테이션을 추가하는 방식은 누락 가능성이 있어 사용하지 않았다.
- 기존 Flyway 마이그레이션과 공개 가상 사건 시드만 사용하고 비공개 시드는 제외한다. Hibernate `validate`와 Flyway `clean-disabled`를 유지하며 관리자 자동 부트스트랩은 빈 이메일·비밀번호로 비활성화한다.
- Gradle 테스트 프로세스는 하나로 실행하고 JUnit 병렬 실행을 끈다. 기존 테스트 내부의 동시성 검증은 유지하되, 여러 클래스가 공용 테스트 데이터를 동시에 정리하는 위험을 줄인다.

### 3. 개발 DB 연결은 테스트 JVM 시작 전에 차단

- `TEST_DB_*`·`TEST_REDIS_*`로 받은 값을 검증한다. PostgreSQL은 localhost의 전용 포트·`lawnambul_test` DB·전용 계정만, Redis는 localhost의 전용 포트만 허용한다. 다른 DB명·호스트·포트와 JDBC URL 옵션은 거절한다.
- 검증된 접속 정보를 JVM 시스템 속성으로 주입하고 JPA와 Flyway의 접속 대상을 동일하게 고정한다.
- 기존 `DB_*`·`SPRING_*`·`FLYWAY_*`·`REDIS_*` 등과 JVM 환경 옵션은 테스트 자식 프로세스에서 제거한다. 외부 설정 파일 로딩과 관련 `jvmArgs` 재지정도 제한해 프로필보다 우선하는 설정의 우회를 막는다.
- IDE 테스트 실행은 Gradle 위임을 권장한다. PR #186 리뷰 반영으로 테스트 전용 `TestEnvironmentGuard`를 추가해 IntelliJ 자체 실행의 `@SpringBootTest`도 빈 생성 전에 접속 대상을 검사한다. 실행기별 보호 범위와 일반 Spring 컨텍스트·직접 JDBC 호출의 한계는 [테스트 환경 안내](../../backend/TESTING.md)에 명시했다.

### 4. 로컬과 GitHub Actions의 접속 계약 통일

- CI는 기존 PostgreSQL·Redis 서비스 컨테이너와 테스트·이미지 빌드 흐름을 유지하고, DB명·계정·호스트 포트·환경변수를 테스트 전용 설정에 맞췄다. CI에서 Compose를 추가 실행하지 않는다.
- 로컬은 테스트 전용 볼륨을 유지하고 CI는 실행마다 임시 서비스를 생성한다. Redis의 로컬 AOF/noeviction 설정과 CI 기본 정책 차이는 유지하며, CI 통과만으로 Redis 운영 정책까지 검증했다고 보지 않는다.

## 고려한 제약 사항

- 기존 마이그레이션·비공개 시드·개발 및 운영 볼륨은 변경하거나 삭제하지 않는다. 테스트 데이터 초기화는 전용 Compose 프로젝트에만 한정한다.
- 하나의 테스트 DB에 여러 Gradle 실행을 동시에 연결하지 않는다. 포트가 테스트 서비스로 연결된다는 전제는 실제 실행 전에 확인한다.
- JVM 환경 옵션을 제거하므로 IDE·에이전트 도구가 해당 옵션에 의존한다면 별도 호환성 검토가 필요하다.
- 실행 절차와 상세 설정값을 이 문서에 복제하지 않고 [테스트 환경 안내](../../backend/TESTING.md)와 실제 설정 파일을 참조한다.

## 검증 결과

- **테스트 전용 PostgreSQL·Redis 정상 실행**: 사용자 전달 결과 기준으로 확인했다.
- **개발 DB 주소 지정 시 Gradle 테스트 실행 차단**: 사용자 전달 결과 기준으로 확인했다. 허용하지 않는 `TEST_DB_URL`은 테스트 JVM 시작 전에 거절한다. 기존 `DB_URL` 등은 테스트 프로세스에 전달하지 않는 방식으로 처리한다.
- **초기 Java 테스트 56개 클래스, 576건 전체 통과**: 사용자 전달 결과와 최초 문서 작성 시점의 로컬 JUnit XML 집계를 대조했다.
- **PR #186 리뷰 반영 후 전체 재실행 통과**: `cleanTest test --no-daemon`으로 기존 576건과 신규 안전장치 9건을 포함해 57개 클래스·585건을 실행했다. 실패 0건·오류 0건·건너뜀 0건이며 기존 RAG 모의 서버·가짜 임베딩·pgvector 검색 테스트도 통과했다. 초기화기 자동 등록·빈 생성 전 차단·환경변수 별칭 우회를 DB 접속 없는 테스트로 검증했고, 가짜 API 키·DB 주소·JSON 환경변수가 Gradle 테스트 환경에서 제거되는 것도 별도 설정 검사로 확인했다. Compose 설정과 YAML 정합성 검증도 통과했다.
- **GitHub Actions CI는 아직 미검증**: 설정 정합성 확인과 로컬 테스트 통과를 CI 통과로 간주하지 않는다. PR 생성 후 실제 CI 결과를 확인해야 한다.

## 추후 재검토가 필요하면

- PR에서 GitHub Actions 테스트·이미지 빌드 결과를 확인하고, 실패 시 로컬과 CI의 차이를 검토한다.
- 테스트 규모가 커져 병렬 실행이 필요하면 실행별 DB·Redis 또는 Testcontainers 도입을 검토한다. 현재 공용 테스트 환경에서 병렬 실행만 켜지 않는다.

## PR #186 리뷰 반영

- **IDE 보호 방식**: Spring Boot 4.1.1의 `SpringApplication`과 `SpringBootContextLoader`가 `spring.factories`의 초기화기를 로드함을 확인했다. 초기화 시 검사와 빈 생성 전 재검사로 테스트 속성 덮어쓰기도 확인한다. 일반 Spring 컨텍스트까지 자동 적용된다고 확대해서 설명하지 않는다.
- **외부 API 키**: 기존 모의 RAG 테스트는 실제 API를 호출하지 않지만, 개발자 환경변수가 실제 임베딩 클라이언트를 활성화할 가능성이 있었다. Gradle에서 API 키 환경변수를 제거하고 테스트 컨텍스트에서는 실제 임베딩 키를 비운다. 모의 서버·가짜 임베딩 빈을 사용하는 기존 테스트는 유지한다.
- **볼륨 유지**: 장애 조사와 재실행 비용을 고려해 현재 볼륨 구조를 유지한다. 브랜치 간 Flyway 체크섬 충돌은 기존 테스트 프로젝트를 중지하고 별도 프로젝트의 새 볼륨으로 검증하는 보존 절차를 안내한다. 검증 비활성화·자동 `repair`·자동 볼륨 삭제는 도입하지 않는다.
- **문서와 이력**: 실행 안내는 `backend/TESTING.md`로 통일하고 macOS/Linux와 Windows 명령을 구분한다. Gradle 속성의 설정 단계/실행 직전 재주입 이유를 주석으로 남겼으며 기존 커밋 이력은 변경하지 않는다.
