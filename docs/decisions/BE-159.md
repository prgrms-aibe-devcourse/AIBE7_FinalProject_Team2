# BE-159 의사결정 기록

BE-149(PR #395) 리뷰에서 나온 후속이다. 생성 단계 검증(`check_opening`)이 닿지 않는 곳과 빈 목록을 다룬다.

## 문제 / 배경

- BE-149의 `ul` 형식 검사는 **새로 생성하는 값**만 막는다. 이미 만든 대본, 승인된 블록, 가져온 값에는 닿지 않는다.
- `ul`이 빈 목록(`[]`)이어도 BE-149 검사는 통과한다. `issues.ul`은 프롬프트가 3개를 요구하므로 빈 카드가 공개될 수 있다.
- 공개 응답(`PublicCaseScriptResponse.publicCards`)과 화면(`assembleScript.cardsOf`)은 이미 틀린 `ul`을 비워 내서 예외는 나지 않는다. 영향은 "카드가 빈 채로 보인다"까지다.

## 확인한 것

- 로컬에 있는 21건 생성 대본(공개 가능 21 / 21)의 U2 카드 세 개 모두 `ul`이 문자열 목록이고 비어 있지 않았다. 지금 확인된 문제 데이터는 없다.
- 관리자 문장 수정(A-13-21)은 블록에 **이미 있는 자리**의 문자열만 바꾼다(없는 자리는 `SCRIPT_LINE_NOT_FOUND`). 그래서 관리자가 `ul`의 모양을 바꿀 수 없다. 형식이 틀린 값이 생길 길은 생성(BE-149가 막음), 직접 가져오기, DB 직접 수정이다.

## 검토한 대안

저장된 블록의 `ul` 점검 방식:

- 대안 1, 파이썬 검수(`script_review`)에 검사를 더한다: 관리자 검수 화면과 파이프라인이 읽는 `review` 목록에 같은 형식으로 나타난다. 변경이 작고 BE-149 검사와 같은 기준을 쓴다.
- 대안 2, 백엔드가 승인 · 수정 저장 때 검사한다: 자바 쪽이 대본 모양을 따로 알아야 하고, 관리자 수정이 모양을 바꾸지 못해 걸러낼 것이 거의 없다. 계약 파일 · 테스트가 늘어난다.
- 대안 3, 일회성 점검 스크립트: 지금 데이터는 확인했지만, 앞으로 가져오는 값에는 닿지 않는다.

빈 `ul`과 모양 오류의 심각도:

- 오류로 두기: 오류는 "이대로 내보낼 수 없다"이고 줄 하나를 고쳐 쓰는 복구(`fix: line`)가 따른다. `ul`은 줄이 아니라 목록이라 줄 고쳐 쓰기(`script_repair`)가 맞지 않고, 공개도 이미 안전하게 방어되고 있다.
- 경고로 두기: 공개는 막지 않고 관리자가 확인하게 한다.

## 선택한 방법과 이유

- **대안 1을 택했다.** `script_review.review_unit`이 U2일 때 `card_list_issues`를 더 부른다. 검사 코드 둘을 추가했다.
  - `CARD_LIST_INVALID`: `ul`이 문자열 목록이 아니다(키가 없는 경우 포함).
  - `CARD_LIST_EMPTY`: `ul`이 빈 목록이거나 공백 문자열뿐이다.
- **둘 다 경고로 뒀다.** 휴리스틱이 아니라 기계적으로 판단할 수 있는 모양 검사지만, 고치는 방법이 줄 고쳐 쓰기가 아니고 공개 응답 · 화면이 이미 비워 내 사용자에게 예외가 나지 않는다. 오류로 올리면 고칠 수 없는 오류로 대본 공개가 막힐 수 있다.
- 카드 자체가 없는 모양(`cards.indict`가 객체가 아님)은 `check_opening`이 이미 다루므로 건너뛴다.
- 백엔드는 바꾸지 않았다. 검사 코드 목록이 백엔드나 계약 파일에 따로 없어 파이썬 쪽(`CODES` · README "검수 조건" 표)만 고쳤다.

## 고려한 제약 사항

- 이미 저장된 블록에 경고를 붙이려면 그 대본의 `review`를 다시 계산해야 한다. 이 PR은 검사를 추가한 것이고, 기존 대본의 재검수는 다음 재생성 · 재검수 때 반영된다. 지금 21건에는 해당 데이터가 없다.

## 추후 재검토가 필요하면

- 직접 가져오기나 DB 수정으로 형식이 틀린 블록이 실제로 생기면, 가져오기 경로에서 검사하는 방안(대안 2)을 다시 본다.
- 빈 카드가 실제로 공개되는 사고가 나면 `CARD_LIST_EMPTY`를 오류로 올리고 U2 단위 재생성(`fix: unit`)과 묶는 것을 검토한다.
