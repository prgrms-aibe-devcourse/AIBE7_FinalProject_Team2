# BE-129 의사결정 기록

대본 생성 단계 통합 실행(분류 → 생성 → 검수 → 적재) 및 기존 파이프라인 · 서비스 연동. 해송님 결정(2026-10-29, BE-125 PR #338 후속)과 범위는 Jira BE-129 본문에 있다.

## 1차 등록 한 번에 대본까지 (PR 백엔드 · 파이프라인 설정)

### 문제 / 배경

- 해송님 결정은 "등록 방식 1회"다. 사건을 등록하면(A-14) 한 작업이 중간에 멈추지 않고 추출 → 분류 → 대본 생성 → 검수까지 돌린다. 사건을 만드는 적재(A-14-1, 초안)는 지금처럼 관리자가 작업이 `SUCCEEDED`가 된 것을 보고 따로 부르며, 그때 대본 · 분류가 사건과 함께 들어간다. 관리자가 내용을 보는 것은 적재 뒤 검수 화면이다. 배역은 등록 요청의 `crimeType`으로 대본보다 먼저 정한다.
- 시작 전에 확인한 지금 상태:
  - 파이프라인은 이미 한 흐름이다. `STAGES`가 `… axis → classify → script → load`이고, `--from` · `--until` · `--skip` · 이어 하기와 "앞 단계를 다시 돌리면 뒤 단계 상태를 지운다"가 새 단계에도 그대로 적용된다(BE-121 · BE-123). `script.full`이면 분류 결과로 U0 ~ U4를 만들고, 검수 오류가 난 줄은 고쳐 쓰고 남으면 그 단위만 다시 만든다(BE-122 2차). 서비스(`jobs.py`)도 classify · script 결과를 돌려준다.
  - 빠진 것은 백엔드다. 등록 요청이 classify를 켜지 않고 대본을 증거조사만(`full` 없음) 요청했으며, 배역은 전역 설정 값(모든 사건이 같은 배역)을 넘겼다. 분류 결과는 민감 플래그만 저장하고 나머지 축과 `needsReview`는 버렸다.
  - 운영에서는 대본이 아예 꺼져 있었다. `pipeline-service.script-model`이 `application.yml` · Compose · `.env.example` 어디에도 연결되지 않아 늘 비어 있었다.

### 검토한 대안

- **배역을 정하는 시점**
  - 적재(A-14-1) 때 정한다(BE-125 방식): 대본이 이미 만들어진 뒤라, 대본을 만든 배역과 규칙이 고른 배역이 다를 수 있다. 1회 방식과 맞지 않는다.
  - 2단계(분류까지 → 적재하며 배정 → 그 배역으로 대본): 해송님이 택하지 않았다.
  - **등록 요청(A-14)을 받을 때 정한다 (택함)**: 대본보다 먼저 정해 파이프라인에 넘긴다. 기준은 요청의 `crimeType`이고, 판결문에서 읽은 유형이 다르면 BE-138이 대본 전에 멈춘다.
- **균형 계산이 세는 대상**
  - 사건만 센다: 등록 중인 사건(아직 사건이 아님)의 배역이 빠져, 그 사이 다음 등록이 같은 배역을 받는다.
  - **사건 + 아직 적재되지 않은 등록, 실패한 등록 제외 (택함)**: 해송님 결정("실패하거나 취소된 등록은 균형 계산에서 뺀다")과 같다. 취소는 서비스가 작업을 멈추면 `FAILED`로 끝나 같은 조건으로 빠진다.
  - 생성이 끝났지만 적재하지 않은 등록(`SUCCEEDED`)을 기간으로 자른다: 버려진 등록이 영영 세어지는 것을 막지만 기준(며칠)이 하나 더 생긴다. 실제로는 드물어 **자르지 않기로 했다**(사용자 확정, 2026-11-01).
- **배정과 작업 생성의 순서 · 잠금**
  - 범죄 유형 잠금을 잡은 채 파이프라인 작업을 만든다: 외부 호출 동안 DB 커넥션 · 잠금을 들고 있게 된다(BE-92 · BE-93이 피한 방식).
  - **짧은 트랜잭션으로 배정하고, 잠금을 놓은 뒤 작업을 만든다 (택함)**: 배정한 값이 균형에 들어가는 것은 작업 행을 저장한 뒤라 그 사이 다른 등록이 같은 배역을 받을 수 있다. 하지만 파이프라인은 한 번에 작업 하나만 받으므로(`IMPORT_IN_PROGRESS`, 서비스도 막는다) 둘 중 하나는 작업을 만들지 못하고 끝난다. 사건 적재와 겹쳐도 같은 잠금을 쓰고, 적재된 등록은 세지 않아 한 번씩만 세어진다.
- **분류 저장 위치**
  - 축마다 칸을 나눈다: 값 목록을 파이프라인이 정하고(`case_classify.py`) 2차 재생성 때 통째로 다시 넘기는 값이라, 칸을 나누면 파이프라인이 축을 늘릴 때마다 마이그레이션이 필요하다.
  - 등록 행(`case_import`)에 둔다: 재생성은 사건을 기준으로 하고, 관리자가 고칠 값이다.
  - **`legal_case.classification` jsonb 한 칸 + `classification_needs_review` (택함, 해송님 제안안)**: 민감 플래그는 BE-125의 `sensitive_flags`가 이미 갖고 A-11로 고치므로 분류 칸에서는 뺀다 — 두 군데 두면 고칠 때 어긋난다.
- **분류 단계를 켜는 조건**
  - 늘 켠다: 대본 없이 등록하는 서버에서도 민감 플래그가 채워지지만, 설정을 건드린 적 없는 서버의 모델 호출이 3회 늘어난다(대본을 기본 꺼짐으로 둔 것과 같은 이유로 피했다).
  - **대본을 켤 때만 함께 켠다 (택함)**: 분류는 대본 전체의 입력이다.

### 선택한 방법과 이유

- A-14가 대본을 켠 서버(`PIPELINE_SCRIPT_MODEL`)에서 `CaseCastAssigner.assign(crimeType)`으로 배역을 정해 `case_import.cast_roles`에 남기고, 파이프라인에 `classify`(모델은 `PIPELINE_CLASSIFY_MODEL`, 비우면 생성 모델의 첫 모델)와 `script`(`full: true`, `cast`)를 켜서 `until: script`로 보낸다.
- 균형 쿼리(`LegalCaseRepository.countDefenseByCrimeType` · `findLastDefenseByCrimeType`)가 `legal_case`와 미적재 `case_import`를 함께 본다. "마지막 배정"은 두 표의 id가 다른 순번이라 만든 시각으로 맞춘다(같으면 등록 쪽, 그다음 id).
  - 시각은 배역을 정한 때로 맞춘다(리뷰 반영). 사건의 적재 시각과 등록의 등록 시각을 섞으면, 등록을 여러 건 해 두고 순서와 다르게 적재했을 때 "마지막"이 바뀌어 같은 배역이 연달아 나올 수 있다. 그래서 등록 때 정한 배역이 그대로 사건 배역이 된 사건은 연결된 등록의 시각을 쓴다. 등록 때 배역을 정하지 않았거나(V46 전 등록 · 대본을 끈 서버), 대본 배역이 달라 적재 때 정해진 사건은 적재 시각을 쓴다 — 늘 등록 시각을 쓰면 이 경우가 다시 어긋난다.
- 적재는 대본의 배역을 그대로 쓴다(BE-125와 같음, 대사에 이름이 들어 있다). 등록 때 정한 배역과 다르면 로그를 남긴다. 대본이 없으면(대본 단계 실패 등) 등록 때 정한 배역을 쓰고, 그것도 없으면 지금까지처럼 규칙으로 정한다.
- 적재가 분류의 축 값과 `needsReview`를 사건에 저장하고 A-6 `content`에 내려 준다. 검수 화면 표시는 프론트 몫이다.
- 전역 배역 설정(`scriptProsecutor` · `scriptDefense`)은 지웠다. 더 이상 쓰는 곳이 없고, 남겨 두면 "설정으로 배역이 바뀐다"고 오해한다.
- 운영 설정을 연결했다: `PIPELINE_SCRIPT_MODEL` · `PIPELINE_CLASSIFY_MODEL`을 `application.yml` · `docker-compose.pipeline.yml` · `.env.example`에 더했다. 기본은 그대로 꺼짐이다.

### 고려한 제약 사항

- 파이프라인 로컬 `load` 단계는 대본 · 분류를 적재하지 않는다. 대본 블록 · 메타 · 기사 · 분류는 백엔드 적재(A-14-1, `CaseImportLoader` · `CaseScriptLoader`)가 넣는다 — 같은 규칙을 파이썬 SQL로 한 벌 더 만들면 어긋난다. 파이프라인 README에 적었다.
- Jira 완료 조건 "BE-125 머지 후 쏠린 배정 수 확인": 운영 `case_script`가 0행이라(2026-10-30 확인) 대본이 있는 등록이 없었고, 보정할 것이 없다.
- 이 PR 동안 API 명세 v0.79는 BE-140 3차 c(PR #366)가 쓰고 있어 v0.80으로 적었다.

### 추후 재검토가 필요하면

- 2차: 블록 재생성 API(연동 표대로 뒤 블록까지), 관리자가 분류 값을 고치는 경로(A-11)와 그 값으로 다시 만들기.
  - **재생성에 넘기는 분류는 `classification` + `sensitive_flags`를 합친 값이어야 한다**(해송님 리뷰). `classification`은 민감 플래그를 일부러 뺀 값인데, 파이프라인 검사(`classification_errors`)는 `sensitiveFlags`가 없으면 빈 목록으로 읽고 오류로 보지 않는다. 그대로 넘기면 민감 사건이 안내 · 표현 가드 없이 조용히 다시 만들어진다. `sensitive_flags`가 비어 있으면(미분류) 재생성하지 않거나 분류부터 다시 한다. 민감 플래그 없이 대본이 생성되지 않는 것을 테스트로 막는다.
  - **분류가 실패하면 등록 전체가 실패한다**(해송님 리뷰). 대본 단계는 실패해도 `publishable: false`로 남고 작업은 끝나지만, 분류는 유효한 응답이 하나도 없으면 파이프라인이 멈춰 작업이 `FAILED`가 된다. 백엔드에는 "분류부터 이어서" 경로가 없어 다시 등록해야 하고, 가장 비싼 추출과 판결 생성을 다시 치른다. 드물어서 1차에서는 두었다. 파이프라인은 `--from classify`로 이어 갈 수 있으니 2차 재생성 API에서 "분류 단계부터 다시"를 함께 연다.
- 버려진 `SUCCEEDED` 등록이 쌓여 균형이 눈에 띄게 기울면, 기간으로 자르거나 등록을 닫는 API를 둔다.
- 대본을 끈 서버에서도 민감 플래그가 필요해지면 분류를 대본과 따로 켜는 설정을 둔다.

## 2차-1 블록 재생성 — 파이프라인 · 서비스 (PR #378)

2차는 PR 두 개로 나눈다. 이 PR은 파이프라인이 고른 블록만 다시 만드는 경로와 서비스 요청이고, 백엔드 API(작업 생성 · 결과 반영 · A-11 분류 수정)는 2차-2다.

### 문제 / 배경

- 관리자가 검수 화면에서 배역 · 분류 · 민감 플래그 · 사건 내용 · 기사를 고치면 그 값을 보고 만든 블록이 낡는다(BE-126 `basis`). 지금은 대본을 다시 등록하는 수밖에 없다.
- 등록 작업 폴더는 적재 뒤 백엔드가 지운다(판결문 원문 보호, COMMON-51). 남아 있어도 관리자가 고친 값은 들어 있지 않다.
- 파이프라인이 실제로 읽는 값은 모두 DB에 있다. 사건 내용(`db_case_input.py`가 같은 일을 한다), AI 판결(U3는 판단 요소 방향 `judgment_factor.direction`, 검수는 형량 숫자 · 권고형으로 누출을 잡는다), 분류 · 민감 플래그 · 배역 · 기사 · 지금 블록이다.

### 검토한 대안

- **재생성 입력**
  - 등록 작업을 `--from script`로 이어 돌린다: 폴더가 지워진 뒤에는 불가능하고, 고친 값을 넣을 자리가 없다.
  - **백엔드가 DB 값으로 입력을 모아 새 작업으로 보낸다 (택함)**: 판결문 원문 없이 돈다. 사건 입력은 작업 폴더의 `input/`에만 두어 작업을 지우면 함께 지워진다.
- **다시 만들 범위**
  - 관리자가 고른 블록만: U0만 다시 만들면 U0 질문을 받는 U2 · 쟁점을 받는 U4가 곧바로 낡는다.
  - 대본 전체: 승인한 블록까지 바뀐다.
  - **고른 블록 + 그 블록을 입력으로 받는 뒤 블록 + 없는 앞 블록 (택함)**: 뒤 블록은 정본 `BLOCK_BASIS`에서 계산한다. 백엔드에 같은 표를 다시 두지 않는다(BE-126 계약 파일은 낡음 계산용으로 이미 있다). 증거조사만 있는 대본(V45 이관)에서 U2를 고르면 U0도 함께 만든다.
- **세부조정(리뷰 반영)**: 해송님 10/30 결정은 "묶음 수정이 기본이되, 블록을 하나씩 따로 만들 수도 있어야 한다"였다. 뒤 블록을 늘 더하면 U0 질문 한 줄 때문에 승인된 U2 · U4까지 다시 만들게 된다. `cascade`(기본 `true`)를 두어 `false`면 고른 블록 + 없는 앞 블록만 만든다. 남은 뒤 블록은 `basis`가 옛 판을 가리켜 백엔드가 낡음으로 본다. 화면에 어떻게 노출할지는 2차-2 몫이다.
- **해송님 연동 표 읽기**: 피해자 측(`U0 → U3 · U4`) · 부가 인물(`U0 → U2 · U3`) 행은 `U0 → U2 → U4` 행과 겹쳐 읽었다(해송님 확인 — 표의 화살표는 고치는 순서이고 실제 의존은 `BLOCK_BASIS`가 정한다). U0를 다시 만들면 U2 · U4도 따라온다. 정본 `BLOCK_BASIS`에서 U2는 U0 질문을, U4는 U0 쟁점을 받기 때문이다. 따라서 피해자 측은 U0 · U2 · U3 · U4, 부가 인물도 U0 · U2 · U3 · U4다. 나머지 행(배역 · 쟁점 · 분위기 · 민감 플래그 · 기사 · U0 · U2)은 표와 같다(`tests/test_script_regenerate.py`가 확인한다).
- **앞 블록을 만들지 못했을 때**
  - 옛 앞 블록으로 뒤 블록을 만든다: 관리자가 바꾸려던 값(예: 새 쟁점)이 뒤 블록에 들어가지 않는데 "다시 만들었다"로 보인다.
  - **뒤 블록도 만들지 않고 `pending`에 남긴다 (택함)**. 호출 한도가 소진되면 그 자리에서 멈춘다. 줄이 모자란 증거조사로 지금 U3를 덮지 않는다.
- **고쳐 쓰기(BE-122 2차) 범위**
  - 대본 전체의 오류: 다시 만들지 않은 블록은 관리자가 이미 승인했을 수 있다.
  - **다시 만든 블록의 오류만 (택함)**: `repair_units`에 대상 단위를 받는 인자를 더했다. 검사는 대본 전체를 한다(U2와 U0 질문이 맞는지 같은, 블록 사이 검사가 있다).
- **돌려주는 검수 결과(리뷰 반영)**
  - 대본 전체: 만들지 않은 블록의 항목까지 들어가, 백엔드가 블록별로 덮어쓰면 승인된 블록이 "오류 블록"(V45 제약)이 되어 다시 승인할 수 없다.
  - **다시 만든 블록의 항목 + 단위 없는 `REVIEW_FAILED`만 (택함)**: 만들지 않은 블록의 검수 결과는 그 블록을 만들 때의 것이 그대로 맞다.
- **지금 U1과 기사(리뷰 반영)**: 검수는 U1을 기사와 비교한다. U4만 다시 만들면서 기사를 넘기지 않으면, 숫자가 든 지금 U1에 가짜 `NUMBER_NOT_IN_SOURCE`가 나왔다(해송님이 실제 대본으로 5건 확인). 그래서 **U1 블록이 있으면 기사를 필수**로 했다(재생성 모듈 오류 · 서비스 400). 위 검수 결과 범위와 함께 두 겹으로 막는다.
- **판 번호**
  - 다시 만든 블록을 1판부터: 백엔드 낡음 계산이 판 번호 비교라 옛 판과 같은 번호가 나오면 낡음을 놓친다.
  - **지금 판 다음 판부터 (택함)**: `block_revisions` · `build_blocks`에 지금 판(`base`)을 받는 인자를 더했다. 다시 만들지 않은 앞 블록은 `basis`에 지금 판으로 남는다.
- **서비스 경로**
  - 새 엔드포인트(`POST /regenerations` 등): 상태 · 결과 · 중단 · 삭제 · 자동 정리 · 단일 작업 규칙을 한 벌 더 만들어야 한다.
  - **같은 `POST /jobs`에 `regenerate` 요청 모양을 더한다 (택함)**: 작업 메타에 종류(`kind`)를 남기고 결과만 나눈다. AI 호출 한도를 함께 쓰므로 등록과 재생성은 한 번에 하나만 돈다.
- **민감 플래그 안전장치(1차 리뷰 1번)**
  - 파이프라인 설정 검사와 재생성 모듈이 분류에 `sensitiveFlags` 키가 없으면 거절한다. 대본 전체 생성의 `classification_errors`는 빠진 키를 빈 목록으로 읽기 때문이다.
  - 서비스도 작업을 만들기 전에 400으로 막는다. 내용 검사는 파이프라인에만 두지만, 이 항목은 안전과 직결돼 두 곳에 두었다.
  - 빈 목록은 "민감 요소 없음"으로 받는다. 백엔드는 미분류(`sensitive_flags`가 null)일 때 요청하지 않는다(2차-2).
- **분류부터 다시(1차 리뷰 2번)**: 분류에서 실패한 등록은 사건이 적재되지 않아 재생성 대상이 아니다. 필요한 기능은 "실패한 등록 작업 이어 하기"(서비스 이어 하기 엔드포인트 + A-14 쪽 API)다. 성격이 달라 **별도 이슈로 분리했다**(사용자 확정, 2026-11-02).

### 선택한 방법과 이유

- `script_regenerate.py`(새 모듈)가 고른 블록을 다시 만든다. 단위를 만드는 요청(`design_request` · `intro_request` · `opening_request` · `closing_request` · BE-107 증거조사)은 대본 전체 생성과 같은 함수를 쓴다. 같은 블록 · 같은 가드로 만들어야 재생성한 블록이 처음 만든 블록과 같은 기준이 된다.
- `pipeline.py`:
  - `stages.script.regenerate`(고른 블록 목록)와 입력 파일 `inputs.judgment`(AI 판결 방향) · `inputs.blocks`(지금 블록)를 더했다.
  - 재생성은 select 결과 대신 넘겨받은 판결 방향을 쓴다. 결과는 `regenerate.json`이고, 입력을 모두 읽고 재생성이 끝난 뒤에야 지난 결과를 지운다.
- 서비스:
  - `POST /jobs` 본문에 `regenerate`가 있으면 입력을 작업 폴더에 쓰고 대본 단계만 켠 설정을 만든다.
  - 배역 · 분류 · 고른 블록은 `regenerate`로만 받고 `stages.script`로 덮을 수 없다.
  - `GET /jobs/{id}/result`는 `{"kind": "regenerate", "regenerated": ...}`다(경로 대신 내용).
- 서비스는 파이프라인 모듈을 불러오지 않는다. 그래서 서비스가 만든 설정이 파이프라인 설정 검사 → 대본 단계 → 서비스 결과 → 삭제까지 통과하는지 교차 테스트(`tests/test_pipeline.py` `ServiceRegenerationTest`)로 묶었다. 1차 리뷰에서 해송님이 손으로 확인한 일을 자동화한 것이다.

### 고려한 제약 사항

- U3는 AI 판결에서 판단 요소 방향(`factors[].factorId · direction`)을 읽는다. 검수는 형량(`prisonMonths` · `suspensionMonths` · `fineAmount`)과 `case.recommended`도 읽어 대사에 새어 나온 숫자를 잡는다(`script_review._leak_numbers`). 방향만 넘겨도 돌지만 누출 판별이 약해지므로, 백엔드는 형량과 권고형도 함께 넘긴다(서비스 README 계약, 리뷰 반영 — 처음에는 "방향만 읽는다"고 잘못 적었다).
- 넘겨받은 판결 방향은 select 결과처럼 "생성 프롬프트와 지금 사건 입력이 같은지" 확인할 수 없다. DB가 기준이라 백엔드가 같은 사건에서 모은 값을 믿는다.
- 실제 모델을 부르는 재생성은 돌리지 않았다(외부 AI 호출). 가짜 모델로 단위 · 단계 · 서비스 경로를 확인했다.

### 추후 재검토가 필요하면

- 2차-2(백엔드):
  - 재생성 API(작업 생성 → 상태 → 결과 반영)
  - 결과 반영 때 블록 내용 · 판 · 근거(DB 판 채우기) · 검수 결과를 바꾸고 승인 해제
  - `sensitive_flags`가 null이면 거절
  - A-11 분류 수정
- 실패한 등록 이어 하기(분류부터 다시)는 별도 이슈.
- U3를 다시 만들면 줄마다 새로 만들어, 관리자가 손으로 고친 줄(A-13-13, `validation.manual`)이 모두 바뀐다. 배역을 바꾸면 U3가 자동으로 포함되므로, 2차-2에서 결과 반영 전에 "수동 수정한 줄 N개가 새 대사로 바뀝니다" 같은 확인과 비교를 둔다(해송님 리뷰).
- 재생성 결과는 호출마다 달라진다. 직전 결과와 비교해 보여 줄지는 2차-2에서 정한다.

## 2차-2 블록 재생성 — 백엔드 API · A-11 분류 수정 (PR #381)

### 문제 / 배경

- 2차-1(PR #378)에서 파이프라인 서비스가 고른 블록만 다시 만드는 작업을 받게 됐다. 남은 일은 세 가지다. 백엔드가 DB 값으로 입력을 모아 작업을 맡기는 것, 관리자가 결과를 반영하는 것, 관리자가 분류를 고치는 경로(A-11)다.
- 지켜야 할 것(1차 · 2차-1 리뷰):
  - 분류에 민감 플래그를 합쳐 넘긴다. 미분류면 요청하지 않는다.
  - U1이 있으면 기사를 함께 넘긴다.
  - 판결은 방향과 함께 형량 · 권고형도 넘긴다.
  - U3를 다시 만들면 손으로 고친 줄이 사라진다는 것을 알린다.
  - 세부조정(`cascade`)을 화면이 고를 수 있게 한다.

### 검토한 대안

- **재생성 작업 저장**
  - `case_script`에 작업 ID · 상태 칸을 더한다: 이력이 남지 않고, 반영하지 않은 결과와 새 요청이 한 칸을 다툰다.
  - **`case_script_regeneration` 표 (택함, V47)**: 사건 등록(`case_import`)과 같은 모양이다(진행 상황을 받아 적고, 끝난 작업은 바꾸지 않는다). 누가 무엇을 다시 만들었는지 남는다.
- **결과 반영**
  - 작업이 끝나면 서버가 자동으로 반영한다: 새 모델 출력이 확인 없이 들어가고, U3의 수동 수정 줄이 말없이 사라진다(PR #378 리뷰 3번).
  - **관리자가 미리보기를 보고 반영한다 (택함, A-13-16 · 17)**: 사건 등록 적재(A-14-1)와 같은 방식이다. 미리보기에 바뀌는 수동 수정 줄 수(`manualLinesReplaced`)를 준다.
- **반영할 때 입력이 바뀌었으면**
  - 그대로 반영한다: 요청한 뒤 대사를 고쳤거나 다른 재생성을 반영했으면, 옛 블록을 보고 만든 결과가 새 블록을 덮는다. 배역 · 분류를 바꿨으면 옛 값으로 만든 대사가 들어간다.
  - **요청 당시 입력을 기록해 두고 다르면 거절한다 (택함)**: 블록 판 · 사건 내용 판 · 기사 판 · 배역 · 분류 · 민감 플래그를 비교한다. 다시 요청하면 된다. 반영할 수 있는 것은 그 사건의 가장 최근 작업뿐이다.
- **어느 AI 판결을 따를지**
  - **공개된 AI 판결, 없으면 적재 때 들어온(가장 먼저 만든) AI 판결 (택함)**: 대본은 처음에 적재된 판결의 방향으로 만들어졌다. 관리자가 다른 후보를 공개했으면 공개된 판결을 따르는 것이 맞다.
- **사건 입력 범위**
  - `db_case_input.py`처럼 생성 입력 전체(형벌 규칙 · 원본 정보 포함)를 보낸다: 대본은 쓰지 않는 값이고, 원본 정보(사건번호 등)를 외부 모델 쪽으로 보낼 이유가 없다.
  - **대본 모듈이 실제로 읽는 필드만 (택함)**: 제목 · 죄명 · 적용 법조 · 개요 · 섹션(용어 설명 · 핵심 정리 제외) · 판단 요소 · 권고형만 보낸다.
- **A-11 분류 수정 모양**
  - 축마다 따로 보낸다: 일부만 있는 분류는 재생성 설정 검사에서 막힌다.
  - **네 축을 통째로 (택함)**: 값 목록은 계약 파일(`contracts/script_blocks.json` `classification`)에 두고 파이썬 · 자바 테스트가 함께 읽는다. 고치면 관리자 확인 필요 목록에서 분류 축 항목을 지운다(사람이 정했으므로). 민감 플래그 항목은 민감 플래그를 고칠 때의 일이라 남긴다.
- **진행 중 작업 막기**
  - 같은 사건의 재생성이 돌면 막는다. 막기 전에 파이프라인에 한 번 확인한다(등록 `guardNoRunningImport`와 같은 이유 — 화면을 닫으면 끝난 작업이 RUNNING으로 남는다).
  - 다른 사건의 등록 · 재생성은 서비스가 409로 막는다. 따로 코드를 만들지 않고 `IMPORT_IN_PROGRESS`를 같이 쓴다(한도를 함께 쓰는 같은 상황이다).

### 선택한 방법과 이유

- `AdminScriptRegenerationService`:
  - 작업 생성(A-13-15) · 상태와 미리보기(A-13-16) · 반영(A-13-17)을 맡는다.
  - 파이프라인 호출은 트랜잭션 밖에서 하고, DB 읽기 · 쓰기만 짧은 트랜잭션으로 묶는다(등록과 같은 이유).
  - 반영은 사건 행을 잠그고 한다(대본 승인 · 대사 수정과 같은 잠금).
  - 반영 버튼을 상태 조회보다 먼저 눌러도 되도록, 도는 중으로 보이면 한 번 확인한다.
- `ScriptRegenerationInputs`가 DB 값을 파이프라인 요청 형식으로 바꾸고, 요청 당시 입력 기록(`snapshot`)과 비교(`sameInputs`, JSON 숫자 Integer · Long 차이를 맞춤)를 맡는다.
- `CaseScript.applyRegeneration`:
  - 다시 만든 블록만 바꾸거나 붙이고, 그 블록의 검수 기록을 지운다.
  - `pending` · 메타 · 대본 전체 검수 결과 · `publishable`을 다시 계산한다. `admits`는 U0 세 번째 답으로 서버가 계산한다(적재와 같은 규칙).
  - 판은 결과 판을 쓰되 지금 판보다 작으면 지금 판 + 1이다(판은 내려가지 않는다).
- 테스트 설정(`application-test.yml`)에서 대본 생성 모델을 켰다. 운영에서 켤 상태로 시험하고, 재생성 API가 이 값이 있어야 열리기 때문이다. 설정 기본값 테스트는 설정 객체를 직접 만들어 본다.

### 고려한 제약 사항

- 파이프라인 클라이언트는 테스트에서 가짜다(`TestPipelineClientConfig`, 컨텍스트를 늘리지 않으려고 `@MockitoBean`을 쓰지 않는다). 보내는 입력과 받은 결과의 반영은 백엔드 테스트가, 실제 재생성은 파이프라인 테스트가 본다.
- 실제 모델을 부르는 재생성 전체 흐름은 돌리지 않았다. 해송님이 머지 뒤 실제 대본 1건으로 연쇄 재생성의 시간 · 호출 수 · 고쳐 쓰기 성공률을 재기로 했다(BE-129 Jira).
- API 번호: A-13-14는 사건 공개 취소(BE-118)가 쓰고 있어 A-13-15 ~ 17로 매겼다.

### 추후 재검토가 필요하면

- BE-126 2차: 블록 단위 승인 · 낡음 표시 · `scriptStatus`. 세부조정으로 남은 뒤 블록과, 배역 · 분류를 바꾼 뒤의 블록이 낡음으로 보이게 된다.
- 반영하지 않고 버린 재생성 작업의 파이프라인 결과는 서비스 자동 정리(기본 7일)가 지운다. 화면에 "버리기"가 필요하면 그때 API를 더한다.
- 프론트: 재생성 버튼 · `cascade` 선택 · 미리보기 · 수동 수정 줄 확인 문구 · A-11 분류 수정 화면.
