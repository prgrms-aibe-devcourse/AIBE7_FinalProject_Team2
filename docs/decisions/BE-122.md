# BE-122 의사결정 기록

대본 생성 검수 조건(검증) 구현. 두 PR로 나눈다.

- 1차: 검사 결과 형식(BE-129가 쓰는 계약)과 README "검수 조건" 표의 검사 구현.
- 2차: 줄 단위 고쳐 쓰기 · 단위 재생성.

## 1차 (검사 결과 형식 · 검사)

### 문제 / 배경

- 조립기(BE-121)는 단위를 받을 때 형식(키 · 개수)과 BE-107 `validate_line`(길이 · 금지어)만 본다. README "검수 조건" 표(BE-119 시험에서 나온 위반: 한글 수사, 데이터에 없는 감정, 사실을 주장으로 낮춤, 한쪽 사정만 전함, 줄 수 미달 등)는 구현되지 않았다.
- 해송님 요청(2026-10-29): 단위별 검사 결과를 **오류 목록으로 돌려주는 형식**을 먼저 정해 BE-129가 쓰게 한다. 대본 저장은 단위 블록(U0 ~ U4)으로 바뀌었고(BE-126 댓글 2026-10-30), 관리자는 블록 단위로 고치고 다시 만든다.
- 근거: `tools/ai-judgment/prompts/script/README.md` "검수 조건", [BE-119](BE-119.md) 시험 기록, [BE-121](BE-121.md) "남은 관찰".

### 검토한 대안

#### 1. 결과 형식

- 대안 A: 지금처럼 단위별 문자열 목록(`{"U2": ["2번째 대사: …"]}`). 사람은 읽기 쉽지만, BE-129와 관리자 화면이 문장을 해석해야 어느 줄을 어떻게 고칠지 안다.
- 대안 B(채택): 결과 하나를 객체로 `{unit, path, code, severity, fix, message}`(U3는 `factorId`).
  - `path`는 JSON Pointer다. 블록 값 안의 위치를 가리키므로, 블록 단위 저장(BE-126)과 블록 수정 화면이 그대로 쓴다. 파이썬 · JS · 자바 모두 표준 방식이 있다.
  - `code`는 기계가 고르는 값, `message`는 사람이 읽는 값으로 나눴다. 문구를 고쳐도 집계 · 화면이 깨지지 않는다.
  - `fix`(`line` · `unit`)는 README의 재생성 범위를 결과에 담는다. BE-129가 단위마다 규칙을 다시 알 필요가 없다.

#### 2. 검사를 어디서 돌리나

- 대안 A: 각 단위의 `check_*`(생성 중 재요청 검사)에 넣는다. 걸리면 그 단위를 다시 요청한다. 휴리스틱 검사가 틀리게 걸리면 단위가 끝내 실패해 막 전체가 빠진다(`pending`).
- 대안 B(채택): 생성이 끝난 뒤 따로 돌려 결과 목록만 남긴다(`script_review.review_script`). 생성 중 재요청 검사는 지금 그대로 둔다. 오류가 있으면 대본은 공개할 수 없다(`publishable: false`). 고쳐 쓰기 · 재생성은 2차에서 이 목록을 읽어 한다.

#### 3. 오류와 경고

- README 표의 오류 · 경고 구분을 따랐다. 표에 없는 두 개(증거조사 군더더기, 같은 말 되풀이)는 Jira의 "추가 후보"라 경고로 두었다.
- 원칙: **문장 비교(휴리스틱)인 검사는 모두 경고다.** 오류는 원문 대조 · 공개 범위 · 형식처럼 기계적으로 판단할 수 있는 것만 둔다. 경고는 공개를 막지 않고 관리자가 본다.

#### 4. 한글 수사

- 대안 A: 한글 수 + 단위를 모두 오류로 본다. "한 번 더 살펴 주십시오", "두 사람은", 사건 1 수작업 대본의 "이 세 가지를"까지 걸린다.
- 대안 B(채택): 한글 수사의 값이 입력의 아라비아 숫자와 같을 때만 오류로 본다(원문 "12번" → 대사 "열두 번"). BE-119 6차 시험의 위반(원문 횟수 · 기간을 풀어 씀)을 그대로 잡고, 수를 옮긴 게 아닌 말은 통과한다. 하나("한 번")와 지시어 "이"는 보지 않는다. 입력에 없는 수를 한글로 지어낸 경우는 놓친다.

#### 5. 쟁점 ↔ 신문 질문 대응

- 대안 A: 질문과 쟁점의 낱말 겹침. 정상 대본(시험 고정 값)에서도 걸렸다. 질문은 쟁점 낱말을 되풀이하지 않는다("범행 경위" 쟁점 → "미리 해칠 생각이 있었습니까?").
- 대안 B(채택): 기계적으로 볼 수 있는 두 가지만 본다. U2 질문이 설계도(U0)가 쟁점에 맞춰 정한 앞 두 질문과 같은가(U2 지시가 "design.questions의 앞 두 개만 쓴다"다). 그리고 정신상태 · 진단 · 치료 이력을 묻는가(쟁점 블록이 막는 질문). 뜻의 대응은 관리자 검수 화면에서 본다.

#### 6. 무엇을 입력으로 보나 (숫자 · 감정 · 누출)

- 단위마다 **모델이 실제로 받은 데이터**와 비교한다. U0 · U2 · U4는 공개 단계 `OVERVIEW` · `DETAIL` · `ARGUMENT`의 사건 데이터, U1은 기사, U3는 BE-107 scene_data와 같은 제목 · 개요 · 그 판단 요소다. 입력에 없는 숫자는 `NUMBER_NOT_IN_SOURCE`다.
- 공개 전 정보는 `LAW` · `SUMMARY` 단계와 권고형(`recommended`), AI 판결 형량(`prisonMonths` · `suspensionMonths` · `fineAmount`)이다. 여기서 온 숫자 · 낱말은 `VERDICT_LEAK`로 따로 본다. 낱말 목록에 "무죄"는 넣지 않았다. 부인 사건의 변호인 입장("무죄를 주장합니다")은 판결이 아니다.

### 선택한 방법과 이유

- 새 모듈 `tools/ai-judgment/script_review.py`. `generate_units`가 끝에 `review_script`를 돌려 `review`를 남기고, `build_script`가 대본에 `review`를 싣고 오류가 있으면 `publishable: false`로 둔다. 파이프라인은 결과를 로그로 남기고 `reviewErrors` · `reviewWarnings`를 단계 출력에 더한다. 서비스 결과(`fullScript.review`)에는 그대로 실린다.
- `evidence.json`(BE-108 적재 계약)은 바꾸지 않았다. U3 결과도 대본의 `review`에만 들어간다.
- 형식 · 검사 목록은 README "검수 조건" · "검수 결과 형식"이 기준이다. 코드 상수(`CODES`)는 그 표를 옮긴 것이다.

### 고려한 제약 사항

- 파이프라인 도구는 표준 라이브러리만 쓴다. 형태소 분석기 없이 낱말 비교는 "두 글자 이상 낱말에서 끝 조사 하나를 뗀 것"으로 대략 본다.
- 실제 생성 대본은 실제 사건 내용이라 저장소에 없다. 오탐은 시험 고정 값과 사건 1 수작업 대본(`frontend/src/content/case-1/script.json`)으로만 확인했다. 수작업 대본에서 한글 수사 오탐 1건("이 세 가지")을 찾아 지시어 "이"와 단위 "세 · 일"을 뺐다. **실제 모델 출력으로 오탐 · 미탐 비율을 재지는 않았다.**

### 리뷰 반영 (PR #352)

해송님이 10/28 실제 생성 대본 3건(비공개)을 `review_script`에 넣고, 알려진 결함 17종을 일부러 넣어 확인했다. 정상 대본은 오류 0건 · 경고 3건(그중 2건 오탐), 결함은 17종 중 15종을 잡았다. 형식(BE-129 계약)과 세 가지 해석(한글 수사 · 쟁점↔질문 · "무죄" 제외)은 그대로 가기로 했다.

- **형량 숫자 미탐(오류)**: 누출을 "입력에 없는 숫자"로만 봐서, AI 판결이 24개월인 사건의 "징역 2년"을 입력 어딘가의 "2" 때문에 놓쳤다. 형량 문형("징역 · 금고 · 벌금 · 집행유예 + 숫자 + 년 · 개월 · 원")을 따로 보고, 값이 권고형 · AI 판결 형량과 같으며 입력에 같은 문형이 없으면 누출로 본다. 전과 사실("징역 10개월을 선고받은 전력")은 입력에 같은 문형이 있어 통과한다.
- **검사 실패로 생성 결과를 잃음(견고성)**: 검사는 `generate_units` 맨 끝에서 돈다. 형식 검사가 보지 않는 모양(`cards`에 모델이 더한 문자열 키, 질문이 문자열 목록)에서 예외가 나면 대본 한 건(약 3만 토큰)이 사라진다. 두 겹으로 막았다.
  - 값을 읽는 곳마다 모양을 확인해 건너뛴다.
  - 그래도 실패하면 생성 결과는 남기고 `REVIEW_FAILED` **오류**를 남긴다. 경고가 아니라 오류인 이유는 검수를 못 한 대본을 공개하면 안 되기 때문이다(해송님 의견과 같음).
- **`FACT_AS_CLAIM` 오탐**: 주장 섹션 본문 전체와 대사를 비교해 겹침 비율이 낮아, 주장을 옮긴 대사를 "사실을 주장으로 낮춤"으로 봤다. 주장을 문장 단위로 쪼개 비교한다. U1은 기사만 받아 주장 목록이 비어 있었으므로, 기사에 "주장"으로 실린 문장을 주장으로 본다. 공소사실이 사실을 "주장"으로 낮춘 미탐은 기준값(0.6)을 맞출 때 다시 본다.
- **정신상태 질문 정규식 오탐**: "약을 · 복용"이 범행 뒤 행동을 묻는 사실 질문(약물 복용)까지 걸었다. 병력을 가리키는 낱말(정신과 · 정신질환 · 진단 · 치료 · 우울 등)만 둔다. "정신" 하나만으로는 "정신을 잃었다" 같은 사실과 겹쳐 넣지 않았다.

### 추후 재검토가 필요하면

- **블록마다 `review`**(BE-126): 지금은 대본 전체에 `review`가 붙는다. 블록을 고쳐 다시 만들면 그 블록의 결과만 갱신해야 하므로, 블록 저장에서는 블록마다 `review`를 붙이거나 블록별로 불러올 수 있어야 한다(해송님 리뷰).
- 2차: `fix`에 따라 줄 고쳐 쓰기(실패한 줄만 앞뒤 대사와 함께 보내기) → 정해진 횟수를 넘기면 단위 재생성.
- 휴리스틱 검사(주장 문형 · 한쪽 사정 · 되풀이)의 기준값(낱말 겹침 0.5 · 0.6 · 0.8)은 실제 대본으로 다시 맞춘다. 오탐이 많으면 경고를 줄이고, 놓침이 많으면 프롬프트 쪽을 먼저 보강한다.
- 기사(PAPER)는 검사하지 않는다. 기사는 API 17이 단일 출처이고(BE-126 댓글), 형식 · 금지어는 `check_paper`가 본다.

## 2차 (검수 오류 고쳐 쓰기)

### 문제 / 배경

- 1차는 검사 결과(`review`)만 남기고, 오류가 있으면 공개를 막았다. README "재생성 범위"(실패한 줄만 고쳐 쓰기 → 그 단위 재생성 → 대본 전체는 다시 만들지 않음)를 구현해, 생성 단계에서 고칠 수 있는 오류는 고친다.
- 1차 리뷰에서 2차로 넘긴 공소사실 미탐(사실을 "주장"으로 낮춤)도 함께 본다.

### 검토한 대안

#### 1. 고쳐 쓰기를 어디서 부르나

- 대안 A: `generate_units` 안에서 생성 · 검사 · 고쳐 쓰기를 한 번에 한다. 호출하는 쪽은 편하지만, 생성 함수가 커지고 고쳐 쓰기를 끄거나 따로 부를 수 없다.
- 대안 B(채택): 새 모듈 `script_repair.py`의 `repair_units`를 파이프라인이 `generate_units` 뒤에 부른다(`stages.script.repairRetries`, 기본 2, 0이면 끔). 생성 결과를 받아 고친 복사본을 돌려준다. 줄 하나를 고쳐 쓰는 함수(`rewrite_line` · `rewrite_evidence`)는 BE-129에서 관리자가 블록을 고칠 때도 쓸 수 있다.

#### 2. 무엇을 고치나

- 대안 A: 오류와 경고를 모두 고친다.
- 대안 B(채택): 오류만 고친다. 경고는 문장 비교(휴리스틱)라, 고쳐 쓰게 하면 맞는 대사를 바꿀 수 있다. 경고는 관리자가 본다.

#### 3. 줄을 고쳐도 남으면 어떤 단위를 다시 만드나

- README는 "그 단위 재생성"이지만, 단위마다 다시 만들 때의 비용이 다르다.
  - U0(설계도): U2 질문 · U4 쟁점이 기댄다. 다시 만들면 뒤 단위가 모두 어긋난다(BE-129 연동 표: U0 → U2 → U4).
  - U2: 쟁점 정리가 모두진술 · 신문과 한 호출이라 다시 만들면 U4까지 어긋난다(BE-119 "U2는 줄 단위만").
  - U3: 요소마다 따로 부르므로 그 줄을 다시 만드는 것이 곧 재생성이다.
- 채택: **U1 · U4만** 한 번 다시 만든다. 다른 단위는 줄 고쳐 쓰기만 하고, 끝내 남은 오류는 둔다(공개 불가, 관리자가 고친다). 다시 만든 값은 **오류가 줄었을 때만** 바꾼다. 늘거나 같으면 지금 값을 둔다.

#### 4. 고친 줄을 받을지 판단

- 고친 줄을 단위 값에 넣어 그 단위 검사를 다시 돌리고, 그 줄의 오류가 없을 때만 받는다. 단위 형식 검사(`check_*`, 예: 공소사실 · 최종변론의 구형 금지, 설계도 마지막 질문 고정)도 다시 본다.
- 받지 않은 줄은 단위 값에 넣지 않는다. 다음 요청에는 **원래 줄 · 원래 고칠 점**에 더해 "받지 않은 줄과 그 이유"를 함께 보낸다. 처음에는 다음 요청의 고칠 점을 새 오류로 바꿔치기했는데, 원래 줄을 보여 주면서 원래 문제를 빼먹는 버그였다(테스트에서 발견).

#### 5. 고쳐 쓰기 프롬프트

- 단위를 만들 때와 같은 블록(페르소나 · ROLE · CASE GUIDE · 가드 · 민감 가드)과 같은 사건 데이터를 쓴다(`unit_prompt`로 생성 요청과 나눠 씀). 거기에 지금 줄 · 앞뒤 줄 · 고칠 점, "말하는 사람 · 역할 · 사실은 그대로", "줄 첫머리 정해진 문구는 그대로"를 더한다. U2 · U4는 구형 금지, 신문 질문은 질문 규칙(`QUESTION_RULES`)을 다시 넣는다.
- U3는 BE-107 프롬프트(`build_evidence_prompt`)에 지난 대사 · 고칠 점을 덧붙여 대사 텍스트로 받는다(BE-107 출력 형식이 JSON이 아니라서).

#### 6. 공소사실 미탐 (1차 리뷰에서 넘어온 것)

- 공소사실은 검사가 사실로 말하는 줄이다. 피고인 주장을 옮긴 게 아니면 "주장" 문형 자체가 사실을 낮춘 것이므로, 요소 라벨과 낱말이 겹치지 않아도 경고한다. 라벨 겹침(0.6)만으로는 바꿔 말한 공소사실을 놓쳤다.

### 선택한 방법과 이유

- 위 각 항목의 채택안. 공통 기준은 **README "재생성 범위"와 단위 의존 관계(BE-119 · BE-129 연동 표)를 그대로 따르는 것**, 그리고 **고쳐 쓰기가 맞는 대사를 망가뜨리지 않는 것**이다(오류만 고치고, 다시 검사해 나아진 것만 받는다).
- 호출 한도가 소진되면 그 자리에서 멈추고 남은 오류는 둔다. 고쳐 쓰기 뒤 검사가 실패하면 1차와 같이 `REVIEW_FAILED`로 공개만 막는다.

### 고려한 제약 사항

- 비용: 오류가 난 줄 하나에 최대 `repairRetries`번(기본 2) 호출하고, U1 · U4는 한 번 더 단위를 만들 수 있다(그 안에서 형식 오류 재요청은 `maxRetries`). 정상 대본은 오류가 없어 호출이 늘지 않는다(해송님 확인: 실제 대본 3건 오류 0건). **실제 모델로 고쳐 쓰기의 성공률 · 토큰은 재지 않았다** — 테스트는 가짜 호출이다.
- 대본 전체(`full`)를 만들 때 고친 증거조사(U3) 대사는 `evidence.json`에도 그대로 들어간다(파이프라인이 고친 뒤의 대사로 쓴다). 모양(BE-108 적재 계약)은 같고, 만들지 못했던 줄을 고치면 그 줄의 `validation.ok`가 참이 되어 `publishable`도 따라 바뀐다. 증거조사만 만드는 경우(`full: false`)는 1 · 2차 모두 바뀌지 않는다.
- U0 줄을 고치면 U2가 이미 옮긴 질문과 달라질 수 있다. 이 경우는 `ISSUE_QUESTION_MISMATCH` 경고로 드러나고 관리자가 본다(U0를 고쳐도 U2를 다시 만들지 않는다).

### 리뷰 반영 (PR #355)

- **`repairs`에 고치기 전 · 후 줄**(해송님): 자동으로 고친 줄은 어조 · 뉘앙스가 바뀔 수 있어 관리자가 원문을 봐야 한다. 줄 기록에 `before` · `after` · `lastRejected`(못 고쳤을 때 마지막으로 받지 않은 줄), 단위 재생성 기록에 `errorsBefore` · `errorsAfter`를 더했다.
- **낡음 신호 `affects`**(해송님): U0를 고쳐도 U2 · U4를 다시 만들지 않는데, U4는 설계도 쟁점을 입력으로 받아 경고(`ISSUE_QUESTION_MISMATCH`)만으로는 드러나지 않는다. BE-129 연동 표대로 값이 바뀐 기록에 영향받는 단위를 남긴다(U0 → U2 · U4, U2 → U4). BE-126 저장 쪽이 낡음 표시 · 고치는 순서 안내에 쓴다.
- **받는 기준을 단위 전체로**(해송님): 고친 줄이 이웃 줄과 겹치거나 다른 곳에 오류를 만들면 마지막 전체 검사에서야 드러났다. 그 줄의 오류가 풀리고 단위의 다른 오류가 늘지 않을 때만 받는다(단위 재생성과 같은 기준). 이미 단위 검사를 돌리고 있어 호출이 늘지 않는다.
- **경고 다시 계산**(CodeRabbit): 고친 단위의 `warnings`(BE-107 `validate_line`)가 옛 대사 기준으로 남았다. 줄을 받으면 다시 계산하고, 단위 재생성은 새 결과의 경고를 쓴다.
- **"N년형" 형량 문형**: 해송님 실측에서 형량 숫자 누출 결함을 놓쳤다는 보고가 있었다. 형량 문형 검사(1차 리뷰 반영, 5d0ff31)는 이미 있지만 "징역 · 금고 · 벌금 · 집행유예 + 숫자" 꼴만 봐서 "2년형"처럼 앞말 없이 쓴 형량은 놓친다. 이 꼴을 더했다. 실측에 쓴 문형이 이것인지는 해송님께 확인을 요청했다.

해송님 실측(실제 사건 대본 1건에 결함 17종, 실제 모델, `repairRetries` 2): 검사가 오류로 잡은 10건 모두 고쳐졌다(줄 고쳐 쓰기 1회에 7건 · 2회에 1건, 줄 실패 뒤 U1 재생성 1건, 처음부터 단위 재생성 1건). 호출 13회 · 약 3.7만 토큰(결함 하나당 1.3회), 고친 뒤 새 오류 0건 · 새 경고 1건. 경고 5건은 설계대로 고치지 않았고, 검사가 놓친 결함은 2건(형량 숫자 · 금지어)이다. **`repairRetries` 기본 2를 유지한다.** 경고 기준값은 정상 대본이 더 모인 뒤 정한다(표본 1건 · 결함 17종).

### 추후 재검토가 필요하면

- 검사는 있는 문장만 본다. 빠진 것(레드플래그 누락, 분위기 오분류)은 고쳐 쓰기가 닿지 못하므로 최종 검수 체크리스트의 몫이다(해송님 리뷰).
- 관리자 검수에서 블록을 고친 뒤 다시 만들기(BE-129): `rewrite_line` · `regenerate_unit`을 그대로 쓰거나, 연동 표에 따라 뒤 블록을 낡음(stale)으로 표시하는 쪽과 합친다.
- 블록마다 `review`(BE-126): 고친 블록의 검사 결과만 바꾸려면 블록 저장 쪽에서 블록별 `review`가 필요하다.
- 실제 대본으로 고쳐 쓰기를 돌려 성공률 · 비용을 재고, 경고 기준값(0.5 · 0.6 · 0.8)도 함께 맞춘다.
