# BE-122 의사결정 기록

대본 생성 검수 조건(검증) 구현. 두 PR로 나눈다.

- 1차: 검사 결과 형식(BE-129가 쓰는 계약)과 README "검수 조건" 표의 검사 구현.
- 2차: 줄 단위 고쳐 쓰기 · 단위 재생성.

## 1차 (검사 결과 형식 · 검사)

### 문제 / 배경

- 조립기(BE-121)는 단위를 받을 때 형식(키 · 개수)과 BE-107 `validate_line`(길이 · 금지어)만 본다. README "검수 조건" 표(BE-119 시험에서 나온 위반: 한글 수사, 데이터에 없는 감정, 사실을 주장으로 낮춤, 한쪽 사정만 전함, 줄 수 미달 등)는 구현되지 않았다.
- 해송님 요청(2026-10-29): 단위별 검사 결과를 **오류 목록으로 돌려주는 형식**을 먼저 정해 BE-129가 쓰게 한다. 대본 저장은 단위 블록(U0 ~ U4)으로 바뀌었고(BE-126 댓글 2026-10-30), 관리자는 블록 단위로 고치고 다시 만든다.
- 근거: `tools/ai-judgment/prompts/script/README.md` "검수 조건", [BE-119](BE-119.md) 시험 기록, [BE-121](BE-121.md) "남은 관찰".

### 검토한 대안

#### 1. 결과 형식

- 대안 A: 지금처럼 단위별 문자열 목록(`{"U2": ["2번째 대사: …"]}`). 사람은 읽기 쉽지만, BE-129와 관리자 화면이 문장을 해석해야 어느 줄을 어떻게 고칠지 안다.
- 대안 B(채택): 결과 하나를 객체로 `{unit, path, code, severity, fix, message}`(U3는 `factorId`).
  - `path`는 JSON Pointer다. 블록 값 안의 위치를 가리키므로, 블록 단위 저장(BE-126)과 블록 수정 화면이 그대로 쓴다. 파이썬 · JS · 자바 모두 표준 방식이 있다.
  - `code`는 기계가 고르는 값, `message`는 사람이 읽는 값으로 나눴다. 문구를 고쳐도 집계 · 화면이 깨지지 않는다.
  - `fix`(`line` · `unit`)는 README의 재생성 범위를 결과에 담는다. BE-129가 단위마다 규칙을 다시 알 필요가 없다.

#### 2. 검사를 어디서 돌리나

- 대안 A: 각 단위의 `check_*`(생성 중 재요청 검사)에 넣는다. 걸리면 그 단위를 다시 요청한다. 휴리스틱 검사가 틀리게 걸리면 단위가 끝내 실패해 막 전체가 빠진다(`pending`).
- 대안 B(채택): 생성이 끝난 뒤 따로 돌려 결과 목록만 남긴다(`script_review.review_script`). 생성 중 재요청 검사는 지금 그대로 둔다. 오류가 있으면 대본은 공개할 수 없다(`publishable: false`). 고쳐 쓰기 · 재생성은 2차에서 이 목록을 읽어 한다.

#### 3. 오류와 경고

- README 표의 오류 · 경고 구분을 따랐다. 표에 없는 두 개(증거조사 군더더기, 같은 말 되풀이)는 Jira의 "추가 후보"라 경고로 두었다.
- 원칙: **문장 비교(휴리스틱)인 검사는 모두 경고다.** 오류는 원문 대조 · 공개 범위 · 형식처럼 기계적으로 판단할 수 있는 것만 둔다. 경고는 공개를 막지 않고 관리자가 본다.

#### 4. 한글 수사

- 대안 A: 한글 수 + 단위를 모두 오류로 본다. "한 번 더 살펴 주십시오", "두 사람은", 사건 1 수작업 대본의 "이 세 가지를"까지 걸린다.
- 대안 B(채택): 한글 수사의 값이 입력의 아라비아 숫자와 같을 때만 오류로 본다(원문 "12번" → 대사 "열두 번"). BE-119 6차 시험의 위반(원문 횟수 · 기간을 풀어 씀)을 그대로 잡고, 수를 옮긴 게 아닌 말은 통과한다. 하나("한 번")와 지시어 "이"는 보지 않는다. 입력에 없는 수를 한글로 지어낸 경우는 놓친다.

#### 5. 쟁점 ↔ 신문 질문 대응

- 대안 A: 질문과 쟁점의 낱말 겹침. 정상 대본(시험 고정 값)에서도 걸렸다. 질문은 쟁점 낱말을 되풀이하지 않는다("범행 경위" 쟁점 → "미리 해칠 생각이 있었습니까?").
- 대안 B(채택): 기계적으로 볼 수 있는 두 가지만 본다. U2 질문이 설계도(U0)가 쟁점에 맞춰 정한 앞 두 질문과 같은가(U2 지시가 "design.questions의 앞 두 개만 쓴다"다). 그리고 정신상태 · 진단 · 치료 이력을 묻는가(쟁점 블록이 막는 질문). 뜻의 대응은 관리자 검수 화면에서 본다.

#### 6. 무엇을 입력으로 보나 (숫자 · 감정 · 누출)

- 단위마다 **모델이 실제로 받은 데이터**와 비교한다. U0 · U2 · U4는 공개 단계 `OVERVIEW` · `DETAIL` · `ARGUMENT`의 사건 데이터, U1은 기사, U3는 BE-107 scene_data와 같은 제목 · 개요 · 그 판단 요소다. 입력에 없는 숫자는 `NUMBER_NOT_IN_SOURCE`다.
- 공개 전 정보는 `LAW` · `SUMMARY` 단계와 권고형(`recommended`), AI 판결 형량(`prisonMonths` · `suspensionMonths` · `fineAmount`)이다. 여기서 온 숫자 · 낱말은 `VERDICT_LEAK`로 따로 본다. 낱말 목록에 "무죄"는 넣지 않았다. 부인 사건의 변호인 입장("무죄를 주장합니다")은 판결이 아니다.

### 선택한 방법과 이유

- 새 모듈 `tools/ai-judgment/script_review.py`. `generate_units`가 끝에 `review_script`를 돌려 `review`를 남기고, `build_script`가 대본에 `review`를 싣고 오류가 있으면 `publishable: false`로 둔다. 파이프라인은 결과를 로그로 남기고 `reviewErrors` · `reviewWarnings`를 단계 출력에 더한다. 서비스 결과(`fullScript.review`)에는 그대로 실린다.
- `evidence.json`(BE-108 적재 계약)은 바꾸지 않았다. U3 결과도 대본의 `review`에만 들어간다.
- 형식 · 검사 목록은 README "검수 조건" · "검수 결과 형식"이 기준이다. 코드 상수(`CODES`)는 그 표를 옮긴 것이다.

### 고려한 제약 사항

- 파이프라인 도구는 표준 라이브러리만 쓴다. 형태소 분석기 없이 낱말 비교는 "두 글자 이상 낱말에서 끝 조사 하나를 뗀 것"으로 대략 본다.
- 실제 생성 대본은 실제 사건 내용이라 저장소에 없다. 오탐은 시험 고정 값과 사건 1 수작업 대본(`frontend/src/content/case-1/script.json`)으로만 확인했다. 수작업 대본에서 한글 수사 오탐 1건("이 세 가지")을 찾아 지시어 "이"와 단위 "세 · 일"을 뺐다. **실제 모델 출력으로 오탐 · 미탐 비율을 재지는 않았다.**

### 추후 재검토가 필요하면

- 2차: `fix`에 따라 줄 고쳐 쓰기(실패한 줄만 앞뒤 대사와 함께 보내기) → 정해진 횟수를 넘기면 단위 재생성.
- 휴리스틱 검사(주장 문형 · 한쪽 사정 · 되풀이)의 기준값(낱말 겹침 0.5 · 0.6 · 0.8)은 실제 대본으로 다시 맞춘다. 오탐이 많으면 경고를 줄이고, 놓침이 많으면 프롬프트 쪽을 먼저 보강한다.
- 기사(PAPER)는 검사하지 않는다. 기사는 API 17이 단일 출처이고(BE-126 댓글), 형식 · 금지어는 `check_paper`가 본다.
