# FE-9 의사결정 기록

> MVP 단계(WBS 3.7) · PR #48 · 담당 백승호

## 문제 / 배경
- 와이어프레임 S-09(세 판결 비교) 화면을 BE-11(API 14)이 완성되기 전에 mock으로 먼저 구현해야 했다.
- "내 판결" 데이터가 화면마다 따로 흩어지지 않고, 사용자가 S-03(사전 판단)·S-06(제출 판결)에서 실제로 입력한 값과 S-09에서 일치해야 했다.

## 검토한 대안
- **내 판결 데이터의 출처**: S-09 화면에서 쓸 "내 판결"을 그때그때 다시 계산할지, S-03·S-06에서 입력한 값을 저장해 두고 그대로 가져다 쓸지 검토했다.
- **완료 전 상태로 S-09에 직접 진입하는 경우의 처리**: 에러를 보여줄지, 현재 진행 단계에 맞는 화면으로 자동 안내할지 검토했다.

## 선택한 방법과 이유
- 정상 진행에서는 S-06 제출 판결(형벌값 + 판단 요소)과 S-03 사전 판단(구간 + 요소)을 목(mock) 저장소에 보존해 S-09의 "내 판결" 데이터가 실제 입력값과 일치하도록 했다. 화면마다 별도로 값을 다시 만들면 사용자가 실제로 고른 값과 비교 화면에 보이는 값이 어긋날 위험이 있었다. 다만 `jumpActMock(8)` 같은 목 전용 바로가기처럼 저장값이 없는 경로에서는 S-09가 `fallbackPreJudgment`·`fallbackMyJudgment`를 사용하므로 실제 입력값과 다를 수 있다.
- 완료 전 상태에서 S-09에 직접 진입하면 공통 래퍼가 `INVALID_STATE` 오류의 `currentStatus`를 `screenByStatus`에 적용해 현재 단계 화면으로 자동 안내하도록 했다. 이미 BE-10/FE-8에서 쓰던 상태 기반 라우팅 방식과 일관되게 맞췄다.
- 형량 막대, 변화 유형 카드, AI 비교 분석, 체험 후 안내 문구는 확장 범위로 보고 이번 PR에서 제외했다.

## 고려한 제약 사항
- BE-11(API 14)이 이 PR 시점에 아직 머지 전이라, mock 연동으로 먼저 화면을 완성하고 실제 API로 교체하는 순서로 진행했다. 이때 API 14의 응답 형식(`judgments`가 `{USER, AI, COURT}` 키를 가진 객체)에 맞춰 mock 데이터 구조를 설계했다.
