# BE-58 의사결정 기록

> 확장 단계(WBS 7.1.1) · PR #114 · 담당 정민석

## 새로 도입한 기술 (선택)

### Docker 멀티스테이지 빌드
- 무엇인가: 하나의 Dockerfile 안에 여러 `FROM` 단계를 두어, 빌드에만 필요한 도구(Node.js 등)는 중간 단계에 남기고 최종 이미지에는 빌드 산출물만 담는 방식. Docker 공식 기능이다.
- 동작 원리: 1) 빌드 단계에서 Vite로 정적 파일을 생성 → 2) 실행 단계(Nginx 이미지)로 그 결과물만 복사 → 3) 최종 이미지에는 Node.js·소스·개발 의존성이 남지 않는다.
- 우리 프로젝트에서: `frontend/Dockerfile`. 빌드 단계에서 `VITE_API_MODE=real`을 고정해, 목(mock) 데이터 모드로 빌드되는 사고를 막는다.
- 주의할 점: 빌드 인자(ARG/ENV)가 빌드 단계와 실행 단계 중 어디에 적용되는지 헷갈리기 쉽다. 실 모드 고정처럼 "반드시 이 값으로 빌드되어야 하는" 설정은 빌드 단계에 명시적으로 둬야 한다.
- 참고: [Docker 멀티스테이지 빌드 공식 문서](https://docs.docker.com/build/building/multi-stage/)

### Nginx SPA fallback + `/api` 프록시
- 무엇인가: SPA(Single Page Application)는 화면 주소가 실제 파일이 아니므로, 존재하지 않는 경로 요청을 전부 `index.html`로 돌려보내 클라이언트 라우터가 처리하게 하는 구성. `/api`만은 예외로 백엔드로 그대로 넘겨야 한다.
- 동작 원리: Nginx `location`별로 우선순위를 둬서, `/api`로 시작하는 요청은 백엔드로 프록시하고 나머지 화면 경로 요청은 `try_files`로 `index.html`에 떨어지게 한다.
- 우리 프로젝트에서: `frontend/nginx/default.conf`(이후 BE-75에서 `frontend/nginx/snippets/app.conf`로 공용 분리). `/api`가 SPA fallback에 가로채여 index.html을 반환하지 않도록 순서를 맞춘 것이 핵심이다.
- 주의할 점: `/api`와 화면 fallback 규칙의 순서·우선순위(`^~`, `=` 등)를 잘못 두면 API 요청이 HTML(index.html)로 새어 나가거나, 반대로 화면 라우트가 404가 날 수 있다.
- 참고: [Nginx `location` 매칭 우선순위 공식 문서](https://nginx.org/en/docs/http/ngx_http_core_module.html#location)

### GHCR(GitHub Container Registry)
- 무엇인가: GitHub가 제공하는 컨테이너 이미지 저장소. GitHub Actions에서 바로 이미지를 올리고 받을 수 있다.
- 동작 원리: develop 브랜치 머지 → 스모크 테스트를 통과한 이미지만 `ghcr.io/prgrms-aibe-devcourse/lawnambul-web`·`-backend`로 업로드. 태그는 `develop`과 `sha-커밋7자리` 두 가지를 쓴다.
- 우리 프로젝트에서: `.github/workflows/deploy-images.yml`. PR에서는 이미지를 빌드·실행·스모크 테스트만 하고 업로드하지 않으며, develop 머지 시에만 업로드한다.
- 주의할 점: 패키지가 기본 비공개(private)라 서버가 받아올 때 로그인 토큰이 필요하다(BE-60에서 다룸). 머지 후 공개 전환을 검토 과제로 남겼다.
- 참고: [GHCR 공식 문서](https://docs.github.com/ko/packages/working-with-a-github-packages-registry/working-with-the-container-registry)

### docker-compose 오버레이 구성
- 무엇인가: 기본 compose 파일에 서버 전용 설정을 덧붙이는 추가 파일(`-f` 여러 개 지정)을 따로 두는 방식.
- 동작 원리: 기본 `deploy/docker-compose.prod.yml` 위에 `deploy/docker-compose.real-seed.yml`을 덧붙이면 실제 사건 seed 폴더가 읽기 전용으로 추가 마운트된다. 덧붙이지 않으면 기본 구성(스키마만, 사건 0건)으로 뜬다.
- 우리 프로젝트에서: `deploy/docker-compose.prod.yml` + `deploy/docker-compose.real-seed.yml`. 경로가 없으면 real-seed 쪽은 기동을 거부한다.
- 주의할 점: 오버레이 조합이 늘어나면(BE-75의 `MONITORING_AGENT` 등) 서버에서 compose 명령을 다시 조립하는 스크립트가 조합을 놓치기 쉽다 — 라벨 기반 식별 등으로 보완한 사례는 `docs/decisions/BE-75.md` 참고.
- 참고: [Docker Compose 다중 파일(`-f`) 공식 문서](https://docs.docker.com/compose/how-tos/multiple-compose-files/merge/)

## 문제 / 배경
- WBS 7.1.1(EC2·Docker·Nginx 배포, 도메인 확보) 중 EC2에 올리기 전 필요한 구성(이미지, Nginx, compose, 스모크 테스트, CI 파이프라인)을 먼저 올려야 했다. EC2 반영 자체는 10/15~16 후속 PR로 분리했다.
- 운영에서 처음 뜨면 사건 데이터가 없는 문제, 익명 ID 쿠키(`NLNB_AID`)가 `Secure`라 http에서는 체험 흐름이 막히는 문제(HTTPS 전 제한), 도메인 미확보 문제를 같이 정리해야 했다.

## 검토한 대안
- **EC2 반영을 같은 PR에 포함할지**: 이미지·compose·CI까지 한 번에 묶으면 리뷰 범위가 커지고 되돌리기도 어려워진다. 구성(이 PR)과 EC2 반영(후속 PR)을 나누기로 했다.
- **도메인 후보 조사(RDAP)**: `lawnambul`·`naelawnambul`·`naeronambul`·`nelonambul`을 `.com`·`.kr`·`.co.kr`·`.net`·`.app`/`.dev`/`.site`로 조회했다. 모두 미등록이었으나 최종 가격·구매 가능 여부는 등록업체 확인이 필요해 결정을 미뤘다(최종 도메인 결정은 BE-75).
  - 10/16까지 못 정하면 무료 하위 도메인(DuckDNS)으로 임시 HTTPS를 여는 대안도 함께 제시했다(실제로는 쓰지 않음).
- **real-seed 데이터를 이미지에 포함할지, 별도 마운트로 둘지**: 이미지에 포함하면 비공개 데이터가 이미지 레이어에 들어가 버린다. 서버 전용 compose 오버레이로 읽기 전용 마운트하는 쪽을 택했다.

## 선택한 방법과 이유
- `frontend/Dockerfile`은 실 모드(`VITE_API_MODE=real`)로 고정 빌드한다 — 목 데이터로 빌드된 이미지가 운영에 올라가는 사고를 원천 차단한다.
- `/api`는 프록시, 화면 경로는 SPA fallback이 되도록 Nginx location 순서를 맞추고, 없는 API 경로는 HTML이 아닌 404 JSON으로 응답하게 했다 — 프론트 에러 처리(FE-2)가 일관되게 JSON을 기대하기 때문이다.
- 운영 compose는 외부로 여는 포트를 80 하나로 제한하고, DB 비밀번호가 없으면 기동 자체를 거부하게 했다 — 설정 누락으로 무방비 상태의 DB가 뜨는 것을 막는다.
- 운영은 "스키마만" 기본값으로 둔다(`FLYWAY_LOCATIONS` 고정) — 실제 사건 데이터는 비공개 저장소 seed를 `docker-compose.real-seed.yml`로 연결해야만 들어오게 했다.
- `deploy/smoke-test.sh`를 CI와 서버(EC2)가 공유한다 — `/`·화면 주소·`/api`(없는 경로도 JSON)·캐시 정책을 같은 기준으로 검증해, "CI는 통과했는데 서버는 다르다"는 괴리를 없앴다.
- GHCR 업로드는 develop 머지 + 스모크 테스트 통과를 조건으로 했다 — PR 단계에서는 빌드·실행·테스트만 하고 업로드하지 않아, 머지되지 않은 이미지가 레지스트리에 쌓이지 않게 했다.

## 고려한 제약 사항
- 서버가 HTTPS 전이라 익명 ID 쿠키(`NLNB_AID`, `Secure`)가 http에서 저장되지 않는다. `/`와 조회 API는 동작하지만 체험 흐름(체험 시작 이후)은 도메인·인증서 확보(BE-75) 전까지 막혀 있었다.
- 실제 사건 seed는 비공개 저장소에 있어 접근 권한이 있는 사람만 연결할 수 있다.
- 프론트·백엔드 PR마다 이 워크플로가 함께 돌아 CI 시간이 늘어난다(백엔드 이미지가 backend CI와 두 번 빌드됨, 캐시로 완화). 길어지면 backend CI 쪽 이미지 빌드 확인을 빼는 것을 후속 검토 과제로 남겼다.
- Spring의 `X-Forwarded-For` 신뢰 설정(실제 사용자 IP 확인)과 정적 파일 보안 헤더·HSTS는 이 이슈 범위 밖이며 각각 7.4.6(Rate limit)·HTTPS 작업으로 넘겼다.

## 추후 재검토가 필요하면
- GHCR 패키지를 공개로 전환하면 서버 로그인 토큰 관리가 필요 없어진다(BE-60에서 실제로 비공개 상태로 운영 중 — `docs/decisions/BE-60.md` 참고).
- 도메인·HTTPS·Rate limit(443 server 블록)은 각각 BE-75·BE-63 이후로 이어졌다.
