# BE-78 의사결정 기록

## 1차 (사건 1 썸네일)

### 문제 / 배경
- FE-32(#152)에서 사건 1 썸네일을 목 데이터만 재연 일러스트(`/images/cases/case-1-reenact.webp`)로 바꿨다. 실제 API(API 1 · 16)는 시드 값이 `NULL`이라 프론트가 공용 재연 컷으로 대신 보여 준다.
- 사건 1은 개발용 가상 시드(`db/seed/R__seed_sample_case.sql`)다. 이 시드는 "이미 사건이 있으면 건너뛰기" 구조라 INSERT 값만 바꾸면 이미 사건이 들어간 로컬 DB에는 반영되지 않는다.

### 검토한 대안
- 대안 A: INSERT 값만 바꾼다. 변경은 가장 작지만, 팀원마다 로컬 DB를 비우고(`docker compose down -v`) 다시 넣어야 반영된다.
- 대안 B: INSERT 값을 바꾸고, 건너뛰기 검사 앞에 "사건 1 썸네일이 비어 있으면 채우는" UPDATE를 둔다. 서버를 다시 띄우면 기존 로컬 DB에도 반영된다.

### 선택한 방법과 이유
- 대안 B. 같은 파일의 요약어 변경(BE-26)도 같은 방식(UPDATE 먼저 → 건너뛰기)을 썼다.
- `thumbnail_url IS NULL`일 때만 채워, 관리자 화면(A-11 사건 수정)에서 바꾼 값은 덮어쓰지 않는다.

### 고려한 제약 사항
- 개발용 시드라 운영 DB에는 들어가지 않는다(`FLYWAY_LOCATIONS`에 `db/seed`를 켠 로컬 · CI만).
- 반복 마이그레이션(R__)은 파일 내용이 바뀔 때만 다시 실행된다. 관리자가 썸네일을 지운(`NULL`) 뒤 시드 파일이 다시 바뀌면 다시 채워진다(개발용이라 감수).

### 추후 재검토
- 2차(사건별 재연 컷 파일명 규칙 · 자동 매칭)는 사건별 재연 컷 제작(7.6.8) 뒤에 이 파일에 이어 적는다. → 2차에서 파일명 자동 매칭은 하지 않기로 했다(아래 "매칭 원칙").

## 2차 검토 (2026-10-21 — 이미지 역할 · 매칭 정책)

### 문제 / 배경
- 1차 이후 사건별 이미지의 역할과 데이터 연결 범위를 정리할 필요가 있었다. 1차의 "자동 매칭"은 당시 남긴 후속 검토 항목이며, 파일명을 파싱하는 기능을 도입한다는 결정이 아니다.
- 그사이 BE-91(사진 저장 · 관리자 업로드), BE-92(신문 지면 콘텐츠), FE-63(프론트 사진 3장 구조 · fallback)이 머지되어, 이미지 구조의 대부분이 정해졌다.
- 이 기록은 머지된 코드로 **확인된 사실**과 BE-91 담당과 **합의한 정책**을 나눠 적는다. BE-78에서는 코드 · API · 스키마를 바꾸지 않는다.

### 확인된 사실 — 현재 구현
- 조사 기준: `develop`의 `6fa3c1a`(#217 머지 커밋). [PR #202](https://github.com/prgrms-aibe-devcourse/AIBE7_FinalProject_Team2/pull/202)(BE-91) · [PR #212](https://github.com/prgrms-aibe-devcourse/AIBE7_FinalProject_Team2/pull/212)(BE-92) · [PR #217](https://github.com/prgrms-aibe-devcourse/AIBE7_FinalProject_Team2/pull/217)(FE-63) 머지 후.
- **화면의 사진 자리는 사건당 3개다(대표 · 발단 · 결론, FE-63).** 화면 구조를 말하며, DB에 3장 제한이 있다는 뜻은 아니다(`case_incident_photo`는 여러 행을 저장할 수 있고 `display_order`에 최대값 제약이 없다).

| 사진 | 화면에서 쓰는 곳 | 저장 위치 |
| --- | --- | --- |
| 대표 | 사건 목록 · 메인 신문 · 기사 지면 큰 사진 | `legal_case.thumbnail_url` (API의 `thumbnailUrl`). 사건 1은 1차 시드 |
| 발단 | 기사 지면 작은 사진 1 + 증거조사 **변호인 측** 사진 | `case_incident_photo` |
| 결론 | 기사 지면 작은 사진 2 + 증거조사 **검사 측** 사진 | `case_incident_photo` |

- 증거조사 사진은 실제 증거자료가 아니라 발단 · 결론 재연 사진을 함께 쓴다. 변호인 측 = 발단, 검사 측 = 결론은 FE-63 리뷰 반영(`b33d799`)에서 정했다. 처음 안의 반대이며, 의도한 변경임은 FE-63 담당에게 확인했다(근거 문구는 FE-63 기록에 없음).
- **사진이 없거나 로딩에 실패하면 프론트가 공용 컷으로 바꾼다(FE-63).** 공용 컷도 실패하면 사진을 뺀다. 발단 · 결론 자리는 자리별 공용 컷을 쓰고, `extraPhotos`가 없는 사건도 같은 모양을 유지하도록 공용 컷으로 채운다. 공용 컷 분류 · 추가는 FE-65에서 다룬다. 서버는 fallback을 내려 주지 않는다.
- **발단 · 결론 사진(BE-91, V19):** `case_incident_photo`는 사건 ID · 이미지 URL · S3 키 · 캡션 · 프롬프트 · `display_order`를 저장한다. 발단 · 결론을 구분하는 칸은 없다.
  - 테이블 · API 경로 이름(`case_incident_photo`, `/photos/incident`)은 "발단(incident)"이지만, 이 결정 이후 발단 · 결론 사진을 모두 담는다. 이름은 바꾸지 않는다.
  - `display_order`는 업로드할 때마다 0부터 1씩 늘어난다(`countByLegalCaseId`). 삭제 · 교체 · 순서 변경 API는 없다.
  - 사건이 공개된 뒤에는 대표 · 발단 사진 모두 업로드할 수 없다(`guardNotPublished`).
- **신문 지면(BE-92):** `photo`는 `legal_case.thumbnail_url`, `extraPhotos`는 `case_incident_photo` 전부를 `display_order` 순서대로 내려준다. 사진을 따로 저장하지 않는다.
- **공개 API는 없다.** 사진 · 신문 지면은 관리자 API(A-13-1 ~ 8)로만 조회된다. 사용자 화면은 아직 대본(`script.json`)의 경로와 `casePhoto()`를 쓰며, 서버 연동은 FE-64에서 다룬다.
- 실제 DB · S3 연동 결과와 화면 표시는 이번 조사에서 검증하지 않았다.

### 매칭 원칙
- **파일명 추측 대신 명시적 관계를 쓴다.** 파일명은 제작 · 검수 편의를 위한 이름일 뿐이고, 화면은 사건 ID와 DB 관계로 사진을 찾는다. 파일명 자동 파싱 · 매칭 기능은 만들지 않는다.
- **같은 사진을 두 곳에 저장하지 않는다.** 대표는 `thumbnail_url`, 발단 · 결론은 `case_incident_photo` 한 곳에만 두고, 신문 지면 · 증거조사는 이를 가져다 쓴다(BE-92와 같은 원칙).
- 정적 이미지와 서버 이미지가 함께 있는 동안 기존 동작(대본 경로 · `casePhoto()`)은 FE-64 전까지 유지한다.

### 확정 사항 (2026-10-21 BE-91 담당과 합의)
- **발단 · 결론 구분은 역할 칸으로 한다.** `case_incident_photo`에 `role`(`ORIGIN` · `CONCLUSION`, CHECK)을 추가하고 `UNIQUE (case_id, role)`로 사건당 역할별 1장을 보장한다. 같은 역할로 다시 올리면 기존 행을 교체(UPDATE)한다. 한 장만 빼는 삭제 API(A-13-9)도 둔다.
  - 교체 · 삭제 때 이전 S3 객체를 지울지 남길지는 후속 이슈 1번에서 정한다. 지금 업로드 키에는 시각이 붙어 매번 새 키가 되므로, 교체해도 캐시 때문에 옛 사진이 보이지는 않는다.
  - `display_order` 약속(0 = 발단, 1 = 결론)은 택하지 않았다. 지금 순번이 "그 사건 사진 개수"로 매겨져 삭제가 생기면 유니크와 겹치고, DB에 흔적이 없는 약속이라 FE · BE 문서가 늘 같이 맞아야 하기 때문이다. BE-92 기록의 "용도 구분 칸 검토"와도 같은 방향이다.
- **마이그레이션은 세 번의 배포로 나눈다(BE-60 규칙: main으로 가는 마이그레이션은 추가만).** `ddl-auto: validate`라 칸을 지운 채 이전 앱으로 되돌아가면 이전 앱이 뜨지 못한다. 배포가 실패하면 바로 앞 단계의 앱으로 되돌아가므로, 각 단계의 스키마는 **바로 앞 단계의 앱**이 뜰 수 있어야 한다.
  - 1단계: `role` 추가(NULL 허용) + CHECK + `UNIQUE (case_id, role)` + 백필(`display_order` 0 → `ORIGIN`, 1 → `CONCLUSION`). `display_order`는 남기고, 새 코드가 `ORIGIN` = 0 · `CONCLUSION` = 1로 계속 채운다. PostgreSQL 유니크는 NULL을 중복으로 보지 않아 역할 없는 행이 여럿이어도 된다.
  - 1단계 마이그레이션과 "역할 없는 행은 지면 · 공개 응답에서 뺀다"는 코드(BE-92 `extraPhotos` 조회 변경 포함)는 같은 PR · 같은 배포로 묶는다. 마이그레이션은 새 앱이 뜰 때 실행되므로 둘이 따로 나가지 않는다. 1단계 뒤 이전 앱으로 되돌아가도 이전 앱은 지금처럼 전부 내려 줄 뿐 오류는 없다.
  - 2단계(1단계가 안정된 뒤의 배포): `display_order`의 NOT NULL만 푼다(호환 변경). 코드는 `display_order`를 더 이상 읽지도 쓰지도 않고 항상 `role`을 채운다. 되돌아가도 1단계 앱은 `display_order`를 계속 채우므로 뜬다.
  - 3단계(2단계가 안정된 뒤의 배포): `display_order`와 `(case_id, display_order)` 유니크 삭제, `role` NOT NULL. 되돌아갈 2단계 앱은 `display_order`를 쓰지 않고 `role`을 항상 채우므로 뜬다.
  - 처음 합의는 두 단계(칸 삭제를 바로 다음 배포에서)였으나, 그러면 칸을 지운 배포가 실패할 때 되돌아갈 1단계 앱이 `display_order`를 써서 뜨지 못한다(#222 리뷰). 그래서 "코드가 칸을 안 쓰게 하는 배포"를 사이에 둔다.
  - `display_order` 2 이상 행은 `role` NULL로 둔다. 지면 · 공개 응답에는 역할이 있는 행만 발단 · 결론 자리에 내려 주고, 관리자 목록(A-13-5)에는 `role: null`로 보여 정리 대상을 드러낸다. 3단계 전에 역할 없는 행 수를 확인하고, 남아 있으면 사람이 삭제하거나 역할을 지정해 다시 올린다. 마이그레이션에 DELETE는 넣지 않는다(BE-60 "데이터 손상 위험이 있는 변경은 사람이 판단").
  - 참고: 1단계 배포 뒤 발단을 삭제한 상태에서 이전 앱으로 롤백되면, 이전 앱은 다음 순번을 사진 개수로 매겨 결론과 유니크가 겹칠 수 있다. 롤백 중 업로드 한 번이 실패하는 정도라 막지 않는다.
- **승인은 사건 공개로 갈음한다.** 사진별 승인 칸은 두지 않는다. 공개된 사건은 사진 업로드가 거부되고(`guardNotPublished`), 공개 전 사건에서 업로드하면 사건이 검토 중(`REVIEW`)으로 바뀐다(`startReview()`). 사진을 바꿀 수 있는 건 공개 전뿐이라 공개 처리가 승인 역할을 한다. 공개 뒤 사진 교체는 아래 후속 이슈 3번(선택)에서 따로 정한다. 공개 조회는 API 16과 같은 기준으로 비공개 사건이면 404.
- **공개 API는 신문 지면과 묶어 하나로 둔다.** 예: `GET /cases/{caseId}/paper`가 `headline` · `deck` · `photo` · `caption` · `article`과 발단 · 결론 사진을 함께 내려 준다.
  - **발단 · 결론 사진은 배열이 아니라 고정 자리로 내려 준다**(예: `{ origin, conclusion }`, 없으면 `null`). FE-63의 `extraPhotosOf`는 배열 위치로 발단 · 결론을 정하므로, 역할이 있는 행만 배열로 내려 주면 발단을 지운 사건에서 결론 사진이 발단 자리로 밀린다(#222 리뷰). FE-63 기록의 "필드 이름을 `origin` · `conclusion`으로 바꿀지 FE-64에서 정한다"와 같은 방향이다. 구체 필드 이름은 후속 이슈 2번에서 API 명세와 함께 정한다.
  - 증거조사 사진도 같은 두 장이라 별도 API를 두지 않는다. API 6(체험 단계 공개)에는 섞지 않는다 — 사진은 단계 잠금과 무관한 자산이다. 체험 화면의 호출 흐름은 FE-64와 정한다.

### 후속 이슈 (BE-91 담당)
1. 역할 칸 1단계 + 업로드 교체 + 삭제 API(A-13-9) + API 명세 · ERD 갱신 — 공개 API 응답에 `role`이 필요해 가장 먼저 한다.
2. 공개 신문 지면 · 사진 조회 API(발단 · 결론 고정 자리) — FE-64의 선행 작업.
- FE-64에서 할 일: 신문 지면 작은 사진과 증거조사 사진을 서버 사진으로 바꾼다. 지금 `evidenceBoard()`는 대본의 `evidencePhotos`를 공용 컷보다 먼저 쓰므로, 서버 사진으로 대체하거나 대본 경로를 지운다.
3. (선택) 공개된 사건의 사진 교체 허용 여부 — 지금은 공개 뒤 잘못된 사진을 고칠 경로가 없다. → **BE-103에서 결정(2026-10-28)**: 공개 중 교체 경로는 두지 않고, BE-118이 추가한 공개 취소(A-13-14) → 교체 → 다시 공개(A-13)를 절차로 삼는다. 코드 변경 없음(`docs/decisions/BE-103.md`).
- 역할 칸 2단계(NOT NULL 풀기 · 코드에서 `display_order` 제거)와 3단계(칸 삭제 · `role` NOT NULL)는 1번 이후 각각 다음 배포에서 한다.

### 이번 검토의 범위와 한계
- 1차 기록은 그대로 두고 2차만 추가했다. API · DB 스키마 · 프론트 코드는 바꾸지 않았다.
- 이 기록은 사용자 화면 연동 완료를 뜻하지 않는다. 구현은 위 후속 이슈에서 한다.
