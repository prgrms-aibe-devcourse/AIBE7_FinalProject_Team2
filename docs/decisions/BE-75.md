# BE-75 의사결정 기록

## 문제 / 배경
- 7.1.1(BE-58)에서 분리한 남은 범위: 도메인 확보 · HTTPS 적용. 도메인은 `naelawnambul.today`(가비아, `@` · `www` A 레코드 → 운영 탄력적 IP)로 확보했다.
- https가 없으면 `Secure` 쿠키(`NLNB_AID`, 관리자 세션)를 브라우저가 저장하지 않아 체험 흐름 · 관리자 로그인이 운영에서 동작하지 않는다. BE-62(카카오 로그인)도 https Redirect URI가 필요해 이 작업에 막혀 있다. M2(10/23) 전 필요.
- 지켜야 할 기존 구조
  - Nginx는 별도 컨테이너가 아니라 웹 이미지(`frontend/Dockerfile`) 안에 설정이 구워져 있고, 운영 반영은 PR → `main` → 서버 자동 배포(BE-60)로만 한다(서버 파일 직접 수정 금지).
  - CI와 서버의 `deploy.sh`는 `http://localhost`로 스모크 테스트하고, 실패하면 직전 이미지로 되돌린다. 되돌릴 때는 **새 커밋의 Compose · 스크립트로 옛 이미지**를 띄운다.
  - Rate limit(BE-63)은 https server에도 똑같이 걸려야 한다.

## 검토한 대안
- 대안 A: `default.conf`에 443 server를 고정으로 추가
  - 인증서 파일이 없는 CI · 로컬 · 발급 전 서버에서 `ssl_certificate`를 못 읽어 Nginx가 뜨지 않는다 → CI 실패, 서버는 배포가 되돌려진다. 탈락.
- 대안 B: 모든 http 요청을 https로 이동
  - `deploy.sh` · CI 스모크 테스트(`http://localhost`)가 301을 받아 실패한다. 탈락.
- 대안 C: certbot을 Compose 서비스(컨테이너)로 추가
  - 일반적인 예제 구성이지만, 갱신 스케줄(cron 등)을 서버에 따로 만들어야 하고 Compose를 서버 개별 설정에 의존하게 만든다. 서버 호스트의 certbot(apt)은 systemd 타이머 · 갱신 훅이 기본으로 딸려 와 설치만 하면 된다.
- 대안 D: ALB + ACM
  - 인증서 관리는 쉽지만 비용이 생기고, 앞단이 바뀌어 Rate limit 기준 IP(`$binary_remote_addr`)가 ALB IP로 묶인다(real_ip 설정 필요). 한 대 구성 · 일정에 비해 범위가 크다.
- 대안 E: IP 주소 인증서 (도메인 없이)
  - 유효기간이 짧고(수일) 도구 지원이 적다. 도메인을 확보했으므로 불필요.

## 선택한 방법과 이유
- **인증서가 있을 때만 https를 켜는 Nginx** (대안 A · B의 문제를 피함)
  - 공식 nginx 이미지의 시작 단계(`/docker-entrypoint.d/`)에 `40-enable-https.sh`를 두어, `SERVER_DOMAIN` + `/etc/letsencrypt/live/<도메인>/` 인증서가 있을 때만 `https.conf.template`으로 `conf.d/https.conf`를 만든다. 없으면 지금처럼 http만 뜬다 → CI · 로컬 · 발급 전 서버 · 되돌림 모두 그대로 동작.
  - 스크립트는 어떤 경우에도 0으로 끝낸다. 실패시키면 http 서비스까지 내려가고 자동 배포가 되돌림을 반복하기 때문이다. 대신 로그에 경고를 남긴다.
  - 템플릿은 공식 이미지가 자동 처리하는 `/etc/nginx/templates/`가 아닌 `/etc/nginx/lawnambul/`에 둔다(거기 두면 인증서 확인 없이 만들어진다).
  - 도메인 값은 설정 파일에 그대로 들어가므로 소문자 · 숫자 · 점 · 하이픈만 허용한다.
- **도메인 요청만 https로 이동**: `default_server`(server_name `_`)는 localhost · IP 요청을 http로 그대로 받는다. 도메인 server(템플릿)만 301 이동 → 스모크 테스트 경로를 바꾸지 않는다.
- **주소를 `https://<도메인>` 하나로**: http(루트 · www)와 `https://www`를 모두 `https://<도메인>`으로 301 이동한다. 쿠키(익명 ID · 관리자 세션)가 호스트 단위라 www · 루트를 섞어 쓰면 같은 사람이 익명 ID를 둘 갖게 되고, 카카오 Redirect URI(BE-62)도 하나로 맞춘다. 이동 주소는 `$host`가 아닌 고정 도메인이라 요청 헤더 값이 `Location`에 들어가지 않는다.
- **모르는 이름의 TLS는 거절**: 443에 `ssl_reject_handshake on`인 `default_server`를 둔다. 도메인 server 하나만 있으면 IP 직접 접속이나 남의 도메인을 우리 IP로 돌린 요청에도 우리 인증서 · 앱이 응답한다(스캐너가 인증서로 도메인을 알아내고, 다른 이름으로 서비스를 띄울 수 있다). http의 기본 server는 스모크 테스트 때문에 그대로 둔다.
- **앱 location을 snippet 하나로**: `/api` 프록시 · Rate limit · SPA fallback을 `snippets/app.conf`로 옮기고 80 · 443 server가 같이 include한다. BE-63에서 걱정한 "443에 limit_req 누락"이 구조적으로 생기지 않는다. zone은 http 블록 설정이라 `default.conf`에 남긴다.
- **인증서는 서버 호스트 certbot(webroot)**: 웹 컨테이너는 `/etc/letsencrypt`의 `live/` · `archive/`(live의 링크가 archive를 가리켜 둘 다 필요)와 `/var/www/certbot`만 읽기 전용으로 붙인다. certbot 계정 키(`accounts/`)와 갱신 설정(`renewal/`)은 컨테이너에 넣지 않는다 — 웹 컨테이너가 뚫려도 계정 키로 인증서를 폐기 · 재발급할 수 없게 하는 최소 권한이다. 갱신 뒤 Nginx reload는 certbot deploy 훅(`deploy/https/reload-web.sh`)이 한다. 훅은 Compose 라벨로 웹 컨테이너를 찾는다 — overlay 조합(`MONITORING_AGENT` · `REAL_SEED_DIR`)에 따라 달라지는 compose 명령을 다시 조립하지 않기 위해서다.
- **Compose 볼륨 기본값은 빈 이름 있는 볼륨**: `.env`에 경로가 없으면(CI · 로컬) `letsencrypt-live` · `letsencrypt-archive` · `certbot-webroot` 볼륨이 붙는다. 상대 경로 기본값(`./certbot/...`)은 저장소 안에 root 소유 빈 폴더를 만들어서 피했다.
- **스모크 테스트에 확인 경로 검사 추가**: `/.well-known/acme-challenge/`가 SPA fallback(200 + index.html)으로 새면 발급 · 갱신이 실패한다. 다만 서버의 되돌림은 새 스크립트로 BE-75 이전 이미지(이 경로가 없음)를 검사하므로, 기본은 경고만 하고 CI에서만 `SMOKE_REQUIRE_ACME=1`로 실패 처리한다. 실패로 두면 이 PR 이후 BE-75 이전 이미지로의 되돌림이 항상 실패한다.

## 고려한 제약 사항
- 서버 한 대(t3.small), 앞단 장비 없음 → Nginx가 TLS를 직접 처리.
- 서버 파일 직접 수정 금지(BE-60 CD) → 설정은 이미지 · Compose로, 서버에서는 `.env` 값 추가 · certbot 설치 · 훅 복사만 한 번 한다(deploy/README.md "HTTPS").
- 로컬 Docker로 CI와 같은 전체 구성(web · backend · postgres · redis)을 띄워 확인했다: CI 모드 스모크 테스트 통과, 테스트용 자체 서명 인증서(certbot과 같은 `live/` → `archive/` 링크 구조)로 https 활성화 · 도메인 http → https 이동 · 실제 백엔드 응답 · https Rate limit(JSON 429) · 갱신 훅 reload · 인증서 제거 후 재시작 시 http만 뜨는지, BE-75 이전 웹 이미지로 되돌렸을 때 서버 모드는 통과(경고) · CI 모드는 실패하는지. 실제 Let's Encrypt 발급은 서버에서만 확인할 수 있다(deploy/README.md "HTTPS").

## 추후 재검토가 필요하면
- HSTS: 갱신이 한 번 이상 정상으로 돈 뒤 짧은 `max-age`부터 켠다. 켠 뒤 인증서가 깨지면 사용자가 `max-age` 동안 접속하지 못하므로 지금은 켜지 않았다.
- `server.forward-headers-strategy=native`: deploy/README.md "Rate limit"의 사용자 IP 확인 뒤 D가 켠다(순서 유지, 이 이슈 범위 아님).
- 앞단에 ALB · CDN을 두게 되면 TLS 종료 위치와 real_ip 설정을 함께 다시 정한다.
- OCSP stapling은 넣지 않았다. Let's Encrypt가 OCSP 응답 제공을 종료해(2025) 붙일 대상이 없다.
