# BE-5 의사결정 기록

> MVP 단계(WBS 1.4) · PR #59 · 담당 정민석

## 문제 / 배경
- CI·로컬 통합 테스트는 이미 실제 PostgreSQL(pgvector 이미지)로 실행되고 있었지만, BE-2가 만든 부분 유니크 인덱스·CHECK 제약 상당수(`uk_judgment_published`, `uk_judgment_experience_timing`, V4의 judgment CHECK 제약군)는 저장소 테스트 없이 BE-2 당시 `psql`로 수동 확인만 한 상태였다.
- 테스트가 "통과"만 하고 실제로 제약을 검증하지 못하는 상태(제약을 지워도 테스트가 계속 통과하는 상태)를 피해야 했다.

## 검토한 대안
- 테스트가 실제로 제약을 검증하는지 확인하는 방법: 테스트를 작성한 뒤 그대로 믿을지, 아니면 제약을 실제로 지워보고 해당 테스트만 정확히 실패하는지 확인할지 검토했다.
- 테스트 구성 자체를 바꿀지: Testcontainers 도입이나 GitHub Actions service 구성 변경도 고려했으나, 이미 CI는 `pgvector/pgvector:pg17` service 컨테이너로, 로컬은 `docker-compose.yml`의 같은 이미지로 돌고 있어 이 부분은 이미 충족된 상태였다.

## 선택한 방법과 이유
- `DbConstraintTest` 22개를 추가해, 서비스를 거치지 않는 SQL로 규칙을 어기는 행을 직접 넣어보고 어느 제약이 막았는지 이름까지 확인하는 방식을 택했다. AI·재판부 판결과 사건 콘텐츠는 팀이 SQL로 직접 넣는 데이터라, 서비스 계층 검증만으로는 이 경로의 제약 위반을 잡을 수 없었다.
- 검증 방법론으로, 제약 3개(`uk_judgment_published`, `chk_judgment_reduced_to`, `uk_penalty_rule_case_penalty_type`)를 임시 DB에서 실제로 지우고 재실행해, 정확히 그 3개 테스트만 실패하는 것을 확인했다. 통과만 하고 아무것도 검증하지 않는 테스트를 가려내기 위한 방법으로, 확인 후 임시 DB는 삭제했다.
- 한 행이 여러 제약을 동시에 어기면 PostgreSQL이 이름순으로 먼저 걸리는 제약을 보고하므로, 각 테스트 케이스가 제약 하나만 어기도록 구성하고 `hasMessageContaining`으로 제약 이름까지 확인했다. 제약 위반이 나면 그 트랜잭션은 더 진행할 수 없어, 거절 확인을 항상 각 테스트의 마지막 문장으로 배치했다(테스트마다 롤백되어 DB에 남는 데이터가 없다).
- backend-ci.yml은 동작을 바꾸지 않고, 테스트 단계 이름에 "DB 제약 검증 포함"을 명시하고 H2로는 이 검증이 불가능하다는 주석을 추가했다. 테스트 실패 시에만 테스트 리포트를 아티팩트로 업로드하도록(7일 보관) 추가해, DB 제약 테스트가 CI에서만 실패했을 때 바로 원인을 볼 수 있게 했다.

## 고려한 제약 사항
- `insertJudgment`의 SQL 문자열 조립에 쓰이는 열 이름은 테스트 코드 내 상수뿐이고 외부 입력이 없어, SQL 인젝션 경로는 아니다(PR "리뷰 참고").
- 앞으로 CHECK·유니크 제약을 바꾸는 마이그레이션을 추가하면 이 테스트에 케이스를 함께 추가해야 한다는 점을 테스트 클래스 Javadoc에 남겼다.
- `docs/tech-stack.md` 등 문서 갱신은 동시에 열려 있던 PR #57과 작성 이력이 충돌할 수 있어 이 PR에서는 다루지 않았다.
- `backend-ci.yml`의 트리거에 `main`을 추가하는 것(현재는 `develop`만)은 브랜치 전략과 맞물린 팀 결정이 필요해 이 PR 범위 밖으로 분리했다.
