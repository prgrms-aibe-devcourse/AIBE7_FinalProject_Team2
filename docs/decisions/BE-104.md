# BE-104 의사결정 기록

> FE-77(PR #249)이 API 명세 v0.50 · ERD v1.36 · 성향 산식 v0.9로 정한 계약을 서버에 구현하고, 화면이 이 브라우저에만 저장하던
> 프로필 선택 값(공개 성향카드 · 프로필카드 아래 성향 · 한 줄 소개)의 저장 API(P-8, v0.51)를 새로 정했다.
> 계약 자체의 근거(초심 · 재심 · 최근, 재심 1회, 공개 범위 없음)는 `docs/decisions/FE-77.md`에 있다.

## 문제 / 배경
- 실제 모드에서 성향카드 재심 · 처음 성향이 "서버 연동 후 열려요"로 막혀 있었다. 서버에 칸 2개(V28)와 P-2 · P-5 처리가 없었다.
- 공개 성향카드 · 프로필카드 아래 성향 · 한 줄 소개는 `localStorage`(`nlnb-shown-card` · `nlnb-profile-card-type` · `nlnb-profile-extras`)에만 있어,
  다른 기기에서 보이지 않고 커뮤니티가 읽을 수 없었다.

## 검토한 대안

### 1. 재심 1회 제한을 어디서 보장할까
- 대안 A — 서비스에서 "이미 재심이 있는지" 조회만 한다. 동시 제출 두 건이 모두 조회를 통과하면 두 건이 저장된다.
- 대안 B(선택) — P-2가 이미 쓰는 **사용자 행 비관적 락**(`findByIdForUpdate`) 뒤에서 조회해 409를 내고, DB에는
  **부분 유니크 인덱스**(`is_baseline_retake = true`, 사용자당 1건)를 마지막 방어선으로 둔다. 동시 재심 두 건 중 한 건만 201(테스트로 확인).

### 2. P-2 `baseline` 형식 검사
- 대안 A — `Boolean`으로 받는다. Jackson이 문자열 `"true"` · 숫자 `1`을 불리언으로 바꿔 받을 수 있어 명세("불리언이 아니면 400")와 어긋난다.
- 대안 B(선택) — `JsonNode`로 받아 불리언 · null · 생략만 허용한다. 형식 검사는 익명 ID 발급 전에 끝낸다(P-2 규칙).

### 3. P-5 `initialPersonality`의 두 모양
- `source`로 모양이 갈린다(FE-77 합의). 하나의 레코드에 빈 칸을 null로 두면 `TEST`에 `experienceCount: null`이 붙는 등 명세와 달라진다.
- 선택: `sealed interface InitialPersonality`와 두 레코드(`InitialTest` · `InitialJudgment`)로 나눴다. 직렬화는 실제 레코드 모양을 따른다.

### 4. 프로필 선택 값 저장 API
- 대안 A — P-7(`PUT /profile-deco`)에 필드를 얹는다. P-7은 전체 덮어쓰기라, 서버가 모르는 필드 · 다른 화면의 저장이 꾸미기를 깨거나 덮어쓴다.
- 대안 B — 새 API를 전체 저장(PUT)으로 둔다. 세 값을 바꾸는 화면이 각각 달라(공개 도장 · 카드 꾸미기 창 · 내 정보 수정),
  오래된 화면이 다른 칸을 옛 값으로 덮어쓸 수 있다(해송님 PR #249 리뷰 의견).
- 대안 C(선택) — **P-8 `PATCH /profile-settings`, 보낸 칸만 저장**, 응답은 세 값 전체. 저장은 새 테이블 `profile_setting`(V29).
  - 요청은 `JsonNode`로 받아 "보내지 않음"과 `null`을 구분한다. `null` · 모르는 칸 · 빈 객체는 400(지우기는 `bio: ""`).
  - 재심이 없는데 `retake`를 골라도 받는다. 화면이 대신 고르는 규칙(`shownSlot` · `selectedChoice`)을 이미 쓴다.
  - 소개 글자 수는 유니코드 코드 포인트로 센다(DB `varchar(40)`과 같은 기준).

## 선택한 방법과 이유
- V28: `personality_result`에 `completed_experience_count`(NULL 허용, CHECK ≥ 0) · `is_baseline_retake`(기본 false) + 부분 유니크.
- P-2: 재심은 첫 테스트가 있을 때만 재심으로 저장, 없으면 첫 테스트로 처리(횟수 안 씀). 응시마다 그 시점의 완료 사건 수를 저장.
- P-5: 초심 = 가장 오래된 응시 행(`TEST`), 테스트 전이면 첫 판결(각 사건의 첫 회차, 완료 순서로 처음 3건, 유형이 있을 때만 `JUDGMENT`).
  유형 조회는 BE-100의 묶음 조회(`findAllById` 한 번)에 첫 판결 코드도 함께 넣었다.
- P-8 · V29 · P-5 `profileSettings`(저장 전이면 `current` · `current` · `""`). 명세 v0.51, ERD v1.37.

## 고려한 제약 사항
- 마이그레이션은 추가만 한다(BE-60). 두 칸은 NULL 허용 · 기본값이 있어 이전 앱이 그대로 뜬다. 새 테이블은 이전 앱이 읽지 않는다.
- 한 줄 소개 금칙어: 해송님 의견대로 있는 편이 좋지만, 금칙어 목록 · 검사 기능(운영 A-39 ~ A-41)이 아직 초안이라 이번에는 넣지 않았다.
- 목(FE-77 `personalityMockApi.js`)과 규칙을 대조했다: 재심 판정 · `available` · 완료 사건 수 · 첫 판결 3건은 같다.
  목의 첫 판결 글자는 평균 점수를 0.5와 비교하고 서버는 정확한 분수의 부호를 본다 — 0.5 근처에서만 다를 수 있다(BE-100과 같은 차이).

## 추후 재검토가 필요하면
- 한 줄 소개 금칙어 검사: 금칙어 기능이 생기면 P-8에 붙인다.
- 커뮤니티가 다른 사람의 공개 성향카드 · 소개를 읽는 API는 커뮤니티 작업에서 붙인다.
- 재심 횟수를 늘릴 수요가 생기면 부분 유니크를 횟수 칸으로 바꾸는 마이그레이션이 필요하다(FE-77 "도전과제 보상 +1회" 안).
