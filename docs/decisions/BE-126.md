# BE-126 의사결정 기록

대본을 단위 블록(U0 ~ U4)과 메타로 저장하고 블록마다 검수 · 승인한다. 설계 결정의 근거는 Jira BE-126 설명 · 댓글(2026-10-29 ~ 30, 해송님 결정과 답변)과 BE-129 댓글(연동 표)이다. 여기에는 구현에서 고른 방법과 이유만 적는다.

1차는 PR 두 개로 나눈다: 파이프라인이 블록을 내보내는 쪽(1차-1)과 백엔드가 적재 · 검수 · 공개하는 쪽(1차-2). 2차(블록 단위 승인 · 낡음 표시 · `scriptStatus`)는 BE-129 뒤다.

## 1차-1 파이프라인 블록 출력 (PR 파이프라인)

### 문제 / 배경

- 파이프라인 대본(`script.json`)은 U1 · U2 · U4를 고정 문구 · 연출과 섞인 `acts`로만 내보냈다. 블록으로 저장하려면 단위 값이 따로 있어야 한다.
- 낡음(stale)을 "만들 때 쓴 값"과 지금 값을 비교해 계산하기로 했다(해송님 동의). 그러면 만들 때 쓴 값을 **생성 시점에** 남겨야 한다 — 적재 뒤에는 알 수 없다.
- 연동 표(어떤 값이 바뀌면 어떤 블록이 낡는지)와 신문 답 규칙(`admits` · `normalize_answer`)이 백엔드(자바)에도 생긴다. 두 언어의 규칙이 어긋나지 않게 해야 한다.

### 검토한 대안

- **앞 블록 기준값: 내용 해시 vs 판 번호.** 해시는 백엔드가 같은 값을 다시 계산해야 하는데, 파이썬과 자바의 JSON 직렬화(키 순서 · 유니코드 · 숫자 표기)를 맞추기 어렵다. 판 번호(`revision`)는 정수 비교뿐이다. → 판 번호.
- **블록 내용: 생성 결과 그대로 vs 화면용 모양으로 변환.** 화면용 모양(`acts`, `_cards`의 `k` 이름표 등)으로 바꾸면 고정 문구가 섞이고 검수 결과 `path`가 맞지 않는다. → 생성 결과 모양을 유지하고, 한 번 정해지면 바뀌지 않는 다듬기(U1 줄 접두어 제거, U2 카드 적용 법조)만 한다.
- **U2 신문 답: 정규화한 값 vs 원래 값.** 해송님 답변 2번의 (나). U2 질문 · 답은 U0를 보고 U2가 다시 쓴 값이라, 정규화한 값을 저장해도 U0와 직접 얽히지는 않는다. 다만 저장값에 계산된 값을 섞지 않는 쪽이 단순하다 → 원래 답 저장, 정규화는 API 18.
- **연동 표 위치: 파이썬 두 곳(`AFFECTS` + 새 표) vs 표 하나에서 계산.** `script_repair.AFFECTS`(BE-122 2차)를 그대로 두면 표가 둘이 된다. → `BLOCK_BASIS` 하나를 정본으로 두고 `AFFECTS`는 그 역(뒤 단위 목록)으로 계산한다.

### 선택한 방법과 이유

- `script_assembler.build_blocks`가 `blocks`(U0 ~ U4) · `meta`(`cast` · `issue` · `admits`)를 만들고 `build_script`가 대본에 싣는다. 서비스는 `fullScript`를 그대로 넘기므로 서비스 코드는 바꾸지 않았다.
- 블록: `content` · `revision` · `basis` · `review` · `warnings` · `repairs`. `review` · `repairs`는 그 단위 것만 나눠 담는다(해송님 답변 1번 — 관리자 화면이 "자동으로 고친 줄"을 블록마다 보여 준다).
- **판 번호는 고쳐 쓰기 기록에서 계산한다**(`block_revisions`). 줄을 받거나(`ok`) 단위를 바꾸면(`replaced`) 1씩 오른다. 단위째 다시 만든 블록은 그때의 앞 블록 판을 본다. 그래서 U0 줄을 고쳐 받으면 그 전에 만든 U2 · U4가 적재 직후 낡음으로 보이는데, 실제로 옛 U0로 만든 값이라 맞는 동작이다.
  - 단위 재생성 기록에 `replaced`를 더했다. U1 · U4는 뒤 단위가 없어 `affects`가 늘 비어서, 값을 바꿨는지 알 방법이 없었다.
- `BLOCK_BASIS`의 분류 축은 `GUIDE_UNITS`(축 블록을 넣는 단위)와 같다. 테스트로 묶었다(블록을 안 넣는 단위가 그 축 때문에 낡을 이유는 없다).
- **`admits`를 `normalize_answer`로 정의했다**: `admits(a) == (normalize_answer(a) == "…네.")`. 전에는 `admits`만 "..."(마침표 셋)을 벗기지 않아 "...네, 인정합니다."를 부인으로 읽었다. 두 규칙이 하나가 되어 자바로 옮길 규칙도 하나다.
- 공용 계약 파일 `tools/ai-judgment/contracts/script_blocks.json`: 연동 표(`basis` · `affects`)와 신문 답 사례(입력 → 기대값). 파이썬 테스트(`BlockContractTest`)가 이 파일과 코드를 비교하고, 백엔드 테스트(1차-2)도 같은 파일을 읽는다(해송님 답변 3 · 4번).

### 고려한 제약 사항

- 운영 `case_script`는 0행(2026-10-30 확인)이라 블록 형식을 바꿔도 옮길 운영 데이터가 없다.
- 기사(`paper`)는 블록이 아니다(API 17 단일 출처).
- 증거조사만 만드는 경로(`stages.script.full = false`, BE-107)는 `script.json`을 쓰지 않아 블록이 없다. 백엔드는 그 경우 `evidence`를 U3 블록 하나로 적재한다(1차-2).

### PR #363 리뷰 반영

- **사건 내용도 `basis`에 넣었다**(CodeRabbit). 관리자는 적재 뒤 A-11로 제목 · 개요 등을 고칠 수 있고, 그 값은 U0 · U2 · U3 · U4의 입력이다. 키 `case`를 더했다(U1은 기사만 받아 빠진다).
- **DB가 가진 값(`case` · `paper`)은 파이프라인이 `null`로 내보내고 적재할 때 백엔드가 DB 판으로 채운다**(`DB_BASIS`). 처음에는 U1 `basis.paper`에 기사 값을 통째로 두었는데, 그러면 백엔드가 API 17 기사와 필드 · 공백 · 문단까지 맞춰 비교해야 한다(해송님 리뷰 3번). 사건 내용도 같은 문제라, "같은지"만 알면 되는 두 값은 백엔드의 판으로 비교한다. 생성 직후 적재하므로 그때의 DB 판이 곧 생성 입력이다. 쓴 기사 값은 대본의 `paper`에 그대로 남는다.
- **신문 답 규칙에 낱말 경계를 넣었다**(해송님 리뷰 1번). 전에는 "예 · 네 · 아니"로 **시작하기만 하면** 답으로 읽어 "예전에는 …" · "네가 …"를 "…네."로 바꿨다. U0 세 번째 답은 "예 또는 아니요"로 형식이 정해져 위험이 작았지만, 이제 정규화가 API 18로 옮겨 자유 문장인 U2 답이 그대로 지나가고, 같은 규칙이 자바로 복사된다. 계약에 박히기 전에 고쳤다. 앞부분은 공백 · 말줄임표 · 마침표가 섞여 있어도 한 번에 벗긴다(전에는 ". …네"를 못 읽었다).
- 계약 파일에 자바로 옮길 때 갈리는 사례를 더했다(해송님 리뷰 5번): 말줄임표 여러 개, 마침표 · 말줄임표 섞임, 전각 공백(U+3000 — 자바 `trim()`은 못 벗긴다), 접두만 같은 낱말.
- `review` · `warnings` · `repairs`는 관리자 전용이고 API 18은 `content`만, U3는 `factorId` · `role` · `text`만 내린다고 README에 못 박았다(해송님 리뷰 4번, 1차-2가 따른다). U3 `content`는 생성 결과를 복사해 담는다.
- 실제 `repair_units` → `build_blocks`로 판 번호를 잇는 테스트를 더했다(합성 기록만으로는 두 모듈의 기록 형식이 어긋나도 통과한다).

### 추후 재검토가 필요하면

- **낡음 "확인하고 그대로 두기"(2차, 해송님 리뷰 2번)**: U0 줄이 자동으로 고쳐진 대본은 U2 · U4가 적재 직후 낡음으로 보이는데, 고쳐 쓰기는 U2 · U4를 다시 만들지 않는다. 사소한 수정마다 다시 만들게 하면 낡음 표시를 믿지 않게 된다. 2차에서 낡음은 승인을 막지 않고 표시만 하고, 관리자가 "확인했음"을 누르면 그 블록의 `basis`를 지금 판으로 맞추는 동작을 둔다.
- 백엔드의 사건 내용 · 기사 판을 무엇으로 둘지(전용 판 번호 칸 vs 수정 시각)는 1차-2에서 정한다. `updated_at`은 공개 상태 변경 같은 다른 수정에도 바뀌어 낡음이 잘못 뜰 수 있다.
- U3는 AI 판결(select 단계가 고른 방향)도 보고 만든다. 지금 표에는 넣지 않았다 — 적재 뒤 판결 후보를 바꾸는 흐름이 대본 재생성과 이어질 때(BE-129) 다시 본다.

## 1차-2 백엔드 적재 · 검수 · 공개 (PR 백엔드)

### 문제 / 배경

- 파이프라인이 `fullScript.blocks` · `meta`를 내보내게 됐지만(1차-1) 백엔드는 `evidence`만 `case_script` 한 칸에 담고 있었다. 블록 단위로 저장하고, 1차 동안은 통승인 · 통거절을 유지하면서 2차(블록 단위 승인)로 넘어갈 자리를 만들어야 한다.
- 블록 `basis`의 사건 내용 · 기사(`case` · `paper`)는 적재할 때 백엔드가 DB 판으로 채우기로 했는데(1차-1 리뷰 반영), 그 "판"이 DB에 없었다.
- 확인하다 보니 **파이프라인이 만든 기사는 어디에도 저장되지 않았다.** 사건 지면(`case_paper`, API 17)은 관리자가 A-13-6으로 따로 만들고(백엔드 Gemini), 적재는 기사를 읽지 않는다. 그런데 U1(1막 해설)은 파이프라인 기사를 보고 만들어진다 — 그대로 두면 화면에는 다른 기사가 나오고 해설은 보이지 않는 기사를 설명한다.

### 검토한 대안

- **대본의 검수 상태: 대본 칸 유지 + 블록 칸 추가 vs 블록 칸만.** 둘 다 두면 1차에는 늘 같은 값이지만 2차에서 블록 단위 승인이 들어오는 순간 두 값이 어긋날 자리가 생긴다(어느 쪽이 공개 기준인지). → 블록 칸만 두고 대본 상태는 계산한다(모두 승인 = 공개, 하나라도 반려 = 반려). 공개 기준 하나(`isPublic` · `findApprovedCaseIds`)가 그대로 2차 기준이 된다.
- **사건 내용 · 기사 판: `updated_at` vs 전용 칸.** `updated_at`은 공개 · 공개 취소 · 사진 · 배역 수정에도 바뀐다 — 대본 입력이 아닌 수정에도 낡음이 뜬다. → `legal_case.content_revision` · `case_paper.revision`을 두고, 대본 입력(제목 · 개요, 기사 본문)이 **실제로 바뀔 때만** 올린다(같은 값 저장은 그대로). 엔티티의 변경 메서드 안에서 올려 호출하는 쪽이 잊을 자리를 없앴다.
- **파이프라인 기사: 버림 vs 지면으로 저장.** 버리면 U1의 생성 입력을 알 수 없고(`basis.paper`가 영원히 모름), 화면 기사와 해설이 어긋난다. 파이프라인 기사는 이미 백엔드 지면과 같은 모양 · 같은 정리 규칙이다(`normalize_paper` "백엔드 parse · normalize와 같게"). → 적재가 지면으로 저장한다. 지면 규칙(A-13-8 길이 · 빈 문단)은 Gemini 응답과 같은 검사(`CasePaperService.checked`)를 쓰고, 어기면 저장하지 않고 `basis.paper`를 비운다. 관리자가 나중에 A-13-6으로 다시 만들면 판이 올라 U1이 낡음으로 보인다(2차) — 실제로 다른 기사이니 맞는 동작이다.
- **`admits`: 파이프라인 값 vs 서버 계산.** Jira 설계는 "서버가 계산해 메타로 둔다, 관리자가 U0를 고치면 다시 계산"이다. 적재 때 파이프라인 값을 받으면 2차에 계산 경로가 따로 생긴다. → 적재 때부터 U0 세 번째 답을 `ScriptAnswers.admits`로 읽는다(규칙은 계약 파일로 파이썬과 같다).
- **API 18에 U0: 포함 vs 제외.** U0는 설계도(신문 질문 초안 · 쟁점 · 말투)로, U2 · U4가 보고 다시 쓴 재료다. 화면이 쓰는 값은 인정 여부 하나라 `meta.admits`로 이미 나간다. 내리면 화면이 U0와 U2 질문 중 무엇을 쓸지 헷갈리고, 바꿀 수 없는 공개 계약이 하나 늘어난다. → 제외. 관리자 화면(A-13-10)에는 준다.
- **대사 수정(A-13-13) 뒤 검수: U3만 대기 vs 모든 블록 대기.** 1차는 통승인이라 U3만 대기로 돌리면 "U3 대기 · 나머지 반려" 같은 섞인 상태가 생기고 화면은 다시 통승인을 누를 수밖에 없다. → 모든 블록을 대기로(BE-108 때와 같은 동작). 블록 단위는 2차.

### 선택한 방법과 이유

- V45: `case_script_block`(블록마다 `content` · `revision` · `basis` · `review` · `warnings` · `repairs` · `publishable` · 검수 칸), 오류 블록 승인 불가 CHECK. `case_script`에 메타 `issue` · `admits`와 `pending` · `review`(대본 전체 검수 결과)를 더하고 `evidence` · 검수 칸은 블록으로 옮겼다. 운영은 0행이지만 개발 · 로컬 DB를 위해 기존 대본을 U3 블록 하나로 옮긴다(검수 상태 그대로 — 승인한 대본은 계속 공개). 데이터가 있는 DB에 V1 ~ V44를 올리고 V45를 돌려 확인했다.
- 적재는 `CaseScriptLoader`로 나눴다(`CaseContentMapper` · `JudgmentMapper`처럼 적재기 옆 부품). 대본 전체면 블록 · 메타 · 기사, 증거조사만이면 U3 하나. 증거조사만 만든 경로는 생성 근거를 내보내지 않아 아는 값(`case` 판 · 배역)만 `basis`에 남긴다.
- 승인 조건(`isApprovable`) = 대본 `publishable`(파이프라인: 멈춤 · 못 만든 단위 · 검수 오류) **그리고** 모든 블록 `publishable`(서버 계산: 블록의 검수 오류 · U3 빈 줄). 대사를 고치면 서버가 같은 식으로 다시 계산한다(그 줄의 검수 오류는 지운다 — 사람이 고친 줄은 더는 그 오류가 아니다, BE-108의 `validation.errors`와 같은 이유).
- 응답은 기존 필드를 모두 남기고 더하기만 했다 — A-13-10의 `evidence` 등 · API 18의 `evidence` · `cast`는 U3 블록에서 같은 모양으로 만든다. 프론트는 바뀌지 않아도 된다.
- 계약: `ScriptUnit`(연동 표) · `ScriptAnswers`(신문 답)를 자바로 옮기고 `ScriptBlockContractTest`가 `tools/ai-judgment/contracts/script_blocks.json`을 읽어 맞춘다. 자바 정규식 `\s`는 ASCII라 `UNICODE_CHARACTER_CLASS`를 켰다(전각 공백 사례). 백엔드 CI가 이 파일이 바뀔 때도 돌도록 경로를 더했다.

### 고려한 제약 사항

- 1차는 `scriptReady` 필드를 유지하고 기준만 "모든 블록 승인"으로 바꾼다(`scriptStatus`는 2차). 증거조사만 만든 대본은 블록이 하나라 전과 같다.
- 사건 1 등 운영 데이터 이관은 없다(운영 `case_script` 0행).

### 추후 재검토가 필요하면

- 마이그레이션으로 옮긴 대본과 증거조사만 만든 대본은 `basis`가 일부(`case` · `cast`)뿐이다. 2차 낡음 계산에서 "근거에 없는 키"를 낡음으로 볼지 모름으로 볼지 정한다.
- 1차-1에서 남긴 "사건 내용 · 기사 판을 무엇으로 둘지"는 위 전용 칸으로 정했다.
