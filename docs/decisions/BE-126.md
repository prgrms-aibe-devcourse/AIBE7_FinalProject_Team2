# BE-126 의사결정 기록

대본을 단위 블록(U0 ~ U4)과 메타로 저장하고 블록마다 검수 · 승인한다. 설계 결정의 근거는 Jira BE-126 설명 · 댓글(2026-10-29 ~ 30, 해송님 결정과 답변)과 BE-129 댓글(연동 표)이다. 여기에는 구현에서 고른 방법과 이유만 적는다.

1차는 PR 두 개로 나눈다: 파이프라인이 블록을 내보내는 쪽(1차-1)과 백엔드가 적재 · 검수 · 공개하는 쪽(1차-2). 2차(블록 단위 승인 · 낡음 표시 · `scriptStatus`)는 BE-129 뒤이고, 역시 둘로 나눈다: 블록 검수 · 낡음(2차-1)과 `scriptStatus` · 점검 상태(2차-2).

## 1차-1 파이프라인 블록 출력 (PR 파이프라인)

### 문제 / 배경

- 파이프라인 대본(`script.json`)은 U1 · U2 · U4를 고정 문구 · 연출과 섞인 `acts`로만 내보냈다. 블록으로 저장하려면 단위 값이 따로 있어야 한다.
- 낡음(stale)을 "만들 때 쓴 값"과 지금 값을 비교해 계산하기로 했다(해송님 동의). 그러면 만들 때 쓴 값을 **생성 시점에** 남겨야 한다 — 적재 뒤에는 알 수 없다.
- 연동 표(어떤 값이 바뀌면 어떤 블록이 낡는지)와 신문 답 규칙(`admits` · `normalize_answer`)이 백엔드(자바)에도 생긴다. 두 언어의 규칙이 어긋나지 않게 해야 한다.

### 검토한 대안

- **앞 블록 기준값: 내용 해시 vs 판 번호.** 해시는 백엔드가 같은 값을 다시 계산해야 하는데, 파이썬과 자바의 JSON 직렬화(키 순서 · 유니코드 · 숫자 표기)를 맞추기 어렵다. 판 번호(`revision`)는 정수 비교뿐이다. → 판 번호.
- **블록 내용: 생성 결과 그대로 vs 화면용 모양으로 변환.** 화면용 모양(`acts`, `_cards`의 `k` 이름표 등)으로 바꾸면 고정 문구가 섞이고 검수 결과 `path`가 맞지 않는다. → 생성 결과 모양을 유지하고, 한 번 정해지면 바뀌지 않는 다듬기(U1 줄 접두어 제거, U2 카드 적용 법조)만 한다.
- **U2 신문 답: 정규화한 값 vs 원래 값.** 해송님 답변 2번의 (나). U2 질문 · 답은 U0를 보고 U2가 다시 쓴 값이라, 정규화한 값을 저장해도 U0와 직접 얽히지는 않는다. 다만 저장값에 계산된 값을 섞지 않는 쪽이 단순하다 → 원래 답 저장, 정규화는 API 18.
- **연동 표 위치: 파이썬 두 곳(`AFFECTS` + 새 표) vs 표 하나에서 계산.** `script_repair.AFFECTS`(BE-122 2차)를 그대로 두면 표가 둘이 된다. → `BLOCK_BASIS` 하나를 정본으로 두고 `AFFECTS`는 그 역(뒤 단위 목록)으로 계산한다.

### 선택한 방법과 이유

- `script_assembler.build_blocks`가 `blocks`(U0 ~ U4) · `meta`(`cast` · `issue` · `admits`)를 만들고 `build_script`가 대본에 싣는다. 서비스는 `fullScript`를 그대로 넘기므로 서비스 코드는 바꾸지 않았다.
- 블록: `content` · `revision` · `basis` · `review` · `warnings` · `repairs`. `review` · `repairs`는 그 단위 것만 나눠 담는다(해송님 답변 1번 — 관리자 화면이 "자동으로 고친 줄"을 블록마다 보여 준다).
- **판 번호는 고쳐 쓰기 기록에서 계산한다**(`block_revisions`). 줄을 받거나(`ok`) 단위를 바꾸면(`replaced`) 1씩 오른다. 단위째 다시 만든 블록은 그때의 앞 블록 판을 본다. 그래서 U0 줄을 고쳐 받으면 그 전에 만든 U2 · U4가 적재 직후 낡음으로 보이는데, 실제로 옛 U0로 만든 값이라 맞는 동작이다.
  - 단위 재생성 기록에 `replaced`를 더했다. U1 · U4는 뒤 단위가 없어 `affects`가 늘 비어서, 값을 바꿨는지 알 방법이 없었다.
- `BLOCK_BASIS`의 분류 축은 `GUIDE_UNITS`(축 블록을 넣는 단위)와 같다. 테스트로 묶었다(블록을 안 넣는 단위가 그 축 때문에 낡을 이유는 없다).
- **`admits`를 `normalize_answer`로 정의했다**: `admits(a) == (normalize_answer(a) == "…네.")`. 전에는 `admits`만 "..."(마침표 셋)을 벗기지 않아 "...네, 인정합니다."를 부인으로 읽었다. 두 규칙이 하나가 되어 자바로 옮길 규칙도 하나다.
- 공용 계약 파일 `tools/ai-judgment/contracts/script_blocks.json`: 연동 표(`basis` · `affects`)와 신문 답 사례(입력 → 기대값). 파이썬 테스트(`BlockContractTest`)가 이 파일과 코드를 비교하고, 백엔드 테스트(1차-2)도 같은 파일을 읽는다(해송님 답변 3 · 4번).

### 고려한 제약 사항

- 운영 `case_script`는 0행(2026-10-30 확인)이라 블록 형식을 바꿔도 옮길 운영 데이터가 없다.
- 기사(`paper`)는 블록이 아니다(API 17 단일 출처).
- 증거조사만 만드는 경로(`stages.script.full = false`, BE-107)는 `script.json`을 쓰지 않아 블록이 없다. 백엔드는 그 경우 `evidence`를 U3 블록 하나로 적재한다(1차-2).

### PR #363 리뷰 반영

- **사건 내용도 `basis`에 넣었다**(CodeRabbit). 관리자는 적재 뒤 A-11로 제목 · 개요 등을 고칠 수 있고, 그 값은 U0 · U2 · U3 · U4의 입력이다. 키 `case`를 더했다(U1은 기사만 받아 빠진다).
- **DB가 가진 값(`case` · `paper`)은 파이프라인이 `null`로 내보내고 적재할 때 백엔드가 DB 판으로 채운다**(`DB_BASIS`). 처음에는 U1 `basis.paper`에 기사 값을 통째로 두었는데, 그러면 백엔드가 API 17 기사와 필드 · 공백 · 문단까지 맞춰 비교해야 한다(해송님 리뷰 3번). 사건 내용도 같은 문제라, "같은지"만 알면 되는 두 값은 백엔드의 판으로 비교한다. 생성 직후 적재하므로 그때의 DB 판이 곧 생성 입력이다. 쓴 기사 값은 대본의 `paper`에 그대로 남는다.
- **신문 답 규칙에 낱말 경계를 넣었다**(해송님 리뷰 1번). 전에는 "예 · 네 · 아니"로 **시작하기만 하면** 답으로 읽어 "예전에는 …" · "네가 …"를 "…네."로 바꿨다. U0 세 번째 답은 "예 또는 아니요"로 형식이 정해져 위험이 작았지만, 이제 정규화가 API 18로 옮겨 자유 문장인 U2 답이 그대로 지나가고, 같은 규칙이 자바로 복사된다. 계약에 박히기 전에 고쳤다. 앞부분은 공백 · 말줄임표 · 마침표가 섞여 있어도 한 번에 벗긴다(전에는 ". …네"를 못 읽었다).
- 계약 파일에 자바로 옮길 때 갈리는 사례를 더했다(해송님 리뷰 5번): 말줄임표 여러 개, 마침표 · 말줄임표 섞임, 전각 공백(U+3000 — 자바 `trim()`은 못 벗긴다), 접두만 같은 낱말.
- `review` · `warnings` · `repairs`는 관리자 전용이고 API 18은 `content`만, U3는 `factorId` · `role` · `text`만 내린다고 README에 못 박았다(해송님 리뷰 4번, 1차-2가 따른다). U3 `content`는 생성 결과를 복사해 담는다.
- 실제 `repair_units` → `build_blocks`로 판 번호를 잇는 테스트를 더했다(합성 기록만으로는 두 모듈의 기록 형식이 어긋나도 통과한다).

### 추후 재검토가 필요하면

- **낡음 "확인하고 그대로 두기"(2차, 해송님 리뷰 2번)**: U0 줄이 자동으로 고쳐진 대본은 U2 · U4가 적재 직후 낡음으로 보이는데, 고쳐 쓰기는 U2 · U4를 다시 만들지 않는다. 사소한 수정마다 다시 만들게 하면 낡음 표시를 믿지 않게 된다. 2차에서 낡음은 승인을 막지 않고 표시만 하고, 관리자가 "확인했음"을 누르면 그 블록의 `basis`를 지금 판으로 맞추는 동작을 둔다.
- 백엔드의 사건 내용 · 기사 판을 무엇으로 둘지(전용 판 번호 칸 vs 수정 시각)는 1차-2에서 정한다. `updated_at`은 공개 상태 변경 같은 다른 수정에도 바뀌어 낡음이 잘못 뜰 수 있다.
- U3는 AI 판결(select 단계가 고른 방향)도 보고 만든다. 지금 표에는 넣지 않았다 — 적재 뒤 판결 후보를 바꾸는 흐름이 대본 재생성과 이어질 때(BE-129) 다시 본다.

## 1차-2 백엔드 적재 · 검수 · 공개 (PR 백엔드)

### 문제 / 배경

- 파이프라인이 `fullScript.blocks` · `meta`를 내보내게 됐지만(1차-1) 백엔드는 `evidence`만 `case_script` 한 칸에 담고 있었다. 블록 단위로 저장하고, 1차 동안은 통승인 · 통거절을 유지하면서 2차(블록 단위 승인)로 넘어갈 자리를 만들어야 한다.
- 블록 `basis`의 사건 내용 · 기사(`case` · `paper`)는 적재할 때 백엔드가 DB 판으로 채우기로 했는데(1차-1 리뷰 반영), 그 "판"이 DB에 없었다.
- 확인하다 보니 **파이프라인이 만든 기사는 어디에도 저장되지 않았다.** 사건 지면(`case_paper`, API 17)은 관리자가 A-13-6으로 따로 만들고(백엔드 Gemini), 적재는 기사를 읽지 않는다. 그런데 U1(1막 해설)은 파이프라인 기사를 보고 만들어진다 — 그대로 두면 화면에는 다른 기사가 나오고 해설은 보이지 않는 기사를 설명한다.

### 검토한 대안

- **대본의 검수 상태: 대본 칸 유지 + 블록 칸 추가 vs 블록 칸만.** 둘 다 두면 1차에는 늘 같은 값이지만 2차에서 블록 단위 승인이 들어오는 순간 두 값이 어긋날 자리가 생긴다(어느 쪽이 공개 기준인지). → 블록 칸만 두고 대본 상태는 계산한다(모두 승인 = 공개, 하나라도 반려 = 반려). 공개 기준 하나(`isPublic` · `findApprovedCaseIds`)가 그대로 2차 기준이 된다.
- **사건 내용 · 기사 판: `updated_at` vs 전용 칸.** `updated_at`은 공개 · 공개 취소 · 사진 · 배역 수정에도 바뀐다 — 대본 입력이 아닌 수정에도 낡음이 뜬다. → `legal_case.content_revision` · `case_paper.revision`을 두고, 대본 입력(제목 · 개요, 기사 본문)이 **실제로 바뀔 때만** 올린다(같은 값 저장은 그대로). 엔티티의 변경 메서드 안에서 올려 호출하는 쪽이 잊을 자리를 없앴다.
- **파이프라인 기사: 버림 vs 지면으로 저장.** 버리면 U1의 생성 입력을 알 수 없고(`basis.paper`가 영원히 모름), 화면 기사와 해설이 어긋난다. 파이프라인 기사는 이미 백엔드 지면과 같은 모양 · 같은 정리 규칙이다(`normalize_paper` "백엔드 parse · normalize와 같게"). → 적재가 지면으로 저장한다. 지면 규칙(A-13-8 길이 · 빈 문단)은 Gemini 응답과 같은 검사(`CasePaperService.checked`)를 쓰고, 어기면 저장하지 않고 `basis.paper`를 비운다. 관리자가 나중에 A-13-6으로 다시 만들면 판이 올라 U1이 낡음으로 보인다(2차) — 실제로 다른 기사이니 맞는 동작이다.
- **`admits`: 파이프라인 값 vs 서버 계산.** Jira 설계는 "서버가 계산해 메타로 둔다, 관리자가 U0를 고치면 다시 계산"이다. 적재 때 파이프라인 값을 받으면 2차에 계산 경로가 따로 생긴다. → 적재 때부터 U0 세 번째 답을 `ScriptAnswers.admits`로 읽는다(규칙은 계약 파일로 파이썬과 같다).
- **API 18에 U0: 포함 vs 제외.** U0는 설계도(신문 질문 초안 · 쟁점 · 말투)로, U2 · U4가 보고 다시 쓴 재료다. 화면이 쓰는 값은 인정 여부 하나라 `meta.admits`로 이미 나간다. 내리면 화면이 U0와 U2 질문 중 무엇을 쓸지 헷갈리고, 바꿀 수 없는 공개 계약이 하나 늘어난다. → 제외. 관리자 화면(A-13-10)에는 준다.
- **대사 수정(A-13-13) 뒤 검수: U3만 대기 vs 모든 블록 대기.** 1차는 통승인이라 U3만 대기로 돌리면 "U3 대기 · 나머지 반려" 같은 섞인 상태가 생기고 화면은 다시 통승인을 누를 수밖에 없다. → 모든 블록을 대기로(BE-108 때와 같은 동작). 블록 단위는 2차.

### 선택한 방법과 이유

- V45: `case_script_block`(블록마다 `content` · `revision` · `basis` · `review` · `warnings` · `repairs` · `publishable` · 검수 칸), 오류 블록 승인 불가 CHECK. `case_script`에 메타 `issue` · `admits`와 `pending` · `review`(대본 전체 검수 결과)를 더하고 `evidence` · 검수 칸은 블록으로 옮겼다. 운영은 0행이지만 개발 · 로컬 DB를 위해 기존 대본을 U3 블록 하나로 옮긴다(검수 상태 그대로 — 승인한 대본은 계속 공개). 데이터가 있는 DB에 V1 ~ V44를 올리고 V45를 돌려 확인했다.
- 적재는 `CaseScriptLoader`로 나눴다(`CaseContentMapper` · `JudgmentMapper`처럼 적재기 옆 부품). 대본 전체면 블록 · 메타 · 기사, 증거조사만이면 U3 하나. 증거조사만 만든 경로는 생성 근거를 내보내지 않아 아는 값(`case` 판 · 배역)만 `basis`에 남긴다.
- 승인 조건(`isApprovable`) = 대본 `publishable`(파이프라인: 멈춤 · 못 만든 단위 · 검수 오류) **그리고** 모든 블록 `publishable`(서버 계산: 블록의 검수 오류 · U3 빈 줄). 대사를 고치면 서버가 같은 식으로 다시 계산한다(그 줄의 검수 오류는 지운다 — 사람이 고친 줄은 더는 그 오류가 아니다, BE-108의 `validation.errors`와 같은 이유).
- 응답은 기존 필드를 모두 남기고 더하기만 했다 — A-13-10의 `evidence` 등 · API 18의 `evidence` · `cast`는 U3 블록에서 같은 모양으로 만든다. 프론트는 바뀌지 않아도 된다.
- 계약: `ScriptUnit`(연동 표) · `ScriptAnswers`(신문 답)를 자바로 옮기고 `ScriptBlockContractTest`가 `tools/ai-judgment/contracts/script_blocks.json`을 읽어 맞춘다. 자바 정규식 `\s`는 ASCII라 `UNICODE_CHARACTER_CLASS`를 켰다(전각 공백 사례). 백엔드 CI가 이 파일이 바뀔 때도 돌도록 경로를 더했다.

### 고려한 제약 사항

- 1차는 `scriptReady` 필드를 유지하고 기준만 바꾼다(`scriptStatus`는 2차). 처음에는 "증거조사만 만든 대본은 블록이 하나라 전과 같다"로 두었다가 리뷰에서 합의와 어긋난 것을 고쳤다(아래 "PR #367 리뷰 반영" 1번).
- 사건 1 등 운영 데이터 이관은 없다(운영 `case_script` 0행).

### 추후 재검토가 필요하면

- 마이그레이션으로 옮긴 대본과 증거조사만 만든 대본은 `basis`가 일부(`case` · `cast`)뿐이다. 2차 낡음 계산에서 "근거에 없는 키"를 낡음으로 볼지 모름으로 볼지 정한다.
- 1차-1에서 남긴 "사건 내용 · 기사 판을 무엇으로 둘지"는 위 전용 칸으로 정했다.

### PR #367 리뷰 반영

- **증거조사만 만든 대본은 "준비 중"이다(해송님 리뷰 1번).** 설계 질문 5번에서 "기존 증거조사만 있는 대본은 U3 블록으로 옮기고 준비 중으로 둔다"로 합의했는데, 처음 구현은 U3 하나만 승인돼도 공개(`scriptReady = true`)했다 — 합의를 놓친 것이다. 공개 · 승인 조건을 **다섯 단위(U0 ~ U4)가 모두 있을 것**으로 바꿨다(`CaseScript.isComplete`, 목록 쿼리는 "승인 블록 수 = 단위 수"). 증거조사만 만든 경로와 V45 이관은 나머지 네 단위를 `pending`에 넣어 화면이 이유를 보이게 했다. `pending`만 채우는 방법도 있었지만, 이관 대본은 U3가 이미 승인 상태라 `pending`만으로는 공개가 꺼지지 않는다 — 조건 자체를 바꿨다.
- **만든 뒤 사건 내용 · 기사가 바뀐 블록은 통승인을 막는다(해송님 리뷰 2번).** 판 칸이 생겼는데 2차까지 아무도 읽지 않으면, 적재 뒤 기사를 다시 만들거나(A-13-6) 개요를 고친(A-11) 다음 통승인할 때 옛 기사를 설명하는 U1이 공개된다. DB 키 둘(`case` · `paper`)만 지금 판과 비교해 다르면 409로 거절하고 어느 블록인지 알린다(`CaseScript.staleOnDbInput`). 분류 · 배역 · 앞 블록의 낡음은 2차 그대로다. 대가: BE-129(블록 재생성) 전까지는 적재 뒤 기사 · 개요를 고치면 대본을 다시 등록해야 승인할 수 있다 — 옛 내용을 말하는 대본이 공개되는 것보다 낫다고 봤다. 2차의 "확인했음"(basis를 지금 판으로 맞춤)이 사소한 수정의 출구가 된다.
- **파이프라인 기사도 사람이 본다(해송님 리뷰 3번).** 자동 검수(BE-122)는 기사를 검사하지 않으므로 최종검수 체크리스트(`docs/script-final-review-checklist.md` 4번)에 기사 항목을 더했다. 검수 화면 안내 문구는 프론트 작업이다.
- **API 18은 단위마다 화면이 쓰는 키만 내린다(해송님 리뷰 4번).** 파이프라인 형식 검사는 필요한 키가 있는지만 보고 여분의 키를 막지 않는다. U1 `lines`, U2 `indict` · `plea` · `issues_narr` · `questions` · `cards`, U4 `prosecutor` · `defense`만 복사한다(U3와 같은 원칙).
- **기사를 다시 생성해도 같은 내용이면 판을 올리지 않는다(CodeRabbit).** 수정(A-13-8)과 같은 기준이다.
- 사소한 점: `pending`에 블록 단위가 아닌 `"PAPER"`가 들어올 수 있음을 V45 · ERD · API 명세에 적었다. V45가 칸을 지우는 것은, 운영이 서버 한 대에서 컨테이너를 바꿔 띄우는 방식이라(`deploy/README.md`, 무중단 아님) 옛 인스턴스가 새 스키마와 함께 도는 구간이 없다. `"예?"`(되묻기)를 인정으로 읽는 것은 파이썬과 같고 모델이 쓸 가능성이 낮아 그대로 둔다.
- **승인한 뒤 사건 내용 · 기사를 고치면 그 블록의 승인을 지운다(CodeRabbit 2차 리뷰).** 판 비교가 통승인 때만 돌아, 초안 사건의 대본을 승인한 다음 개요(A-11)나 기사(A-13-6 · 8)를 고치면 블록이 `APPROVED`로 남아 사건 공개 때 옛 내용을 말하는 대본이 나갔다.
  - 검토한 대안: (a) 고치는 경로에서 판이 낡은 블록의 승인을 지운다. (b) 공개 조회 · 목록(`scriptReady`)에서 지금 판을 함께 비교한다. (b)는 목록 쿼리가 jsonb `basis`를 사건 · 기사 판과 맞춰 봐야 해 JPQL이 복잡해지고, 2차의 낡음 표시와 겹친다.
  - (a)를 택했다(`CaseScript.revokeStaleApprovals`, `AdminCaseScriptService.revokeStaleApprovals`). 세 경로가 모두 사건 행을 잠근 트랜잭션 안에서 부르므로 승인(A-13-11)과 엇갈리지 않는다. 판은 값이 실제로 바뀔 때만 오르므로 같은 값으로 고치면 지우지 않는다. 반려한 블록은 그대로 둔다. 지웠으면 고친 쪽 감사 로그에 `scriptApprovalRevoked`로 단위를 남긴다.
  - 두 경로 모두 공개한 사건은 고칠 수 없어, 공개 중인 사건의 대본이 갑자기 내려가는 일은 없다.
  - 배역(`castRoles`) · 민감 플래그를 고치는 것도 같은 종류의 낡음이지만, 그 비교는 2차(분류 · 배역 낡음 계산)에서 한다.
- **`pending`이 남아 있으면 승인하지 않는다(CodeRabbit 2차 리뷰).** `pending`에는 단위가 아닌 `"PAPER"`도 들어와, 블록이 다섯 개여도 기사를 만들지 못한 대본이 있을 수 있다. `isApprovable`에 `pending.isEmpty()`를 더했다.
- **API 18의 U2 질문은 `q` · `a`만 담는다(CodeRabbit 2차 리뷰).** 최상위 키만 거르면 질문 안에 모델이 덧붙인 키가 그대로 나간다. `cards`도 안쪽이 겹친 구조라 같은 일이 생길 수 있지만 모양이 깊어 화면 계약을 정할 때(FE-139) 함께 거른다.
- 2차 메모(해송님 추천): `basis`에 없는 키는 "모름 = 낡지 않음 + 표시"로 본다. 이관 · 증거조사만 만든 대본의 `basis`가 일부뿐이라 낡음으로 보면 옛 대본이 모두 처음부터 낡음으로 뜬다.

## 2차-1 블록 단위 검수 · 낡음 표시 (PR #383)

Jira BE-126을 다시 열어 진행한다(1차 머지 뒤 "완료"로 닫았었다). 결정의 근거는 이슈 댓글(10/30 승인 흐름 · 공개 뒤 수정, 11/01 1차 리뷰의 "2차로 넘기는 것")이다. 여기에는 구현에서 고른 방법과 이유만 적는다.

### 문제 / 배경

- 1차는 통승인 · 통거절만 있어, 반려한 대본의 블록 하나를 고치거나 다시 만들어도 승인 상태를 블록마다 다룰 수 없었다(BE-129 재생성 반영도 그 블록만 대기로 돌린다).
- 블록 근거(`basis`)는 1차부터 저장했지만 사건 내용 · 기사 판만 승인 때 비교했다. 배역 · 분류 · 민감 플래그 · 앞 블록이 바뀌어도 화면은 알 수 없었다.
- 관리자가 U0 · U1 · U2 · U4를 손으로 고칠 길이 없었다(U3만 A-13-13).

### 검토한 대안

- **블록 단위 승인을 언제 허용할지**
  - 통거절한 뒤에만: 해송님 흐름("처음엔 통승인, 거절하면 블록 단위")을 서버가 강제한다. 재생성으로 블록 하나만 대기가 된 대본(다른 블록은 승인)을 풀 길이 복잡해진다.
  - **언제든 허용 (택함, 사용자 확정)**: "처음엔 통승인"은 화면 흐름으로 안내한다. 마지막 블록 승인으로 대본이 공개되므로, 블록 승인도 통승인과 같은 대본 조건을 지킨다 — 멈추지 않았고 · `pending`(기사 포함)이 없고 · 대본 전체 검수 오류가 없고, 그 블록에 오류가 없다(`canApproveBlocks`). 처음에는 `pending` · `stopped`를 빠뜨려 블록 하나씩 승인하면 통승인 409를 우회할 수 있었다(PR #383 CodeRabbit 리뷰). 대본의 `publishable`을 그대로 쓰지 않은 이유: 블록 오류까지 합친 값이라 다른 블록 하나의 오류 때문에 멀쩡한 블록도 승인할 수 없게 된다.
- **낡음이 승인을 막는 범위**
  - 모두 표시만(11/01 합의 문장 그대로): 1차에서 이미 막던 사건 내용 · 기사 낡음이 풀린다. 민감 플래그가 바뀐 블록이 가드 없이 공개될 수 있다.
  - 모두 막기: U0 줄이 자동으로 고쳐진 대본은 적재 직후 U2 · U4가 낡음이라(1차 리뷰) 바로 승인할 수 없다.
  - **사건 내용 · 기사 · 민감 플래그만 막고 나머지는 표시 (택함, 사용자 확정)**: `BlockStaleness.BLOCKING`. 막힌 블록은 재생성하거나 "확인했음"으로 푼다. A-11로 민감 플래그를 고치면 사건 내용과 같이 승인한 블록의 승인을 지운다(승인을 막는 낡음이 생기므로).
- **근거에 키가 없을 때**: 11/01 합의대로 "모름 = 낡지 않음 + 표시"(`unknownBasis`). 1차의 판 비교는 키가 없는 것과 `null`을 같게 봐 낡음으로 쳤는데, 2차에서 하나의 규칙으로 맞췄다. 적재는 U1 `basis.paper`를 기사가 없어도 `null`로 채우므로(키는 있다) 실제 대본은 그대로 비교된다.
- **"확인했음"이 바꾸는 것**: 근거 전체를 지금 값으로 맞춘다(바뀐 키만이 아니라). 확인한 시점의 값을 보고 "그대로 둬도 된다"고 판단한 것이라, 그 뒤 다시 바뀌면 다시 낡음이 된다. 내용 · 판 · 검수 상태는 바꾸지 않는다.
- **U0 · U1 · U2 · U4 수정 모양**
  - 블록 내용을 통째로 받는다: 형식은 파이프라인이 정해 서버가 다시 검사해야 한다.
  - **문자열 한 줄을 JSON Pointer로 고친다 (택함)**: 검수 결과의 `path`와 같은 자리라 화면이 오류 줄에서 바로 고칠 수 있다. 이미 문자열이 있는 자리만 고쳐 모양이 바뀌지 않는다. 길이 규칙은 A-13-13과 같다.
- **대사 수정(A-13-13)의 검수 초기화 범위**: 1차는 통승인이라 모든 블록을 대기로 돌렸다. 2차부터 U3만 돌린다(U3를 보고 만드는 뒤 블록은 없다).

### 선택한 방법과 이유

- 낡음 계산은 도메인(`CaseScript.staleness`)에 둔다. 지금 값(`currentBasis`)은 블록 근거와 같은 키 · 같은 모양이다(앞 블록 판, 사건 내용 · 기사 판, 사건의 배역 · 분류 네 축, 정렬한 민감 플래그). 비교는 JSON 숫자(Integer · Long) · 목록 순서 차이를 맞춘 값으로 한다.
- A-13-10 블록에 `stale` · `staleReasons` · `staleBlocksApproval` · `unknownBasis`를 더했다. 저장하지 않고 조회할 때 계산한다 — 사건 값이 바뀔 때마다 블록을 다시 쓸 필요가 없고, 기준이 하나다.
- 블록 단위 API: 승인(A-13-18) · 반려(19) · 확인했음(20) · 문장 수정(21). 사건 행을 잠그고 한다(1차와 같은 잠금). 감사 로그는 기존 액션(`CASE_SCRIPT_APPROVE` · `REJECT` · `UPDATE`)에 `unit`을 담는다 — 액션을 늘리지 않았다.

### 고려한 제약 사항

- U3가 보는 AI 판결 방향 · 판단 요소 문구는 근거 키가 아니라 이번 낡음 계산에서 다루지 않는다. 근거 키 목록은 파이썬 정본(`BLOCK_BASIS`)과 계약 테스트로 묶여 있어, 더하려면 파이프라인부터 바꿔야 한다. 재생성 반영은 BE-129 2차-2가 보낸 입력의 해시로 이미 막는다.
- **공개 중인 사건 (리뷰 반영, PR #383 1번)**: 블록 반려 · 문장 수정 · 대사 수정(A-13-13 포함)은 승인을 지워, 점검 상태(2차-2)가 없는 지금은 체험 중인 사용자의 API 18이 404가 된다(FE-139 "다시 시도"에 갇힌다). 2차-2 전까지 이 셋을 409로 막는다(BE-129 재생성 반영과 같은 방식). 블록 승인 · 확인했음은 대본을 내리지 않아 막지 않고, 통거절(A-13-12)은 잘못 승인한 공개 대본을 내리는 길이라 일부러 둔다.
- **새로 생긴 민감 플래그 (리뷰 반영, 2번)**: 민감 플래그가 새로 생긴 블록은 그 플래그의 가드 문구 없이 만들어졌다. "확인했음"으로 풀면 승인을 막은 이유가 사라지므로 거절하고 재생성만 허용한다. 빠진 플래그는 확인으로 충분하다.
- 지금 값이 없는 키는 "모름"이라, 플래그를 가진 채 만든 블록이 있는데 사건 민감 플래그가 null이면 막지 않는다(리뷰 3번). A-11은 `sensitiveFlags` · `classification`에 null을 받지 않으므로 관리자가 지워서 생기는 경우는 없고, 한 번도 분류하지 않은 사건만 null이다 — 그런 사건은 대본 근거에도 플래그가 없다.
- 기존 적재 테스트 하나(`load_castBalanceCountsPendingImports`)가 develop에서도 깨져 있었다. 테스트가 SQL로 넣는 등록 행은 DB 시계(`now()`), 사건 행은 JVM 시계(`@CreationTimestamp`)라 도커 VM 시계가 늦으면 "마지막 배정" 순서가 뒤바뀐다. 테스트 행도 JVM 시각을 쓰게 고쳤다(운영은 두 행 모두 JVM 시계라 문제가 없다).

### 추후 재검토가 필요하면

- 2차-2: `scriptStatus`(READY · PREPARING · MAINTENANCE) · API 18 503 `SCRIPT_UNDER_MAINTENANCE` · 공개 중 블록 수정 = 점검. BE-129 2차-2가 임시로 막은 "공개 중 재생성 반영"을 그때 연다.
- 프론트: 블록 검수 화면(블록 승인 · 반려 · 낡음 표시 · 확인했음 · 문장 수정).

## 2차-2 대본 상태 `scriptStatus` · 점검 중 (PR #384)

근거: 이슈 설명 "2차"(`scriptStatus: READY | PREPARING | MAINTENANCE`, `scriptReady`는 호환용으로 `scriptStatus == READY`, 공개 뒤 블록 수정 = 점검, API 18은 점검 중 503 `SCRIPT_UNDER_MAINTENANCE`)와 2차-1의 "추후 재검토". 프론트는 FE-145가 이 이름으로 먼저 만들어 두었다(`docs/decisions/FE-145.md`).

### 문제 / 배경

- 대본 승인이 풀리면 API 18은 404였다. 그래서 2차-1(PR #383)과 BE-129 2차-2(PR #381)는 공개 중인 사건의 블록 반려 · 문장 · 대사 수정 · 재생성 반영을 409로 막았다 — 체험 중인 사용자의 대본이 "없음"이 되기 때문이다. 공개 사건의 대본을 고치려면 사건 공개를 취소해야 했다.
- "준비 중"(아직 체험할 수 없는 사건)과 "점검 중"(체험하던 사건을 잠깐 고치는 중)을 화면이 나눠 보일 값이 없었다.

### 검토한 대안

- **점검 중을 어떻게 알아내나**
  - 대본 상태 칸(`status`)을 두고 요청마다 바꾼다: 블록 승인 상태와 따로 저장돼 어긋날 수 있다. 블록 승인을 바꾸는 길(승인 · 반려 · 수정 · 재생성 반영 · A-11 · 기사 수정의 승인 해제)마다 칸도 함께 바꿔야 한다.
  - 사건 공개 여부로만 정한다(공개 사건 + 승인 안 됨 = 점검): 대본이 아직 한 번도 승인되지 않은 공개 사건(대본이 늦게 들어온 경우, 운영의 사건 1이 지금 이렇다)도 점검 중이 된다. 실제로는 준비 중이다.
  - **"처음 나간 시각"만 저장하고 상태는 계산한다 (택함)**: `case_script.released_at`. 상태는 공개 대본이면 READY, 아니면 `released_at`이 있으면 MAINTENANCE, 없으면 PREPARING이다. 블록 승인 상태는 그대로 정본이고, 더한 것은 "한 번 나갔다"는 사실 하나다.
- **"나갔다"의 기준**
  - 다섯 단위가 처음 모두 승인된 때: 초안 사건에서 승인만 한 대본을 고치면 공개 전인데도 점검 중이 되고, 그 뒤 사건을 공개하면 사용자가 본 적 없는 대본이 "점검 중"으로 보인다.
  - **사건이 공개된 상태에서 다섯 단위가 모두 승인된 첫 순간 (택함)**: 사용자가 실제로 받을 수 있게 된 때다. 둘 중 나중에 채워지는 쪽에서 남긴다 — 대본 승인(A-13-11 · 18) 때 사건이 공개돼 있으면, 사건 공개(A-13) 때 대본이 승인돼 있으면. 공개 취소 · 통거절 뒤에도 지우지 않는다(한 번 나간 대본이다).
- **공개 중 막기를 어떻게 바꾸나**
  - 막기를 남기고 "점검 시작" API를 따로 둔다: 관리자가 한 단계 더 거친다. 승인을 푸는 길이 여럿이라 그 API를 거치지 않은 경우도 막아야 한다.
  - **막기를 빼고, 승인이 풀린 동안을 점검 중으로 본다 (택함, 이슈 설명 "공개 뒤 블록 수정 = 점검")**: 블록 반려 · 문장 · 대사 수정(PR #383) · 재생성 반영(PR #381 `CASE_PUBLISHED`)의 409를 뺐다. 체험 중인 사용자는 받아 둔 대본으로 이어 간다(FE-145). 누가 내렸는지는 감사 로그에 남긴다(`scriptMaintenance: true`, READY → MAINTENANCE가 된 요청만).
- **API 18이 점검 중에 내려줄 것**: 마지막 승인 대본을 계속 주는 방법은 승인 이력 · 블록 이전 판을 저장해야 해 범위가 커진다. 503으로 알리고, 이어 가기는 화면이 받아 둔 대본으로 한다(FE-145 합의).

### 선택한 방법과 이유

- 상태 계산은 `ScriptStatus.of(CaseScript)` 한 곳이다. API 16 · 18은 대본 행으로, API 1 · C-6 목록은 쿼리 두 번(모두 승인한 사건 · `released_at`이 있는 사건)으로 같은 규칙을 쓴다(`CaseScriptRepository.findScriptStatuses`). 목록이 사건마다 대본을 읽지 않는다.
- `scriptReady`는 지우지 않고 `scriptStatus == READY`로 둔다(이슈 설명, 화면 호환). 커뮤니티 메인 C-6도 API 1과 같은 값을 쓰므로 `scriptStatus`를 함께 붙였다(FE의 `isScriptReady`가 세 화면에서 같은 기준이다).
- 관리자 쪽: A-13-10에 `scriptStatus` · `releasedAt`, A-6 `script`에 `scriptStatus`. 화면이 "이 대본을 고치면 점검 중이 된다"를 미리 알릴 수 있다.
- 이관: 이미 공개 사건 + 모두 승인인 대본은 마지막 승인 시각(공개 시각이 더 늦으면 공개 시각)으로 채운다. 운영은 대본이 0행이라 개발 · 로컬 DB용이다.

### 고려한 제약 사항

- 사건 내용 · 기사 · 사진의 "공개 중이면 409"(8-3 #1 · #9)는 그대로다. 그쪽은 사건 내용이라 이미 체험한 사용자의 결과가 바뀐다. 대본은 체험 연출이라 점검으로 충분하다. 그래서 A-11 · 기사 수정의 승인 해제(`revokeStaleApprovals`)는 공개 중인 사건에서 일어나지 않는다(공개 취소한 사건에서 일어나면 그 사건은 사용자에게 보이지 않는다).
- 점검 중에도 승인 조건(낡음 · 오류 · `pending`)은 그대로다. 점검을 빨리 끝내려고 조건을 느슨하게 하지 않는다.
- 503은 서버 장애로 오해될 수 있지만, 이슈 설명과 프론트(FE-145)가 이미 이 코드로 맞춰 두었다. 본문 `code`로 장애(다른 코드)와 구분한다.

### PR #384 리뷰 반영

- **공개 중 수정의 관리자 쪽 안전장치 (1번)**: 서버는 막지 않는다(이 PR의 설계). 대신 관리자 화면이 `releasedAt`이 있는 대본을 고치기 전에 "다시 승인할 때까지 점검 중이 된다"를 확인받는다 — 후속 이슈 FE-148(관리자 대본 블록 검수 화면 · 공개 중 수정 점검 안내)으로 잡았다.
- **V48의 `= 5` (2번)**: 이 시점의 단위 수(U0 ~ U4, `chk_case_script_block_unit`)다. 마이그레이션은 한 번 돌고 끝나 리터럴로 둔다. 실행 중 판정은 `CaseScriptRepository.findApprovedCaseIds`가 `ScriptUnit` 개수로 한다. **주석을 V48에 더하지 않았다** — 주석만 바꿔도 Flyway 체크섬이 바뀌어, 이 브랜치로 V48을 이미 돌린 DB(로컬 · 테스트)가 `Validate failed`로 뜨지 않는다(실제로 테스트 DB에서 겪었다).
- **V48 이관 UPDATE 확인 (3번)**: 빈 DB 테스트에서는 0행이라 테스트 DB에서 트랜잭션 안에 사건 넷을 만들어 V48의 UPDATE 문을 그대로 돌리고 되돌렸다 — 공개 + 다섯 승인(승인이 나중)은 마지막 승인 시각, 공개 + 다섯 승인(공개가 나중)은 공개 시각, 초안 + 다섯 승인 · 공개 + 네 승인은 null.
- **503의 헤더 (5번)**: `Retry-After: 60`을 붙인다(`ApiExceptionAdvice`, 이 코드에만). 캐시 금지는 Spring Security 기본 `Cache-Control: no-store`가 이미 붙어 테스트로 고정했다. 프록시가 본문을 바꾸는지: 앞단 nginx는 `error_page 429`만 쓰고 `proxy_intercept_errors`가 없어 백엔드 503 본문(`code`)이 그대로 간다. 운영은 ALB 없이 이 nginx가 바로 TLS를 받는 한 대 구성이라(BE-75 — ALB · CDN은 검토 뒤 두지 않았다) 앞단은 이것뿐이다. 그래도 배포 뒤 운영 주소로 API 18 503 응답의 본문 `code`와 헤더가 그대로 오는지 한 번 확인한다(앞에 ALB · CDN을 두게 되면 그때 다시 본다).
- **감사 로그 `scriptMaintenance` (6번)**: 사건 공개 여부는 보지 않는다(공개 취소한 사건에서 승인을 풀어도 남는다). 사용자 영향이 없는 경우라 로그가 조금 더 남을 뿐이라 그대로 둔다.
- **공개 사건 대본을 다시 만들어 반영하는 운영 절차 (리뷰 의견)**: 반영(A-13-17)하는 순간 그 사건은 점검 중이다. 여러 사건을 다시 만들 때는 **한 건씩** 반영 → 바로 그 블록 검수 · 승인(A-13-18)까지 이어서 해 점검 시간을 짧게 둔다. 여러 건을 먼저 반영해 두고 나중에 몰아 승인하지 않는다. 재생성 요청(A-13-15)과 결과 확인(A-13-16)은 대본을 내리지 않아 미리 해 둬도 된다.
- **CodeRabbit**: API 명세에 남아 있던 "승인이 풀리면 404 · 준비 중" 문구(API 1 · 16 · 18)를 나간 적 없는 대본에만 해당하도록 고쳤다. READY에서 바로 문장 · 대사를 고치는 경로도 점검 전이 · 503 · 감사 로그를 각각 테스트한다. 커뮤니티 메인 테스트는 대상 사건이 "이야기 많은 사건" 셋에 꼭 든다고 단정하지 않는다(공용 테스트 DB라 다른 이야기에 밀릴 수 있다) — 대신 실린 사건마다 `scriptStatus`가 세 값 중 하나인지 늘 본다.

### 추후 재검토가 필요하면

- 점검이 길어질 때 알림(운영 경보)은 두지 않았다. `released_at`이 있는데 오래 READY가 아닌 대본을 찾는 쿼리로 나중에 붙일 수 있다.
- 프론트: 관리자 대본 화면의 점검 안내(`releasedAt`), FE-145의 `scriptStatus` 이름 · 503 형식 확인.
