# FE-72 의사결정 기록

## 문제 / 배경
- BE-93 2차(PR #242)가 적재를 **별도 엔드포인트 A-14-1**(`POST /admin/case-imports/{importId}/load`)로 두었다 —
  2초마다 불리는 조회(A-15)에서 적재하면 같은 사건이 여러 번 만들어질 수 있어서다. 그래서 "관리자가 버튼을
  누른다"는 화면 작업이 남았다(`docs/decisions/BE-93.md` 2차 "검토한 대안 2").
- 그때까지 `adminRegisterPage.js`는 `SUCCEEDED`면 `caseId`가 있다고 보고 **"사건 #null"** 문구와 깨진 주소의
  검수 버튼을 띄웠다(BE-93 1차 문서가 "화면에 남는 문제"로 명시해 둔 항목).
- 실제 모드의 사건 등록 메뉴는 `serverReady: false`로 닫혀 있었다 — API 명세 A-15가 "2차 전에 메뉴를 열려면
  `caseId == null`을 다루는 처리가 화면에 먼저 있어야 한다"고 조건을 달아 두었다.

## 검토한 대안

### 1. 목(mock)도 적재를 두 단계로 나눌까
- 대안 A — 목은 그대로 둔다(생성이 끝나면 목이 바로 사건을 만들고 `caseId`를 채운다). 목 모드 화면이 지금처럼
  동작하니 손댈 것이 없다.
  - 단점: **목 모드에서는 적재 버튼 흐름을 한 번도 볼 수 없다.** 화면 개발 · 시연이 모두 목 모드인데, 정작
    새로 만든 경로가 목에서는 죽은 코드가 된다.
- 대안 B(선택) — 목도 실제 서버와 같이 생성이 끝나면 `caseId`를 `null`로 두고, `loadImport`를 불러야 사건이
  생긴다. `adminMockApi.js` 머리말의 "목과 실제는 함수 이름 · 인자 · 응답 형식이 같다"는 규칙을 응답 **흐름**까지
  지키는 쪽으로 읽었다.
- 같은 이유로 늘 건너뛰는 세 단계(`contamination` · `rag` · `load`)도 목이 `SKIPPED`로 내려주게 맞췄다 —
  실제 서버는 이 셋을 항상 건너뛰는데(COMMON-50) 목만 `DONE`으로 칠하면 단계 표시를 실제와 다르게 개발한다.

### 2. 적재가 거절됐을 때 다시 누르게 할까
적재 거절은 성격이 둘로 갈린다.
- 대안 A — 모두 "다시 시도" 버튼으로 둔다. 코드가 단순하다.
  - 단점: `DUPLICATE_TITLE`(같은 제목의 사건이 이미 있음) · `IMPORT_RESULT_INVALID`(생성 결과 자체가 잘못됨)는
    **다시 눌러도 같은 결과다.** 눌러 볼 수 있게 두면 관리자가 같은 버튼을 반복해서 누른다.
- 대안 B(선택) — 두 코드만 버튼을 "입력으로 돌아가기"로 바꾸고 새로 생성하도록 안내한다. 나머지
  (`IMPORT_UNAVAILABLE` 등 일시적 실패)는 적재 버튼을 그대로 남겨 다시 누를 수 있게 한다.

### 3. 화면을 닫은 뒤 끝난 생성을 어떻게 적재할까
적재가 수동이 되면서 생긴 구멍이다. 생성은 수십 분 걸리고 `importId`는 화면 메모리에만 있었다. **관리자가 탭을
닫으면 끝난 생성을 아무도 사건으로 만들 수 없다** — 등록 작업 목록 API도 없어서 번호를 되찾을 길이 없다.
(1차까지는 적재가 자동이라 "화면을 닫아도 끝나면 검수 목록에 올라와요"가 사실이었다.)
- 대안 A — 그대로 두고 "이 화면을 닫지 마세요"로 안내한다. 저장소를 건드리지 않는다.
  - 단점: 수십 분짜리 작업에 탭을 붙잡아 두라는 안내는 지켜지지 않는다. 지켜지지 않으면 생성 결과가 버려지고,
    판결문 원문도 파이프라인 볼륨에 남는다(COMMON-51이 치울 때까지).
- 대안 B — 등록 작업 목록 API(A-14 계열 신설)를 서버에 요청해 "적재 대기 중인 등록"을 목록으로 보여준다.
  - 가장 깔끔하지만 **서버 작업이 새로 생긴다.** 10/30 통합 테스트 전에 BE 범위를 늘릴 이유가 약하다.
- 대안 C(선택) — **작업 번호만** `sessionStorage`에 남겨, 같은 탭에서 등록 화면을 다시 열면 진행 상황 · 적재
  버튼으로 돌아온다. 번호가 가리키는 작업이 없으면(`IMPORT_NOT_FOUND`) 지우고 입력 화면으로 보낸다.
  - 판결문 원문은 저장하지 않는다는 원칙(FR-5-3)을 지킨다 — 작업 번호만으로는 사건 내용을 알 수 없다.
  - 저장소를 못 쓰는 환경(사생활 보호 모드 등)에서도 깨지지 않게 읽기 · 쓰기를 `try/catch`로 감쌌다.

### 4. 실제 모드 메뉴를 이번에 열까
- 대안 A — 계속 "준비 중"으로 둔다. 운영에 파이프라인 서비스를 아직 켜지 않았다(COMMON-50 — RDS 전환 뒤로 미룸).
  - 단점: 메뉴를 닫아 두면 **운영에서 등록 흐름을 한 번도 확인할 수 없다.** 서비스를 켜는 시점에 화면까지
    처음 시험하게 된다.
- 대안 B(선택) — 연다. API 명세가 걸어 둔 조건(`caseId == null` 처리)을 이번 작업이 채웠고, 서비스를 켜지 않은
  서버에서 등록을 시도하면 `502 IMPORT_UNAVAILABLE` 안내가 뜬다(이번에 문구를 추가했다). 되돌리려면 플래그
  한 줄이라 위험도 낮다.

## 선택한 방법과 이유
- `adminRealApi.js`에 `loadImport(importId)`(A-14-1) 추가. `adminMockApi.js`는 `finishImport`를
  `succeedImport`(생성만 끝냄)와 `loadImport`(사건 · 판결 후보 생성)로 나눴다.
- 목 전용 실패 표식을 기존 `[실패]` 관례에 맞춰 늘렸다 — `[제목중복]` → `DUPLICATE_TITLE`,
  `[적재실패]` → `IMPORT_RESULT_INVALID`(`details[].field` 포함). 표식은 등록할 때 읽어 두고 원문은 목에도
  남기지 않는다.
- `adminLabels.js`에 `IMPORT_NOT_READY` · `IMPORT_RESULT_INVALID` · `IMPORT_UNAVAILABLE` 안내를 추가했다.
  `IMPORT_RESULT_INVALID`는 서버가 준 `details[].field`(예: `case.factors[2].label`)를 그대로 보여준다 —
  BE-93이 "관리자가 보는 화면에 그대로 쓸 수 있어야 한다"며 경로를 담아 주기로 한 값이다.
- `IMPORT_STAGE.load` 라벨을 "DB 적재 (서버가 따로 해요)"로 바꿨다. 항상 `SKIPPED`인 단계라 그냥 "DB 적재"로
  두면 적재가 빠진 것처럼 읽힌다.
- `adminRegisterPage.js`: `SUCCEEDED`를 `caseId` 유무로 나눠 그린다. 없으면 "사건으로 만들기"(적재) 버튼,
  있으면 완료 문구 · 검수 화면 · 새 등록 버튼. 머리글도 "생성을 마쳤어요" / "등록을 마쳤어요"로 구분한다.
- `adminMenu.js`에서 사건 등록의 `serverReady: false`를 지우고, `docs/information-architecture.md` S-19
  설명을 2단계 흐름으로 맞췄다.

## 고려한 제약 사항
- 적재 실패 중 `DUPLICATE_TITLE`의 안내는 "제목을 바꿔 다시 등록"이라고 쓰지 않았다 — 제목은 파이프라인이
  만들고 **등록 폼에 제목 입력칸이 없다.** 관리자가 실제로 할 수 있는 일(다시 생성하거나 이미 있는 사건 확인)로
  문구를 적었다.
- 적재는 한 트랜잭션이고(BE-93 2차) 두 번 부르면 `IMPORT_NOT_READY`로 거절되므로, 버튼 중복 클릭은 화면에서도
  `loadBusy`로 막되 서버 거절에 의존해도 안전하다.
- 작업 번호 복원은 **같은 탭** 안에서만 동작한다(`sessionStorage`). 다른 기기 · 다른 브라우저에서 이어 적재해야
  하면 등록 작업 목록 API가 필요하다(위 대안 B).

## 추후 재검토가 필요하면
- **등록 작업 목록 API**: 적재 대기 중인 등록을 여러 관리자가 나눠 처리하거나 다른 기기에서 이어야 하면
  서버에 목록 API를 요청한다. 그때 `sessionStorage` 복원은 지워도 된다.
- **멎은 작업**: 파이프라인이 살아 있는 채 멎으면 화면은 계속 "실행 중"을 보여준다(BE-93 "남겨 둔 것"). 서버에
  상한 · 중단 API가 생기면 화면에도 중단 버튼을 둔다.
- **파이프라인 서비스를 켠 뒤**: 실제 모드로 등록 한 건을 끝까지 돌려 단계 표시 · 적재 · 검수 연결을 확인해야
  한다. 이번 작업은 목 모드 기준으로만 확인했다.

## PR #285 리뷰 반영

### 적재 뒤 `IMPORT_NOT_READY`를 받으면 화면이 막혔다
서버는 `IMPORT_NOT_READY`를 세 경우에 쓴다 — ① 이미 적재함 ② 생성이 안 끝남 ③ 생성 결과가 사라짐.
화면은 이 코드를 "다시 눌러도 되는 실패"로 보고 버튼을 남겨 두었는데, ①(탭을 두 개 열었거나 적재는 됐는데
응답만 유실된 경우)에서는 다시 눌러도 같은 거절만 받고 `caseId`가 비어 있어 검수 화면으로 갈 길도 없었다.
- 대안 A — `loadBlocked`에 `IMPORT_NOT_READY`를 더해 늘 "입력으로 돌아가기"로 보낸다. 한 줄이지만 ①에서
  **이미 만들어진 사건을 두고 새로 등록하게** 만든다.
- 대안 B(선택) — 거절을 받으면 상태(A-15)를 한 번 다시 묻는다. 세 경우를 화면이 직접 구분할 수는 없지만
  **다시 물으면 갈라진다**: `caseId`가 채워져 있으면 ①이라 그대로 완료 화면으로 잇고, 아직 `QUEUED` · `RUNNING`이면
  ②라 진행 상황으로 돌아가 폴링을 다시 시작하고, 적재도 안 됐는데 생성이 끝나 있으면 ③이라 새로 등록하게 막는다.
  조회 자체가 실패하면 일시적인 문제일 수 있어 버튼을 남긴다.
- ③의 안내는 `errorText`의 고정 문구("생성이 끝났는지 확인해 주세요")와 맞지 않아, 서버가 준 `message`가 있으면
  그 문구를 먼저 쓴다(`VALIDATION_ERROR`가 이미 쓰던 방식과 같다).
- 목에도 `[결과소실]` 표식을 더해 ③을 목 모드에서 눌러 볼 수 있게 했다.

### 적재가 끝나도 작업 번호가 남았다
`sessionStorage`의 번호는 "끝난 생성을 적재하러 돌아오기" 위한 것이라, 적재가 끝나면(`caseId`가 채워지면)
들고 있을 이유가 없다. 그대로 두면 사이드바로 나갔다 사건 등록을 다시 열 때 새 등록 폼 대신 완료 화면이 떴다.
`caseId`가 있는 응답을 그릴 때 지운다.
