# FE-19 의사결정 기록

> 확장 단계(WBS 7.7.2) · PR #142 · 담당 정민석

## 문제 / 배경
- S-02(신문형 사건 목록)에 사용자 본인의 체험 진행 상태(진행 중 / 완료)를 배지로 보여주고, 버튼 문구도 "체험 시작 / 이어서 하기 / 결과 다시 보기"로 나눠야 했다.
- FE 이슈지만 이 값을 계산하려면 서버가 "이 사건에 대해 이 사용자가 어디까지 했는지"를 알려줘야 해서, 백엔드(API 1 `myStatus` 필드)와 프론트를 한 PR로 묶었다.
- 이미 마이페이지(API 2 · 3)에 "사건마다 최신 회차"를 구하는 로직(`findLatestPerCase`)이 있어, 이를 그대로 쓸지 새로 만들지 정해야 했다.

## 검토한 대안
- API 1 응답에 `myStatus`를 넣는 방법: 마이페이지용 `findLatestPerCase`를 재사용할지, 목록 API 전용 조회를 새로 만들지 검토했다.
- 익명 ID 쿠키 처리 방식: 목록 조회 시점에 쿠키가 없으면 새로 발급할지, 조회만 하고 발급은 하지 않을지 검토했다.

## 선택한 방법과 이유
- **기존 `findLatestPerCase` 재사용**: 마이페이지(API 2 · 3)와 "사건마다 최신 회차" 판단 기준을 동일하게 가져가, 목록에서 보는 상태와 마이페이지에서 보는 상태가 어긋나지 않게 했다. 사건 목록 조회 한 번에 전체 사건의 최신 회차를 같이 가져와 N+1을 피했다.
- **익명 ID 쿠키는 읽기만 하고 발급하지 않음**: 목록 조회는 로그인 여부와 무관하게 누구나 호출하는 화면이라, 여기서 쿠키를 새로 발급하면 단순 조회만으로 익명 사용자가 생겨난다. 쿠키가 없거나 형식이 잘못됐거나 존재하지 않는 ID면 `myStatus`를 `null`로 돌려준다.
- **버튼 문구만 상태에 따라 분기, 이동 로직은 그대로**: 어느 화면으로 이동할지는 기존처럼 API 2 응답 상태로 결정하고, 이번 PR에서는 문구와 오류 문구(`STATUS_VIEW`)만 상태에 맞춰 바꿨다. 이동 로직까지 새로 만들면 기존 플로우와 중복되는 상태 판단이 두 곳에 생긴다.
- **배지 색은 기존 의미 토큰 재사용**: 진행 중 = accent, 완료 = muted. 이 PR만을 위한 색을 새로 추가하지 않았다.

- 사건 목록을 캐시하게 되면(6.5.3) `myStatus`는 사용자마다 다른 값이라 캐시 대상에서 빼야 한다는 제약을 "확인 사항"으로 남겼다.
