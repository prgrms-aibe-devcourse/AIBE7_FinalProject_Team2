# BE-83 의사결정 기록

> 확장 단계 · 담당 정민석 (D) · 관련: FE-132, FE-44, BE-96, BE-97, BE-106

## 문제 / 배경
- 마이페이지 컬렉션(FE-44 2차)은 체험 기록에서 모은 목록을 그때그때 계산했다(A안). 획득 시점 · "새로 얻음" 표시처럼 **수집 상태를 기억해야 하는 요구**가 생겨(BE-83 댓글, 2026-10-29) 서버에 저장하는 B안으로 진행한다.
- BE-96에서 수집 도전과제 2개(`collect-5` · `collect-20`)는 서버가 셀 수 없어 `PENDING`(잠김)으로 남아 있었다. 그 보상도 저장할 수 없었다.
- BE-96이 범위에서 뺀 도전과제 "새로 열림" 기록도 함께 다룬다(BE-96 · BE-83 댓글).
- 계약은 FE-132 담당(김해송)과 BE-83 댓글로 정했다. 댓글에서 정하지 않은 세부 사항은 이 문서 "백엔드에서 정한 것"에 적는다.

## 검토한 대안

### 1. 획득 조건을 누가 판정하는가
- 대안 A: 서버가 대본(역할 의상 · 신문 사진 · 증거 사진)을 갖고 판정한다. 대본은 서버에 없고, 조건이 자주 바뀔 예정이라 바뀔 때마다 백엔드를 고쳐야 한다.
- **대안 B(선택): 판정은 화면(`collectionOf` · `castOf`)이 계속 하고, 서버는 항목 · 획득 시각 · 확인 여부만 저장한다.** 조건이 바뀌어도 백엔드 수정이 거의 없다. 서버가 판정해야 하는 조건(점수 기준 등)이 생기면 그때 따로 협의한다.

### 2. 조작 방어
- 서버가 항목 목록을 모르므로 가짜 항목 id로 수집 도전과제 보상을 열 수 있다.
- 대안 A: 서버 화이트리스트(사건별 항목 id 목록). 대본이 서버에 없어 지금은 만들 수 없다.
- **대안 B(선택): 최소 검증** — 그 사건을 완료했는지, 형식(종류 · id 정규식), 종류별 상한(일러스트 사건당 5 · 의상 사용자당 12). 획득 시각은 서버 시각.
- **재검토 조건: 랭킹처럼 다른 사용자와 비교하는 기능에 `collected`(또는 이로 생기는 XP · 레벨)를 쓰기 전에 서버 화이트리스트 검증으로 바꾼다.** 지금은 백엔드에 랭킹이 없어 영향이 본인 화면 · 본인 레벨에 그친다.
- → **BE-136에서 화이트리스트로 바꿨다**(커뮤니티 레벨 랭킹 C-6). 일러스트는 공개 사건의 규칙 이름, 의상은 역할 의상 그림. 의상 사용자당 상한 12는 지웠다(`docs/decisions/BE-136.md`).

### 3. key 범위 — 사건별 vs 그림별
- 처음 안은 사건별 key(`{caseId}:paper` 등)였다.
- **그림별 key로 바꿨다(김해송 최종 정리).** 사건 사진을 배경 / 시간대 / 일러스트로 쪼개 합성할 계획이라 같은 일러스트를 여러 사건에서 다시 쓴다. 사건별 key면 같은 그림이 사건마다 따로 세어져 목표값이 의미를 잃는다.
- 저장 단위: `kind`(`illustration` · `cast`, 이후 `background` · `time`) + `item_id` + `case_id`(처음 얻은 사건). 기본 키는 (사용자, `kind`, `item_id`).

### 4. 의상(cast)을 수에 넣는가
- 정민석 의견: 의상은 "만난 모습"으로 따로 다루고 수에서 뺀다.
- **김해송 최종 정리(선택): 의상도 `collected`에 넣는다.** 같은 테이블에 `kind`만 다르게 저장하므로 추가 부담이 작다. 의상은 사건과 무관한 같은 옷이라 전체 최대 8가지이고, "새로 얻음"도 처음 만났을 때 한 번만 뜬다.

### 5. 도전과제 해금 기록 시점
- 판정은 저장하지 않고 계산하므로, "언제 처음 CLEARED가 됐는가"를 남길 곳이 필요하다.
- 대안 A: 해금을 만드는 모든 요청(체험 완료 · 출석 · 성향 테스트 · 수집)에서 기록한다. 기록 지점이 흩어지고 하나라도 빠뜨리면 기록이 없다.
- **대안 B(선택): 판정하는 곳에서 기록한다 — 마이페이지 조회(P-5)와 수집 기록(P-9).** 해금 시각은 "서버가 처음 판정해 기록한 때"라 실제 달성보다 조금 늦을 수 있지만, 화면은 마이페이지에서만 "새로 열림"을 보여 주므로 차이가 없다.
- 마이페이지 조회는 읽기 전용이라 기록은 **별도 트랜잭션**(`REQUIRES_NEW`)에서 한다. 수집 기록은 같은 사용자 행을 잠근 트랜잭션이라 **같은 트랜잭션**에서 한다(별도 트랜잭션을 열면 FK 검사가 그 잠금을 기다려 교착된다).
- **조회 트랜잭션 밖에서 기록한다** (PR #335 리뷰). 처음에는 조회 전체를 읽기 전용 트랜잭션으로 묶고 그 안에서 `REQUIRES_NEW`를 열어, 조회가 연결을 잡은 채 기록이 두 번째 연결을 기다렸다. 운영 풀(`EXTERNAL_DB_POOL_SIZE`, 기본 5)만큼 해금 조회가 동시에 오면 모두 두 번째 연결을 기다리며 대기 시간(Hikari 기본 30초)만큼 멈추고, 그동안 다른 요청도 연결을 얻지 못한다. 그래서 `MyPageService.get`은 메서드 전체에 트랜잭션을 걸지 않고 **사용자 찾기 → 통계 읽기 → 해금 기록 → 읽기 전용 조회 조립**을 차례로 열고 닫아 연결을 한 번에 하나만 쓴다(`open-in-view`가 꺼져 있어 조회 조립은 `TransactionTemplate` 읽기 전용으로 묶는다). `MyPageUnlockFailureTest`가 기록 중 사용 중인 연결이 1개인지 확인한다(수정 전 구조에서는 2개로 실패).
- 기록 트랜잭션은 **새로 남길 해금이 있을 때만** 연다(`AchievementJudge.unrecordedClears`가 비면 열지 않는다). 대부분의 조회는 새 해금이 없다.
- 기록에 실패해도 **마이페이지는 그대로 내려 준다**(경고 로그만). 판정은 계산값이라 화면은 같고, 다음 조회 때 다시 기록한다.

## 선택한 방법과 이유

### 저장 (V35)
- `collection_item` · `achievement_unlock` 두 테이블(ERD 13장). 형식은 V22 · V23과 같다(`uuid` + `anonymous_user` FK, `timestamptz`, CHECK 없음).
- FK는 `ON DELETE CASCADE`: 익명 사용자에 딸린 기록이고 운영에서는 익명 사용자를 지우지 않는다. 마이페이지 조회가 해금을 기록하게 되면서, 익명 사용자를 지우는 기존 테스트 정리 코드가 이 테이블을 몰라도 되게 했다.
- 저장은 `INSERT … ON CONFLICT DO NOTHING`(출석과 같다). 이미 가진 항목 · 이미 기록된 해금은 조용히 건너뛰어 처음 시각이 남는다.

### 판정 (`AchievementJudge`)
- `ProfileStats`에 `collected`(= `collection_item` 행 수)와 해금 기록(`unlocks`)을 넣었다. 판정 함수의 모양은 그대로이고, 경험치(`LevelXp`) · 꾸미기 잠김 검사(`ProfileDecoValidator`)도 같은 값을 쓴다.
- **해금 기록이 있으면 계산값과 상관없이 `CLEARED` · `value = goal`.** BE-96 원칙("열렸던 도전과제는 다시 잠기지 않는다")을 표가 바뀌는 경우까지 넓혔다. 보상도 계속 열려 있다.
- `PENDING`은 이제 나오지 않지만 값은 남긴다(이후 서버가 셀 수 없는 값이 생길 때).

### API (API 명세 v0.63)
- P-9 `POST /collection`: 완료한 사건의 항목을 한 번에(1 ~ 20개). 멱등. 응답에 새로 저장된 항목 · 모은 수 · 새로 해금된 도전과제.
- P-10 `POST /collection/seen`: 항목 지정 또는 종류 전부. P-11 `POST /achievements/seen`: 도전과제 id 목록. 둘 다 204 · 멱등. 항목 지정은 종류별로 묶어 `IN`으로 UPDATE를 한 번씩만 보낸다(종류가 일러스트 · 의상이라 많아야 2번, 최대 100건을 항목마다 보내지 않음, PR #335 리뷰).
- P-5 `collection` 추가, `achievements[]`에 `unlockedAt` · `isNew` 추가.
- 거절: 쿠키 없음 · 체험 없음은 404 `EXPERIENCE_NOT_FOUND`(익명 ID를 발급하지 않는다, L-3 SNS 보상과 같다), 미완료는 409 `INVALID_STATE` + `currentStatus`, 상한 초과는 409 `COLLECTION_LIMIT_EXCEEDED`(신설). 새 에러 코드는 상한 하나만 만들고 나머지는 기존 코드를 썼다.

## 배포 순서 (FE-132와 함께)
- 이 변경만 먼저 운영에 나가면 수집 도전과제가 "준비 중"(`PENDING`)에서 `0 / 5`(`IN_PROGRESS`)로 바뀐다. 화면은 아직 P-9를 부르지 않아 서버 수집 수가 0이고, 마이페이지 "모은 일러스트 N장"(화면이 기록에서 센 값)과 어긋나 보인다.
- 그래서 **develop 머지는 바로 해도 되지만, main(운영) 반영은 FE-132(획득 전송 · 백필)와 같은 배포로 묶는다.**
- 화면 목(`profileDecoMockApi.js`)은 아직 수집 도전과제를 `PENDING`으로 흉내 낸다. FE-132에서 서버 응답(`IN_PROGRESS` · `collection` · `isNew`)에 맞춘다.

## 고려한 제약 사항
- 서버는 항목 id의 의미를 모른다 → 가짜 id는 상한까지 막지 못한다(위 재검토 조건). → BE-136에서 해결.
- 해금 시각은 첫 판정 시각이다. 체험 완료 직후가 아니라 다음 마이페이지 조회 때 기록될 수 있다.
- 로그인한 회원도 지금은 이 브라우저의 익명 ID 기준으로만 모인다(출석 · 꾸미기와 같다).
