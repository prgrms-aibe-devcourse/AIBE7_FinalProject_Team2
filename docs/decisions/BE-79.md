# BE-79 의사결정 기록

## 문제 / 배경
- 체험 화면 상단 바(S-04 ~ S-09)에 사건 제목 · 죄명이 필요한데, S-04 이후 화면의 API(API 6 등)에는 사건 제목이 없다. 정합성 점검 D-01에서 공급원을 정하기로 하고, 프론트는 임시로 사건 목록(API 1)에서 `caseId`로 제목을 찾아 썼다.
- 임시 방식의 남은 문제: 목록 응답에 죄명이 없어 범죄 유형(살인 · 사기 · 상해) 또는 분류명(`crimeCategoryLabel`, 예: 재산범죄)으로 대신했고, 실제 죄명과 다를 수 있었다(횡령 성격 사건이 `crimeType=FRAUD`인 경우 등). 사건 개요(API 4)를 지나야 정확한 죄명으로 갱신됐다.

## 검토한 대안
- 대안 A: S-04 ~ S-09 화면 API 응답마다 `case: { caseId, title, chargeName }` 추가. 화면 진입 시 추가 요청이 없고 새로고침에도 안전하다. 반면 백엔드 API · 명세 · 목 데이터를 여러 곳 고쳐야 하고 같은 필드가 응답마다 중복된다.
- 대안 B: 공통 사건 헤더 API(`GET /cases/{caseId}/header` 같은 가벼운 API) 신설. 공급원이 한 곳이고 프론트 변경이 작다. 반면 요청이 하나 늘고 새 API · 명세가 필요하다.
- 대안 C: API 1 응답에 `chargeName`만 추가하고 현재 방식(목록에서 `caseId`로 찾기) 유지. 백엔드 변경이 필드 1개로 가장 작다.
- 대안 D: API 4(사건 개요)를 공급원으로 통일. 새 API가 필요 없지만, 개요 화면을 거치지 않는 진입(새로고침 · 주소 직접 입력)을 따로 처리해야 해서 화면 호출 순서에 의존하게 된다.

## 선택한 방법과 이유
- **대안 C.** 임시 방식의 실제 문제는 "죄명이 부정확하다" 하나였고, C는 필드 하나로 해결한다.
- 새 API · 화면별 응답 변경 없이 MVP 일정 안에서 끝나고, 사건 수가 적어 목록 조회 비용도 작다.
- 프론트의 `exact` 구분과 범죄 유형 대체 라벨이 필요 없어져 `caseHeader.js`가 단순해졌다.

## 고려한 제약 사항
- 사건 목록(API 1)은 상태와 관계없이 열려 있어 어느 화면에서든 호출할 수 있다.
- 새로고침 · 주소 직접 입력으로 S-04 이후 화면에 바로 들어와도 상단 바가 동작해야 한다.
- 사건 수가 적은 MVP 단계(현재 9건)다.

## 추후 재검토가 필요하면
- 목록에 페이지네이션 · 검색이 들어가 `caseId`로 목록에서 찾는 방식이 깨질 때, 또는 사건 수가 늘어 목록 전체를 받는 비용이 커질 때: **대안 B**(공통 사건 헤더 API)로 옮긴다. 프론트는 `loadCaseHeader` 한 곳만 바꾸면 된다.
- 상단 바 외 화면에서도 제목 · 죄명이 필요해져 화면마다 같은 조회를 반복하게 되거나, 사건 상태에 따라 노출 규칙이 달라져 서버가 화면별로 정해 줘야 할 때: **대안 A**를 검토한다.
