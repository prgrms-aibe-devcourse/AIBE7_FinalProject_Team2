# BE-15 의사결정 기록

> MVP 단계(WBS 4.4) · PR #30, #58 · 담당 백승호

## 문제 / 배경
- MVP의 AI 판결은 실시간 LLM 호출 없이, 오프라인에서 생성·검수한 뒤 DB에 적재하는 방식으로 만들어야 했다. LLM 제공사가 기술 스택 단계에서 아직 미정이었기 때문이다.
- 생성된 판결이 모델의 사전 학습(사건을 이미 알고 있는 상태)에 오염되지 않았는지 점검(REQ-102)하고, 출력이 형벌·감경 조합·선고 범위·집행유예 규칙을 지키는지 검증해야 했다.

## 검토한 대안
- **도구를 서비스 코드(backend) 안에 둘지, 별도 독립 도구로 분리할지**: 서비스 코드와 같이 두면 Spring 컨텍스트나 의존성을 재사용할 수 있지만, 실제 대표 사건 입력(민감 정보)이 서비스 저장소 경로에 섞여 들어갈 위험이 있었다.
- **적재 SQL이 대상 행을 지정하는 방식(PR #58에서 재검토)**: `case_id`/`factor_id`를 숫자로 직접 심을지, 사건 제목·요소 순번으로 실행 시점에 조회할지 검토했다. 로컬과 운영의 auto-increment id가 서로 달라, 숫자를 직접 심은 SQL은 환경마다 다시 만들어야 했다.
- **Flyway 마이그레이션과의 트랜잭션 처리**: 적재 SQL에 자체 `BEGIN`/`COMMIT`을 유지할지, Flyway가 이미 트랜잭션으로 감싸는 반복 마이그레이션(`backend/private-seed`)에 맞춰 트랜잭션 구문을 뺄지 검토했다.

## 선택한 방법과 이유
- `tools/ai-judgment/`를 Python 3.8+ 표준 라이브러리만으로 만든 독립 도구로 분리했다. 서비스 코드와 완전히 분리되면 실제 사건 입력을 `cases/` 아래 git 제외 경로에 둘 수 있고, LLM 호출 자체는 도구에 포함하지 않아 제공사가 정해지기 전에도 프롬프트 생성·검증·적재 SQL 변환까지는 먼저 만들 수 있었다.
- (PR #58) 적재 SQL을 `legal_case.title`과 `factor.display_order`를 실행 시점에 조회하는 `DO $$ ... $$` 블록으로 바꿨다. id를 직접 심으면 환경마다 값이 달라 매번 SQL을 다시 만들어야 했는데, 제목·순번 기반 조회는 어느 환경에서나 같은 SQL로 동작한다.
- (PR #58) `--flyway` 옵션으로 `BEGIN`/`COMMIT` 유무를 선택할 수 있게 했다. 기본값은 기존처럼 트랜잭션 구문을 포함해 수동 `psql` 실행에 쓰고, Flyway 마이그레이션에 쓸 때만 옵션을 켜 트랜잭션 중첩 충돌을 피한다.

## 고려한 제약 사항
- 실제 대표 사건의 AI 판결 생성·검수·시드 반영은 이 PR(#30) 범위가 아니라, BE-13(사건 입력 준비)과 BE-16(시드 적재)이 끝난 뒤 진행하는 것으로 범위를 나눴다.
- 사전 학습 점검에서 `knowsCase` 값이 문자열 `"true"`인 경우도 오염으로 보고, true/false가 아닌 값은 SUSPECT로 판정하도록 리뷰에서 보완했다 (62b8ace).
- 판단 요소가 적재 대상 사건 소속이 아니면 `RAISE EXCEPTION`으로 적재를 중단하도록 해, 잘못된 사건에 판단 요소가 섞여 들어가는 사고를 막았다.
