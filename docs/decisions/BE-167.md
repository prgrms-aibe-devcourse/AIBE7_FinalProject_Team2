# BE-167 의사결정 기록

## 문제 / 배경
- 커뮤니티 작성글을 지울 방법이 없었다(FE-164에서 발견). 본인 삭제와 관리자 삭제가 필요하다.
- 글을 쓰면 경험치(XP)를 주고 레벨은 XP 합계로 계산하므로, 지운 글의 XP를 그대로 두면 쓰고 지우기로 XP를 모을 수 있다.

## 검토한 대안
- 삭제 방식: (A) 실제 삭제 (B) 삭제 표시만(soft delete) → 스키마에 삭제 상태가 없고 공개 서비스라 개인정보 측면에서도 (A)가 단순하다.
- 익명(비회원) 글 삭제용 암호키: 글쓰기가 이미 로그인 회원 전용이고(`member_id NOT NULL`, `requireMember()`) 비회원 글이 존재할 수 없어 **만들지 않았다**. 비회원 글쓰기를 열 때 함께 설계한다.
- XP 회수 후 레벨 유지: (A) 레벨을 따로 저장해 내려가지 않게 → 레벨이 XP 계산값이라는 BE-106 구조를 깬다. (B) 회수 후 레벨 시작 XP보다 모자라면 그 차이를 `LEVEL_FLOOR` 보정 지급으로 채운다 → 구조 유지, 마이그레이션은 CHECK 목록 확장뿐.
- 쓰고 지우기 방지(#428 리뷰): (A) 회수한 지급 행을 지우지 않고 금액만 0으로 둔다 → 하루 글 3건 상한 · 중복 지급 방지가 유지된다. (B) 보정 기준을 "XP를 받기 전 레벨"로 → 글로 올린 레벨이 삭제하면 내려가 "레벨 하락 없음" 요청과 충돌해 택하지 않았다.
- 감사 로그: 관리자 삭제는 기존 `AdminAuditLogger.record`를 한 트랜잭션에 묶는다(기록 없는 삭제 방지).

## 선택한 방법과 이유
- 실제 삭제. 댓글 · 좋아요는 기존 FK `ON DELETE CASCADE`가 함께 지운다.
- 본인 삭제 `DELETE /api/v1/community/posts/{id}` (남의 글 403 · 없는 글 404 · 비로그인 401), 관리자 삭제 `DELETE /api/v1/admin/community/posts/{id}`(관리자 체인: 세션 + CSRF).
- 회수는 지급 행의 금액을 0으로 바꾸는 것이다(행은 남는다). 그래서 지운 글도 그날 글 3건 상한에 계속 포함되고, 같은 사건 판결 공유 보너스는 다시 받을 수 없다. 받은 좋아요 XP 행만 지운다(글이 사라져 다시 쓸 일이 없다). V52는 `amount` 하한을 `>= 0`으로 넓힌다.
- 회수 대상은 글쓴이의 글 작성 XP · 그 글이 받은 좋아요 XP · (판결 공유 글이면) 판결 공유 보너스. 같은 사건에 판결을 붙인 다른 글이 남아 있으면 보너스는 거두지 않는다.
- 남이 그 글에 단 댓글 · 누른 좋아요의 XP는 그 사람이 한 일이라 거두지 않는다.
- 삭제 뒤 홈 캐시를 비워 랭킹 · 사건별 글 수가 바로 바뀌게 한다(컨트롤러에서, 트랜잭션 커밋 뒤).
- 심한 어뷰징은 관리자가 밴하는 것으로 다룬다(레벨 하락은 하지 않는다 — 요청 사항).

## 고려한 제약 사항
- 레벨은 저장하지 않고 XP 합계로 계산(BE-106). `member_xp_event`의 `amount > 0` · source CHECK.
- main 배포 마이그레이션은 추가만(BE-60): V52는 CHECK 제약을 넓히기만 한다.
- 감사 로그에는 글 ID와 글쓴이 회원 ID만 남기고 본문 · 제목은 남기지 않는다(공개 저장소 · 개인정보).

## 추후 재검토가 필요하면
- 판결 공유 글을 지우면 그 사건의 공유 보너스는 다시 받을 수 없다(어뷰징 방지). 정책을 바꾸려면 `zeroOne` 대신 행을 지운다.
- 회수 뒤 XP가 레벨 시작 XP에 붙어 있으므로, 같은 레벨에서 글을 지우기만 반복하는 사용자는 XP가 늘지 않는다(의도). 정책을 바꾸면 `LevelService.revokePostXp`만 고친다.
- 관리자 화면의 삭제 버튼과 프론트 작성자 삭제 버튼은 별도 FE 작업이다.
