# BE-70 의사결정 기록

> 확장 단계(WBS 7.2.2) · PR #120 · 담당 백승호

## 문제 / 배경
- BE-66이 노출한 메트릭을 Prometheus로 로컬에서 수집하는 구성(`monitoring/`)이 필요했다.
- 7.3.1 "p95 지연" 경보의 선행 조건으로, HTTP 요청 지연을 퍼센타일 히스토그램으로 봐야 했다.
- 운영 적용(EC2 배포, 포트 노출 방식, 메모리·디스크 예산)까지 이번 이슈 범위로 가져갈지 정해야 했다.

## 검토한 대안
- **운영 반영을 이번 PR에 포함할지**: `deploy/docker-compose.prod.yml`의 소유자가 D(배포·운영 담당)라, 로컬 구성만 먼저 만들고 운영 반영은 별도로 협의할지, 이번 PR에서 바로 운영까지 붙일지 검토했다.
- **히스토그램 버킷 범위**: 기본 버킷 그대로 켤지, 실제 쓰는 지연 구간에 맞춰 좁힐지 검토했다 (#120 리뷰). 라우트 하나당 버킷 수만큼 시계열이 늘어나 API 수가 늘수록 비용이 선형으로 커지는 문제가 있었다.
- **Prometheus UI 포트 노출 범위**: 로컬 compose의 `9090:9090`을 그대로 둘지, 접근 범위를 좁힐지 검토했다.

## 선택한 방법과 이유
- 이번 PR은 로컬 Prometheus 수집 구성까지만 하고, 운영 반영은 "D와 협의할 것" 섹션으로 분리해 PR에 남겼다. `deploy/docker-compose.prod.yml` 변경은 파일 소유자(D)와 먼저 맞춰야 할 사안(서비스 추가 방식, 메모리·디스크 예산, 포트 노출 방식, 설정 파일 배포 방법)이 많아, 합의 없이 먼저 반영하면 되돌리는 비용이 더 컸다.
- (리뷰 반영) 히스토그램 버킷을 10ms~5s로 좁혀 라우트당 시계열 수를 69개에서 44개로 줄였다. 실제 서비스 응답 시간이 이 범위를 벗어나는 경우가 드물어, 쓰지 않는 구간의 버킷을 없애는 쪽이 카디널리티 비용 대비 손해가 없었다.
- (리뷰 반영) `/actuator/**` 요청을 `http.server.requests` 메트릭에서 제외했다. Prometheus의 스크레이프 요청 자체가 지연 지표에 섞이면 실제 사용자 트래픽의 지연을 왜곡한다.
- (리뷰 반영) Prometheus 포트를 `127.0.0.1`에만 바인딩했다. 로컬 개발 환경에서조차 같은 네트워크의 다른 기기가 접근할 이유가 없었다.

## 고려한 제약 사항
- Actuator 관리 포트(8081)만 스크레이프하고 애플리케이션 포트(8080)는 건드리지 않는다는 BE-66의 결정을 그대로 따랐다.
- `node_exporter`·`postgres_exporter` 추가, Prometheus Agent 모드 여부는 각각 7.2.4·7.1.2(RDS 전환)·7.3 경보 설계 이후로 범위에서 뺐다.
- `host.docker.internal`이 Docker Desktop과 Linux에서 동작이 달라, 직접 재현해 `monitoring/README.md`와 주석에 남겼다.
