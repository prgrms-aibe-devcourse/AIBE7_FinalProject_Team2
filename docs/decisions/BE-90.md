# BE-90 의사결정 기록

> 근거: PR #196 · WBS 7.4.4

## 문제 / 배경
- WBS 7.4.4 "해시 알고리즘 적용"에서 비밀번호(관리자 계정) 해시 알고리즘을 BCrypt와 Argon2id 중 선정해야 했다.
- 7-5 범위 조정안 2번에는 일정 단축을 위해 "비교 생략하고 BCrypt로 바로 확정"이 올라가 있었으나, 실제 진행 시점에 비교 검토를 그대로 진행하기로 했다.

## 검토한 대안
- **BCrypt**: Spring Security `BCryptPasswordEncoder` 내장, 추가 의존성 없음. 수십 년간 검증된 안정성. 다만 메모리 하드니스가 없어 GPU/ASIC 병렬 크래킹에는 Argon2id보다 약하다.
- **Argon2id**: OWASP Password Storage Cheat Sheet 1순위 권장(Password Hashing Competition 우승). 메모리 하드니스로 GPU 기반 무차별 대입에 더 강하다. Spring Security의 `Argon2PasswordEncoder`는 BouncyCastle(`bcprov-jdk18on`)이 classpath에 있어야 동작하며, 이 프로젝트에는 없어 의존성 추가가 필요했다.

## 선택한 방법과 이유
- **Argon2id**로 확정했다.
- `AdminBootstrap`(첫 관리자 계정 생성, `ADMIN_BOOTSTRAP_*`)이 기동 시 BCrypt 해시로 계정을 만들어 왔기 때문에, dev·운영 DB에 이미 `{bcrypt}` 계정이 있을 수 있다(PR 리뷰 지적, 최초 기록의 "기존 해시 데이터가 전혀 없다"는 설명은 부정확했다). 이 계정들은 전환 비용과 무관하게 `DelegatingPasswordEncoder`가 `bcrypt`를 함께 등록해 두어 계속 로그인은 된다.
- 다만 `bcrypt`로 로그인만 할 뿐 자동으로 재해시되지는 않으므로, `AdminUserDetailsService`에 `UserDetailsPasswordService`를 구현해 **로그인에 성공할 때마다 그 계정의 해시를 `{argon2}`로 바꿔 저장**하도록 했다(`DaoAuthenticationProvider.setUserDetailsPasswordService`). 로그인하지 않는 계정은 그대로 BCrypt로 남지만, 검증 가능한 상태이므로 서비스 영향은 없다.
- 관리자 계정만 대상이라 트래픽·동시 로그인 규모가 작아, Argon2id의 메모리 비용(요청당 19 MiB)이 실제 운영 서버(t3.small 2GB, 7.2.4 협의로 모니터링 스택은 별도 분리)에 부담이 되지 않는다고 판단했다.
- `Argon2PasswordEncoder.defaultsForSpringSecurity_v5_8()`는 기본 파라미터가 `m=16384(16 MiB),t=2,p=1`로 OWASP Password Storage Cheat Sheet 권장값(`m=19 MiB,t=2,p=1`, 솔트 16바이트·해시 32바이트)과 달라, `new Argon2PasswordEncoder(16, 32, 1, 19 * 1024, 2)`로 OWASP 권장값을 직접 지정했다(PR 리뷰 지적으로 defaults 호출에서 변경).
- `DelegatingPasswordEncoder`에 `bcrypt`도 함께 등록해, 추후 다른 경로로 BCrypt 해시가 유입되더라도 검증은 가능하게 열어뒀다(인코딩은 항상 `argon2`).

## 고려한 제약 사항
- `admin_account.password_hash` 컬럼이 `varchar(100)`이었는데, Argon2id 인코딩 결과(`{argon2}$argon2id$v=19$m=19456,t=2,p=1$<salt>$<hash>`)가 100자를 넘어 `DataException`이 발생했다. `V18__widen_admin_password_hash.sql`로 `varchar(255)`로 확장했다.
- BouncyCastle 의존성(`org.bouncycastle:bcprov-jdk18on:1.85`)을 `runtimeOnly`로 추가했다. 버전 선택 시점에 알려진 취약점이 없는 안정 버전을 확인하고 골랐으나, 특정 CVE 번호를 근거로 단정할 만큼 출처를 명확히 남기지 못했다(PR 리뷰 지적) — 버전을 올릴 때는 이 기록보다 BouncyCastle 릴리스 노트·보안 공지를 직접 확인한다.

## 추후 재검토가 필요하면
- 로그인 트래픽이 크게 늘어나 Argon2id의 메모리 비용이 서버 부담이 되면, 파라미터(메모리 비용)를 낮추거나 BCrypt로 되돌리는 것을 재검토한다.
- Argon2id는 검증마다 19 MiB를 쓰는데, 운영 백엔드 힙(`mem_limit 1g` × `MaxRAMPercentage=60` ≈ 600MB) 기준 동시 30~40건 검증이면 힙이 찬다. 반면 현재 Nginx 요청 제한은 `/api` 전체에 IP당 평균 초당 20·순간 40으로, 로그인 전용 제한이 없다(BE-63 2차, WBS "Rate limit은 Nginx `limit_req`만"으로 7.4.6 이후로 미뤄둔 상태). 로그인 트래픽이 늘거나 이 위험이 실제로 문제가 되면, 로그인 엔드포인트 전용 `limit_req`(또는 애플리케이션 레벨 동시 해시 수 제한)를 BE-63 2차보다 앞당겨 적용하는 것을 재검토한다.
