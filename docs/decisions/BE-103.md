# BE-103 의사결정 기록

> `docs/decisions/BE-78.md` 2차 검토의 후속 이슈 3번("(선택) 공개된 사건의 사진 교체 허용 여부"). **코드는 바꾸지 않았다** — 문서(API 명세 v0.62)와 이 기록만 남긴다.

## 문제 / 배경
- 사진 API(A-13-3 대표사진 · A-13-4 발단 · 결론 업로드 · A-13-9 삭제)는 모두 `guardNotPublished`로 공개된 사건을 409(`CASE_PUBLISHED`)로 막는다. 공개 뒤 잘못된 사진을 발견해도 고칠 경로가 없었다.
- BE-78에서 이 판단을 미룬 이유는 "되돌릴 수단이 없어서"였다. 그런데 이슈가 열린 뒤 **BE-118(PR #321, 10/28 머지)이 공개 취소 API(A-13-14)를 추가**해 전제가 바뀌었다. `PUBLISHED → REVIEW`로 내리고 `published_at`을 지우며, 사유(1 ~ 200자)가 필수고 감사 로그(`CASE_UNPUBLISH`)에 남는다.
- 그래서 이 이슈의 질문은 "고칠 길을 만들까"가 아니라 **"이미 생긴 길(공개 취소)로 충분한가, 아니면 공개 중 사진만 바꾸는 예외를 따로 둘까"**가 됐다.

## 검토한 대안

### 대안 A — 현상 유지, 아무것도 정하지 않는다
- 경로가 생겼는데 "공개 뒤엔 못 고친다"는 인상만 남아, 급할 때 DB를 직접 고치게 된다(BE-118이 없애려던 상황).

### 대안 B(선택) — 공개 취소 → 교체 → 다시 공개를 **공식 절차**로 삼고, 예외 경로는 두지 않는다
- 코드 변경 0. `guardNotPublished`는 그대로 두고, 절차와 그 대가를 명세(A-13-3 · 8-3 #9)에 적는다.

### 대안 C — 공개 중 사진 교체만 허용 (사진 API에서 `guardNotPublished` 해제 + 사유 필수 + 전용 감사 로그)
- 장점: 사건을 내리지 않으므로 사용자 영향이 없다. 아래 "선택의 대가"가 전부 사라진다.
- 단점: **공개가 곧 사진 승인**이라는 BE-78 합의("승인은 사건 공개로 갈음한다, 사진별 승인 칸은 두지 않는다")가 깨진다. 검수를 거치지 않은 사진이 업로드 즉시 사용자에게 보인다. 사진별 승인 칸을 새로 두면 그때는 C가 다시 후보가 되지만, 그건 이 이슈보다 훨씬 큰 변경이다.
- 또한 8-3 #1(공개 뒤 판결 교체 · 내용 수정은 409로 막는다)과 어긋난다. 대표사진은 `legal_case.thumbnail_url`이라 **A-11 내용 수정으로는 막히는 칸이 사진 API로는 열리는** 모순이 생긴다.

## 선택한 방법과 이유
**대안 B.** 공개 중 사진 교체 경로는 만들지 않는다. 고쳐야 하면 A-13-14(공개 취소) → 사진 교체 → A-13(다시 공개).

- 가드를 둘로 쪼개지 않는다. "공개한 사건은 관리자가 고칠 수 없다"는 한 줄이 판결 · 내용 · 사진에 똑같이 적용된다.
- BE-118이 사유 필수 + 감사 로그를 이미 갖췄다. C를 택하면 같은 성격의 기록 경로를 하나 더 만들어야 한다.
- 사진 교체는 **드물게 일어나는 운영 사고 처리**다. 상시 기능이 아니라면, 쓰기 편한 전용 API보다 흔적이 남는 절차가 낫다.

### 선택의 대가 (절차를 쓸 때 알고 있어야 하는 것)
코드로 확인한 범위다. 명세 A-13-3에도 같은 내용을 적었다.

| 무엇 | 내용 | 근거 |
| --- | --- | --- |
| 내린 동안 사용자 영향 | 목록 · 상세 · 체험에서 사라지고, **이미 끝낸 체험의 결과까지 404** | BE-118 기록의 표(`MyExperienceService`가 사건 공개 여부를 먼저 본다) |
| 다시 공개한 뒤 | `published_at`이 새로 기록돼 **사건 목록에서 맨 위로 올라온다** — 사진 한 장 고친 사건이 "새 사건"처럼 보인다 | `LegalCaseRepository`가 `order by c.publishedAt desc nulls last, c.id desc` |
| 다시 공개가 막힐 위험 | 없다. 공개 조건(`PublishReadiness`)은 공개 판결 2건 · 판단 요소 · 형벌 규칙만 보고 **사진은 보지 않는다** | `AdminReviewQueryService.readiness` |
| 대본 승인 | 사진 교체는 대본 검수 상태를 건드리지 않는다(대사를 고칠 때만 대기로 돌아간다) | A-13-13 |

- 운영 수칙: ① 교체할 파일을 **먼저 준비한 뒤** 내리고 끝나면 바로 다시 공개한다(내려둔 시간이 곧 사용자 영향이다). ② 공개 취소 사유에 `"대표사진 교체"`처럼 적어, 권리 요청으로 내린 사건과 감사 로그에서 구분되게 한다. ③ 내린 김에 판결 · 내용까지 바꾸지 않는다(8-3 #8 운영 규칙 — 이미 체험한 사용자의 비교 결과가 바뀐다).

## 고려한 제약 사항
- `case_incident_photo`에는 사진별 검수 칸이 없다(BE-78 · BE-101). 공개 중 교체를 안전하게 열려면 이 칸이 먼저 필요하다.
- MVP 운영 규모에서 사진 교체는 드물고, 공개 사건 수도 적다(10/28 기준 실제 판례 21건 공개 예정, BE-118). 잠깐 내리는 비용을 감당할 수 있는 규모다.
- 역할 칸 2 · 3단계(BE-78)가 남아 있어 사진 쪽 스키마는 아직 움직이는 중이다. 이 시점에 사진 전용 승인 · 교체 구조를 더하면 되돌릴 거리가 늘어난다.

## 추후 재검토가 필요하면
- **공개 사건 수가 늘고 사진 교체가 잦아지면** 대안 C를 다시 본다. 그때 필요한 선행 조건은 사진별 승인 칸(공개 중 교체본을 "대기"로 올려 두고 승인 시점에 바꾸는 구조)이다.
- **다시 공개할 때 목록 맨 위로 올라오는 문제**가 운영에 걸리면, "처음 공개 시각"을 따로 두는 방법이 있다(BE-118도 8-3 #8에서 "한 번이라도 공개된 사건" 표시가 필요하다고 적었다 — 같은 칸으로 두 문제를 함께 풀 수 있다).
- BE-118 2단계(권리 요청에 따른 삭제·파기)를 정할 때 이 절차와 겹치는 부분(S3 옛 객체 정리)을 함께 본다. 지금은 교체 · 삭제 모두 S3 객체를 남긴다(A-13-4 · BE-101).
