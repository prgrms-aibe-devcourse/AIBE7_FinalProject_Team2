# BE-113 의사결정 기록

## 문제 / 배경
- 지금 회원은 카카오 로그인(BE-62)으로만 만든다. 화면에는 아이디 · 비밀번호 회원가입(FE-104)과 로그인 폼이 이미 있지만 서버 API가 없어 실제 모드에서는 "준비 중"이다.
- 아이디 · 비밀번호 회원가입(M-5)과 아이디 로그인(M-6)을 만든다. 토큰 발급 · 재발급 · 로그아웃은 기존 것(BE-94)을 그대로 쓴다.
- 로그인 화면은 아이디 · 비밀번호를 **관리자 로그인(A-1)으로 먼저 보낸다**(FE-53). 회원 로그인이 생기면 회원 비밀번호가 관리자 API로 가고, 관리자 감사 로그 · 관리자 로그인 요청 제한에 회원 시도가 섞인다.
- 범위는 **가입 + 로그인만**이다. 비밀번호 변경 · 탈퇴 · 찾기는 이번에 만들지 않는다(빨리 끝나면 별도 이슈).

## 결정
### 1. 저장 — 회원 행은 그대로, 비밀번호는 별도 테이블 (V33)
- `member.provider`에 `LOCAL` 추가(CHECK 제약 `ck_member_provider`를 새 마이그레이션에서 DROP 후 ADD). 허용값을 넓히기만 해서 기존 행과 충돌하지 않는다.
  BE-60의 "기존 V 파일 수정 금지"는 이미 적용된 파일을 고치지 말라는 규칙이라 새 파일의 제약 변경은 해당하지 않는다.
- `member.nickname varchar(12)` 추가(NULL 허용). 카카오 회원은 NULL이고 화면은 지금처럼 "카카오 회원"으로 보인다.
- `member_password(member_id PK · FK, login_id UNIQUE, password_hash, changed_at)` 새 테이블. 카카오 회원 행 · 기존 쿼리는 영향이 없다.
- LOCAL 회원의 `member.provider_user_id`는 **UUID**다. 로그인 아이디는 `member_password.login_id` 한 곳에만 둔다(바꿀 수 있는 값을 공급자 회원번호 칸에 넣지 않는다).

### 2. 아이디 · 비밀번호 · 닉네임 규칙
| 항목 | 규칙 |
| --- | --- |
| 아이디 | 영문 · 숫자 · 밑줄 4~20자, **소문자로 바꿔 저장 · 비교**(`Abc`와 `abc`는 같은 아이디). `@`를 쓸 수 없다 → 화면이 `@` 유무로 관리자 · 회원을 나눈다 |
| 비밀번호 | 8~64자, 영문과 숫자를 하나 이상 포함. 최대 64자는 Argon2(m=19MiB) 해시 비용 상한 |
| 닉네임 | 한글 · 영문 · 숫자, 2자 이상. 한글이 있으면 8자 · 영문 · 숫자만이면 12자까지. 공백 · 기호 불가. 화면의 가입 · 마이페이지가 함께 쓰는 `frontend/src/utils/nickname.js`(FE-114에서 한글 8자로 변경)와 같게 한다 |
| 해시 | 기존 `PasswordEncoder` 빈(`{argon2}`, BE-90)을 그대로 쓴다 |

### 3. 로그인 흐름 — 관리자 인증과 분리
- 전역 `AuthenticationManager`(관리자 `AdminUserDetailsService` 전용)는 쓰지 않는다. 두 번째 빈을 만들면 `AdminAuthService` 주입이 모호해진다. 회원 서비스가 `PasswordEncoder.matches()`를 직접 부르고, 토큰은 항상 `MemberPrincipal.user(id)`로 발급한다 → 회원 로그인으로 관리자 권한이 생기지 않는다.
- 실패는 사유(아이디 없음 · 비밀번호 틀림 · 형식 틀림)를 나누지 않고 `INVALID_CREDENTIALS`(401) 하나로 답한다.
- **없는 아이디도 더미 해시와 비교**해서 응답 시간을 맞춘다(아이디 존재 여부를 시간으로 알 수 없게).
- 해시 계산 · 비교 동안 트랜잭션을 잡지 않는다(BE-67과 같은 이유). 회원 행 · 익명 연결만 짧은 트랜잭션으로 묶는다.
- 성공하면 카카오와 같은 흐름: 익명 기록 연결(BE-62 결정 6 규칙 그대로) → `TokenIssuer.issue` → **리프레시 토큰 쿠키만** 심고 `{ nickname }` 응답 → 화면이 M-1 재발급으로 액세스 토큰을 받는다.
- 쿠키는 **모든 처리가 성공한 뒤에만** 심는다(`OAuthLoginSuccessHandler`와 같은 순서). 사용자 체인은 무상태 그대로(세션 없음).

### 4. 회원가입 흐름
- 형식 검사 → 아이디 소문자 정규화 → (빠른 확인) 이미 있는 아이디면 해시 전에 409 `DUPLICATE_ID` → 해시(트랜잭션 밖) → 트랜잭션: 회원 행 · 비밀번호 행 저장 · 익명 연결 → 로그인과 같은 쿠키 처리.
- 동시 가입: 비밀번호 행은 `INSERT ... ON CONFLICT (login_id) DO NOTHING`으로 넣고 0행이면 `DUPLICATE_ID`를 던져 트랜잭션 전체(회원 행 포함)를 되돌린다. 유니크 위반 예외로 트랜잭션이 깨지지 않고, 전역 처리(`INVALID_STATE`)로 새지 않는다.
- 중복 아이디는 가입 화면에서 알려 줄 수밖에 없다(계정 존재가 드러남) → 가입 경로 요청 제한으로 대량 조회를 막는다.

### 5. 로그인 CSRF — Origin 검증
- 사용자 체인은 CSRF 토큰을 쓰지 않는데, 로그인 · 가입 응답이 리프레시 쿠키를 심는다. 다른 사이트가 공격자 계정으로 로그인시키는 것(로그인 CSRF)을 막으려고 `POST /api/v1/auth/login` · `POST /api/v1/auth/signup`을 재발급 · 로그아웃과 같은 Origin 검증 대상(`originProtectedRequests()`)에 넣는다.

### 6. 요청 제한 — Nginx (별도 PR, D 영역)
- 로그인 · 가입 전용 zone(IP별)과 **전체 합계 상한**을 둔다. Argon2는 요청 하나에 19MiB를 쓰므로 여러 IP에서 동시에 몰리면 메모리가 부족해질 수 있다(BE-62 `oauth_all`과 같은 이유).
- 관리자 로그인 zone(IP별 분당 5)과 분리한다 → 같은 와이파이의 회원 로그인이 관리자 로그인을 429로 막지 않는다.

### 7. 계정 병합 없음
- 카카오 계정과 아이디 계정은 **서로 다른 회원**이다. 같은 사람이어도 합치지 않는다.
- 익명 기록은 그 브라우저에서 먼저 로그인한 회원에 연결된다(BE-62 결정 6). 다른 회원으로 로그인하면 새 익명 ID를 받는다.

## 검토한 대안
- 저장: (A) `member`에 `login_id` · `password_hash` 칼럼 추가 / (B) 별도 `member_password` 테이블
- `provider_user_id`: (A) 로그인 아이디 그대로 / (B) UUID
- 비밀번호 검증: (A) 전역 `AuthenticationManager` 재사용 / (B) 회원용 `AuthenticationManager` 빈 추가 / (C) 서비스에서 `PasswordEncoder.matches()` 직접 호출
- 로그인 응답: (A) 액세스 토큰을 응답 본문에 / (B) 리프레시 쿠키만 + 화면이 재발급 호출
- 계정 실패 잠금: (A) Redis로 아이디별 실패 횟수 잠금 / (B) Nginx IP별 제한만

## 선택한 방법과 이유
- 저장 (B): 카카오 회원에게 NULL 칼럼이 생기지 않고, 비밀번호가 필요한 쿼리만 이 테이블을 본다. 비밀번호 변경 · 찾기를 붙일 때도 이 테이블만 바꾼다.
- `provider_user_id` (B): (A)는 아이디 변경 기능이 생기면 공급자 키가 바뀌고, 유니크 · 소문자 규칙이 두 곳에 생긴다.
- 검증 (C): (A)는 관리자 계정 조회기라 회원을 찾지 못하고, (B)는 같은 타입 빈이 둘이 되어 관리자 쪽 주입이 모호해진다. 직접 호출이 범위가 가장 좁다.
- 응답 (B): 카카오 로그인과 화면 흐름 · 토큰 보관 방식(액세스 토큰은 메모리)이 같아진다.
- 잠금 (B): 이번 일정(M3 10/30) 안에 Redis 키 · TTL(`noeviction`) 설계까지 하기 어렵다. 아이디별 잠금은 남이 일부러 틀려 정상 사용자를 잠글 수 있는 문제도 함께 정해야 한다.

## 고려한 제약 사항
- Spring Boot 4.1 · Spring Security 7.1, PostgreSQL. Redis는 `noeviction`이라 새 키를 만들면 TTL이 필수 — 이번에는 새 키를 만들지 않는다.
- **개인정보 수집 범위가 늘어난다**: BE-62 결정 5("개인정보 없이")는 카카오 회원에만 해당하게 된다. LOCAL 회원은 아이디 · 비밀번호(일방향 해시) · 닉네임을 저장한다 → 이용약관 "회원가입과 계정" · 개인정보 처리방침(수집 항목 · 보유 기간 · 안전성 확보조치)을 함께 고친다(`frontend/src/app/legalPage.js`, 문서 PR).
- 마이그레이션 번호는 처음에 V32로 두었으나, PR #306을 올린 뒤 BE-108(#300)의 `V32__case_script.sql`이 develop에 먼저 머지되어 V33으로 옮겼다(CI의 Flyway 번호 중복 오류로 확인). 머지 직전에 develop 마지막 번호를 한 번 더 확인한다.
- 로그 · 예외 메시지에 비밀번호 · 토큰 · 입력 원문(아이디 포함)을 남기지 않는다. 오류 클래스명 · 코드만 남긴다.

## 추후 재검토가 필요하면
- **비밀번호 변경 · 탈퇴 · 찾기**: 이번 범위 밖. 찾기가 없으므로 비밀번호를 잊으면 문의처로 안내한다(약관에 명시). 탈퇴는 BE-62에 남긴 `anonymous_user.member_id` FK 처리와 함께 정한다.
- **계정 단위 실패 잠금(Redis)**: 지금은 Nginx IP별 제한만이다. 여러 IP로 한 아이디를 노리는 공격이 보이면 아이디별 실패 횟수(TTL 있는 키) · 잠금 해제 정책을 함께 정한다.
- **가입 직후 토큰 발급 실패**: 회원 행 저장(커밋) 뒤 Redis 장애로 토큰 발급이 실패하면 500이 되고 계정은 남는다. 다시 로그인하면 되므로 되돌리지 않는다.
- **관리자 로그인 경로 분리(`/admin/login`)**: 지금은 화면이 `@` 유무로 나눈다. 관리자 화면을 따로 만들면 로그인 화면의 관리자 시도를 없앤다.
- **비밀번호 해시 업그레이드**: 지금은 모두 `{argon2}`라 다시 인코딩할 일이 없다. 인코더 설정을 바꾸면 로그인 성공 때 `upgradeEncoding`으로 다시 저장한다.
- **닉네임 중복 · 변경**: 닉네임은 유일하지 않다. 커뮤니티 작성자 표시에 쓰게 되면 중복 허용 여부와 변경 API를 정한다.
