# BE-77 의사결정 기록

## 문제 / 배경

- API 5는 사전 판단을 저장하지만 완료 전에는 다시 조회할 수 없어, 1막부터 다시 보기의 엽서가 브라우저 저장값에 의존했다.
- 재판부 판결과의 비교도 프론트가 구간 label을 해석해 표시 문구 변경에 취약했다.

## 검토한 대안

- API 2·3 공용 DTO 확장: API 2의 응답과 체험 생성·중복 시작 경로까지 불필요하게 영향을 받는다.
- 새 조회 API·테이블: 기존 체험 및 USER·PRE 기록으로 해결할 수 있어 필요하지 않다.
- 프론트 구간 파싱 유지: 서버에 이미 존재하는 종류·개월 범위 기반 비교 규칙과 중복된다.

## 선택한 방법과 이유

- API 3 전용 `ExperienceStatusResponse`를 추가하고 API 2의 `ExperienceResponse`는 유지한다. 공통 상태 필드 변환은 재사용한다.
- `MyExperienceService`로 사건·익명 사용자 소유권·최신 회차를 확인한 뒤 `JudgmentRepository.findPreJudgment()`로 본인 기록만 읽는다.
- STARTED는 명시적 null, 제출 이후는 선택 구간 ID·현재 label을 반환한다. 제출 상태인데 기록이 없으면 기존 판결 조회처럼 `IllegalStateException`으로 불변식 위반을 알리고 공통 처리기가 500 INTERNAL_ERROR를 반환한다. 상세 원인은 응답하지 않는다.
- API 14 최상위 `preToCourt.direction`은 이미 읽은 PRE와 COURT에 `PreToFinalDirection.of()`를 적용한다. 추가 판결 조회나 새 비교 규칙은 없다.
- 방향은 재판부 기준이다. HEAVIER는 재판부가 더 무거움, LIGHTER는 더 가벼움이며 SAME은 같은 종류·구간에 해당한다는 뜻이다. 기존 프론트 PRE_HEAVIER/PRE_LIGHTER와는 관점이 반대다.

## 고려한 제약 사항

- 본인 선택 구간의 조기 조회만 예외로 허용한다. API 3은 선택 요소·AI·재판부·비교를 포함하지 않는다. API 4·5 및 결과 조회의 상태 제한, 판단 수정 금지, 성향 산식은 유지한다.
- 스키마·마이그레이션·상태 전이·프론트는 변경하지 않는다. 기존 명세는 [API 명세](../api-specification.md)의 API 2·3·14를 기준으로 함께 맞춘다.
- 체험 소유자는 아직 익명 ID 쿠키로 식별한다. 다른 브라우저·기기의 기록 복원은 회원 연결 작업이 필요하다.
- 테스트는 BE-87 전용 PostgreSQL·Redis 및 보호 설정을 사용한다. 운영·개발 DB나 비공개 자료를 사용하지 않는다.

## 추후 재검토가 필요하면

- 프론트에서 API 3 조회를 추가하고 서버 값 우선·캐시 대체 정책을 적용한다. 서버의 null·소유권 오류를 오래된 캐시로 덮지 않는다.
- 8막 편집부 의견과 대사를 서버 direction으로 바꾸고 Mock 응답도 맞춘다. 이번 백엔드 변경만으로 프론트 동작이 바뀌지는 않는다.
- 로그인 연동 때 익명 기록 연결·최신 회차 및 캐시 사용자 구분 정책을 함께 확인한다.
