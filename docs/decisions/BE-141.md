# BE-141 의사결정 기록

사건 사진 주소 규칙 기본값 — 저장된 값이 있으면 그것을, 없으면 사건 번호로 정한 규칙 주소를 응답에 채운다.

## 문제 / 배경

- 사건 사진(대표 · 발단 · 결론)은 팀이 따로 제작하고, 관리자 업로드(A-13-3 ~ 5, S3)로 올리게 설계되어 있었다. 사건 1만 시드 SQL로 정적 파일 주소(`/images/cases/case-1-*.webp`)가 들어가 있다.
- 사건 정보는 적재되었는데 사진 주소는 비어 있어(`thumbnail_url` NULL, 사진 행 없음) 실제 사건은 공용 컷이 보인다.
- 사진은 사건 번호만으로 이름이 정해지므로, 주소를 DB에 따로 채우지 않아도 된다.

## 검토한 대안

- 대안 A: 파일 이름을 번호로 맞추고 1회 실행 SQL로 `thumbnail_url` · 사진 행을 채운다. 기존 사건에는 되지만 새 사건에 적용되지 않고, 환경마다 SQL을 따로 돌려야 한다.
- 대안 B: 적재 코드가 사건을 저장할 때 규칙 주소를 DB에 넣는다. 새 사건에는 되지만 파일이 없는 사건의 깨진 주소가 DB에 남고, 이미 적재된 사건에는 따로 채워야 한다.
- 대안 C(채택): 응답을 만들 때 저장된 값이 없으면 규칙 주소를 채운다. DB를 건드리지 않고, 기존 · 새 사건에 모두 적용되며, 관리자 업로드 값이 있으면 그것이 우선한다.
- 대안 D: 업로드 API를 없애고 사진을 저장소에만 두는 방식. 서버가 실행 중에 정적 파일을 추가할 수 없어(프론트 파일은 빌드 때 이미지에 구워진다) 대체가 아니라 사용 중단이 된다. 이번에는 둘 다 쓰는 쪽으로 했다.

## 선택한 방법과 이유

- 대안 C. 주소 규칙은 사건 1이 이미 쓰는 `/images/cases/case-{id}-{reenact|origin|conclusion}.webp`와 같다.
- 한 곳(`CasePhotoUrls`)에서 규칙을 정하고 사건 목록 · 상세(API 1 · 2 · 16)와 공개 신문 지면(API 17)이 쓴다. 관리자 응답(A-6, A-13-x)은 저장된 값 그대로 보여 준다 — 관리자가 업로드 여부를 구분할 수 있어야 하기 때문이다.
- API 17의 `extraPhotos.origin` · `conclusion`은 사진 행이 없어도 `null`이 아니라 규칙 주소를 낸다(캡션 `null`). 자리가 비는 일이 없어 프론트는 항상 같은 모양을 받는다.

## 고려한 제약 사항

- 규칙 주소의 파일이 없으면 Nginx의 화면 주소 fallback(`location /`)이 `index.html`을 **200**으로 돌려준다. 브라우저가 이를 이미지로 읽지 못해 `error` 이벤트가 나고, 프론트가 공용 컷으로 바꾼다(`useCommonPhotoOnError`, FE-63 · FE-65). 상태 코드로 파일 유무를 확인하지는 못한다 — `/images/` 경로에 `try_files $uri =404`를 두면 404가 되지만, 배포 설정 변경이라 이 PR에서는 하지 않았다(후속 검토). 목록 카드 · 신문 지면 · 무대 증거 화면에 이 처리가 있다.
- `thumbnailUrl`이 항상 값이 있어 "사진 없음 = `null`" 신호가 사라진다. 목록 카드처럼 `null`이면 인쇄 망점 카드로 바꾸던 분기는 이제 항상 사진 카드를 타고, 파일이 없는 사건은 카드마다 요청이 한 번 나간 뒤(응답은 200 HTML) 공용 컷으로 바뀐다(PR #344 리뷰). 파일이 정해진 사건이 21건뿐이라 감수하는 트레이드오프이고, 사진이 없는 사건이 늘면 `hasPhoto` 같은 표시를 따로 두는 방안을 다시 본다.
- 사건 번호는 환경마다 같아야 사진이 같은 사건에 붙는다. 번호가 다른 환경에서는 파일 이름을 그 환경 번호로 맞춰야 한다.
- 같은 이름의 파일을 새 컷으로 교체해 배포하면 브라우저 캐시 때문에 옛 사진이 보일 수 있다.

## 추후 재검토가 필요하면

- 업로드 화면(A-13-3 ~ 5)과 S3 설정을 계속 둘지: 사진을 항상 제작해서 저장소에 올리는 방식이라면 사용을 중단할 수 있다.
- 파일 이름 캐시 처리(버전 붙이기 등).
