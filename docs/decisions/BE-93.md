# BE-93 의사결정 기록

사건 등록 API(A-14 · A-15) 구현. 관리자가 판결문을 넣으면 AI 판결 파이프라인을 돌려 사건을 만든다.

작업량이 커서 한 이슈 안에서 PR을 둘로 나눈다.

- **1차 (이 문서의 아래 내용)**: 등록 접수 · 파이프라인 연동 · 진행 상황 조회
- **2차**: 적재 (파이프라인 결과 → `legal_case` DRAFT 생성)

## 문제 / 배경

COMMON-50에서 파이프라인(`tools/ai-judgment`, BE-31)을 내부 컨테이너로 띄워 두었다. 하지만 **아무도 부르지 않는
상태**였다. 관리자 화면(FE-45)에는 등록 폼이 이미 있고 `adminRealApi.js`가 `/admin/case-imports`를 부르는데,
서버에 그 경로가 없어 404를 받고 있었다.

이 이슈는 그 빈칸을 채운다. 어려운 점은 셋이었다.

1. **파이프라인은 수십 분 걸린다.** HTTP 요청 하나로 기다릴 수 없다.
2. **진행 상황을 누가 아는가.** 단계별 상태는 파이프라인의 `state.json`에만 있다.
3. **판결문 원문을 어디에 두는가.** 파이프라인 서비스는 원문을 결과로 돌려주지 않는데(FR-5-3),
   적재 대상인 `case_source.original_text`에는 원문이 들어가야 한다.

## 검토한 대안

### 1. 진행 상황을 어디서 관리하는가

- **대안 A — 백엔드가 직접 센다**: 단계 시작 · 끝을 백엔드가 기록한다.
  - 장점: DB만 보면 되어 조회가 빠르다.
  - 단점: **출처가 둘이 된다.** 파이프라인도 `state.json`에 쓰고 백엔드도 쓰면 반드시 어긋난다.
    파이프라인이 중간에 죽으면 백엔드 기록만 "진행 중"으로 남는다.
- **대안 B — 파이프라인에 물어서 그대로 옮긴다** ← **선택**
  - 장점: 출처가 하나다. COMMON-50이 "상태의 단일 출처는 `state.json`"으로 설계된 것을 그대로 잇는다.
  - 단점: 조회할 때마다 내부 HTTP 호출이 한 번 더 생긴다. 화면이 2초마다 묻기 때문에 적지 않다.

**선택 이유**: 어긋나는 상태를 만드는 비용이 호출 한 번보다 훨씬 비싸다. 다만 단점을 두 가지로 줄였다.

- 끝난 작업(`SUCCEEDED` · `FAILED`)은 더 묻지 않는다. 화면은 끝나면 폴링을 멈추므로 실제 호출은 작업당 진행 중일 때뿐이다.
- 마지막으로 받은 단계 상태를 `case_import.stages`에 저장해 둔다 → 다음 항목.

### 2. 끝난 작업의 단계 상태를 어떻게 보여주는가

단계별 상태는 파이프라인만 안다. 그런데 작업이 끝나면 더 묻지 않고, 나중에 작업을 지우면 물을 수도 없다.
그 상태에서 화면을 새로 열면 무엇을 보여줄 것인가.

- **대안 A — 작업 상태로 지어낸다**: 성공이면 전부 `DONE`, 아니면 전부 `PENDING`.
  - 단점: **실패한 작업이 "아무것도 안 한" 것처럼 보인다.** 어느 단계에서 실패했는지가 가장 중요한 정보인데 그것을 잃는다.
- **대안 B — 마지막으로 받은 값을 저장해 둔다** ← **선택**
  - 장점: 나중에 열어도 실제로 어디까지 갔고 어디서 멈췄는지 보인다.
  - 단점: 컬럼이 하나 는다(`stages jsonb`).

**선택 이유**: 컬럼 하나로 "사실과 다른 화면"을 없앨 수 있다. 진행 상황을 세는 것이 아니라 **받아 적는 것**이라
출처가 하나라는 원칙도 깨지 않는다.

### 3. 판결문 원문을 어디에 두는가

적재할 때 `case_source.original_text`에 원문이 필요하다. 그런데 파이프라인 서비스는 원문을 돌려주지 않는다
(COMMON-50에서 `result()`가 일부러 뺀다, FR-5-3).

- **대안 A — 서비스에 원문을 돌려주는 경로를 만든다**
  - 단점: COMMON-50에서 의도적으로 그은 경계를 도로 무른다. "원문은 결과에 넣지 않는다"는 규칙에 예외가 생긴다.
- **대안 B — 백엔드가 받은 원문을 들고 있다가 적재 때 옮긴다** ← **선택**
  - 장점: 원문을 처음 받는 쪽이 원래 백엔드다(A-14 요청 본문). 서비스 쪽 규칙을 건드리지 않는다.
  - 장점: 최종 목적지(`case_source.original_text`)도 백엔드 DB다. 같은 DB 안에서 옮기는 일이 된다.
  - 단점: 적재 전까지 원문이 `case_import_source.original_text`에 남는다.

**선택 이유**: 경계를 무르게 만드는 쪽이 더 위험하다. 단점은 2차에서 **적재가 끝나면 비우는 것**으로 줄인다
(`CaseImportSource.clearOriginalText()`). 그래야 같은 원문이 두 벌로 남지 않는다.

### 4. "한 번에 하나"를 어디서 막는가

- **대안 A — 백엔드만 막는다**: 진행 중인 `case_import`가 있으면 409.
  - 단점: 두 요청이 거의 동시에 오면 둘 다 검사를 통과할 수 있다.
- **대안 B — 파이프라인 서비스만 막는다**: 서비스가 409를 주면 옮긴다.
  - 단점: 백엔드 DB에는 작업 행이 이미 생긴 뒤라 정리가 필요하다.
- **대안 C — 둘 다 막는다** ← **선택**

**선택 이유**: 역할이 다르다. 백엔드 검사는 **빠른 피드백용**(파이프라인을 부르기 전에 거절)이고,
진짜 경계는 **서비스가 지킨다** — COMMON-50에서 확인과 시작을 잠금으로 묶어 두어, 백엔드 검사를 동시에
통과해도 둘째 요청은 409로 거절된다. 백엔드는 그 409를 `IMPORT_IN_PROGRESS`로 옮기기만 하면 된다.

## 선택한 방법과 이유 (정리)

```
관리자 → A-14 → ① 검증 · 중복 확인 (파이프라인 호출 전에 거절)
                ② 파이프라인에 작업 생성 (트랜잭션 밖)
                ③ case_import 행 + 감사 로그 (한 트랜잭션)
                → 202 {importId, status}

화면 2초마다 → A-15 → 파이프라인에 물어 받아 적고 그대로 내려준다
                      (끝난 작업은 묻지 않고 저장해 둔 값을 쓴다)
```

- 외부 호출(②)은 **트랜잭션 밖**에서 한다. DB 커넥션을 외부 응답 동안 잡고 있지 않기 위해서다(BE-92와 같은 이유).
  저장(③)만 `TransactionTemplate`으로 짧게 묶고, 감사 로그를 같은 트랜잭션에 넣어 **작업 행과 기록이 함께 남거나
  함께 없도록** 했다.
- ③이 실패하면 파이프라인에 만들어 둔 작업을 지운다. 추적할 수 없는 작업에 원문이 남는 것을 막기 위해서다(FR-5-3).
- 감사 로그에는 **사건번호 · 심급만** 남긴다. 원문은 넣지 않는다(A-14).

## 고려한 제약 사항

### 파이프라인 서비스를 켜지 않은 서버가 정상이다

지금 운영은 파이프라인 오버레이를 **켜지 않은 상태**다(COMMON-50 — t3.small 메모리 때문에 7.1.2 RDS 전환
뒤로 미뤘다). 그래서 `PIPELINE_SERVICE_URL`이 없는 것이 비정상이 아니다.

이 경우 **사건 등록만 꺼지고 서버는 정상으로 뜬다**. `GEMINI_API_KEY` 없이 RAG만 꺼지는 것과 같은 방식이다.
등록을 시도하면 `502 IMPORT_UNAVAILABLE`로 "지금 쓸 수 없다"고 알린다.

### 적재가 없는 채로 1차를 끝낸다

A-15 계약은 `SUCCEEDED`면 `caseId`를 준다고 되어 있다. 1차에는 적재가 없어 `null`이다
(명세 A-15에 차수별 표로 나눠 적었다 — 한 줄에 두 계약이 섞여 있으면 어느 쪽을 따라야 할지 알 수 없다).
숨기지 않고 API 명세 · PR 본문 · 이 문서에 모두 적었다.

⚠️ **화면에 남는 문제**: `adminRegisterPage.js`는 `SUCCEEDED`면 `caseId`가 있다고 보고 "사건 #{caseId}" 문구와
검수 화면 버튼을 띄운다. 지금 그대로면 "사건 #null"이 보이고 버튼이 깨진 주소로 간다. 2차에서 적재가 들어가면
저절로 풀리지만, 그 전에 운영에서 켜려면 화면 쪽에 `caseId` 없을 때의 처리가 먼저 필요하다.

### 기존 스키마를 건드리지 않는다

`case_source`는 `case_id`가 NOT NULL이라 사건이 생기기 전에는 행을 넣을 수 없다. 그래서 등록 중인 판결문은
`case_import_source`라는 별도 표에 두고, 적재 때 `case_source`로 옮긴다. 컬럼 구성을 그 표와 맞춰 두어
옮기는 코드가 단순해지게 했다(`source_org`만 NULL을 받는다 — A-14에서 선택 값이라서다).

## PR 올리기 전 자체 검토에서 고친 것

올리기 전에 코드를 한 번 더 훑어 아래를 고쳤다. 셋은 **운영에서 기능이 통째로 멈추는** 종류였다.

### 긴 실패 사유 하나가 사건 등록 전체를 막는다

`case_import.message`는 `varchar(500)`인데 파이프라인이 주는 실패 사유에는 길이 제한이 없다
(`jobs.py`는 첫 줄만 보내지만 그 줄이 길 수 있다). 500자를 넘으면 저장이 실패하고,

- A-15는 2초마다 **500을 돌려주며 작업이 끝난 상태로 넘어가지 못하고**,
- 다음 A-14도 같은 행을 갱신하다 같은 예외를 만나 **새 등록까지 막힌다.**

사람이 DB를 직접 고치기 전에는 풀리지 않는다. 엔티티에서 컬럼 길이에 맞춰 자르고(`…`를 붙여 잘린 것이
보이게), `@Column(length = ...)`로 길이를 코드에도 적었다.

### A-15가 외부 호출 동안 DB 커넥션을 잡고 있었다

이 문서에 "외부 호출은 트랜잭션 밖에서 한다"고 적어 놓고 정작 A-15는 `@Transactional` 안에서
파이프라인을 불렀다. 화면이 **2초마다** 부르는 경로라, 파이프라인이 멎으면 호출마다 커넥션을 30초씩
붙잡는다 — 탭 몇 개만 열려 있어도 풀이 말라 **사용자 화면까지 멈춘다.** 읽기 · 쓰기만 짧은 트랜잭션으로
묶고 호출은 밖으로 뺐다 (A-14가 이미 쓰던 방식과 같게).

### 판결문 원문이 로그로 샐 수 있었다

파이프라인 오류를 옮기면서 응답 본문을 그대로 로그에 찍고 있었다. 작업 생성 요청의 본문이 원문이라,
서비스(FastAPI)가 요청 값을 되비추는 응답(422 검증 오류의 `input` 필드)을 주면 원문이 로그에 남는다.
본문을 찍지 않도록 바꾸고, 같은 이유로 **원인 예외도 달지 않는다** — Spring의 `RestClientResponseException`
메시지에 본문 일부가 들어 있어 스택트레이스를 찍으면 똑같이 샌다. 회귀를 잡는 테스트를 넣었다.

### 그 밖에

- **처음부터 실패한 작업이 실패 사유를 잃었다**: 생성할 때 상태를 두 번 적어서, 파이프라인이 바로 FAILED를
  주면 "끝난 작업은 건드리지 않는다" 규칙에 걸려 사유 · 단계가 하나도 남지 않았다. 한 번만 적도록 고쳤다.
- **중복 검사가 사실상 동작하지 않았다**: 적재가 2차라 `case_source`가 비어 있어, 같은 판결문으로 수십 분짜리
  생성을 몇 번이고 다시 돌릴 수 있었다. 진행 중인 등록(`case_import_source`)도 함께 본다 (실패한 등록은 제외).
- 파이프라인이 단계 값을 빠뜨린 응답을 줘도 500이 되지 않게 했다.
- 작업 ID가 컬럼 길이를 넘으면 저장 전에 막는다 (저장에서 터지면 이미 파이프라인이 돌고 있어 되돌리기 어렵다).

## 남겨 둔 것 (알고 두는 것)

고치지 않고 두기로 한 것들이다. 증상을 알아보지 못하면 원인을 찾기 어려운 것들이라 적어 둔다.

### 동시 갱신으로 끝난 상태가 뒤집힐 수 있다

`applyProgress`의 "끝난 작업은 바꾸지 않는다"가 메모리 안에서만 보장된다. 외부 호출을 트랜잭션 밖으로
빼면서 쓰기 구간이 아주 짧아져 창이 좁고, 2초마다 불리는 경로에 비관적 잠금이나 낙관적 버전을 걸면 그
자체가 더 큰 문제를 만든다고 보았다. 실제로 뒤집히는 일이 보이면 조건부
UPDATE(`WHERE status NOT IN ('SUCCEEDED','FAILED')`)로 바꾼다.

### 정말로 멎은 작업은 사람이 풀어야 한다 (PR #232 리뷰)

파이프라인 **프로세스가 죽는 경우는 서비스가 이미 처리한다** — `jobs.py`가 프로세스 생존을 보고
"파이프라인이 끝나기 전에 멈췄습니다"로 FAILED를 돌려주고, 백엔드의 `stillRunning`이 그걸 받아 적어
다음 등록의 길을 비운다.

남는 경우는 둘이다.

- 프로세스가 **살아 있는 채 멎은** 경우(외부 LLM 호출이 영영 안 끝나는 등). 서비스가 RUNNING으로 보고,
  백엔드도 RUNNING으로 받아 적어 새 등록이 계속 `IMPORT_IN_PROGRESS`가 된다.
- 서비스가 **모르는 상태 문자열**을 주는 경우. `statusOf`가 안전한 쪽으로 RUNNING에 접어 같은 결과가 된다.

지금은 사람이 DB를 고치거나 파이프라인 컨테이너를 다시 띄워야 풀린다. 고치는 방법은 두 가지가 보인다 —
작업 시작 시각 기준 상한(예: N시간 넘으면 FAILED로 끊기)이나 관리자 중단 API(파이프라인 서비스에는
`POST /jobs/{id}/cancel`이 이미 있다). **어느 쪽이든 "얼마나 지나면 멎은 것으로 볼지"를 정해야 하는데,
파이프라인이 실제로 몇 분 걸리는지는 운영에서 돌려 봐야 안다.** 그래서 이 PR에서는 두지 않았다.

### 작업 생성이 타임아웃되면 고아 작업이 남는다 (PR #232 리뷰)

`createJob`의 읽기 타임아웃(기본 30초)이 터져도 파이프라인은 작업을 이미 만들어 돌고 있을 수 있다.
이때 백엔드에는 행이 없고 작업 ID도 모르므로 `deleteJobQuietly`를 부를 수도 없다. 증상은 이렇다.

- 다음 등록이 파이프라인 쪽 잠금에 걸려 `IMPORT_IN_PROGRESS`가 되는데, **백엔드에는 도는 작업이 없다.**
- 판결문 원문이 서비스 볼륨에 남는다.

작업 생성은 202로 바로 답하는 호출이라 30초가 걸릴 일이 거의 없지만, 파이프라인이 멎으면 생길 수 있다.
볼륨에 남은 원문은 COMMON-51(오래된 작업 자동 정리)이 마지막으로 치운다.

### 적재 전에는 성공한 등록도 사건번호를 계속 쓴다 (PR #232 리뷰)

중복 검사는 `case_source`와 `case_import_source`를 함께 보고 **FAILED만 제외한다.** 적재(2차)가 들어가기
전에는 성공한 등록이 `case_source`에 남지 않으므로, 같은 사건번호로 다시 등록할 수 없다.

운영에서 파이프라인을 켜지 않는 동안에는 영향이 없다. 2차 전에 시험 삼아 켜서 같은 판결문을 다시 넣어야
하면 `case_import` 행을 지우면 된다.

### 대본은 이 흐름에서 생기지 않는다 (PR #232 리뷰)

이 파이프라인이 만드는 것은 사건 내용 · 판단 요소 · AI 판결 · 가치관 축까지다. **판결 체험 대본
(`frontend/src/content/scripts.js`)은 여기서 만들어지지 않는다.** 대본 생성은 COMMON-41의 남은 항목이고,
퓨샷용 형식은 FE-60(PR #226)에서 준비해 두었다(`source` · `basis` · `slots` 필드, `docs/script-fewshot-mock.md`).

다만 **대본이 없다고 화면이 비지는 않는다** — `scripts.js`가 "대본이 없는 사건은 MVP 화면 그대로 보여 준다"로
되어 있어 MVP 화면으로 넘어간다. 그래도 사건을 등록 · 공개하는 것과 그 사건의 대본을 넣는 것은 **별개
단계**라는 점은 알고 있어야 한다.

## 추후 재검토가 필요하면

- **폴링 주기**: 화면이 2초마다 묻고, 그때마다 내부 HTTP 호출이 한 번 일어난다. 같은 서버 안이라 비용이 작지만,
  파이프라인이 수십 분 도는 동안 수백 번이 된다. 부담이 보이면 주기를 늘리거나 조회 결과를 짧게 캐시한다.
- **실패한 작업의 원문 정리**: 지금은 작업이 실패해도 `case_import_source.original_text`가 남는다. 다시 시도할
  때 쓸 수 있어 일부러 두었지만, 보관 기간을 정해 지우는 편이 안전하다. 파이프라인 쪽 정리는 COMMON-51에 있다.
- **`errorCode` 세분화**: 지금은 파이프라인이 실패하면 모두 `INTERNAL_ERROR`로 내려준다. 어느 단계에서
  어떤 이유로 실패했는지는 `stages[].status`와 `message`로만 구분된다. 실패 유형이 쌓이면 코드를 나눈다.
- **모델 설정**: `pipeline-service.models`(생성)와 `extract-model`(비식별화)을 환경변수로 뒀다. 어떤 모델이
  좋은지는 운영에서 돌려 본 뒤 정한다 — 특히 `extract`는 판결문 원문이 나가므로 **유료 등급 키의 모델만** 쓴다.
