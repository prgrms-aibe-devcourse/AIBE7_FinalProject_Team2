# BE-109 의사결정 기록

> 근거: BE-108(`CaseScript` 적재 · 검수, `docs/decisions/BE-108.md`) · BE-107(파이프라인 `script` 단계, 증거조사 대사만 생성) · FE-60(대본 포맷 · 자리표시자 설계) · 해송님(FE-33 담당)과의 계약 협의(Jira BE-109 댓글, 2026-10-27)

## 문제 / 배경

- BE-108까지는 대본이 DB에 적재 · 검수될 뿐, 프론트에 내려주는 공개 API가 없었다. 지금 프론트는 `frontend/src/content/case-1/script.json`의 정적 `acts.steps`(1a · 1b · 2 · 3 · 4 · 5 · 6, 일곱 막)를 쓰고, `scripts.js`는 `SCRIPTS = { 1: case1 }` 한 줄이라 대본이 있는 사건은 사건 1뿐이다.
- 파이프라인(BE-107)이 만드는 것은 **판단 요소별 증거조사 대사뿐**이다(`factorId` · `role` · `character` · `text`). 연출 값(`card` · `confirm` · `proc` · `spots` · `tags` · `look` · `slots`)이나 나머지 막(1막 해설, 공소사실 · 모두진술, 쟁점 정리, 피고인신문, 검사 의견 · 최종변론 · 최후진술)은 만들지 않고 만들 계획도 없다(COMMON-65 범위 밖).
- `api-specification.md`에는 대본 서빙 필드가 "별도로 정한다"로 비어 있었다(FE-60 · API 16 v0.29 메모). 이번에 FE-33 담당(해송님)과 계약을 정했다.

## 검토한 대안

### 1. 서버가 acts 전체를 줄까, 증거조사 대사만 줄까
- A. acts 전체: 파이프라인이 연출 값을 만들지 않으므로 서버가 그 값을 새로 들고 있어야 한다 — BE-109 범위를 크게 넘고, 애초에 파이프라인 사건에는 정적 대본 파일 자체가 없어 "acts 전체"가 성립하지 않는다.
- B(선택). **서버는 2막 증거조사 대사만 준다.** 나머지 막은 FE-33이 사건에 상관없는 공통 틀로 채운다. 서버는 사건마다 달라지는 부분만 책임지고, 연출은 프론트가 그대로 쥔다. "대본이 없으면 MVP 화면 그대로"(`scripts.js`) 원칙도 자연스럽게 지켜진다.
- 다만 "나머지 막 = 전부 공통 틀"은 아니다. 공소사실 · 모두진술 · 쟁점 정리 · 피고인신문 · 검사 의견 · 최종변론 · 최후진술처럼 사건마다 달라지는 줄도 있다 — 이 줄들은 **BE-107 후속 확장으로 분리**했다(이번 이슈 범위 아님). 파이프라인 사건은 당분간 "증거조사 중심 축약판"으로 두고, 그 모양은 FE-33이 정한다.

### 2. 증거 카드 문구(`card`)를 서버가 줄까
- A. 안 준다: 사건 1처럼 수작업 대본이 있는 사건은 정적 `evidence` 배열을 그대로 쓸 수 있다.
- B(선택). **서버가 준다.** 파이프라인 사건에는 정적 `evidence` 배열이 없어서, `card`가 없으면 증거 카드 자체를 그릴 수 없다. 값은 A-13-10의 `label`과 같다 — 사건의 판단 요소 문구(`factor.label`)를 그대로 쓴다.

### 3. 배역 코드(`side`) 표기
- A. 대본처럼 한글(검사 · 변호인): 2막 step에 그대로 꽂기는 편하다.
- B(선택). **`PROSECUTOR` · `DEFENSE` 대문자 코드값.** 다른 공개 API가 모두 코드값이라 형식을 맞췄고, 서버가 화면 한글 문구에 묶이지 않는다. 화면 한글 변환은 프론트 몫.
- 구현 메모: 파이프라인은 `role`을 소문자로 준다(`script_generation.py`의 `ROLE_BY_DIRECTION = {"UP": "prosecutor", "DOWN": "defense"}`). `PublicCaseScriptResponse`에서 대문자로 바꿔 내려준다(`String.toUpperCase`) — 대소문자를 미리 맞추자고 적재(BE-108) 쪽을 건드리지 않는다.

### 4. 대본이 없거나 미승인일 때 404 vs 빈 배열
- A. 빈 배열: 호출 쪽이 분기를 하나 덜 쓴다.
- B(선택). **404 `SCRIPT_NOT_FOUND`.** 빈 배열이면 "대본이 없음"과 "대사가 0줄"을 구분할 수 없다. API 17 `PAPER_NOT_FOUND`와 같은 모양으로 맞춰, 프론트가 같은 방식(404 → MVP 화면)으로 처리할 수 있게 했다.
- **승인(`reviewStatus: APPROVED`)한 대본만 내려준다**(`CaseScript.isPublic()`, BE-108에서 이미 만들어 둔 메서드). 검수 전 · 반려된 대본은 없는 것으로 본다.
- 비공개 사건은 `CASE_NOT_FOUND`(API 17과 같은 기준, `LegalCaseRepository.findPublishedById`). **사건 공개와 대본 공개는 별개**라서, 사건이 `PUBLISHED`여도 대본이 미승인이면 `SCRIPT_NOT_FOUND`로 내려간다 — 사건은 먼저 공개하고 대본은 나중에 승인하는 순서를 막지 않기 위해서다(BE-108 결정과 동일한 원칙).

### 5. 검수용 값(`manual` · `editedAt` · `validation` · `attempts`)을 내려줄까
- A안(해송님 제안, 채택). **안 내려준다.** 사람이 고친 줄도 같은 응답에 그대로 나오면 충분하고, 검수 내부 사정을 공개 API에 노출할 이유가 없다. `PublicCaseScriptResponse.EvidenceLine`은 `factorId` · `side` · `character` · `card` · `text` 다섯 칸만 둔다(A-13-10의 `CaseScriptResponse`와는 다른 레코드).

### 6. 재생 순서
- 지금은 배열 순서에 의존한다. 별도 `order` 필드를 둘지 해송님께 여쭸으나, "배열 순서 = 재생 순서"를 계약에 명시하는 것으로 충분하다고 정리됐다 — 구현에서 저장된 `evidence` 리스트 순서를 그대로 보존한다(필터링 · 재정렬 없음).

## 선택한 방법과 이유

- `GET /cases/{caseId}/script`(API 18)를 `LegalCaseController`에 API 17과 나란히 둔다. 서비스(`CaseScriptQueryService`)는 `CasePaperQueryService`와 같은 모양 — "적재 · 검수가 끝난 것을 가져다 조립만 한다. 새로 저장하지 않는다."
- `factorId`별 `card`는 A-13-10의 `AdminCaseScriptService.response()`와 같은 방식으로 판단 요소를 조회해 붙인다(파이프라인 `factorId` = `factor.display_order`, BE-93 2차).
- 피고인신문처럼 한 캐릭터가 두 배역을 번갈아 맡는 장면은 이번 응답에 들어오지 않는다(해송님 지적) — 그 장면이 서버 데이터로 들어올 때 `cast` 구조 확장이 필요하다(FE-60 "추후 재검토" 항목, 아래 참고).

## 고려한 제약 사항

- BE-108이 `CaseScript.isPublic()`을 이미 만들어 두었다(`reviewStatus == APPROVED`) — BE-109는 이 메서드를 그대로 쓴다.
- `case_script.evidence`는 jsonb 한 칸이라(BE-108 결정 2) 서버는 저장된 `Map` 그대로 읽어 변환만 한다 — DB 스키마 변경 없음.

## 추후 재검토가 필요하면

- 공소사실 · 쟁점 정리 · 피고인신문 등 사건마다 달라지는 나머지 막 — BE-107 후속 확장(파이프라인이 더 많은 대사를 만들게 되면) 때 이 API의 응답에 막을 추가할지, 별도 API로 둘지 다시 정해야 한다.
- 피고인신문처럼 한 캐릭터가 두 배역을 번갈아 맡는 장면이 서버 데이터로 들어오면 `cast` 구조(지금은 `{prosecutor, defense}` 고정 두 자리) 확장이 필요하다(FE-60).
