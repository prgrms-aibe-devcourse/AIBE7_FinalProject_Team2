# BE-102 의사결정 기록

## 문제 / 배경
- BE-78 2차 검토에서 "공개 API는 신문 지면과 묶어 하나로 둔다"까지는 합의했지만, 발단 · 결론 사진을 응답에
  정확히 어떤 모양으로 담을지는 구현 단계에서 정해야 했다.
- FE-64 이슈 설명에는 `subPhotos: [발단, 결론]`(배열, `{src, caption}`)이라는 초안이 이미 적혀 있었다 —
  FE-64 담당(김해송)이 BE-78 · BE-91 결론이 나오기 전에 먼저 적어 둔 추정치였다.

## 검토한 대안

### 1. 발단 · 결론 사진을 배열로 줄까, 고정 자리로 줄까
- 대안 A — FE-64 초안대로 `subPhotos: [{src, caption}, ...]` 배열. 프론트가 이미 그런 형태를 가정하고
  있었다면 수정이 적을 수 있다.
- 대안 B(선택) — `extraPhotos: { origin, conclusion }` 고정 자리(그 역할이 없으면 그 자리는 `null`).
  배열로 주면 "발단을 아직 안 올렸을 때 결론 사진이 배열 0번 자리로 밀려 발단처럼 보이는" 문제가 그대로
  재현된다 — 이게 정확히 BE-101에서 `display_order`(채번) 대신 `role`(역할 칸)을 둔 이유다. 같은 문제를
  공개 API에서 배열로 다시 만들 이유가 없다고 판단했다.

### 2. 대표사진 필드 이름 — `photo` vs `thumbnailUrl`
- 대안 A — FE-64 초안의 `thumbnailUrl`을 그대로 쓴다. API 16(`GET /cases/{caseId}`)이 이미 쓰는
  이름이라 프론트 입장에서 더 익숙할 수 있다.
- 대안 B(선택) — 관리자 신문 지면 API(A-13-6 ~ 8, `CasePaperResponse.photo`)와 같은 이름 `photo`를
  쓴다. 신문 지면 응답(관리자 · 공개 둘 다)이 같은 필드명을 쓰면 나중에 두 응답을 비교하거나 한쪽 코드를
  재사용하기 쉽다. API 16의 `thumbnailUrl`은 "사건 카드"라는 다른 맥락의 필드라 이름이 겹쳐도 의미가
  다르다는 점도 고려했다.
- 둘 다 구현 비용은 DTO 필드 이름 하나 차이라 크지 않다. 결정 전 Jira(BE-102) 댓글로 제안하고 FE-64
  담당의 확인을 기다렸다 — 반대 의견이 없으면 이 문서의 선택대로 간다.

### 3. 조회 실패를 어떤 순서로 가릴까
- 대안 A — `case_paper`가 없으면(관리자가 아직 신문 지면을 안 만들었으면) 사건 자체가 없는 것처럼
  `CASE_NOT_FOUND`로 뭉뚱그린다.
- 대안 B(선택) — 공개 여부는 `CASE_NOT_FOUND`, 신문 지면 존재 여부는 기존 에러 코드 `PAPER_NOT_FOUND`로
  따로 구분한다. 이미 있는 에러 코드(BE-92, 관리자 API가 쓰던 것)를 재사용했을 뿐이라 비용이 없고,
  프론트가 "사건이 없다"와 "사건은 있는데 지면이 아직 없다"를 구분해 안내할 수 있다.

## 선택한 방법과 이유
- `GET /cases/{caseId}/paper` 신설. 응답: `desk · headline · deck · photo · caption · article`
  (관리자 응답과 같은 필드명) + `extraPhotos: { origin, conclusion }`(고정 자리, 각 `{imageUrl, caption}`).
- 비공개 · 존재하지 않는 사건은 404 `CASE_NOT_FOUND`(API 16과 같은 기준, `LegalCaseRepository.findPublishedById`
  재사용), 신문 지면 미생성은 404 `PAPER_NOT_FOUND`.
- 새 테이블 · 새 컬럼 없음 — `CasePaperRepository.findByLegalCaseId` · `CaseIncidentPhotoRepository.findByLegalCaseIdAndRole`
  (BE-101)를 그대로 재사용해 조립만 하는 `CasePaperQueryService`를 신설했다(`LegalCaseController`에 엔드포인트
  추가).

## 고려한 제약 사항
- FE-64가 이 응답을 실제로 어떻게 쓰는지(증거조사 `evidencePhotos` 연결, 공용 컷 fallback 분기)는 프론트
  쪽 작업이라 이번 범위에 넣지 않았다.
- `photo`/`thumbnailUrl` 필드 이름은 FE-64 담당이 반대하면 쉽게 바꿀 수 있는 부분이라, 이견이 나오면
  이 문서를 갱신하고 응답만 고치면 된다(스키마 변경이 아니므로 마이그레이션 영향 없음).

## FE-64 담당(김해송) 확인 반영
- 응답 형태(고정 자리, `photo` 필드명, `imageUrl` 필드명, null 처리, `CASE_NOT_FOUND`)는 제안대로 확정.
- `evidencePhotos`는 "검사 = 결론, 변호인 = 발단"이 맞는 기준이다(FE-64 설명에 반대로 적혀 있던 건
  오기) — BE-102는 `evidencePhotos`를 직접 내려주지 않고 `extraPhotos.origin`/`conclusion`만 주므로
  이 매핑은 프론트(FE-64)가 연결할 때 적용한다.
- **`desk` 기본값을 "사회면" → "사회부"로 바꿨다**(프론트 S-02 기사 기자 줄과 맞춤, `CasePaperService.DEFAULT_DESK`).
  이미 생성된 `case_paper` 행의 `desk`는 바뀌지 않는다 — 관리자가 A-13-6(재생성)을 다시 눌러야 새 기본값이
  반영된다. 스키마 변경이 아니라 마이그레이션은 두지 않았다.
- **호출 흐름**: API 16(`GET /cases/{caseId}`)은 `title · overview · thumbnailUrl` 등 사건 카드 값만
  주고 `headline · deck · article`은 아예 없다 — 두 API가 필드 자체는 겹치지 않는다. S-20(사건 디테일)은
  카드 정보(API 16)와 신문 기사 지면(API 17)을 **함께** 부르는 화면이고, 체험 중 신문 지면만 보여주는
  장면은 API 17만 부르면 된다고 확인했다.
- **마이페이지 일괄 조회**: 이번 이슈 범위에는 넣지 않고, 완료한 사건마다 API 17을 사건별로 부르는
  방식으로 먼저 간다(FE-64 담당 동의). 사건 수가 늘어 성능 문제가 생기면 그때 일괄 조회 API를 별도
  이슈로 만든다.
- `caption`이 `null`이면 프론트가 고정 문구로 대체한다 — 서버는 `null`을 그대로 내려주면 된다(구현
  변경 없음, 이미 그렇게 돼 있었다).
