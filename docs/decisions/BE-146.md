# BE-146 의사결정 기록

> 근거: 10/29 회의(사건 체험은 로그인 없이, **순차 해금식**), BE-140 결정("해금 조건은 체험 횟수, 구체 값은 도전과제 리밸런싱과 함께 BE-146"). 값은 김해송 결정(2026-11-02). 관련: BE-96(도전과제 판정) · BE-83(수집) · BE-106(경험치) · BE-126(대본 상태). 테이블은 ERD v1.56(V50), API는 명세 v0.89.

## 문제 / 배경
- 사건을 처음부터 모두 열어 두면 "다음 사건을 열고 싶다"는 동기가 없다. 손님(로그인 전)도 해금이 동작해야 한다.
- 해금 조건과 도전과제(사건 · 수집 목표)가 따로 놀면 같은 행동에 보상 기준이 둘이 된다. 그래서 함께 정한다.
- 지금 사건에는 해금 순서로 쓸 칸이 없다. 서버는 공개일 최신순, 화면은 체험 가능 → 참여자 수 순으로 다시 정렬한다.

## 검토한 대안

### 1. 해금 순서
- **A(선택): 새 칸 `legal_case.unlock_order`** — 운영자가 쉬운 사건부터 정할 수 있다. 칸 추가뿐이라 BE-60에 맞다.
- B: 공개일 오래된 순 — 마이그레이션은 없지만 새 사건이 늘 맨 뒤이고 순서를 고칠 수 없다.
- C: 난이도 → 사건 번호 — 운영 부담은 없지만 같은 난이도 안의 순서를 정할 수 없다.

### 2. 해금 규칙
- 처음 3건 + 완료마다 1건 — 단순하지만 도전과제와 맞물리는 지점이 없다.
- 처음 1건 + 완료마다 1건 — 첫 사건이 맞지 않으면 진행이 막힌다.
- **단계 묶음(선택)** — 처음에는 0 → 3 · 1 → 6 · 3 → 10 · 6 → 15 · 10 → 전체를 냈으나, 시연 · 테스트 기간에 전체를 빨리 볼 수 있게 **0 → 3 · 1 → 6 · 3 → 12 · 5 → 전체**("더 빠르게")로 정했다. 단계 1 · 3 · 5가 도전과제 `first-case` · `cases-3` · `cases-5`와 겹친다.

### 3. 서버에서도 막는가
- 화면만 막기 — 대본 준비 중(`scriptReady`)과 같은 방식. 주소를 직접 열면 체험할 수 있다.
- **API 2에서 409 `CASE_LOCKED`(선택)** — 기존 체험이 없을 때만 본다. 진행 중 · 가져온 체험은 잠김과 상관없이 이어 간다. API 4 ~ 15는 기존 체험이 있어야 하므로 API 2 한 곳만 막으면 된다.

### 4. 준비 중 · 점검 중 사건
- 순서에 넣기 — 단순하지만 열린 자리가 "준비 중" 사건이면 실제로 할 수 있는 사건이 줄어든다.
- **순서에서 빼고 세기(선택)** — 체험할 수 있는(`READY`) 사건만 자리를 차지한다. 준비 중 · 점검 중 사건은 `locked: false`이고 화면이 "준비 중" · "점검 중"으로 막는다. 대본이 READY가 되면 그때 순서에 들어온다.

### 5. 새 도전과제
- **`cases-5` · `collect-50` 추가, 꾸미기 보상 없이 경험치 200씩(선택)** — 새 그림 · 테두리가 필요 없고, 보상은 나중에 `ProfileDecoCatalog`만 고쳐 더할 수 있다.
- 기존 보상(예: `attend-30`의 보상) 옮기기 / `cases-10`만 추가 / 표 유지 — 채택하지 않았다.

## 선택한 방법과 이유

### 해금 계산 (`CaseUnlock` · `LegalCaseService`)
- 상태를 저장하지 않고 요청마다 계산한다. 완료한 사건 수는 도전과제 `completed`와 같은 쿼리(`countCompletedCases(Owner)`)다 — 마이페이지의 완료 수와 해금 기준이 어긋나지 않는다.
- 주인은 BE-140 `Owner`다: 회원이면 회원, 아니면 익명 ID 쿠키, 쿠키가 없으면 완료 0건. 첫 로그인 가져오기(M-10)로 체험이 옮겨지면 해금도 그대로 따라온다.
- 순서는 `unlock_order` 오름차순, 비면 그 뒤에 id 순. 처음에는 모두 비어 있어 **사건 id 순**으로 열린다.
- **이미 체험한 사건은 늘 열려 있고, 다른 사건의 자리를 빼앗지 않는다**(순서 창은 체험 여부와 상관없이 앞에서부터 센다). 그래서 API 2는 "이 사건을 아직 체험하지 않았을 때"만 확인하면 된다.
- 해금은 `crimeType` 필터와 상관없이 전체 공개 사건 기준이다.

### API
- API 1: 최상위 `unlock`(`completedCases` · `nextStepAt`) · 카드 `locked`. API 16: `locked`. 필드 추가뿐이라 기존 클라이언트와 호환된다.
- API 2: 기존 체험이 없고 잠긴 사건이면 409 `CASE_LOCKED`. **쿠키를 발급하기 전에 확인한다** — 잠긴 사건으로 익명 ID만 생기는 일을 막는다.

### 도전과제
- `ProfileDecoCatalog.ACHIEVEMENTS`에 `cases-5`(`cases-3` 뒤) · `collect-50`(`collect-20` 뒤)를 더했다. `rewards`는 `Rewards.NONE`. XP는 `LevelXp`에 200씩. 도전과제 XP 합계 850 → 1250.
- V35 백필(1회성)은 고치지 않는다. 배포 뒤 이미 5건을 완료한 회원은 다음 마이페이지 조회 때 "새로 열림"으로 보이는데, 새 도전과제라 맞는 동작이다(`ProfileDecoCatalogTest`가 V35 이후 추가분을 제외한다).
- 화면: 제목 · 문구를 `ACHIEVEMENT_TEXT`에 더했고, 꾸미기 보상이 없으면 "보상: 경험치"로 보인다.

## 운영 절차 — 해금 순서 정하기
- 관리자 화면 없이 SQL로 정한다. 값이 겹치면 id 순이고, 비어 있는 사건은 값이 있는 사건 뒤에 id 순이다.

```sql
-- 예: 처음 열릴 세 사건을 정한다 (사건 id는 환경마다 다르니 제목으로 찾는다)
UPDATE legal_case SET unlock_order = 1 WHERE title = '…';
UPDATE legal_case SET unlock_order = 2 WHERE title = '…';
UPDATE legal_case SET unlock_order = 3 WHERE title = '…';
-- 지금 순서 확인 (체험할 수 있는 사건만 순서에 선다 — 대본 상태는 API 1 scriptStatus로 확인)
SELECT id, title, unlock_order FROM legal_case WHERE status = 'PUBLISHED'
 ORDER BY unlock_order NULLS LAST, id;
```

- **운영 `unlock_order` 제안**(PR #392 리뷰): 처음 열리는 3건은 서비스의 첫인상이라, 사전 학습 점검(AI가 판결을 미리 알고 있을 가능성)에서 CLEAN으로 분류된 사건 중 대본이 준비된 사건을 앞에 두고 CONTAMINATED 사건은 뒤 단계로 둔다. 분류는 비공개 자료에 있어 이 문서에는 적지 않는다(값은 비공개로 공유).
- 순서를 바꾸면 그 즉시 모든 사용자의 잠김이 다시 계산된다. 이미 체험한 사건은 영향이 없다.

## 고려한 제약 사항
- **대본 승인 · 점검으로 열림 · 잠김이 바뀔 수 있다**(PR #392 리뷰): 순서에는 READY 사건만 서므로 (1) 순서가 앞선 사건의 대본이 새로 승인되면(PREPARING → READY) 그 사건이 자리를 차지해, 사용자가 "열림"으로 본 뒤 아직 시작하지 않은 사건이 잠길 수 있고, (2) 점검 중(MAINTENANCE)으로 바뀐 사건이 순서에서 빠지면 뒤 사건이 일시적으로 열렸다가 점검이 끝나면 다시 잠길 수 있다. 이미 체험한 사건은 영향이 없다. 사건 적재 · 대본 승인이 제출 직전까지 이어질 예정이라 **알고 감수한다** — 점검 중 사건도 순서에 세우는 안(화면이 "점검 중"으로 막음)은 대안 4의 결정을 뒤집는 일이라 따로 정한다.
- **새 도전과제 소급**: `cases-5` · `collect-50`은 기록으로 계산하므로, 이미 5건을 완료했거나 50장을 모은 사용자는 배포 직후 경험치 200씩과 "새로 열림"을 한꺼번에 받는다. 새 도전과제라 의도된 동작이다(회원 데이터는 BE-140으로 초기화돼 영향받는 사용자는 거의 없다).
- **배포 순서**: develop → main PR은 누가 올리든 develop 전체가 나간다. 화면 작업 전에 다른 이유로 main 배포가 있으면 아래 일이 운영에서 일어나므로 **main 배포 담당에게 이 조건을 공유한다**(PR #392 리뷰). 이 변경만 운영에 나가면 지금 화면은 `locked`를 몰라 잠긴 사건도 "체험 시작"을 보이고, 누르면 API 2가 409를 준다. 그래서 **develop 병합은 바로 해도 되지만 main(운영) 반영은 화면 작업(잠김 표시 · 409 처리)과 같은 배포로 묶는다**(BE-83과 같은 방식).
- 도전과제 화면 · 레벨 · 마이페이지는 로그인 전용이라(BE-140 3b) 손님은 도전과제를 보지 못하지만, 해금은 손님에게도 동작한다.
- 해금은 공개 사건 전체를 읽어 계산한다. 사건 수가 수십 건이라 목록 · 상세 · 체험 시작마다 한 번 더 읽어도 부담이 작다(API 1은 이미 읽은 목록을 쓴다).
- 사건 1이 비공개로 바뀌어도(저작권) 순서 계산에서 자동으로 빠진다.

## 추후 재검토가 필요하면
- 사건 수가 크게 늘면 단계 값(특히 "5건 → 전체")을 다시 본다. 값은 `CaseUnlock.STEPS` 한 곳이다.
- 운영자가 순서를 자주 바꾸면 관리자 사건 수정(A-11)에 `unlockOrder`를 더한다.
- 새 도전과제(`cases-5` · `collect-50`)의 꾸미기 보상은 그림이 준비되면 `ProfileDecoCatalog`에 더한다.
- 체험 기록 무효화(BE-144)가 생기면 무효 기록은 완료 수에서 빠져 해금 단계가 내려갈 수 있다 — 이미 체험한 사건은 열려 있으므로 진행 중인 체험은 막히지 않는다.
