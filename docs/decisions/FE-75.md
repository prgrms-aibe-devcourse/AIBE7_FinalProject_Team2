# FE-75 의사결정 기록

## 문제 / 배경
- 마이페이지 "내가 체험한 사건"에서 사건마다 내 결과(처음 판단 · 최종 판결 · 그 사건으로 나온 판결 성향)를 다시 볼 자리가 없었다.
- 마이페이지 응답(P-5)에는 사건별 형량이 없고, 사건별 축 점수만 `history`에 있다.
- 마친 체험은 "1막부터 다시 보기"도 읽기 전용이라(API 명세 BE-77) 상태가 `COMPLETED`에서 바뀌지 않는다. 그래서 버튼은 `COMPLETED` 사건에만 둔다.
- 같은 이슈에서 마이페이지 첫 화면 성향카드 · 프로필카드가 성향카드 화면과 다른 유형(성향 테스트 유형)을 보여 주던 것도 맞췄다.

## 검토한 대안

### 데이터
- 대안 A: 버튼을 누를 때 API 14(세 판결 비교)를 부른다. `preToFinal`에 처음 판단 · 최종 판결이 이미 있다. 백엔드 변경이 없고, 누를 때 한 번 로딩이 있다.
- 대안 B: P-5 `experiences[]`에 처음 판단 · 최종 판결을 넣는다. 화면은 바로 그릴 수 있지만 `MyPageService` · DTO · API 명세 · 테스트를 고쳐야 하고, 자주 쓰지 않는 값을 마이페이지를 열 때마다 모든 사건에 실어 보낸다.

### 화면
- 대안 C: 6막 세 판결 비교 화면(S-08, `/cases/{caseId}/compare`)을 `from: 'me'` 표시로 재사용하고 맨 위 기사만 바꾼다. 처음에는 이 방법으로 만들었다.
- 대안 D: 마이페이지 아래에 별도 화면(`/me/cases/{caseId}`)을 두고, 6막 지면의 부품(제호 · 1면 · 독자 의견 · 만난 모습 · 광고)만 가져다 쓴다.

## 선택한 방법과 이유
- 데이터는 대안 A. 자주 쓰지 않는 칸이라 필요할 때 부르는 쪽이 맞고, 백엔드를 건드리지 않는다. 이 사건의 성향과 흐름 그래프는 P-5(`history` · `judgmentPersonality`)를 함께 불러 쓴다.
- 화면은 대안 D. 요구가 "세 판결 · 판단 요소 · 공통점과 차이점" 세 기사를 모두 바꾸는 것으로 정해지면서 6막 지면에서 남는 것이 제호 · 1면 · 독자 의견 · 만난 모습 · 광고뿐이 됐다. 대안 C로 두면 6막 코드에 분기가 여러 군데 생기고, 무대 대본이 찾는 기사를 지우지 못해 CSS로 감춰야 했다. 표시가 주소가 아니라 방문 기록(`history.state`)에 있어서 주소를 새 탭에 열면 6막 화면이 열리는 문제도 있었다.
- 지면 구성(6막 → 내 결과):
  - 제호 · 1면 · 광고: 모양은 그대로. 1면 헤드라인 · 리드는 사건 제목과 판결을 내린 판사(나, 닉네임)를 중심으로 바꾼다. 리드의 바뀌는 값은 모두 API 값(사건 제목 · `preToFinal.preJudgment.label` · `finalJudgmentText` · `direction`)이고, 값 바로 뒤에 받침에 따라 갈리는 조사를 붙이지 않는다. `direction`은 세 문장 중 하나로 고른다
  - 독자 의견 · 세 판결, 나란히 · 만난 모습: 싣지 않는다. 첫인상 구간과 최종 판결은 1면 리드에 굵게 싣는다. AI · 실제 판결은 싣지 않는다
  - 왼쪽 단은 1면 · 판결 성향, 오른쪽 단은 흐름 그래프. 두 단은 각자 세로로 쌓는다(한 격자에 두면 긴 그래프가 줄 높이를 늘려 다른 단 기사 사이가 벌어진다). 두 단의 위 · 아래 끝선을 맞추고, 짧은 단의 남는 높이는 기사 사이에 똑같이 나눈다
  - 판단 요소, 어디서 갈렸나 → 이 사건으로 달라진 내 성향(성향카드의 성향 변화 흐름 그래프, 이 사건 칸에 띠)
  - 같게 본 것, 다르게 본 것 → 이 사건에서 드러난 판결 성향(이 사건 한 건의 4축 + 그 유형의 성향카드(마이페이지 `typeFace` 그대로, 왼쪽) + 오른쪽 설명: 유형 이름 + P-4 `verdictDescription`)
  - 지면 글(리드 · 그래프 안내 · 카드 설명)은 기사 문체("~다")로 쓴다. 불러오기 실패 안내만 화면 안내 문체로 둔다
- 이 사건 한 건의 유형은 API가 바로 주지 않는다(P-5 `history`는 축 점수만). 화면이 축 점수로 유형 코드를 고르고(`typeCodeOf`, 네 축이 다 있을 때만, 반반은 관대 글자), 코드를 shareId로 바꿔(`utils/personalityTypes.js`의 `shareIdOfCode`, 유형 번호 → `og/personality-types.json`의 서버 시드 shareId) P-4 `GET /personality/types/{shareId}`로 유형을 받아 온다. 카드 내용(이름 · 대사 · 이미지)은 서버 값이다.
  - 이를 위해 목 P-4의 shareId를 코드 해시에서 서버 시드 값으로 바꿨다(목과 실제가 같은 shareId). 유형 번호표(`TYPE_NUMBERS`)는 목 데이터에서 `utils/personalityTypes.js`로 옮겼다.
  - 대안: 서버가 P-5 `history[]`에 유형을 넣는다. 화면이 코드를 다루지 않아도 되지만 백엔드 변경이 필요해 이번에는 하지 않았다.
- 6막 읽기 화면과 같은 클래스 구조(`.comparison-full .stage-wrap.reading-paper .stage .scene .sheet`)로 감싸 지면 스타일을 그대로 받는다. 대사 · 카메라는 쓰지 않는다.
- 성향 변화 흐름 그래프는 `components/trendGraph.js`로 옮겨 마이페이지와 함께 쓴다. 강조할 사건이 최근 10건 밖이면 칸을 끼워 넣는다(`trendSlotOrders`).

## 고려한 제약 사항
- 목 API 14는 1번 사건 · 체험 완료 상태만 응답하는데, 마이페이지 목은 9개 사건을 마친 기록이다. 목 전용 두 번째 인수 `{ record: true }`로 상태 · 사건 번호 검사를 건너뛰고 1번 사건 비교 목을 돌려주며, 화면에 "목데이터"를 표기한다. 실제 API는 이 인수를 쓰지 않는다.
- 실제 API의 P-5 `judgmentPersonality`는 아직 전체 평균이다(API 명세 v0.44, 서버 구현은 후속 백엔드 작업). 성향카드 일치와 흐름 그래프의 "현재" 칸은 서버 반영 전까지 명세와 다를 수 있다.

## 추후 재검토가 필요하면
- 서버가 P-5 `history[]`에 사건별 유형을 넣게 되면 `shareIdOfCode` 경유 대신 그 값을 쓴다.
- 판사 이름은 마이페이지 프로필카드와 같은 값(`data.nickname`, 없으면 "익명의 판사")이다. P-5에는 닉네임이 없어 지금은 늘 "익명의 판사"다. 로그인 닉네임을 쓰게 되면 마이페이지와 함께 바꾼다.
- "내 결과 보기"를 자주 쓰게 되면 P-5에 요약 필드를 넣는 대안 B를 다시 본다.
