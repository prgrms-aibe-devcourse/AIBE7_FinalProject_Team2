# BE-140 의사결정 기록

> 근거: Jira BE-140 댓글(10/29 ~ 30 결정), FE-138(PR #347, 로그인 전 화면 · 첫 로그인 가져오기 창 — 먼저 배포됨), BE-62(익명 ID ↔ 회원 연결), BE-137(로그아웃 시 익명 ID 쿠키 해제). 테이블은 ERD v1.50(15장 · 3-2 · 8 ~ 14장), API는 명세 M-9 ~ M-11(PR3c에서 추가).

## 문제 / 배경
- 마이페이지 · 레벨 · 꾸미기 · 출석 · 컬렉션 · 도전과제 · 커뮤니티 명함 데이터가 모두 **익명 ID(브라우저 쿠키 `NLNB_AID`) 기준**이다. 처음 설계가 익명 중심이었고, 로그인(BE-62)은 익명 ID에 회원 ID를 붙이기만 하고 데이터를 옮기지 않았다.
- 10/29 회의 결정: 로그인 없이는 **체험(과 성향 테스트)만** 하고, 수집 · 꾸미기 · 커뮤니티 글쓰기는 로그인 뒤에 쓴다. 로그인 전 마이페이지는 껍데기만 보인다.
- 그래서 사용자 데이터의 주인을 회원으로 바꾸되, 손님도 쓰는 체험 · 성향 테스트는 손님과 회원이 함께 쓸 수 있어야 한다.

## 결정 사항 (김해송 결정, 10/29 ~ 30)
- **체험만 이관**한다. 첫 로그인(회원 체험 0건)일 때 이 브라우저(쿠키의 익명 ID 하나)의 체험을 회원 것으로 **이동**한다(복사가 아니다 — 공용 PC에서 여러 사람이 로그인할 때 무한 복제를 막는다). 첫인상 엽서(사전 판단)와 체험 기여(`experience_personality`)는 체험에 딸려 간다.
- 성향 테스트 결과(`personality_result`)는 이관하지 않는다. 로그인 전에도 테스트는 할 수 있다.
- 나머지(출석 · 꾸미기 · 프로필 설정 · 경험치 · 직업 · 수집 · 도전과제)는 **초기화**한다. 도전과제 · 수집은 체험 결과를 다시 보거나 다시읽기 모드로 열면 다시 풀린다. 이미 쌓인 익명 데이터는 버려도 된다(기존 회원 없음).
- 첫 로그인 때 **경고 창**으로 [가져오기] · [초기화하고 로그인]을 고르게 한다. 창을 닫으면 로그인하지 않는 것(로그아웃)이다(FE-138).
- 가져오기 후보는 **현재 쿠키의 익명 ID 하나뿐**이다. 로그인 연결은 익명 ID에 회원 ID를 붙이는 것이라 다른 익명 ID가 후보가 될 일이 없다.
- 커뮤니티 글쓰기는 지금 로그인 전용이되, 반응을 보고 비로그인 작성으로 넓힐 여지를 남긴다(작성자 = 회원 또는 익명 ID).
- 해금 조건(체험 횟수)은 도전과제 리밸런싱과 함께 BE-146에서 정한다.
- 배포는 프론트 먼저(FE-138, 병합됨), 서버 나중.

## 검토한 대안
### 소유 키
- A: **이중 칸**(익명 ID · 회원 ID 둘 중 정확히 하나 + 부분 유니크) — 선택. 손님 · 회원이 함께 쓰는 두 테이블에만 쓴다
- B: 통합 소유자 ID(owner 테이블을 따로 두고 모든 데이터가 owner를 가리킴) — 깔끔하지만 모든 사용자 테이블의 키를 바꾸는 큰 이관이 필요하고, BE-60(추가만) 규칙으로는 한 번에 못 한다
- 나머지 7개 도메인: 기존 테이블에 회원 칸을 더하는 대신 **회원 키 새 테이블**(선택). 익명 데이터는 초기화하므로 옮길 것이 없고, 옛 테이블을 쓰지 않게 두었다가 지우면 된다. 기본 키(익명 ID)를 바꾸지 않아 지금 앱이 그대로 돈다

### 거절(초기화) 처리
- 익명 기록을 바로 지운다 / **결정만 남기고 기록은 두었다가 정리 배치로 지운다**(선택). 잘못 눌러도 되돌릴 여지가 있고(PR #347 리뷰 — jms0326), 지우는 비용을 요청 경로에서 뺀다

### PR 나누기
- 한 PR / **단계별 PR**(선택): PR1 스키마 → PR2 `Requester`/`Owner` 도입(동작 변화 없음) → PR3 통합 브랜치에서 3a 체험 · 성향 이중 소유 → 3b 7개 도메인 회원 키 전환 → 3c 가져오기 API → PR4 커뮤니티 작성자. 깨지는 테스트가 32개 파일이라 한 번에 리뷰하기 어렵다

## 1차 (PR1 — 스키마 V40 ~ V43)
- **V40**: `experience` · `personality_result`의 `anonymous_user_id` NOT NULL을 풀고, 회원 칸(`experience.member_id`는 V3부터 있던 칸을 "주인 회원"으로 다시 쓴다 — 아무도 채우지 않았다) · FK · CHECK `num_nonnulls(anonymous_user_id, member_id) = 1`을 더한다. 기존 익명 유니크(`uk_experience_user_case_attempt` 등)는 그대로 둔다 — NULL끼리는 겹치지 않아 회원 행을 막지 않는다. 회원 쪽 유니크 · 조회는 `WHERE member_id IS NOT NULL` 부분 인덱스로 따로 둔다.
- **V41**: 회원 키 테이블 7개. 칸 · 제약은 익명 쪽과 같고, FK 삭제 동작만 `ON DELETE CASCADE`다(회원이 지워지면 함께 지운다).
- **V42**: `member_anonymous_import` — 회원마다 한 줄(IMPORTED · DISCARDED, 옮긴 체험 수). 기록이 있으면 다시 묻지 않는다. 버린 익명 ID 쿠키만 지우고 기록은 둔다.
- **V43**: 커뮤니티 글 · 댓글 작성자를 회원 또는 익명 ID로 넓힌다. 지금 앱이 두 칸을 다 채우므로 "적어도 하나"로만 묶고, "정확히 하나"로 좁히는 일은 PR4 이후 배포로 나눈다.
- **BE-60(추가만) 확인**: NOT NULL 해제 · 칸 · 제약 · 인덱스 · 테이블 추가뿐이다. 지금 앱은 늘 익명 ID만 채우고 회원 칸을 쓰지 않아 새 CHECK를 어기지 않는다. 지금 코드 그대로 새 스키마에서 백엔드 전체 테스트(1053개)가 통과했다.
- 테스트: `DbConstraintTest`에 BE-140 제약 13건(주인 정확히 하나 · 회원 부분 유니크 · 회원 테이블 기본값 · 유니크 · CASCADE · 가져오기 결정 CHECK · 커뮤니티 작성자).

## 고려한 제약 사항
- 서버 한 대 · 자동 되돌림(BE-60): 배포가 실패해 이전 앱으로 돌아가도 새 스키마에서 떠야 한다 → 스키마는 이전 앱과 호환되게 먼저(PR1) 내보내고 코드 전환은 뒤에 한다.
- 체험 · 성향 결과 · 커뮤니티의 회원 FK는 `NO ACTION`이라 회원 탈퇴를 만들 때 그 행들을 먼저 정리해야 한다(탈퇴는 아직 없다).
- 마이그레이션 번호: BE-115 · BE-139에서 develop과 두 번 겹쳤다. 각 PR 시작 전에 `origin/develop`과 열린 PR의 번호를 확인한다.

## 리뷰 반영 (PR #351, jms0326)
- **번호 충돌**: #349(BE-133)가 같은 `V40` · ERD v1.50을 쓴다. 이 PR을 먼저 병합하고 BE-133이 V44 · ERD v1.51로 옮긴다(jms0326 제안, 병합 순서 합의). 마이그레이션은 파일 이름이 달라 git이 충돌로 알려 주지 않으므로 병합 전에 `origin/develop`의 번호를 다시 확인한다.
- **`member_anonymous_import.anonymous_user_id`의 FK(NO ACTION)**: 버린 익명 기록은 정리 배치가 `experience` 등 **데이터 행**만 지우고 `anonymous_user` 행은 남기는 것이 의도다(익명 ID는 쿠키 값이라 행이 작고, 가져오기 기록이 가리킨다). 행까지 지우게 되면 그때 이 칸을 비울 수 있게 하는 마이그레이션을 더한다.
- **PR3 배포 뒤 자동 되돌림**: 회원만 주인인 행(`anonymous_user_id IS NULL`)이 생기면 이전 앱이 익명 ID가 늘 있다고 가정한 경로에서 깨질 수 있다. PR2(`Requester`/`Owner`, 동작 변화 없음) 리뷰에서 **익명 ID가 빈 행을 견디는지** 함께 확인해, PR3 배포 뒤 되돌림이 PR2까지만 가도 안전하게 한다.
- 큰 테이블에 제약을 더할 때는 `NOT VALID` 뒤 `VALIDATE CONSTRAINT`로 나눈다(지금은 행이 작아 한 번에 더했다).
