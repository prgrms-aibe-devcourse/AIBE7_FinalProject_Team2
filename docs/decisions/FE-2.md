# FE-2 의사결정 기록

> MVP 단계(WBS 3.1) · PR #55 · 담당 정민석

## 문제 / 배경
- S-01 ~ S-09 화면이 각자 목(mock) API로만 동작하고 있어, 이를 하나의 앱으로 묶는 공통 기반(History API 라우터, API 클라이언트, 공통 레이아웃)이 필요했다.
- 팀원 화면 파일(각 `renderXxxPage`)은 수정하지 않고 공통 기반만 추가해야 했다 (IA 7장 · API 명세 1-6 기준).
- S-04 · S-05 · S-06에 "FE-2 연결 시 이동"이라는 TODO가 남아 있어, 에러 응답에 따른 화면 이동을 화면 수정 없이 해소해야 했다.

## 검토한 대안
- 에러 발생 시 이동 처리 위치: 화면(`renderXxxPage`) 각자에서 처리할지, 화면을 감싸는 공통 지점(`api` 객체)에서 처리할지 검토했다. 화면은 이미 `api`를 주입받아 에러를 코드별로 처리하는 구조라, 화면 수정 없이 이동만 추가하려면 `api` 객체를 감싸는 쪽이어야 했다.
- 뒤로 가기 동작: `INVALID_STATE` 이동에 `replace`를 쓰되, 더 앞선 기록은 그대로 남아 있어 뒤로 가기를 반복하면 같은 이동이 반복되는 문제가 있었다 (PR 리뷰에서 발견).

## 선택한 방법과 이유
- 에러 시 화면 이동은 화면이 아니라 `api` 객체를 감싸 처리한다. 화면은 모두 자기 `root`에 그리고 `active()`로 자신이 현재 화면인지 확인하므로, 이동 뒤 이전 화면의 늦은 응답이 새 화면을 덮어쓰지 않는다.
- 요청 시작 시점의 이동 번호(`navigationToken`)를 저장해 두고 에러 때 지금 번호와 비교한다. 요청 중 다른 화면으로 이동하면 이전 요청의 에러가 새 화면을 덮어쓰지 않고, 같은 화면의 동시 요청이 여러 개 실패해도 이동은 한 번만 일어난다.
- (리뷰 반영) 조회(get*) 요청의 `INVALID_STATE` 이동이 직전과 같은 화면으로 또 보내졌으면, 뒤로 가기 연타로 보고 기록을 한 걸음 더 건너뛰도록(`history.go(-1)`) 고쳤다. 제출(post*)은 사용자가 직접 누른 동작이라 건너뛰지 않는다.
- `startExperience`의 `CASE_NOT_FOUND`는 이동하지 않는다. 사건 목록 화면이 목록에 머무르며 직접 안내하는 기존 동작을 유지하기 위해서다.
- 사건 상단 바 제목은 사건 목록(API 1) 응답에 제목 · 죄명이 없어, caseId로 목록에서 찾는 임시 방식을 썼다. 개요(API 4) 조회 이후에는 정확한 값으로 갱신되며, `src/app/caseHeader.js` 한 곳만 바꾸면 교체할 수 있게 분리했다.

## 고려한 제약 사항
- 화면이 쓰는 `navigate(이름, { caseId })` 약속과 화면 진입 함수 형태(`renderXxxPage(container, { caseId, caseHeader, api, navigate, section })`)는 그대로 유지해야 했다 (팀원 화면 파일 무수정 원칙).
- 실제 백엔드의 사건 ID는 시드 적재 순서에 따라 1이 아닐 수 있어(시드가 ID를 지정하지 않음), 화면·샘플 페이지 모두 ID를 하드코딩하지 않는다.
- 배포 빌드에서 API 모드 기본값이 `mock`으로 남아 있던 문제, 2xx 응답인데 JSON이 아니면 `null`을 반환하던 문제, `navigate`의 extras가 `api` · `navigate`를 덮어쓸 수 있던 문제 등을 PR 과정에서 발견해 수정했다.
- 쿠키 기반 인증을 쓰므로 `SameSite` 제약(Chrome이 `http://localhost`에서 `Secure` 쿠키를 저장하는지 등)을 직접 확인해야 했다.

## 추후 재검토가 필요하면
- 사건 제목 · 죄명이 API 응답에 추가되면(D-01 결정 이후) `caseHeader.js`만 바꾸면 된다.
- 실제 모드에서 API 10 ~ 14(AI 판결 · 실제 판결 · 비교)가 백엔드에 추가되면 `realApi.js`가 그대로 동작한다.
