# BE-137 의사결정 기록

로그아웃 시 회원에 연결된 익명 ID 쿠키 해제 (공용 PC 기록 섞임 방지). 담당 D(정민석), 리뷰 C(백승호, 로그아웃 BE-94 담당).

## 문제 / 배경

- 로그인(카카오 BE-62 · 아이디 BE-113)은 브라우저의 익명 ID(`NLNB_AID`)를 회원에 연결한다(`AnonymousLinkService`, BE-62 결정 6).
- 로그아웃(M-2, BE-94)은 리프레시 토큰만 지우고 익명 ID 쿠키는 그대로 두었다.
- 그래서 로그아웃 뒤에도 같은 브라우저의 체험 · 판결 · 출석 · 꾸미기가 그 회원 계정으로 쌓인다. 공용 PC에서 A가 로그아웃한 뒤 B가 쓰면 B의 기록이 A의 회원 계정에 섞인다.
- BE-62 "추후 재검토"에 남겨 둔 항목이다. 원인은 연결을 만든 BE-62 쪽이라 D가 맡고, 로그아웃 담당 C가 리뷰한다.

## 검토한 대안

### 1. 로그아웃 때 무엇을 할까

- 대안 A — 로그아웃 때 새 익명 ID를 바로 발급해 쿠키를 바꾼다: 다음 사람이 곧바로 손님 상태가 된다. 그러나 로그아웃만 하고 떠난 브라우저에도 `anonymous_user` 행과 출석 기록이 생긴다. BE-97 "실제로 행동했을 때만 발급" 원칙과 어긋난다.
- 대안 B — 익명 ID 쿠키를 지운다 (**선택**): 다음 행동(API 2 체험 시작 · P-2 성향 테스트 · P-7 꾸미기) 때 기존 `getOrIssue`가 회원과 연결 안 된 새 익명 ID를 발급한다. 새 발급 경로를 만들지 않는다.
- 대안 C — 익명 ID의 회원 연결을 끊는다(`member_id = NULL`): 이전 기록이 회원 계정에서 사라진다. 회원이 다른 기기에서 자기 기록을 볼 수 없게 되므로 택하지 않았다.

### 2. 언제 지울까

- 항상 지운다 / 회원에 연결된 익명 ID일 때만 지운다 (**선택**).
- 로그인하지 않은 상태에서 로그아웃이 불리면(화면 상태가 꼬였을 때 등) 쿠키는 손님 익명 ID다. 이걸 지우면 손님의 체험 기록에 다시 접근할 수 없게 된다. 회원에 연결된 경우만 다음 사람에게 새는 문제가 있으므로 그때만 지운다.
- 리프레시 쿠키 유무와는 관계없이 판단한다. 리프레시 토큰이 만료된 뒤 로그아웃 버튼을 눌러도 익명 ID는 여전히 회원에 연결되어 있기 때문이다.

### 3. 판단을 어디에 둘까

- `AnonymousLinkService.isLinkedToMember` — 연결 규칙(누가 회원에 연결되는가)을 이미 가진 곳에 "연결되어 있는가"도 둔다. 로그아웃(`AuthController`)은 결과만 보고 쿠키를 지운다.
- 쿠키 삭제는 `AnonymousIdCookie.clear`. 발급과 같은 이름 · `Path=/`로 `Max-Age=0`을 보내야 브라우저가 같은 쿠키로 보고 지우므로, 발급과 삭제가 같은 빌더를 쓴다.

## 선택한 방법과 이유

- 로그아웃 응답에서 쿠키의 익명 ID가 회원에 연결되어 있으면 `NLNB_AID`를 `Max-Age=0`으로 지운다.
- 새 익명 ID는 발급하지 않는다. 이전 기록은 회원 계정에 그대로 남는다.
- 카카오 · 아이디 로그인이 같은 `AnonymousLinkService`로 연결하므로 로그아웃 한 곳만 고치면 두 경로가 함께 해결된다.
- API 명세 1-2 · M-2 v0.69에 반영했다(처음 v0.65로 썼으나 develop 머지로 작성 이력 번호가 네 번 밀렸다, PR #340 리뷰).

## 고려한 제약 사항

- 로그아웃 뒤에는 다음 행동 전까지 마이페이지 등이 빈 상태로 보인다. 화면은 로그아웃 때 `nlnb-session`을 지우므로(FE-74) 같은 흐름으로 본다 — PR에서 김해송에게 확인을 요청했다.
- 로그아웃 API는 Origin 검증(BE-94 `OriginVerificationFilter`)을 그대로 받는다. 남의 사이트가 로그아웃을 불러 익명 쿠키를 지우게 할 수 없다.
- 쿠키 삭제는 그 브라우저의 쿠키만 바꾸고 DB는 바꾸지 않으므로, 다른 사람의 익명 ID 값을 넣어 호출해도 영향이 없다.

### 연결 여부를 확인하지 못할 때 (리뷰 반영)

- 로그아웃은 리프레시 토큰을 먼저 폐기하고 그다음 익명 ID 연결을 조회한다. 조회가 실패(DB 오류 · 연결 풀 고갈)하면 처음에는 로그아웃 전체가 500이 되었다 — 리프레시는 이미 폐기됐는데 화면은 로그아웃 실패로 본다.
- 실패 시 **쿠키를 지운다**(안전한 쪽)를 택했다. 처음에는 DB 계열(`DataAccessException` · `TransactionException`)만 받았으나, 리프레시를 폐기한 뒤라 다른 실행 중 예외도 로그아웃을 500으로 만들므로 `RuntimeException` 전체로 넓혔다(PR #340 리뷰). 예상하지 못한 예외도 삼키게 되므로 종류와 스택을 경고 로그에 남긴다. 남겨 두면 다음 사람 기록이 회원 계정에 쌓일 수 있고, 손님 값이었다면 다음 행동 때 새 익명 ID를 받는 것으로 끝난다. 응답은 204, 경고 로그를 남긴다. `LogoutAnonymousCheckFailureTest`가 확인한다.

## 확인

- `AuthControllerTest`: 연결된 익명 ID면 쿠키 삭제(이름 · `Path=/` · `Max-Age=0`), 기록은 회원 연결 유지 / 리프레시 쿠키 없이도 삭제 / 손님 · DB에 없는 값 · 형식 틀린 값은 유지 / 로그아웃 뒤 체험을 시작하면 회원과 연결 안 된 새 익명 ID 발급 — 이 흐름은 `java.net.CookieManager` 저장소에 실제 발급 `Set-Cookie`를 넣고 로그아웃 응답을 적용해, 이름 · Domain · Path 규칙으로 기존 쿠키가 지워져 다음 요청에 실리지 않는지까지 본다(PR #340 리뷰).
- 로그아웃의 삭제 코드를 빼면 연결된 익명 ID 테스트 2건이 "지우는 쿠키 0개"로 실패하는 것을 확인했다.
- `LogoutAnonymousCheckFailureTest`: 연결 확인 중 DB 오류 · 트랜잭션 생성 실패 · 그 밖의 실행 중 예외여도 204, 리프레시 폐기, 익명 ID 쿠키 삭제.

## 추후 재검토가 필요하면

- **리프레시 토큰 만료로 "자동 로그아웃"된 경우**: 서버가 로그아웃 시점을 알 수 없어 익명 ID가 회원에 연결된 채 남는다. 이번 범위는 명시적 로그아웃이다.
  - 화면이 재발급 실패 때 M-2를 함께 부르는 방법은 **지금은 권하지 않는다**. 재발급 실패에는 탭 두 개가 동시에 재발급해 한쪽이 로테이션으로 실패하는 경우도 들어 있다. 이때 M-2를 부르면 아직 로그인된 다른 탭의 익명 ID까지 지워, 그 탭의 이후 기록이 다음 로그인 전까지 회원 계정에서 빠진다.
  - 메우려면 재발급 실패 사유를 나눠(만료 · 폐기 vs 로테이션 경합) 만료일 때만 정리하거나, 서버가 리프레시 만료 시점에 익명 ID를 정리하는 방식을 함께 검토한다.
- **회원 탈퇴**: 탈퇴 때 익명 ID 연결을 끊을지는 BE-62 "회원 탈퇴" 항목과 함께 정한다.
