# FE-55 의사결정 기록

> 근거: PR #190 · 담당 김해송

## 문제 / 배경
- 8막 "리뷰하기"가 임시 팝업(곧 열려요)이었다. 별점과 내 의견을 남기는 사건 리뷰 화면이 필요했다.
- 리뷰 API는 아직 명세에 없다.

## 검토한 대안
- 대안 A: 8막 안의 팝업을 키워 쓰기만 지원. 구현은 작지만 다른 독자 의견을 볼 곳이 없고, 커뮤니티 화면과 이어 붙이기 어렵다.
- 대안 B: 별도 주소의 화면(`/cases/:caseId/opinion`). 평균 별점 · 내 엽서 · 다른 독자 엽서를 한 화면에 둔다.

## 선택한 방법과 이유
- B. 사건 단위로 주소를 가지면 사건 상세 · 커뮤니티에서도 같은 화면으로 올 수 있다.
- 엽서 한 장 = 사건 하나당 한 번, 보낸 뒤 수정 불가. 2막 사전 판단 엽서와 규칙을 맞췄다.
- API가 없으므로 목 전용(`caseReviewMockApi.js`). 실제 모드에서는 준비 중 안내.

## 고려한 제약 사항
- 서버 명세 없음 → 응답 모양은 화면이 필요한 최소(`count`, `averageRating`, `mine`, `reviews`)로 가정했다. BE 협의 시 맞춘다.

## 추후 재검토가 필요하면
- 수정 · 삭제를 허용할지(지금은 불가), 신고 · 정렬 · 페이지네이션은 API 설계 때 함께 정한다.

## 추가: 8막 성향 테스트 면 · 다른 사건 보기 플립

### 문제 / 배경
- 8막 지면 아래 "판결 성향 테스트" 광고가 누를 수 없는 장식이었다. 누르면 신문 속 면으로 들어가는 연출과, 기존 `/test`와 다른 레이아웃이 필요했다.
- "다른 사건 보기"는 지면이 위로 접히며 사라졌다. 신문을 뒤집는 느낌으로 바꿔야 했다.

### 검토한 대안
- 주소: (A) `/cases/:caseId/test` — 사건 제목을 상단 바에 채울 수 있다. (B) `/test/paper` — 사건과 무관한 신문 속 면.
- 레이아웃: (A) 기존 서류철 컴포넌트를 재사용하고 색만 바꾼다. (B) 8막 지면 문법(제호 띠 · 이중 괘선 · 명조 기사체)으로 새로 짠다.

### 선택한 방법과 이유
- 주소 B. 8막으로 되돌아갈 필요가 없고 들어가는 연출일 뿐이라 사건 번호를 기억하지 않는다. 기존 `/test`는 그대로 둔다.
- 레이아웃 B. "8막 신문의 뒷면(오피니언 2면)"이라는 연출과 맞도록, 문항을 찬반 토론 지면(A | B 두 단)으로, 답을 독자 설문 응모권으로 싣는다. 문항 · 제출 api와 결과 화면(`/test/result`)은 기존 것을 쓴다.
- 플립은 두 단계 WAAPI(옆으로 세우기 → 마저 뒤집기)로, 중간에 앞면 기사를 감춰 빈 뒷면을 보인다. 읽기 모드 지면이 `transform`을 `!important`로 끄므로 개별 속성(`rotate` · `scale`)만 쓴다(합성 단계만 거친다).

### 추후 재검토가 필요하면
- 신문 면에서 낸 결과도 기존 결과지(서류철)로 간다. 결과도 신문 면으로 낼지는 사용자 반응을 보고 정한다.
- 같은 신문 한 장으로 이어지게: 성향 테스트 면(`/test/paper`)과 플립 뒤 사건 목록 지면은 8막 읽기 화면 지면과 같은 폭 · 같은 자리에 놓는다. 성향 테스트 면은 세로가 가로의 2배인 긴 지면이다.
- 플립 뒤 깜빡임: 주소가 바뀌면 지면이 새로 그려지므로, 뒤집힌 빈 뒷면을 `paperHandoff.js`(메인으로 갈 때 쓰는 넘겨주기)로 사건 목록에 넘긴다. 목록은 기사가 다 그려질 때까지 그 빈 종이를 덮어 두었다가 기사만 페이드인한다.
- 레이아웃 고정: 제목 · 한마디 · A · B를 부분마다 모든 문항 것을 한 칸에 겹쳐 쌓아(지금 문항만 보임) 가장 긴 문항 높이를 차지하게 했다. 그래서 모든 문항에서 각 부분 · 응모권 · 버튼 자리가 같다. 화면 폭마다 높이를 재는 스크립트 없이 CSS 격자만으로 폭 변화에 따라간다.

## 추가: 8막 리뷰 팝업 → 날아오는 엽서

- 흰 팝업 대신 대화상자 자체를 항공우편 엽서 한 장으로 만들고, 2막 사전 판단 엽서의 건네기 연출(`nambul-hand` · `postcard-in`)을 재사용했다.
- 출발점은 진입 경로에 따라 다르다. 대사창 "리뷰하기"는 남불 손에서, 읽기 화면에서 누른 독자 의견 엽서는 그 엽서 자리에서 날아온다(읽기 화면에는 남불이 없다). 닫으면 온 곳으로 돌아간다.
- 엽서 내용(API)을 받은 뒤(최대 0.5초) 날린다. 먼저 날리면 날아오는 중에 엽서 높이가 바뀌어 출발 위치 계산이 틀어진다.
- 별도 화면(`/cases/:caseId/opinion`)은 그대로 둔다.

## 추가: PR #190 리뷰 반영 — 성향 테스트 진행 규칙 공통화 · 리뷰 작성 조건

- 진행 규칙(답 모으기 · 칸/숫자 키로 넘기기 · 건너뛰기 없음 · 제출 최소 대기)을 `pages/personality/personalityFlow.js`로 모으고 `/test`와 `/test/paper`가 같이 쓴다. 화면 파일은 그리기만 한다. 대안으로 두 화면을 한 컴포넌트로 합치는 것도 봤지만, 서류철과 신문 지면은 배치 · 연출이 전혀 달라 그리기는 나누고 규칙만 합쳤다.
- 리뷰는 체험을 마친 사람만 보낸다. 목은 `EXPERIENCE_NOT_COMPLETED`(임시 이름)로 거절하고 화면은 안내 + "이 사건 체험하러 가기"를 보인다. 오류 코드 이름 · 판정 기준(사건별 완료 여부)은 리뷰 API 설계 때 BE와 확정한다. 목 체험 기록은 사건별이 아니라 하나라서, 지금은 그 기록이 `COMPLETED`인지만 본다(`comparisonMockApi`와 같다).
