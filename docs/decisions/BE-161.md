# BE-161 의사결정 기록

## 1차 (PR #412) — 파이프라인 서비스의 RAG 검색 경로

### 문제 / 배경
- 운영 사건 등록에서 RAG(살인 사건만)를 켜려 한다. 판례 · 양형기준 데이터는 운영 RDS에 이미 적재돼 있다(비공개 시드 R__40 · R__41).
- 파이프라인의 RAG 검색(`rag_context.py`)은 `pipeline.py` `query_db()`가 **psql**로 DB 함수를 부르는 구조다.
  - 부르는 함수: `rag_precedent_search` · `rag_guideline_search` · `sentencing_guideline_at`
- 그런데 `query_db()`는 적재(`apply_sql`)와 같은 `psql_command()`를 써서 **로컬 DB만** 허용한다(#143 리뷰).
- 서비스 컨테이너에서는 DB(RDS)가 로컬이 아니라 검색할 수 없었다. 그래서 `jobs.py`가 `rag`를 기본으로 꺼 두었다.
- 이미지에는 psql도 없었다.

### 검토한 대안
- 대안 A: `psql_command()`의 로컬 검사에 RDS 호스트를 허용 목록으로 추가
  - 장점: 변경이 가장 작다.
  - 단점: 적재(운영 DB에 쓰기)도 같은 함수를 쓴다. 검사를 넓히면 적재의 방어선이 함께 약해진다.
- 대안 B: psycopg로 검색 코드를 새로 작성
  - 단점: `rag_context.py`의 검색 SQL과 DB 함수 호출을 두 벌로 두게 된다. 드라이버 의존성도 늘어난다.
  - 파이프라인 도구는 표준 라이브러리만 쓴다는 원칙(README)과도 어긋난다.
- 대안 C: 백엔드(Java)가 검색해서 결과를 파이프라인에 넘김
  - 단점: 생성 프롬프트 자료(형량범위 · 양형인자 · 유사 판례)를 만드는 로직이 `rag_context.py`에 있다. 옮기면 오프라인 생성(로컬 Python)과 서비스 생성의 로직이 갈라진다.
- 대안 D: **RAG 검색에만** 쓰는 원격 읽기 경로를 따로 둔다(`query_rag_db`). 적재 · 로컬 검색 경로는 그대로 둔다.

### 선택한 방법과 이유
- 대안 D를 택했다.
  - `rag_context.py`의 SQL과 DB 함수를 그대로 쓴다. 오프라인 생성 · `rag_check.py`와 같은 로직이다.
  - 원격을 여는 범위가 RAG 검색 하나로 좁다. `apply_sql`과 `query_db`의 로컬 전용 검사는 그대로다(테스트로 고정).
- 접속 값은 `RAG_DB_*` 환경변수로만 받는다.
  - 설정 파일(`stages.load.db`)이나 요청 `stages`로는 원격을 열 수 없다.
  - 백엔드 요청이 설정을 덮어쓰는 구조라서, 접속 대상까지 요청으로 바뀌면 안 된다.
- 읽기 전용은 두 겹으로 지킨다.
  - ① DB 계정: `rag_reader`. 권한은 `rag_guideline` · `rag_precedent` · `sentencing_guideline`의 SELECT만 있고, `default_transaction_read_only`가 걸려 있다.
  - ② 코드: `PGOPTIONS`로 `default_transaction_read_only=on`과 `statement_timeout`을 고정한다.
  - 계정을 잘못 넣어도(예: 앱 계정) 쓰기는 막힌다.
- `sentencing_guideline`도 SELECT 권한이 필요하다.
  - DB 함수가 `SECURITY DEFINER`가 아니라서 호출한 계정의 권한으로 돈다.
  - 검색 SQL이 양형기준 버전을 이 표에서 고른다.
- 물려받은 `PG*` 환경변수는 지우고 넣는다. `PGSERVICE` · `PGHOSTADDR` 같은 값으로 다른 호스트에 붙는 길을 막기 위해서다(#143 리뷰와 같은 이유).
- 접속 값은 명령줄이 아니라 환경변수로 넘긴다. 프로세스 목록에 남지 않게 하기 위해서다.
- SSL은 `require`로 고정한다. RDS는 SSL 접속만 받는다.
- 오류 문구에서 서버 주소(호스트 · IP)를 지운다. 사유가 작업 보고(references.json)를 통해 백엔드까지 가기 때문이다.
- 설정이 없거나, 일부만 있거나, psql이 없거나, 접속에 실패하면 모두 `RagUnavailable`로 처리한다.
  - 이 경우 기존 정책(요구사항 v5.5 "RAG 우선, 안 되면 퓨샷")대로 사건 입력의 참고 자료로 진행한다.
  - `stages.rag.required=true`면 멈춘다.

### 고려한 제약 사항
- pipeline 네트워크는 `internal`이 아니다(외부 LLM API 호출 때문). 그래서 RDS에 닿는다. 운영에서 `pg_isready`로 확인했다.
- 이미지의 psql은 베이스 이미지(데비안) 저장소 버전이다(11/02 빌드 기준 17). SELECT 질의만 하므로 서버 버전과 조금 어긋나도 된다.
- 3072차원 벡터에는 pgvector 인덱스를 걸 수 없다(2000차원 상한). 판례 53건 · 조각 237건이라 순차 스캔으로 충분하다. 타임아웃은 10초로 둔다.
- 운영 계정 생성 · 권한은 저장소 밖 작업이다. 절차는 `deploy/.env.example`에 적었고, 실행 기록은 Jira BE-161에 둔다.

### 추후 재검토가 필요하면 (선택)
- 판례가 크게 늘면 순차 스캔 시간과 `statement_timeout`(10초)을 다시 잰다.
- **SSL 서버 인증서 검증** (PR #412 리뷰): 지금은 `PGSSLMODE=require`라 암호화만 하고 서버 인증서는 검증하지 않는다.
  운영 VPC 안의 접속이라 당장 위험은 작지만, RDS CA 번들을 이미지에 넣고 `verify-full`로 올리는 일을 후속 이슈(**BE-162**)로 둔다.
  이번에 같이 하지 않은 이유: CA 번들을 빌드 때 받을지 저장소에 둘지, 갱신(RDS CA 교체 주기)을 누가 챙길지 정해야 해서
  읽기 전용 경로를 여는 이 PR과 따로 보는 편이 낫다.

### 2차 계획 (PR #412 리뷰 반영)
- 백엔드가 `PIPELINE_RAG_ENABLED` + **등록 요청의 `crimeType == MURDER`**일 때만 `stages.rag`를 켠다.
  추출 결과가 아니라 등록 요청의 범죄 유형으로 판단한다 — 대본 배역(BE-129)과 같은 기준이라 한 사건에서 기준이 갈리지 않는다.
- **RAG 결과를 생성 기록에 남긴다.** 적재 뒤 파이프라인 작업이 지워지므로, `rag` 보고의 상태 · 대체 사유 · 양형기준 버전 ·
  판례 건수(본문 · 사건번호 없이)를 `ai_generation.generation_report.rag`에 담는다(BE-160의 `contamination`과 같은 방식,
  오프라인 적재 `build_generation_report`의 `rag`와 같은 모양).
  - `RAG_DB_*`를 일부만 넣은 설정 실수도 이 대체 사유(`DB 검색 실패: RAG 읽기 전용 DB 설정이 일부만 있습니다 (빠진 값: …)`)로 남아, 관리자가 생성 정보에서 알아챌 수 있다.
- "왜 살인에만 켜는가"의 경위는 2차 절에 적는다(리뷰에서 받은 초안을 바탕으로).

## 2차 (PR #xxx) — 백엔드가 살인 등록에만 RAG를 요청 · 결과를 생성 기록에 저장

### 문제 / 배경
- 1차(#412)로 파이프라인 서비스가 운영 RDS를 읽기 전용으로 검색할 수 있게 됐지만, 서비스는 `rag`를 기본으로 끄고 백엔드는 켜 달라고 보내지 않았다.
- 1차 리뷰(#412)에서 두 가지를 더 받았다.
  - 적재 뒤 파이프라인 작업이 지워지므로, RAG가 실제로 쓰였는지와 대체 사유를 생성 기록에 남겨야 한다.
  - `RAG_DB_*`를 일부만 넣은 설정 실수가 관리자에게 보여야 한다.

### 왜 살인에만 켜는가
(초안: PR #412 리뷰 — 근거 문서와 대조해 옮겼다)

**검토한 대안**
- 모든 범죄 유형에 켠다
  - 코드는 유형을 가리지 않지만, RAG가 읽는 자료가 살인뿐이다.
  - 다른 유형에 켜면 검색할 자료가 없어 "못 찾음 → references로 대체"만 매번 일어난다.
  - 그동안 검색어 임베딩 호출과 DB 질의만 늘고, 대체 사유(`fallbackReasons`)가 매 등록마다 쌓여 진짜 문제와 구분하기 어려워진다.
- 켜지 않는다(현 상태 유지)
  - 자료가 있는 살인 사건에서도 양형기준과 유사 판례를 쓰지 못한다.
  - RAG를 끈 생성과 켠 생성은 이미 비교했다([RAG 인수인계](../rag-handover.md) 5-7, BE-76).
- **살인에만 켠다(택함)**
  - 자료가 있는 유형에만 켜고, 다른 유형은 지금처럼 references로 진행한다.
  - 자료가 늘어나면 유형을 하나씩 더한다.

**선택한 이유**
- 양형기준 데이터가 살인뿐이다.
  - 살인범죄 6개 버전(2009 최초 ~ 2026 수정), 237개 조각만 데이터화돼 있다([양형기준 저장소](../sentencing-guideline-rag.md), WBS v1.5 결정 4).
  - 다른 범죄는 같은 도구로 범죄명만 바꿔 돌리면 되지만 아직 하지 않았다.
  - 사건의 양형기준 버전도 살인만 자동으로 연결된다([ERD](../erd.md) v1.40: 강도 · 절도는 없음).
- 유사 판례 자료도 살인 중심이다.
  - 검색 대상은 47건이다(살인 27 · 살인미수 16 · 강도살인 3 · 촉탁 · 승낙 1, [RAG 인수인계](../rag-handover.md) 1장).
  - 운영 `rag_precedent` 53건이 모두 `crime_type = MURDER`이고, 보류 6건을 빼면 47건이다(운영 확인).
- 자료가 적은 곳에 켜도 해가 없게 한다.
  - 못 찾으면 멈추지 않고 사건 입력의 references로 진행한다(`rag.required`를 보내지 않아 기본값 false).
  - 살인 사건이라도 발생일이 양형기준 시행 전이거나 비슷한 판례가 기준 점수 미만이면 대체되고, 이유가 생성 기록에 남는다.
- 켜고 끄는 단위를 범죄 유형으로 둔다. 유형을 더할 때는 이 조건과 자료 적재만 바뀐다.

**한계**
- 판례 자료가 많지 않다. 살인 기수가 27건이라 목표인 100건 안팎에 못 미친다.
- 그래서 RAG가 도움이 안 되는 살인 사건도 있다. 판례 확충([RAG 인수인계](../rag-handover.md) 5-3)으로 풀 문제이고, "살인에만"이라는 결정과는 별개다.

### 선택한 방법과 이유
- 켜는 조건은 `PIPELINE_RAG_ENABLED`(기본 꺼짐)와 **등록 요청의 `crimeType == MURDER`**다.
  - 추출 결과가 아니라 등록 요청으로 판단한다. 대본 배역(BE-129, `CaseCastAssigner`)과 같은 기준이라 한 사건 안에서 기준이 갈리지 않는다.
  - 추출 결과가 등록 요청과 다르면 파이프라인이 멈추므로(BE-138), 두 값이 어긋난 채로 생성까지 가지는 않는다.
- `{"enabled": true}`만 보낸다. 점수 기준 · 개수 · required는 파이프라인 기본값(`rag_context.DEFAULT_OPTIONS`)을 쓴다. BE-160 점검과 같은 방식이다.
- RAG 결과를 생성 기록에 남긴다.
  - 서비스 결과 API에 `rag`를 넣고, 백엔드가 `ai_generation.generation_report.rag`에 저장한다.
  - 키는 오프라인 적재의 `pipeline.rag_report`와 같다: 상태 · 대체 사유 · 임베딩 모델 · 양형기준 버전 · 기준 종류 · 조각과 판례의 id · 점수 · 경고. 판례 본문 · 사건번호 · 참고 자료 파일 경로는 넣지 않는다.
  - 두 경로의 키가 어긋나지 않게 테스트로 고정했다(`test_service_rag_result_keys_match_offline_generation_report`).
  - 안 돌렸으면 `{"status": "SKIPPED"}`다.
- `RAG_DB_*` 설정 실수도 대체 사유(`DB 검색 실패: RAG 읽기 전용 DB 설정이 일부만 있습니다 (빠진 값: …)`)로 생성 기록에 남는다. 값은 넣지 않는다.

### 고려한 제약 사항
- 백엔드는 날짜를 따로 보내지 않는다.
  - 양형기준 버전은 공소제기일이 없으면 extract가 판결문에서 뽑은 발생일로 고른다(`pipeline.rag_inputs`).
  - 자기 사건을 빼는 데 쓰는 사건번호 해시도 extract 결과에서 가져온다.
- 비용: RAG를 켜면 생성 입력 토큰이 약 2.6배가 된다(BE-76 끔 · 켬 비교). 살인 등록에만 켜는 이유이기도 하다.
- 운영 켜는 순서: 1차 경로를 EC2에서 확인한 뒤 `PIPELINE_RAG_ENABLED=true` → `./deploy.sh --reapply`.
  - 사전 학습 점검(BE-160)과 같은 첫 등록에서 처음 켜지 않는다. 메모리 · 소요 시간이 늘었을 때 원인을 나눠 보기 위해서다.

### 추후 재검토가 필요하면 (선택)
- 다른 범죄 유형의 양형기준과 판례를 적재하면 그 유형을 켠다. 조건은 "그 유형의 자료가 운영 DB에 있다"이다.
- 살인 사건에서도 RAG 결과가 대부분 "못 찾음"으로 대체되면 판례 확충(5-3)을 먼저 한다.
- A-8(판결 후보 상세)은 `generationReport`를 통째로 내려주므로 `rag` · `contamination`도 API 변경 없이 실린다(API 명세 v0.92에 모양 명시).
  관리자 화면에 요약을 보기 좋게 보여 줄지는 별도 이슈(FE)로 본다.
