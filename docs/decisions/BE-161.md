# BE-161 의사결정 기록

## 1차 (PR #412) — 파이프라인 서비스의 RAG 검색 경로

### 문제 / 배경
- 운영 사건 등록에서 RAG(살인 사건만)를 켜려 한다. 판례 · 양형기준 데이터는 운영 RDS에 이미 적재돼 있다(비공개 시드 R__40 · R__41).
- 파이프라인의 RAG 검색(`rag_context.py`)은 `pipeline.py` `query_db()`가 **psql**로 DB 함수를 부르는 구조다.
  - 부르는 함수: `rag_precedent_search` · `rag_guideline_search` · `sentencing_guideline_at`
- 그런데 `query_db()`는 적재(`apply_sql`)와 같은 `psql_command()`를 써서 **로컬 DB만** 허용한다(#143 리뷰).
- 서비스 컨테이너에서는 DB(RDS)가 로컬이 아니라 검색할 수 없었다. 그래서 `jobs.py`가 `rag`를 기본으로 꺼 두었다.
- 이미지에는 psql도 없었다.

### 검토한 대안
- 대안 A: `psql_command()`의 로컬 검사에 RDS 호스트를 허용 목록으로 추가
  - 장점: 변경이 가장 작다.
  - 단점: 적재(운영 DB에 쓰기)도 같은 함수를 쓴다. 검사를 넓히면 적재의 방어선이 함께 약해진다.
- 대안 B: psycopg로 검색 코드를 새로 작성
  - 단점: `rag_context.py`의 검색 SQL과 DB 함수 호출을 두 벌로 두게 된다. 드라이버 의존성도 늘어난다.
  - 파이프라인 도구는 표준 라이브러리만 쓴다는 원칙(README)과도 어긋난다.
- 대안 C: 백엔드(Java)가 검색해서 결과를 파이프라인에 넘김
  - 단점: 생성 프롬프트 자료(형량범위 · 양형인자 · 유사 판례)를 만드는 로직이 `rag_context.py`에 있다. 옮기면 오프라인 생성(로컬 Python)과 서비스 생성의 로직이 갈라진다.
- 대안 D: **RAG 검색에만** 쓰는 원격 읽기 경로를 따로 둔다(`query_rag_db`). 적재 · 로컬 검색 경로는 그대로 둔다.

### 선택한 방법과 이유
- 대안 D를 택했다.
  - `rag_context.py`의 SQL과 DB 함수를 그대로 쓴다. 오프라인 생성 · `rag_check.py`와 같은 로직이다.
  - 원격을 여는 범위가 RAG 검색 하나로 좁다. `apply_sql`과 `query_db`의 로컬 전용 검사는 그대로다(테스트로 고정).
- 접속 값은 `RAG_DB_*` 환경변수로만 받는다.
  - 설정 파일(`stages.load.db`)이나 요청 `stages`로는 원격을 열 수 없다.
  - 백엔드 요청이 설정을 덮어쓰는 구조라서, 접속 대상까지 요청으로 바뀌면 안 된다.
- 읽기 전용은 두 겹으로 지킨다.
  - ① DB 계정: `rag_reader`. 권한은 `rag_guideline` · `rag_precedent` · `sentencing_guideline`의 SELECT만 있고, `default_transaction_read_only`가 걸려 있다.
  - ② 코드: `PGOPTIONS`로 `default_transaction_read_only=on`과 `statement_timeout`을 고정한다.
  - 계정을 잘못 넣어도(예: 앱 계정) 쓰기는 막힌다.
- `sentencing_guideline`도 SELECT 권한이 필요하다.
  - DB 함수가 `SECURITY DEFINER`가 아니라서 호출한 계정의 권한으로 돈다.
  - 검색 SQL이 양형기준 버전을 이 표에서 고른다.
- 물려받은 `PG*` 환경변수는 지우고 넣는다. `PGSERVICE` · `PGHOSTADDR` 같은 값으로 다른 호스트에 붙는 길을 막기 위해서다(#143 리뷰와 같은 이유).
- 접속 값은 명령줄이 아니라 환경변수로 넘긴다. 프로세스 목록에 남지 않게 하기 위해서다.
- SSL은 `require`로 고정한다. RDS는 SSL 접속만 받는다.
- 오류 문구에서 서버 주소(호스트 · IP)를 지운다. 사유가 작업 보고(references.json)를 통해 백엔드까지 가기 때문이다.
- 설정이 없거나, 일부만 있거나, psql이 없거나, 접속에 실패하면 모두 `RagUnavailable`로 처리한다.
  - 이 경우 기존 정책(요구사항 v5.5 "RAG 우선, 안 되면 퓨샷")대로 사건 입력의 참고 자료로 진행한다.
  - `stages.rag.required=true`면 멈춘다.

### 고려한 제약 사항
- pipeline 네트워크는 `internal`이 아니다(외부 LLM API 호출 때문). 그래서 RDS에 닿는다. 운영에서 `pg_isready`로 확인했다.
- 이미지의 psql은 베이스 이미지(데비안) 저장소 버전이다(11/02 빌드 기준 17). SELECT 질의만 하므로 서버 버전과 조금 어긋나도 된다.
- 3072차원 벡터에는 pgvector 인덱스를 걸 수 없다(2000차원 상한). 판례 53건 · 조각 237건이라 순차 스캔으로 충분하다. 타임아웃은 10초로 둔다.
- 운영 계정 생성 · 권한은 저장소 밖 작업이다. 절차는 `deploy/.env.example`에 적었고, 실행 기록은 Jira BE-161에 둔다.

### 추후 재검토가 필요하면 (선택)
- 판례가 크게 늘면 순차 스캔 시간과 `statement_timeout`(10초)을 다시 잰다.
- 2차: 백엔드가 살인 사건일 때만 `stages.rag`를 켜는 스위치(BE-160 머지 뒤, `PipelineProperties`가 겹친다).
