# FE-53 의사결정 기록

## 문제 / 배경
- 관리자 계정으로 로그인하면 마이페이지 진입점(헤더 닉네임 · 메인 책상 커피잔)이 관리자 페이지로 바뀌어야 한다.
- 관리자 인증은 이미 사용자 로그인과 따로 있다: 관리자 API(A-1 ~ A-4)의 세션 쿠키 + CSRF, 이메일 · 비밀번호. 사용자 로그인 API는 아직 없다(FE-52 목업뿐).
- 선행: FE-52(#178 로그인 화면), FE-45(#180 관리자 페이지). 둘 다 머지되기 전이라 #178 브랜치에서 분기해 시작했고, #180이 갱신된 뒤(`homeRoute()` 추가) #180을 병합해 맞췄다. 두 PR이 머지되면 이 브랜치의 변경만 남도록 `develop` 기준으로 정리한다.

## 검토한 대안
- 관리자 판별:
  - 로그인 응답의 role을 쓴다: 사용자 로그인 API가 없어 지금은 불가능하다.
  - 아이디 문자열로 프론트가 판단한다: 아무나 흉내 낼 수 있어 권한 판단으로는 쓸 수 없다.
  - **로그인 화면이 관리자 로그인(A-1 · A-2)을 먼저 시도한다**: 성공 여부는 서버가 판단한다.
- 진입점 교체 범위: 헤더만 / 헤더 + 책상 커피잔 + `/me` 주소 → 후자(어느 입구로 들어와도 관리자 페이지).

## 선택한 방법과 이유
- 아이디 · 비밀번호 로그인은 관리자 로그인을 먼저 시도하고, 관리자 계정이 아니면(`INVALID_CREDENTIALS` · `VALIDATION_ERROR`) 일반 로그인으로 넘어간다. 성공하면 `utils/session.js`에 `role: 'admin'`을 표시값으로 둔다.
- `role`은 헤더 · 책상이 입구를 고르는 표시값일 뿐이다. 관리자 화면은 이전과 같이 서버 세션(A-4)으로 다시 확인하고, 표시값을 조작해도 관리자 API는 열리지 않는다.
- 관리자 입구가 가는 곳은 #180의 `homeRoute()`를 따른다(목 모드 대시보드 · 실제 모드 서버가 있는 사건 검수). 서버 API가 없는 화면으로 실제 모드 관리자를 보내지 않기 위해서다. 관리자가 `/me`로 오면 같은 곳으로 바꿔 보낸다. 관리자 로그아웃(관리자 화면 · 로그인 화면)은 표시값도 지운다.

## 고려한 제약 사항
- 목 관리자 로그인은 아무 값이나 받아서 그대로 쓰면 모든 목 사용자가 관리자가 된다. 목 모드에서는 아이디가 `admin`으로 시작할 때만 관리자 로그인을 시도한다(목 전용 규칙, 실제 모드는 서버가 판단).
- #178 리뷰 반영(FE-52)으로 실제 모드 로그인 화면은 입력칸 없이 "준비 중"만 보여 줬는데, 그러면 실제 모드에서 관리자가 로그인할 길이 없다. 사용자 로그인이 없는 실제 모드에서는 카카오 · 회원가입 없이 **관리자 로그인 입력칸만** 보여 주고 "일반 로그인은 준비 중"을 안내한다. 관리자가 아닌 계정은 "아이디와 비밀번호를 확인해 주세요. 로그인은 아직 준비 중…"이 나온다.

## 추후 재검토가 필요하면
- 사용자 로그인 API가 생기면 응답의 role로 바꾸고, 관리자 로그인을 먼저 시도하는 흐름을 정리한다(관리자 이메일 · 사용자 아이디 체계 통합 여부).
- 관리자 화면 안에서 세션이 끝나(401) 로그인 폼으로 돌아가도 사용자 사이트의 관리자 표시값은 남는다. 다음에 입구를 누르면 관리자 화면이 다시 로그인을 받는다.

## 2차 (PR #183 리뷰 반영)
- 관리자 로그인 오류 격리: 사용자 로그인(`api.login`)이 있는 모드에서는 관리자 로그인 시도가 CSRF 발급 실패 · 5xx · 네트워크 오류로 던져도 삼키고 일반 로그인으로 넘어간다. 관리자 API가 불안정하다고 일반 사용자가 로그인하지 못하면 안 되기 때문이다. 관리자 입력칸만 있는 실제 모드(`adminOnly`)에서는 오류를 그대로 알린다.
- 테스트: 관리자 로그인 시도 규칙(목 모드 `admin` 접두어, 오류 코드 → `null`)을 `adminLoginRule.js`로 분리했다. `adminLogin.js`는 `import.meta.env`를 읽어 node 테스트에서 불러올 수 없어서, 환경값과 api 불러오기를 인자로 받는 순수 함수로 나눴다. 로그인 폼(`loginPage.js`)은 DOM이 필요해 테스트하지 않았다.
- 관리자 로그인을 먼저 시도하는 구조는 그대로 둔다(리뷰 2번). 일반 사용자의 아이디 · 비밀번호가 관리자 로그인 엔드포인트로 먼저 가는 것은 사용자 로그인 API가 없는 동안의 임시 구조다. 사용자 로그인 API가 생기면 응답의 role로 관리자 여부를 정하게 바꾸고, 그때 이 선행 시도는 없앤다. 별도 진입(아이디 규칙 · 별도 입력칸)은 로그인 화면 구조가 바뀌는 데다 임시 구조를 위해 들이기엔 커서 택하지 않았다. 그 전에 서버(A-1)의 실패 횟수 제한 · 요청 로그 정책은 백엔드에 확인한다.
- 관리자 로그인 폼(`adminShell.js`)의 이메일 · 비밀번호 칸은 FE-54의 공통 라벨 헬퍼(`labeledField`)로 바꿨다(FE-54 #182 리뷰에서 이 브랜치와 겹친다는 이유로 미룬 부분).
- 헤더 `aria-current`: 관리자 홈은 모드에 따라 `/admin`(실제) 또는 `/admin/dashboard`(목)이라 `/admin`으로 시작하는 경로면 붙인다.
