# BE-92 의사결정 기록

## 문제 / 배경

COMMON-41에서 "서비스 안 생성 파이프라인"에 신문 지면 · 사건 스크립트 · 사건 사진 세 콘텐츠를 추가하기로
했고, 사진은 BE-91에서 먼저 구현했다(관리자 업로드 + Gemini 한글 프롬프트 추천). BE-92는 그 다음으로
**신문 지면**(메인 화면에서 신문을 눌렀을 때 보이는 헤드라인 · 부제 · 사진 · 본문)을 구현한다.

사건 스크립트(내로 · 남불 대사, PR #138 `acts.steps` 포맷)는 `card`/`ev`(실제 카드 · 증거 인덱스 참조) ·
`choices`/`confirm`/`next`(게임 진행 로직)까지 들어 있는 복잡한 구조라, 신문 지면보다 훨씬 검증이
까다롭다고 판단해 **별도 이슈로 미뤘다**(이번 범위 아님).

## 검토한 대안

### 1. 저장 방식 — DB 테이블 vs 정적 파일

- **대안 A — 지금처럼 프론트 정적 파일(`frontend/src/content/case-N/script.json`)로 생성 결과를 출력한다.** DB · API를 새로 만들지 않아도 되지만, 생성할 때마다 사람이 파일을 커밋해야 해서 COMMON-41이 추구하는 "서비스 안(실시간) 생성 파이프라인"과 맞지 않는다.
- **대안 B(선택) — `case_paper` DB 테이블 + 관리자 API.** BE-91(사진)과 같은 패턴. 팀이 이 방향으로 정했다(사용자 확인).

### 2. `photo`/`extraPhotos`를 어디서 가져올까 (BE-78 문의와 직결)

- **대안 A — `case_paper`에 사진 URL을 따로 저장한다.** 구조는 단순하지만, BE-91의 `legal_case.thumbnail_url`(대표사진) · `case_incident_photo`(발단사진)와 같은 사진을 두 군데에 중복 저장하게 된다. BE-78 담당자가 바로 이 중복을 우려해 질문했다.
- **대안 B(선택) — 저장하지 않고 응답 조립 시점에 그대로 가져다 쓴다.** `photo`는 `legal_case.thumbnail_url`, `extraPhotos`는 `case_incident_photo`를 `display_order`대로 매핑해 내려준다. 같은 사진이 신문 지면과 "사건 발단 사진" 화면 양쪽에 나타나도 실제 저장은 한 곳뿐이다.

### 3. Gemini 응답을 어떻게 구조화된 필드로 받을까

- **대안 A — 필드마다 따로 호출한다(headline 한 번, deck 한 번, article 한 번 …).** 필드별 프롬프트를 더 간단히 짤 수 있지만, BE-91에서 Gemini 호출 1회가 40 ~ 90초까지 걸리는 걸 실제로 겪었다 — 4번 부르면 최악의 경우 수 분이 걸려 관리자 화면에서 쓸 수 없는 지연이 된다.
- **대안 B(선택) — 한 번의 호출로 JSON 하나를 받아 파싱한다.** 지시문에 `{"headline":…, "deck":…, "caption":…, "article":[…]}` 형식으로만 답하라고 명시하고, 응답을 그대로 역직렬화한다. 모델이 지시를 어기고 \`\`\`json 코드블록으로 감싸 보내는 경우를 대비해 코드펜스를 벗기는 전처리를 먼저 한다.

### 4. 기존 `CasePhotoPromptClient`를 그대로 쓸까, 새로 만들까

- **대안 A — `CaseContentGenerationClient` 같은 이름으로 새로 만들거나 기존 걸 리네이밍한다.** 이름이 실제 쓰임(범용 텍스트 생성)과 맞아떨어지지만, BE-91의 클래스 · 설정(`case-photo-prompt.*`) · 테스트 · 문서를 전부 고쳐야 해서 이번 이슈(신문 지면 구현) 범위를 넘어서는 리팩터링이 된다.
- **대안 B(선택) — 이름은 그대로 두고 재사용한다.** `CasePhotoPromptClient.generateText(instruction)`은 이미 "지시문 받아 텍스트 돌려주는" 범용 인터페이스라, 사진 프롬프트든 신문 기사든 그대로 쓸 수 있다. 다만 기사 본문은 더 긴 출력이 필요해 `generateText(instruction, maxOutputTokens)` 오버로드를 추가했다(사진 프롬프트 쪽 기본 400은 그대로 유지).

## 선택한 방법과 이유

- `case_paper` 테이블(사건당 1건): `desk`(지면 섹션명, 지금은 "사회면" 고정값) · `headline` · `deck` · `caption` · `article`(jsonb 배열). `(case_id)` 유니크 — 재생성은 새로 만들지 않고 덮어쓴다.
- `photo`/`extraPhotos`는 저장하지 않고 응답 조립 시점에 `legal_case.thumbnail_url` · `case_incident_photo`에서 가져온다.
- `CasePaperService`가 사건 내용(`overview` · `factor` · `chargeName`)으로 지시문을 만들고, `CasePhotoPromptClient.generateText(instruction, 1200)`로 JSON 하나를 받아 파싱한다.
- API: `POST /admin/cases/{caseId}/paper/generate`(생성 · 재생성) · `GET /admin/cases/{caseId}/paper`(조회) · `PATCH /admin/cases/{caseId}/paper`(수정, A-11과 같은 "보낸 필드만 · null = 지움" 방식). 번호는 BE-91의 A-13-1 ~ 5 다음으로 A-13-6 ~ 8을 썼다.
- 감사 로그: `CASE_PAPER_GENERATE` · `CASE_PAPER_UPDATE` 신설(관리자 감사 로그 CHECK에 추가, V21).

## 고려한 제약 사항

- `CasePhotoPromptClient`/`GeminiCasePhotoPromptClient`라는 이름이 이제 "사진 전용"이 아닌데도 그대로 남아 있다. 혼동의 여지가 있어 `generateText`의 Javadoc에 범용 클라이언트임을 명시했지만, 이름 자체를 바꾸는 리팩터링은 하지 않았다(3-4절 참고).
- `desk`(지면 섹션명)는 지금 항상 "사회면"으로 고정한다. 범죄 유형별로 다른 섹션을 쓰게 하려면 매핑 규칙을 별도로 정해야 한다 — 이번 범위에 넣지 않았다.
- `extraPhotos`는 그 사건의 `case_incident_photo` 전부를 `display_order`대로 내려준다. "이 사진은 신문 지면용, 저 사진은 증거판용"처럼 용도를 구분해 **선택적으로** 내려주는 기능은 없다 — BE-78이 물어본 "용도 구분 필드" 질문과 같은 맥락이며, 필요해지면 `case_incident_photo`에 `purpose`/`usage_type` 컬럼을 추가해야 한다.
- 공개용(사용자 화면) API는 만들지 않았다. 지금은 관리자 조회 · 수정 API만 있고, 프론트가 정적 파일(`script.json`) 대신 이 API를 실제로 쓰게 하려면 프론트 쪽 작업(별도 이슈, FE 협의 필요)이 더 필요하다.
- 사건 스크립트(내로 · 남불 대사)는 이번 이슈에서 다루지 않았다(문제/배경 참고).

## 추후 재검토가 필요하면

- 신문 지면을 실제 사용자 화면에 연결하려면: ① 공개 API 신설 ② 프론트가 정적 파일 대신 API를 쓰도록 변경(FE 협의) 이 두 가지가 필요하다.
- `case_incident_photo`에 용도 구분이 필요해지면(신문 지면 vs 증거판 등) 스키마 변경을 검토한다(BE-78 문의 참고).
- `CasePhotoPromptClient` 계열 이름을 범용 이름으로 리네이밍하는 건 별도 정리 이슈로 미룬다.
- `desk`를 범죄 유형별로 다르게 분류할지는 실제 사건 유형이 늘어나면 다시 본다.

## 2차 (PR #212 리뷰 반영, peanutboi710 · coderabbitai)

- **Gemini 호출을 사건 행 잠금 밖으로 분리**: `AdminCasePaperService.generatePaper()`가 `lockCase()`로
  잠근 채 40 ~ 90초짜리 Gemini 호출을 기다리면, 그동안 같은 사건에 대한 다른 쓰기 요청(A-11 수정 · 사진
  업로드 · 공개 처리)이 전부 막힌다는 지적(coderabbitai, Major)을 받아들였다. `CasePaperService`를
  `generateContent(LegalCase)`(트랜잭션 없음, Gemini 호출만) · `savePaper(LegalCase, GeneratedPaper)`
  (`@Transactional`, upsert만)로 나누고, `AdminCasePaperService`는 `TransactionTemplate`
  (`AdminAuditLogger`와 같은 패턴)으로 저장 단계만 짧게 잠근다. 생성하는 동안 사건이 공개될 수 있어 저장
  직전에 공개 여부를 다시 확인한다.
- **Gemini 응답 검증 강화**: `headline`(200자) · `deck`(300자) · `caption`(200자) 길이와 `article`의
  null/빈 문단을 PATCH(`CasePaperEditRequest`)와 같은 기준으로 검증해, DB 컬럼 길이 초과로 500이 새는
  경로를 막았다. `ObjectMapper`는 `FAIL_ON_UNKNOWN_PROPERTIES`를 꺼서 모델이 필드를 하나 더 보내도 생성이
  실패하지 않게 했다. 생성 응답도 PATCH처럼 앞뒤 공백을 지우고 `deck`/`caption`이 빈 값이면 `null`로
  맞춰, 두 경로(생성 · 수정)가 같은 모양으로 저장되게 했다.
- **재생성이 수동 수정을 덮어쓰는 동작은 의도된 것이다**(peanutboi710 확인 질문). `case_paper`는
  `(case_id)` 유니크라 재생성은 항상 "덮어쓰기"고, 되돌릴 별도 이력(버전)을 두지 않는다. 관리자가 PATCH로
  다듬은 뒤 실수로 다시 생성을 누르면 그 수정은 복구할 수 없다 — 프론트에서 재생성 버튼에 확인창을 붙이는
  것으로 막을 계획이며(FE 협의 필요), 백엔드에 "수정됨" 플래그나 이력 테이블을 추가하는 것은 이번 범위에
  넣지 않았다. 필요해지면 별도 이슈로 다룬다.
- **마이그레이션 번호가 V19 → V21로 뛰는 것은 의도된 상태다**(peanutboi710 확인 질문). BE-91(PR #202)이
  1차로 `V19`(생성) · `V20`(수동 업로드 전환)으로 나눠 올렸다가, 리뷰 중 둘 다 이번 PR에서 처음 들어오는
  신규 마이그레이션이라는 점을 이용해 최종 형태의 `V19` 하나로 합치고 `V20`은 지웠다(`docs/decisions/
  BE-91.md` 12절). 그 사이 BE-92가 이미 `V21`로 분기해 있었던 것이 합쳐지면서 번호 하나가 빈 채로
  남았다. `V20`을 쓰는 다른 브랜치 · PR은 없고, 앞으로도 그 번호를 쓸 계획이 없어 Flyway
  `outOfOrder` 설정 없이 그대로 둔다 — 빈 번호가 늘 하나뿐이라 나중에 실수로 `V20`을 다시 쓰면 바로
  충돌이 나서 눈에 띈다.
