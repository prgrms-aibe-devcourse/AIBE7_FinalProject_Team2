# FE-45 의사결정 기록

## 문제 / 배경
- 관리자 검수 화면(FE-16)을 실제 관리자 API(BE-41 ~ BE-43)에 연결하고, S-19 명세에 있지만 빠져 있던 표시(요약어 후보 · 참고 자료 · 회차 선택 근거 · 사전 학습 점검 판정)를 채운다.
- FE-16에서 뺐던 사건 등록을 다시 넣는다. 파이프라인을 자바로 옮겨 서버에서 실행할 예정이라, 화면이 먼저 필요로 하는 계약을 정해야 했다.

## 검토한 대안
- 생성 정보 표시
  - 대안 A: 기존처럼 JSON 원본을 접어서 보여 준다. 구현은 쉽지만 사전 학습 점검 판정 같은 핵심 판단을 눈으로 찾아야 한다.
  - 대안 B: 판정 · 선택 근거 · 경고 · 참고 자료 검색을 항목으로 풀고, 원본 JSON은 맨 아래에 남긴다.
- 사건 등록 방식
  - 대안 A: 사건 필드(제목 · 개요 · 요소 등)를 폼으로 직접 입력. 비식별화 · AI 판결 생성은 별도로 해야 해서 파이프라인과 중복된다.
  - 대안 B: 원본 판결문을 넣고 서버 파이프라인이 전부 수행. 입력이 단순하고 기존 파이프라인 흐름과 같다.
- 등록 진행 확인
  - 대안 A: 요청 하나가 끝날 때까지 기다린다. 파이프라인이 몇 분 걸려 타임아웃 위험이 크다.
  - 대안 B: 작업을 만들고(202) 진행 상황을 따로 묻는다(폴링).
  - 대안 C: 서버 푸시(SSE). 관리자 1명 용도에 비해 서버 · 프록시 설정이 크다.

## 선택한 방법과 이유
- 생성 정보는 B. 검수자가 가장 먼저 보는 것이 사전 학습 점검 판정이라 눈에 띄게 하고, 원본 JSON도 남겨 풀어 쓰는 쪽이 놓친 값을 확인할 수 있게 했다. 풀어 쓰는 로직은 DOM 없는 순수 함수(`adminFormat.js`)로 분리해 테스트한다.
- 사건 등록은 B + 폴링(B). 입력은 원본 판결문(최대 3건, 심급별), 결과는 `DRAFT` 사건이다. 계약은 API 명세 A-14 · A-15에 **초안**으로 적고, 서버 구현 전까지 목으로 화면을 완성한다.
- 한 번에 하나만 실행(409 `IMPORT_IN_PROGRESS`). 파이프라인이 외부 AI 호출 한도를 쓰기 때문이다.
- 요약어 후보는 제안만 보여 준다. 요약어 수정 API가 없고(명세 A-6), 파이프라인도 "제안만" 하도록 만들었기 때문이다.

## 판결문 입력 방법 (파일 · 붙여넣기 · 직접 입력)
- 처음에는 PDF 가져오기 / 텍스트 전문 / 직접 입력을 탭으로 나눴으나, 어느 쪽이든 결과가 같은 `originalText` 문자열이고 "원문에서 항목을 읽어 채우기"가 공통이라 **한 화면으로 합쳤다.** 파일 선택(PDF · txt) 아래에 원문 입력칸, 그 아래에 항목 입력칸이 있다. A-14 계약은 바뀌지 않는다.
- 자동 채우기는 파일을 올릴 때, 원문 칸에 붙여넣거나 입력할 때(입력이 400ms 멈춘 뒤) 돈다. 사람이 직접 고친 항목은 다시 덮어쓰지 않는다. 새 파일을 올리면 그 표시를 지우고 다시 채운다.
- 읽는 항목: 사건번호 · 법원명 · 선고일 · 심급 · 범죄 유형(첫 판결문만). "서 울 중 앙 지 방 법 원"처럼 글자를 띄운 첫머리와 "2025. 3. 14. 선고" 순서도 읽는다.
- txt는 UTF-8을 먼저 읽고 실패하면 EUC-KR로 읽는다.
- PDF 글자 뽑기 위치
  - 대안 A: PDF를 서버로 올려 서버(자바 파이프라인)가 뽑는다. 화면은 단순하지만 A-14를 multipart로 바꿔야 하고 서버 구현 전에는 확인할 수 없다.
  - 대안 B: 브라우저에서 pdf.js로 뽑는다. 뽑은 글을 사람이 원문 칸에서 바로 확인 · 고칠 수 있고 계약이 그대로다. 대신 프론트에 의존성(`pdfjs-dist`)이 생긴다.
  - B를 택했다. 옛 브라우저에서도 돌도록 pdf.js의 legacy 빌드를 쓴다. PDF를 처음 고를 때만 불러오는 별도 청크(약 430KB, gzip 130KB)라 다른 화면에는 영향이 없다. 서버가 PDF를 직접 받는 방식이 필요해지면 A-14에 선택 필드로 더한다.
- 보안: `pdfjs-dist` 5.6.83 ~ 6.2.107에 악성 PDF로 임의 스크립트가 실행되는 취약점(GHSA-hq66-cqwq-w95j)이 있어 고쳐진 6.4.299 이상을 쓴다. `isEvalSupported: false`로 읽고, 20MB · 200쪽 · `%PDF-` 머리글 검사로 제한한다.
- 스캔한 이미지 PDF는 글자 인식(OCR)을 하지 않고 "글자를 읽지 못했어요"로 안내한다(텍스트 전문 · 직접 입력으로 유도).
- 예시 PDF는 가상 판결문이다(OFL 글꼴 Nanum Gothic을 부분 포함, 쪽마다 "실제 판결문이 아닙니다" 표시). 정적 파일로 두고 생성 스크립트는 저장소에 넣지 않았다.

## 고려한 제약 사항
- 원본 판결문은 내부 정보다. 요청 본문 로그, 브라우저 저장소, 목 상태에 남기지 않고 등록이 시작되면 입력칸도 비운다.
- 파이프라인 `generation_report` 모양은 `tools/ai-judgment/pipeline.py`의 `build_generation_report`를 기준으로 했다. 자바화하면서 키 이름이 바뀌면 `adminFormat.js`와 목을 함께 고친다. 사람이 검수해 넣은 행은 값이 비어 있으므로 모든 키를 없을 수 있다고 보고 읽는다.
- 이 PR 시점에 로컬 브라우저 확인은 하지 못했다(확장 미연결). 목 API · 변환 함수는 테스트로 확인했다.

## 추후 재검토가 필요하면
- 서버가 A-14 · A-15를 구현할 때 이 계약(필드 · 에러 코드 · 단계 이름)을 확정하고 1-5 에러 코드 목록에 추가한다.
- 등록 작업 목록 조회(새로고침 후 진행 중인 작업 다시 찾기)는 넣지 않았다. 필요해지면 `GET /admin/case-imports`를 추가한다.
- 요약어 수정 API가 생기면 "제안으로 바꾸기" 버튼을 붙인다.
