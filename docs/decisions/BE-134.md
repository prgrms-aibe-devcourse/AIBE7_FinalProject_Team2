# BE-134 의사결정 기록

닉네임 검증 오류 사유 코드 통일 및 혼합 입력 규칙 안내 보완 (BE-113 · FE-117 후속). 담당 D(정민석). FE-133 · FE-134 · FE-135와 한 PR.

## 문제 / 배경

- 2026-10-29 운영 점검: 닉네임 검증 자체는 화면 · 서버 모두 맞게 거절했다. 두 가지가 어긋났다.
  - **사유 이름**: 가입(M-5)에서 길이 · 글자 위반은 요청 DTO 검사라 `reason`이 `Size` · `Pattern`인데, 서비스 검사(한글 8자 · `방청객` 시작)는 모두 `VALIDATION_ERROR`였다. 닉네임 설정(M-7, BE-139)은 DTO 검사가 없어 모든 위반이 `VALIDATION_ERROR`였다.
  - **혼합 입력 안내**: 가입 화면 안내는 "한글은 8자 · 영문 · 숫자는 12자까지"라 한글 8자 · 영문 12자가 따로 있는 것처럼 읽혔다. 실제 규칙은 한글이 하나라도 들어가면 전체 8자다. `가나다abcdefghij`를 치면 안내 없이 `가나다abcde`로 잘렸다.

## 검토한 대안

### 1. 사유 이름

- 대안 A — 커스텀 어노테이션(`@ValidNickname`)을 만들어 DTO에 붙인다: M-7은 DTO 검사가 없고(본문을 그대로 서비스가 본다), 사유가 하나(`ValidNickname`)로 뭉쳐 무엇을 고칠지 알 수 없다.
- 대안 B — **규칙 한 곳(`Nickname.validate`)이 사유별 이름을 준다(선택)**: `NotBlank` · `Pattern` · `Size`는 DTO 어노테이션과 같은 이름이라 M-5에서 DTO가 먼저 걸러도 · 서비스가 걸러도 같은 값이 나온다. 어노테이션으로 표현할 수 없는 둘은 `SizeWithHangul` · `Reserved`. 처음 걸린 하나만 싣는다(글자 → 길이 → 한글 길이 → 예약어, 화면 `nicknameError`와 같은 순서).
- 화면은 `reason`으로 분기하지 않는다(칸 이름만 본다). 응답 모양 · 에러 코드는 그대로라 다른 영향이 없다.

### 2. 혼합 입력 안내

- 자르지 않고 오류로 알린다 / **자르되 알린다(선택)**: 입력칸 잠금(`lockNicknameLength`, FE-114)은 카드 폭을 지키려고 한글 한도를 넘게 쳐지지 않게 한다. 자르는 동작은 두고, 잘랐을 때 칸 아래에 "한글이 들어가면 8자까지라 뒤는 잘랐어요."를 보인다(가입 · 내 정보 수정). 오류가 아니라 `aria-invalid`는 붙이지 않는다.
- 가입 안내문: "2자 이상 · 한글이 들어가면 8자, 영문 · 숫자만이면 12자까지 · 커뮤니티와 랭킹에 보여요".
- 잘림 안내는 다른 input 처리(칸 안내 지우기)가 끝난 뒤에 부른다. 한글 조합이 끝날 때 잠금이 input 이벤트를 다시 보내 칸 안내를 지우므로, 그보다 먼저 보이면 바로 사라진다.

## 확인

- `MemberNicknameApiTest`: M-7 본문별 `reason`(빈 값 · null `NotBlank`, 1자 · 영문 13자 `Size`, 공백 · 기호 · 자동 이름 `Pattern`, 한글 9자 · 혼합 9자 `SizeWithHangul`, `방청객` 시작 `Reserved`), 한글 8자 · 혼합 8자 경계 통과
- `LocalAuthControllerTest`: 가입의 `방청객99` → `Reserved`, 한글 9자(DTO @Size 12 통과) → `SizeWithHangul`
- `nickname.test.js`: 잘림 때 `onClamp`, 조합 끝에는 input 처리 뒤에 부름, 영문 · 숫자만이면 자르지 않음

## 추후 재검토가 필요하면

- 금칙어 기능(A-39 ~ A-41)이 생기면 `Reserved` 검사를 그리로 옮기고 사유 이름을 맞춘다.
