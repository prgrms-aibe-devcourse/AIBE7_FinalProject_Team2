# BE-101 의사결정 기록

> 정책 자체의 검토 · 합의 과정은 `docs/decisions/BE-78.md` "2차 검토"에 이미 기록돼 있다. 이 문서는
> 그 합의를 실제로 구현하면서 생긴, BE-78에는 없던 구현 단위 선택만 추가로 남긴다.

## 문제 / 배경
- BE-78 2차 검토에서 합의한 대로, `case_incident_photo`에 역할 칸(`role`)을 1단계로 도입하고 업로드
  교체 · 삭제 API(A-13-9)를 구현한다.

## 검토한 대안

### 1. 같은 역할 재업로드를 어떻게 처리할까 — 기존 행 교체 vs 삭제 후 재삽입
- 대안 A — 기존 행을 삭제하고 새 행을 insert한다. 구현이 단순해 보이지만, `(case_id, role)` 유니크가
  걸려 있어 삭제와 삽입을 한 트랜잭션 안에서도 순서를 신경 써야 하고, 사진의 `id`가 매번 바뀐다.
- 대안 B(선택) — 기존 엔티티의 필드만 바꾼다(`CaseIncidentPhoto.replace()`). JPA 영속성 컨텍스트가
  UPDATE 하나로 처리하고, id가 유지돼 외부에서 그 사진을 참조하는 쪽(있다면)이 깨지지 않는다.

### 2. S3 객체 교체 때 이전 객체를 지울까
- BE-78 문서가 "후속 이슈 1번에서 정한다"고 남긴 항목. 지금 업로드 키는 `incident-{role}-{timestamp}`
  형식으로 교체할 때마다 새 키가 되므로, 지우지 않아도 캐시 때문에 옛 사진이 다시 보이는 문제는 없다.
  BE-91이 이미 받아들인 "저장 실패 시 고아 객체가 남을 수 있다"는 트레이드오프와 같은 선상이라, 이번에도
  **지우지 않는 쪽**을 택했다(삭제 로직을 추가하면 실패 시 사진은 지웠는데 DB 행은 남는 등 또 다른 실패
  모드가 생긴다). S3 수명 주기 규칙 등 정리는 후속 과제로 남긴다(BE-91 문서와 같은 항목).

### 3. 삭제 API의 식별자 — role vs photo id
- 대안 A — `DELETE /photos/incident/{photoId}`. REST 관례상 자연스럽지만, 호출하는 쪽이 먼저 목록을
  조회해 id를 알아내야 한다.
- 대안 B(선택) — `DELETE /photos/incident/{role}`. 업로드(A-13-4)가 이미 role로 사진을 특정하므로,
  삭제도 같은 키로 하는 편이 호출하는 쪽 입장에서 대칭적이다. role이 없는(1단계 이전) 사진은 이 API로
  지울 수 없다는 제약이 남는데, 그런 사진은 애초에 정리 대상(관리자가 직접 보고 판단)이라 괜찮다고 봤다.

## 선택한 방법과 이유
- 교체는 엔티티 필드 변경(UPDATE)으로, S3 객체는 지우지 않는다(BE-91과 같은 트레이드오프).
- 삭제는 role로 식별한다. role 없는 행은 이번 API로 정리할 수 없다 — 2 · 3단계 전에 남아 있으면 사람이
  직접 DB에서 확인한다(BE-78 문서, "마이그레이션에 DELETE를 넣지 않는다"와 같은 원칙).
- 마이그레이션 버전은 BE-78 문서가 예시로 든 "V22"가 아니라 **V26**을 썼다 — 작업 시작 시점에 develop에
  V22 ~ V25(BE-97 출석, BE-96 꾸미기, BE-93 사건 등록, BE-62 회원)가 이미 먼저 들어가 있었다.

## 고려한 제약 사항
- 로컬 테스트 DB(`docker-compose.test.yml`)에 다른 브랜치에서 쓰던 옛 `V26`(설명이 다른 마이그레이션)의
  Flyway 이력이 남아 있어 체크섬 검증이 깨졌다 — BE-92 2차 PR 때와 같은 상황이라 볼륨을 지우고
  재기동해 다시 처음부터 적용받았다(로컬 테스트 전용이라 지장 없음).
- 공개 API(BE-102)가 이 역할 칸에 의존하므로, BE-102는 이 이슈 이후에 진행한다(BE-78 문서에 이미 명시).

## PR #243 리뷰 반영 (YOLO-NIM)
- API 명세 A-13-5가 "role 없는 행은 A-13-9로 지운다"처럼 적혀 있었는데, 실제 A-13-9는 `{role}`
  (`ORIGIN` · `CONCLUSION`)로만 찾으므로 role 없는 행은 지울 수 없다 — 이 문서(위 "선택한 방법과 이유")와
  어긋나는 설명이었다. API 명세를 "role 없는 행은 이 API로 지울 수 없다"로 바로잡았다(동작은 처음부터
  의도한 그대로였고, 설명만 틀려 있었다).
- 신문 지면(A-13-6 ~ 8) `extraPhotos` 정렬이 "역할 순"으로 설명돼 있는데 실제 구현은 `display_order`
  정렬이다 — 1단계에서는 업로드 시 `ORIGIN` = 0 · `CONCLUSION` = 1로 고정 채번돼 결과가 같지만, 설명과
  구현 방식이 다르다는 지적에 동의해 API 명세와 `AdminCasePaperService` 코드 주석에 "1단계는
  `display_order`로 정렬하며, 그게 결과적으로 역할 순과 같다"는 점과 "2 · 3단계(`display_order` 제거)
  에서는 역할 기준 정렬로 바꿔야 한다"는 점을 명시했다. 지금 당장 정렬 로직을 역할 기준으로 바꾸지 않은
  이유: `role` 문자열을 그대로 정렬하면 알파벳순으로 `CONCLUSION`이 `ORIGIN`보다 앞에 와 순서가 뒤집히므로
  별도 분기(`CASE WHEN role = 'ORIGIN' ...`)가 필요한데, 2 · 3단계에서 `display_order`를 뺄 때 어차피
  정렬 방식을 다시 손봐야 해서 지금 추가 복잡도를 들이지 않았다.
