# FE-62 의사결정 기록

## 문제 / 배경
- 메인 책상의 펜(의견 보내기)이 "준비 중"으로 막혀 있었고, 이용약관 · 개인정보처리방침 입구가 없었다.
- 완료한 사건에서 독자 엽서(S-21)로 가는 길이 6막 팝업 하나뿐이었다.
- 마이페이지의 사건 행이 사건 디테일을 건너뛰고 현재 막으로 바로 가서, 사건 디테일의 `결과만 보기 / 1막부터 다시 보기` 선택(FE-57)을 거치지 못했다.
- 로그인하면 항상 메인으로 가서, 보던 화면으로 돌아오지 못했다.

## 검토한 대안
- 로그인 뒤 돌아가기
  - 대안 A: 로그인 화면에 돌아갈 주소(`next`)를 넘기고, 이동 때 주소를 화면 이름으로 되돌린다. 라우터에 주소 → 화면 변환이 필요하고, 임의 주소를 받으면 열린 리다이렉트 위험이 있다.
  - 대안 B: 앱 안에 이전 기록이 있으면 `history.back()`, 없으면 메인으로 간다(`canGoBackInApp`).
- 약관 · 방침 입구 위치
  - 대안 A: 공통 푸터 전체에 단다(IA는 "모든 화면 푸터 링크").
  - 대안 B: 메인 맨 아래 푸터에만 단다.
- 의견 보내기 제출
  - 대안 A: 목 저장소(`localStorage`)에 쌓는다.
  - 대안 B: 접수하지 않고 "준비 중"으로 알린다.

## 선택한 방법과 이유
- 로그인 뒤 돌아가기는 **대안 B**. 주소를 받지 않아 안전하고, 라우터를 건드리지 않는다. 진행 상태는 서버 · 쿠키에 있어 돌아가도 그대로다. 바로 `/login`으로 들어왔으면 메인으로 간다.
- 약관 · 방침 입구는 요청대로 **대안 B(메인 맨 아래)**. `renderSiteFooter({ navigate })`에 옵션으로 넣어 두어, 다른 화면에 달 때 인자만 넘기면 된다. 페이지는 조항이 정해질 때까지 "준비 중" 틀이다.
- 의견 보내기는 **대안 B**. 받는 서버 API가 없고, 목에 쌓아도 팀이 볼 수 없어 오해를 부른다. 틀(열기 · 닫기 · 포커스 · 쓰던 내용 확인)만 만들고 제출은 서버 API가 생길 때 `submit()`에 붙인다.
- 마이페이지 사건 행은 사건 디테일로 보내고, 마친 사건에는 `독자 엽서 쓰기`를 따로 둔다. 독자 엽서 입구는 사건 디테일(내로 대사 아래 세 번째 선택지)과 마이페이지 두 곳이다.
- `독자 엽서 쓰기`는 화면을 옮기지 않고 6막과 같은 엽서 창(`openCaseReviewPopup`)을 쓴다. 사건 디테일에서는 화면에 있는 남불이 엽서를 꺼내 건네고(`hand: true`), 남불이 없는 마이페이지에서는 누른 버튼 자리에서 엽서가 떠오른다. 창을 닫으면 선택지로 돌아오게 사건 디테일의 `chosen`은 비우지 않는다.
- 메인 책상의 엽서도 펜과 같은 의견 보내기 창을 연다. 엽서 버튼은 Tab · 낭독기에서 숨기고(펜 하나만 남김) 마우스 범위와 호버만 넓혔다. 펜과 엽서는 어느 쪽에 올려도 함께 밝아진다.

- 사건 디테일에서 남불이 엽서를 건네지 못하던 원인은 `release()`가 붙인 `entering` 클래스가 걷히지 않아, 우선순위가 더 높은 들어오기 연출이 `.delivering`을 덮은 것이었다. 연출이 끝나는 시점(1초 뒤)에 클래스를 걷도록 `stage.js`를 고쳤다.
- 엽서 창이 스크롤을 잠글 때 스크롤바가 사라져 뒤 지면이 움찔하던 것은, 스크롤바가 있던 화면에 한해 `scrollbar-gutter: stable`로 자리를 비워 두어 막았다. 가림막은 남불이 손을 내민 뒤에 어두워지게 해 남불이 가려지지 않게 했다.

## 고려한 제약 사항
- 로그인이 아직 개발용 목업이라 로그인 후 진행 상태 연결(기록 옮기기, REQ-066 · 067)은 이번에 하지 않았다.
- 좁은 화면 메인 메뉴에도 의견 보내기를 추가했다(메뉴 카드 4개 → 5개, 2열이라 줄이 하나 늘어난다).

## 추후 재검토가 필요하면
- 약관 · 방침 입구를 모든 화면 푸터로 넓힐지(IA는 모든 화면).
- 의견 접수 API가 생기면 `feedbackDialog.js`의 `submit()`을 연결하고 성공 문구로 바꾼다.
- 실제 로그인이 붙으면 로그인 직후 "이 브라우저의 기록을 내 계정에 연결할까요?" 단계를 둔다.
- 로그인 뒤 돌아가기는 앱 안 이동(`history.back()`)에서만 맞다. 카카오 로그인은 콜백으로 전체 페이지가 바뀌어 앱 안 기록이 사라지므로, OAuth `state`로 돌아갈 화면을 넘긴다(BE-62, 허용 목록 검증). (#213 리뷰)
- 개인정보처리방침은 지금 "준비 중" 틀이다. 카카오 로그인(BE-62)으로 회원 정보를 받기 전까지 본문을 올려야 한다. (#213 리뷰)
- `독자 엽서 쓰기` 입구는 리뷰 API 전에도 실제 모드에서 보인다(누르면 "준비 중"). API가 곧 나올 예정이라 숨기지 않았다. 일정이 밀리면 실제 모드에서 숨길지 다시 본다. (#213 리뷰)

## BE-82 반영 (PR #213, #214 머지 뒤)
- 독자 엽서 화면 ID를 S-21에서 S-09(리뷰 페이지)로 맞췄다. 결정 과정은 `docs/decisions/FE-61.md`의 "BE-82 반영"을 본다.
- IA S-09 절에 입구 세 곳(6막 `엽서 쓰기` · 사건 디테일 · 마이페이지 `독자 엽서 쓰기`), 완료 사건만이라는 조건, 팝업(주소 그대로)과 직접 진입(별도 화면) 동작을 적었다(#213 CodeRabbit 리뷰).
- 주소는 아직 `/opinion`이다. `/letters`로 옮기는 일은 FE-58.
