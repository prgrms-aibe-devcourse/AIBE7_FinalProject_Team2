# BE-59 의사결정 기록

> 확장 단계(WBS 7.1.2) · 1차 외부 DB 모드 · 담당 정민석

운영 DB를 같은 서버의 postgres 컨테이너에서 외부 PostgreSQL로 옮기는 작업. RDS는 요금 제한으로 10/28부터 쓸 수 있어, **10/22 ~ 10/28 오전은 팀 공용 Supabase DB(COMMON-59)** 에 붙고 **10/28 오후에 RDS로 바꾼다.** 1차는 **두 경우 모두 같은 구성으로 붙을 수 있게 하는 것**까지다.

## 1차 (외부 DB 모드)

### 문제 / 배경

- 운영 구성이 postgres 컨테이너에 묶여 있다 — backend 접속 주소(`postgres:5432`)와 `depends_on: postgres`, `backup-db.sh`의 `compose exec postgres`, `deploy.sh`의 파이프라인 메모리 가드(compose 파일에 postgres가 있으면 차단)와 스키마 번호 조회.
- 10/22 결정: 운영에도 테스트 데이터만 있으니, 10/22 ~ 10/28 오전은 운영도 공용 Supabase DB를 함께 쓴다(같은 실데이터로 화면 · API 검증, 운영 데이터 이전 없음).
- RDS(10/28 오후)까지 1주 안에 DB를 두 번 바꾸게 되므로, 바꿀 때마다 compose를 고치는 방식은 피해야 했다.

### 검토한 대안

- **`docker-compose.prod.yml`에서 postgres를 지우고 DB_URL을 바꾼다**: 원래 README "다음 작업에서 바꿀 곳"의 방식. 되돌리려면 다시 PR이 필요하고, Supabase → RDS 때 또 바꿔야 한다. 같은 서버 DB(`pgdata`)로 돌아갈 길도 사라진다.
- **서버에서 compose를 손으로 고친다**: 자동 배포(`cd-agent.sh`)가 저장소 사본을 배포 커밋으로 맞추므로 다음 배포 때 조용히 원래대로 돌아간다(서버에서 파일 직접 수정 금지 규칙).
- **오버레이 + `.env` 스위치** ← 선택: `docker-compose.external-db.yml`을 겹치면 외부 DB, 빼면 같은 서버 DB. Supabase → RDS는 `.env` 값만 바꾼다. 다른 오버레이(모니터링 · 실제 사건 시드 · 파이프라인)와 같은 방식이다.

postgres를 오버레이에서 빼는 방법:
- Compose는 오버레이로 서비스를 지우지 못한다 → **`profiles: ["embedded-db"]`** 로 기본 실행에서 뺀다. 정의 · 볼륨은 남아 되돌릴 수 있다.
- backend의 `depends_on`은 목록이 합쳐지므로 **`!override`**(Compose 2.24.4+)로 redis만 남긴다. `deploy.sh`가 버전을 먼저 확인한다.

### 선택한 방법과 이유

- `deploy/docker-compose.external-db.yml`: backend `DB_URL` · `DB_USERNAME` · `DB_PASSWORD`를 `EXTERNAL_DB_*`로, 연결 풀 기본 5(`EXTERNAL_DB_POOL_SIZE`), `depends_on`은 redis만, postgres는 `profiles`로 제외.
- `deploy.sh`:
  - `.env`에 `EXTERNAL_DB_URL`이 있으면 오버레이를 자동으로 겹친다(빼먹으면 같은 서버 DB로 조용히 붙는 것을 막는다)
  - 배포 전 중단(종료 코드 4, 아무것도 바꾸지 않음): 사용자명 · 비밀번호 없음 / `sslmode=require` 이상 없음 / `REAL_SEED_DIR` 있음 / Compose 2.24.4 미만
  - **`--reapply`**: 자동 배포는 이미지 태그가 바뀔 때만 동작해 `.env`만 바꾼 전환이 적용되지 않는다 → 같은 이미지로 같은 확인(백엔드 준비 · 스모크)을 한다. 실패해도 자동으로 되돌리지 않는다(되돌릴 대상이 사람이 바꾼 `.env`라서)
  - 파이프라인 메모리 가드는 외부 DB 모드에서 묻지 않는다. 스키마 번호 조회는 건너뛴다 — 전환 직후에는 옛 postgres가 아직 떠 있어 엉뚱한 DB 번호를 읽게 되기 때문이다(실패 경고용 값)
- `backup-db.sh`: 외부 DB면 `postgres:17-alpine` 클라이언트 컨테이너로 `public` 스키마만 덤프한다(Supabase 자체 스키마 제외). 비밀번호는 환경변수 이름만 넘겨 명령줄 · 로그에 남지 않는다.
- 운영 실제 사건 시드는 외부 공용 DB에 올리지 않는다(COMMON-59 규칙 6 · LBox). 그래서 전환하면 운영 화면의 사건이 공용 DB의 가상 사건으로 바뀐다 — 테스트 목적이라 감수했다.

### 검증

- `docker compose config`: 오버레이를 겹치면 postgres가 서비스 목록에서 빠지고, backend `depends_on`은 redis만, 접속 값 · 풀 크기가 바뀐다. 파이프라인 · 모니터링 오버레이와 함께 써도 정상.
- 전환 재현(작은 구성): 오버레이로 `up -d backend` → backend만 외부 주소로 재생성되고 **옛 postgres는 계속 떠 있다**(그래서 README에 수동 정지 절차) / 오버레이 없이 다시 `up -d backend` → postgres가 다시 뜨고 원래 주소로 돌아간다.
- `deploy.sh`를 가짜 docker로 실행: 외부 DB 없음 → 오버레이 없음, 정상 → 오버레이 포함, 사용자명 없음 · sslmode 없음 · prefer · 실제 사건 시드 · Compose 2.21 · 2.24.3 · 확인 불가 → 중단, 2.24.4 · 2.29.7 → 통과, 외부 DB + 파이프라인 → 메모리 가드 통과, 내부 DB + 파이프라인 → 기존대로 차단. 비밀번호 출력 0건.
- `backup-db.sh`를 실제 Supabase 공용 DB로 실행: `public`만 128KB, Supabase 자체 스키마 0줄, 권한 600, 비밀번호 출력 0건.

### 고려한 제약 사항

- 공용 DB라 운영과 팀원 로컬의 데이터가 섞인다(테스트 데이터 전제). 운영 backend도 main 기준으로 Flyway를 돌린다 — develop 기준으로 먼저 적용하는 담당자보다 같거나 뒤다.
- 전환 · 되돌리기 모두 데이터를 옮기지 않는다. 외부 DB에 쓰인 데이터는 되돌린 뒤 같은 서버 DB에 없다.
- 옛 postgres 컨테이너는 전환해도 저절로 멈추지 않는다(512m 계속 사용) → 확인 뒤 사람이 `stop`.
- `sslmode=require`는 암호화만 하고 서버 인증서는 확인하지 않는다(COMMON-59 규칙 8과 같은 판단).
- 외부 DB 백업은 같은 서버 디스크에 둔다(기존 백업과 같은 한계). RDS로 옮기면 RDS 자동 백업으로 해결한다.

## 추후 재검토가 필요하면

- **RDS 전환(10/28 오후)**: `.env`의 `EXTERNAL_DB_*`만 RDS 값으로 바꾸고 `--reapply`. Supabase 데이터를 옮길지는 그때 정한다(옮기면 `CREATE EXTENSION vector` 후 `pg_restore --no-owner --no-privileges`).
- **비밀값 관리**: 지금은 서버 `.env`(600). RDS 전환 때 시크릿 저장소(SSM Parameter Store 등)로 옮길지 본다.
- **스키마 번호 비교**: 외부 DB 모드에서도 실패 경고를 남길지(클라이언트 컨테이너로 조회).
- **postgres 정의 삭제**: RDS가 안정되면 `docker-compose.prod.yml`에서 postgres 서비스 · `pgdata`를 지우고 오버레이를 기본 구성으로 합칠지.

## 후속: 외부 DB에 실제 사건 시드 (10/26)

### 결정

- 팀 합의(10/26): RDS 전환 전 **Supabase에서도 실데이터로 최종 테스트**한 뒤 RDS로 넘어간다.
- `deploy.sh`의 외부 DB 차단을 지우지 않고 **명시적 합의 표시**로 바꿨다: 외부 DB 모드에서 `REAL_SEED_DIR`은 `.env`에 `EXTERNAL_DB_ALLOWS_REAL_SEED=1`이 **함께** 있을 때만 허용한다.
- 함께 넣은 배포 전 중단(종료 코드 4): 표시 없음 / `REAL_SEED_DIR`에 SQL 없음(경로 실수 → Flyway가 아무것도 안 넣고 성공으로 끝나는 것 방지) / LBox 행(`'LBOX'`) 있음(`run-shared-db.sh`와 같은 검사, 라이선스상 사용 불가).

### 대안

| 안 | 판단 |
|---|---|
| 차단을 RDS에서만 푼다(호스트로 판별) | Supabase 최종 테스트를 못 한다. 호스트 문자열 판별은 깨지기 쉽다 |
| 차단을 지운다 | 경로만 남은 `.env`(되돌리기 사본 등)로 비공개 데이터가 조용히 외부 DB에 올라간다 |
| 담당자 로컬 `run-shared-db.sh --with-private-seed`로만 올린다 | Supabase는 되지만 RDS 전환 때 다시 같은 문제. 운영 기준(main) 시드와 어긋날 수 있다 |
| **합의 표시 값 하나 추가(채택)** | Supabase · RDS 모두 같은 절차. 실수로 켜지지 않는다 |

### 검증

- 차단 블록 · 오버레이 판정만 떼어 7가지로 실행: 경로 없음 → 통과(오버레이 없음) / `REAL_SEED_DIR=""` → 통과(오버레이 없음) / 경로만 → 중단 / 표시 0 → 중단 / 빈 폴더 → 중단 / LBox 행 → 중단 / 경로 · 표시 모두(따옴표 포함) → 통과(real-seed 오버레이 추가).
- 경로는 한 번만(따옴표 · 공백 · CR 정리) 읽어 검사와 오버레이 판정에 같이 쓴다 — 따로 읽으면 `REAL_SEED_DIR=""`가 검사는 건너뛰고 오버레이만 붙는다(최종 검토에서 수정).
- PR #281 CodeRabbit 리뷰 반영: ① 검사한 경로를 `export REAL_SEED_DIR`로 Compose에도 강제한다(셸에 남은 다른 경로가 `.env`보다 우선돼 검사하지 않은 폴더가 붙는 것 방지 — 셸에 다른 경로를 export한 상태로 실행해 `.env` 경로가 쓰이는 것 확인) ② SQL 확인은 읽을 수 있는 일반 파일만 센다(이름만 `*.sql`인 폴더는 중단 — 실행해 확인).
- PR #281 팀 리뷰 반영: LBox 검사가 읽기 오류(grep 종료 코드 2)를 "없음"으로 보고 통과하던 것을 실패 쪽으로 닫았다 — 종료 코드 1일 때만 통과. 배포 계정이 못 읽는 `*.sql`이 있으면 검사 전에 중단한다(컨테이너는 다른 uid라 읽을 수 있음). `backend/run-shared-db.sh`의 같은 검사도 함께 고쳤다.
- PR #281 CodeRabbit 리뷰(Major) 반영: Flyway `filesystem:` 위치는 하위 폴더까지 재귀로 읽는데 검사는 최상위 `*.sql`만 봐서, 하위 폴더의 V 마이그레이션이 LBox 검사를 건너뛸 수 있었다. `find -L … -type f -name '*.sql'`로 재귀 수집하고, `find` 실패(못 읽는 하위 폴더 · 링크 순환)는 "없음"과 구분해 중단한다. `run-shared-db.sh`도 같은 방식으로 고쳤다.
- 실제 사건 시드와 공용 DB의 가상 사건 시드는 ID를 쓰지 않고 제목(`uk_legal_case_title`)이 달라 함께 들어가도 충돌하지 않는다.
- `bash -n deploy/deploy.sh` 통과.

### 제약

- 공용 DB라 팀원 로컬에도 실제 사건이 보인다. 가상 사건 시드도 남는다.
- `.env`에서 값을 빼도 들어간 데이터는 지워지지 않는다 → RDS 전환 후 Supabase 정리 때 지운다.

## 2차: RDS 전환 (10/28)

### 문제 / 배경

- 1차로 외부 DB 모드를 만들어 두었고, 10/28 RDS 요금 제한이 풀려 운영 DB를 Supabase 공용 DB에서 RDS로 옮겼다.
- 팀 요구(10/28): **운영 RDS에는 실데이터만** 둔다. Supabase에는 팀원이 만든 테스트 계정 · 체험 기록과 가상 사건 시드가 섞여 있다.
- 같은 날 실제 판례 21건이 Flyway 시드가 아니라 **한 번 실행하는 적재 파일**(비공개 저장소 `loads/`, BE-31)로 왔다. 그래서 "시드 머지를 기다렸다가 전환"할 필요가 없어졌다.
- t3.small 한 대(2GB) 제약은 그대로다. 운영 비밀값은 서버 `.env`(600)로만 넣는다.

### 검토한 대안

| 항목 | 안 | 판단 |
| --- | --- | --- |
| 인스턴스 | db.t4g.small | 팀 규모(사용자 소수 · 사건 수십 건 · RAG 약 12MB)에 비해 크다. 비용이 두 배 |
| | db.t3.micro | 동작은 같다. 같은 크기에서 Graviton(t4g)이 더 싸고, 앱은 JDBC만 써 CPU 종류 영향이 없다 |
| | **db.t4g.micro(채택)** | 가장 작은 클래스(프리 티어 템플릿). 단일 AZ · gp3 20GiB · 자동 확장 끔. 부족하면 클래스만 올린다 |
| 데이터 | Supabase 덤프를 RDS에 복원 | 테스트 계정 · 가상 사건이 운영에 섞인다. 골라 지우는 작업이 실수하기 쉽다 |
| | **빈 RDS + Flyway + 실데이터만(채택)** | 운영에 들어간 것이 전부 출처가 분명하다(스키마 · 비공개 시드 R__ 6개 · `loads/`). 대가: 팀원 계정 재가입 |
| 접속 계정 | 마스터 계정을 backend에 그대로 | `rds_superuser`라 앱이 뚫리면 DB 전체 권한. `docs/rag-handover.md` 6장 체크리스트와도 어긋난다 |
| | **앱 계정 `lawnambul_app` 분리(채택)** | 확장(`vector`)만 마스터로 먼저 만들고, 앱 계정은 `public` 스키마 주인 + DB 접속 · 임시 테이블 권한만. Flyway · 백업 · `loads/`도 앱 계정 |
| `.env` 편집 | nano로 붙여 넣기 | 실제로 실패했다(아래 검증). 섞인 글자가 눈에 안 보인다 |
| | 셸 함수를 그때그때 붙여 넣기 | 당일 이 방식으로 넘겼지만 매번 길고, 함수를 빼먹기 쉽다 |
| | **`deploy/env-set.sh`(채택)** | 비밀값 숨김 입력, 터미널 신호 제거, 키별 형식 검사, 같은 키 한 줄, 권한 600 · 주인 확인. 값은 길이만 출력 |
| `loads/` 실행 | 파일을 서버에 복사(scp) 후 실행 · 삭제 | 사람 손을 한 번 더 거치고, 지우는 것을 빼먹기 쉽다 |
| | **서버 비공개 저장소 사본에서 `git show … \| psql`(채택)** | 작업 폴더에 파일이 생기지 않고 `seed/` 고정 커밋을 건드리지 않는다. 다만 partial clone이라 받은 내용이 `.git/objects`에 남는다 → `.git`을 다른 계정이 못 읽게 막았다 |

### 선택한 방법과 이유

- RDS: PostgreSQL 17, `db.t4g.micro`, 단일 AZ, 퍼블릭 액세스 없음, 콘솔 "EC2 컴퓨팅 리소스에 연결"로 만든 보안 그룹 한 쌍으로만 접근, 저장 암호화 · 삭제 방지 · 자동 백업 7일.
- 마스터로 `CREATE EXTENSION vector` → 앱 계정 생성 → `GRANT lawnambul_app TO lawnambul`(스키마 주인 변경에 필요) → `ALTER SCHEMA public OWNER TO lawnambul_app`. V11의 `CREATE EXTENSION IF NOT EXISTS`는 이미 있어 권한 없이 넘어간다.
- `.env` 한 번 수정 → `--reapply` 한 번: DB 3개 · 비공개 시드 2개 · 관리자 부트스트랩 2개, 같은 날 파이프라인(COMMON-52) 4개. 키는 넣기 전에 무료 조회(모델 목록)로 200을 확인했다.
- 적재 순서: 배포(R__ 6개) → **RDS 수동 스냅샷** → `loads/` 21건. 적재 파일이 큰 데이터를 한꺼번에 넣으므로 그 직전 상태를 DB 단위로 남겼다.
- 되돌리기 사본(`.env`)은 저장소 폴더 밖(`~/`)에 둔다. 저장소 폴더는 cd-agent가 배포 커밋으로 맞추는 곳이다.

### 검증 (10/28 운영)

- EC2 → RDS: TLS 1.3, PostgreSQL 17.11, `vector` 0.8.2, 빈 DB(테이블 0) 확인 후 앱 계정 권한 시험(테이블 생성 · 삭제) 통과.
- `--reapply`: 빈 RDS에 Flyway **38개 적용**(V1 ~ V32, 비공개 시드 R__ 6개, 성향 콘텐츠), `ERROR` 없음. backend가 RDS에 연결 5개(연결 풀). pipeline healthy · 호스트 포트 없음. 메모리 available 938 → 867MiB.
- `loads/` 21건 21/21 성공 → `legal_case` `PUBLISHED 1 · DRAFT 21`. `member` 0, 관리자는 `admin_account` 1. 관리자 로그인 확인 후 부트스트랩 값을 비우고 다시 적용.
- 비밀번호 입력 실패 원인을 실제로 확인했다: 54자 중 hex가 아닌 6자가 `ESC [ O ESC [ I`(창 전환 신호)였다. 따로 247 · 28 · 15자가 들어간 경우는 클립보드가 채팅의 명령어로 바뀐 것이었다. 둘 다 `env-set.sh --secret`이 저장 전에 거절한다.
- `env-set.sh`: 형식 위반(URL `sslmode` 없음 · `PIPELINE_SERVICE=2` · `$` 포함) 거절, 비밀값을 명령줄로 넣으면 거절, 붙여 넣기 · 창 전환 신호 제거 후 저장, 명령어가 붙여 넣어진 경우(공백) · 남은 제어 문자 거절, 파이프 입력 거절, 주인이 다른 `.env` 거절, `--check`의 권한 · ESC · 중복 · 형식 판정을 실행해 확인. `bash -n` 통과.

### 고려한 제약 사항

- 단일 AZ: 장애 때 자동 대체가 없다. 프로젝트 기간 · 비용 기준으로 감수하고, 자동 백업 · 스냅샷으로 복구한다.
- `sslmode=require`는 암호화만 하고 서버 인증서는 확인하지 않는다(1차와 같은 판단). 같은 VPC 안 사설 주소로만 붙는다.
- 비밀값은 여전히 서버 `.env`(600)다. 시크릿 저장소(SSM 등)는 IAM 권한이 없어 이번에 하지 않았다.
- 비공개 시드 `seed/`는 컨테이너가 다른 uid(10001)로 읽어 다른 계정 읽기 권한을 막지 못한다. `.git`만 막았다. 서버에 sudo · docker 그룹 계정을 늘리지 않는 것으로 보완한다(10/28 시험 계정 정리).
- Supabase 데이터를 옮기지 않아 팀원 계정 · 체험 기록은 운영에 없다(재가입 안내, 10/28 팀 공지).

### 추후 재검토가 필요하면

- DB 지표 경보(CloudWatch 또는 `postgres_exporter`, COMMON-64 후속), `docker-compose.prod.yml`의 postgres 정의 삭제.
