# BE-59 의사결정 기록

> 확장 단계(WBS 7.1.2) · 1차 외부 DB 모드 · 담당 정민석

운영 DB를 같은 서버의 postgres 컨테이너에서 외부 PostgreSQL로 옮기는 작업. RDS는 요금 제한으로 10/28부터 쓸 수 있어, **10/22 ~ 10/28 오전은 팀 공용 Supabase DB(COMMON-59)** 에 붙고 **10/28 오후에 RDS로 바꾼다.** 1차는 **두 경우 모두 같은 구성으로 붙을 수 있게 하는 것**까지다.

## 1차 (외부 DB 모드)

### 문제 / 배경

- 운영 구성이 postgres 컨테이너에 묶여 있다 — backend 접속 주소(`postgres:5432`)와 `depends_on: postgres`, `backup-db.sh`의 `compose exec postgres`, `deploy.sh`의 파이프라인 메모리 가드(compose 파일에 postgres가 있으면 차단)와 스키마 번호 조회.
- 10/22 결정: 운영에도 테스트 데이터만 있으니, 10/22 ~ 10/28 오전은 운영도 공용 Supabase DB를 함께 쓴다(같은 실데이터로 화면 · API 검증, 운영 데이터 이전 없음).
- RDS(10/28 오후)까지 1주 안에 DB를 두 번 바꾸게 되므로, 바꿀 때마다 compose를 고치는 방식은 피해야 했다.

### 검토한 대안

- **`docker-compose.prod.yml`에서 postgres를 지우고 DB_URL을 바꾼다**: 원래 README "다음 작업에서 바꿀 곳"의 방식. 되돌리려면 다시 PR이 필요하고, Supabase → RDS 때 또 바꿔야 한다. 같은 서버 DB(`pgdata`)로 돌아갈 길도 사라진다.
- **서버에서 compose를 손으로 고친다**: 자동 배포(`cd-agent.sh`)가 저장소 사본을 배포 커밋으로 맞추므로 다음 배포 때 조용히 원래대로 돌아간다(서버에서 파일 직접 수정 금지 규칙).
- **오버레이 + `.env` 스위치** ← 선택: `docker-compose.external-db.yml`을 겹치면 외부 DB, 빼면 같은 서버 DB. Supabase → RDS는 `.env` 값만 바꾼다. 다른 오버레이(모니터링 · 실제 사건 시드 · 파이프라인)와 같은 방식이다.

postgres를 오버레이에서 빼는 방법:
- Compose는 오버레이로 서비스를 지우지 못한다 → **`profiles: ["embedded-db"]`** 로 기본 실행에서 뺀다. 정의 · 볼륨은 남아 되돌릴 수 있다.
- backend의 `depends_on`은 목록이 합쳐지므로 **`!override`**(Compose 2.24.4+)로 redis만 남긴다. `deploy.sh`가 버전을 먼저 확인한다.

### 선택한 방법과 이유

- `deploy/docker-compose.external-db.yml`: backend `DB_URL` · `DB_USERNAME` · `DB_PASSWORD`를 `EXTERNAL_DB_*`로, 연결 풀 기본 5(`EXTERNAL_DB_POOL_SIZE`), `depends_on`은 redis만, postgres는 `profiles`로 제외.
- `deploy.sh`:
  - `.env`에 `EXTERNAL_DB_URL`이 있으면 오버레이를 자동으로 겹친다(빼먹으면 같은 서버 DB로 조용히 붙는 것을 막는다)
  - 배포 전 중단(종료 코드 4, 아무것도 바꾸지 않음): 사용자명 · 비밀번호 없음 / `sslmode=require` 이상 없음 / `REAL_SEED_DIR` 있음 / Compose 2.24.4 미만
  - **`--reapply`**: 자동 배포는 이미지 태그가 바뀔 때만 동작해 `.env`만 바꾼 전환이 적용되지 않는다 → 같은 이미지로 같은 확인(백엔드 준비 · 스모크)을 한다. 실패해도 자동으로 되돌리지 않는다(되돌릴 대상이 사람이 바꾼 `.env`라서)
  - 파이프라인 메모리 가드는 외부 DB 모드에서 묻지 않는다. 스키마 번호 조회는 건너뛴다 — 전환 직후에는 옛 postgres가 아직 떠 있어 엉뚱한 DB 번호를 읽게 되기 때문이다(실패 경고용 값)
- `backup-db.sh`: 외부 DB면 `postgres:17-alpine` 클라이언트 컨테이너로 `public` 스키마만 덤프한다(Supabase 자체 스키마 제외). 비밀번호는 환경변수 이름만 넘겨 명령줄 · 로그에 남지 않는다.
- 운영 실제 사건 시드는 외부 공용 DB에 올리지 않는다(COMMON-59 규칙 6 · LBox). 그래서 전환하면 운영 화면의 사건이 공용 DB의 가상 사건으로 바뀐다 — 테스트 목적이라 감수했다.

### 검증

- `docker compose config`: 오버레이를 겹치면 postgres가 서비스 목록에서 빠지고, backend `depends_on`은 redis만, 접속 값 · 풀 크기가 바뀐다. 파이프라인 · 모니터링 오버레이와 함께 써도 정상.
- 전환 재현(작은 구성): 오버레이로 `up -d backend` → backend만 외부 주소로 재생성되고 **옛 postgres는 계속 떠 있다**(그래서 README에 수동 정지 절차) / 오버레이 없이 다시 `up -d backend` → postgres가 다시 뜨고 원래 주소로 돌아간다.
- `deploy.sh`를 가짜 docker로 실행: 외부 DB 없음 → 오버레이 없음, 정상 → 오버레이 포함, 사용자명 없음 · sslmode 없음 · prefer · 실제 사건 시드 · Compose 2.21 · 2.24.3 · 확인 불가 → 중단, 2.24.4 · 2.29.7 → 통과, 외부 DB + 파이프라인 → 메모리 가드 통과, 내부 DB + 파이프라인 → 기존대로 차단. 비밀번호 출력 0건.
- `backup-db.sh`를 실제 Supabase 공용 DB로 실행: `public`만 128KB, Supabase 자체 스키마 0줄, 권한 600, 비밀번호 출력 0건.

### 고려한 제약 사항

- 공용 DB라 운영과 팀원 로컬의 데이터가 섞인다(테스트 데이터 전제). 운영 backend도 main 기준으로 Flyway를 돌린다 — develop 기준으로 먼저 적용하는 담당자보다 같거나 뒤다.
- 전환 · 되돌리기 모두 데이터를 옮기지 않는다. 외부 DB에 쓰인 데이터는 되돌린 뒤 같은 서버 DB에 없다.
- 옛 postgres 컨테이너는 전환해도 저절로 멈추지 않는다(512m 계속 사용) → 확인 뒤 사람이 `stop`.
- `sslmode=require`는 암호화만 하고 서버 인증서는 확인하지 않는다(COMMON-59 규칙 8과 같은 판단).
- 외부 DB 백업은 같은 서버 디스크에 둔다(기존 백업과 같은 한계). RDS로 옮기면 RDS 자동 백업으로 해결한다.

## 추후 재검토가 필요하면

- **RDS 전환(10/28 오후)**: `.env`의 `EXTERNAL_DB_*`만 RDS 값으로 바꾸고 `--reapply`. Supabase 데이터를 옮길지는 그때 정한다(옮기면 `CREATE EXTENSION vector` 후 `pg_restore --no-owner --no-privileges`).
- **비밀값 관리**: 지금은 서버 `.env`(600). RDS 전환 때 시크릿 저장소(SSM Parameter Store 등)로 옮길지 본다.
- **스키마 번호 비교**: 외부 DB 모드에서도 실패 경고를 남길지(클라이언트 컨테이너로 조회).
- **postgres 정의 삭제**: RDS가 안정되면 `docker-compose.prod.yml`에서 postgres 서비스 · `pgdata`를 지우고 오버레이를 기본 구성으로 합칠지.
- **실제 사건 시드**: RDS(공용 DB 아님)로 옮긴 뒤 운영에 실제 사건을 다시 올릴 때 `deploy.sh`의 `REAL_SEED_DIR` 차단을 RDS에서만 풀지 정한다.
