# FE-44 의사결정 기록

## 문제 / 배경
- S-17 마이페이지에 종합 판결 성향(4축)과 성향 변화 흐름을 더하고, 성향 API(P-1 ~ P-5)를 실제 API 쪽에 연결해야 했다.
- 체험 → 성향 저장(7.6.7, BE-64) 전에는 `judgmentPersonality`가 `null`, `history`가 빈 배열로 온다.
- WBS 예비 조정안 9순위가 "성향 변화 그래프 제외"였지만, FE-44 완료 조건에 변화 흐름이 있어 범위대로 구현하기로 했다.

## 검토한 대안
- 변화 흐름 표현 A: 4축을 한 차트에 선 4개로 그린다. 축마다 양 끝 이름이 달라 한 Y축에 설명하기 어렵고, 색으로만 선을 구분하게 된다.
- 변화 흐름 표현 B: 축마다 기존 엄격 ↔ 관대 막대 위에 체험 번호가 붙은 점을 찍는다.
- 종합 4축 그래프: 성향 결과(S-16)의 막대 줄을 그대로 쓸지, 마이페이지용으로 새로 만들지.

## 선택한 방법과 이유
- 변화 흐름은 B. 결과 화면의 막대와 같은 언어라 따로 배울 것이 없고, 번호로 순서를 읽으니 색에 기대지 않으며, 모바일 폭에서도 줄이 겹치지 않는다. "처음보다 ○○ 쪽으로 ○○%p 움직였어요" 문장을 함께 둔다(계산은 `utils/myPageView.js`, 테스트 포함).
- 종합 그래프는 막대 줄을 `components/axisRow.js`로 빼서 S-16과 S-17이 함께 쓴다. 값이 없는 축(`null`)은 막대 대신 "체험 자료가 아직 없어요"로 보인다.
- `realApi.js`에 P-1 ~ P-5를 추가했다. 함수 이름 · 인자 · 응답은 목과 같다.

## 고려한 제약 사항
- 점수 방향은 API 그대로 "관대 쪽 비중"이고 화면은 왼쪽 = 엄격 쪽이다(S-16 막대와 같다).
- 목 `getMyPage`는 화면 확인용으로 체험 기록 3건을 채운다. 실제 API는 BE-64 전까지 비어 있다. 빈 상태는 `?empty=history`로 본다.

## 추후 재검토가 필요하면
- 체험이 많아져 점이 겹치면(10건 이상) 최근 N건만 보이는 방식을 검토한다.
- BE-64가 붙어 실제 `history`가 채워지면 실제 모드(`VITE_API_MODE=real`)에서 한 번 확인한다.

## 2차 (PR #xxx) — 일러스트 컬렉션

### 문제 / 배경
- 판결 체험에서 나온 일러스트를 마이페이지에서 모아 볼 수 있어야 했다. 세계관 문서는 저장 · 컬렉션을 로그인(REQ-066 · 067)과 함께 이후로 두었다.

### 검토한 대안
- A. 체험 기록(`experiences`의 완료 사건)에서 모은 목록을 매번 계산한다. 별도 저장이 없다.
- B. "수집했다"는 상태를 따로 저장한다(서버 API · DB, 목 단계는 localStorage). 획득 시점 · 새로 얻음 표시 같은 상태를 다룰 수 있다.

### 선택한 방법과 이유
- 이번 PR은 A. 백엔드 변경이 없고, 로그인 전에도 익명 ID 기준 체험 기록만으로 동작한다. 저장 상태와 체험 기록이 어긋날 일이 없다.
- 계산은 `utils/myPageView.js`의 `collectionOf`(테스트 포함). 같은 그림은 한 장으로 센다. 대본이 없는 사건은 건너뛴다.
- B는 필요성이 생기면 낮은 우선도로 따로 진행하기로 하고 별도 이슈로 분리했다. 이슈 키: BE-83

### 고려한 제약 사항
- 모으는 대상은 사건 대본의 일러스트다. 캐릭터 모습(볼따구 · 재연 의상 등) 컬렉션은 이미지 자산 정리(WBS 7.6.8)가 끝나지 않아 제외했다.

### 추후 재검토가 필요하면
- 획득 시점 표시, 새로 얻음 표시, 사건 수 증가로 계산 비용이 커지는 경우, 캐릭터 모습 컬렉션을 넣는 경우에는 B(저장 방식)를 다시 검토한다.

## 3차 (PR #xxx) — 마이페이지 디자인 · 커피잔 입구

### 문제 / 배경
- 마이페이지에 디자인을 입혀야 했다. 처음 컨셉은 메인 책상의 "휴대폰 = 마이페이지"를 따라 핸드폰 화면이었다.
- 책상 오브제는 메뉴일 뿐이라 내용에 맞는 물건으로 바꿀 수 있다. 마이페이지 내용(내 성향 · 판결 성향 · 변화 흐름 · 만난 모습 · 체험한 사건 · 책갈피 캐릭터)에 맞는 오브제부터 다시 골랐다.

### 검토한 대안
- 입구 오브제: 개인 수첩(기록 · 책갈피와 잘 맞음, 서류철과 같은 종이 계열) / 커피잔(이미 책상에 있고 내로가 옆에 있음, 내용을 담을 그릇은 없음) / 책상 서랍 / 명패 / 휴대폰 유지(앱 UI 흉내로 "폰 안의 웹페이지"처럼 보이기 쉬움).
- 화면 구조(시안 3안): 탭 세 개(성향 · 기록 · 컬렉션) / 컬렉션이 주인공 / 프로필 + 항목 목록.
- 컬렉션 범위: 사건 일러스트만 / 캐릭터 역할 의상만 / 둘 다.

### 선택한 방법과 이유
- 입구는 **커피잔**(사용자 결정). 연출은 처음에 "잔이 들리고 가운데로 다가와 커피가 화면을 채운 뒤 페이드아웃"으로 만들었다가(10/17), **커다란 커피잔이 우상단에서 빠르게 날아와 서고, 책상이 마이페이지로 바뀌면 오른쪽으로 빠져나가는** 방식으로 바꿨다(사용자 요청, 잔 페이드아웃은 취소). 날아오는 도중(0.2초)에 마이페이지로 이동하고 본뜬 책상은 0.72초에 다 사라진다(손잡이는 날아오는 잔만 오른쪽). 휴대폰은 장식으로 남겼다. 잔 아래 책상은 이동 직전 메인 화면을 본뜬 층(`cloneNode`)이 덮고 있다가, 마이페이지로 넘어간 뒤 페이드아웃해 마이페이지로 부드럽게 바뀐다.
- 잔은 화면 크기로 미리 그려 두고 `transform`만 움직인다(책상 층은 `opacity`)(`utils/coffeeDive.js`). 연출 층은 body에 얹어 화면이 바뀌어도 끝까지 재생되고 스스로 걷히므로, 이전의 "커피 층 넘겨주기(`takeCoffee` · `fadeCoffee`)"는 없앴다. 움직임 줄이기 설정이면 연출 없이 바로 이동한다.
- 마이페이지 안에는 커피 요소를 잔 테두리 링(책갈피 캐릭터 둘레) 하나만 둔다(사용자 요청 "커피 요소 많지 않게").
- 구조는 **프로필 + 항목 목록**(사용자 결정). 항목 화면은 주소가 같고 `view`만 달라 뒤로 가기로 첫 화면에 돌아온다. 항목을 오갈 때 다시 불러오는 깜빡임을 줄이려고 마지막 응답을 두고 바로 그린 뒤 새로 받는다.
- 컬렉션은 **둘 다**. 8막 사진란의 역할 의상 모으기를 `castOf`(`utils/myPageView.js`)로 빼서 8막과 마이페이지가 함께 쓰고, 8막 "만난 모습"을 누르면 마이페이지 컬렉션으로 간다(Jira 완료 조건).
- 책갈피 캐릭터는 이 브라우저에만 저장한다(`utils/bookmarkCharacter.js`). 서버 저장은 수집 상태와 함께 BE-83에서 검토한다.

### 고려한 제약 사항
- 시안 고르기는 impeccable 절차(구조 3안 → 사용자 선택)를 따랐다. 색 · 글꼴은 기존 토큰(FE-17)을 그대로 쓰고, 마이페이지 잔 링은 역할 토큰 `--color-cup` · `--color-cup-rim`을 새로 두어 책상 그림 전용 색을 화면 CSS에서 직접 쓰지 않게 했다.
- FE-48(판결 체험 책갈피)은 아직 develop에 없어 책갈피 얼굴은 내로로 고정돼 있다. FE-48이 합쳐지면 `getBookmarkCharacter()`로 얼굴을 고르게 이어야 한다.

### 추후 재검토가 필요하면
- 실제 폰에서 커피잔 연출이 끊기는지 확인하지 못했다(헤드리스 캡처로만 확인). 끊기면 잔의 `will-change`와 손잡이 가상 요소부터 점검한다(커다란 잔 하나만 움직인다).
- FE-48 합류 후 진행 책갈피가 고른 캐릭터 얼굴을 쓰도록 연결한다.
