# BE-138 의사결정 기록

사건 등록 요청의 범죄 유형과 파이프라인이 판결문에서 읽은 범죄 유형의 일치 점검.

## 문제 / 배경

- 사건 등록 요청(A-14)의 `crimeType`(관리자가 고름, `case_import.crime_type`)은 파이프라인에 전달되지 않았다. 추출 모델(extract)은 판결문만 보고 유형을 스스로 골랐다(`case.json` `crimeType`).
- 적재(A-14-1)에서 두 값이 서로 다른 곳에 쓰였다.
  - 요청 값: 양형기준 선택(`CaseImportLoader.guidelineFor`).
  - 읽은 값: `legal_case.crime_type`, 배역 균형 계산(BE-125), 사전판단 형량 선택지, 판례 검색.
  - 두 값을 비교하는 곳이 없어, 다르면 한 사건 안에서 유형이 어긋난 채 적재됐다.
- 해송님이 등록을 1회 방식으로 정했고, 배역을 등록 요청의 `crimeType`으로 대본보다 먼저 정한다(BE-129). 그래서 두 값이 같다는 보장이 BE-129의 선행 조건이다. 근거: [BE-125](BE-125.md) "추후 재검토", Jira BE-129 결정 사항.

## 검토한 대안

- 대안 A: 요청 값으로 덮어쓴다(읽은 값을 무시). 늘 적재되지만, 관리자가 유형을 잘못 고르면(살인 사건을 사기로) 양형기준 · 판례 · 사전판단 선택지가 모두 틀린 채 들어간다. 틀린 것이 드러나지 않는다.
- 대안 B: 적재(A-14-1)에서만 비교해 다르면 거절한다. 백엔드만 고치면 되지만, 판결 생성 · 대본까지 다 돌린 뒤에야 막힌다(대본 한 건에 약 3만 토큰).
- 대안 C(채택): 요청 값을 파이프라인에 넘겨 **extract 직후** 비교하고, 다르면 그 자리에서 멈춘다. 적재에서도 한 번 더 비교한다.
- (C 안에서) 추출 모델에 요청 값을 힌트로 줄지: 주지 않는다. 힌트를 주면 모델이 판결문과 다른 요청 유형에 끌려가 어긋남을 숨길 수 있다. 판결문만 보고 고른 값과 비교해야 어긋남이 드러난다. 프롬프트도 바뀌지 않아 추출 프롬프트 버전(`extract-v8`)을 올리지 않는다.

## 선택한 방법과 이유

- **백엔드 → 파이프라인**: `PipelineJobRequest`에 `crimeType`을 더해 보낸다(`AdminCaseImportService.toPipelineRequest`). 모델에게는 보내지 않고 비교에만 쓴다.
- **파이프라인 서비스**: `POST /jobs`의 `crimeType`을 검사(다섯 값 중 하나, 아니면 400)해 설정 최상위 `crimeType`으로 넣는다.
- **파이프라인**: `stage_extract`가 끝나면 `case.json`의 `crimeType`과 비교한다. 다르면 `PipelineError`로 멈춘다. 메시지는 "범죄 유형이 다릅니다: 등록 요청은 FRAUD, 판결문에서 읽은 유형은 MURDER입니다. …"처럼 두 값을 모두 적는다. 이 메시지가 작업 실패 사유로 A-15 `message`에 그대로 실려 관리자가 본다. 읽은 유형은 단계 출력(`crimeType`)에도 남긴다. 요청에 유형이 없으면(로컬 실행) 비교하지 않는다.
  - 비교는 `require_crime_type`으로 뺐다. extract를 돌리지 않는 실행(이어서 돌려 끝난 extract를 건너뛰거나 `--from`으로 뒤 단계부터 시작)에서는 `run_pipeline`이 첫 단계 전에 같은 비교를 한다. 서비스(`POST /jobs`)는 작업마다 새 폴더에서 처음부터 돌아 이 경로가 생기지 않으므로 로컬 실행용이다(PR #356 리뷰). 로컬 `stage_load`는 백엔드 안전망을 거치지 않아서 README 한 줄로 넘기지 않고 막았다.
- **적재(안전망)**: `CaseImportLoader.load`가 같은 비교를 해서 다르면 422 `IMPORT_RESULT_INVALID`(`details[].field`: `case.crimeType`)로 거절한다. 트랜잭션 안이라 아무것도 쓰지 않는다. 비교는 `case.json` 내용으로 양형기준을 찾기(`guidelineFor`, 요청 값 사용) 전에 해서, 어긋난 사건이 다른 오류로 먼저 끝나 원인이 가려지지 않게 한다(PR #356 리뷰). 범죄 유형을 보내지 않던 때 만든 작업이나 로컬 실행 결과가 들어와도 어긋난 채 적재되지 않게 한다.
- 어느 쪽이 맞는지는 사람이 정한다. 관리자는 판결문을 확인해 맞는 유형으로 다시 등록한다.

## 고려한 제약 사항

- 파이프라인 서비스(`service/jobs.py`)는 파이프라인 모듈을 불러오지 않는다(단계 목록 `STAGES`도 따로 갖는다). 그래서 범죄 유형 목록이 세 곳(추출기 스키마 · `common.CRIME_TYPES` · 서비스)에 있다. 유형을 늘릴 때 한 곳만 고치면 깨지도록 테스트(`test_crime_types_match_extractor_and_service`)를 두었다. 백엔드 `CrimeType` enum도 함께 늘려야 한다.
- 파이프라인 실패는 지금 A-15에서 `errorCode: INTERNAL_ERROR`로 오고, 사유는 `message`에 있다. 범죄 유형 불일치만 따로 코드를 주지는 않았다. 화면은 `message`를 보여 준다.

## 추후 재검토가 필요하면

- 불일치가 잦으면(관리자가 자주 틀리거나 모델이 자주 틀림) 등록 화면에서 결과를 보고 고르게 하거나(예: 추출 결과의 유형을 제안), 파이프라인 실패에 전용 오류 코드를 두는 것을 검토한다.
- 실제 등록에서 얼마나 자주 멈추는지는 아직 재지 않았다.
