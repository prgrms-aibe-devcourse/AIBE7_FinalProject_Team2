# COMMON-50 의사결정 기록

AI 판결 파이프라인을 운영 서버에서 돌릴 수 있게 컨테이너로 만들고 배포 경로에 넣는 작업.
백엔드 쪽 구현(A-14/A-15 핸들러)은 BE-93으로 나눠 두었다.

## 문제 / 배경

`tools/ai-judgment`의 파이프라인(BE-31)은 **사람이 로컬에서 돌리는 오프라인 도구**다.
판결문을 넣으면 비식별화 → 재판부 판결 정리 → AI 판결 생성 → 회차 선택 → 가치관 축 분류까지 자동으로 하고,
마지막에 `load` 단계가 로컬 DB에 적재한다.

관리자가 화면에서 판결문을 넣고 사건을 등록하게 하려면(A-14) 백엔드가 이 파이프라인을 불러야 한다.
그런데 파이프라인은 Python이고 백엔드는 Spring Boot(Java)다. **둘을 어떻게 잇느냐**가 이 이슈의 문제다.

같이 풀어야 했던 조건이 셋 있었다.

1. 운영 서버는 EC2 **t3.small 한 대(2GB)**이고 base 구성이 이미 1.75GB를 할당한다.
2. 파이프라인에는 **판결문 원문**이 들어간다. 원문은 서비스 밖으로도, 공개 저장소로도 나가면 안 된다 (FR-5-3).
3. 파이프라인은 한 번 도는 데 수십 분 걸리고 외부 LLM API를 여러 번 부른다. HTTP 요청 하나로 기다릴 수 없다.

## 검토한 대안

멘토님께 여쭤본 세 가지 그대로다.

### 대안 A — 백엔드가 Python을 서브프로세스로 직접 실행

- 장점: 컨테이너가 늘지 않는다. 메모리에 가장 유리하다.
- 단점: **백엔드 이미지에 Python 런타임과 파이프라인 의존성을 다 넣어야 한다.** 지금 백엔드 이미지는 JRE만 있는
  얇은 이미지인데 여기에 Python 3.12 + pip 패키지(anthropic · pypdf · cryptography)가 들어간다.
  빌드 시간 · 이미지 크기 · 취약점 점검 대상이 모두 백엔드 쪽으로 번진다.
- 단점: 파이프라인이 메모리를 많이 쓰거나 죽으면 **같은 컨테이너의 백엔드가 같이 영향을 받는다.**
  OOM Killer가 JVM을 고를 수도 있다. 관리자 전용 기능 때문에 사용자 서비스가 내려가는 건 받아들이기 어렵다.
- 단점: 경계가 없어서 "파이프라인이 어디까지 할 수 있는가"를 코드로 막기 어렵다 (예: `load` 단계 차단).

### 대안 B — 같은 Compose에 내부 전용 컨테이너로 띄우고 HTTP로 부른다 ← **선택**

- 장점: 파이프라인은 지금 모습 그대로 둔다. 바꾼 코드가 없다(서비스 층만 새로 썼다).
- 장점: 런타임 · 의존성 · 메모리 상한(`mem_limit`)이 백엔드와 분리된다. 파이프라인이 죽어도 백엔드는 멀쩡하다.
- 장점: 포트를 호스트로 열지 않으면 **백엔드만 부를 수 있다**는 경계가 인프라 차원에서 생긴다.
- 단점: 컨테이너가 하나 늘어 메모리를 더 쓴다 → 아래 "고려한 제약 사항"에서 다룬다.
- 단점: 프로세스 사이 통신(HTTP)과 작업 상태 관리가 새로 필요하다 → 이번에 만든 것이 그 부분이다.

### 대안 C — 파이프라인을 Java로 이식

- 장점: 언어가 하나가 된다. 배포 · 테스트 · 모니터링이 단순해진다.
- 단점: **양이 너무 많다.** 파이프라인 도구는 약 6,100줄에 단위 테스트 393개다. 프롬프트 · 검증 · 비식별화 ·
  RAG · 회차 선택 · 가치관 축까지 전부 옮겨야 하고, 옮기는 동안 두 벌을 같이 유지해야 한다.
- 단점: 옮겨서 얻는 것이 **운영 편의뿐**이다. 기능은 똑같다. 남은 일정에 쓸 자리가 아니다.
- 단점: `case-extractor`는 Claude SDK · pypdf에 기대고 있어 그대로 옮기기도 어렵다.

## 선택한 방법과 이유

**대안 B.** 파이프라인을 건드리지 않고 HTTP 껍데기만 덧씌워 내부 전용 컨테이너로 띄운다.

결정적인 이유는 둘이다.

- **관리자 전용 기능 때문에 사용자 서비스가 위태로워지면 안 된다.** A가 가진 "같은 프로세스 공간" 문제는
  메모리가 빠듯한 t3.small에서 특히 위험하다. B는 상한과 경계를 인프라로 긋는다.
- **파이프라인을 손대지 않는다.** 이미 393개 테스트로 받쳐 둔 코드를 그대로 쓰는 쪽이, 옮기거나(C)
  백엔드 이미지에 섞는(A) 쪽보다 틀릴 여지가 적다.

### 세부 결정

#### 1. 작업은 서브프로세스로 돌리고, 상태의 출처는 파이프라인의 `state.json`으로 둔다

파이프라인을 FastAPI 프로세스 안에서 직접 부르는 방법(`import pipeline`)도 됐지만 서브프로세스로 띄운다.

- 파이프라인은 이미 `out/pipeline/<name>/state.json`에 단계별 상태를 쓰고, 그걸로 **이어 하기**를 지원한다(BE-31).
  서비스가 진행 상황을 따로 세면 출처가 둘이 되고 반드시 어긋난다. 그래서 서비스는 그 파일을 **읽기만** 한다.
- 작업이 죽어도 서비스는 살아 있다. 컨테이너가 재시작돼도 어디까지 갔는지 남는다(볼륨).
- 서비스가 가진 상태는 PID 하나뿐이고, 그것도 "살아 있는지"를 보는 용도다.

서브프로세스를 쓰기로 하면서 한 가지를 같이 정해야 했다. **끝난 자식을 거둬 가는(reap) 책임**이다.
처음에는 PID만 들고 `os.kill(pid, 0)`으로 생사를 봤는데, 이러면 끝난 자식이 좀비로 남아 그 검사가 계속 성공한다
— 작업 하나가 끝난 뒤로 새 작업이 영원히 `409`가 되고 지우지도 못했다(컨테이너로 돌려 보다 발견).
그래서 이 프로세스가 띄운 작업은 `Popen` 핸들을 들고 `poll()`로 판단한다(이 호출이 자식을 거둬 간다).
서비스를 다시 띄운 뒤라 더 이상 자식이 아닌 경우에만 PID로 보고, 이때는 init이 거둬 가므로 좀비가 남지 않는다.
끝난 사실은 메타에도 한 번 적어 둔다 — 그래야 핸들이 없는 상황에서도 끝난 작업을 "도는 중"으로 보지 않는다.

#### 2. 한 번에 한 작업만 돌린다

외부 LLM 호출 한도와 메모리 때문이다. 도는 작업이 있는데 또 시작하면 `409`로 거절하고,
백엔드는 이걸 A-14의 `IMPORT_IN_PROGRESS`로 내려준다.

#### 3. 서비스 자체에는 인증을 두지 않는다

포트를 호스트로 열지 않고 같은 Compose 네트워크의 백엔드만 부른다. 관리자 인증 · CSRF는 백엔드의 관리자
체인(API 명세 8-1)이 이미 한다. 여기에 또 두면 **관리할 비밀값이 하나 더 늘 뿐** 실제로 막히는 것이 없다.

다만 이건 "밖에서 닿을 수 없다"는 전제에 기댄 결정이다. 전제가 깨지면 인증이 필요하다 → 아래 "추후 재검토".

#### 4. `load` 단계는 요청으로도 켤 수 없게 막는다

`load`는 운영 DB에 직접 쓰는 단계다. 적재는 **관리자가 화면에서 검수한 뒤 백엔드가** 한다 — 그게 이 기능의 핵심이다.
그래서 기본으로 끄는 것으로는 부족하다고 보고, 요청의 `stages`로 켜려 해도 되돌려 끈다
(`jobs.py`의 `NEVER_ENABLED_STAGES`, 테스트로 고정).

`rag` · `contamination`도 기본은 끄지만 이쪽은 요청으로 켤 수 있다. 끄는 이유가 "위험해서"가 아니라
"컨테이너에서 못 쓰거나(rag는 로컬 DB를 요구한다) 비싸서"이기 때문이다.

#### 5. 결과에 판결문 원문을 넣지 않는다

`GET /jobs/{id}/result`는 사건 · 재판부 판결 · AI 판결 · 가치관 축만 돌려준다. 원문은 작업 폴더(볼륨)에만 있고
A-7로만 본다 (FR-5-3). 검수가 끝나면 백엔드가 `DELETE /jobs/{id}`로 작업 폴더째 지운다.
원문이 이미지에 들어가지 않도록 `.dockerignore`로 `cases/` · `out/`도 뺐다.

#### 6. 운영에는 **opt-in 오버레이**로 넣는다

`docker-compose.prod.yml`에 바로 넣지 않고, `.env`의 `PIPELINE_SERVICE=1`일 때만 겹쳐 쓰는 별도 파일로 뒀다
(`docker-compose.real-seed.yml` · `docker-compose.monitoring-agent.yml`과 같은 방식).

메모리 때문이다 → "고려한 제약 사항". 값을 넣지 않은 서버는 지금과 완전히 같게 동작한다.

#### 7. 파이프라인이 실패해도 배포를 되돌리지 않는다

`deploy.sh`는 `web` · `backend`가 확인된 **뒤에** 파이프라인을 올리고, 실패하면 경고만 남긴다.
관리자 전용 기능 하나 때문에 정상인 사용자 서비스 배포가 되돌려지면 손해가 더 크다.
이미지를 못 받는 경우도 마찬가지로 경고다 — 아직 그 태그가 GHCR에 없을 수 있기 때문이다.

대신 **조용히 넘어가지는 않게** 했다. 모니터링 오버레이에서 겪은 "빠뜨리면 조용히 끊긴다"(COMMON-43)와 같은 문제라,
배포 로그에 `⚠` 줄을 남기고 `deploy/README.md`에 증상별 대응을 적었다.

#### 8. 이미지는 오버레이를 켜지 않은 지금도 항상 빌드 · 업로드한다

켜는 순간 그 태그가 GHCR에 있어야 `deploy.sh`가 받아 올릴 수 있다. CI에서는 스택에 띄우지 않는 대신
이미지만 두 가지로 확인한다 — 서비스 단위 테스트를 **이미지 안에서** 돌리고, `uvicorn`이 떠서 `/health`가 200인지 본다.
파이프라인을 실제로 돌리지는 않는다 (LLM 호출 비용 · CI에 키가 없다).

## 고려한 제약 사항

### 메모리 (이번 결정에서 가장 크게 작용한 조건)

t3.small은 2GB인데 base 구성이 이미 1.75GB를 할당한다(backend 1g · postgres 512m · redis 256m).
실측 여유는 약 250MB이고, 모니터링 에이전트(COMMON-43)를 켠 서버는 그중 100MB를 이미 쓴다.

파이프라인 컨테이너는 쉴 때 **약 32MB**(로컬 실측, 10/21)지만 `extract`(PDF 읽기 · 비식별화) 단계에서 더 쓴다.
유휴 사용량 자체는 작아도, 문제가 되는 건 작업이 도는 동안의 최대치와 그때 백엔드가 밀리는지다.
그래서 **기능은 다 만들어 두되 운영에서 켜는 것은 7.1.2 RDS 전환 뒤를 전제로 한다.**
전환하면 `postgres` 컨테이너 512m이 통째로 빠진다. `mem_limit: 512m`은 상한이지 예약이 아니고,
백엔드를 밀어내지 못하게 막는 용도다.

이 판단은 모니터링을 서버 밖으로 옮긴 COMMON-43과 같은 근거를 쓴다.

### 무료 등급 키를 쓰면 안 되는 단계가 있다

판결문 원문이 나가는 `extract` · `court`에는 유료 등급 키만 쓴다 (무료 등급은 입력을 제품 개선에 쓸 수 있다).
`.env.example` · 서비스 README에 적어 뒀다. 키는 이미지에 넣지 않고 실행할 때 환경변수로만 넘긴다.

### 공개 저장소

이 문서와 `deploy/` · `tools/`는 공개 저장소에 있다. 실제 사건 정보 · 비밀값 · 서버 접속 정보는 적지 않았다.
`cases/`(실제 사건 입력)와 `out/`(생성 결과)는 `.gitignore`에 이어 `.dockerignore`에도 넣어 이미지에서도 뺐다.

### 기존 배포 흐름을 바꾸지 않는다

자동 배포(`cd-agent.sh` → `deploy.sh`)는 2분마다 도는 운영 경로다. 여기에 손대는 변경은 실패했을 때
사용자 서비스에 바로 영향을 준다. 그래서 플래그를 켜지 않은 서버에서는 분기 자체를 타지 않게 하고,
켠 서버에서도 기존 `web` · `backend` 경로의 성공 조건을 하나도 바꾸지 않았다.

## 추후 재검토가 필요하면

- **운영에서 켜는 시점**: 7.1.2 RDS 전환 뒤. 켤 때 `docker stats`로 실제 사용량을 보고,
  `extract` 단계가 도는 동안 백엔드가 밀리지 않는지 확인한다. 밀리면 `backend`의 `mem_limit`을 먼저 조정한다.
- **인증**: 지금은 "밖에서 닿을 수 없다"는 전제로 인증을 두지 않았다. 파이프라인을 다른 호스트로 옮기거나
  포트를 열게 되면 그 전제가 깨진다. 그때는 내부 토큰(백엔드만 아는 공유 비밀) 정도를 붙인다.
- **작업 폴더 정리**: 지금은 백엔드가 `DELETE /jobs/{id}`로 지우는 것에 기댄다. 백엔드가 지우지 못하고 끝난
  작업이 쌓이면 볼륨이 찬다. 운영에서 켜 본 뒤 필요하면 "N일 지난 작업 자동 삭제"를 서비스에 넣는다.
- **`rag` 단계**: 컨테이너에서는 DB가 로컬이 아니라 못 쓴다(`pipeline.py`의 `_is_local_host` 제한).
  RAG를 서비스 안에서도 쓰려면 그 제한을 어떻게 풀지부터 다시 정해야 한다
  (지금은 "RAG가 안 되면 사건 입력의 references로 진행"하는 기존 정책을 따른다, 요구사항 v5.5).
- **여러 작업 동시 실행**: 지금은 하나씩이다. 등록할 사건이 몰려서 불편해지면 큐를 두는 쪽을 검토한다.
  다만 외부 LLM 호출 한도와 메모리가 먼저 막는다.
