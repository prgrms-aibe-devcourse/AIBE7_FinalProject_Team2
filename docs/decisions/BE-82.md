# BE-82 의사결정 기록

## 문제 / 배경
- 판결 체험이 8막 → 6막으로 바뀌었다(FE-48). 화면에 보이는 막 이름 · 번호는 바뀌었지만, 화면 주소 · 화면 ID는 8막 시절 그대로라 막 번호와 어긋났다(1 · 2막이 한 주소, 4막은 거쳐 가는 주소). 정리 화면(`/summary`)이 남는 주소가 됐다.
- 리뷰 페이지(FE-55, 사건별 후기 · 독자 엽서)가 들어갈 주소가 필요했다(`/opinion` 임시 사용).
- 프론트 제안(김해송, 10/20 BE-82 댓글)을 기준으로 주소 · 화면 ID · API 명세 1-6을 정리한다. 서버 진행 상태 값 · API 경로는 바꾸지 않는다.

## 결정
### 화면 주소 (모두 `/cases/{caseId}` 아래)
| 막 | 옛 주소 | 새 주소 | 서버 상태 (변경 없음) |
| --- | --- | --- | --- |
| 1막 첫인상 | `/start` | `/impression` | `STARTED` → `PRE_JUDGED` |
| 2막 재판 | `/review` | `/trial` | `PRE_JUDGED` · `REVIEWING` → `REVIEWED` |
| (없앰) 정리 | `/summary` | → 리뷰 페이지 `/letters` | — |
| 3막 내 판결 | `/verdict` | `/verdict` | `REVIEWED` → `VERDICT_CONFIRMED` |
| 4막 AI 판결 | `/result/ai` | `/ai-verdict` | `VERDICT_CONFIRMED` → `AI_REVEALED` |
| 5막 실제 판결 | `/result/court` | `/court-verdict` | `AI_REVEALED` |
| 6막 세 판결 비교 | `/result/compare` | `/compare` | `COMPLETED` |
| 리뷰 페이지 | `/summary` · `/opinion` | `/letters` | `COMPLETED`만 |

- `REVIEWED`가 보내는 화면: 정리 화면 → 3막 `/verdict`
- `/opinion`은 없앤다. 옛 주소 redirect(공유 링크 · 북마크)는 FE-58에서 넣는다.

### 화면 ID 매핑 (S-05 ~ S-09 뜻이 바뀜)
| 화면 | 옛 ID | 새 ID |
| --- | --- | --- |
| 1막 첫인상 (사건 개요 · 사전 판단) | S-03 | S-03 |
| 2막 재판 (사건 정보 확인) | S-04 | S-04 |
| 정리 (판결 전 최종 정리) | S-05 | 없앰 |
| 3막 내 판결 (판결 입력) | S-06 (S-06a ~ d) | **S-05** (S-05a ~ d) |
| 4막 AI 판결 | S-07 | **S-06** |
| 5막 실제 판결 | S-08 | **S-07** |
| 6막 세 판결 비교 | S-09 | **S-08** |
| 리뷰 페이지 | — | **S-09** (새로 추가) |

- 이 결정 전의 PR · 이슈 · 문서 작성 이력은 옛 ID를 쓴다. 읽을 때 이 표로 바꿔 읽는다. 작성 이력 행은 고치지 않았다.

### 범위에서 뺀 것
- 대본 키(1 ~ 8) 정리: 화면에 보이는 막 이름 · 번호는 FE-48에서 이미 바뀌었고, 대본 키는 사용자에게 보이지 않는 내부 값이라 대본 · 목 데이터 · 테스트까지 움직이는 비용이 더 크다. **FE-59**(우선순위 낮음, FE-58 머지 이후)로 분리했다.
- 사건별 후기(독자 엽서): 이번에는 주소(`/letters`)와 노출 조건(`COMPLETED`만, 체험 전에는 숨김)만 정한다. 리뷰 페이지는 **확장** 화면으로 둔다. 후기 API · DB, 신고 · 숨김 등 운영 기준은 후속 이슈로 분리한다. 그 전까지 화면은 목 데이터로만 동작하고(FE-55), `COMPLETED` 조건은 화면이 지킨다. 후기 API를 만들 때 서버도 같은 조건을 확인한다.

## 검토한 대안
- 화면 ID: (A) 막 순서대로 재배치 / (B) ID는 그대로 두고 비는 S-05(정리)만 리뷰 페이지로 재사용
- 대본 키: (A) 이번에 함께 정리 / (B) 후속 이슈로 분리
- 후기: (A) API · DB까지 이번에 구현 / (B) 주소 · 노출 조건만 정하고 후속 / (C) 보류

## 선택한 방법과 이유
- 화면 ID는 (A). 제안자(프론트)의 안이고, 막 번호 · 주소 · 화면 ID가 한 순서로 맞아 이후 문서를 읽기 쉽다. (B)는 고칠 곳이 적지만 막 순서와 ID 순서가 계속 어긋난다. 재배치로 생기는 문서 · 주석 수정은 FE-58 계획에 이미 들어 있었다.
- 대본 키는 (B), 후기는 (B). 위 "범위에서 뺀 것"과 같다. 이번 주 BE-62 · M2(10/23) 일정을 우선했다.

## 역할 나누기
| 작업 | 담당 |
| --- | --- |
| 이 결정 기록, API 명세(1-6 포함) · 정보 구조(IA) 화면 ID · 주소, 백엔드 `backend/src/main/java` 주석의 화면 ID | BE-82 (정민석) |
| 그 밖의 `docs/` 문서 · 프론트 코드 주석의 ID · 주소 참조, 라우트 · redirect · `screenByStatus` · 정리 화면 정리 | FE-58 (김해송) |
| 대본 키 1 ~ 8 → 6막 체계 | FE-59 (김해송) |

- API 명세 · IA는 1-6 표 · 화면 목록 표만이 아니라 **파일 전체**의 화면 ID를 BE-82에서 바꿨다. 같은 파일을 두 사람이 나눠 고치면 충돌 · 누락이 생기기 때문이다.
- `backend/src/test`의 화면 ID 주석 2곳(`PreJudgmentApiTest` · `ComparisonApiTest`의 S-09 → S-08)도 이번에 함께 바꿨다(PR #214 리뷰). 백엔드(`backend/src`)에서 옛 뜻의 S-05 ~ S-09가 남은 곳은 `V2__create_case_content.sql` 주석("사건 정보 섹션 (S-04 · S-05)")뿐이다. 이미 적용된 마이그레이션은 내용을 바꾸면 Flyway 체크섬이 달라져 기동이 실패하므로 고치지 않는다(ERD 7장 규칙).
- PR #214 리뷰 시점에 옛 ID가 남아 있던 그 밖의 문서는 위 표대로 **FE-58**에서 고친다: `docs/character/character-asset-architecture.md` · `character-image-checklist.md` · `character-profile-worldview.md`, `docs/cases/sample-virtual-murder.md`. 그전까지 이 문서들의 S-05 ~ S-09는 옛 뜻이다(위 매핑 표로 바꿔 읽는다).

## 고려한 제약 사항
- 서버 진행 상태 값 · API 경로 · 응답 형식은 바꾸지 않는다. 그래서 백엔드는 주석만 바뀌고 동작 변경은 없다.
- API 6의 `summary`(핵심 사실 요약, `case_section` `SUMMARY`)는 보여 주던 정리 화면이 없어졌지만 응답에는 그대로 둔다(형식 변경 없음). 화면에서 쓸지는 FE-58에서 정한다.

## 추후 재검토가 필요하면
- 후기 저장 기능을 만들 때 API 명세 1-6의 S-09 허용 조건(`COMPLETED`)과 IA S-09 절을 함께 고친다.
- `summary` 필드를 어느 화면도 쓰지 않기로 정하면, API 6 응답과 `SectionStage.SUMMARY` 데이터를 정리할지 별도 이슈로 검토한다.
