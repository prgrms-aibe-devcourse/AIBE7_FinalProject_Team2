# BE-153 의사결정 기록 (PR #390)

대본 블록 문장 수정(A-13-21)의 길이 규칙을 말하는 대사 자리에만 건다. FE-148 PR #388 리뷰(해송님 1부 1번)에서 나왔다.

## 문제 / 배경

- A-13-21은 고칠 수 있는 모든 문자열 자리에 대사 길이 규칙(100자 · 2줄)을 걸었다(`CaseScriptTextRequest.lengthViolation` — A-13-13 대사 수정과 같은 규칙을 그대로 빌림).
- 파이프라인 검수(`script_review.py`)는 `LINE_TOO_LONG`을 **말하는 대사**(`SPOKEN_KINDS`: guide · narrator · prosecutor · defense)에만 건다. 설계도(U0) · U2 카드 글 · 신문 답은 화면 대사가 아니라 길이 제한이 없다.
- 그래서 카드 문단이나 설계도 질문을 정당하게 고쳐도 400으로 막혔다. 관리자 화면(FE-148)도 같은 규칙을 모든 자리에 걸고 있었다.

## 검토한 대안

- **모든 자리에서 규칙을 빼기**: 말하는 대사가 화면 말풍선을 넘치게 된다. 파이프라인이 오류로 보는 값을 사람이 넣을 수 있다.
- **검수 결과에 `LINE_TOO_LONG`이 붙은 자리에만 걸기**: 그 자리를 고치면 결과가 지워지고, 처음부터 결과가 없던 대사 자리는 규칙 없이 고칠 수 있다.
- **자리 종류로 나누기 (택함)**: 말하는 대사 자리 목록(`spokenPaths`, `*`는 배열 순번)을 공용 계약 파일에 두고, 파이썬 · 자바 · 프론트 테스트가 같은 파일을 읽는다. 파이썬 테스트는 그 목록이 `unit_lines`의 말하는 대사 자리와 같은지 본다(정본은 파이썬). 연동 표 · 신문 답 규칙과 같은 방식이다(BE-126).

## 선택한 방법과 이유

- `ScriptUnit`이 블록마다 `spokenPaths`를 갖고 `isSpoken(path)`로 판단한다. 컨트롤러는 그 자리일 때만 길이 규칙을 건다. 나머지는 Bean Validation(빈 값 · 500자)만 막는다.
- U3는 계약 파일에 두지 않는다. 대사 수정(A-13-13)이 늘 대사로 보고, A-13-21은 U3를 받지 않는다.
- `unit_lines`는 줄 수를 앞에서부터 잘라 본다(예: U1 다섯 줄). 계약 목록의 `*`는 순번 제한이 없지만, 그 뒤 줄은 화면에 나오지 않아 길이 규칙을 걸어도 해가 없다.

## 고려한 제약 사항

- 계약 파일은 이미 파이썬 · 자바 테스트가 읽는다. 키 하나를 더했고 설명은 `spokenPathsNote`에 둔다(JSON에 주석을 쓸 수 없다).
- 의미 검사(금지어 · 형량 문형 · 말투)는 여전히 다시 돌리지 않는다 — BE-154에서 다룬다.

## PR #390 리뷰 반영

해송님 리뷰(1부 코드 · 2부 파이프라인 설계자 관점).

- **규칙을 서비스로 (1부 1번)**: 길이 판단을 컨트롤러에서 `AdminCaseScriptService.editText`로 옮겼다. 이 서비스를 부르는 다른 경로가 생겨도 우회되지 않는다.
- **검사 순서 (1부 3번)**: 블록 · 자리 존재(404)를 먼저 보고 길이(400)를 나중에 본다(`CaseScript.hasText` — 값을 바꾸지 않고 `editText`가 고칠 수 있는 자리인지 확인). 명세 거절 표와 순서가 같다.
- **테스트 범위 (1부 2번)**: U1 `/lines/n` · U4 `/defense`의 101자 400, 정확히 100자(50자 두 줄) 200, 없는 자리에 긴 글은 404를 더했다.
- **500자 근거 (1부 4번)**: 대사 수정(A-13-13)과 같은 Bean Validation 상한이다. 파이프라인에 상한이 없는 자리(설계도 · 카드)도 터무니없는 본문을 먼저 끊으려는 값이고, 칸(jsonb)이나 화면이 500자를 요구하는 것은 아니다.
- **계약을 자리별 종류로 (2부 1번)**: `spokenPaths`(대사인가) 대신 `pathKinds`(자리 → guide · narrator · prosecutor · defense · design · card)와 `spokenKinds`를 계약에 두었다. 파이프라인 검사 규칙이 종류마다 달라(길이 · 해요체 · 되풀이), 고친 문장 재검사(BE-154)도 같은 표를 쓰게 되면 계약 파일과 세 언어 테스트를 다시 바꾸지 않는다. 카드처럼 이름이 바뀌는 자리는 `{key}`(이름 토큰 하나)로 적는다. `spokenPaths`는 남기되 `pathKinds`에서 파생한 값으로 두고 파이썬 테스트가 일치를 본다 — 이미 develop에 들어간 관리자 화면(#388)이 이 키를 읽는다.
- **U0 앞 두 질문 (2부 2번)**: 안 (b)로 갔다. U2 신문 질문은 모델이 U0를 보고 다시 쓰는 값이라, U0를 길게 고쳐도 막지 않는다. 다시 만들 때 100자 안으로 줄여 써서 질문 불일치 경고(`ISSUE_QUESTION_MISMATCH`, 경고라 공개는 막지 않음)가 남을 수 있다는 점을 계약 설명에 적었다. 화면 안내는 FE-148 2차.
- **계약 테스트 표본 (2부 3번)**: 표본에서 나온 종류가 여섯 가지를 모두 담는지 단언한다. 파이프라인이 새 종류를 더하면 테스트가 깨져 계약을 다시 보게 된다. 한 자리에 종류가 둘이면 실패한다.
- **순번 상한 (2부 4번)**: 계약 설명(`pathKindsNote`)에 적었다.
- **목의 U2 `plea` 모양 (2부 5번)**: 관리자 화면 목(develop)이 문자열로 두고 있다 — FE-148 2차에서 리스트로 고친다.
