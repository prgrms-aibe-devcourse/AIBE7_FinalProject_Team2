# BE-95 의사결정 기록

> 근거: BE-94(`OriginVerificationFilter`, `docs/decisions/BE-94.md` "추후 재검토") · BE-62(`forward-headers-strategy: native` · Nginx forwarded 헤더 적용, PR #229) · BE-95 완료 조건 ("HTTPS 환경에서 재발급 · 로그아웃 정상 동작 확인")

## 문제 / 배경

- BE-62(PR #229)에서 `server.forward-headers-strategy: native`와 Nginx의 `X-Forwarded-Proto` · `Host` · `Port` 전달은 코드로 확인했다. 남은 완료 조건 하나 — "운영(또는 동일 TLS 종료 구성 스테이징)에서 실제 HTTPS로 재발급 · 로그아웃을 호출해 `OriginVerificationFilter`가 정상 통과시키는지" — 는 코드 리뷰로는 볼 수 없다. 배포된 환경에 실제로 요청을 보내야 한다.
- 이번 작업은 그 검증을 반복 실행할 수 있는 스크립트(`deploy/verify-origin-headers.sh`)를 만들어 둔다. 최초 검증은 승호님이 운영에서 직접 실행했고(BE-95 Jira 댓글, 결과 모두 통과), 앞으로는 운영 서버 · 배포 파이프라인 담당(jms0326, BE-58 · BE-60)이 배포마다 실행한다.

## 검토한 대안

### 1. 검증에 실제 로그인(카카오 OAuth → NLNB_RT 쿠키)이 필요한가
- A. 필요: 실제 로그인 플로우를 거쳐 쿠키를 받은 뒤 재발급 · 로그아웃을 호출해 200/204를 확인한다. 가장 확실하지만, 스크립트 혼자서는 카카오 로그인을 자동화할 수 없어 사람이 브라우저로 쿠키를 받아 스크립트에 넘겨줘야 한다 — 매번 수작업이 든다.
- B(선택). **불필요.** `OriginVerificationFilter`는 보호 대상 경로면 쿠키를 읽기 전에 Origin부터 검사한다(필터 코드 순서, `doFilterInternal`). 그래서 쿠키 없이 호출해도 상태 코드만으로 "필터를 통과했는지"를 구분할 수 있다.
  - 필터를 통과했다면: 로그아웃은 쿠키가 없어도 204(멱등, `AuthController.logout`), 재발급은 401 `TOKEN_INVALID`(쿠키 없음, `TokenException.invalid`).
  - 필터가 막았다면: 403 `FORBIDDEN`(`OriginVerificationFilter` → `JsonSecurityErrorHandler`) — 이 이슈가 막으려던 장애(재발급 · 로그아웃이 전부 막히는 상황)가 그대로 재현된 것이다.
  - 로그인 없이, 반복 실행 가능한 스크립트로 만들 수 있어 배포마다 재사용할 수 있다.

### 2. 거짓 양성(필터가 꺼져서 전부 통과) 배제
- A. 정상 Origin 검사만 한다: 403이 안 나오면 통과로 본다. 그러나 필터 자체가 어떤 이유로 비활성화돼 있어도(예: `SecurityConfig`에서 빠짐) 같은 결과(204/401)가 나와, "설정이 맞아서 통과"와 "필터가 꺼져서 통과"를 구분하지 못한다.
- B(선택). **대조군을 추가한다.** scheme이 다른(`http://`) Origin으로 같은 요청을 보내 403이 나오는지 확인한다. 이게 403이 아니면 필터가 아예 동작하지 않는 것이므로, 정상 Origin 검사의 "통과"가 의미 없다는 걸 같이 알 수 있다.

### 3. 위치 · 형식
- A. Jira 댓글에 curl 커맨드만 적어 둔다.
- B(선택). **`deploy/smoke-test.sh`와 같은 자리에 `deploy/verify-origin-headers.sh`로 만든다.** 배포 직후 체크리스트(`deploy/README.md` "확인")에 `smoke-test.sh` 바로 다음 줄로 넣어, 다음 배포 때도 재사용하기 쉽게 했다. BE-95는 배포 "전" 1회성 확인으로 시작했지만, scheme 관련 설정은 Nginx 교체 · Tomcat 설정 변경이 있을 때마다 다시 깨질 수 있어 스크립트로 남겨 배포마다 반복 실행하는 쪽이 낫다고 판단했다. 이 스크립트는 BASE_URL에 지금 떠 있는 배포만 확인하므로, 운영에서는 배포 "직후"마다, 동일 TLS 종료 구성의 스테이징이 있으면 배포 "전"에도 미리 돌릴 수 있다(coderabbitai PR #316 리뷰).

### 4. 대조군 Origin을 http 주소에도 똑같이 만들 수 있는가
- A. scheme만 단순 치환(`https:` → `http:`)한다. 입력이 처음부터 `http://`라면 바꿀 게 없어 대조군이 정상 Origin과 같아지고, TLS 없는 환경에서는 정상 검사와 대조군이 둘 다 통과해 "필터가 꺼져서 통과하는 거짓 양성"을 바로 잡아내지 못한다(jms0326 PR #316 리뷰, 실제 버그).
- B(선택). **`https://` 주소만 받도록 스크립트 맨 앞에서 거른다.** 이 스크립트는 애초에 "TLS 종료(Nginx) 뒤에서 scheme이 올바르게 전달되는지"를 확인하는 용도라, http 주소를 받을 이유가 없다. 입력을 `https://`로 강제하면 대조군은 항상 `http://`로 바뀌어 정상 Origin과 달라짐이 보장된다.

## 선택한 방법과 이유

- `deploy/verify-origin-headers.sh <배포 도메인>` 하나로: (1) 정상 Origin + 쿠키 없음 → 로그아웃 204 · 재발급 401 기대, (2) scheme이 다른 Origin(대조군) → 403 기대, 총 3번의 요청으로 로그인 없이 검증한다.
- `smoke-test.sh`와 같은 스타일(상태 코드 기반 pass/fail, 실패해도 나머지 검사 계속, 전체 실패 개수를 종료 코드로)을 따라 팀이 읽기 쉽게 했다.

## 고려한 제약 사항

- 스크립트의 응답 처리 로직은 로컬 더미 서버로 확인했고, 실제 배포 환경 실행 결과는 배포 담당이 확인한다(최초 1회는 승호님, 이후는 jms0326).

## 추후 재검토가 필요하면

- Nginx 설정이나 Tomcat `internal-proxies` 범위가 바뀌면 이 스크립트를 CI 배포 파이프라인(`deploy.sh` 또는 `deploy-images.yml`)에 자동으로 끼워 넣는 것도 고려할 수 있다. 지금은 배포 전 1회 수동 실행으로 충분하다고 보고 범위에 넣지 않았다.
