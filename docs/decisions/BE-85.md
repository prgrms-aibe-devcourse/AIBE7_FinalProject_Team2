# BE-85 의사결정 기록

## 문제 / 배경

COMMON-40(generate 모델 고정)은 여러 사건 × 여러 모델 × 다회차 테스트 결과를 근거로 모델 하나를 고른다. 그런데 `compare.py`는 사건 1개(`batch_dir` 1개) 단위로만 비교표를 만들어서, 여러 사건을 비교하려면 사람이 표 여러 개를 눈으로 합산해야 했다. 또 징역 형량은 최소·중앙값·최대만 있어 "같은 모델이 매번 비슷한 형량을 내는가"(안정성)를 숫자로 볼 수 없었다.

## 검토한 대안

### 1. 여러 사건을 어떻게 입력받을 것인가

- **대안 A — 새 서브커맨드(`compare.py aggregate <dir1> <dir2> ...`)를 만든다.** `generate.py`가 `run`/`import` 서브커맨드를 쓰는 것과 일관된다. 다만 기존 사용자가 외워 둔 `compare.py <batch_dir>` 형태와 완전히 달라져, 단일 사건 비교와 사건 간 집계가 서로 다른 명령처럼 느껴진다.
- **대안 B(선택) — 기존 위치 인자 `batch_dir`를 `nargs="+"`로 바꿔, 1개면 지금과 똑같이 동작하고 여러 개면 집계 모드로 전환한다.** 기존 호출(`compare.py out/runs/case ...`)은 글자 하나 안 바꿔도 그대로 동작해 하위 호환이 완전하다. "여러 사건을 보고 싶으면 폴더를 여러 개 나열한다"는 것도 직관적이다.

### 2. 판단 요소 관련 칸(요소 방향 일관성 · 전체 다수 의견 일치율)을 집계에도 넣을 것인가

- **대안 A — 사건마다 `factorId`가 다르니, 같은 번호끼리는 같은 의미라고 보고 그대로 합친다.** 틀린 가정이다. 사건마다 판단 요소 자체가 다르므로(예: 사건 1의 "3번 요소"와 사건 2의 "3번 요소"는 전혀 다른 사실관계) 숫자를 합치면 의미 없는 값이 나온다.
- **대안 B(선택) — 집계표에서는 요소 일관성 · 전체 다수 의견 칸 자체를 뺀다.** 사건별 비교표(`compare.py <사건 1개>`)에는 이미 있으니 필요하면 거기서 본다고 안내한다.

### 3. "사건 간 편차"를 어떤 지표로 볼 것인가

- **대안 A — 모든 사건의 형량을 그대로 풀어서(pool) 표준편차 하나만 본다.** "선택한 방법과 이유"의 3번(징역 표준편차 · IQR)과 사실상 같은 값이 되어, 사건 자체의 난이도 차이(사건이 다르면 형량 자체가 다른 게 당연함)와 모델의 회차 간 변동(같은 사건에서 매번 다른 답을 내는 것)이 뒤섞인다.
- **대안 B(선택) — 사건별 중앙값을 먼저 구하고, 그 중앙값들의 표준편차("사건별 중앙값 편차")를 따로 낸다.** 회차 간 변동은 기존 "징역 표준편차 · IQR"이 보여주고, "사건이 바뀌어도 이 모델이 비슷한 수준으로 선고하는가"는 이 값이 따로 보여준다. 모델이 한 사건에만 등장하면(비교 대상이 없어) 계산하지 않는다(`None`).

## 선택한 방법과 이유

### 1. 위치 인자를 `nargs="+"`로 바꿔 1개/여러 개로 모드를 나눔 (대안 B)

`len(args.batch_dir) == 1`이면 기존 코드 경로(요소 일관성 · 법원 비교 · 사건 하나의 비교표)를 그대로 타고, 2개 이상이면 새 `aggregate()` 경로를 탄다. `--case` · `--court`는 사건마다 다른 값이라 여러 사건 합산과 함께 쓸 수 없게 `CompareError`로 막았다.

### 2. 요소 일관성 · 전체 다수 의견 칸은 집계표에서 뺌 (대안 B)

대신 집계표 머리말에 "사건별 비교표를 따로 보라"는 안내를 넣었다(`render_markdown_aggregate`).

### 3. 징역 최소·중앙값·최대에 표준편차·IQR을 추가 (완료 조건의 "형량 산포")

`statistics.pstdev`(모집단 표준편차)와 사분위수(`statistics.quantiles(..., method="inclusive")`)로 Q3-Q1을 계산한다. 값이 2개 미만이면 퍼진 정도를 말할 수 없어 `None`으로 둔다(기존 `consistency()`가 회차 2개 미만일 때 `None`을 주는 것과 같은 규칙). 이 칸은 **사건 1개짜리 비교표에도** 넣었다 — 한 사건 안에서도 "같은 모델이 회차마다 들쭉날쭉한지"는 의미 있는 정보이기 때문이다.

### 4. "사건별 중앙값 편차" 지표 추가 (대안 B)

사건마다 해당 모델의 징역 중앙값을 구한 뒤, 그 중앙값들의 모집단 표준편차를 낸다. 값이 작을수록 "이 모델은 사건 난이도가 달라져도 비슷한 수준으로 선고한다"는 뜻이다.

## 고려한 제약 사항

- **기존 단일 사건 비교표의 출력·CLI를 바꾸지 않음**: `compare.py <폴더 1개>`의 동작·칸 구성(새로 추가한 징역 표준편차·IQR 2칸 제외)은 그대로다. 기존 테스트(`test_compare_summary`)가 그대로 통과한다.
- **표준 라이브러리만 사용**: `statistics` 모듈만으로 계산한다(이 폴더의 "설치 없이 실행" 원칙).
- **권고 범위 판정은 사건마다 자신의 `recommended` 값을 쓴다**: 집계표의 "권고 범위 안" 칸은 사건마다 다른 권고 범위로 판정한 횟수를 단순 합산한 값이다. 사건 중 하나도 `recommended`가 없으면 그 모델 행은 `None`이다.

## 추후 재검토가 필요하면

- 지금은 "사건별 중앙값 편차" 하나만 추가했다. COMMON-40 진행 중에 다른 산포 지표(예: 사건별 IQR의 평균)가 더 필요해지면 그때 추가한다.

## 2차 (PR #174 리뷰 반영)

### 문제 / 배경

CodeRabbit과 peanutboi710의 리뷰에서 세 가지를 지적했다 (1 · 3번은 둘 다, 2번은 peanutboi710).

1. 같은 사건의 결과 폴더를 실수로 두 번 주면(`compare.py out/runs/case-run1 out/runs/case-run2`, 둘 다 같은 사건) `aggregate()`가 이를 서로 다른 사건 2개로 세어, `crossCaseMedianStdev`에 같은 사건의 형량이 중복 반영된다. 추가한 CLI 테스트(`test_aggregate_cli_combines_batches`)도 실제로 같은 사건으로 만든 두 폴더를 썼다.
2. 집계표의 `징역 표준편차 · IQR`을 모든 사건의 형량을 한 덩어리로 모아 계산하고 있어서, "검토한 대안" 3-A에서 스스로 기각한 방식(사건 간 난이도 차이와 회차 간 변동이 뒤섞임)과 같은 문제가 있었다. "같은 모델이 매번 비슷한 형량을 내는지(안정성)"를 본다는 설명과 실제 계산이 맞지 않았다.
3. 여러 폴더 경로(`_case_from_records`)는 `recommended`(권고 범위)를 돌려주지 않아, 집계표의 "권고 범위 안" 칸이 여러 사건 모드에서는 항상 `None`이 되는데도 표에는 그대로 칸이 남아 있었다.

### 검토한 대안 및 선택 (1번 — 중복 사건)

- **대안 A — 중복 사건을 하나로 병합해서 집계한다.** 어느 폴더의 실행을 "대표"로 할지, 중복된 사건의 가중치를 어떻게 둘지 등 규칙이 더 필요해 복잡도에 비해 얻는 게 적다.
- **대안 B(선택) — 같은 `caseTitle`의 폴더가 두 번째로 들어오면 `CompareError`로 막는다.** "폴더마다 다른 사건이어야 한다"는 이 기능의 전제를 어긴 사용 실수이므로, 조용히 보정하기보다 바로 알려주는 쪽이 안전하다. `main()`에서 `batch.json`의 `caseTitle`을 모아 집합으로 중복 검사한다.
- 기존 CLI 테스트(`test_aggregate_cli_combines_batches`)는 같은 사건을 두 번 쓰고 있었으므로, 서로 다른 사건(제목만 바꾼 복사본)을 쓰도록 수정하고, 중복 사건을 거부하는지 확인하는 테스트(`test_aggregate_cli_rejects_duplicate_case`)를 추가했다.

### 검토한 대안 및 선택 (2번 — 징역 표준편차 · IQR)

- **대안 A — 집계표에서 두 칸을 빼고 `사건별 중앙값 편차`만 남긴다.** 가장 단순하지만, "같은 사건 안에서 회차마다 들쭉날쭉한지"를 보여주는 정보 자체는 여전히 유용해서 아예 없애기는 아깝다.
- **대안 B(선택) — 사건마다 따로 표준편차 · IQR을 구한 뒤 평균을 낸다("사건 내 평균").** 사건 간 난이도 차이는 더 이상 섞이지 않고, "회차 간 변동이 평균적으로 얼마나 큰가"라는 원래 의도가 유지된다. 열 이름에 "(사건 내 평균)"을 붙이고, 머리말에도 사건 간 차이가 아니라는 점을 명시했다.
- `aggregate()`의 사건별 루프에서 `case_prison`으로 사건별 `_stdev` · `_iqr`을 구해 모은 뒤, 모델 행에는 그 평균(`_mean`)을 넣는 식으로 고쳤다.

### 선택한 방법과 이유 (3번 — 권고 범위)

- **계산 자체를 고치지는 않되(데이터가 없어 불가능), 집계표(Markdown · CSV)에서 "권고 범위 안" 칸을 뺀다(peanutboi710 제안 c).** `recommended`는 `--case` 입력 파일에만 있고, `generate.py`가 만드는 `batch.json`·실행 기록 어디에도 저장되지 않는다. 즉 여러 폴더 경로에서 `_case_from_records`를 아무리 고쳐도 결과 폴더만으로는 권고 범위를 복원할 **데이터 자체가 없다**. 이를 고치려면 `generate.py`가 `batch.json`에 `recommended`를 함께 저장하도록 실행 기록 포맷을 바꿔야 하는데, 이는 별도 범위의 변경이라 이번 PR에서는 하지 않는다.
- 대신 `AGGREGATE_COLUMNS`에서 `inRecommended`를 빼서, 항상 비어 있을 칸을 표에 보여주지 않게 했다. `aggregate()`가 돌려주는 행(dict)에는 `recommended`가 있는 `case`를 직접 넘겨 호출하는 코드(테스트 등)를 위해 `inRecommended` 값 자체는 남겨 뒀다.
- 이 제한은 애초에 `_case_from_records`의 독스트링("권고 범위 칸은 사건 파일이 있어야 계산하므로 비어 있게 된다")에 이미 적혀 있던 것으로, 여러 사건 집계에서도 같은 제한이 그대로 이어진 것뿐이며 이번에 새로 생긴 버그는 아니다.

### 추후 재검토가 필요하면

- 여러 사건 집계에서도 "권고 범위 안" 칸을 쓰고 싶어지면, `generate.py`의 `batch.json`에 `recommended`를 저장하도록 포맷을 확장하는 별도 이슈로 진행한다.
