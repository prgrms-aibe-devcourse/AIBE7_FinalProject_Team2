# COMMON-17 의사결정 기록

> 근거: Jira COMMON-17(운영 DB 실제 사건 시드 적용 방식), [`deploy/README.md`](../../deploy/README.md) "운영 데이터", 10/19 운영 적용 · 10/20 미포함 검증.

## 문제 / 배경
- 운영(Docker 이미지)은 스키마만 넣는다. 실제 사건 시드는 비공개 저장소(`backend/private-seed` 서브모듈)에 있고 jar · 이미지에 들어가지 않아, 이대로면 운영 사건 목록이 0건이다.
- 사용자는 DB 데이터를 API로 볼 뿐이라 비공개 저장소 권한은 **시드를 넣는 쪽(운영 서버)만** 있으면 된다.
- 파이프라인(BE-31)으로 추가되는 사건은 `seed/`가 아니라 `loads/`(Flyway 밖, 한 번 실행하는 파일)로 남는다. 후검수 뒤 공개 · 승인 상태는 DB에만 있어 백업 정책도 함께 정해야 한다(Jira 코멘트, 10/07).

## 검토한 대안
- **대안 A — 수동 1회 실행**: 권한 있는 사람이 로컬에서 운영 DB를 대상으로 `FLYWAY_LOCATIONS=…,filesystem:./private-seed/seed`를 한 번 실행. 운영 DB를 밖으로 열어야 하고(지금은 컨테이너 내부 전용), 실행한 사람 · 시점이 남지 않는다.
- **대안 B — CI/CD에서 체크아웃 후 Flyway 실행**: Actions가 서브모듈 토큰으로 받아 운영 DB에 적용. IAM 권한이 없어 Actions가 서버 · DB에 들어갈 경로가 없다(BE-60과 같은 제약). 비공개 데이터가 Actions 러너를 거친다.
- **대안 C — 이미지에 포함**: 비공개 데이터가 이미지 레지스트리에 섞인다. 비권장(Jira 본문).
- **대안 D — 서버에 비공개 저장소 사본을 두고 컨테이너에 읽기 전용으로 붙임(BE-58의 `docker-compose.real-seed.yml`)**: 백엔드 기동 시 Flyway가 `filesystem:/real-seed`를 함께 읽는다.

## 선택한 방법과 이유
- **D.** 운영 DB를 밖으로 열지 않고, 비공개 데이터가 서버 밖(이미지 · CI)으로 나가지 않는다. 자동 배포(BE-60)도 `.env`의 `REAL_SEED_DIR`를 보고 같은 덧붙임 파일을 쓰므로 배포 경로가 하나로 유지된다.
- **서버 권한은 Deploy key(읽기 전용, 저장소 하나)**: 개인 PAT는 사람 계정의 권한 범위 · 만료에 묶이고, 쓰기 권한이 생길 수 있다. Deploy key는 그 저장소 읽기만 되고 만료가 없다. 개인키는 서버에만 둔다.
- **`seed/`만 sparse checkout**: 서버에 필요한 건 적재 SQL뿐이다. 원본 판결문(`source/`) · 작업 파일(`work/`)은 운영 서버에 둘 이유가 없어 받지 않는다. `loads/`는 실행할 때만 `git sparse-checkout add loads`로 더한다.
- **비공개 저장소 변경은 자동 반영하지 않는다(서버에서 `git pull`)**: `cd-agent.sh`에 `pull`을 넣으면 검토 전 시드가 바로 운영 기동에 들어간다. 시드 SQL 오류는 백엔드 기동 실패로 이어지는데, 자동 되돌림은 이미지만 바꾸므로 같은 시드로 다시 실패한다. 사건 추가는 드물어 사람이 확인하고 받는 비용이 작다.
- **`loads/`는 컨테이너 안 `psql`로 실행**: 운영 DB 포트를 열지 않고, 접속 정보는 컨테이너 환경변수를 쓴다. 파일 자체가 재실행에 안전하다(같은 제목 사건 · 같은 `runKey` 건너뜀).
- **백업**: 매일 `deploy/backup-db.sh`를 서버 cron으로 실행해 7일 보관 + 시드 갱신 · `loads/` 실행 · 위험한 마이그레이션 직전 수동 백업(같은 스크립트, 작업 이름을 붙여서). 스크립트는 임시 파일에 덤프한 뒤 `pg_dump` 성공 · `pg_restore --list` 확인을 모두 통과할 때만 최종 이름으로 옮겨, 실패한 덤프가 백업처럼 남지 않게 한다. 복구는 `--single-transaction --exit-on-error`로 한 트랜잭션에서 한다. RDS 전환(7.1.2, 10/28) 뒤에는 RDS 자동 백업(7일)으로 바꾼다.
- **수동 작업 중 자동 배포 타이머**: 손으로 backend를 다시 만드는 동안은 타이머를 멈추되, 서브셸 `trap`으로 어떻게 끝나든(실패 · Ctrl+C · SSH 끊김) 다시 켠다. 켜는 걸 빼먹으면 이후 `main` 머지가 조용히 배포되지 않는다(PR #199 리뷰).

## 적용 · 확인 결과
- 10/19 운영 적용: 실제 사건 1건 · 판례 53건(R__40) · 양형기준 237건(R__41), Flyway 6개 적용 약 1초 · 백엔드 기동 31초. https에서 체험 시작 ~ 세 판결 비교(API 2 ~ 14)까지 확인.
- 10/20 비공개 시드 미포함 검증(운영 이미지 `sha-468bafe`):
  - 공개 저장소: `backend/private-seed`는 서브모듈 포인터(커밋)만, 파일 0개
  - 이미지 빌드: `backend/.dockerignore`가 `private-seed/`를 빌드 컨텍스트에서 제외, Dockerfile은 `src` · Gradle 파일만 복사
  - 이미지 파일 시스템: 실제 사건 · RAG 시드 파일, `private-seed` 폴더 없음
  - jar: 반복 마이그레이션(`R__`)은 공개 시드 `db/migration/R__personality_content.sql` · `db/seed/R__seed_sample_case.sql`(개발용 가상 사건, 운영 `FLYWAY_LOCATIONS`에 없어 읽히지 않음) 두 개뿐이고, `private-seed` 경로는 없다
- 실제 사건 적재 전, 운영 검증용으로 넣었던 가상 사건과 시험 기록은 백업 후 지웠다(사건 번호가 1부터 다시 시작).

## 고려한 제약 사항
- IAM 권한 없음 → Actions의 서버 · DB 접속, S3 백업 불가.
- 백업이 같은 서버 디스크에 있어 서버 자체 유실에는 대비하지 못한다. RDS 전환으로 해결한다.
- 시드는 "같은 제목이면 건너뛰기"라 기존 사건 수정은 `UPDATE` 문이 필요하다(비공개 저장소 README).

## 추후 재검토가 필요하면
- 7.1.2 RDS 전환 때: Flyway 대상만 RDS로 바뀌고 시드 경로 · 방식은 그대로. 백업은 RDS 자동 백업으로 옮기고 서버 cron은 끈다.
- 사건 추가가 잦아지면 `cd-agent.sh`에 "비공개 저장소 새 커밋 확인 → 알림만" 정도를 검토한다(자동 적용은 위 이유로 하지 않음).
