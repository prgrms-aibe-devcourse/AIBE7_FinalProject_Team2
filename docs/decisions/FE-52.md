# FE-52 의사결정 기록

## 문제 / 배경
- 공통 헤더 맨 오른쪽 로그인(FE-50에서 준비 중으로 둠)을 실제 화면과 이어야 했다: 로그아웃이면 "로그인", 로그인하면 닉네임, 닉네임을 누르면 마이페이지.
- 사용자 로그인 API가 없다. IA의 S-12는 "이후" 단계이고 카카오 로그인은 검토 중이다(tech-stack v1.11). MVP는 로그인 없이 끝까지 체험할 수 있어야 한다(REQ-003).
- 공통 헤더는 화면이 그릴 때 동기적으로 만들어진다(`renderSiteHeader({ navigate })`, api를 받지 않음).

## 검토한 대안
- 로그인 화면 형태: 카카오 버튼만(IA 방향) / 아이디 · 비밀번호 폼 / 둘 다 → **둘 다**(사용자 결정). 방식이 정해지면 하나를 지운다.
- 로그인 상태를 확인할 방법: 개발용 목업 로그인 / 상태 구조만 두고 항상 로그아웃 → **목업 로그인**(사용자 결정). 로그인 · 닉네임 · 마이페이지 이동을 지금 눈으로 확인할 수 있다.
- 헤더가 로그인 상태를 읽는 곳:
  - 헤더가 api로 세션을 물어보기: 헤더를 그리는 모든 화면이 기다리거나, 그린 뒤 다시 바꿔야 해서 "로그인 → 닉네임"이 깜빡인다.
  - **브라우저 저장소의 닉네임 표시값**(`utils/session.js`): 헤더가 바로 그린다. 로그인 · 로그아웃은 api가 하고, 성공하면 화면이 표시값을 적고 지운다. 실제 로그인이 생기면 서버 세션이 진짜 상태이고 이곳은 표시용으로 남는다(만료 확인은 그때 추가).

## 선택한 방법과 이유
- `mocks/authMockApi.js`의 `login({ method, id, password })` · `logout()`을 목 api에 합쳤다. 어떤 값이든 로그인되고 닉네임은 아이디의 @ 앞부분(최대 12자), 카카오는 고정 닉네임. **비밀번호는 저장 · 전송하지 않는다.** 실제 모드에는 함수가 없어 화면이 "준비 중"을 안내한다 — 목 전용 동작이 실제 배포에 섞이지 않는다.
- 목 모드 화면에는 "개발용 목업 로그인" 안내를 붙여 실제 로그인으로 오해하지 않게 했다.
- 로그인 성공 → 메인으로 이동(기록 바꿔치기, 뒤로 가기로 로그인 화면에 돌아오지 않음). 로그아웃은 마이페이지 맨 아래와, 로그인 상태로 `/login`에 왔을 때 둔다(헤더의 로그인 자리는 닉네임 → 마이페이지 한 가지로 둔다).
- 마이페이지 기록은 아직 익명 ID 기준이라, 로그인 상태에서도 "기록은 이 브라우저 기준"이라고 그대로 밝혔다.

## 고려한 제약 사항
- FE-50(#176)에서 헤더 메뉴가 다섯 개로 늘어 390px 폭에서 글자가 한 자씩 줄바꿈되며 깨졌다. 로그인 자리를 메뉴 밖으로 빼고, 720px 이하에서는 두 줄(윗줄 로고 · 로그인, 아랫줄 메뉴, 넘치면 가로 스크롤)로 바꿨다. 성향 검사는 헤더가 `fixed`라 모바일 위 여백을 112px로 늘렸다.
- 색은 토큰만: 카카오 버튼 색(카카오 디자인 가이드)을 팔레트 · 역할 토큰으로 추가했다(`--color-kakao` · `--color-on-kakao`).

## 추후 재검토가 필요하면
- 실제 로그인 방식이 정해지면 폼 · 카카오 중 하나를 지우고, 카카오는 리다이렉트 흐름으로 버튼 동작을 바꾼다. 회원가입(`/signup`)도 그때.
- 로그인과 익명 기록 잇기(REQ-066 · 067, `anonymous_user.member_id`)는 백엔드 작업과 함께.
