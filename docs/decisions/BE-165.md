# BE-165 의사결정 기록

## 문제 / 배경
- 사건 등록(A-14) 중 extract · court 검사가 실패하면 재시도를 다 써도 등록이 멈춘다. 원문 인용 대조 · 상세 주소 규칙의 오탐이 주원인이다.
- 검사 규칙 자체를 고치는 일은 BE-164에서 따로 한다. 이 이슈는 그 사이에도(또 앞으로 다른 오탐이 생겨도) 관리자가 직접 검수해 등록을 끝낼 수 있는 길을 만든다.

## 검토한 대안
- **대안 A: 검사 끄기 플래그 (모든 오류 무시)**: 가장 단순하다. 하지만 주민등록번호 · 전화번호 같은 개인정보가 DB까지 들어가고, 길이 · 스키마 오류는 낮춰도 적재에서 다시 실패한다.
- **대안 B: 낮출 오류를 막을 목록(차단 목록)으로 정하기**: 목록에 없는 오류는 모두 낮춘다. 새 검사가 생기면 자동으로 낮춰져서, 개인정보 검사를 늘려도 특별 모드에서 그냥 통과될 수 있다.
- **대안 C: 낮출 오류를 허용 목록으로 정하기 (선택)**: 허용 목록에 있는 오류만 낮춘다. 새 검사는 기본으로 막힌다.
- 관리자 표시: 새 DB 칸 · 새 화면을 두는 방법과, 이미 관리자 화면이 보여 주는 `ai_generation.generation_report.validationWarnings`에 얹는 방법을 비교했다.
- 공개 차단: "경고 확인" 상태를 새로 두는 방법과, 지금의 비공개 적재 → 관리자 승인 흐름을 그대로 쓰는 방법을 비교했다.

## 선택한 방법과 이유
- **허용 목록(대안 C), 모드 두 개**:
  - `format`(B): 원문 인용 대조("원문에서 찾을 수 없음"만) · 상세 주소(행정구역)를 낮춘다. 정확한 날짜 · 정확한 나이는 court에서만 낮춘다.
  - `all`(A): `format`에 평가 표현 · 재판부가 고려한 판단 요소 없음을 더한다.
  - 해송님 결정: A에도 개인정보 최소선(마스킹 표시 · 주민등록번호 · 이메일 · 전화번호 · 계좌번호 · 사건번호 · 법원명)을 둔다.
  - DB 길이 상한 · 스키마 · 판단 요소 번호 오류는 낮춰도 적재가 실패하므로 낮추지 않는다. 실제 선고 형량 노출도 낮추지 않는다. AI 입력이 오염되기 때문이다.
- **분류는 `check_draft` · `process_output` 바깥에서 한다(`special_mode.split_errors`)**: 검사 함수는 BE-164가 같은 시기에 고친다. 검사 쪽을 건드리지 않아 충돌을 줄인다. 오류 메시지 문구(`위치: 규칙`)로 분류하므로, 메시지 문구를 바꾸면 `tests/test_special_mode.py`가 깨지도록 했다.
- **court는 낮출 수 있는 초안이 나와도 재시도를 끝까지 한다**: 통과하는 초안이 나오면 그것을 쓴다. 모두 실패할 때만 후보를 쓰고, 낮춘 오류가 가장 적은 후보(같으면 더 나중)를 고른다. 재시도 중 호출이 실패해도 보관한 후보를 버리지 않는다(과부하 · 한도는 BE-45의 다음 모델 전환을 그대로 둔다). 호출 비용보다 검수 부담을 줄이는 쪽을 택했다.
- **인용 대조는 "찾을 수 없음"만 낮춘다 (PR 리뷰 반영)**: 같은 오류 문구(`원문 인용이 아닙니다 — …`)에 지어낸 인용을 막는 사유(원문 그대로인 부분이 너무 적음 · `⟦ ⟧` 안 길이 · 짝)도 들어 있어서, 문구 전체를 낮추면 지어낸 문장이 "판결문 발췌"로 적재될 수 있다. 사유까지 맞춰 분류한다.
- **동 · 호수 주소는 따로 막는다 (PR 리뷰 반영)**: 검사 규칙 `상세 주소`가 행정구역과 `101동 202호`를 한 이름으로 묶고 있어서, 낮추면 동 · 호수까지 통과했다. 규칙을 `상세 주소`(행정구역)와 `동 · 호수 주소`로 나눠 앞의 것만 낮춘다.
- **표시는 기존 칸에 얹는다**: 낮춘 오류는 `[특별 모드] 위치: 규칙`으로 `generation_report.validationWarnings` 맨 앞에 넣는다. 관리자 화면이 이미 이 칸을 보여 주므로 화면 수정 없이 보인다. 단계별 원본 표시는 `generation_report.specialMode`에 남긴다. 오프라인 적재(`pipeline.py build_generation_report`)와 서버 적재(`CaseImportLoader`)가 같은 모양이다.
- **공개 차단은 사건의 확인 상태로 한다 (PR 리뷰 반영, 해송님 결정 (가))**: 판결 승인만으로는 extract(사건 본문)에서 낮춘 경고를 봤다는 보장이 없다. 그래서 `legal_case.special_mode_review`(PENDING → CONFIRMED, V51)를 두고, PENDING이면 공개 조건 `SPECIAL_MODE_UNREVIEWED`로 막는다. 관리자가 A-13-22로 확인하면 풀리고 확인자 · 시각 · 감사 로그가 남는다. 특별 모드가 아닌 사건은 NULL이라 영향이 없다.

- **날짜 · 나이는 court에서만 낮춘다 (해송님 결정)**: court 근거는 원문 그대로 인용해야 해서 모델이 피하기 어렵고 실패가 반복된 곳이다. extract는 사용자에게 보이는 사건 본문이라 정확한 날짜 · 나이가 남으면 식별 위험이 커서 어느 모드든 막는다. 분류는 `split_errors(errors, mode, stage)`의 단계 인자로 한다.

- **과부하 · 한도에서는 후보를 버리고 다음 모델로 넘어간다 (PR 리뷰 확인)**: BE-45의 모델 전환을 그대로 둔다. 다음 모델이 처음부터 다시 요청해 더 나은 초안을 만들 수 있기 때문이다. 대신 모든 모델이 막히면 앞 모델에서 보관했던 후보 없이 등록이 실패한다 — 한도 소진은 재시도로 풀리므로 후보를 억지로 쓰지 않는다.
- **오프라인 적재(`pipeline.py` load)도 같은 공개 차단을 건다 (PR 리뷰 반영)**: 낮춘 경고가 있으면 사건 SQL 뒤에 `UPDATE legal_case SET special_mode_review='PENDING' …`(확인된 CONFIRMED는 되돌리지 않음)을 붙인다. 새 사건 · 이미 있던 DRAFT · `load.case=false` 모두 같은 한 문장으로 덮는다. 표시는 단계를 돌린 결과 또는 건너뛴 단계의 `inputs` 파일(`report.json` · `court_draft.json`)에서 읽는다.

## 고려한 제약 사항
- 운영 등록은 백엔드 → 파이프라인 서비스(`service/jobs.py`) → 결과를 서버가 적재하는 경로다. 그래서 요청 필드(A-14 `specialMode`)부터 서비스 설정, 적재 기록까지 한 줄로 이어야 했다.
- 서비스는 파이프라인 모듈을 불러오지 않는다. 그래서 모드 목록을 따로 들고, 테스트로 같은지 확인한다(`CRIME_TYPES`와 같은 방식).
- 낮춘 오류 메시지에는 위치와 규칙만 있고 원본 값은 없다(`residual_check` 원칙).

## 추후 재검토가 필요하면
- 관리자 화면에서 특별 모드 등록을 켜는 입력(A-14 화면), "특별 모드" 배지, "경고 확인" 버튼은 이번에 넣지 않았다(FE 이슈로 뺀다). 확인 버튼이 생기기 전에는 API(A-13-22)로 확인하며, 공개 불가 사유는 기존 `publishReadiness.reasons`에 보인다.
- BE-164가 머지되어 오탐이 줄면 `format` 허용 목록을 다시 본다.
