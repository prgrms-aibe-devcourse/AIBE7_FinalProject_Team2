# BE-97 의사결정 기록

> 확장 단계 · 담당 김현중 (B) · 관련: FE-68, BE-96

## 문제 / 배경
- 마이페이지 프로필 수치의 "출석 일수"는 서버 기록이 없어 프론트 목 값(12일)으로 보여 준다(`frontend/src/pages/myPage/myPage.js`의 `MOCK_PROFILE` · `statsOf`).
- FE-68 도전과제 중 3개(3일 · 7일 · 30일 출석)가 출석 일수로 판정된다. BE-96(서버 측 도전과제 판정)도 이 값을 쓴다.
- 지금 마이페이지 응답(P-5, `MyPageResponse`)에는 `profile` 필드가 없다. 이번에 `profile.attendanceDays`를 새로 더한다.

## 검토한 대안

### 1. 하루를 나누는 기준
- 대안 A: 서버 기본 시간대(UTC). 한국 시각 오전 9시에 날짜가 바뀌어 사용자 감각과 다르다.
- **대안 B(선택): 한국 시간(`Asia/Seoul`) 기준, 하루 시작 시각을 설정값으로 둔다.** 기본은 자정(0시). 마이페이지 응답도 이미 KST를 쓴다.

### 2. 무엇을 하면 출석인가
- 대안 A: 마이페이지 조회(`GET /my-page`)에서 기록한다. 조회 API가 쓰기까지 하게 되고, 마이페이지에 들어가지 않는 사용자는 출석이 잡히지 않는다.
- **대안 B(선택): 출석 API(`POST /attendance`)를 따로 두고, 프론트가 사이트 진입 시 한 번 부른다.** 목적이 분명하고 어느 화면으로 들어와도 출석이 잡힌다. 같은 날 여러 번 불러도 1일이다.
- 대안 C: 사건 체험 시작 시 기록한다. 체험하는 사용자만 출석으로 친다.

### 3. 익명 ID 쿠키가 없는 방문자
- 대안 A: 출석 API에서 익명 ID를 새로 발급한다(P-2처럼). 아무것도 하지 않은 방문자 · 검색 로봇까지 익명 사용자가 생긴다.
- **대안 B(선택): 쿠키가 있을 때만 기록한다.** 쿠키는 성향 테스트 · 체험 시작 때 발급된다. 아무것도 하지 않고 떠난 날은 출석에서 빠지는 것을 감수한다.
  - (BE-98 보완) 쿠키를 새로 발급하는 순간에도 그날 출석을 남긴다. 아래 "2차" 참고.

### 4. 저장 방식
- 대안 A: 익명 사용자에 출석 일수 · 마지막 출석일 칸을 둔다. 칸 두 개로 끝나지만, 연속 출석 계산이나 회원 이관 때 날짜 기록이 없어 다시 만들어야 한다.
- **대안 B(선택): 출석한 날짜를 한 줄씩 저장한다(`attendance`).** 줄 수가 출석 일수다. 날짜가 남아 연속 출석을 나중에 계산할 수 있다.

## 선택한 방법과 이유
- **테이블 `attendance`(V22)**: `anonymous_user_id`(FK) · `attended_on`(date) · `created_at`. 기본 키 `(anonymous_user_id, attended_on)`로 하루 한 줄만 들어간다. 테이블 추가뿐이라 BE-60 규칙("main으로 가는 마이그레이션은 추가만")에 맞는다. V20은 비워 두기로 한 번호(BE-92)라 쓰지 않는다.
- **출석 날짜 계산**: `attended_on = (지금 시각을 설정 시간대로 바꾼 값 − 하루 시작 시각).날짜`.
  - 설정: `attendance.zone`(기본 `Asia/Seoul`) · `attendance.day-start-hour`(기본 `0`, 0 ~ 23).
  - 예: 시작 시각이 4시이면 10/22 03:00 접속은 10/21 출석, 10/22 05:00 접속은 10/22 출석이다.
- **출석 API `POST /attendance`**: 쿠키가 있으면 오늘 날짜로 한 줄 넣고(이미 있으면 그대로), 없으면 아무것도 하지 않는다. 둘 다 `204`. 같은 날 여러 번 불러도 결과가 같다(멱등).
- **출석 일수**: P-5 응답에 `profile.attendanceDays`(누적 출석 일수, 정수)를 더한다. 쿠키가 없거나 기록이 없으면 `0`. 프론트는 값이 오면 목 값 대신 쓴다.
- **로그인 이관 방안**: 데이터를 옮기지 않는다. 로그인으로 익명 ID가 회원에 연결되면(`anonymous_user.member_id`), 그 회원에 연결된 익명 ID들의 출석 날짜를 **중복 없이** 센다(같은 날 두 기기에서 출석해도 1일). 계산은 로그인 연동(BE-62 이후) 때 붙인다.

## 고려한 제약 사항
- **하루 시작 시각을 바꾸면** 이미 저장된 날짜는 그대로이고, 그 뒤 기록부터 새 기준이 적용된다. 바꾸는 그날만 경계가 어긋나 최대 하루가 덜 · 더 잡힐 수 있다. 운영 중에는 자주 바꾸지 않는다.
- **출석은 "사이트에 들어온 날"이다.** 프론트가 진입 시 부르지 않으면 기록되지 않는다. 호출 위치는 FE와 맞춘다.
- 동시에 두 번 불려도 기본 키 충돌은 무시한다(`ON CONFLICT DO NOTHING`), 오류로 내지 않는다.
- 익명 ID는 기기 · 브라우저마다 따로라, 로그인 전에는 기기마다 출석이 따로 센다.

## 추후 재검토가 필요하면
- 연속 출석 도전과제가 생기면 `attendance` 날짜로 계산을 더한다(테이블 변경 없음).
- 출석을 "사이트 진입"이 아닌 다른 행동(체험 시작 등)으로 바꾸려면 출석 API를 부르는 위치만 바꾼다.

## 2차 (BE-98 — 익명 ID 발급 시 출석 기록)

### 문제 / 배경
- FE-71(PR #233) 리뷰에서 첫 방문날 출석이 빠지는 것을 확인했다. 앱 시작 때 부르는 출석 API는 쿠키가 생기기 전이라 기록되지 않고, 같은 방문에서 체험 시작(API 2) · 성향 테스트 제출(P-2) · 꾸미기 저장(P-7)으로 쿠키가 생겨도 출석 호출은 이미 지나간 뒤다. 쿠키가 `HttpOnly`라 프론트는 발급 여부를 알 수 없다.

### 검토한 대안
- 대안 A: 프론트가 쿠키를 만드는 요청 뒤에 출석 API를 한 번 더 부른다. FE-71이 임시로 넣었지만, 요청이 늘 때마다 프론트가 챙겨야 한다.
- **대안 B(선택): 서버가 익명 ID를 새로 발급할 때(`AnonymousUserService.getOrIssue`) 그날 출석도 함께 남긴다.** 발급은 세 요청 모두 이 한 곳을 지나고, 사용자가 실제로 행동했을 때만 일어나 1차의 "봇 · 아무것도 안 한 방문자는 기록하지 않는다"는 원칙이 유지된다.

### 선택한 방법과 이유
- 날짜 계산 · 한 줄 기록을 `AttendanceRecorder`로 떼어 출석 API(`AttendanceService`)와 발급(`AnonymousUserService`)이 함께 쓴다. 출석 서비스가 이미 익명 사용자 서비스를 쓰고 있어, 반대로 부르면 순환 의존이 생기기 때문이다. 날짜 기준도 한 곳에만 있다.
- 발급은 `saveAndFlush`로 익명 사용자 행을 먼저 DB에 내보낸 뒤 출석을 넣는다(출석은 직접 쓴 SQL이라 외래 키가 가리킬 행이 먼저 있어야 한다). 같은 트랜잭션이라 요청이 실패해 롤백되면 출석도 함께 취소된다.
- 기존 사용자(쿠키 있음)의 동작은 바뀌지 않는다. 같은 날 다시 출석해도 기본 키로 하루다.
- 프론트의 임시 보정(쿠키를 만드는 요청 뒤 출석 재호출)은 이 변경이 머지된 뒤 걷어낸다(프론트 후속).
