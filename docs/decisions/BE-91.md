# BE-91 의사결정 기록

## 문제 / 배경

BE-89(Cloudflare Workers AI 사건 사진 생성 연동)에서 저장(S3 등 스토리지)·DB 기록·컨트롤러를 "스토리지·스키마 결정이 끝난 뒤 후속 이슈에서 진행한다"며 범위에서 뺐다(`docs/decisions/BE-89.md`). BE-91은 그 후속으로, 생성된 사진을 실제로 저장하고 관리자가 쓸 수 있는 API까지 만드는 작업이다. 스토리지는 AWS S3로 정했다(팀 확인).

## 검토한 대안

### 1. 사건 대표사진(신문용)을 어떻게 저장할까

- **대안 A — `LegalCase`에 전용 컬럼을 새로 추가한다.** 생성 프롬프트·모델 등 생성 이력을 남기기 좋지만, 이미 "사건 카드 이미지"로 쓰이는 `thumbnail_url`과 의미가 겹쳐 같은 개념을 두 칸에 나눠 관리하게 된다.
- **대안 B(선택) — 기존 `legal_case.thumbnail_url`을 그대로 쓴다.** 이 컬럼은 이미 "없으면 범죄 유형별 기본 이미지" 규칙으로 쓰이고 있고, 관리자 A-11 수정 API로 이미 자유롭게 바꿀 수 있는 칸이다. AI로 생성한 URL이든 관리자가 수동으로 붙인 URL이든 "사건 대표 이미지"라는 같은 역할이라, 새 컬럼을 만들 이유가 없다고 판단했다.

### 2. 사건 발단 사진(여러 장)을 어떻게 저장할까

- **대안 A — `legal_case`에 jsonb 배열 컬럼을 추가한다.** 테이블을 늘리지 않아도 되지만, 기존 `case_section`·`penalty_rule`·`factor`·`case_source`가 전부 "사건과 1:N인 개념은 별도 테이블"로 되어 있는 것과 어긋나고, 사진 한 장 단위로 조회·삭제·순서 변경을 하기 어렵다.
- **대안 B(선택) — `case_incident_photo` 전용 테이블.** `case_source` 등과 같은 패턴(FK + 식별자 PK)으로 사건마다 여러 행을 둔다. `(case_id, display_order)` 유니크로 순서를 보장한다(V7의 `factor` 패턴과 동일).

### 3. 생성 이력(프롬프트·모델)을 남길까

- **대안 A — 남기지 않는다.** 스키마가 더 단순해진다.
- **대안 B(선택) — `case_incident_photo`에 `prompt`·`model` 컬럼을 둔다.** AI가 생성한 사진이라 "왜 이 사진이 나왔는지"를 관리자가 검수 과정에서 확인할 수 있어야 한다고 판단했다(COMMON-40에서도 모델 비교 결과를 의사결정 기록으로 남긴 것과 같은 맥락). 대표사진(`thumbnail_url`)에는 이 이력을 붙이지 않았다 — 관리자가 수동으로 바꿀 수도 있는 범용 칸이라 생성 이력 전제가 맞지 않는다.

### 4. S3 연동 방식

- **대안 A — AWS SDK v2(`S3Client`)를 직접 쓴다.** 더 세밀한 제어가 가능하지만 멀티파트 업로드·에러 처리를 직접 짜야 한다.
- **대안 B(선택) — Spring Cloud AWS의 `S3Template`.** 참고 프로젝트(`imagegen`)가 이미 이 방식을 쓰고 있고, 업로드 한 줄로 끝나 보일러플레이트가 적다. 버전은 참고 프로젝트가 쓴 `4.1.0`을 그대로 가져왔다(Spring Boot 4.1.x와 맞춘 조합을 이미 확인한 값이라 재검증 없이 재사용).
- 자격 증명은 코드·설정 파일에 두지 않고 Spring Cloud AWS 기본 체인(운영 EC2는 인스턴스 프로필/IAM 역할, 로컬은 `AWS_ACCESS_KEY_ID`·`AWS_SECRET_ACCESS_KEY` 환경변수)을 그대로 쓴다 — RAG(Gemini API 키)·Cloudflare(계정 ID·토큰)와 달리 버킷 이름만 애플리케이션 설정(`case-storage.bucket`)으로 받는다.

### 5. 동기 vs 비동기 호출, 그리고 사건 행 잠금

- **대안 A — 비동기(작업 생성 → 상태 폴링).** A-14/A-15(사건 등록, 초안)가 이미 이 패턴(202 + 폴링)을 쓰고 있어 일관성이 있다.
- **대안 B(선택, 지금은) — 동기 호출.** Cloudflare 생성(수십 초) + S3 업로드 정도는 관리자 화면에서 로딩 상태로 기다릴 수 있는 범위라고 보고, 폴링 인프라(작업 테이블·상태 전이)를 새로 만들지 않았다. A-14/A-15처럼 호출이 길어지거나 여러 단계로 늘어나면 그때 비동기로 바꾼다.
- 동기로 가면서 생긴 부수 효과: `AdminCasePhotoService`가 A-11·A-13과 같은 패턴(사건 행 `SELECT ... FOR UPDATE` 잠금 → 확인 → 변경 → 저장)을 그대로 따르다 보니, **Cloudflare 호출·S3 업로드가 끝날 때까지 그 사건 행 잠금이 걸려 있다.** 잠금을 짧게 유지하려면(생성은 잠금 밖에서 먼저 끝내고 저장만 별도 트랜잭션으로) 영속화 로직을 다른 빈으로 분리해야 하는데(같은 클래스 안에서 `@Transactional` 메서드를 호출하면 프록시를 안 거쳐 트랜잭션이 안 걸리는 Spring 자기호출 문제), 이 작업은 **관리자 전용 · 저빈도(사건마다 몇 번) 호출**이라 그 정도 복잡도를 들일 이득이 적다고 보고 지금은 잠금이 오래 걸리는 쪽을 그대로 받아들였다.

## 선택한 방법과 이유

- 대표사진: 기존 `legal_case.thumbnail_url` 재사용(새 컬럼 없음).
- 발단 사진: `case_incident_photo` 신설(case_id FK, image_url, s3_key, caption, prompt, model, display_order, created_at). 유니크 `(case_id, display_order)`.
- S3 업로드: Spring Cloud AWS `S3Template`(`io.awspring.cloud:spring-cloud-aws-starter-s3:4.1.0`), 버킷 없으면 저장 기능만 꺼지고 서버는 정상 기동(기존 RAG·Cloudflare와 같은 원칙).
- API는 기존 관리자 검수 흐름(`admin.review` 패키지)에 자연스럽게 얹었다: `AdminCasePhotoController`/`AdminCasePhotoService`가 A-11·A-13과 같은 방식(사건 행 잠금 → 공개 여부 확인 → 변경 → 감사 로그)을 따른다. 번호는 A-16 ~ A-41이 8-4(운영 메뉴 API 초안)에 이미 예약돼 있어, A-13에 딸린 추가 API라는 뜻으로 A-13-1 ~ A-13-3을 썼다(`docs/api-specification.md` v0.37).
- Cloudflare 호출 → S3 업로드(`CaseImageGenerationService`) → DB 저장(`AdminCasePhotoService`)을 한 트랜잭션으로 묶었다. 그 결과 사건 행 잠금이 생성·업로드가 끝날 때까지 걸려 있는데, 이 트레이드오프는 의도적으로 받아들였다(5절 참고).

## 고려한 제약 사항

- 저장 실패(S3는 성공했는데 DB 트랜잭션이 실패하는 경우)에서는 S3에 고아 객체가 남을 수 있다. 재생성하면 새 키로 다시 올라가므로 서비스에는 지장이 없지만, 고아 객체 정리(수명 주기 정책 등)는 이번 범위에 넣지 않았다.
- `caseSummary`/`incidentDescription`은 관리자가 영문으로 직접 입력해야 한다. 한글 사건 개요(`overview`)에서 자동 번역하는 기능은 넣지 않았다(번역 LLM 호출이 추가되어 범위가 커진다고 판단) — 관리자가 비식별화한 영문 요약을 직접 짓는 전제다.
- 동기 호출이라 Cloudflare 응답이 느리면(최대 60초, `cloudflare.imagegen.timeout`) 관리자 화면이 그만큼 기다려야 한다. Nginx·브라우저 타임아웃 설정이 이보다 짧으면 504가 날 수 있다 — 운영 반영 시 확인이 필요하다.

## 추후 재검토가 필요하면

- 호출이 자주 느려지거나 실패율이 높으면 A-14/A-15처럼 비동기(작업 생성 + 폴링) 패턴으로 바꾸는 것을 검토한다.
- `caseSummary`/`incidentDescription` 영문 작성 부담이 크면, 한글 입력 → 번역(또는 한글 프롬프트 지원 모델)으로 바꾸는 것을 검토한다.
- S3 고아 객체 정리(Lifecycle 규칙 등)는 운영 비용이 쌓이면 다시 본다.
- `CaseImagePromptBuilder`의 스타일 문구(얼굴 없는 회색 엑스트라 묘사)는 실제 생성 결과를 보고 다듬어야 한다(BE-89 문서와 동일한 재검토 항목).

## 재검토 (PR #202 리뷰 중 — Cloudflare 직접 생성 포기)

실제로 Cloudflare Workers AI(`flux-1-schnell`)를 호출해 대표사진을 생성해 보니, 그림 품질이 사건 내용을
반영하지 못할 정도로 기대에 못 미쳤다(팀 확인, 실제 호출 테스트 결과). 그래서 "AI가 이미지를 직접
만든다"는 COMMON-41의 핵심 결정 자체를 다시 뒤집었다.

### 6. 사진을 누가 만들까 (재검토)

- **대안 A(기존) — Cloudflare Workers AI가 직접 생성.** 위 테스트에서 품질 미달로 기각.
- **대안 B — 더 나은 이미지 생성 모델로 교체.** Cloudflare Workers AI 안에 다른 모델(`stable-diffusion-xl` 등)이 있지만, 비교 검증(COMMON-40처럼 여러 모델 테스트)에 시간이 들고, 외부 이미지 생성 모델 전반의 품질이 "사건 내용을 반영한 삽화"라는 요구 수준에 못 미칠 수 있다는 근본 우려가 남는다.
- **대안 C(선택) — 사람이 사진을 만들어 업로드한다.** 2026-10-16 COMMON-41 회의에서 원래 검토했던 "AI는 프롬프트만 제공" 방향(v5.13)으로 돌아가되, 이번엔 실제 업로드 기능까지 함께 만든다. AI(Gemini)는 사건 내용을 바탕으로 사람이 참고할 **한글** 프롬프트를 지어줄 뿐, 이미지 자체는 만들지 않는다.

### 7. 프롬프트 언어 — 영문 vs 한글

- BE-89 때는 Cloudflare Workers AI 모델이 영어 캡션 위주로 학습되어 있다고 보고 영문 프롬프트(관리자가 직접 작성)로 설계했다.
- 이번에는 **AI가 참고용 프롬프트 문구만 지어주고, 실제 그림은 사람(또는 사람이 고르는 외부 도구)이 그린다.** 그 사람이 한글 환경에서 작업하는 게 자연스러우므로, 프롬프트도 한글로 짓는다 — 어떤 이미지 생성 도구를 쓰든 결국 사람이 보고 다시 가공할 문구이지, 모델에 그대로 넣는 입력이 아니기 때문에 언어 제약에서 자유롭다.

### 8. 프롬프트 재료 — 관리자 수동 입력 vs 사건 내용 자동 반영

- **대안 A(BE-89 · 기존 BE-91) — 관리자가 매번 영문 설명을 직접 짓는다.** 테스트해 보니 사건과 무관한 일반적인 문장을 넣기 쉬워서(실제로 그렇게 테스트했다가 "사건 발단이 전혀 안 들어간다"는 문제가 나왔다), 매번 양질의 설명을 새로 쓰는 부담이 실제로 드러났다.
- **대안 B(선택) — 사건의 `overview`(개요) · `factor`(판단 요소) · `chargeName`(죄명)을 서버가 모아 Gemini에게 넘기고, Gemini가 자연스러운 한글 프롬프트 문단을 짓는다.** 관리자는 입력 없이 버튼만 눌러도 되고(발단 사진은 선택적으로 `hint`로 특정 장면을 짚을 수 있다), 매번 사건 내용이 실제로 반영된다.

### 9. 업로드 스토리지 — COMMON-47과의 정합

- BE-91 1차 작업 때는 Spring Cloud AWS `S3Template`(`case-storage.*` 커스텀 설정)로 직접 구성했다.
- 그 사이 COMMON-47(S3 업로드용 multipart 상한 · `cloud.aws.*` 설정, PR #204)이 develop에 먼저 머지되어, 팀이 이미 **AWS SDK v2 직접 사용 + `cloud.aws.region`/`cloud.aws.s3.bucket`/`cloud.aws.s3.dir-prefix`** 구성으로 합의해 둔 상태였다. 이 재검토에서 BE-91의 스토리지 계층을 그 합의에 맞춰 `com.team2.project.common.storage`(공용 `FileStorage`/`S3FileStorage`)로 다시 짰다 — 기능별로 S3 설정을 따로 두면 나중에 다른 기능(게시글 첨부 등)이 똑같은 걸 또 만들게 된다.

### 선택한 방법 (재검토 반영)

- `CaseImageGenClient`/`CloudflareCaseImageGenClient`/`CaseImagePromptBuilder`(BE-89)와 `CaseImageStorage`/`S3CaseImageStorage`(BE-91 1차)를 모두 제거했다.
- 프롬프트 추천: `CasePhotoPromptClient`/`GeminiCasePhotoPromptClient` — Gemini `generateContent`로 사건 내용을 반영한 한글 프롬프트 문단을 짓는다. 등장인물(얼굴 없는 회색 엑스트라, 내로 · 남불 미등장) 규칙은 지시문에 고정으로 포함한다.
- 업로드: `com.team2.project.common.storage`(`FileStorage`/`S3FileStorage`, COMMON-47 설정 재사용) — 관리자가 올린 파일을 그대로 저장한다.
- `case_incident_photo.model`(생성 모델) 컬럼은 더 이상 자동으로 알 수 없어 뺐다(V20). `prompt`는 관리자가 참고용으로 남기는 선택 항목이 되어 NOT NULL을 뗐다.
- API: A-13-1 · A-13-2(프롬프트 추천, 각각 대표사진 · 발단사진) · A-13-3 · A-13-4(파일 업로드, multipart) · A-13-5(발단 사진 목록)로 나눴다(`docs/api-specification.md` v0.36).

### 재검토에서 남긴 제약

- Gemini 프롬프트 추천도 외부 LLM 호출이라, 실패하면 관리자가 수동으로 프롬프트를 지어 업로드하는 경로는 막혀 있지 않다(추천은 참고용, 업로드 API의 `prompt` 필드는 완전히 선택).
- 사진 자체의 품질 · 저작권(외부 생성 도구 이용약관, 혹은 관리자가 직접 그린 그림)은 이 결정 범위 밖이다 — 운영 전에 팀 확인이 필요하다.
