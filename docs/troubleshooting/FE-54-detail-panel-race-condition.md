# FE-54 회고 · 트러블슈팅: 관리자 상세 보기의 늦은 응답 덮어쓰기

> 관련: [#182](https://github.com/prgrms-aibe-devcourse/AIBE7_FinalProject_Team2/pull/182), [FE-54 의사결정 기록](../decisions/FE-54.md)
> 이 문서는 "왜 Redis · 메시지 큐가 아니라 요청 번호(seq)였는가"를 포함해, 동시성 문제를 **어디서 일어나는지부터 구분**하는 법을 정리한다.

## 1. 현상

관리자 회원 관리 · 게시글 관리에서 목록의 항목을 누르면 아래에 상세가 열린다. 항목 A를 누른 직후 항목 B를 빠르게 누르면, **늦게 도착한 A의 응답이 B의 상세를 덮어써서** 화면에는 A가 보인다.

```
시간 →
클릭 A ─ 요청 A ──────────────(느림)──────────── 응답 A 도착 → A를 그림 (잘못됨)
클릭 B ─ 요청 B ─ 응답 B 도착 → B를 그림
```

화면 제목은 A인데 마지막으로 누른 건 B다. 이 상태에서 "정지하기" 같은 버튼을 누르면 의도하지 않은 대상에게 조치가 갈 수 있어, 관리자 화면에서는 실제 피해로 이어질 수 있다.

## 2. 원인

- 서버는 잘못이 없다. 요청 A에는 A를, 요청 B에는 B를 정확히 돌려줬다.
- 비동기 응답은 **요청한 순서대로 도착한다는 보장이 없는데**, 기존 `showDetail`은 응답이 도착하면 "아직 필요한 응답인지" 확인하지 않고 그대로 그렸다(클라이언트 측 race condition).
- 목록 로더(`createLoader`)에는 이미 `seq` 방식의 방어가 있었지만, 상세 보기에는 없었다.
- 회원 관리 · 게시글 관리 두 화면에 같은 코드가 복사되어 있어 문제도 두 곳에 있었다.

## 3. 동시성 문제는 일어나는 곳이 다르다

| | 이번 문제 | Redis · RabbitMQ · DB 락이 푸는 문제 |
|---|---|---|
| 어디서 | 브라우저 한 개 안 | 서버 · DB |
| 누가 겹치나 | 한 사람이 보낸 요청 둘의 **응답 도착 순서** | 여러 사람(또는 여러 서버)이 **같은 데이터를 동시에 수정** |
| 망가지는 것 | 화면에 보이는 데이터 | DB에 저장되는 값 |
| 예 | A 클릭 → B 클릭 → 늦은 A 응답이 B 화면을 덮음 | 관리자 둘이 같은 사건을 동시에 공개 · 승인 |

Redis · 큐는 서버에서 동작하므로, 브라우저에서 응답이 어떤 순서로 도착하는지는 건드릴 수 없다. **서버 쪽 도구로는 풀리지 않는 문제**라서 후보에서 제외했다.

## 4. 해결 방법 비교 (브라우저 쪽)

| 방법 | 동작 | 장점 | 단점 |
|---|---|---|---|
| **요청 번호(seq)** ✅ 선택 | 요청마다 번호를 붙이고, 최신 번호가 아니면 응답을 버림 | 코드 몇 줄. 이미 `createLoader`가 쓰던 방식 | 요청은 끝까지 진행됨(네트워크 약간 낭비) |
| AbortController | 새 요청을 보낼 때 이전 요청을 실제로 취소 | 네트워크 낭비 없음 | `fetch`까지 `signal`을 넘기도록 API 레이어 수정 필요, 취소 오류 처리 필요 |
| 로딩 중 클릭 막기 | 응답이 올 때까지 다른 항목을 못 누르게 함 | 가장 단순 | 목록을 빠르게 훑어보기 어려워 답답함 |
| 응답 id 비교 | 응답의 id가 지금 열린 id와 같은지 확인 | 직관적 | 같은 항목을 두 번 열면 구분 못 함, 응답 모양마다 따로 처리 |
| TanStack Query · SWR | 요청 키별 캐시 · 최신 응답을 라이브러리가 관리 | 캐시 · 재시도까지 해결 | 프레임워크 없는 바닐라 JS 구조라 도입 비용이 큼 |

### seq를 고른 이유
1. 문제가 브라우저 안에서 생기므로 브라우저에서 고치는 것이 맞다.
2. 목록 로더에 이미 있는 패턴이라 팀이 새로 배울 것이 없다.
3. 이번 PR은 "동작 변경 없음"이 조건이었고, 가장 작은 변경으로 해결된다.
4. 상세 조회는 읽기(GET)라 요청이 끝까지 가도 부작용이 없어 실제 취소(Abort)가 꼭 필요하지 않다.

## 5. 해결

`frontend/src/pages/admin/adminKit.js`의 `detailPanel`이 요청마다 번호를 올리고, 응답이 도착했을 때 번호가 최신이 아니면 버린다.

```js
let seq = 0;
async function show(id) {
  const mine = ++seq;                        // 이번 요청 번호
  ...
  const data = await fetcher(id);
  if (!active() || mine !== seq) return;     // 그사이 더 새 요청이 있었으면 버림
  draw(data, node);
}
```

- `catch`에서도 같은 검사를 해서, 오래된 요청의 오류 문구나 로그아웃 처리가 최신 화면을 덮지 않게 했다.
- `active()`는 다른 페이지로 이동한 뒤 도착한 응답을 버리는 기존 검사다.
- 중복 코드를 `detailPanel` 한 곳에 모은 덕분에 회원 · 게시글 두 화면이 함께 고쳐졌다.

## 6. 검증

`frontend/src/pages/admin/adminKit.test.js`가 상황을 그대로 재현한다. 1번 요청의 응답을 일부러 붙잡아 두고, 2번을 먼저 완료시킨 뒤 1번을 풀어도 화면에 그려진 것은 2번뿐인지 확인한다.

## 7. 서버 쪽 동시성은 어떻게 되어 있나 (확인한 사실)

백엔드 코드를 확인한 결과는 다음과 같다.

| 상황 | 사용 중인 방법 | 위치 |
|---|---|---|
| 관리자 둘이 같은 사건 상태를 동시에 변경 | **비관적 락**(`PESSIMISTIC_WRITE`, `SELECT ... FOR UPDATE`) | `LegalCaseRepository.findByIdForUpdate` |
| 같은 사용자의 성향 재응시 동시 요청 | **비관적 락** | `AnonymousUserRepository.findByIdForUpdate` |

- 낙관적 락(`@Version`)은 쓰지 않는다.
- Redis는 **캐시(DB 0) · 토큰 저장소(DB 1)** 용도이고 락으로는 쓰지 않는다. RabbitMQ 같은 메시지 큐는 도입하지 않았다.
- 서버가 한 대이고 락 대상이 모두 DB 행이므로 DB 행 잠금으로 충분하다. Redis 분산 락은 서버가 여러 대로 늘어나 DB 밖의 자원을 함께 다룰 때 검토 대상이다.

### 서버 쪽 방법 한눈에 보기 (참고)

| 방법 | 동작 | 언제 쓰나 |
|---|---|---|
| 낙관적 락(`@Version`) | 수정 시 버전 번호를 비교해 그사이 바뀌었으면 실패 | 충돌이 드문 경우 |
| 비관적 락(`FOR UPDATE`) | 읽는 순간 행을 잠가 다른 요청을 기다리게 함 | 충돌이 잦고 순서가 중요한 경우 (현재 사용) |
| Redis 분산 락 | 서버 여러 대가 Redis에 "처리 중" 표시를 남김 | 서버가 여러 대일 때 |
| 메시지 큐(RabbitMQ · Kafka) | 요청을 줄 세워 순서대로 처리 | 트래픽 완충, 오래 걸리는 작업의 비동기 처리 |
| 멱등성 키 | 같은 요청이 두 번 와도 한 번만 처리 | 결제 · 중복 제출 방지 |

## 8. 한계와 남은 과제

- seq는 늦은 응답을 **그리지 않을 뿐 요청을 취소하지는 않는다.** 읽기(GET)에는 문제없지만, 같은 패턴을 쓰기 요청에 쓰면 서버에서는 요청이 그대로 실행된다. 쓰기 중복은 `runAction`의 버튼 `disabled`와 서버 쪽 락으로 막는다.
- 요청 자체를 끊어야 할 일이 생기면 `AbortController` 도입을 검토한다(예: 응답이 크거나 느린 조회).

## 9. 배운 점

- "동시성"이라는 말만 듣고 도구부터 고르지 않는다. **브라우저 · 서버 · DB 중 어디서 겹치는지**부터 구분한다.
- 서버 응답이 정확한데 화면이 틀리다면 클라이언트의 응답 처리 순서를 의심한다.
- 같은 코드가 여러 곳에 복사되어 있으면 버그도 함께 복사된다. 공통 헬퍼로 모으면 한 번에 고칠 수 있다.
