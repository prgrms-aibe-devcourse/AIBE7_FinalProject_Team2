## 2. 성향 테스트 채점

### 2-1. 축과 글자

| 축 (`axis`) | 엄격 쪽 | 관대 쪽 |
| --- | --- | --- |
| `APOLOGY_SINCERITY` 사과와 진정성 | E 행동증명형 | I 마음신뢰형 |
| `FAULT_STANDARD` 잘잘못의 기준 | S 결과중시형 | N 의도중시형 |
| `PRINCIPLE_RELATION` 원칙과 관계 | T 원칙형 | F 관계형 |
| `ORDER_OPPORTUNITY` 질서와 기회 | J 질서형 | P 기회형 |

"엄격 · 관대"는 관용 지수(FR-8-3)를 계산하기 위한 방향 이름일 뿐이다. 화면에는 쓰지 않고, 어느 쪽이 옳다는 뜻도 없다(FR-8-4).

### 2-2. 선택지 → 점수

문항은 상황 하나와 두 행동(A · B)을 보여 주고, 5칸 중 하나를 고르게 한다. 어느 쪽도 아니라고 느끼는 사용자에게 억지로 한쪽을 고르게 하는 것도 결과를 흐리므로 가운데 칸(보통)을 둔다(PR #109 리뷰).

| 칸 | 매우 A | 조금 A | 보통 | 조금 B | 매우 B |
| --- | --- | --- | --- | --- | --- |
| `personality_choice` | letter = A의 글자, score = 2 | A의 글자, 1 | letter = NULL, score = 0 | B의 글자, 1 | B의 글자, 2 |

- A · B 중 어느 쪽이 엄격 글자인지는 문항마다 섞는다. 같은 쪽만 계속 고르는 응답 습관이 한 글자로 몰리지 않게 하기 위해서다. 문항이 A · B를 보여 주는 형식이라 일반 성향 테스트의 역문항은 따로 두지 않는다.
- 선택지 문구는 칸마다 둘 수도 있고, 양 끝 두 문구만 두고 "매우 · 조금 · 보통"은 화면이 붙일 수도 있다. 문항 콘텐츠(7.6.1)에 맞춘다.

### 2-3. 축 점수와 글자

축마다 문항이 n개(3 ~ 4개, FR-8-2)일 때:

- L = 관대 글자로 받은 점수 합, S = 엄격 글자로 받은 점수 합 (보통은 0점이라 어느 쪽에도 더하지 않는다)
- **축 점수 = (L − S + 2n) ÷ 4n** → 0(모두 매우 엄격) ~ 1(모두 매우 관대), 0.5 = 균형
- 0.5보다 크면 관대 글자, 작으면 엄격 글자
- **정확히 0.5(L = S, 동점)면 관대 글자**

동점은 문항 수와 관계없이 L = S이면 난다(예: 3문항 매우 E + 조금 I + 조금 I → L = S = 2, 보통만 고른 경우 L = S = 0).

**동점 = 관대 글자로 정한 이유와 감수하는 점**

- 첫 문항 배치처럼 콘텐츠 순서에 결과가 좌우되지 않고, 테스트 · 체험 · 종합을 한 규칙으로 정리할 수 있다.
- 체험(3-3)의 동점을 "그때의 테스트 결과 글자"로 정하면, 같은 선택이라도 테스트 전에 한 체험과 후에 한 체험의 글자가 달라진다. 관대 글자로 고정하면 이 문제가 없다.
- **감수하는 편향**: 보통 칸이 있어 동점이 늘고, 동점이 모두 관대 쪽으로 가므로 관용 지수가 다소 관대 쪽으로 기운다. 보통만 고른 사용자는 INFP(관용 지수 4)가 된다. 4축 그래프에는 50 : 50으로 보이므로 사용자는 균형이었음을 알 수 있다. 관용 지수는 좋고 나쁨이 아니라는 안내(FR-8-4)도 그대로 둔다.

### 2-4. 계산 예시

| 축 | 4문항 답 | L | S | 축 점수 | 글자 |
| --- | --- | --- | --- | --- | --- |
| 사과와 진정성 | 매우 E · 조금 I · 보통 · 조금 I | 2 | 2 | (2 − 2 + 8) ÷ 16 = **0.5** | 동점 → 관대 → **I** |
| 잘잘못의 기준 | 매우 N · 조금 N · 조금 S · 매우 N | 5 | 1 | (5 − 1 + 8) ÷ 16 = **0.75** | **N** |
| 원칙과 관계 | 매우 T · 매우 T · 조금 F · 조금 T | 1 | 5 | (1 − 5 + 8) ÷ 16 = **0.25** | **T** |
| 질서와 기회 | 조금 P · 조금 P · 조금 J · 매우 P | 4 | 1 | (4 − 1 + 8) ÷ 16 = **0.6875** | **P** |

→ 유형 **INTP**, 관용 지수 **3**(I · N · P). 사과 축은 그래프에 "I 50% · E 50%"로 보인다. 그 밖의 축은 "N 75% · S 25%"처럼 축 점수를 백분율로 보여 준다.

### 2-5. 제출 검증 (7.6.4)

- 활성 문항(`is_active`)마다 답이 정확히 하나 있어야 한다. 빠지거나 겹치거나 모르는 문항이 있으면 400.
- 답은 5칸 `value`(0 매우 A · 1 조금 A · 2 보통 · 3 조금 B · 4 매우 B)로 받는다(API 명세 P-2). 서버가 그 문항의 `display_order = value + 1` 선택지로 바꿔 채점하고, 저장하는 답은 `{questionId, choiceId}`다. 0 ~ 4 정수가 아니면 400.
- 문항마다 선택지는 5개(매우 · 조금 · 보통 · 조금 · 매우)이고, 보통 1개 · 두 글자 쪽 각 2개(2점 · 1점)여야 한다. V15 CHECK(`chk_personality_choice_order_score`)가 한 칸씩, 시드 검증 테스트(`PersonalityContentSeedTest`)가 5칸이 다 있는지를 본다.
- 검증을 통과한 뒤에만 익명 ID를 발급한다(400이면 사용자 · 쿠키를 만들지 않는다).
- 활성 문항이 축마다 1개 이상이어야 계산할 수 있다. 콘텐츠 시드에서 축당 3 ~ 4개를 지킨다.

## 3. 판결 체험 → 성향

### 3-1. 쓰는 기록

| 조건 | 이유 |
| --- | --- |
| `judgment.subject_type = USER`, `timing = FINAL` | 사전 판단(`PRE`)은 방향이 없고, 성향은 최종 판단 기준이다(ERD 8장) |
| `judgment_factor.direction`이 `UP` 또는 `DOWN` | 행이 없는 요소는 "고려하지 않음"이라 세지 않는다 |
| `factor.value_axis`가 NULL이 아님 | NULL 요소는 성향 계산에서 빠진다(ERD 4장 · 8장) |
| `value_axis_status`는 따지지 않음 | `AUTO`도 쓴다. 관리자 확정을 기다리면 성향이 거의 계산되지 않는다. 대신 3-4처럼 저장 시점 값으로 고정한다 |
| `experience.attempt_no = 1`만 | 두 번째 체험부터는 실제 판결을 이미 알고 있어서 통계에서 빼는 규칙(ERD 결정 #5)과 같다. MVP는 항상 1이다 |

형량 선택은 쓰지 않는다(ERD v1.13).

### 3-2. 방향 → 글자

**감경(DOWN)으로 고른 요소는 그 축의 관대 글자, 가중(UP)으로 고른 요소는 엄격 글자로 센다.**

| 축 | 감경으로 고르면 | 가중으로 고르면 | 예 |
| --- | --- | --- | --- |
| 사과와 진정성 | I | E | 반성을 감경으로 → I |
| 잘잘못의 기준 | N | S | 결과의 중대성을 가중으로 → S |
| 원칙과 관계 | F | T | 합의 · 처벌불원을 감경으로 → F |
| 질서와 기회 | P | J | 전과를 가중으로 → J |

**한계.** 이 규칙은 "관대 = 감경"이라는 하나의 방향 규칙이라 요소의 뜻과 어긋나는 경우가 있다. 예를 들어 계획성을 가중으로 고르는 것은 "의도"를 본 판단인데 S(결과중시)로 셈해진다. 이런 요소가 많다고 확인되면 ERD 8장 방침대로 `factor` 옆에 요소별 글자 · 가중치 보조 테이블을 추가한다. 이번 단계에서는 만들지 않는다.

### 3-3. 체험별 축 점수

- **축 점수 = 감경 개수 ÷ (가중 개수 + 감경 개수)**
- 그 축에 해당하는 요소를 하나도 고르지 않았으면 `null`(자료 없음)
- 글자: 0.5보다 크면 관대, 작으면 엄격, **0.5면 관대**(2-3과 같은 규칙)
- 체험 유형 코드는 저장하지 않는다. 동점 규칙이 고정이라 개수만으로 언제나 같은 글자가 나오므로, 필요할 때 계산한다. 네 축 모두 값이 있을 때만 4글자 코드가 있다
- 저장하는 것은 축별 **감경 · 가중 개수**다(6장 `axis_counts`). 소수로 저장하면 1/3 같은 값이 잘려 종합 동점 판정이 흔들리고, 그렇다고 지금의 `factor` · `judgment_factor`로 다시 계산하면 3-4의 고정 저장이 깨진다

### 3-4. 저장 시점

체험이 **처음** `COMPLETED`가 될 때(API 13 비교 공개, `AI_REVEALED` → `COMPLETED`) 서버가 상태 변경과 **같은 트랜잭션**에서 개수를 세어 `experience_personality`에 저장한다(7.6.7).

- **이미 `COMPLETED`인 체험에 API 13이 다시 오면** 상태와 함께 기존 기록을 그대로 둔다(다시 세지 않는다). `experience_id` 유니크라 행이 둘 생기지 않는다.
- **구현 (v0.6, BE-64)**: `RevealService.revealComparison`이 상태 전이 결과(`TransitionResult.changed`)가 참일 때만 `ExperiencePersonalityRecorder`를 부른다. 첫 회차(`attempt_no = 1`)만 저장하고(3-1), 기록기는 `MANDATORY` 트랜잭션이라 단독으로 부를 수 없다. API 13 본문도 함께 고쳤다(API 명세 v0.34 — PR #109 리뷰에서 "7.6.7 PR에서 구현과 함께 고친다"로 미룬 항목).

- **고정 저장.** 나중에 관리자가 `value_axis`를 고쳐도 지난 체험의 성향은 바뀌지 않는다. 성향 변화 흐름이 저절로 바뀌면 사용자가 혼란스럽기 때문이다.
- 성향 테스트를 하기 전에 끝낸 체험도 저장한다(ERD 8장). 나중에 테스트를 하면 바로 종합 성향에 들어간다.
- 판단 요소를 하나도 고르지 않은 체험도 행은 남긴다(네 축 모두 `{"down": 0, "up": 0}` = 자료 없음).

### 3-5. 계산 예시

최종 판단에서 고른 요소:

| 요소 | `value_axis` | 방향 |
| --- | --- | --- |
| 반성 | 사과와 진정성 | 감경 |
| 계획성 | 잘잘못의 기준 | 가중 |
| 결과의 중대성 | 잘잘못의 기준 | 가중 |
| 합의 · 처벌불원 | 원칙과 관계 | 감경 |
| 피해 회복 | 원칙과 관계 | 감경 |
| 전과 | 질서와 기회 | 가중 |
| (축이 NULL인 요소) | NULL | 가중 → **제외** |

| 축 | 감경 | 가중 | 축 점수 | 글자 |
| --- | --- | --- | --- | --- |
| 사과와 진정성 | 1 | 0 | 1.0 | I |
| 잘잘못의 기준 | 0 | 2 | 0.0 | S |
| 원칙과 관계 | 2 | 0 | 1.0 | F |
| 질서와 기회 | 0 | 1 | 0.0 | J |

→ 이 체험의 4글자는 **ISFJ**(저장하지 않고 계산). 사건 하나에서는 요소가 적어 0과 1로 크게 튄다. 종합 성향(4장)에서 평균을 내면 고르게 된다.

## 4. 종합 성향

- **완료 순서로 최근 3건(각 사건의 첫 회차)의 축마다 체험별 축 점수 평균**(v0.8, 현재 판결 성향). 체험이 3건보다 적으면 있는 만큼으로 낸다. 전체 평균은 오래된 체험이 계속 같은 무게를 가져 "지금" 경향이 묻히므로 바꿨다. `null`인 체험은 그 축 평균에서 뺀다. 체험마다 같은 무게다(요소를 많이 고른 체험이 더 크게 반영되지 않게).
- 글자 · 동점 처리는 3-3과 같다(0.5면 관대).
- **네 축 모두 값이 있을 때만 종합 유형 코드를 보여 준다.** 값이 없는 축(그 축의 요소를 한 번도 고르지 않음)은 그래프에 "체험 자료 없음"으로 두고, 테스트 글자로 채우지 않는다. 채우면 종합에 테스트가 섞이고, 축 있는 요소를 고르지 않은 체험만 있으면 종합이 테스트 유형과 똑같아진다.
- 네 축이 모두 비었거나 완료한 체험이 없으면 "종합 없음"이다(5장 "체험 없이 테스트만"과 같은 처리).
- 테스트 점수는 평균에 넣지 않는다. FR-8-8이 종합 성향을 "체험 평균"으로 정했고, 테스트(일상 가치관)와 체험(판결)을 섞으면 두 성향을 비교하는 의미가 흐려진다(FR-8-7) ⚠️
- 관용 지수는 종합 유형 코드의 I · N · F · P 개수다(종합 유형이 있을 때만).
- **대표 캐릭터는 테스트 유형으로 고정한다.** 체험 1건이면 축 점수가 0과 1로 크게 튀어, 종합을 대표로 쓰면 사건 하나로 캐릭터가 바뀌고 공유한 S-16 결과와도 달라진다. 종합은 "판결에서는 ○○○○"처럼 테스트 유형과 나란히 비교로 보여 준다(FR-8-7 테스트 ↔ 판결 비교 취지).

**예시** (체험 3건)

| 축 | 체험 1 | 체험 2 | 체험 3 | 평균 | 글자 |
| --- | --- | --- | --- | --- | --- |
| 사과와 진정성 | 1.0 | 0.5 | null | 0.75 | I |
| 잘잘못의 기준 | 0.0 | 0.33 | 0.0 | 0.11 | S |
| 원칙과 관계 | 1.0 | 1.0 | 0.5 | 0.83 | F |
| 질서와 기회 | 0.0 | null | null | 0.0 | J |

→ 네 축 모두 값이 있으므로 종합 **ISFJ**, 관용 지수 2. 4축 그래프에는 "I 75% · E 25%"처럼 보여 준다. 만약 질서와 기회 축이 세 체험 모두 null이었다면 종합 유형은 없고, 세 축 그래프와 "질서와 기회: 체험 자료 없음"만 보여 준다.

종합 성향은 저장하지 않고 조회할 때 계산한다(체험이 많아야 수십 건이라 부담이 없다).

## 5. 재응시 · 테스트 없이 체험만 한 사용자

| 상황 | 처리 |
| --- | --- |
| 재응시 | 새 `personality_result` 행을 만들고 이전 행은 `is_current = false`. 이력은 지우지 않는다 |
| 테스트 없이 체험만 | 체험 성향은 저장한다. 마이페이지의 성향 영역은 테스트 권유로 채운다(user-flow 3장). 테스트를 하면 지난 체험이 바로 종합에 들어간다 |
| 체험 없이 테스트만 | 종합 성향은 없다("종합 없음"). 마이페이지는 테스트 결과만 보여 준다 |
| 체험 중(S-03 ~ S-07) | 성향 결과를 보여 주지 않는다(FR-8-5). 계산도 `COMPLETED` 뒤에만 한다 |

## 6. 저장 형식 (7.6.3 기준)

| 테이블 · 컬럼 | 값 |
| --- | --- |
| `personality_choice.axis` | 문항의 축을 복제한 값. (`question_id`, `axis`) → `personality_question`(`id`, `axis`) 복합 FK로 문항 축과 같음을 DB가 보장한다 |
| `personality_choice.letter` | 그 축의 두 글자 중 하나, 보통이면 NULL |
| `personality_choice.score` | 1 · 2(글자 있음), 0(보통) |
| `personality_result.axis_scores` | `{"APOLOGY_SINCERITY": 0.5, "FAULT_STANDARD": 0.75, "PRINCIPLE_RELATION": 0.25, "ORDER_OPPORTUNITY": 0.6875}` — 관대 쪽 비중 |
| `personality_result.type_code` | 4글자(축 점수에서 계산한 값과 같아야 한다). `personality_type` FK · 공유 조회용으로 저장한다 |
| `personality_result.answers` | `[{"questionId": 1, "choiceId": 3}, …]` |
| `experience_personality.axis_counts` | `{"APOLOGY_SINCERITY": {"down": 1, "up": 0}, "FAULT_STANDARD": {"down": 0, "up": 2}, …}` — 축마다 감경 · 가중 개수. 네 키를 모두 두고, 고른 요소가 없으면 `{"down": 0, "up": 0}`(= 자료 없음). 축 점수 = down ÷ (down + up) |

- 체험 성향은 개수만 저장하고 축 점수(0 ~ 1)는 조회할 때 계산한다. 테스트 결과의 `axis_scores`는 화면 표시용이고(3문항 축은 ÷ 12라 소수가 잘릴 수 있다), 글자는 제출 때 정수로 판정해 `type_code`에 저장하므로 다시 판정하지 않는다. 화면에는 정수 %로 반올림해 보여 준다.
- 4글자 순서는 축 순서(사과 · 잘잘못 · 원칙 · 질서) 그대로다.
- ERD 8장 제안의 `experience_personality.type_code`는 빼고 `axis_scores`는 `axis_counts`로 바꾸며, `personality_choice`에 `axis`를 더한다. ERD 반영은 7.6.3 마이그레이션에서 한다.

**선택지 글자 검사 (7.6.3 마이그레이션).** PostgreSQL CHECK는 다른 테이블을 참조할 수 없으므로 복합 FK로 축을 끌어와 같은 행 안에서 검사한다. 트리거 · 앱 검증보다 DB가 직접 막고, 시드를 잘못 넣어도 실패한다. CHECK는 결과가 NULL이면 통과시키므로 `letter IS NOT NULL` · `score NOT NULL`을 따로 적는다(`letter = NULL, score = 1` 같은 행 차단).

```sql
ALTER TABLE personality_question ADD CONSTRAINT uk_personality_question_id_axis UNIQUE (id, axis);

-- personality_choice
axis varchar(20) NOT NULL,
score smallint NOT NULL,
CONSTRAINT fk_personality_choice_question_axis
    FOREIGN KEY (question_id, axis) REFERENCES personality_question (id, axis),
CONSTRAINT chk_personality_choice_letter CHECK (
    (letter IS NULL AND score = 0)
    OR (letter IS NOT NULL AND score IN (1, 2) AND (
           (axis = 'APOLOGY_SINCERITY'  AND letter IN ('E', 'I'))
        OR (axis = 'FAULT_STANDARD'     AND letter IN ('S', 'N'))
        OR (axis = 'PRINCIPLE_RELATION' AND letter IN ('T', 'F'))
        OR (axis = 'ORDER_OPPORTUNITY'  AND letter IN ('J', 'P'))))
)
```

## 7. 구현 메모

```text
testScore(axis):
  n = 그 축 활성 문항 수
  L = Σ score (letter가 관대 글자인 답)
  S = Σ score (letter가 엄격 글자인 답)
  return (L - S + 2n) / (4n)

countAxis(experienceId, axis):          # COMPLETED 때 한 번만, axis_counts로 저장
  rows = USER · FINAL judgment_factor ⨝ factor
         where factor.value_axis = axis and direction in (UP, DOWN)
  return {down: count(DOWN), up: count(UP)}

experienceScore(counts):                 # 조회할 때 (저장한 개수로)
  if down + up = 0: return null
  return down / (down + up)

letter(axis, sign):            # sign = 아래 판정값의 부호
  sign >= 0 → 관대 글자 (0 = 동점 → 관대) / sign < 0 → 엄격 글자

판정값 (저장한 소수가 아니라 원래 개수로 계산):
  테스트: L - S
  체험:   감경 - 가중                        (= 2 × 감경 - 전체)
  종합:   Σ (downᵢ - upᵢ) / (downᵢ + upᵢ)    (저장한 axis_counts에서, 값이 있는 체험 i만, 정확한 분수)
```

- 축 · 글자 대응은 백엔드 enum 하나에 둔다(예: `ValueAxis.APOLOGY_SINCERITY(strict='E', lenient='I')`). `factor.value_axis`와 같은 키를 쓴다.
- 글자 판정은 저장한 소수(`axis_scores`)로 하지 않는다. 0.5 근처에서 실수 오차로 글자가 바뀌지 않도록 테스트 · 체험은 정수, 종합은 정확한 분수(공통 분모, `BigInteger` 또는 분자 · 분모 정수 쌍)로 부호만 본다. 종합의 판정값은 축 점수를 −1 ~ +1로 옮긴 값의 합과 같다(PR #109 리뷰 제안).
- 화면용 축 점수는 0 ~ 1(관대 쪽 비중)을 그대로 쓴다. 그대로 백분율이 되어 화면 변환이 없다.
