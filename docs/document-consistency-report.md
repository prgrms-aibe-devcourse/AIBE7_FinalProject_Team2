## 2. 🔴 높음

### C-01. API 응답 형식 — 성공 응답을 `data`로 감싸는가

| 문서 | 위치 | 내용 |
| --- | --- | --- |
| 기술 스택 | `tech-stack.md:144`, `:166`, `:219`, `:228` | "API 응답은 공통 형식(`code`, `message`, `data`)을 사용한다", 프론트 공통 함수는 "성공 → `data` 반환" |
| API 명세 | `api-specification.md:49` | "성공 응답은 결과 객체를 그대로 돌려준다(**감싸는 객체 없음**)". 에러는 `{ code, message, currentStatus, details }` |

- **문제**: 프론트는 `response.data`를 꺼내도록, 백엔드는 결과 객체를 그대로 내려주도록 구현하게 된다. 에러 형식도 기술 스택에는 `currentStatus`·`details`가 없어서, 화면 이동(`currentStatus`로 보낼 화면 결정, API 1-6)이 빠진다.
- **제안**: API 명세(v0.2)가 더 최신이고 상세하므로 **API 명세 기준으로 기술 스택 4장·5장을 고친다.** 반대로 감싸는 형식을 쓰기로 하면 API 명세 1-4와 모든 응답 예시를 고쳐야 한다. 어느 쪽이든 한 문서에만 정의하고 다른 문서는 참조만 하게 한다.

### C-02. 선고 가능 범위 밖 에러 코드 이름

| 문서 | 위치 | 코드 |
| --- | --- | --- |
| 기술 스택 | `tech-stack.md:170`, `:229` | `VERDICT_OUT_OF_RANGE` |
| API 명세 | `api-specification.md:77`, `:380` | `OUT_OF_ALLOWED_RANGE` (HTTP 422) |

- **문제**: 프론트는 기술 스택 예시대로 `VERDICT_OUT_OF_RANGE`에 경고 박스를 연결하게 되는데, 서버는 `OUT_OF_ALLOWED_RANGE`를 보낸다. S-06c 방어 로직이 동작하지 않는다.
- **제안**: 기술 스택의 예시 코드를 `OUT_OF_ALLOWED_RANGE`로 바꾸고, 에러 코드 목록은 API 명세 1-5만 기준으로 삼는다고 명시한다.

### C-03. API 경로 체계 — 체험 ID를 경로에 넣는가

| 문서 | 위치 | 내용 |

| 기술 스택 | `tech-stack.md:149-159` | `/api/v1/experiences/{id}/...` (체험 ID 기반). 경로 이름도 `reviews`(↔ `review-steps`), `complete`(↔ `comparison-reveal`)로 다름 |

- **문제**: 기술 스택에는 "예시이며, 최종 경로는 API 명세서에서 확정한다"는 단서가 있지만, 시퀀스 v0.3은 "API 명세서 v0.2와 맞춤"이라고 해 놓고도 체험 ID를 주고받는 흐름을 그대로 두었다. 문서를 보는 사람에 따라 체험 ID 기반으로 구현할 수 있다.
- **제안**: 시퀀스 3 ~ 6장의 "체험 ID"를 "사건 ID(+ 쿠키)"로 바꾸고, 기술 스택의 경로 예시는 지우거나 API 명세 경로로 맞춘다.

### C-04. 예시 사건의 경합범 가중과 선고 가능 상한 (120개월)

| 문서 | 위치 | 내용 |
| --- | --- | --- |
| 요구사항 | `requirements-specification.md:511` (15장 미정) | "같은 죄명을 여러 번 저지른 사건(동종 경합범, 예: 피해자 여러 명 반복 사기)… 경합범 가중(형법 제38조)을 적용하면 **예시 사건의 상한이 10년 → 15년**이 될 수 있음" |
| 기획서 | `final-planning.md:857` | 같은 내용을 추후 결정 사항으로 둠 |
| ERD | `erd.md:457-463` | 예시 `penalty_rule`에서 `PRISON allowed_max = 120`으로 확정 서술, "S-06c(12년 = 144개월)는 120을 넘으므로 확정 불가" |
| API 명세 | `api-specification.md:270`, `:329` | `allowedMax: 120`, "징역 1개월 ~ 10년" |
| IA / 와이어프레임 | IA `:239`, 와이어프레임 p.11 (S-06c) | 12년 입력 → "선고할 수 있는 범위를 벗어났습니다" 확정 불가 예시 |
| 기능 명세 / 요구사항 | `기능_명세서.md:173` (REQ-081), `requirements-specification.md:281` | 경합범은 **"여러 죄명이 결합된"** 사건만 MVP 제외 |

- **문제**: 대표 예시 사건(10개월간 37회, 피해자 37명)이 바로 요구사항이 미정으로 둔 "동종 경합범"에 해당한다. 경합범 가중을 적용하면 상한이 15년(180개월)이 되어, ERD 예시 데이터·API 예시·와이어프레임 S-06c의 "12년은 확정 불가" 시나리오가 법적으로 틀린 예시가 된다. 또 REQ-081의 제외 대상은 "여러 죄명" 결합뿐이라, 이 사건이 MVP 대상인지도 문서만으로 판단할 수 없다.
- **제안**: 대표 판례를 고르기 전에 ① 동종 경합범을 MVP에 넣을지 ② 넣는다면 `allowed_max` 산정에 경합범 가중을 포함할지 먼저 정한다. 정해진 뒤 ERD 6장 예시, API 6·8 예시, 와이어프레임 S-06c 예시 값을 함께 고친다. REQ-081 문구도 "이종 경합범"인지 "경합범 전체"인지 분명히 한다.

### C-06. AI 판결 생성 방식 (RAG / 퓨샷 / 오프라인 적재)

| 문서 | 위치 | 서술 |
| --- | --- | --- |
| 요구사항 | `requirements-specification.md:306` | MVP는 **오프라인에서 생성·검수한 결과를 적재**. 서비스 안 파이프라인은 확장 단계이며 **퓨샷 우선**, 필요할 때 RAG로 전환 |
| 기술 스택 | `tech-stack.md:256-259`, `:300` | "MVP에서는 **퓨샷 방식으로** 먼저 전체 흐름을 검증하고, RAG는 **이후** 단계" |
| 기획서 | `final-planning.md:437`, `:445`, `:458` | "유사 판례 및 양형기준 등 필요한 자료는 **RAG를 활용하여 검색**", 제목 "에이전틱 RAG 구조", Agent 2 활용 자료는 "판례 Vector Store"만 있음 |
| 기능 명세 | REQ-040 ~ 045 | 파이프라인은 **확장** 단계 |

- **문제**: 기획서는 RAG를 기본 방식처럼 서술하고 퓨샷 우선 결정이 빠져 있다. 기술 스택은 "MVP = 퓨샷"처럼 읽혀 "MVP = 오프라인 적재"와 맞지 않고, 단계 표현도 기능 명세서의 정의("이후" = 6주 이후)와 다르게 "(이후)"를 쓴다.
- **제안**: 요구사항 FR-4-2를 기준으로 삼는다. 기획서 6-4-3과 Agent 2 활용 자료에 "퓨샷 우선, 필요 시 RAG"를 반영하고, 기술 스택 6장은 "MVP: 오프라인 생성 결과 적재 / 확장: 퓨샷 파이프라인 / 필요 시: RAG(pgvector)"처럼 기능 명세서의 단계 용어로 고쳐 쓴다.

### C-07. ERD가 DB 확정(PostgreSQL)을 반영하지 않음

| 문서 | 위치 | 내용 |

| ERD | `erd.md:347` | "PostgreSQL은 부분 유니크 인덱스, **MySQL은 생성 컬럼 또는 서비스 로직**으로 구현" |

## 6. 권장 정리 순서

1. **구현 계약 먼저** (C-01 · C-02 · C-03 · C-09): API 명세를 기준 문서로 정하고, 기술 스택 4 · 5장과 시퀀스의 체험 ID 표현을 API 명세에 맞춘다. BE/FE 개발 착수 전에 끝내야 한다.

4. **와이어프레임 보정** (C-13 · C-14 · C-16 · C-27): 점선 표시와 데이터가 없는 요소를 정리한다.
5. **표기 · 참조 정리** (C-10 · C-11 · C-17 ~ C-26 · C-28 ~ C-30): 한 번에 묶어 문서 정리 PR로 처리한다.
